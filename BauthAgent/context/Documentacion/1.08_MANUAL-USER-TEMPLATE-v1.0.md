## 1. Audiencia, propósito y alcance

Este manual documenta el **usuario** en bAuth: la tabla `idn_user_template`, el contrato JSONB
v6.0 de 15 secciones, la asignación temporal de roles, el ciclo de vida
Joiner-Mover-Leaver (JML), la validación y las protecciones de PII.

**Audiencia:** desarrolladores bAuth, administradores de tenant (alta/baja de usuarios), RRHH
(dueños funcionales del ciclo de vida), auditores RGPD.

**Deslinde:** los ROLES que el usuario recibe viven en [MANUAL-ROLES](1.09_MANUAL-ROLES-v1.0.md);
sus ATRIBUTOS 1:N (emails, teléfonos, documentos) en [MANUAL-ATRIBUTOS](1.07_MANUAL-ATRIBUTOS-v1.0.md);
su SESIÓN en [MANUAL-CONTEXT-PLANE](1.11_MANUAL-CONTEXT-PLANE-v1.0.md); sus MÉTODOS de
autenticación en [MANUAL-AUTENTICACION](2.01_MANUAL-AUTENTICACION-v1.0.md).

> **Nota de soberanía (ADR-010):** el contrato v6.0 (jun-2026) es contemporáneo a la
> deprecación de Keycloak/Tryton y conserva lenguaje legacy ("sincroniza en KC", "SAM-128",
> columnas `kc_user_id`/`tryton_user_id`). Este manual presenta el flujo **soberano** vigente
> y marca lo legacy explícitamente (§11.4 incluye su saneamiento).

## 2. El principio absoluto — identidad vs autoridad

> **El UserTemplate es el contrato que define QUIÉN ES y QUÉ TIENE este usuario concreto.**
> Los permisos NO viven aquí — viven en el RolTemplate asignado.
> El UserTemplate define la identidad; el RolTemplate define la autoridad.

| Dimensión | UserTemplate | RolTemplate |
|-----------|--------------|-------------|
| Pregunta | ¿QUIÉN es este usuario? | ¿QUÉ puede hacer este tipo de rol? |
| Permisos | **Hereda** del RolTemplate | **Define** los permisos |
| Autenticación | Qué métodos TIENE enrolados | Qué métodos son REQUERIDOS |
| Horario | Excepciones individuales | El horario base del rol |
| Biometría | El hash del individuo (referencia) | La política de enrolamiento |
| Multiplicidad | 1 template → 1 usuario | 1 template → N usuarios |

Es la misma separación del token (MANUAL-TOKENS §9): la identidad viaja, la autoridad se
evalúa. Un usuario sin roles ES alguien — pero no PUEDE nada.

## 3. Las dos capas del usuario — tabla y contrato JSONB

### 3.1 La tabla `idn_user_template` (DDL verificado — 26 columnas)

```sql
CREATE TABLE bauth.idn_user_template (
    uuid              UUID PRIMARY KEY DEFAULT uuidv7(),  -- INMUTABLE de por vida
    external_id       TEXT,                    -- id del sistema de RRHH origen
    username          TEXT UNIQUE NOT NULL,    -- ^[a-z][a-z0-9._-]{2,64}$
    email             TEXT NOT NULL,
    -- El árbol D00 del usuario:
    tenant_id         TEXT NOT NULL,
    empresa_id        TEXT NOT NULL,
    sucursal_id       TEXT,
    pos_logico        TEXT,
    bos_contexts      TEXT[] DEFAULT '{}',     -- contextos autorizados
    context_actual    TEXT,                    -- el contexto activo
    -- Autoridad heredada:
    rol_ids           TEXT[] DEFAULT '{}',
    rol_bitmask_base64 TEXT NOT NULL DEFAULT '',  -- el BitMask efectivo precomputado
    -- Ciclo de vida:
    status            TEXT NOT NULL DEFAULT 'ACTIVE',
    termination_date  DATE,
    termination_reason TEXT,
    -- Legacy (ADR-010 — a revisar):
    sync_status       TEXT NOT NULL DEFAULT 'PENDING',
    kc_user_id        TEXT,                    -- ⚠️ legacy Keycloak
    tryton_user_id    INTEGER,                 -- ⚠️ legacy Tryton
    -- Actividad:
    last_login_at     TIMESTAMPTZ,
    last_activity_at  TIMESTAMPTZ,             -- alimenta detección de cuentas dormidas
    -- El contrato:
    template          JSONB NOT NULL DEFAULT '{}',
    template_version  TEXT NOT NULL DEFAULT '6.0',
    ctx_id            TEXT NOT NULL DEFAULT 'system',
    created_at / updated_at TIMESTAMPTZ
);
```

### 3.2 Qué vive en columna y qué en el JSONB

La regla de cardinalidad (compartida con MANUAL-ATRIBUTOS §7) decide el almacenamiento:

| El dato… | Vive en… | Ejemplos |
|-----------|----------|----------|
| Identifica o controla (1:1, consultado en caliente) | **Columna** | uuid, username, árbol D00, status, rol_bitmask_base64 |
| Describe al individuo (estructurado, contrato) | **JSONB `template`** | las 15 secciones §4 |
| Es 1:N o repetible | **`idn_identity_attribute`** | emails work/home, teléfonos, documentos, idiomas |
| Es autoridad | **NUNCA aquí** | permisos → RolTemplate |

## 4. Las 15 secciones del template

El validador (`usertemplate_validator.rs`, contrato `BAUTH-USERTEMPLATE-SECCIONES.md` v6.0)
verifica **15 secciones**:

| # | Sección | Qué contiene | Norma |
|---|---------|--------------|-------|
| 1 | `identity` | Identidad canónica: account_type (HUMAN/SERVICE/SYSTEM/GUEST), display name | SCIM §4.1 |
| 2 | `personal_info` | Datos personales: nacimiento, documento, contacto (los 1:N → `idn_identity_attribute`) | SCIM · RGPD Art. 4 |
| 3 | `professional` | Cargo, departamento, employee_type | SCIM Enterprise §4.3 |
| 4 | `roles` | Asignaciones activas y temporales (espejo de `idn_user_role`) | INCITS 359 |
| 5 | `keycloak_credentials` ⚠️ | Métodos enrolados, AAL alcanzable — **nombre legacy; contenido = credenciales bAuth nativas** | NIST 800-63B |
| 6 | `physical_credentials` | Tarjetas RFID, referencias biométricas (`ref://` — nunca el binario) | OSDP v2.2 |
| 7 | `device_registry` | Dispositivos vinculados (device binding) | NIST 800-63B §4 |
| 8 | `session_state` | Límites de sesión individuales (max_concurrent, ttl) | D8 |
| 9 | `location` | Perfil de ubicación por defecto | D6 |
| 10 | `temporal` | Horario y excepciones individuales | D4 |
| 11 | `network` | IPs permitidas, perfil VPN | D7 |
| 12 | `audit` | Nivel de auditoría individual | D11 |
| 13 | `external_services` | IdPs externos federados vinculados | OIDC |
| 14 | `compliance` | Consentimientos, certificaciones (con `blocking`) | RGPD Art. 7 · ISO 27701 |
| 15 | `lifecycle` | Estado, fechas, razón de terminación | ISO 24760 |

> **La cuenta de bloques:** el análisis de cobertura D00 habla de "16 bloques" porque cuenta
> además el bloque de sincronización/BitMask — que en la implementación vive en **columnas**
> (`rol_bitmask_base64`, `sync_status`), no en el JSONB. Las secciones validadas del JSONB
> son 15. Ambas cifras son correctas en su contexto.

### 4.1 Verificación contra las fuentes primarias (2026-07-11)

Las secciones de la tabla anterior **no son agrupaciones propias del proyecto — son las
secciones normadas de la industria de identidad**, verificadas contra las fuentes primarias:

- **Sección 3 (`professional`):** sus atributos son **literales de la SCIM Enterprise User
  Extension** (RFC 7643 §4.3): `employeeNumber`, `costCenter`, `organization`, `division`,
  `department`, `manager` — el esquema estándar con el que todo IGA/IdP del sector representa
  al empleado. Nada inventado.
- **Sección 5 (credenciales):** la distinción que este manual subraya — *lo que el usuario
  TIENE vs lo que el rol REQUIERE* — es la separación formal de NIST SP 800-63B: los
  autenticadores registrados (§5 del estándar) pertenecen al sujeto; el AAL exigido (§4)
  pertenece a la política del recurso (aquí: el B4 del RolTemplate, MANUAL-ROLES §2.5).
- **Sección 8 (`session_state`):** materializa la estructura exacta de gestión de sesiones de
  NIST 800-63B §7 — timeout total + timeout de inactividad + reautenticación según AAL.
- **La división identidad/autoridad** (este manual vs MANUAL-ROLES) corresponde a los conjuntos
  formales del estándar RBAC: `USERS` ↔ UserTemplate · `ROLES`+`PRMS` ↔ RolTemplate · `UA` ↔
  la asignación (§5) — ANSI INCITS 359.

**Consecuencia operativa:** cada cambio a una sección del UserTemplate toca una sección normada
— y esa sección determina su clasificación SemVer, su aprobación y su retención cuando el
UserTemplate se acoja al Motor de Versionado Universal (MANUAL-MOTOR-VERSIONADO 1.13, fase F5,
con anonimización RGPD Art. 17 sobre versiones históricas).

## 5. La asignación de roles — `idn_user_role`

La relación usuario↔rol es una tabla propia (T-171) con **vigencia temporal y revocación
auditada**:

```sql
CREATE TABLE bauth.idn_user_role (
    assignment_id  UUID PRIMARY KEY DEFAULT uuidv7(),
    user_uuid      UUID NOT NULL,
    role_id        TEXT NOT NULL REFERENCES idn_role_template(id) ON DELETE CASCADE,
    assigned_by    UUID,           -- quién asignó (SoD: no se auto-asigna)
    valid_from     TIMESTAMPTZ,    -- asignaciones futuras programables
    valid_until    TIMESTAMPTZ,    -- roles temporales que expiran solos
    is_active      BOOLEAN NOT NULL DEFAULT true,
    revoked_by     UUID, ...
);
```

**Las reglas del contrato v6.0:**
- **Un solo rol activo por defecto** — múltiples roles simultáneos requieren aprobación ARB.
- Toda asignación pasa el **SoD check** del tenant antes de persistir (la matriz de conflictos
  de MANUAL-ROLES).
- Las asignaciones temporales (`temporary_assignments`) se verifican contra el
  `delegation_config` del RolTemplate fuente — nadie delega lo que su rol no permite delegar
  (reducción AND de D10).

## 6. El RolBitMask del usuario

`rol_bitmask_base64` es **la autoridad efectiva precomputada**: el OR de los BitMask de todos
los roles activos del usuario, con herencia DAG resuelta (`compute_rol_bitmask` +
`inherit_from_parents` — MANUAL-ATOMOS §9.1).

```
Cambio de asignación (alta/baja/expiración de rol)
  → recálculo del RolBitMask → UPDATE columna + Redis
  → efecto INMEDIATO en el FastPath (<0.5ns por evaluación)
  → los tokens vigentes NO necesitan re-emitirse (los permisos no viajan en el token)
```

Esta es la razón arquitectónica de que el "Mover" del JML sea barato en bAuth: cambiar de
puesto es recalcular un vector de bits, no re-provisionar cuentas.

## 7. El ciclo de vida — Joiner · Mover · Leaver

### 7.1 Estados

```
PENDING ──activación──► ACTIVE ──suspensión──► SUSPENDED ──► ACTIVE
   │                       │
   └───────────────────────┴──terminación──► TERMINATED (retención RGPD/Ley 843)
```

### 7.2 JOINER — onboarding (flujo soberano, 5 pasos)

```
1. Alta: el admin (o el conector de RRHH vía biedata) crea el UserTemplate → PENDING
   → bAuth valida: RolTemplate existe y está ACTIVE · certificaciones bloqueantes al día
2. Validación del contrato: usertemplate_validator (15 secciones — §8)
3. Cómputo de autoridad: rol_ids → RolBitMask precomputado → Redis
4. Enrolamiento de credenciales: el usuario configura contraseña (Argon2id, política del
   tier) + el MFA que su RolTemplate exige (TOTP/WebAuthn nativos — MANUAL-AUTENTICACION)
5. ACTIVE: primer login → ctx_id promovido → JWT propio emitido
```

*(El flujo del SSOT v6.0 describía pasos de sincronización KC/Tryton — bajo ADR-010 la
autenticación y el enforcement son nativos; la "sincronización" sobrevive solo como prueba de
consistencia opcional.)*

### 7.3 MOVER — cambio de puesto/sucursal

```
RRHH actualiza (cargo, sucursal, rol) → validación SoD del nuevo conjunto
  → recálculo del RolBitMask → actualización del árbol D00 en columnas
  → reconcile propaga → auditoría del delta (qué ganó, qué perdió)
```

### 7.4 LEAVER — offboarding (el paso crítico)

```
1. RRHH marca la salida (OrangeHRM → biedata → bAuth)
2. bAuth revoca TODAS las sesiones activas — ctx.invalidate → tokens muertos en <30 s
3. Roles desactivados (idn_user_role.is_active=false, revoked_by registrado)
4. status=TERMINATED + termination_date + termination_reason
5. Retención de datos: RGPD Art. 17 + jurisdicción — Bolivia: 10 años (Ley 843)
   → pasado el plazo, purga (el uuid NUNCA se reutiliza)
```

## 8. La validación — schema y semántica

`usertemplate_validator.rs` aplica dos niveles (del contrato v6.0):

**Schema (estructura):**

| Campo | Regla | Error |
|-------|-------|-------|
| `uuid` | UUID válido y único | `DUPLICATE_UUID` |
| `username` | Único por tenant · `^[a-z][a-z0-9._-]{2,64}$` | `INVALID_USERNAME` |
| `account_type` | HUMAN·SERVICE·SYSTEM·GUEST | `INVALID_ACCOUNT_TYPE` |
| `roles[].role_id` | Existe y está ACTIVE | `ROLE_NOT_FOUND` |
| MFA enrolado | ≥1 factor cuando el rol exige LoA ≥ 2 | `MFA_NOT_CONFIGURED` |
| Certificaciones `blocking` | Todas CURRENT para HUMAN | `BLOCKING_CERT_MISSING` |

**Semántica (coherencia):**

| Regla | Qué impide |
|-------|-----------|
| Credential coverage | Activar un usuario que no cubre los métodos requeridos por su rol |
| Biometric consent | Registrar plantillas biométricas sin `consent_given=true` (RGPD Art. 9) |
| SoD check | Conjuntos de roles que violan la matriz de conflictos del tenant |
| Delegation valid | Asignaciones temporales que exceden el `delegation_config` del rol fuente |

## 9. PII y enmascaramiento

Los campos PII (RGPD) van **siempre enmascarados** en las respuestas API — solo roles con
`zone_logical/rrhh:READ` **+ LoA 3** ven el valor completo:

```
personal_info.basic.birth_date        → "****-**-**"
personal_info.basic.national_id       → "****5678Z"
physical_credentials.*.card_number    → "****4567"
personal_info.contact.phones.number   → "+591 7****5"
credenciales (hash de contraseña)     → [NEVER RETURNED]
biometric_templates.template_hash     → [NEVER RETURNED vía API]
```

El enmascaramiento se define por zona en `zone_data_policy` (D1 — con clasificación PII/PHI,
base legal y retención; la UI operativa lo administra: MANUAL-POLITICAS §10.3).

## 10. Los 6 invariantes de seguridad

1. **El biométrico crudo NUNCA entra al UserTemplate** — solo hashes/referencias (`ref://bionexus/...`).
2. **La contraseña NUNCA vive en el template** — vive en el credential store de bAuth
   (Argon2id por tier). *(El SSOT decía "en Keycloak (bcrypt)" — superado por ADR-010.)*
3. **El UUID es INMUTABLE** — sobrevive cambios de rol, empresa y hasta la terminación.
4. **Los permisos NUNCA viven en el UserTemplate** — siempre heredados del RolTemplate.
5. **Un solo rol activo por defecto** — multi-rol requiere aprobación ARB.
6. **Consentimiento biométrico EXPLÍCITO** — boolean + fecha, verificado por el validador.

## 11. Estado del arte — ciclo de vida de identidad 2026: lo que hay y lo que no hay

### 11.1 Lo que hay — inventario verificado

| Capacidad | Estado | Evidencia |
|-----------|:------:|-----------|
| Tabla `idn_user_template` (26 col., uuidv7, SCIM-aligned) | ✅ DDL | `sbos_00:3840` + 3 índices |
| Contrato JSONB v6.0 (15 secciones) | ✅ especificado | SSOT (1,153 líneas) |
| Validador de las 15 secciones | ✅ **implementado** | `usertemplate_validator.rs` |
| Asignación temporal de roles (`idn_user_role` con valid_from/until + revoked_by) | ✅ DDL | T-171 |
| RolBitMask precomputado por usuario | ✅ | columna + `compute_rol_bitmask` |
| Handlers de usuario (template CRUD, listado, merge) | ✅ | `user_template.rs` · `user_list.rs` · `merge_templates.rs` |
| Reglas PII y enmascaramiento | ✅ especificadas | contrato v6.0 + `zone_data_policy` |
| Invariantes de seguridad (6) | ✅ especificados | contrato v6.0 |
| Automatización JML (conector RRHH → alta/cambio/baja) | ❌ | `sync/` contiene solo `mod.rs` — esqueleto |
| Offboarding end-to-end certificado (<30 s medidos) | ❌ | diseño sin evidencia AA-1 |
| Columnas legacy (`kc_user_id`, `tryton_user_id`, `sync_status`) saneadas | ❌ | vigentes en DDL — contradicen ADR-010 |
| Contrato v6.0 con lenguaje soberano (sin KC/SAM-128) | ⚠️ | actualización documental pendiente |
| Detección de cuentas dormidas (`last_activity_at` > 90 d) | ❌ | columna existe, barrido no (gap compartido con MANUAL-ROLES §14) |
| Migración de PII 1:N a `idn_identity_attribute` | ⚠️ | depende del DDL de atributos (ADR-016) |

### 11.2 Lo que hace la industria en 2026

1. **HR como sistema de registro (HR-driven ILM):** el patrón dominante — Workday, SAP
   SuccessFactors o ServiceNow HR disparan el aprovisionamiento automático; el alta en RRHH ES
   el evento de creación de identidad. En SBOS el equivalente soberano es
   **OrangeHRM → biedata → bAuth**.
2. **Birthright provisioning:** el acceso base se asigna automáticamente por atributos
   (departamento, sede, cargo) al momento del alta — exactamente lo que el RolTemplate por
   plantilla + árbol D00 permiten hacer por diseño.
3. **El dato duro del mercado:** dos tercios de los líderes de TI reportan fricción moderada-alta
   en los procesos JML; y automatizar el 20–30% fácil no basta — **el 70–80% del riesgo vive en
   el long-tail** (SaaS menores, sistemas legacy, OT/ICS) donde fallan los offboardings y nacen
   los desastres de auditoría.
4. **El tema emergente 2026:** el ciclo de vida de **agentes de IA** — las identidades no
   humanas (SERVICE/BOT en el account_type de bAuth) necesitan JML propio; la industria admite
   que el ILM tradicional "no fue construido para agentes".

### 11.3 Comparativa — el usuario bAuth vs la industria

| Criterio | bAuth | Okta Lifecycle | Entra ID Governance | SailPoint |
|----------|:-----:|:--------------:|:-------------------:|:---------:|
| Identidad separada de autoridad (template vs rol) | ✅ contrato explícito | ⚠️ | ⚠️ | ✅ |
| Árbol organizacional en la identidad (D00 4 niveles) | ✅ único | ❌ | ⚠️ 2 niveles | ⚠️ |
| Asignación de rol con vigencia temporal nativa | ✅ valid_from/until | ✅ | ✅ | ✅ |
| Autoridad precomputada O(1) (BitMask) | ✅ único | ❌ | ❌ | ❌ |
| Revocación total de sesión < 30 s | ✅ diseño ctx_id | ⚠️ | ✅ CAE | ⚠️ |
| JML automatizado desde RRHH | ❌ gap | ✅ | ✅ workflows | ✅ |
| Birthright por atributos | ⚠️ por plantilla (manual) | ✅ | ✅ | ✅ |
| Identidades no humanas tipadas (SERVICE/SYSTEM/BOT) | ✅ account_type | ⚠️ | ✅ workload id | ⚠️ |
| PII enmascarada por zona + LoA | ✅ único | ❌ | ⚠️ | ⚠️ |
| Soberano | ✅ | ❌ | ❌ | ❌ |

**Lectura honesta:** el modelo de datos del usuario bAuth es superior (separación
identidad/autoridad, árbol D00, BitMask precomputado, PII por zona+LoA). La brecha está en la
**automatización del ciclo**: hoy el JML es manual — el conector de RRHH, el birthright
automático y el barrido de cuentas dormidas no existen. Es la misma conclusión de
MANUAL-ROLES §14: motor excelente, gobernanza operativa por construir.

### 11.4 Brechas por prioridad

**P1 — Cerrar el ciclo de vida:**

| Brecha | Enfoque | Requiere |
|--------|---------|:--------:|
| Automatización JML | Conector OrangeHRM → biedata → sagas `user.joiner` / `user.mover` / `user.leaver` (el módulo `sync/` está vacío — construirlo) | contrato biedata |
| Offboarding certificado | Saga `user.leaver` con evidencia AA-1: sesiones revocadas <30 s medidos + checklist de sistemas | Testeador |
| Saneamiento legacy | `kc_user_id`/`tryton_user_id`/`sync_status` → NULLABLE + marcar `[DEPRECADO]` (alineación ADR-010, junto con `realm_kc` del tenant — MANUAL-D00 §6.2 fase D) | HITL |
| Contrato v6.0 en lenguaje soberano | Purgar KC/SAM-128 del SSOT → v6.1 vía buzón del Bibliotecario | Bibliotecario |

**P2 — Gobernanza del usuario:**

| Brecha | Enfoque |
|--------|---------|
| Barrido de cuentas dormidas | `last_activity_at` > 90 d → suspensión + notificación (NIST AC-2(3) — compartido con MANUAL-ROLES P1) |
| Birthright automático | Regla plantilla D00 × cargo → rol por defecto al alta (evaluada por el validador) |
| Mover con recertificación | El cambio de puesto dispara mini-campaña: el nuevo jefe confirma los accesos heredados |
| PII 1:N a `idn_identity_attribute` | Migrar emails/teléfonos/documentos del JSONB a la tabla de atributos (depende de ADR-016) |

**P3 — Futuro:**

- JML para identidades no humanas (SERVICE/BOT): ciclo de vida de agentes IA y service accounts con dueño humano responsable
- Import/export SCIM 2.0 del UserTemplate (interoperabilidad con IGA externos — fachada compartida con MANUAL-ATRIBUTOS P2)
