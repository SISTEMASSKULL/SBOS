## 1. El problema que resuelve el BitMask

Un sistema de identidad empresarial necesita responder una pregunta en menos de un milisegundo en cada request:

> **¿Puede el usuario X ejecutar la acción A sobre el recurso R en el dominio D?**

La respuesta ingenua — consultar la base de datos en cada verificación — no escala. Un sistema con 500 usuarios activos, 6000 átomos de privilegio, y 20 requests por segundo necesita **120.000 verificaciones por segundo**. Una query PostgreSQL típica tarda 1–3 ms: eso es 120–360 segundos de DB time por segundo de tráfico — imposible.

La solución de bAuth: **representar todos los privilegios de un usuario como bits en un vector**. La verificación se reduce a un shift y un AND sobre enteros de 64 bits — menos de 0.5 nanosegundos.

```
Pregunta: "¿tiene el usuario permiso para el átomo en posición 42?"
Respuesta: rol_bitmask[42 / 64] >> (42 % 64) & 1   ← 0.5ns
```

## 2. Dos estructuras, dos propósitos

**La regla más importante del sistema.** Existen DOS tipos de BitMask con propósitos completamente diferentes. Confundirlos rompe la arquitectura de permisos.

| | **AtomBitMask** | **RolBitMask** |
|---|---|---|
| **¿Qué es?** | Etiqueta que identifica UN átomo | Vector de N bits que representa los permisos de UN rol |
| **Tamaño** | 64 bits fijos | N bits (N = total de átomos en el catálogo, actualmente ~6000) |
| **Encoding** | Label encoding — cada campo ocupa un rango de bits | One-hot encoding — cada bit es una posición independiente |
| **Se almacena en** | `bauth.privilege_atom` (BD) | Redis (cache, TTL 30s) + `bauth.idn_role_template` (BD) |
| **¿OR/AND/XOR entre dos?** | **PROHIBIDO — destruye el significado** | **PERMITIDO y es la operación fundamental** |
| **¿Para qué sirve?** | Identificar el átomo en lookup, comparar igualdad | Combinar roles, verificar acceso, heredar privilegios |

**Por qué el OR entre dos AtomBitMasks es incorrecto:**

```
D1.app1.grupo1.nuevo  = 0x0001_0001_0001_0001  (label encoding)
D1.app1.grupo1.editar = 0x0001_0001_0001_0002  (label encoding)

OR de los dos        = 0x0001_0001_0001_0003  ← NO es ningún átomo real
```

El resultado del OR no identifica ningún átomo del catálogo — es un valor inválido. El test en `atom.rs` lo verifica explícitamente:

```rust
// test: or_between_atoms_is_not_equal (atom.rs:382)
let or_raw = a1.to_u64() | a2.to_u64();
assert_ne!(or_raw, a1.to_u64());
assert_ne!(or_raw, a2.to_u64());
```

## 3. AtomBitMask — el átomo de 64 bits

### 3.1 Estructura de los 64 bits (actualizado B48.T67 — junio 2026)

El AtomBitMask divide sus 64 bits en dos mitades de 32 bits: **Contextual** y **Lógica**.

```
 63                              32 31                               0
 ┌──────────────────────────────────┬──────────────────────────────────┐
 │         PARTE CONTEXTUAL         │          PARTE LÓGICA             │
 │ [8 device][4 domain][9 app][11 g]│ [3 trust][2 bind][1 blk][2 pol][24 verb] │
 └──────────────────────────────────┴──────────────────────────────────┘
  bits 63-32 (u32 alto)              bits 31-0 (u32 bajo)
```

#### Parte Contextual (bits 63–32)

| Campo | Bits | Rango | Descripción |
|-------|------|-------|-------------|
| `device_allowed` | 8 | bitmap | Categorías de dispositivo que pueden ejecutar este átomo |
| `domain` | 4 | 1–15 (D1–D15) | Dominio de soberanía al que pertenece el átomo |
| `app` | 9 | 1–511 | Código de aplicación (biedata, PACS, Besu, etc.) |
| `group` | 11 | 1–2047 | Código del grupo funcional dentro de la aplicación |

**Bit positions exactas (desde el `u32` contextual):**

```
bits [7:0]   → device_allowed  (DEVICE_SHIFT = 0)
bits [11:8]  → domain_code     (DOMAIN_SHIFT = 8)
bits [20:12] → app_code        (APP_SHIFT = 12)
bits [31:21] → group_code      (GROUP_SHIFT = 21)
```

#### Parte Lógica (bits 31–0)

| Campo | Bits | Rango | Descripción |
|-------|------|-------|-------------|
| `min_trust` | 3 | 0–4 | Nivel mínimo de confianza del dispositivo requerido |
| `token_binding` | 2 | 0–3 | Tipo de binding del token requerido |
| `blockchain_anchored` | 1 | 0–1 | ¿Requiere anclaje blockchain para este átomo? |
| `policy_state` | 2 | 0–3 | Estado de política evaluado — se superpone en runtime |
| `verb` | 24 | 1–16,777,215 | Código del verbo (acción: nuevo, editar, eliminar, ver) |

**Bit positions exactas (desde el `u32` lógico):**

```
bits [2:0]   → min_trust        (TRUST_SHIFT = 0)
bits [4:3]   → token_binding    (BINDING_SHIFT = 3)
bit  [5]     → blockchain_anch  (BLOCKCHAIN_SHIFT = 5)
bits [7:6]   → policy_state     (POLICY_SHIFT = 6)
bits [31:8]  → verb_code        (VERB_SHIFT = 8)
```

### 3.2 El campo `device_allowed` — bitmap de 8 categorías

Cada bit del byte `device_allowed` es una categoría de dispositivo independiente. El átomo define qué categorías de dispositivo pueden ejecutarlo.

| Bit | Constante | Valor hex | Dispositivo |
|-----|-----------|-----------|-------------|
| 0 | `MOBILE` | `0x01` | Celular / tablet |
| 1 | `WATCH` | `0x02` | Smartwatch |
| 2 | `RING` | `0x04` | Anillo inteligente |
| 3 | `IMPLANT` | `0x08` | Dispositivo médico implantado |
| 4 | `CARD` | `0x10` | Tarjeta inteligente / PIV |
| 5 | `WEARABLE` | `0x20` | Casco, guante, exoesqueleto |
| 6 | `IOT` | `0x40` | Sensor / actuador industrial |
| 7 | `CHIP` | `0x80` | PUF / secure element standalone |
| — | `ALL` | `0xFF` | Todos los dispositivos permitidos |

**Ejemplo:** Un átomo para firmar facturas con certificado ADSIB solo puede ejecutarse desde CARD o CHIP:

```rust
let device = DeviceCategories::new(DeviceCategories::CARD | DeviceCategories::CHIP);
// device_allowed = 0b10010000 = 0x90
```

**Verificación en runtime** (`<0.5ns`):

```rust
pub fn allows_device(&self, device_category: u8) -> bool {
    self.device_categories().allows(device_category)
    // Implementación: (self.0 & category) != 0
}
```

### 3.3 El campo `min_trust` — niveles de confianza del dispositivo

| Valor | Constante | Descripción |
|-------|-----------|-------------|
| 0 | `None` | Sin requisito de confianza |
| 1 | `Low` | Dispositivo registrado |
| 2 | `Medium` | Dispositivo gestionado (MDM) |
| 3 | `High` | Dispositivo con secure enclave |
| 4 | `Critical` | Hardware security key + PIV |

**Comparación:** `trust_level_presentado >= min_trust_del_atomo` → acceso permitido. Esta comparación preserva orden (PartialOrd sobre TrustLevel).

### 3.4 El campo `token_binding`

| Valor | Constante | Descripción |
|-------|-----------|-------------|
| 0 | `None` | Sin binding requerido |
| 1 | `Device` | Token vinculado al dispositivo |
| 2 | `Session` | Token vinculado a la sesión |
| 3 | `Hardware` | Token vinculado a hardware key (DPoP) |

### 3.5 El campo `blockchain_anchored`

Un único bit: `1` = el evento de acceso a este átomo debe anclarse en blockchain (Besu/QBFT). Se usa para átomos de D12 y D13 donde la inmutabilidad jurídica es requerida (Ley 164 Bolivia, auditorías de liquidación).

### 3.6 El campo `policy_state` — se superpone en runtime

**NO se almacena en el catálogo** — se inyecta en el AtomBitMask en memoria durante la evaluación de acceso.

| Valor binario | Estado | Significado |
|:---:|---|---|
| `00` | `NoAplica` | D1 y D2: el verbo es suficiente, sin política adicional |
| `01` | `Pendiente` | Requiere step-up, segunda firma, aprobación dual |
| `10` | `Aprobado` | PolicyEngine evaluó favorablemente |
| `11` | `Rechazado` | PolicyEngine evaluó desfavorablemente |

**Método para superponer sin tocar otros campos** (`atom.rs:261`):

```rust
pub fn with_policy_state(&self, state: PolicyState) -> Self {
    let logical = (self.logical_mask() & !((POLICY_MASK as u32) << POLICY_SHIFT))
        | ((u8::from(state) as u32) << POLICY_SHIFT);
    AtomBitMask(((self.contextual_mask() as u64) << 32) | (logical as u64))
}
```

### 3.7 Constructor completo

```rust
// atom.rs:159 — constructor con todos los campos
let atom = AtomBitMask::new(
    domain_code:        12,                                    // D12 — Blockchain
    app_code:           5,                                     // besu_app
    group_code:         100,                                   // liquidacion_group
    verb_code:          42,                                    // verbo personalizado
    policy_state:       PolicyState::Aprobado,
    device_categories:  DeviceCategories::new(DeviceCategories::CHIP),
    min_trust:          TrustLevel::Critical,
    token_binding:      TokenBinding::Hardware,
    blockchain_anchored: true,
);
```

## 4. RolBitMask — vector N-bit one-hot

### 4.1 Principio one-hot encoding

En un RolBitMask, **cada posición del vector corresponde a un único átomo del catálogo global**. Si el bit en la posición `p` está en `1`, el rol otorga ese átomo.

```
Catálogo (ejemplo simplificado con 8 átomos):
  pos 0 → D1.tryton.comprobantes.nuevo
  pos 1 → D1.tryton.comprobantes.editar
  pos 2 → D1.tryton.comprobantes.eliminar
  pos 3 → D1.tryton.comprobantes.ver
  pos 4 → D3.finanzas.pago.nuevo
  pos 5 → D3.finanzas.pago.aprobar
  pos 6 → D4.pacs.zona_ventas.acceso
  pos 7 → D12.besu.tx.firmar

RolBitMask "Cajero":    [1 1 0 1 1 0 1 0]
                         ↑ ↑   ↑ ↑   ↑
                         nuevo, editar, ver, pago.nuevo, zona_ventas

RolBitMask "Supervisor": [1 1 1 1 1 1 1 0]
                          ↑ todos menos blockchain
```

Las posiciones son **inmutables una vez asignadas**. Si se reasignara una posición, todos los RolBitMasks almacenados en BD y Redis tendrían el significado corrompido.

### 4.2 Estructura Rust

```rust
pub struct RolBitMask {
    bits: BitVec<u64, Lsb0>,  // Vector de bits sobre palabras de u64
}
```

Implementado sobre `bitvec` crate. Para 6000 átomos, el vector ocupa `ceil(6000/64) = 94` palabras de u64 = **750 bytes**. Serializado en base64: ~1000 bytes (manejable en Redis y JWT).

### 4.3 La verificación FastPath

La operación más crítica del sistema — se llama en cada request de autorización:

```rust
// rol.rs:127 — #[inline(always)] garantiza expansión en el lugar de llamada
#[inline(always)]
pub fn check(&self, position: AtomPosition) -> bool {
    if position >= self.bits.len() { return false; }
    // SAFETY: bounds check garantiza position < len.
    // get_unchecked evita la segunda verificación de índice (<0.5ns hot path).
    *unsafe { self.bits.get_unchecked(position) }
}
```

**Rendimiento medido (benchmark en fastpath.rs, modo release, LTO activo):**
- Promedio: < 0.5 ns por verificación
- P99: < 1.0 ns
- 1.000.000 verificaciones en < 1 ms

## 5. Las 4 operaciones bitwise y cuándo usarlas

Todas operan sobre `RolBitMask` — **NUNCA sobre AtomBitMask**.

### 5.1 OR — Unión de roles

**Caso de uso:** Un usuario tiene múltiples roles. La máscara efectiva es la unión de todos sus roles.

```rust
pub fn union(&self, other: &RolBitMask) -> Self {
    RolBitMask { bits: self.bits.clone() | other.bits.clone() }
}
```

**Ejemplo real:**

```
Cajero:     [1 1 0 1 1 0 1 0]
Recepción:  [0 0 0 1 0 0 1 1]
─────────────────────────────── OR
Efectiva:   [1 1 0 1 1 0 1 1]  ← todos los privilegios de ambos roles
```

**Regla:** El OR nunca inventa bits. Solo puede activar bits que ya existían en alguno de los operandos.

```rust
// test: test_or_does_not_invent_permissions (rol.rs:229)
let combined = a.union(&b);
assert!(!combined.check(2), "OR no debe inventar bits");
```

### 5.2 AND — Mínimo privilegio (delegación)

**Caso de uso:** Un gerente delega temporalmente una parte de sus privilegios a un subordinado. El subordinado no puede recibir más privilegios de los que el gerente tiene.

```rust
pub fn intersection(&self, other: &RolBitMask) -> Self {
    RolBitMask { bits: self.bits.clone() & other.bits.clone() }
}

// API semántica de delegación:
pub fn delegate(senior: &RolBitMask, junior: &RolBitMask) -> RolBitMask {
    senior.intersection(junior)
}
```

**Ejemplo real:**

```
Gerente:       [1 1 1 1 1 1 1 1]
Junior:        [1 1 0 1 1 0 1 0]
─────────────────────────────── AND
Delegado:      [1 1 0 1 1 0 1 0]  ← solo lo que tienen en común
```

El AND es la única operación que puede REDUCIR privilegios. Es la base del principio de **mínimo privilegio** (NIST SP 800-53 AC-6).

```rust
// test: test_delegate_and_reduction (rol.rs:258)
let delegated = RolBitMask::delegate(&senior, &junior);
assert_eq!(delegated.count_active(), 5);
assert!(!delegated.check(2)); // senior lo tiene, junior no → fuera
```

### 5.3 AND NOT — Revocación quirúrgica

**Caso de uso:** Revocar un átomo específico de un rol sin afectar el resto.

```rust
pub fn without(&self, other: &RolBitMask) -> Self {
    RolBitMask { bits: self.bits.clone() & !other.bits.clone() }
}

// API semántica de revocación:
pub fn revoke(mask: &RolBitMask, revoke: &RolBitMask) -> RolBitMask {
    mask.without(revoke)
}
```

**Ejemplo real:**

```
Supervisor:  [1 1 1 1 1 1 1 0]
Revocar[2]:  [0 0 1 0 0 0 0 0]  ← solo el átomo a revocar
─────────────────────────────── AND NOT
Resultado:   [1 1 0 1 1 1 1 0]  ← eliminar_doc revocado
```

```rust
// test: test_revoke_specific_atom (rol.rs:270)
assert!(!result.check(2), "átomo 2 debe estar revocado");
assert_eq!(result.count_active(), 4);
```

### 5.4 XOR — Delta entre dos estados

**Caso de uso:** Detectar qué cambió entre la máscara anterior y la nueva. Máximo 2 operandos.

```rust
pub fn delta(&self, other: &RolBitMask) -> Self {
    RolBitMask { bits: self.bits.clone() ^ other.bits.clone() }
}
```

**Ejemplo real — audit trail de cambio de rol:**

```
Antes:    [1 1 0 1 0 0]
Después:  [1 1 0 0 1 0]
───────────────────────── XOR
Delta:    [0 0 0 1 1 0]  ← pos 3 fue revocada, pos 4 fue otorgada
```

El XOR solo se usa para comparación de dos estados. **NUNCA usar XOR para combinar más de 2 máscaras** — el resultado no es semánticamente válido.

### 5.5 MergeRoles — Fusión de N roles

Para fusionar múltiples roles, se aplica OR secuencial:

```rust
// rol.rs:94
pub fn merge(masks: &[&RolBitMask]) -> Option<RolBitMask> {
    if masks.is_empty() { return None; }
    let mut result = masks[0].clone();
    for m in &masks[1..] {
        result = result.union(m);
    }
    Some(result)
}
```

```rust
// test: test_merge_multiple_roles (rol.rs:240)
let cajero     = RolBitMask::from_positions(&[0, 1, 4, 6, 8], 180);
let supervisor = RolBitMask::from_positions(&[0, 1, 2, 4, 5, 6, 7, 8, 9], 180);
let merged = RolBitMask::merge(&[&cajero, &supervisor]).unwrap();
assert_eq!(merged.count_active(), 9);  // unión sin duplicados
```

## 6. Los verbos — los 4 bits de acción

Los verbos son universales — aplican a todos los dominios y todas las aplicaciones. Los 4 verbos del sistema (seeds en `catalog.rs:170`):

| Código | Nombre ES | Slug en API | Descripción |
|:------:|-----------|-------------|-------------|
| 1 | `nuevo` | `create` | Crear un recurso nuevo |
| 2 | `editar` | `update` | Modificar un recurso existente |
| 3 | `eliminar` | `delete` | Eliminar un recurso |
| 4 | `ver` | `read` | Leer / consultar sin modificar |

**Posición en el AtomBitMask:** bits 31–8 del dominio lógico (24 bits = hasta 16.777.215 verbos posibles). Actualmente solo se usan 4, el espacio extra está reservado para verbos de dominio especializado.

**Nomenclatura de átomo:** `D{N}.{app}.{modulo}_{campo}.{VERBO}`

```
D3.finanzas.pago_empresa.nuevo
│  │        │            └── verbo (CREATE)
│  │        └── grupo funcional (campo dentro del módulo)
│  └── aplicación (módulo de negocio)
└── dominio de soberanía (D3 = Financiero)
```

**Ejemplo de catálogo (4 átomos CRUD de un mismo campo):**

```
D4.pacs.zone_access.C  → pos D4.001 → CREATE regla de acceso a zona
D4.pacs.zone_access.R  → pos D4.002 → READ ver zonas del rol
D4.pacs.zone_access.U  → pos D4.003 → UPDATE modificar nivel de acceso
D4.pacs.zone_access.D  → pos D4.004 → DELETE revocar acceso a zona
```

## 7. Los 12 dominios de soberanía (D1–D12)

### 7.1 Tabla maestra

Los 12 dominios están definidos en `src/bitmask/catalog.rs:153` (SEED_DOMAINS). El campo `bool` indica si requiere evaluación de política (`true` = PolicyPath, `false` = FastPath o pre-condición).

| Código | Nombre | PolicyPath | Path de evaluación | Descripción |
|:------:|--------|:----------:|-------------------|-------------|
| **D1** | Lógico | No | **FastPath** | Apps y recursos digitales. El verbo es suficiente |
| **D2** | Físico | No | **FastPath + OSDP** | Zonas y hardware. OSDP Secure Channel AES-128 |
| **D3** | Financiero | Sí | **PolicyPath** | Límites BOB, SoD, dual-approval. Policy-Path |
| **D4** | Temporal | Sí | **PolicyPath** | Horarios, turnos, feriados. Encadenado a D1 |
| **D5** | Biométrico | No | **ExternalPath** | Huella, rostro, iris. Validado por auth_methods |
| **D6** | Geoespacial | Sí | **PolicyPath** | Ubicación GPS, viaje imposible (900 km/h) |
| **D7** | Red | Sí | **PolicyPath** | CIDR, VPN, mTLS, device posture. Vía Kong PEP |
| **D8** | Contexto | No | **PreCondición** | `ctx_id` en Redis. Precondición de todo el BitMask |
| **D9** | Credenciales | No | **PreCondición** | Passwords, MFA, certificados. Pre-BitMask |
| **D10** | Delegación | Sí | **AND reduction** | Privilegios temporales. Máscara reducida con AND |
| **D11** | Auditoría | No | **Post-hoc** | WORM. No evalúa acceso — solo registra events |
| **D12** | Blockchain | Sí | **PolicyPath** | Merkle anchoring + liquidación Besu QBFT |

### 7.2 D1 — Dominio Lógico

**El dominio más común.** Controla acceso a recursos digitales: aplicaciones (biedata, bsearch), módulos ERP, APIs, menús, campos de formulario.

**FastPath:** Solo se verifica si el bit del átomo está activo en el RolBitMask. Sin consulta de política adicional.

```
Usuario solicita → PACS verifica RolBitMask[atom_position] → 0 ó 1 → resp inmediata
```

**¿Cuándo usar D1?** Para cualquier operación digital donde la decisión de acceso depende solo del rol del usuario, sin condiciones contextuales. La gran mayoría de las operaciones empresariales pertenecen a D1.

**Tabla de política:** `ath_policy_d1` — configura rate limiting por tier, no restricciones adicionales.

**Estándares:** ANSI INCITS 359-2004 (RBAC) · NIST SP 800-53 AC-3

### 7.3 D2 — Dominio Físico

Controla acceso a espacios y hardware físico: zonas, puertas, pisos de ascensor, cámaras ONVIF, cajones de dinero.

**FastPath + OSDP:** La verificación BitMask es inmediata, pero el comando físico (abrir puerta, activar relé) viaja por OSDP 2.2 con Secure Channel AES-128 entre bhnexus y los lectores banexus.

```
RolBitMask[zona_ventas.acceso] = 1
  → bhnexus envía OSDP cmd READER_CONTROL vía Secure Channel
  → banexus ejecuta el relé/solenoide
```

**PolicyState NO aplica en D2** (campo = `00 = NoAplica`): la política de zona se pre-valida al calcular el RolBitMask del usuario, no en el momento de apertura.

**Estándares:** ANSI/SIA AC-01-2010 · OSDP 2.2 · ONVIF Profile A · ISO 22341:2021 · NIST SP 800-116 Rev.1

### 7.4 D3 — Dominio Financiero

Controla operaciones de valor económico: crear pagos, aprobar compras, emitir facturas, transferencias bancarias.

**PolicyPath obligatorio.** Toda operación financiera pasa por el PolicyEngine XACML 3.0:

```
RolBitMask[pago.nuevo] = 1
  → PolicyEngine consulta ath_policy_d3:
      ¿monto <= daily_limit?        → sí: continúa
      ¿SoD: ¿también puede aprobar? → no: continúa (SoD cumplido)
      ¿monto > dual_approval_limit? → sí: PolicyState = PENDIENTE
  → JWT emitido con atom.policy_state = 01 (Pendiente)
  → Segundo firmante aprueba
  → atom.policy_state = 10 (Aprobado)
  → Transacción ejecutada
```

**Separación de Deberes (SoD) — NIST SP 800-53 AC-5:**

Los átomos conflictivos en D3 se definen en la matriz de conflictos (`bitmask/conflict.rs`). Si un RolBitMask tiene activos dos átomos conflictivos, el sistema alerta drift.

```
CONFLICTO: pago.nuevo + pago.aprobar  ← mismo usuario no puede crear y aprobar
CONFLICTO: compra.crear + compra.autorizar
```

**Estándares:** NIST SP 800-53 AC-5/6 · ISO 27001:2022 A.5.18 · PCI DSS 4.0 Req 6.3

### 7.5 D4 — Dominio Temporal

Restringe el acceso a franjas horarias, días de semana, turnos, y feriados nacionales. Se **encadena a D1**: el átomo D1 es el permiso base, el átomo D4 es la restricción temporal.

**PolicyPath encadenado:**

```
RolBitMask[login.acceso] = 1                  ← D1: permiso base
RolBitMask[turno_manana.acceso] = 1           ← D4: restricción temporal

Evaluación D4:
  hora_actual = 14:35
  turno.inicio = 08:00, turno.fin = 13:00
  → FUERA DE TURNO → PolicyState = 11 (Rechazado)
  → Aunque D1 sea 1, D4 bloquea el acceso
```

**Feriados:** `ath_policy_d4` incluye el catálogo de feriados por país/región. Si el día es feriado y el rol no tiene `holiday_access`, el acceso se deniega aunque el turno esté activo.

**Estándares:** NIST SP 800-53 AC-2(j) · ISO 27001:2022 A.8.1

### 7.6 D5 — Dominio Biométrico

Controla el uso de factores biométricos como método de autenticación o como condición de acceso adicional.

**ExternalPath:** La validación biométrica ocurre en `src/domain/auth_methods/` (nativa en Rust). El resultado entra en el `auth_chain` del JWT y eleva el LoA.

```
RolBitMask[huella.enroll] = 1   ← permiso para enrolar huella
RolBitMask[huella.verify] = 1   ← permiso para verificar huella como factor
```

**Importante:** Los templates biométricos NUNCA se almacenan en bAuth — solo el hash SHA-256 del template. bhnexus recibe el hash del lector y lo compara contra el almacenado en `idn_user_template`. El raw biométrico es transitorio — desaparece al cerrar el canal OSDP.

**Estándares:** ISO/IEC 30107-3 (anti-spoofing) · NIST SP 800-63B-4 §5.2.3 · GDPR Art. 9

### 7.7 D6 — Dominio Geoespacial

Controla acceso basado en la ubicación GPS del usuario. Detecta el patrón **"viaje imposible"**: si el usuario hace login desde Buenos Aires y 10 minutos después desde Madrid, uno de los dos es una sesión fraudulenta.

**PolicyPath con geo-fence:**

```
RolBitMask[app_erp.acceso] = 1
  → PolicyEngine consulta ath_policy_d6:
      geo_fence = [{"lat": -16.5, "lon": -68.1, "radio_km": 50}]  ← La Paz, Bolivia
      ip_geolocated = {lat: 48.8, lon: 2.3}  ← París
      distancia = 10.489 km
      → FUERA DE GEOFENCE → PolicyState = 11 (Rechazado)
```

**Velocidad imposible:** Si la ubicación anterior fue hace T segundos a distancia D km, la velocidad = D/T. Si supera 900 km/h (velocidad de avión) → flag de anomalía → notificación al usuario + audit_event.

**Estándares:** NIST SP 800-207 §2.1 · ISO 27001:2022 A.8.16

### 7.8 D7 — Dominio de Red

Controla el acceso basado en red de origen: CIDR, zona de red, VPN activa, estado del dispositivo (device posture).

**PolicyPath vía Kong PEP:** El daemon Kong actúa como PEP (Policy Enforcement Point) en el borde de red. Verifica que el request viene de una red autorizada antes de llegar a bAuth.

```
RolBitMask[admin.acceso] = 1
  → Kong PEP verifica ath_policy_d7:
      allowed_cidrs = ["10.0.0.0/8", "192.168.1.0/24"]
      ip_origen = "203.0.113.5"  ← IP pública externa
      → NO ESTÁ EN CIDR PERMITIDO → deny en Kong (sin llegar a bAuth)
```

**Device posture (MDM):** Para `SU` y `SYS`, el dispositivo debe tener estado de gestión verificado (`device_trust = HIGH` mínimo).

**Estándares:** NIST SP 800-207 (ZTA) · RFC 8705 (mTLS) · NIST SP 800-124 Rev.2 (MDM)

### 7.9 D8 — Dominio de Contexto

**Pre-condición obligatoria de todo el sistema.** Antes de evaluar cualquier otro dominio, bAuth verifica que el `ctx_id` de la operación exista y sea válido en Redis.

```
ctx_id "01924f3c-8b2d-7000..." → Redis GET bauth:ctx:{ctx_id}
  HIT  → contexto válido → continúa evaluación
  MISS → sin contexto → AccessResult::Denegado (sin eval de BitMask)
```

El contexto almacena: `user_uuid`, `session_id`, `tenant_id`, `device_id`, `network_zone`, `risk_score`. Estos datos enriquecen la evaluación de D3-D7 sin consultar BD.

**¿Por qué es pre-condición?** Sin `ctx_id`, no hay trazabilidad. La norma SBOS-049 exige `ctx_id` en toda operación — operaciones sin contexto son señal de ataque o bug.

**TTL:** 30 segundos en Redis. Si el context expira, el siguiente request regenera el contexto (re-autentica silenciosamente si tiene refresh token válido).

**Estándares:** SBOS-049 · W3C Trace Context · NIST SP 800-207

### 7.10 D9 — Dominio de Credenciales

**Pre-condición del nivel de autenticación.** Verifica que el LoA alcanzado en la sesión sea suficiente para el átomo solicitado.

```
Átomo D1.erp.cierre_fiscal.nuevo  requiere loa_required = 2
Usuario autenticado con loa = 1  (solo contraseña)
  → LoA insuficiente → bAuth emite challenge step-up (RFC 9470)
  → Usuario completa TOTP → loa = 2
  → Pre-condición satisfecha → continúa evaluación D1
```

D9 NO es un dominio de evaluación de permisos en sí mismo — es el guardián que garantiza que el método de autenticación fue suficientemente fuerte para el átomo solicitado.

**Estándares:** NIST SP 800-63B-4 (AAL1/2/3) · RFC 9470 (Step-Up)

### 7.11 D11 — Dominio de Auditoría

**Post-hoc — nunca deniega acceso.** D11 no participa en la evaluación de permisos. Su función es registrar en `bauth.audit_event` cada operación, independientemente de si fue permitida o denegada.

```
Toda operación (PERMITIDA o DENEGADA) → audit_event INSERT
  actor_id, atom_slug, verb_code, domain_code,
  ctx_id, device_category, trust_level,
  access_result, auth_method_used, loa_achieved,
  timestamp
```

Los átomos D11 controlan **quién puede leer y exportar los audit_events** — no quién es auditado (todos son auditados siempre).

**WORM:** `bauth.audit_event` es append-only. No existe UPDATE ni DELETE en el schema.

**Retención por jurisdicción:** Bolivia = 10 años · Argentina = 10 años · México = 5 años.

**Estándares:** ISO 27001:2022 A.8.15 · NIST SP 800-53 AU-2/3/6 · PCI DSS 4.0 Req 10

### 7.12 D12 — Dominio Blockchain

Controla operaciones de anclaje de integridad y trazabilidad inmutable. Dos variantes:

**Variante A — Merkle Anchoring:**  
Cada N eventos de auditoría (configurable, default=1000), bAuth calcula el hash raíz del árbol Merkle y lo ancla en Besu/QBFT. Prueba que los audit_events no fueron alterados.

```
audit_events[0..999] → Merkle root hash → tx Besu QBFT
→ Hash almacenado en blockchain: inmutable, verificable externamente
```

**Variante B — Liquidación Besu:**  
Operaciones de liquidación financiera entre tenants que requieren prueba de integridad entre partes no confiables (ej: operaciones interbancarias).

**PolicyState D12 siempre = `Aprobado` o `Rechazado`:** No hay operación blockchain en estado `Pendiente` — o la transacción es enviada a la red (gas pagado) o no lo es.

**`blockchain_anchored = 1`:** Todo átomo D12 tiene este bit activo — indica que el evento de acceso mismo se ancla en blockchain, no solo el resultado de la operación.

**Estándares:** EIP-155 · EIP-1559 · EIP-712 · Hyperledger Besu 24.x · NIST FIPS 186-5

## 9. Paths de evaluación — FastPath vs PolicyPath

### 9.1 Diagrama de flujo de evaluación

```
REQUEST → D8 ctx_id válido?  ── NO → DENEGADO (sin eval)
             │ SÍ
             ▼
          D9 LoA suficiente?  ── NO → Challenge step-up (RFC 9470)
             │ SÍ
             ▼
          RolBitMask[atom_position] == 1?  ── NO → DENEGADO
             │ SÍ
             ▼
     ┌───────┴────────────────────────────────┐
     │                                        │
  FastPath                               PolicyPath
  (D1, D2, D5)                      (D3, D4, D6, D7, D10, D12, D13)
     │                                        │
  Redis cache?                         PolicyEngine XACML 3.0
  HIT → AccessResult                   consulta ath_policy_dN
     │                                        │
  MISS → Eval + cache 30s              PolicyState en AtomBitMask:
     │                                   00=NoAplica
     └──────────┬─────────────────────   01=Pendiente → step-up/dual
                │                         10=Aprobado → PERMITIDO
                ▼                         11=Rechazado → DENEGADO
          D11 audit_event INSERT (siempre, independiente del resultado)
```

### 9.2 FastPath — sub-nanosegundo

Para D1 y D2, la evaluación no requiere consultar ninguna tabla de política. Solo:

1. `ctx_id` presente en Redis (D8) — ~300 µs (network)
2. `RolBitMask[atom_position]` activo — < 0.5 ns
3. `device_category` permitida — < 0.5 ns
4. `trust_level` mínimo cumplido — < 0.5 ns

**Latencia total FastPath:** ~300 µs (dominado por Redis, no por el BitMask).

### 9.3 PolicyPath — evaluación adicional

Para D3, D4, D6, D7, D10, D12, D13:

1. FastPath: mismo que arriba
2. PolicyEngine XACML 3.0 evalúa `ath_policy_d{N}` — ~1-2 ms (PostgreSQL)
3. Si `PolicyState = Pendiente`: se registra en `bauth.policy_pending` y se notifica al actor secundario

**Redis cache de resultado:** El resultado del PolicyPath se cachea en Redis con TTL configurable (default 30s para D3, 5s para D7). Evita re-consultar la política en cada request.

## 10. Herencia DAG y Closure Table

### 10.1 El DAG de herencia de roles

Los roles de bAuth forman un **Directed Acyclic Graph (DAG)**: un rol senior hereda los átomos de todos sus descendientes en el DAG.

```
SU (Superusuario)
├── SYS (Sistema)
│   ├── BIZ_N1 (Gerencia)
│   │   ├── BIZ_N2 (Jefaturas)
│   │   │   ├── BIZ_N3 (Profesionales)
│   │   │   │   ├── BIZ_N4 (Operativos)
│   │   │   │   │   └── BIZ_N5 (Asistentes)
│   │   │   │   └── EXT_N0 (Externos)
│   │   │   └── M2M (Machine-to-Machine)
│   │   └── VISITANTE
```

**Invariante del DAG:** No puede haber ciclos. Si `A hereda de B` y `B hereda de A`, se detecta y rechaza.

```rust
// closure.rs:51 — detección de ciclos
pub fn add_edge(&mut self, padre: &str, hijo: &str) -> Result<Vec<ClosureEdge>, String> {
    if self.path_exists(hijo, padre) {
        return Err(format!("Ciclo detectado: {} → {} crearía un ciclo", padre, hijo));
    }
    // ...
}
```

### 10.2 La Closure Table — herencia precomputada

Para evitar recursión en runtime, bAuth precomputa todas las relaciones de herencia en una **Closure Table** en PostgreSQL (`bauth.idn_role_closure`).

```sql
-- Estructura: (ancestro, descendiente, profundidad)
bauth.idn_role_closure:
  (SU,    SU,       0)  ← self-reference
  (SU,    N1,       1)  ← hijo directo
  (SU,    N2,       2)  ← nieto
  (SU,    N3,       3)  ← bisnieto
  (N1,    N1,       0)
  (N1,    N2,       1)
  ...
```

**La herencia se resuelve con una sola query JOIN** — sin recursión, sin múltiples queries:

```sql
-- Obtener todos los átomos de un rol incluyendo herencia
SELECT pa.atom_position
FROM bauth.privilege_atom pa
JOIN bauth.bos_role_atom bra ON pa.id = bra.atom_id
JOIN bauth.idn_role_closure rc ON rc.descendiente = bra.role_id
WHERE rc.ancestro = $role_id AND bra.allowed = TRUE;
```

### 10.3 Cómputo de la máscara efectiva con herencia

```rust
// resolver.rs:193 — inherit_from_parents
pub async fn inherit_from_parents(pg: &PgPool, role_id: &str) -> Result<RolBitMask, ComputeError> {
    // 1. Obtener todos los ancestros del rol desde la closure table
    let ancestors = crate::db::load_role_ancestors(pg, role_id).await?;

    // 2. Cargar átomos de todos los roles (propio + ancestros)
    let mut all_ids = vec![role_id.to_string()];
    all_ids.extend(ancestors);
    let positions = crate::db::load_atoms_for_roles(pg, &all_ids).await?;

    // 3. Construir RolBitMask con OR implícito (from_positions activa todos los bits)
    Ok(RolBitMask::from_positions(&atom_positions, total_atoms))
}
```

**El OR es implícito** en `from_positions`: activar múltiples posiciones en un solo vector es equivalente a hacer OR de las máscaras individuales.

**Ejemplo:**

```
Rol N3 propio:          posiciones [0, 1, 5, 8]
Heredado de N4:         posiciones [0, 1, 2, 3, 5]
Heredado de N5:         posiciones [0, 1, 2, 3, 4, 5, 6]

Máscara efectiva N3:    posiciones [0, 1, 2, 3, 4, 5, 6, 8]
                         (unión de todos — OR implícito)
```

## 12. Serialización y almacenamiento

### 12.1 AtomBitMask — almacenamiento

Se almacena como `BIGINT` (64 bits) en la columna `bitmask_value` de `bauth.privilege_atom`. En JWT y Redis se representa como el valor `u64` decimal o hexadecimal.

```rust
// Serialización
let raw: u64 = atom.to_u64();

// Deserialización
let atom = AtomBitMask::from_u64(raw);
```

### 12.2 RolBitMask — formatos soportados

```rust
// resolver.rs:28 — RolBitMaskFormat
pub enum RolBitMaskFormat {
    Base64Url,   // URL-safe base64 sin padding — para Redis y JWT (~1KB para 6000 átomos)
    Bytes,       // Bytes crudos — para transmisión binaria
    Positions,   // Array de posiciones activas — para debug y logs
}
```

**Redis:** `SETEX bauth:rol:{role_id} 30 <base64_rol_bitmask>` — TTL 30s, se recalcula si expira.

**PostgreSQL:** `BYTEA` o `TEXT` (base64) en `bauth.idn_role_template.rol_bitmask_cache`.

**¿Por qué base64 y no JSON?** El array JSON de 6000 posiciones ocuparía 20+ KB. El vector de bits comprimido en base64 ocupa ~1 KB — 20x más eficiente.

### 12.3 Roundtrip verificado

```rust
// test: test_base64_roundtrip (rol.rs:215)
let positions = vec![0, 1, 3, 4, 14, 42, 100, 255];
let mask = RolBitMask::from_positions(&positions, 500);
let b64 = mask.to_base64();
let restored = RolBitMask::from_base64(&b64, 500).unwrap();
assert_eq!(mask.count_active(), restored.count_active());
for pos in &positions {
    assert!(restored.check(*pos));
}
```

| # | Regla | Fundamento |
|---|-------|------------|
| **1** | **NUNCA aplicar OR/AND/XOR entre dos AtomBitMask** | Label encoding — el resultado no es un átomo válido |
| **2** | **SOLO aplicar OR/AND/XOR sobre RolBitMask** | One-hot encoding — las operaciones son semánticamente correctas |
| **3** | **Las posiciones de átomos son INMUTABLES una vez asignadas** | Cambiar una posición corrompe todos los RolBitMasks almacenados |
| **4** | **PolicyState NO se almacena en catálogo — solo se superpone en runtime** | El estado de política depende del contexto del request, no del átomo en sí |
| **5** | **OR nunca inventa bits** | La unión de dos conjuntos contiene solo lo que está en alguno de los dos |
| **6** | **XOR máximo 2 operandos** | Con más de 2, el resultado es semánticamente inválido |
| **7** | **D8 y D9 son pre-condiciones, no dominios de permiso** | Sin ctx_id y sin LoA suficiente, no se evalúa el RolBitMask |
| **8** | **D11 nunca deniega acceso** | La auditoría registra — no decide |
| **9** | **D13 requiere min_trust = Critical para legalsg** | Firma con validez jurídica solo desde hardware certificado |
| **10** | **La herencia es OR implícito — un rol senior siempre tiene al menos lo que tiene el junior** | El DAG garantiza que la herencia acumula, no resta |

### 14.2 El panorama de motores de autorización en 2026

La autorización de grano fino (FGA — Fine-Grained Authorization) se consolidó como categoría
propia. Los actores que definen el estándar:

| Motor | Modelo | Origen |
|-------|--------|--------|
| **Google Zanzibar** (paper 2019) | ReBAC — relaciones entre sujetos y recursos | Autorización de Google Docs/Drive |
| **SpiceDB** (AuthZed) | ReBAC — implementación abierta de Zanzibar | Startup, adopción enterprise |
| **OpenFGA** (CNCF) | ReBAC — donado por Auth0/Okta a la CNCF | Sandbox CNCF, ecosistema cloud-native |
| **AWS Cedar** | Policy language + ABAC/RBAC | Amazon Verified Permissions |
| **OPA / Rego** (CNCF) | Policy-as-code de propósito general | Estándar de facto en Kubernetes |
| **Casbin** | Multi-modelo (ACL/RBAC/ABAC) embebido | Biblioteca multi-lenguaje |
| **AuthZEN** (OpenID Foundation) | Estándar de interoperabilidad de PDPs | API común para consultar cualquier motor |

**Tendencias 2026:** (1) ReBAC ganó la batalla del modelo para colaboración tipo documentos —
"¿puede Ana ver este archivo que Juan le compartió?" no se expresa bien en RBAC puro. (2)
Policy-as-code con revisión en Git es la práctica esperada. (3) **AuthZEN 1.0** emergió como el
"OIDC de la autorización": una API estándar `POST /access/v1/evaluation` para que cualquier PEP
consulte cualquier PDP — interoperabilidad entre motores.

### 14.3 Comparativa — BitMask Dual vs motores de la industria

| Criterio | bAuth BitMask | SpiceDB/OpenFGA | AWS Cedar | OPA/Rego | Casbin |
|----------|:-------------:|:---------------:|:---------:|:--------:|:------:|
| Modelo | RBAC N3 + dominios contextuales | ReBAC | Policy lang (ABAC+RBAC) | Policy-as-code | Multi-modelo |
| Latencia de evaluación | **< 0.5 ns** (bitwise en proceso) | ~1–10 ms (red) | ~1 ms | ~0.1–1 ms | ~µs |
| Evaluación sin red ni BD | ✅ (RolBitMask en Redis local) | ❌ servidor central | ⚠️ | ⚠️ sidecar | ✅ |
| Consistencia distribuida | Redis FastPath + reconcile | ✅ zookies (Zanzibar) | ✅ | ❌ (datos externos) | ❌ |
| Relaciones por recurso (ReBAC) | ❌ | ✅ nativo | ⚠️ | ⚠️ manual | ⚠️ |
| Jerarquía organizacional DAG | ✅ nativa + closure | ⚠️ modelable | ⚠️ | ⚠️ manual | ✅ básica |
| SoD nativo | ✅ matriz de conflictos | ❌ | ❌ | ⚠️ manual | ❌ |
| Dominio físico (OSDP) y blockchain | ✅ D2/D12 únicos | ❌ | ❌ | ❌ | ❌ |
| Lenguaje de políticas auditable | ⚠️ tablas declarativas | ⚠️ schema | ✅ Cedar | ✅ Rego | ⚠️ CSV |
| What-if / simulación | ❌ | ✅ (check con contexto) | ✅ (test bench) | ✅ (unit tests) | ⚠️ |
| Interop AuthZEN | ❌ | ✅ | ✅ | ✅ | ❌ |
| Soberano, sin dependencia cloud | ✅ | ✅ self-host | ❌ AWS | ✅ | ✅ |

**Lectura honesta:** el BitMask gana por órdenes de magnitud en latencia (bitwise vs red) y es el
único con SoD, acceso físico y blockchain integrados. Pierde en dos frentes: **expresividad ReBAC**
(relaciones arbitrarias por recurso: propietario, compartido-con, miembro-de) y **tooling de
políticas** (simulación, tests, replay de decisiones). La estrategia correcta no es reemplazar el
BitMask por ReBAC — es añadir la capa de relaciones *encima* del BitMask para los dominios que la
necesiten (documentos, registros CRM), manteniendo el FastPath para el 95% de las evaluaciones.
