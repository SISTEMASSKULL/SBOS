## 1. Audiencia, propósito y alcance

Este manual documenta las **herramientas de línea de comandos** de bAuth y el **protocolo para
delegar pruebas externas**: cómo un actor que NO desarrolló bAuth (el Testeador de la fábrica, un
operador, un auditor del cliente) verifica de forma **independiente y reproducible** que el daemon
hace lo que sus manuales afirman — sin leer el código fuente.

**Audiencia:** el **Testeador** de la fábrica ORQUESTA (verificación empírica en VPS), el Revisor
(auditoría post-commit), operadores del cliente, auditores externos.

**Por qué manual propio:** la regla ORQUESTA-056 establece que *el auto-reporte de un agente no es
fuente confiable*. bAuth afirma; un tercero verifica. Para que esa verificación sea delegable, las
herramientas y los criterios PASS/FAIL deben estar escritos — este manual es ese contrato de prueba.

---

## 2. El principio — nadie se audita a sí mismo

La fábrica separa roles (CLAUDE SBOS): el desarrollador entrega, el **Revisor** audita el código, el
**Testeador** verifica el funcionamiento REAL en la VPS y **dictamina VERDADERO/FALSO con evidencia**.
Este manual equipa al Testeador con tres niveles de prueba, del más superficial al más profundo:

```
Nivel 1 — ¿VIVE?      systemd + bauthctl health          (segundos)
Nivel 2 — ¿DECIDE?    bauthctl policy/ctx/saga/role      (minutos)
Nivel 3 — ¿ES ÍNTEGRO? verify_policies + bos_verify      (minutos, con BD/proof)
```

Cada nivel es delegable por separado. Toda afirmación del resultado lleva **evidencia AA-1** (§8) —
sin evidencia, el dictamen se rechaza (C12).

## 3. Inventario de CLI

Los 4 binarios del producto ([9.01 §4](9.01_MANUAL-PRODUCTO-v1.0.md)) vistos como herramientas de prueba:

| Binario | Qué prueba | Necesita | Nivel |
|---------|-----------|----------|:-----:|
| `bauthctl` | El daemon **vivo**: socket, dispatcher, handlers, sagas | Socket `/run/bos/bauth.sock` | 1–2 |
| `verify_policies` | El **plano de políticas** en BD: átomos → políticas → evaluación → BitMask → herencia | `DATABASE_URL` (PostgreSQL) | 3 |
| `bos_verify` | La **integridad del ancla blockchain** (D12) sin confiar en el daemon | Un archivo `.proof.json` (offline) o RPC (online) | 3 |
| `bauth` (el daemon) | — es el sujeto bajo prueba, no herramienta | — | — |

> **Nota de independencia:** `verify_policies` y `bos_verify` **no** pasan por el daemon — atacan
> directamente la BD y la prueba criptográfica. Eso es deliberado: si el daemon mintiera, estas
> herramientas lo delatan (verificación por canal separado).

## 4. `bauthctl` — operación y prueba del daemon vivo

Cliente JSON-RPC 2.0 sobre el Unix socket (verificado, `bauthctl.rs`). Selección de socket:
`--socket <ruta>` > variable `BAUTH_SOCKET` > default `/run/bos/bauth.sock`. Timeout de lectura: 10 s.

### 4.1 Comandos implementados (verificados en el parser)

| Comando | Método JSON-RPC invocado | Prueba que |
|---------|--------------------------|------------|
| `bauthctl health` | `bauth.health.check` | El camino completo socket→dispatcher→handler responde |
| `bauthctl version` | (local) | El binario es la versión esperada |
| `bauthctl role list` | `bauth.role.list` | El catálogo de roles carga desde BD |
| `bauthctl role compute <role_id>` | `bauth.role.compute_mask` | El PrivilegeEngine computa el BitMask |
| `bauthctl user list` | `bauth.user.list` | UserTemplates accesibles |
| `bauthctl auth login <user>` | `bauth.saga.execute` (saga `auth.password.login`) | El flujo de login completo (pide contraseña **sin eco** — OWASP ASVS V2.7.1) |
| `bauthctl auth mfa <código>` | `bauth.saga.execute` (saga `auth.mfa.totp`) | El segundo factor TOTP |
| `bauthctl ctx validate <ctx_id>` | `bauth.ctx.validate` | El Context Plane valida sesiones |
| `bauthctl policy eval <app> <grupo> <átomo>` | `bauth.policy.evaluate` | El PDP evalúa un átomo concreto |
| `bauthctl saga list` / `saga execute <n>` | `bauth.saga.list` / `.execute` | El motor de sagas |
| `bauthctl sign internal <payload>` | `bauth.sign.internal` | La firma Ed25519 interna |
| `bauthctl tenant list` | `bauth.tenant.list` | Multi-tenancy |
| `bauthctl sync reconcile` / `sync status` | `bauth.sync.reconcile` / `.status` | El reconcile loop bajo demanda |

**Códigos de salida:** `0` = éxito (imprime el JSON de respuesta, formateado) · `1` = error (argumento
faltante, subcomando desconocido, socket inaccesible, params inválidos). El error va a stderr en español.

### 4.2 ⚠️ Brecha conocida (para no confundir al probador externo)

El texto de ayuda (`--help`) muestra ejemplos de operaciones **aún no cableadas** en el parser
(`role create --file`, `user assign-role`, `sign external-factura`, `tenant create`). Si el Testeador
las invoca, recibirá `subcomando no implementado` — eso **no** es un fallo del daemon, es la brecha
O3 de [6.01 §15](6.01_MANUAL-OPERACION-v1.0.md). La tabla §4.1 es la lista real.

## 5. `verify_policies` — validación end-to-end del plano de políticas

Binario independiente que ataca PostgreSQL directamente (verificado, `verify_policies.rs`):

```bash
export DATABASE_URL='postgres://usuario:clave@host:5432/SBOS_db'
verify_policies          # o: cargo run --bin verify_policies
```

**Qué ejecuta (pipeline de 7 pasos, verificado):**

1. Conexión a PostgreSQL (falla → `exit 1` con mensaje).
2. Carga una muestra de **5 átomos** de `bauth.privilege_atom`.
3. Carga las **políticas encadenadas** de cada átomo (`privilege_atom_policy`, orden por prioridad).
4. **Valida la estructura JSONB** de cada política (✅/❌ por política).
5. **Evalúa** cada política válida contra un contexto de prueba construido por átomo.
6. **Resumen:** átomos totales en catálogo, políticas activas, dominios y políticas por dominio,
   contador `evaluadas/total`.
7. **ComputeRolBitMask** (posiciones de átomos por rol desde BD) e **InheritFromParent**
   (ancestros vía `idn_role_closure`) — valida el álgebra de roles contra los datos reales.

**Criterio PASS del Testeador:** conexión ✅, cero ❌ en validación JSONB, contadores > 0 coherentes
con el seed declarado, y roles con posiciones no vacías. La salida es texto legible — se adjunta
completa como evidencia.

> ⚠️ **Limitación honesta:** el binario usa `unwrap()` en sus queries (es una herramienta de
> verificación, no el daemon) — con un esquema incompleto **entra en pánico** en vez de reportar
> elegantemente. Interpretación para el Testeador: pánico = esquema no conforme = FALLO del entorno,
> distinto de FALLO de bAuth. Endurecerlo es brecha C3 (§11).

## 6. `bos_verify` — verificación independiente del ancla blockchain

Verifica pruebas Merkle del ancla D12 **sin depender del daemon** (RFC 6962 + Keccak-256, verificado):

```bash
# Modo OFFLINE — verifica un proof local contra una raíz esperada
bos_verify offline --proof batch-42.proof.json [--expected-root 0x...]

# Modo ONLINE — consulta el smart contract y compara
bos_verify online --rpc <url> --contract <dirección> --batch-id 42

bos_verify version
```

Es la materialización de la **soberanía verificable**: un auditor del cliente puede probar que la
auditoría WORM no fue alterada usando solo el proof y la cadena — bAuth no participa. Detalle del
modelo en [5.02 Blockchain D12](5.02_MANUAL-BLOCKCHAIN-D12-v1.0.md).

> ⚠️ **Inconsistencia detectada (a resolver en la reparación):** la cabecera de `bos_verify.rs`
> menciona **Arbitrum One** como red del modo online, mientras el corpus (CLAUDE, 5.02) declara
> **Besu** como motor blockchain soberano. El RPC es configurable (`--rpc`), así que funciona contra
> cualquier EVM — pero la doctrina debe fijar cuál es la red canónica. Registrado en el informe de
> consistencia; decisión → HITL.

## 7. Prueba cruda por socket (sin CLI)

Para descartar que un fallo sea de `bauthctl` y no del daemon, el Testeador puede hablar JSON-RPC
crudo al socket (ADR-020 — el mismo canal que usan los daemons):

```bash
printf '{"jsonrpc":"2.0","method":"bauth.health.check","params":{},"id":1}\n' \
  | nc -U /run/bos/bauth.sock
# Esperado: {"jsonrpc":"2.0","result":{"status":"operativo","version":"3.0.0",...},"id":1}
```

Cualquier método de la superficie (~115, ver [9.01 §5](9.01_MANUAL-PRODUCTO-v1.0.md)) es invocable
así. Requiere pertenecer al grupo del socket (`bosagent`, modo 0660) — un `Permission denied` aquí
es una prueba POSITIVA del control de acceso del socket, no un fallo.

## 8. La evidencia AA-1 — `verificar_afirmacion.sh`

**Toda afirmación verificable del dictamen DEBE adjuntar evidencia firmada** (C12 — no negociable).
La herramienta canónica de la fábrica:

```bash
# Desde BauthAgent/:
../fabrica/scripts/verificar_afirmacion.sh "<descripción de la afirmación>" <comando>
```

La salida incluye **timestamp + SHA256** del comando y su resultado — se adjunta al informe del
Testeador. Ejemplos aplicados a esta suite:

```bash
../fabrica/scripts/verificar_afirmacion.sh "bauth responde health operativo" \
  "bauthctl health"

../fabrica/scripts/verificar_afirmacion.sh "el binario compila sin errores" \
  "cargo check 2>&1 | tail -1"

../fabrica/scripts/verificar_afirmacion.sh "el socket rechaza a usuarios fuera del grupo" \
  "sudo -u nobody nc -U /run/bos/bauth.sock < /dev/null"
```

**Regla:** afirmación sin su bloque de evidencia = RECHAZO automático del Revisor. Reincidencia =
tarea devuelta.

## 9. Suite de humo delegable — tabla PASS/FAIL

La secuencia mínima que un probador externo ejecuta **sin conocer bAuth por dentro**. Cada fila es
independiente; el dictamen agrega los resultados.

| # | Comando | Salida esperada | PASS si | Nivel |
|---|---------|-----------------|---------|:-----:|
| S1 | `systemctl is-active bauth` | `active` | literal | 1 |
| S2 | `bauthctl health` | JSON `status: "operativo"` + `version` | status exacto | 1 |
| S3 | `bauthctl version` | `bauthctl v3.0.0` | versión = release esperado | 1 |
| S4 | `journalctl -u bauth -p err --since "1 hour ago"` | vacío o solo conocidos | sin errores nuevos | 1 |
| S5 | `bauthctl saga list` | JSON con lista de sagas | lista no vacía | 2 |
| S6 | `bauthctl policy eval 1 1 1` | JSON con resultado de evaluación | respuesta JSON-RPC sin error -32xxx | 2 |
| S7 | `bauthctl role list` | JSON con roles | roles ≥ 1 (seed cargado) | 2 |
| S8 | `bauthctl tenant list` | JSON con tenants | respuesta válida | 2 |
| S9 | `bauthctl ctx validate ctx-inexistente` | Error controlado en español | error LEGIBLE, no crash | 2 |
| S10 | `bauthctl sync status` | JSON de estado del reconcile | respuesta válida | 2 |
| S11 | `verify_policies` (con `DATABASE_URL`) | Resumen con contadores | 0 ❌ de estructura; contadores coherentes | 3 |
| S12 | `bos_verify offline --proof <archivo>` | Veredicto de la prueba Merkle | VÁLIDO para un proof legítimo; INVÁLIDO para uno adulterado | 3 |
| S13 | JSON-RPC crudo (§7) | `status: "operativo"` | igual que S2 (descarta al CLI como variable) | 2 |
| S14 | `sudo -u nobody nc -U /run/bos/bauth.sock` | `Permission denied` | el rechazo ES el pass (0660 funciona) | 2 |

**Prueba negativa obligatoria (S9, S12-adulterado, S14):** una suite que solo prueba caminos felices
no dictamina nada — el Testeador DEBE incluir al menos una prueba que espera el rechazo.

## 10. Protocolo de delegación al Testeador

Cómo se entrega este trabajo a la fábrica (CLAUDE SBOS — staff):

1. **Quién delega:** el humano se lo pide al **Bibliotecario**, que delega en el **Testeador**
   (el Bibliotecario nunca testea él mismo).
2. **Qué recibe el Testeador:** este manual (el contrato de prueba), la versión esperada del
   binario, y acceso a la VPS. NO recibe el "informe de éxito" del desarrollador como fuente.
3. **Qué ejecuta:** la suite §9 (o el subconjunto acordado), cada fila con `verificar_afirmacion.sh`.
4. **Qué entrega:** dictamen **VERDADERO/FALSO por afirmación**, con el bloque de evidencia de cada
   una, depositado en `context/buzon-bibliotecario/TESTEADOR-BAUTH-<ASUNTO>-<YYYYMMDD-HHMM>.md`.
5. **Qué pasa después:** dictamen limpio → el Bibliotecario invoca al Documentador (cierre de
   certificación). Dictamen con FALSO → tarea devuelta al desarrollador con la evidencia del fallo.

> **Regla de oro heredada:** el agente que desarrolló NO escribe el dictamen. Este manual existe
> exactamente para que el dictamen no requiera al desarrollador.

## 11. Madurez L0-L4 y brechas

| Capacidad | Madurez | Nota |
|-----------|:-------:|------|
| CLI de operación (`bauthctl`) | **L2** | 11 comandos reales; parser incompleto vs ayuda (O3 de 6.01) ⚠️ |
| Validador de políticas E2E | **L2** | Pipeline de 7 pasos funcional; `unwrap()` frágil ante esquema incompleto |
| Verificador blockchain independiente | **L2** | Offline/online operativos; red canónica sin fijar (Arbitrum vs Besu) |
| Evidencia firmada AA-1 | **L3** | `verificar_afirmacion.sh` operativa en fábrica ✅ |
| Suite de humo empaquetada | **L1** | Este manual la define (§9); no existe aún como script único ejecutable |

### Brechas priorizadas

| # | Brecha | Prioridad |
|---|--------|:---------:|
| C1 | Empaquetar la suite §9 como `scripts/suite_humo.sh` (una llamada → dictamen tabulado con evidencia AA-1 por fila) | **P1** |
| C2 | Completar el parser de `bauthctl` a la ayuda declarada (= O3 de 6.01) | P2 |
| C3 | Endurecer `verify_policies` (eliminar `unwrap()`, reportar esquema incompleto con mensaje en español y `exit 2`) | P2 |
| C4 | Fijar la red canónica de `bos_verify online` (Besu soberano vs Arbitrum) — decisión HITL | P2 |
| C5 | Agregar `bauthctl` a los paquetes de prueba del Testeador en la VPS (instalación junto al daemon) | P3 |

**Veredicto:** las herramientas de prueba **existen y cubren los 3 niveles** (vivo/decide/íntegro);
la distancia es empaquetado (suite única) y robustez de las herramientas mismas — no falta capacidad
de verificación, falta comodidad de delegación.
