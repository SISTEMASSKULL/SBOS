## 2. La visión: catálogo universal de identidad

En bAuth, **todo es una entidad**. Un empleado es una entidad. Una empresa es una entidad.
Un vehículo es una entidad. Un producto de almacén es una entidad. Un servidor es una entidad.
Una puerta con OSDP es una entidad. Un bot de integración es una entidad.

Todas comparten la misma estructura, las mismas tablas, el mismo motor de validación.
Lo que cambia es el `tipo` y los atributos. Esto permite que el sistema de identidad
Sirva como **registro maestro para cualquier sistema**: RRHH, inventario, flota, TI,
proveedores, clientes, control de acceso físico, catálogo de productos.

**ISO 9001:2015 §3.2.4** define "cliente" como quien recibe el producto/servicio, y
"proveedor" (§3.2.5) como quien lo provee. Una misma entidad (empresa SKULL-CORP) puede
ser AMBAS: cliente de su proveedor de internet, proveedor del SBOS para sus clientes.
No son tipos excluyentes — son **membresías a conjuntos**.

## 3. Las tres tablas de identidad

La arquitectura separa tres responsabilidades en tres tablas:

| Tabla | Responsabilidad | Estructura |
|---|---|---|
| **`idn_identity_entity`** | Jerarquía de entidades | `parent_id` (adjacency list). Niveles: tenant, bdomain, bsubdomain, pos, actor |
| **`idn_identity_attribute`** | Atributos extensibles de cualquier entidad | EAV con `attr_namespace` explícito. `atom_code` vincula con BitMask |
| **`idn_role`** (existente) | Roles y jerarquía DAG | `idn_role_template` + `idn_role_closure` |

### 3.1 `idn_identity_entity` — DDL

```sql
CREATE TABLE IF NOT EXISTS bauth.idn_identity_entity (
    entity_id        UUID        NOT NULL DEFAULT uuidv7(),
    parent_id        UUID        REFERENCES bauth.idn_identity_entity(entity_id) ON DELETE RESTRICT,
    tenant_id        UUID        NOT NULL,
    level            TEXT        NOT NULL CHECK (level IN ('tenant','bdomain','bsubdomain','pos','actor')),
    entity_type      TEXT        NOT NULL,
    name             JSONB       NOT NULL,   -- {"es":"...","en":"..."}
    slug             TEXT        NOT NULL,
    path             TEXT        NOT NULL,   -- tenant.company.branch.pos.actor
    status           TEXT        NOT NULL DEFAULT 'ACTIVE',
    is_internal      BOOLEAN     NOT NULL DEFAULT false,
    sort_order       INT         NOT NULL DEFAULT 0,
    ctx_id           TEXT        NOT NULL,
    created_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (entity_id),
    CONSTRAINT uq_iie_tenant_slug UNIQUE (tenant_id, level, slug)
);
```

### 3.2 `idn_identity_attribute` — DDL

```sql
CREATE TABLE IF NOT EXISTS bauth.idn_identity_attribute (
    attribute_id     UUID        NOT NULL DEFAULT uuidv7(),
    entity_id        UUID        NOT NULL REFERENCES bauth.idn_identity_entity(entity_id) ON DELETE CASCADE,
    attr_namespace   TEXT        NOT NULL,   -- core, professional, verification, security, contact, fiscal
    attr_key         TEXT        NOT NULL,
    attr_value       JSONB       NOT NULL,   -- valor del atributo (texto, número, objeto)
    source           TEXT        NOT NULL DEFAULT 'self',
    is_verified      BOOLEAN     NOT NULL DEFAULT false,
    verified_at      TIMESTAMPTZ,
    verified_by      UUID,
    is_active        BOOLEAN     NOT NULL DEFAULT true,
    sort_order       SMALLINT    NOT NULL DEFAULT 0,
    ctx_id           TEXT        NOT NULL,
    created_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (attribute_id),
    CONSTRAINT uq_iia_entity_key UNIQUE (entity_id, attr_namespace, attr_key)
);
```

## 4. El árbol de 5 niveles con tipos variables

La jerarquía es fija: **5 niveles obligatorios**. Lo que cambia es el `tipo` en cada nivel.

| Nivel | Significado | Ejemplos de `tipo` |
|---|---|---|
| **tenant** | Raíz de aislamiento | interno, externo |
| **bdomain** | Unidad principal | empresa, persona, hogar, desarrollador, m2m, edificio, almacen, catalogo, finca, hospital, hotel, universidad, datacenter, centro_distribucion, obra |
| **bsubdomain** | División | sucursal, dependiente, familiar, oficina, deposito, patio, sala, categoria, parcela, piso, zona, aula, habitacion, facultad |
| **pos** | Punto de operación | caja, terminal, puerta, sensor, actuador, punto_virtual, estante, camara, rack, estacionamiento, rubro, muelle |
| **actor** | Quien opera | HUMAN, SERVICE, DEVICE, BOT, producto, equipo, vehiculo, servidor, storage, switch, firewall, marca, paciente, alumno, huesped, cultivo, maquina, paquete, contenedor |

### 4.1 Ejemplo: la entidad puede ser cualquier cosa

```
SKULL (tenant, interno)

  │     └── Norte (bsubdomain, sucursal)

  ├── Casa-Juan (bdomain, hogar)          ← hogar
  │     └── Principal (bsubdomain, familiar)
  │           └── Puerta-Entrada (pos, puerta)
  │
  ├── Almacén-Central (bdomain, almacen)  ← inventario
  │     └── Depósito-A (bsubdomain, deposito)
  │           └── Estante-01 (pos, estante)

  ├── Datacenter (bdomain, datacenter)    ← TI
```

## 5. Catálogo de Identidades (D93) — gobernanza de tipos

**D93** es el dominio del lenguaje AtomLang que define qué `tipo` es válido para cada `nivel`,
qué atributos son requeridos, y qué conjuntos de membresía son permitidos. Esto elimina
el riesgo del texto libre en `tipo`.

| Dominio | Rol |
|---|---|
| **D93** | Catálogo de Identidades — tipos válidos, atributos requeridos, conjuntos permitidos |
| D94 | Registro de Usuarios — conjuntos de usuarios (USERSET) |
| D95 | Catálogo de Átomos — compilados y listos |
| D96 | Contrato de Métodos — entradas/salidas/flujos auth |
| D97 | Conformidad Normativa — requisitos ISO/NIST/XACML |
| D98 | Registro Estructural — conjuntos de roles (SET) |
| D99 | Administrativo Global — garante transversal |

### 5.1 Membresía a conjuntos — sin duplicación

Una entidad existe UNA SOLA VEZ. Su `tipo` dice QUÉ es. Su pertenencia a conjuntos
(USERSET) dice DÓNDE opera. Mismo patrón que D98 (SET de roles).

```
Juan Pérez (actor, tipo=HUMAN)
  ├── Pertenece a USERSET(autenticacion)   ← puede loguearse
  ├── Pertenece a USERSET(RRHH)            ← es empleado
  ├── Pertenece a USERSET(proveedor)       ← vende servicios freelance
  ├── Pertenece a USERSET(cliente)         ← compra en la tienda interna
  ├── NO pertenece a USERSET(deposito)     ← no es un almacén
  └── NO pertenece a USERSET(flota)        ← no es un vehículo

Camión Volvo (actor, tipo=vehiculo)
  ├── Pertenece a USERSET(flota)           ← es un vehículo
  ├── Pertenece a USERSET(activos_fijos)   ← es un activo
  ├── NO pertenece a USERSET(autenticacion)← no se loguea
  └── NO pertenece a USERSET(RRHH)         ← no es empleado
```

### 5.2 Validación de pertenencia por tipo

D93 define qué conjuntos son válidos para cada tipo de entidad:

```
tipo=persona  → conjuntos_permitidos: [autenticacion, rrhh, proveedor, cliente]
tipo=empresa  → conjuntos_permitidos: [autenticacion, proveedor, cliente]
tipo=vehiculo → conjuntos_permitidos: [flota, activos_fijos]
tipo=producto → conjuntos_permitidos: [inventario]
tipo=servidor → conjuntos_permitidos: [activos_ti, monitoreo]
```

## 6. El motor de identidad — validación de datos

El motor de identidad usa el **mismo lenguaje AtomLang** que el motor BitMask. La diferencia
es el propósito: validar datos, no permisos.

### 6.1 Verbos del motor de identidad

| Verbo | Qué hace |
|---|---|
| `validate` | Valida formato/dato ANTES de guardar. Deny → rechaza el set. |
| `verify` | Verifica contra fuente externa (SIN, SEGIP, ADSIB). Actualiza `verified_by`. |
| `format` | Transforma a formato canónico antes de guardar. |

### 6.2 Ejemplo: validación de NIT boliviano

```yaml
politica "validacion_nit"
  combining_algorithm: deny-overrides

  regla "nit_14_digitos"
    target:
      resource: idn_identity_attribute.tributario
      type: NIT
      verbo: validate
    condition:
      property_id: idn_identity_attribute.value_text
      operator: REGEX
      value: "@bauth_config_param.regex_nit_bo"
    effect:
      decision: Permit

  regla "nit_verificar_en_sin"
    target:
      resource: idn_identity_attribute.tributario
      type: NIT
      verbo: verify
    condition:
      property_id: idn_identity_attribute.source
      operator: "=="
      value: api_sin
    effect:
      decision: Permit
      obligation:
        api_call: sin_verificar_nit
        marca_verificado: true
        verified_by: api_sin
```

### 6.3 API del motor de identidad

```
bauth.entidad.atributo.get(entity_id, resource, type?)
  → { value_text, value_data, display_format, is_verified, verified_by }

bauth.entidad.atributo.set(entity_id, resource, type, value)
  → Evalúa reglas → Permit (guarda) o Deny (error)

bauth.entidad.atributo.list(entity_id, category?)
  → [{ resource, type, value_text, display_format, ... }]

bauth.entidad.atributo.search(resource, type, value_pattern)
  → [{ entity_id, nombre, value_text }]
```

## 7. Prueba de escritorio — el sistema registra cualquier cosa

El sistema de identidad de bAuth es un **catálogo universal**. Las 5 capas con `tipo`
variable y los atributos en `idn_identity_attribute` permiten modelar cualquier dominio sin
tocar el DDL:

| Sector | bdomain | bsubdomain | pos | actor |
|---|---|---|---|---|
| RRHH | empresa | sucursal | oficina | empleado (HUMAN) |
| Inventario | almacen | deposito | estante, cámara | producto, equipo |
| Flota | empresa | patio | estacionamiento | vehiculo, equipo |
| TI | datacenter | sala | rack | servidor, switch, storage, firewall |
| Catálogo | catalogo | categoria | rubro | marca |
| Educación | universidad | facultad | aula | alumno, profesor |
| Salud | hospital | piso | habitacion | paciente, medico, equipo_medico |
| Hotelería | hotel | piso | habitacion | huesped |
| Agricultura | finca | parcela | silo | cultivo, maquinaria |
| Construcción | obra | sector | zona | maquina, operario |
| Logística | centro_distribucion | zona | muelle | paquete, contenedor |

**Mismas 5 tablas. Mismo motor de validación. Mismas políticas AtomLang.**
Agregar un sector nuevo es agregar `tipo` al catálogo D93 y definir sus atributos requeridos.
Nunca un ALTER TABLE.

## 8. Conexión con el Context Plane (ctx_id)

El ctx_id (SBOS-049) transporta el árbol D00 en cada request. Las primeras 4 capas son
exactamente los niveles de `idn_identity_entity`:

```
ctx_id = interno.{tenant_id}.{bdomain_id}.{bsubdomain_id}.{pos_logico}.{user_id}.{traceparent}
         ────── ─────────────────────────────────────────────────── ──────── ──────────
         prefijo   árbol D00 (4 capas)                               actor    W3C

El prefijo `interno.` o `externo.` se deriva de idn_tenant.is_internal.
Va INCRUSTADO en el string. No se consulta. BOS lo lee UNA VEZ al crear la sesión.
```

## 9. Conexión con roles y BitMask — gobernanza de atributos

Los atributos de identidad son gobernados por átomos D00. El `atom_code` en `idn_identity_attribute`
vincula cada atributo con un átomo en `privilege_atom`. Los átomos se asignan a roles vía
`privilege_role_atom`. Los roles se asignan a usuarios vía `idn_user_role`. El UserBitMask
determina quién puede ver/editar cada atributo.

```
idn_identity_attribute.atom_code ──→ privilege_atom ──→ privilege_role_atom ──→ idn_role_template
                                                       │
                                                       ▼
                                              idn_user_role ──→ idn_user_template
                                                       │
                                                       ▼
                                              UserBitMask[pos] == 1 → Permit
```

El detalle completo de la gobernanza está en [A.50](anexos/A.50_ANEXO-MODELO-SIMPLIFICADO-ROLES-USUARIOS-v1.0.md)
y [A.51](anexos/A.51_ANEXO-MERGE-ROLES-TEMPORAL-v1.0.md).

## 10. Estado del arte y comparativa

### 10.1 Lo que hace la industria

- **Azure AD / Okta / SailPoint**: todos usan variaciones de este patrón (entidad genérica + atributos extensibles). Ninguno modela vehículos, productos de almacén o puertas como ciudadanos de primera clase.
- **GLEIF vLEI (ISO 17442-3:2024)**: identidad organizacional verificable criptográficamente. El modelo D00 está alineado.
- **SCIM 2.0 (RFC 7643)**: el UserTemplate de bAuth ya está alineado con SCIM Enterprise.

### 10.2 Diferenciadores de bAuth

- Catálogo universal de 5 niveles con tipos variables (no solo personas y empresas)
- Motor de validación de identidad con el mismo lenguaje que las políticas de acceso
- Gobernanza unificada: los átomos D00 son átomos del BitMask, no un sistema separado
- Soberano: sin proveedores externos de identidad

## §12 — v2.1.0: El potencial completo del sistema de identidad (2026-07-15)

### 12.1 Los 37 dominios de identidad

| Tipo de ente | # | Dominios |
|---|---|---|
| **PERSONA** | 16 | civil, familiar, educativo, laboral, autenticacion, cliente, proveedor, productor, independiente, propietario, inquilino, paciente, fiscal, financiero, viajero, asegurado |
| **ORGANIZACION** | 13 | civil, cliente, proveedor, productor, empleador, fiscal, propietario, inquilino, importador, exportador, franquiciado, franquiciante, financiero |
| **COSAS** | 8 | origen, comercial, propiedad, alquilado, operativo, asegurado, siniestrado, desactivado |

Cada dominio es una capa de atributos que se agrega/quita durante el ciclo de vida.
La historia se preserva. Nada se borra. Respaldado por SAP Business Partner, Odoo
res.partner e ISO 9001:2015.

### 12.2 Flexibilidad por registro — sin esquema fijo

Un código de farol puede tener 2 atributos o 100. El sistema no impone un esquema.
Cada entidad define sus propios atributos. DEPO define 8 para su farol. BOSCH define
11 para el suyo. La Tiendita agrega 7 más. Sin conflicto. Sin ALTER TABLE.

### 12.3 Relaciones N-to-N nativas

Un farol puede ser compatible con 4 sistemas de Toyota + 2 de Nissan + 1 de Honda.
Múltiples fabricantes (DEPO, BOSCH) compiten con productos para el mismo sistema.
Una mantequilla distribuida por N distribuidores. Un chocolate custodiado en N puntos
de entrega. Todo resuelto con múltiples filas en `idn_identity_attribute`.

### 12.4 Multi-tenant con visibilidad controlada

Cada tenant es una isla. `tenant_id` + `ctx_id` garantizan aislamiento. Referencias
cross-tenant con `origen_tenant` en `value_data`. Visibilidad PRIVADA por defecto:
nadie sabe que existes. COMPARTIDA: el dueño del código puede verte. PUBLICA: todos.

### 12.5 Trazabilidad y auditoría

`value_data` JSONB registra quién referenció qué, con qué visibilidad, y desde qué
tenant. Auditoría completa de uso de códigos entre tenants. Base para modelos de
negocio (porcentaje por referencia, marketplace, recomendaciones).

### 12.6 El ctx_id con identidades variables

La estructura del ctx_id NO cambia: 6 segmentos fijos. Los valores vienen de
`idn_identity_entity.slug`. La diversidad está en los ~40 tipos posibles, no en la forma.
Solo los ACTORES tienen ctx_id. El resto son referenciados.
