## 1. Audiencia, propósito y alcance

Este manual es el **runbook operativo** del daemon `bauth`: cómo se arranca, se supervisa, se
diagnostica y se **recupera** — la Fase 6 (Recuperación) del ciclo cerrado de seguridad de identidad.
No documenta *qué decide* bAuth (eso es el resto del corpus) sino *cómo se lo mantiene vivo, sano y
restaurable* en el servidor del cliente.

**Audiencia:** operadores SRE/SysAdmin, el instalador `bos`, analistas de guardia (on-call).

**Por qué es crítico:** bAuth es el cimiento — sin él no hay autenticación, roles, permisos,
facturación ni acceso físico. Un bAuth caído es una **interrupción total del ecosistema**. La calidad
de su operación (arranque determinista, recuperación en minutos, cero pérdida de identidad) es parte
de la categoría IAM Enterprise: la resiliencia es un requisito, no un lujo.

## 2. Identidad del servicio

| Atributo | Valor (verificado en `bauth.service`) |
|----------|----------------------------------------|
| Unidad systemd | `bauth.service` — "SBOS bAuth — Identity Core v2.0" |
| Tipo | **`Type=notify`** (`NotifyAccess=main`) — el daemon avisa READY=1 cuando está listo |
| Binario | `/usr/local/bin/bauth` |
| Usuario / grupo | `User=bauth` · `Group=bosagent` (+ `systemd-journal`) |
| Socket | `/run/bos/bauth.sock` (Interface Dual ADR-020: WebSocket RPC + JSON-RPC 2.0) |
| Config | `/etc/bos/bauth.toml` (montado `ReadOnly`) |
| Watchdog | **`WatchdogSec=30s`** — systemd mata y reinicia si no hay latido |
| Restart | `on-failure`, `RestartSec=5s`, salvo `SIGKILL` |
| Reload | `ExecReload=/bin/kill -HUP $MAINPID` → recarga config sin reiniciar |
| Timeouts | `TimeoutStartSec=30s` · `TimeoutStopSec=10s` |
| Logging | journald, `SyslogIdentifier=bauth`, salida estructurada JSON |

**Regla SBOS:** bAuth corre como **daemon systemd en el host** (no pod K8s). K8s solo aloja la
infraestructura (PostgreSQL, Redis, Vault). El socket es la **única** superficie entre daemons — nunca
HTTP/TCP entre daemons (SBOS-050 P9).

## 3. El ciclo de vida — arranque en 6 fases

`main.rs` arranca en una secuencia **determinista** de 6 fases (verificado). Conocerla es la base del
diagnóstico: cada fallo de arranque cae en una fase concreta.

```
Fase 0  Logging          tracing JSON + EnvFilter (RUST_LOG)
Fase 1  Preflight        valida entorno ANTES de todo: socket path, grupo bosagent,
                         permisos dir 0o750, /etc/bos/bauth.toml, min 4096 FDs
                         └─ falla → exit(2) con mensajes accionables
Fase 2  Configuración    carga /etc/bos/bauth.toml
                         └─ falla → exit(1)
Fase 2.5 Base de datos   conecta PostgreSQL + Redis
                         └─ falla → WARN "modo degradado" (NO aborta, §7)
Fase 3  Drenaje          DrainManager (para el cierre graceful)
Fase 4  Dispatcher       JSON-RPC 2.0 + JwtSigner Ed25519 + registro de handlers
Fase 5  Servidor         escucha en /run/bos/bauth.sock · reconcile loop (60s) ·
                         calendar alarm poller (60s)
Fase 5+ systemd notify   envía READY=1 → systemd marca el servicio "active"
Fase 6  Señales          espera SIGTERM/SIGINT (→ drenaje) o SIGHUP (→ reload config)
```

> **Preflight (Fase 1) es la red de seguridad:** valida el entorno *antes* de tocar nada y aborta con
> exit(2) y mensajes accionables si algo falta. La mayoría de fallos de despliegue (permisos de socket,
> config ausente, límite de FDs bajo) se atrapan aquí, no en runtime.

**Cierre graceful:** al recibir SIGTERM, bAuth **drena** las conexiones activas con timeout
`DRAIN_TIMEOUT_SECS = 5s` (verificado). Si drena limpio → "detenido limpiamente"; si expira →
"drenaje forzado — quedaron conexiones activas". Sale con `exit(0)`.

## 4. Operación básica — arranque, parada, reload, estado

```bash
# Instalación de la unidad (una vez)
sudo cp bauth.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now bauth      # habilita + arranca

# Operación diaria
sudo systemctl start bauth             # arrancar
sudo systemctl stop bauth              # parar (SIGTERM → drenaje 5s)
sudo systemctl restart bauth           # reiniciar
sudo systemctl reload bauth            # SIGHUP → recarga /etc/bos/bauth.toml SIN reiniciar
sudo systemctl status bauth            # estado + últimas líneas de log

# Verificación de que está vivo y respondiendo (no solo "active")
bauthctl health                        # RPC real al socket → {"status":"operativo",...}
```

> **`reload` vs `restart`:** `reload` (SIGHUP) recarga la configuración **sin cortar el socket ni las
> sesiones** — es la operación preferida para cambios de config. `restart` corta el servicio (drenaje
> 5s) y debe reservarse para upgrades de binario.

## 5. Dependencias y orden de arranque

`bauth.service` declara (verificado):

```ini
After=network-online.target postgresql.service redis.service
Wants=network-online.target postgresql.service redis.service
Requires=postgresql.service
```

| Dependencia | Relación | Efecto si falta |
|-------------|----------|-----------------|
| **PostgreSQL** | `Requires` (dura) | Si postgres no arranca, systemd **no arranca** bauth |
| **Redis** | `Wants` (blanda) | bauth arranca; cache de BitmaskBundle/sesiones degradada |
| **network-online** | `Wants` + `After` | Espera la red antes de arrancar |

**DDL y seeds NO son responsabilidad del daemon** (verificado, `main.rs` Fase 2.5): la DDL y los
catálogos los instala `bosctl install`. El daemon solo **conecta** — no verifica esquema ni precarga.
Cualquier handler que necesite datos los consulta *lazy* de PostgreSQL. Consecuencia operativa: un
bAuth que arranca no garantiza que el esquema esté completo — eso lo valida el instalador.

## 6. Configuración — `/etc/bos/bauth.toml`

Se carga en Fase 2 (`config::load()`) y se recarga con SIGHUP (`config::reload()`). Secciones
(verificadas en `config/mod.rs`):

| Sección | Claves principales | Para qué |
|---------|--------------------|----------|
| `[server]` | `socket_path`, `socket_perms` (0660), `socket_group` (bos), `max_request_bytes` | El socket y sus límites |
| `[database]` | `url`, `pool_size`, `connect_timeout_secs` | PostgreSQL `bauth` schema |
| `[redis]` | `url`, `default_ttl_secs` | Cache de bundles y sesiones |
| `[jwt]` | `issuer`, `jwks_uri` | Emisión y verificación de tokens |
| `[hibp]` | `api_url`, `timeout_secs` | Screening de contraseñas (Have I Been Pwned) |
| `[engines]` / `[nexus]` | `grpc_socket_path` | Integración con bhnexus |
| `[audit]` | `default_level` | Nivel de auditoría por defecto |
| `[financial]` | límites D3 | Umbrales financieros |

> **Regla de operación:** el archivo se monta `ReadOnlyPaths=/etc/bos/bauth.toml` en la unidad — el
> daemon **no puede** escribir su propia config. Los cambios se hacen fuera y se aplican con
> `systemctl reload bauth`.

## 7. Modos degradados y códigos de salida

bAuth distingue fallos **fatales** (aborta) de fallos **tolerables** (opera degradado). Saberlo evita
diagnósticos equivocados.

| Situación | Comportamiento | Código |
|-----------|----------------|:------:|
| Preflight falla (socket/config/FDs) | **Aborta** con mensajes accionables | `exit(2)` |
| Config `/etc/bos/bauth.toml` inválida/ausente | **Aborta** | `exit(1)` |
| JwtSigner no puede generar clave | **Aborta** | `exit(1)` |
| **PostgreSQL no disponible** | **Modo degradado** — el socket sube, pero **sin reconcile loop** ni datos | opera |
| **Redis no disponible** | Opera — cache degradada (más latencia, sin corte) | opera |
| Drenaje excede 5s al parar | Fuerza cierre, avisa conexiones activas | `exit(0)` |

> **⚠️ Modo degradado (DB caída):** bAuth **arranca igual** y el socket responde `health`, pero el
> reconcile loop **no corre** (verificado, `main.rs`: *"reconcile loop no iniciado — base de datos no
> disponible"*) y los handlers que consultan datos fallarán *lazy*. Un `systemctl status` en verde
> **no** garantiza plena funcionalidad — por eso `bauthctl health` + verificación de DB es el chequeo
> real. Este es un patrón deliberado: preferir "disponible parcial" a "caído total".

## 8. Salud y observabilidad

### 8.1 Los tres niveles de "¿está sano?"

```
1. ¿systemd lo tiene activo?   systemctl is-active bauth      → active/failed
2. ¿el watchdog late?          (automático — WatchdogSec=30s; si no late, systemd reinicia)
3. ¿responde el socket?        bauthctl health                → {"status":"operativo"}
```

`bauth.health.check` retorna (verificado, `health.rs`): `status: "operativo"`, `version`, `socket`,
`uptime_seconds`. Es el único chequeo que prueba el **camino completo** (socket → dispatcher → handler).

### 8.2 Logs

```bash
journalctl -u bauth -f                      # seguir en vivo
journalctl -u bauth --since "10 min ago"    # ventana reciente
journalctl -u bauth -p err                  # solo errores
journalctl -u bauth -o json | jq .          # log estructurado (tracing JSON)
```

Los logs son **JSON estructurado** (`tracing_subscriber::fmt().json()`), filtrados por `RUST_LOG`
(EnvFilter). Todo evento lleva `ctx_id` cuando aplica (SBOS-049). Identidad de syslog: `bauth`.

### 8.3 SIEM

La salida a **Wazuh** vía syslog es **diseño, no código** (corrección 2026-07-10: no existe
`audit/siem.rs` ni referencia a Wazuh/syslog en `src/` — verificado con grep). El diseño vive en
[5.01 Auditoría y Trazabilidad §7](5.01_MANUAL-AUDITORIA-TRAZABILIDAD-v1.0.md); implementarlo es
brecha de esa fase. Lo que SÍ existe hoy: journald estructurado (§8.2) y los eventos de seguridad
al canal Seguridad vía bNotify (§ [4.01](4.01_MANUAL-BAUTH-BNOTIFY-v1.0.md)).

## 9. `bauthctl` — operación del daemon

`bauthctl` es la CLI que habla JSON-RPC 2.0 al socket. Usa `BAUTH_SOCKET` o `--socket`
(default `/run/bos/bauth.sock`). **11 comandos** (verificado):

| Comando | Operación | Ejemplo |
|---------|-----------|---------|
| `health` | Estado del daemon | `bauthctl health` |
| `version` | Versión del binario | `bauthctl version` |
| `role list` / `role compute <id>` | Roles y cálculo de BitMask | `bauthctl role compute ROL-CAJERO` |
| `user list` | Usuarios | `bauthctl user list` |
| `auth login <user>` / `auth mfa <code>` | Login (contraseña sin eco) y MFA TOTP | `bauthctl auth login juan` |
| `ctx validate <ctx_id>` | Validar un contexto | `bauthctl ctx validate ctx-abc123` |
| `policy eval <app> <grp> <atom>` | Evaluar un átomo de permiso | `bauthctl policy eval 1 1 1` |
| `saga list` / `saga execute <n>` | Sagas de autenticación | `bauthctl saga list` |
| `sign internal <payload>` | Firma Ed25519 interna | `bauthctl sign internal <hex>` |
| `tenant list` | Tenants | `bauthctl tenant list` |
| `sync reconcile` / `sync status` | Forzar/consultar reconcile | `bauthctl sync reconcile` |

> **Nota de estado:** el `print_usage` de `bauthctl` lista más operaciones de ejemplo (role create,
> user assign-role, sign external-factura, tenant create) que aún **no** están cableadas en el parser
> — los subcomandos implementados son los de la tabla. Es una brecha de completitud de la CLI (§15).

## 10. El reconcile loop y la detección de drift

Cada **60 segundos** (verificado, `sync/mod.rs`: `interval(Duration::from_secs(60))`), bAuth compara
el **estado declarado** (su `bauth` schema) con el **estado real** y corrige la deriva:

| Tarea del reconcile | Qué hace |
|---------------------|----------|
| Drift de políticas | Revalida que las políticas activas coinciden con lo declarado |
| Revalidación de contextos | Verifica los `ctx_id` vigentes |
| Invalidación de sesiones expiradas | Marca `EXPIRED` las sesiones vencidas |
| Emisión de eventos CAEP | Detecta `session-revoked` (hoy **loguea**, no despacha — ver [4.01 §6](4.01_MANUAL-BAUTH-BNOTIFY-v1.0.md)) |

Operación manual:

```bash
bauthctl sync reconcile     # forzar un ciclo ahora (no esperar los 60s)
bauthctl sync status        # ver el último resultado
```

**Requiere DB:** en modo degradado (sin PostgreSQL) el reconcile loop no arranca. Restaurada la DB,
**reinicie** el daemon para relanzarlo (`systemctl restart bauth`).

## 11. Break-glass y recuperación

El núcleo de la Fase 6. Escenarios ordenados de menor a mayor severidad.

### 11.1 El daemon no arranca

```bash
systemctl status bauth                 # ¿qué fase falló?
journalctl -u bauth -n 50 --no-pager   # el mensaje de preflight es accionable
```

| Síntoma en el log | Causa | Acción |
|-------------------|-------|--------|
| `preflight falló` (exit 2) | Socket/grupo/permisos/FDs | Corregir lo que preflight indica (crear `/run/bos`, grupo `bosagent`, subir FDs) |
| `fallo al cargar configuración` (exit 1) | TOML inválido/ausente | Validar `/etc/bos/bauth.toml` |
| `base de datos no disponible` (WARN) | PostgreSQL caído | Arrancar postgres; bauth ya está degradado |
| Reinicios en bucle | Fallo repetido | `RestartSec=5s` da respiro; ver la causa raíz en el log antes de `RestartPreventExitStatus` |

### 11.2 Clave de firma — el break-glass más delicado

> **⚠️ Estado real (verificado, `main.rs`):** hoy el `JwtSigner` arranca en **modo development** con
> una **clave Ed25519 efímera** generada en memoria (WARN: *"en prod usar Vault PKI. H-031"*).
> **Implicación operativa:** al reiniciar bAuth, la clave cambia → **todos los JWT emitidos dejan de
> validar** hasta que los consumidores refresquen el JWKS. Para producción, la clave DEBE provenir de
> **Vault PKI** (persistente, rotable con solapamiento) — es la **brecha P1** de operación (§15). El
> procedimiento de rotación con solapamiento (publicar nueva + mantener anterior ≥ 1h) está
> especificado en el contrato con bNotify ([4.01 §5.1](4.01_MANUAL-BAUTH-BNOTIFY-v1.0.md), C-BNOTIFY-003).

### 11.3 Revocación de emergencia (contención de incidente)

Ante una sesión/credencial comprometida: invalidar el contexto en bAuth (`ctx.invalidate`) → el
reconcile la marca `EXPIRED` → se emite `session-revoked` (CAEP). El SLA objetivo extremo a extremo es
**< 35 s** (revocación → CAEP < 5 s → bNotify suspende entregas < 30 s, contrato C-BNOTIFY-002).

### 11.4 Recuperación total (host perdido)

Como la DDL/seeds son del instalador y no del daemon (§5), la reconstrucción es:
1. Reinstalar infraestructura (PostgreSQL, Redis, Vault) — `bosctl install`.
2. Restaurar el `bauth` schema desde respaldo (§12).
3. Restaurar el material de claves desde Vault (no desde archivos).
4. `systemctl enable --now bauth` → preflight valida → reconcile reconstruye el estado en vivo.

> **⚠️ No hay un `bootstrap.rs` codificado** (verificado: `sync/` solo tiene `mod.rs`). La
> reconstrucción-desde-cero es **operativa** (instalador + restore), no un comando del daemon. Diseñar
> un flujo de bootstrap idempotente es brecha P2 (§15).

## 12. Respaldo y restauración

**Qué respaldar (los tres activos de estado de bAuth):**

| Activo | Dónde vive | Cómo respaldar |
|--------|-----------|----------------|
| Estado de identidad/roles/sesiones | `bauth` schema en `SBOS_db` (PostgreSQL) | `pg_dump -n bauth` (lógico) o snapshot del cluster |
| Material de claves de firma | **Vault** (Ed25519 interno, RSA ADSIB externo) | Backup/unseal de Vault — nunca en archivos |
| Configuración | `/etc/bos/bauth.toml` | Versionar fuera del host |

**Cache (Redis)** NO se respalda — es reconstruible (bundles, sesiones) desde PostgreSQL en el
próximo reconcile.

> **⚠️ Brecha:** no hay scripts de backup/restore versionados en el repo (verificado). El respaldo es
> hoy responsabilidad de la operación del cluster PostgreSQL/Vault, no un procedimiento propio de
> bAuth. Estandarizar `backup.sh`/`restore.sh` con evidencia AA-1 es brecha P2 (§15).

## 13. Runbook de troubleshooting

| Síntoma | Diagnóstico | Resolución |
|---------|-------------|------------|
| `systemctl status` = active pero `bauthctl health` falla | Socket vivo pero handler colgado, o permisos de socket | Ver `journalctl`; revisar grupo/permisos de `/run/bos/bauth.sock` |
| `bauthctl: no se pudo conectar a /run/bos/bauth.sock` | Daemon caído o socket ausente | `systemctl status bauth`; ¿preflight creó el socket? |
| Reinicios cada 5s | Fallo de arranque repetido | `journalctl -u bauth`: identificar la fase (preflight/config/signer) |
| Tokens dejan de validar tras restart | Clave efímera (§11.2) | Migrar a Vault PKI; mientras tanto, avisar refresco de JWKS |
| `reconcile loop no iniciado` en log | DB no disponible al arrancar | Arrancar PostgreSQL y `systemctl restart bauth` |
| Watchdog reinicia el servicio | El daemon no envió latido en 30s (bloqueo) | Revisar bloqueos/saturación; subir `WatchdogSec` solo como último recurso |
| Latencia alta en operaciones | Redis caído (cache degradada) | Restaurar Redis; el reconcile repuebla la cache |

## 14. Hardening — la postura de seguridad del servicio

`bauth.service` aplica un sandbox systemd **estricto** (verificado) — parte de la categoría IAM
Enterprise (defensa en profundidad a nivel de proceso):

| Control | Valor | Efecto |
|---------|-------|--------|
| `ProtectSystem=strict` + `ProtectHome=true` | FS de solo lectura salvo `ReadWritePaths=/run/bos` | El daemon no puede tocar el sistema |
| `NoNewPrivileges=true` | Sin escalada | No puede ganar privilegios |
| `CapabilityBoundingSet=CAP_NET_BIND_SERVICE` | Solo esa capacidad | Mínimo privilegio |
| `SystemCallFilter=@system-service @network-io` | Lista blanca de syscalls | Reduce superficie de kernel |
| `MemoryDenyWriteExecute=true` | W^X | Bloquea inyección de código |
| `PrivateTmp` · `PrivateDevices` · `ProtectKernel*` | Aislamiento | Sin `/tmp` compartido, sin dispositivos, sin kernel |
| `RestrictAddressFamilies=AF_UNIX AF_INET AF_INET6` | Familias limitadas | Coherente con el socket Unix |
| `LimitNOFILE=65536` | FDs | Capacidad de conexiones concurrentes |

Estos controles materializan SBOS-047 (ISO 27001) a nivel de unidad: aunque un atacante comprometiera
el proceso, el sandbox limita drásticamente lo que puede hacer en el host.

## 15. Madurez L0-L4 y brechas

**Escala:** L0 Ad-hoc · L1 Diseñado · L2 Implementado · L3 Integrado (operativo) · L4 Optimizado.

| Capacidad operativa | Madurez | Nota |
|---------------------|:-------:|------|
| Servicio systemd + hardening | **L3** | Unidad completa, sandbox estricto, watchdog ✅ |
| Arranque determinista (6 fases + preflight) | **L3** | Preflight accionable, modo degradado ✅ |
| Salud y logs | **L3** | health RPC + journal JSON ✅ (salida SIEM/Wazuh: diseño — 5.01) |
| `bauthctl` | **L2** | 11 comandos; parser incompleto vs el usage ⚠️ |
| Reconcile / drift | **L2** | Corre 60s; CAEP solo loguea (4.01) ⚠️ |
| Gestión de claves de firma | **L1** | ⚠️ **clave efímera dev** — falta Vault PKI |
| Bootstrap-desde-cero | **L1** | Sin `bootstrap.rs`; reconstrucción manual |
| Backup/restore | **L1** | Sin scripts propios versionados |

### Brechas priorizadas

| # | Brecha | Prioridad |
|---|--------|:---------:|
| O1 | **JwtSigner → Vault PKI** (clave persistente, rotación con solapamiento) — hoy efímera (§11.2, H-031) | **P1** |
| O2 | Cablear despacho real de CAEP en el reconcile (hoy loguea) — ver 4.01 §6 | **P1** |
| O3 | Completar el parser de `bauthctl` (role create, user assign-role, sign external, tenant create) | P2 |
| O4 | Flujo `bootstrap` idempotente (reconstrucción-desde-cero como comando) | P2 |
| O5 | Scripts `backup.sh`/`restore.sh` del `bauth` schema + Vault, con evidencia AA-1 | P2 |
| O6 | Reinicio automático del reconcile al restaurarse la DB (sin `restart` manual) | P3 |

**Veredicto (carta rectora IAM Enterprise):** la **operabilidad base es L3** (servicio robusto,
hardening, arranque determinista, salud). Las brechas son de **resiliencia avanzada** (claves
persistentes, bootstrap, backup automatizado) — distancia de integración, no de arquitectura.
