## 1. Audiencia, propósito y alcance

Este manual documenta el **frontend de bAuth**: el Dashboard de administración (Flutter), su
sistema de diseño, su conexión con el daemon y los prototipos HTML de prueba que sirven de
referencia de UX. Fusiona "interfaz de usuario" y "frontend" en un solo manual (decisión de
alcance del INDICE).

**Audiencia:** desarrolladores frontend (Flutter/Dart), diseñadores, administradores que operan
el Dashboard, quien construya un cliente contra el daemon.

**Deslinde:** el widget de atributos se ancla en [MANUAL-ATRIBUTOS](1.07_MANUAL-ATRIBUTOS-v1.0.md)
§6 (máscaras/validación); los prototipos de composición y reglas se introdujeron en
[MANUAL-POLITICAS](2.05_MANUAL-POLITICAS-v1.0.md) §6.4/§10.3 — aquí se documenta el frontend como
producto unificado.

---

## 2. El propósito — un Dashboard soberano

El Dashboard es la cara humana de bAuth: la herramienta con que el SU y los administradores
componen roles, gestionan usuarios, definen políticas y monitorean los 12 dominios en tiempo
real. Es **soberano** en el mismo sentido que el daemon: corre en la infraestructura del
cliente, se conecta al socket local, no llama a ninguna nube.

**El principio de UX rector** (heredado del daemon): *el frontend refleja el modelo atómico* —
el árbol `dominio.aplicación.módulo.verbo` que el usuario ve en pantalla es el mismo
`d.a.m.v` del catálogo. No hay traducción entre "lo que el sistema es" y "lo que el usuario
ve" — la UI es el modelo hecho visible.

## 3. El stack — Flutter + Riverpod + WebSocket

El stack definitivo (`PLAN-DESKTOP-BAUTH.md`, verificado):

| Capa | Tecnología | Rol |
|------|-----------|-----|
| Framework | **Flutter 3.44+** (Dart ≥3.4.0) | UI multiplataforma nativa (desktop primero) |
| Componentes | `tf_shadcn_flutter` 0.0.53 (84+ componentes) | Base UI con árbol nativo |
| Estado | `flutter_riverpod` 3.x + `riverpod_annotation` | State management con providers por módulo (scoped) |
| Transporte | `web_socket_channel` 2.4 | WebSocket hacia el daemon (ADR-020) |
| Tablas | `pluto_grid` 8.0 | Grids avanzados (roles, usuarios, políticas) |
| Gráficos | `fl_chart` 0.70 | Métricas de los 12 dominios |
| Ruteo | `go_router` 14 | Navegación declarativa + deep linking |
| Inmutabilidad | `freezed` + `json_serializable` | Estado inmutable + serialización |

**Por qué Flutter y no web:** el Dashboard es una app de escritorio soberana — se instala en la
máquina del administrador, no se sirve desde un servidor. Flutter compila a binario nativo
(Linux/Windows/Mac), coherente con el "systemd en el host" del ecosistema. La regla de
providers: **scoped por módulo** para evitar rebuilds globales (práctica estándar 2026).

## 4. El sistema de diseño — SBOS Dark Professional

`DESIGN-DESKTOP-BAUTH.md` define un sistema de diseño completo con **CSS custom properties**
(regla R1: todo color, fuente, espacio y sombra es una variable). La paleta **SBOS Dark**:

### 4.1 Fondos (escala de profundidad)

```
--color-bg-root:      #060A10   Fondo raíz (el más profundo)
--color-bg-primary:   #0B1018   Panel principal
--color-bg-secondary: #0F161F   Cards, secciones
--color-bg-tertiary:  #141C28   Inputs, celdas
--color-bg-elevated:  #192230   Modales, popups
--color-bg-hover:     #1E2A3A   Hover
--color-bg-active:    #243040   Seleccionado
```

La escala de 7 fondos crea **profundidad por elevación** — un modal (`elevated`) flota sobre un
card (`secondary`) que flota sobre el panel (`primary`). El ojo lee la jerarquía sin bordes.

### 4.2 Texto y acento

```
Texto:   primary #E8EEF6 · secondary #8899B0 · tertiary #556880   (jerarquía de 3 niveles)
Acento:  #3B82F6 (azul) · hover #4F94F7 · active #2563EB · subtle 10%
```

Un solo color de acento (azul), usado con restricción — la disciplina del sistema es que el
color **significa algo** (§5), no decora.

## 5. Los colores por dominio — el semáforo de 12 planos

La decisión de diseño más distintiva: **cada uno de los 12 dominios tiene su color asignado** —
el color codifica el plano de control, no la estética:

| Dominio | Color | Dominio | Color |
|---------|-------|---------|-------|
| D1 Lógico | `#8B5CF6` violeta | D7 Red | `#6366F1` índigo |
| D2 Físico | `#F97316` naranja | D8 Contexto | (escala) |
| D3 Financiero | `#22C55E` verde | D9 Credenciales | (escala) |
| D4 Temporal | `#3B82F6` azul | D10 Delegación | (escala) |
| D5 Biométrico | `#EC4899` rosa | D11 Auditoría | (escala) |
| D6 Geoespacial | `#14B8A6` teal | D12 Blockchain | (escala) |

Más el **semáforo semántico** (separado del acento y de los dominios): success `#22C55E` ·
warning `#EAB308` · error `#EF4444` · info `#06B6D4`. La regla de oro del diseño de información:
el color de dominio, el de estado y el de acento son **tres sistemas distintos** — un átomo D3
es verde por ser financiero, no por estar "bien"; el "bien" es el semáforo.

## 6. La conexión con el daemon — WebSocket RPC

El Dashboard es un cliente de la **Vía 1 de la Interface Dual** (ADR-020): WebSocket RPC sobre
el socket Unix. El daemon implementa WebSocket **RFC 6455 nativo** (`server/websocket.rs`,
verificado — sin dependencias externas, solo RFC 6455 + base64):

```
Flutter (web_socket_channel) ──wss──► /run/bos/bauth.sock ──► WebSocket RPC (humanos/CLI)
                                                             └► JSON-RPC 2.0 (daemons)
```

**La separación de vías es de seguridad** (MANUAL-SEGURIDAD §5): el Dashboard humano usa
WebSocket; los daemons usan JSON-RPC — misma superficie de socket, distinto protocolo, distinto
tipo de cliente. El Dashboard nunca abre un puerto TCP: se conecta al socket local del daemon
que corre en la misma máquina.

## 7. Los prototipos de prueba — HTML como referencia de UX

Antes del Flutter definitivo, cuatro prototipos HTML validaron la UX y **son la referencia
canónica de diseño** para implementar en Flutter:

| Prototipo | Tamaño | Qué valida | Referencia |
|-----------|:------:|-----------|-----------|
| `rol-template-builder.html` | 140KB | Composición rol/usuario con **METHOD_BUNDLES** (método×dominio → pols+attrs+atoms) · 6 paneles | POLITICAS §6.4 |
| `bauth-rules-ui.html` | 60KB | 9 vistas de tablas de política operativa + **Break-Glass** + gate «Modificar — AAL3» | POLITICAS §10.3 |
| `bAuth Desktop.html` | 625KB | El Dashboard completo — la maqueta de referencia del Flutter | DESIGN-DESKTOP |
| `webauthn-demo.html` | 4.5KB | Flujo WebAuthn/passkey en el navegador (`webauthn.js`) | AUTENTICACION §4.3 |

Estos prototipos **no son producción** — son la especificación visual ejecutable. El plan de
8 fases (`PLAN-DESKTOP-BAUTH.md`) migra de estas maquetas HTML al Flutter nativo, preservando el
sistema de diseño y los patrones de UX que ya validaron.

**Dos patrones de UX que quedaron como norma** (de los prototipos):
1. **«Modificar — AAL3»**: los botones de acción sensible exigen el nivel de aseguramiento en la
   propia UI — el anillo de autenticación aplicado literalmente al botón.
2. **Break-Glass visible**: el override de emergencia no se esconde — es una vista de primera
   clase con motivo + ticket + ventana + autorizador.

## 8. El árbol A.M.V y los modales de catálogo

La UI central es el **árbol jerárquico** que espeja el catálogo atómico. `ESPECIFICACION-
MODALES-APP-MODULO-VERBO.md` define los 3 modales que lo alimentan, con su correspondencia
DDL exacta:

| Concepto UI | Tabla | Clave | Realidad |
|-------------|-------|-------|----------|
| **Aplicación** | `privilege_application` | `app_code` (1-511) | 12 reales (tryton, bauth, org…) |
| **Grupo Funcional** (alias "Módulo") | `privilege_group` | `(app_code, group_code)` | ~48 |
| **Verbo** | `privilege_verb` | `verb_code` (1-255) | 50 disponibles |

El flujo: el admin navega el árbol `Aplicación → Módulo → Verbo`, y cada nivel tiene su modal
de «➕ Agregar» que inserta en la tabla correspondiente. **La UI no inventa conceptos** — cada
elemento visual mapea a una fila de una tabla real (MANUAL-ATOMOS · MANUAL-VERBOS). Hay una
especificación paralela para los modales de políticas y configuraciones
(`ESPECIFICACION-MODALES-POLITICAS-CONFIGURACIONES.md`).

## 9. El widget universal de atributos

El frontend materializa el `display_format`/`validation_policy` de `idn_identidad_atributo`
(MANUAL-ATRIBUTOS §6) con un **widget universal** que se configura por datos, no por código:

| Fase | Librería | Uso |
|------|----------|-----|
| Prototipo HTML | IMask.js + Yup | Máscaras de entrada + validación en el navegador |
| Producción Flutter | `flutter_multi_formatter` + `reactive_forms` + `intl_phone_field` | Máscara + formulario reactivo + teléfono internacional |

El widget recibe el `display_format` (`E164`, `TAX_BO`, `LOCALE_BCP47`…) y renderiza la máscara
correcta; recibe la `validation_policy` (JSONB) y valida igual que el backend. **Un solo widget
sirve para todos los atributos** — agregar un tipo de dato nuevo no requiere un widget nuevo,
igual que agregar el atributo no requiere DDL. La extensibilidad del backend se refleja en el
frontend.

## 10. Accesibilidad e idioma

| Requisito | Norma | Estado |
|-----------|-------|:------:|
| Español obligatorio en toda la UI | DOC-SBOS-001 | ✅ inmutable |
| Contraste ≥ 4.5:1 texto normal | WCAG 2.2 AA | ⚠️ paleta oscura — verificar los pares |
| Target táctil ≥ 44-48px | WCAG / Material | ⚠️ a verificar en Flutter |
| Foco de teclado visible | WCAG 2.4.7 | ⚠️ a implementar |
| Semantics tree (lectores de pantalla) | Flutter Semantics | ⚠️ a poblar |

Flutter genera el árbol de accesibilidad automáticamente y se personaliza con `Semantics`/
`MergeSemantics`/`ExcludeSemantics` — la base está; falta el trabajo de etiquetado (§11.4).
El español obligatorio (DOC-SBOS-001) aplica a **todo** lo que la UI emite: labels, errores,
menús, tooltips — sin excepción.

### 11.2 Lo que hace la industria en 2026

1. **Flutter es opción enterprise seria para desktop:** un solo código para Linux/Windows/Mac
   nativo — la elección correcta para una app soberana que se instala en la máquina del cliente
   (vs web que requiere servidor).
2. **Providers scoped por módulo:** el consenso de state management — Riverpod/Bloc con
   providers acotados al módulo del dashboard para evitar rebuilds globales. bAuth lo adopta.
3. **WCAG 2.2 AA es el objetivo de producción:** Level A es el mínimo (30 criterios), **AA el
   estándar para apps en producción**. Contraste ≥ 4.5:1 (texto normal), target ≥ 44-48px, foco
   visible. Flutter genera el accessibility tree automáticamente; el trabajo es el etiquetado
   semántico.
4. **Dashboards responsive adaptativos:** breakpoints + navegación adaptativa (NavigationRail en
   desktop, drawer en móvil) + deep linking para performance.
5. **Design tokens como custom properties:** exactamente lo que SBOS Dark hace (R1) — todo color
   y espacio como variable, un cambio de tema es un cambio de tokens.

**Lectura honesta:** el DISEÑO del frontend es distintivo y coherente con la soberanía (Flutter
nativo sin servidor, socket local sin puerto, color como semántica de dominio, UI que espeja el
modelo). Pero el estado es **maquetas HTML validadas, sin el proyecto Flutter iniciado** — la
fase 1 del plan (proyecto compilando) no ha comenzado. Es el componente con mayor distancia
entre diseño (excelente) e implementación (cero código Flutter). Y la accesibilidad WCAG está
planificada pero sin verificar.
