## 1. Audiencia, propósito y alcance

Este manual documenta el **sistema de atributos extensibles** de bAuth v2.1: qué atributos existen,
cómo se clasifican, cómo se validan, y cómo se gobiernan. Una sola tabla (`idn_identidad_atributo`)
almacena cualquier atributo de cualquier entidad — sea persona, empresa, vehículo, producto,
servidor, puerta, o bot. Sin ALTER TABLE. Sin tablas nuevas por tipo.

**Audiencia:** desarrolladores bAuth, administradores del Dashboard, diseñadores de DDL.

**Los dos motores que operan sobre los atributos:**

| Motor | Rol sobre atributos | Manual |
|---|---|---|
| **Motor de Identidad** | Ejecuta los verbos `validate`, `verify`, `format`, `mask` sobre atributos usando políticas AtomLang. Delega a `bi18n` las operaciones de formato, enmascaramiento y validación regional vía `obligation.service: bi18n`. | [2.15](2.15_MANUAL-MOTOR-IDENTIDAD-v1.0.md) |
| **Motor BitMask** | Gobierna QUIÉN puede ver/editar cada atributo. Usa `atom_code` → `privilege_atom` → `UserBitMask`. | [1.04](1.04_MANUAL-BITMASK-v1.0.md) |
| **bi18n (servicio de formato, enmascaramiento y validación regional)** | Provee el CÓMO: recibe solicitudes del Motor de Identidad y aplica reglas regionales (formato ICU4X, máscara PII, regex de país). No ejecuta verbos ni decide Permit/Deny. Sin bi18n, los metadatos `mask`, `display_format` y `pattern` son texto inerte. | [i18n-orchestrator §12](i18n-orchestrator-rust.md) · [§4.0.1](#401-bi18n--el-servicio-que-valida-y-ejecuta-los-metadatos) |

**Deslinde:** este manual cataloga los ATRIBUTOS (qué son, qué tipos existen, qué formatos de
presentación usan). La validación de cada atributo la define el Motor de Identidad usando políticas
AtomLang ([2.15](2.15_MANUAL-MOTOR-IDENTIDAD-v1.0.md) §4). La gobernanza de quién puede ver/editar
cada atributo la hace el BitMask vía `atom_code` ([1.04](1.04_MANUAL-BITMASK-v1.0.md)).

## 2. El patrón EAV con `type` explícito

Cada atributo se clasifica con 4 niveles de jerarquía en columnas + `type` explícito:

```
entidad_id → category → attr_key → type → value_text / value_data
```

El campo `type` es explícito y permite búsquedas atómicas sin parsear strings:

```
# v1.0 (obsoleto)
attr_subtype: "emergency"

# v2.0+ (actual)
type: emergency
```

### 2.1 El pipeline de escritura: Motor de Identidad → persistencia

Cuando se escribe un atributo vía `bauth.identidad.atributo.set()`, el Motor de Identidad
ejecuta un pipeline AtomLang antes de tocar la base de datos:

```
bauth.identidad.atributo.set(entidad_id, resource, type, value)
  │
  ├── 1. format    → Normaliza a formato canónico (E.164, ISO, etc.)
  ├── 2. validate  → Valida formato/dato contra reglas AtomLang
  ├── 3. verify    → Verifica contra fuente externa si aplica (SIN, SEGIP, ADSIB)
  │
  └── 4. INSERT/UPDATE en idn_identidad_atributo + INSERT en idn_identidad_atributo_history
```

**El atributo NUNCA se persiste sin pasar el pipeline completo.** Si cualquier etapa Deny →
la operación se rechaza con el Effect como mensaje de error.

### 2.2 El pipeline de lectura: Motor BitMask → enmascaramiento

Cuando se lee un atributo, el Motor BitMask gobierna la visibilidad:

```
bauth.identidad.atributo.get(entidad_id, resource, type)
  │
  ├── 1. Buscar en idn_identidad_atributo
  ├── 2. BitMask: ¿UserBitMask[atom_code] == 1? → Deny → error
  └── 3. PII: ¿zona y LoA permiten ver el valor completo? → enmascarar o retornar
```

### 2.3 Búsquedas con columnas generadas

`idn_identidad_atributo` tiene dos columnas generadas STORED que se calculan UNA VEZ al INSERT/UPDATE:

| Columna | Cálculo | Motor de búsqueda | Uso |
|---|---|---|---|
| `value_normalized` | `lower(unaccent(value_text))` | pg_trgm (GIN) | Fuzzy: "tolota" → TOYOTA (<100ms) |
| `value_search` | `to_tsvector('spanish', ...)` | Full-text (GIN) | Búsqueda con sinónimos + stemming (<50ms) |

La tabla `idn_identidad_sinonimo` (administrable desde D93) alimenta los diccionarios de sinónimos
que `value_search` usa. "foco del izq" encuentra "Farol Delantero Izquierdo" sin que el usuario
sepa el nombre exacto. Ver [A.56 §4.3](anexos/A.56_ANEXO-DISENO-BD-IDENTIDAD-v1.0.md).

## 3. DDL de `idn_identidad_atributo` — referencia canónica

El DDL en disco está en `DDLs/migrations/bauth_47__idn_identidad_entidad.sql`. Esta sección
documenta la estructura de la tabla como referencia para desarrolladores y administradores.
Es la definición autoritativa de qué columnas existen, sus tipos, y sus constraints.

```sql
CREATE TABLE bauth.idn_identidad_atributo (
    -- ── Identidad ──
    atributo_id     BIGSERIAL,                  -- PK local + tenant_id para particionamiento
    entidad_id      UUID        NOT NULL,       -- FK lógica a idn_identidad_entidad
    tenant_id       UUID        NOT NULL,       -- FK lógica a idn_tenant. Aislamiento multi-tenant

    -- ── Clasificación (3 niveles + type explícito) ──
    category        TEXT        NOT NULL,       -- contacto, identificacion, laboral, comercial...
    attr_key        TEXT        NOT NULL,       -- email, telefono, CI, NIT, placa, codigo...
    type            TEXT,                       -- work, home, mobile, fiscal, emergency, CI, NIT...

    -- ── Valor (simple o complejo) ──
    value_text      TEXT,                       -- 80% de atributos: texto simple
    value_data      JSONB,                      -- 20%: estructura compleja (dirección, certificación)

    -- ── Columnas generadas STORED (calculadas UNA VEZ al INSERT/UPDATE) ──
    value_normalized TEXT GENERATED ALWAYS AS (
        lower(unaccent(COALESCE(value_text, '')))
    ) STORED,                                   -- fuzzy search con pg_trgm GIN, <100ms
    value_search     TSVECTOR GENERATED ALWAYS AS (
        to_tsvector('spanish', lower(unaccent(COALESCE(value_text, ''))))
    ) STORED,                                   -- full-text con sinónimos + stemming español, <50ms

    -- ── Gobernanza ──
    display_format  TEXT,                       -- E164, EMAIL_RFC5321, DATE_ISO, MONEY, UUID, NULL...
    atom_code       INT,                        -- NULL=libre, NOT NULL=FK a privilege_atom (BitMask)
    dominio_origen  TEXT,                       -- civil, laboral, comercial, fiscal, salud...

    -- ── Metadatos y auditoría ──
    is_primary      BOOLEAN     NOT NULL DEFAULT false,
    is_verified     BOOLEAN     NOT NULL DEFAULT false,
    verified_by     TEXT,                       -- manual, api_sin, api_segip, api_adsib, email, sms
    verified_at     TIMESTAMPTZ,
    sort_order      SMALLINT    NOT NULL DEFAULT 0,
    ctx_id          TEXT        NOT NULL DEFAULT 'system',  -- SBOS-049 §5.3
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT now(),

    -- ── Constraints ──
    PRIMARY KEY (atributo_id, tenant_id),       -- PK compuesta para particionamiento
    CONSTRAINT fk_atributo_atom FOREIGN KEY (atom_code)
        REFERENCES bauth.privilege_atom(atom_code),
    CONSTRAINT ck_valor_presente CHECK (
        value_text IS NOT NULL OR value_data IS NOT NULL)
) PARTITION BY HASH (tenant_id);

-- Índices B-tree — búsquedas puntuales (<1ms)
CREATE INDEX ix_atributo_entidad ON bauth.idn_identidad_atributo
    (entidad_id, category, attr_key);
CREATE INDEX ix_atributo_atom    ON bauth.idn_identidad_atributo
    (atom_code) WHERE atom_code IS NOT NULL;
CREATE INDEX ix_atributo_exact   ON bauth.idn_identidad_atributo
    (tenant_id, attr_key, value_normalized);
CREATE INDEX ix_atributo_search  ON bauth.idn_identidad_atributo
    (attr_key, type, value_text);

-- Índices GIN — búsquedas fuzzy, full-text, JSONB y categorías
CREATE INDEX ix_atributo_fuzzy   ON bauth.idn_identidad_atributo
    USING GIN (value_normalized gin_trgm_ops);   -- "tolota" → TOYOTA, <100ms
CREATE INDEX ix_atributo_fts     ON bauth.idn_identidad_atributo
    USING GIN (value_search);                    -- "foco del izq" → Farol Del Izq, <50ms
CREATE INDEX ix_atributo_data    ON bauth.idn_identidad_atributo
    USING GIN (value_data);                      -- value_data @> '{"cert":"TOEFL"}'
CREATE INDEX ix_atributo_cat     ON bauth.idn_identidad_atributo
    USING GIN (category gin_trgm_ops);           -- categorías que contengan "contacto"
```

**Tablas compañeras en el mismo archivo DDL (bauth_47):**

| Tabla | Propósito | Particionamiento |
|---|---|---|
| `idn_identidad_atributo_history` | Trazabilidad WORM de cada cambio. Solo INSERT. ISO 27001 A.8.15 · PCI DSS 10.3.2 · GDPR Art. 30 | `RANGE (changed_at)` mensual |
| `idn_identidad_requisito` | Completitud mínima por tipo de entidad y nivel (IAL1/IAL2). El Motor de Identidad verifica ANTES de crear | — |
| `idn_identidad_sinonimo` | Sinónimos y abreviaturas para fuzzy search. Administrable desde D93. Fuente de verdad de archivos `.syn` | — |
| `idn_identidad_sinonimo_sync` | Control de sincronización: regenera archivos `.syn` cuando `updated_at > last_sync_at` | — |

### 3.1 Timestamps y configuración regional multi-tenant

**Principio: un dato, dos vistas.** Todos los campos `TIMESTAMPTZ` (`created_at`, `updated_at`,
`verified_at`, `changed_at` en history) almacenan **siempre UTC** en disco. La conversión a la
zona horaria del tenant ocurre **solo en el momento de mostrar o consultar**, nunca al guardar.
El dato en disco es invariable; lo que cambia es cómo se presenta.

#### El modelo

```
SE GUARDA (disco)              SE MUESTRA (por sesión)
──────────────────              ──────────────────────
TIMESTAMPTZ = UTC               Tenant Bolivia:  05:00 AM (UTC-4)
2026-07-16T09:00:00Z            Tenant Alemania: 11:00 AM (UTC+2)
(el mismo dato para ambos)      Auditoría:       09:00 UTC
```

#### Mecanismo en PostgreSQL: `SET timezone` por sesión

`TIMESTAMPTZ` no almacena zona horaria — siempre es un instante UTC absoluto. La zona se aplica
al interpretar y al mostrar. El daemon ejecuta `SET timezone` como primer comando al tomar una
conexión del pool, usando la zona del tenant resuelta de `RegionalConfig`:

```sql
-- Al abrir la conexión para el tenant Bolivia
SET timezone = 'America/La_Paz';

-- Lectura: PostgreSQL convierte automáticamente
SELECT created_at FROM bauth.idn_identidad_atributo WHERE entidad_id = '...';
-- → 2026-07-16 05:00:00-04  (hora de La Paz)

-- Auditoría: siempre UTC
SET timezone = 'UTC';
SELECT created_at FROM bauth.idn_identidad_atributo WHERE entidad_id = '...';
-- → 2026-07-16 09:00:00+00  (UTC real, evidencia forense)
```

#### Mecanismo en Rust: `jiff` con zona explícita

El orquestador **nunca** lee el locale o la zona horaria del sistema operativo. Recibe
`RegionalConfig` del tenant como parámetro explícito en cada operación:

```rust
use jiff::{Timestamp, tz::TimeZone};

// Guardar: siempre Timestamp UTC
let instante_utc = Timestamp::now();  // equivalente a date -u

// Mostrar al tenant: convertir solo al presentar
let tz_tenant = TimeZone::get(&regional.timezone)?;  // "America/La_Paz"
let hora_tenant = instante_utc.to_zoned(tz_tenant);
// Formatear con locale del tenant
let texto = orch.format_date(&hora_tenant, DateStyle::Long, &regional.locale);
// → "16 de julio de 2026, 05:00 AM" (es-BO)
```

#### Jerarquía de resolución de `RegionalConfig`

La configuración regional del tenant se resuelve por capas, de más específica a más general.
El orquestador (`i18n-orchestrator`) define el contrato `RegionalConfigResolver`:

```
1. Usuario individual  (preferencia personal de locale/zona)
2. Sucursal / Branch   (si opera en otro país)
3. Tenant / Empresa    (configuración principal)
4. Default del sistema (explícito, NUNCA implícito del SO del servidor)
```

```rust
pub struct RegionalConfig {
    pub locale: Locale,                  // BCP 47, ej. "es-BO"
    pub timezone: jiff::tz::TimeZone,    // IANA, ej. "America/La_Paz"
    pub currency: String,               // ISO 4217, ej. "BOB"
    pub country: String,                // ISO 3166, ej. "BO"
}

// Resolver al inicio de cada request, nunca del SO
let regional = resolver.resolve(tenant_id, branch_id, Some(user_id))?;
```

#### Qué NO se debe hacer

- ❌ `Zoned::now()` sin `.with_time_zone(...)` explícito — usa la zona del SO
- ❌ `icu::datetime` formateando con locale por defecto — usa el locale del SO
- ❌ Leer `TZ` o `LANG` de variables de entorno del proceso
- ❌ `postgresql.conf` con `timezone` fijo — rompe multi-tenant

#### Checklist de aceptación

- [x] `TIMESTAMPTZ` en todas las tablas de identidad — siempre UTC en disco
- [x] `SET timezone` por sesión al tomar conexión del pool
- [x] `jiff` con zona explícita del tenant, nunca implícita del SO
- [x] `RegionalConfig` resuelto por request, nunca global ni `thread_local`
- [x] UTC disponible para auditoría (`date -u`, `SET timezone = 'UTC'`)
- [x] VPS en Alemania con `TZ=UTC` es irrelevante para el resultado

**Referencia completa:** [i18n-orchestrator — Orquestador Universal de Internacionalización en Rust §10](i18n-orchestrator-rust.md)

## 4. Catálogo de atributos por categoría

### 4.0 Metadatos completos del atributo — el modelo de 25 características

Cada atributo en bAuth se define con 25 metadatos, alineados con seis estándares internacionales:
SCIM 2.0 (RFC 7643 §2.2), NIST SP 800-63A (IAL, evidence), OpenID Connect for Identity
Assurance 1.0 (OIDC4IDA, trust_framework, verification), ISO 27001:2022 §5.12-5.13
(clasificación, etiquetado), GDPR Art. 5-6 (propósito, base legal, retención), y ETSI/eIDAS
(trust_framework para firma digital cualificada).

#### Bloque A — Identidad y clasificación (6)

| # | Metadato | Estándar | Valores | Significado |
|---|---|---|---|---|
| 1 | **attr_key** | bAuth | `nombre`, `email`, `CI`, `NIT`... | Identificador del atributo dentro de su categoría |
| 2 | **type** | SCIM §2.2 | `work`, `home`, `mobile`, `CI`, `NIT`... | Subtipo explícito. Permite búsquedas atómicas sin parsear strings |
| 3 | **category** | bAuth | `contacto`, `identificacion`, `laboral`... | Categoría de agrupación del atributo |
| 4 | **multiValued** | SCIM §2.2 | `true`, `false` | Si el atributo puede tener múltiples instancias. `true` para contacto (1:N emails), `false` para birth_date |
| 5 | **canonicalValues** | SCIM §2.2 | `[]` o lista de valores | Valores permitidos. `['CI','DNI','CPF','PASSPORT']` para `id_nacional.type`. Vacío = texto libre |
| 6 | **caseExact** | SCIM §2.2 | `true`, `false` | Si la comparación de strings es case-sensitive. `false` para email, `true` para UUIDs |

#### Bloque B — Control de acceso y modificación (4)

| # | Metadato | Estándar | Valores | Significado |
|---|---|---|---|---|
| 7 | **mutability** | SCIM §2.2 | `readWrite`, `readOnly`, `immutable`, `writeOnly` | `readWrite`: modificable. `readOnly`: asignado por el sistema. `immutable`: solo al crear la entidad. `writeOnly`: se escribe pero no se lee (password_hash) |
| 8 | **returned** | SCIM §2.2 | `always`, `default`, `never`, `request` | Cuándo se incluye en respuestas API. `never`: nunca (password_hash). `request`: solo si se pide explícitamente |
| 9 | **uniqueness** | SCIM §2.2 | `none`, `server`, `global` | `server`: único en todo el tenant. `global`: único entre tenants (ej: email como login) |
| 10 | **required** | SCIM §2.2 + NIST | `true`, `false`, `conditional(ial)` | Si es obligatorio. Puede ser condicional al IAL: opcional en IAL1, requerido en IAL2 |

#### Bloque C — Verificación de identidad (NIST SP 800-63A + OIDC4IDA) (7)

| # | Metadato | Estándar | Valores | Significado |
|---|---|---|---|---|
| 11 | **ial** | NIST SP 800-63A §4 | `IAL1`, `IAL2`, `IAL3` | Nivel de aseguramiento mínimo para este atributo |
| 12 | **source** | NIST SP 800-63A §5 | `self_asserted`, `authoritative`, `derived`, `verified_external` | Origen del valor. `authoritative`: documento oficial. `verified_external`: SIN, SEGIP, ADSIB |
| 13 | **evidence_type** | OIDC4IDA §4 | `id_document`, `utility_bill`, `electronic_record`, `vouch`, `qes`, `attestation` | Tipo de evidencia usada para verificar. `id_document`: pasaporte, CI. `qes`: firma electrónica cualificada. `attestation`: atestación notarial |
| 14 | **evidence_strength** | NIST SP 800-63A §5 | `NONE`, `WEAK`, `FAIR`, `STRONG`, `SUPERIOR` | Fortaleza de la evidencia. `SUPERIOR`: pasaporte biométrico, PIV. `STRONG`: CI con chip. `FAIR`: factura de servicios |
| 15 | **verification_method** | OIDC4IDA §4 | `pipp`, `sripp`, `eid`, `document_check`, `biometric`, `kbv`, `authoritative_source` | Método de verificación. `pipp`: presencial. `sripp`: remoto supervisado. `eid`: verificación electrónica. `kbv`: preguntas de conocimiento |
| 16 | **trust_framework** | OIDC4IDA §3 | `nist_800_63A`, `eidas`, `fido`, `iso_27001`, `sin_bolivia`, `segin_bolivia` | Marco de confianza que rige la verificación. Referencia al estándar, ley o entidad certificadora |
| 17 | **verified_by** | bAuth | `manual`, `api_sin`, `api_segip`, `api_adsib`, `email`, `sms`, `oidc4ida_op` | Quién o qué sistema realizó la verificación. Compatible con `verified_by` en la tabla |

#### Bloque D — Presentación, privacidad y ciclo de vida (5)

| # | Metadato | Estándar | Valores | Significado |
|---|---|---|---|---|
| 18 | **display_format** | SCIM + bAuth | `E164`, `EMAIL_RFC5321`, `DATE_ISO`, `MONEY`, `UUID`, `TAX_BO`, `ID_BO`, `PASSPORT_ICAO`, `IPV4`, `ADDR_INTL`, `COORDENADAS_DD`, `URL`, `LOCALE_BCP47`, `TIMEZONE_IANA`, `NULL` | Máscara de presentación para frontend. No valida; la validación la hace el Motor de Identidad |
| 19 | **classification** | ISO 27001:2022 §5.12 | `PUBLIC`, `INTERNAL`, `CONFIDENTIAL`, `RESTRICTED` | `RESTRICTED`: CI, NIT, biométricos. `CONFIDENTIAL`: datos personales. `INTERNAL`: uso interno. `PUBLIC`: libre |
| 20 | **mask** | GDPR Art. 5/25/32 | `none`, `partial(N)`, `full` | `none`: se muestra completo. `partial(4)`: últimos 4 visibles (CI: ****4823). `full`: nunca se muestra en UI/logs |
| 21 | **retention** | GDPR Art. 5(1)(e) | `permanent`, `X_years_after_deletion`, `until_purpose_ends` | `permanent`: trazabilidad de auditoría. `10_years_after_deletion`: obligación legal (tributario). `until_purpose_ends`: se borra al terminar el propósito |
| 22 | **purpose** | GDPR Art. 5(1)(b) | Texto descriptivo | Propósito explícito del tratamiento. Ej: "Identificación tributaria para facturación electrónica SIN" |

#### Bloque E — Gobernanza, dependencias y ciclo de vida (3)

| # | Metadato | Estándar | Valores | Significado |
|---|---|---|---|---|
| 23 | **atom_code** | bAuth (D00) | `NULL` o `INT` (FK `privilege_atom`) | Gobernanza BitMask. `NULL`: atributo libre. `NOT NULL`: controlado por UserBitMask |
| 24 | **cross_tenant_visibility** | bAuth (D00) | `PRIVADA`, `COMPARTIDA`, `PUBLICA` | Visibilidad cross-tenant del atributo. `PRIVADA`: solo el tenant dueño. `COMPARTIDA`: el referenciado sabe quién lo usa. `PUBLICA`: todos |
| 25 | **depends_on** | bAuth | `[]` o lista de `attr_key` | Dependencias. `id_nacional.CI` depende de `birth_date` y `nationality`. El motor verifica que existan antes de validar |

**Los catálogos en §4.1-4.8 muestran 13 columnas** de las 25 (las de uso más frecuente en el día a día: attr_key, type, display_format, mutability, returned, uniqueness, required, ial, source, classification, mask, retention, atom_code). Las 12 restantes (multiValued, caseExact, canonicalValues, evidence_type, evidence_strength, verification_method, trust_framework, verified_by, purpose, cross_tenant_visibility, depends_on, category) se definen por tipo de entidad y contexto, y están documentadas en el [Motor de Identidad](2.15_MANUAL-MOTOR-IDENTIDAD-v1.0.md) y en [A.56](anexos/A.56_ANEXO-DISENO-BD-IDENTIDAD-v1.0.md).

### 4.0.1 bi18n — el servicio que valida y ejecuta los metadatos

Los 25 metadatos del modelo de características (§4.0) son **declaraciones**. Un valor como
`mask: "partial(4)"` o `display_format: "ID_BO"` guardado en una fila de `idn_identidad_atributo`
no produce ningún efecto por sí mismo. Nada impide que alguien escriba `mask: "inventado(999)"`
o `display_format: "COSA_QUE_NO_EXISTE"` — strings que en runtime causarían errores silenciosos,
datos mal formateados, o exposición de PII.

**El daemon `bi18n` es el servicio que el Motor de Identidad invoca para transformar esas
declaraciones en comportamiento real.** No ejecuta verbos ni decide Permit/Deny — eso lo hace
el Motor de Identidad (PDP de bAuth). bi18n provee el CÓMO: recibe una solicitud, aplica
reglas regionales, y devuelve el resultado transformado.

| Momento | Qué hace | Metadatos que cubre |
|---|---|---|
| **Diseño** (al guardar el metadata) | Valida que el valor del metadato sea sintácticamente correcto y esté registrado en los catálogos de bi18n. Rechaza valores inválidos antes de que lleguen a disco. | `mask`, `display_format`, `canonicalValues`, `pattern`, `input_mask`, `date_granularity`, `classification` |
| **Runtime** (al leer/escribir el valor del atributo) | Ejecuta el metadato sobre el valor concreto: formatea con ICU4X, enmascara PII, valida regex, verifica pertenencia a enum, localiza según locale del tenant. | Todos los anteriores + `locale_sensitive`, `required`, `type` |

**Ejemplo concreto — el atributo `id_nacional` tipo `CI`:**

```
Metadatos declarados en idn_identidad_atributo:
  display_format: "ID_BO"
  mask: "partial(4)"
  canonicalValues: ["CI", "DNI", "CPF", "PASSPORT"]
  pattern: "^\\d{7,13}-[A-Z]{2}$"         (en TOML de Bolivia)

              ▼ bi18n valida al guardar

✅ "ID_BO"       → registrado en format_map → input_mask: "9999999-AA", ICU4X: "0000000-LL"
✅ "partial(4)"  → MaskStrategy::Partial { visible_from_end: 4 } — sintaxis válida
✅ ["CI","DNI","CPF","PASSPORT"] → valores únicos, lista no vacía

              ▼ bi18n ejecuta al leer

bauth.entidad.atributo.get(act-jperez, id_nacional, CI)
  → valor crudo en disco: "7654321-LP"
  → bi18n.mask_value("7654321-LP", "ID_BO", "partial(4)")
  → "****321-LP"     ← PII enmascarado antes de llegar al dashboard
```

**Qué pasa sin bi18n:**

| Sin bi18n | Con bi18n |
|---|---|
| `mask: "cualquier_cosa"` se guarda sin rechistar. En runtime falla o se ignora silenciosamente. | bi18n rechaza el valor al guardar. El metadata nunca está corrupto. |
| `display_format: "INVENTADO"` → ICU4X falla o muestra basura | Solo se aceptan códigos del `format_map`. Falla temprano, no en producción. |
| `canonicalValues: ["M","M","F"]` → duplicados, comportamiento impredecible | bi18n rechaza: valores duplicados. |
| `pattern: "[\\d{7,13"` → regex malformado, error en runtime | bi18n compila y valida la regex. Detecta ReDoS. |
| El dashboard muestra `7654321-LP` sin enmascarar (PII expuesto) | `.mask()` se aplica automáticamente al leer atributos con `classification >= CONFIDENTIAL` |
| Cada atributo valida con código hardcodeado en bAuth | La validación es una política AtomLang que referencia a bi18n — cambia sin tocar código |
| Agregar un país nuevo requiere modificar bAuth y redeploy | Se agrega un archivo `country-rules/{país}.toml` — cero código |

**Referencia completa:** [i18n-orchestrator — §12: bi18n como motor de validación y ejecución del AtomLang](i18n-orchestrator-rust.md).
La integración con las políticas AtomLang (verbos `validate`, `verify`, `format`, `mask` que delegan
en bi18n vía `obligation.validator: bi18n`) está documentada en [Manual 2.13 §5.4](2.13_MANUAL-ATOMLANG-LENGUAJE-v2.0.md).

## 6. Validación con el motor de identidad

La validación de atributos NO usa JSONB `validation_policy`. Usa políticas AtomLang en el
[Motor de Identidad](2.15_MANUAL-MOTOR-IDENTIDAD-v1.0.md). Mismo lenguaje que el BitMask,
distinto propósito.

```yaml
# Ejemplo: validación de teléfono
politica "validacion_telefonos"
  combining_algorithm: deny-overrides
  regla "telefono_formato_e164"
    target:
      resource: idn_identidad_atributo.telefono
      type: ANY
      verbo: validate
    condition:
      property_id: idn_identidad_atributo.value_text
      operator: REGEX
      value: "@bauth_config_param.regex_e164"
    effect:
      decision: Permit
```

Tres verbos: `validate` (formato), `verify` (fuente externa), `format` (canónico).

## 7. Gobernanza BitMask — `atom_code`

Cada atributo puede estar vinculado a un átomo D00 vía `atom_code`. Si `atom_code IS NOT NULL`,
el atributo está controlado por el Motor BitMask: solo actores con ese átomo en su UserBitMask
pueden ver/editar el atributo. Si `atom_code IS NULL`, el atributo es libre: gobernado por
categoría y políticas de visibilidad del Motor de Identidad.

### 7.1 La cadena de gobernanza

```
idn_identidad_atributo.atom_code ──→ privilege_atom ──→ privilege_role_atom ──→ UserBitMask
```

El `atom_code` en `idn_identidad_atributo` es una FK real a `privilege_atom.atom_code`. Cada átomo D00
define un campo de identidad (nombre, email, CI, NIT, placa...). Los átomos se asignan a roles vía
`privilege_role_atom`. Los roles se asignan a usuarios vía `idn_user_role`. El `UserBitMask` resultante
determina —en <0.5ns— si el actor puede ver o editar cada atributo.

### 7.2 Evaluación en runtime

Cuando el Motor de Identidad lee un atributo, consulta al Motor BitMask:

```
Actor: Juan Pérez (UserBitMask)
Atributo solicitado: idn_identidad_atributo.id_nacional, type=CI, atom_code=5826

1. UserBitMask[5826] == 1  →  Permit
2. ¿Zona y LoA permiten ver el valor completo?
   → zona=RRHH, LoA=3 → retorna valor completo
   → zona≠RRHH → retorna enmascarado: "****4823"
```

Cuando el Motor de Identidad escribe un atributo, la misma evaluación aplica:

```
Actor: Admin BIZ_N1
Intenta: bauth.identidad.atributo.set(bd-skull-corp, tributario, NIT, "...")
         atom_code=5812

1. UserBitMask[5812] == 1  →  Permit  →  ejecuta pipeline format→validate→verify→INSERT
2. UserBitMask[5812] == 0  →  Deny    →  { error: "No tiene permisos para editar este atributo" }
```

### 7.3 Atributos libres vs controlados

| `atom_code` | Gobernanza | Ejemplo |
|---|---|---|
| `NULL` | Libre. Gobernado por categoría + visibilidad. | `red_social.linkedin`, `idioma` |
| `NOT NULL` | Controlado por BitMask. | `CI` (5826), `NIT` (5812), `email` (5813) |

La decisión de qué atributos son controlados (con átomo D00) y cuáles son libres (sin átomo)
la toma el dominio D93 (Catálogo de Identidades) usando políticas AtomLang.
