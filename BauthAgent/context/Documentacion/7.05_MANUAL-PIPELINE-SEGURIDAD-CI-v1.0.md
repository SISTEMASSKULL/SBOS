**Código:** 7.05  
**Versión:** 1.0.0  
**Fecha:** 2026-08-02  
**Pilar IAM Enterprise:** Standards (NIST SP 800-53 SA-10 · ISO 27001:2022 A.8.25 · OWASP ASVS v5.0)  
**Fase del ciclo:** 7 — Remediación

## §1 Propósito

El control SA-10 (NIST 800-53) y su equivalente A.8.25 (ISO 27001:2022) exigen que todo sistema
de seguridad aplique **análisis de seguridad automatizado en el ciclo de desarrollo**: escaneo
de vulnerabilidades en dependencias, análisis estático de código (SAST) y política de dependencias.

Este manual documenta el pipeline CI/CD soberano de bAuth: un conjunto de herramientas ejecutadas
en **Podman** (sin Docker, sin daemon root) que analizan el código en un entorno reproducible y
registran los hallazgos directamente en **SBOSDB** (`bauth.vul_component` + `bauth.vul_auth_impact`).

> **Por qué Podman y no Docker:** SBOS es un ecosistema soberano. Podman opera sin daemon root
> (`rootless` opcional), usa el mismo formato OCI que Docker, y no genera dependencias de servicios
> en background. En la VPS del ecosistema SBOS, Podman 5.7.0 es el motor de contenedores oficial.

## §2 Arquitectura del pipeline

```
BauthAgent/ci/
├── Containerfile.security        ← imagen Podman: Rust 1.85 + cargo-audit + cargo-deny
├── cargo-deny.toml               ← política de dependencias (licencias, advisories, bans)
├── security-scan.sh              ← script principal: 5 fases
├── bauth-security-scan.service   ← unidad systemd (one-shot)
└── bauth-security-scan.timer     ← timer systemd (semanal, lunes 02:00 UTC)
```

**Flujo de ejecución:**

```
[Timer systemd / make security-scan]
        │
        ▼
security-scan.sh
  Fase 1: podman build  ──► imagen bauth-security-scanner (cacheada)
  Fase 2: cargo-audit   ──► cargo-audit.json (RustSec DB)
  Fase 3: cargo-deny    ──► cargo-deny.txt   (política licencias)
  Fase 4: cargo-clippy  ──► clippy.txt       (SAST)
  Fase 5: ingest        ──► psql → SBOSDB
                                ├── bauth.vul_component  (T-527)
                                └── bauth.vul_auth_impact (T-528)
```

**Principio de no-fallar-el-build:** el pipeline reporta hallazgos pero no falla con código de
salida distinto de 0 por vulnerabilidades — la decisión de remediar o aceptar riesgo es humana.
Solo falla (código 2) ante errores de infraestructura (Podman no disponible, SBOSDB inaccesible).

## §3 Containerfile.security — La imagen Podman

**Ruta:** `BauthAgent/ci/Containerfile.security`

### §3.1 Base y herramientas instaladas

```dockerfile
FROM docker.io/library/rust:1.85-slim
```

La imagen base es la imagen oficial de Rust 1.85 en Debian slim. Se instalan:

| Herramienta | Versión | Fuente | Propósito |
|-------------|---------|--------|-----------|
| `cargo-audit` | latest locked | crates.io | Escanea Cargo.lock contra RustSec Advisory Database |
| `cargo-deny` | latest locked | crates.io | Aplica política de licencias, advisories y bans |
| `cargo-clippy` | bundled con Rust | toolchain | Análisis estático SAST — lints de seguridad |
| `jq` | sistema | apt | Procesamiento JSON en el container |

El argumento `--locked` en `cargo install` garantiza que se usa exactamente la versión del
`Cargo.lock` del crate de la herramienta — comportamiento reproducible.

### §3.2 Optimización de capas

```dockerfile
RUN cargo install cargo-audit --locked \
    && cargo install cargo-deny  --locked \
    && rm -rf /root/.cargo/registry/src \
              /root/.cargo/registry/cache \
              /root/.cargo/git/db
```

El directorio de caché de crates se elimina después de instalar las herramientas para reducir
el tamaño de la imagen. Las binarios (`cargo-audit`, `cargo-deny`) quedan en `~/.cargo/bin/`
que ya está en el `PATH` de la imagen base.

### §3.3 Montaje del workspace

La imagen no copia el código fuente — lo recibe **montado como volumen en tiempo de ejecución**:

```bash
podman run --rm \
    --volume "$PROJECT_DIR:/workspace:ro" \   # fuente: solo lectura
    --volume "$OUTPUT_DIR:/output:rw"  \      # salida:  escritura
    --workdir /workspace \
    bauth-security-scanner \
    "cargo audit --json > /output/cargo-audit.json"
```

Ventaja: la imagen nunca necesita reconstruirse por cambios en el código fuente.

### §3.4 Construir la imagen manualmente

```bash
cd BauthAgent/
podman build \
    --tag bauth-security-scanner:latest \
    --file ci/Containerfile.security \
    ci/
```

La imagen se construye una vez y se cachea en el registro local de Podman. El script
`security-scan.sh` la reconstruye automáticamente en cada ejecución (controlable con
`BUILD_IMAGE=false` para saltar el build si ya existe).

## §4 cargo-deny.toml — Política de dependencias

**Ruta:** `BauthAgent/ci/cargo-deny.toml`

### §4.1 Sección advisories

```toml
[advisories]
vulnerability = "deny"    # vulnerabilidad activa → BLOQUEA el pipeline
unmaintained  = "warn"    # crate sin mantenimiento → advertencia
yanked        = "deny"    # versión descontinuada en crates.io → BLOQUEA
notice        = "warn"    # aviso informativo → advertencia
ignore        = []        # ninguna excepción sin revisión manual
```

**Impacto:** si se detecta una vulnerabilidad activa en cualquier dependencia directa o
transitiva, `cargo deny check` retorna código de salida distinto de 0 y el pipeline reporta
el hallazgo.

### §4.2 Sección licenses

Licencias aprobadas para el ecosistema SBOS (soberanas y compatibles):

| Licencia | Estado |
|----------|--------|
| MIT | ✅ Aprobada |
| Apache-2.0 | ✅ Aprobada |
| Apache-2.0 WITH LLVM-exception | ✅ Aprobada |
| BSD-2-Clause / BSD-3-Clause | ✅ Aprobadas |
| ISC | ✅ Aprobada |
| Unicode-DFS-2016 / Unicode-3.0 | ✅ Aprobadas |
| OpenSSL / CC0-1.0 / Zlib / MPL-2.0 | ✅ Aprobadas |
| GPL-2.0 / GPL-3.0 / AGPL-\* / LGPL-\* / EUPL-\* | ❌ Prohibidas |
| Copyleft débil sin clasificar | ⚠️ Advertencia |
| Sin clasificación explícita | ❌ Error (default = deny) |

### §4.3 Sección bans

```toml
[bans]
multiple-versions = "warn"   # múltiples versiones del mismo crate → advertencia
wildcards         = "allow"  # rangos semver normales → permitidos
```

Versiones con múltiples instancias conocidas en el árbol de dependencias de bAuth
(rand 0.7, rand_core 0.5/0.6) están en la lista `skip` para evitar falsos positivos.

### §4.4 Sección sources

```toml
[sources]
unknown-registry = "deny"     # solo crates.io oficial
unknown-git      = "deny"     # sin dependencias git sin verificación
allow-registry   = ["https://github.com/rust-lang/crates.io-index"]
allow-git        = []         # ningún repositorio git externo sin aprobación
```

## §5 security-scan.sh — Script principal

**Ruta:** `BauthAgent/ci/security-scan.sh`  
**Permisos:** `chmod +x` (755)

### §5.1 Variables de entorno configurables

| Variable | Default | Descripción |
|----------|---------|-------------|
| `BAUTH_DB_DSN` | `postgres://postgres:postgres@localhost:15432/SBOSDB` | DSN de SBOSDB oficial |
| `OUTPUT_DIR` | `/tmp/bauth-security-scan/<timestamp>` | Directorio de salida de reportes |
| `BUILD_IMAGE` | `true` | `false` = saltar build si imagen ya existe |

### §5.2 Fase 1 — Build de imagen Podman

Construye `bauth-security-scanner:latest` desde `ci/Containerfile.security`. Si `BUILD_IMAGE=false`
y la imagen ya existe, se salta esta fase para acelerar ejecuciones frecuentes.

```bash
podman build \
    --tag "bauth-security-scanner:latest" \
    --file "ci/Containerfile.security" \
    --quiet \
    ci/
```

### §5.3 Fase 2 — cargo-audit (RustSec Advisory Database)

```bash
podman run --rm \
    --volume "$PROJECT_DIR:/workspace:ro" \
    --volume "$OUTPUT_DIR:/output:rw" \
    --workdir /workspace \
    --security-opt=no-new-privileges \
    bauth-security-scanner \
    "cargo audit --json > /output/cargo-audit.json"
```

**Salida:** `cargo-audit.json` con estructura:

```json
{
  "vulnerabilities": {
    "found": false,
    "count": 0,
    "list": []
  },
  "lockfile": {
    "packages": [...]
  }
}
```

El campo `list[]` contiene objetos con `advisory.id`, `advisory.aliases` (CVE-XXXX-XXXXX),
`advisory.severity`, `advisory.cvss`, `package.name`, `package.version`.

### §5.4 Fase 3 — cargo-deny (política de dependencias)

```bash
podman run --rm \
    --volume "$PROJECT_DIR:/workspace:ro" \
    --volume "ci/cargo-deny.toml:/workspace/deny.toml:ro" \
    --volume "$OUTPUT_DIR:/output:rw" \
    --workdir /workspace \
    bauth-security-scanner \
    "cargo deny --config /workspace/deny.toml check 2>&1 | tee /output/cargo-deny.txt"
```

**Salida:** `cargo-deny.txt` con líneas de diagnóstico en formato:
`error[advisories]: <descripción>` / `warning[licenses]: <descripción>`

### §5.5 Fase 4 — cargo-clippy (SAST)

```bash
podman run --rm \
    --volume "$PROJECT_DIR:/workspace:rw" \
    --volume "$OUTPUT_DIR:/output:rw" \
    --workdir /workspace \
    bauth-security-scanner \
    "cargo clippy --all-targets -- -D warnings 2>&1 | tee /output/clippy.txt"
```

El flag `-D warnings` convierte toda advertencia en error — garantiza cero tolerancia para
lints de seguridad. El volumen es `:rw` porque Cargo necesita escribir en `target/` durante
la compilación.

### §5.6 Fase 5 — Ingesta en SBOSDB

Python3 parsea `cargo-audit.json` y genera SQL:

1. **`bauth.vul_component` (T-527):** upsert del componente `bauth` (binario principal) y de
   cada crate con vulnerabilidad detectada. Columnas clave:
   - `name` — nombre del crate
   - `component_type` — `RUST_BINARY` (bauth principal) o `RUST_DEPENDENCY`
   - `version` — versión afectada
   - `source = 'Cargo.lock'`
   - `last_scanned` — timestamp del escaneo
   - `scan_tool = 'cargo-audit'`

2. **`bauth.vul_auth_impact` (T-528):** un registro por vulnerabilidad encontrada. Columnas:
   - `cve_id` — CVE-XXXX-XXXXX o RUSTSEC-XXXX-XXXX si sin CVE
   - `component_id FK` → `vul_component`
   - `affected_methods TEXT[]` — inicialmente vacío; el equipo completa manualmente
   - `severity` — CRITICAL/HIGH/MEDIUM/LOW mapeado desde RustSec
   - `cvss_score` — score numérico si disponible
   - `impact_desc` — título + descripción del advisory (truncada a 500 chars)
   - `mitigation` — recomendación de actualización de crate
   - `action_taken` — `PENDIENTE — detectado por cargo-audit en escaneo SA-10 <timestamp>`

La ingesta usa `ON CONFLICT DO NOTHING` en `vul_auth_impact` para ser idempotente.
La ingesta de `vul_component` usa `ON CONFLICT ... DO UPDATE SET last_scanned = EXCLUDED.last_scanned`.

## §6 bauth-security-scan.service — Unidad systemd

**Ruta:** `BauthAgent/ci/bauth-security-scan.service`  
**Instalación:** `/etc/systemd/system/bauth-security-scan.service`

### §6.1 Configuración clave

```ini
[Service]
Type=oneshot
WorkingDirectory=/opt/skull/orquestador/proyectos/SBOS/BauthAgent
Environment="BAUTH_DB_DSN=postgres://postgres:postgres@localhost:15432/SBOSDB"
Environment="OUTPUT_DIR=/var/log/bauth-security-scan"
Environment="BUILD_IMAGE=true"
ExecStart=/opt/skull/orquestador/proyectos/SBOS/BauthAgent/ci/security-scan.sh
TimeoutStartSec=1800   # 30 minutos (cargo-audit descarga advisory DB)
```

### §6.2 Restricciones de seguridad (ISO 27001 A.8.2)

```ini
PrivateTmp=true           # /tmp aislado del host
ProtectSystem=full        # filesystem del sistema en solo lectura
ReadOnlyPaths=...         # fuentes del proyecto solo lectura
ReadWritePaths=/var/log/bauth-security-scan /tmp
```

### §6.3 Ejecutar manualmente

```bash
# Ejecutar el servicio ahora (sin esperar el timer)
sudo systemctl start bauth-security-scan.service

# Ver salida en tiempo real
journalctl -u bauth-security-scan.service -f

# Ver el log completo del último escaneo
journalctl -u bauth-security-scan.service --since "1 hour ago"
```

## §7 bauth-security-scan.timer — Timer systemd semanal

**Ruta:** `BauthAgent/ci/bauth-security-scan.timer`  
**Instalación:** `/etc/systemd/system/bauth-security-scan.timer`

### §7.1 Configuración

```ini
[Timer]
OnCalendar=Mon *-*-* 02:00:00 UTC   # lunes 02:00 UTC (fuera de horario)
Persistent=true                       # ejecuta al arrancar si se perdió el disparo
RandomizedDelaySec=300               # dispersión de ±5 min para evitar saturación
Unit=bauth-security-scan.service
```

### §7.2 Comandos de gestión

```bash
# Ver estado del timer
systemctl status bauth-security-scan.timer

# Ver próxima ejecución
systemctl list-timers bauth-security-scan.timer

# Deshabilitar temporalmente (sin desinstalar)
sudo systemctl stop bauth-security-scan.timer

# Rehabilitar
sudo systemctl start bauth-security-scan.timer

# Ver logs de todas las ejecuciones pasadas
journalctl -u bauth-security-scan.service --since "1 month ago" | grep -E "RESUMEN|CERRADO|OK|WARN|FAIL"
```

## §8 Instalación en la VPS — procedimiento idempotente

El procedimiento completo es **idempotente**: ejecutarlo N veces produce el mismo estado final.

### §8.1 Prerrequisitos en la VPS

| Herramienta | Versión mínima | Verificar |
|-------------|---------------|-----------|
| `podman` | 5.0+ | `podman --version` |
| `psql` | 18.x | `psql --version` |
| `python3` | 3.10+ | `python3 --version` |

### §8.2 Paso a paso

```bash
# 1. Crear estructura de directorios (idempotente con -p)
ssh root@<VPS_IP> 'mkdir -p /opt/skull/orquestador/proyectos/SBOS/BauthAgent/ci \
                            /var/log/bauth-security-scan'

# 2. Copiar archivos necesarios desde la máquina de desarrollo
BASE=/opt/skull/orquestador/proyectos/SBOS/BauthAgent
scp "$BASE/Cargo.toml" "$BASE/Cargo.lock" root@<VPS_IP>:"$BASE/"
scp "$BASE/ci/"* root@<VPS_IP>:"$BASE/ci/"

# 3. Instalar unidades systemd (cp sobrescribe → idempotente)
ssh root@<VPS_IP> '
    cp /opt/skull/orquestador/proyectos/SBOS/BauthAgent/ci/bauth-security-scan.service \
       /etc/systemd/system/
    cp /opt/skull/orquestador/proyectos/SBOS/BauthAgent/ci/bauth-security-scan.timer \
       /etc/systemd/system/
    chmod +x /opt/skull/orquestador/proyectos/SBOS/BauthAgent/ci/security-scan.sh
    systemctl daemon-reload
    systemctl enable bauth-security-scan.timer
    systemctl start  bauth-security-scan.timer
'

# 4. Verificar
ssh root@<VPS_IP> 'systemctl list-timers bauth-security-scan.timer --no-pager'
```

### §8.3 Atajo con Makefile

```bash
# En la máquina de desarrollo (con acceso SSH a la VPS)
make install-security-timer
```

Este target ejecuta los pasos 3 en la máquina local (asume que los archivos ya están en la VPS).
Para sincronizar los archivos a la VPS primero, usar `scp` o el proceso manual del §8.2.

### §8.4 Actualizar archivos en VPS cuando cambia el código

Cuando se modifica `security-scan.sh`, `Containerfile.security`, `cargo-deny.toml` o
`Cargo.lock` en la máquina de desarrollo y se commitea:

```bash
BASE=/opt/skull/orquestador/proyectos/SBOS/BauthAgent
# Sincronizar solo los archivos modificados
scp "$BASE/Cargo.lock" \
    "$BASE/ci/Containerfile.security" \
    "$BASE/ci/cargo-deny.toml" \
    "$BASE/ci/security-scan.sh" \
    root@<VPS_IP>:"$BASE/ci/"

# Reconstruir imagen (la versión anterior queda en caché; se reemplaza)
ssh root@<VPS_IP> '
    cd /opt/skull/orquestador/proyectos/SBOS/BauthAgent
    podman build --tag bauth-security-scanner:latest --file ci/Containerfile.security ci/
'
```

Las unidades systemd solo necesitan re-copiarse si cambia `bauth-security-scan.service`
o `bauth-security-scan.timer`; en ese caso, agregar `systemctl daemon-reload` después.

## §9 Interpretar los resultados en SBOSDB

### §9.1 Ver componentes escaneados

```sql
-- Todos los componentes con su último escaneo
SELECT name, component_type, version, last_scanned, scan_tool
FROM bauth.vul_component
WHERE is_active = true
ORDER BY last_scanned DESC;
```

### §9.2 Ver vulnerabilidades activas

```sql
-- Vulnerabilidades sin resolver, por severidad
SELECT
    vc.name          AS crate,
    vc.version,
    vi.cve_id,
    vi.severity,
    vi.cvss_score,
    vi.impact_desc,
    vi.action_taken,
    vi.sla_deadline
FROM bauth.vul_auth_impact vi
JOIN bauth.vul_component  vc ON vc.component_id = vi.component_id
WHERE vi.resolved_at IS NULL
ORDER BY
    CASE vi.severity
        WHEN 'CRITICAL' THEN 1
        WHEN 'HIGH'     THEN 2
        WHEN 'MEDIUM'   THEN 3
        WHEN 'LOW'      THEN 4
        ELSE 5
    END,
    vi.created_at;
```

### §9.3 Marcar una vulnerabilidad como resuelta

```sql
-- Después de actualizar el crate afectado
UPDATE bauth.vul_auth_impact
SET
    resolved_at  = now(),
    action_taken = 'RESUELTO: crate actualizado a <version> en Cargo.toml/Cargo.lock'
WHERE cve_id = 'CVE-XXXX-XXXXX';
```

### §9.4 Ver historial de escaneos del componente bauth

```sql
SELECT name, version, last_scanned, scan_tool, updated_at
FROM bauth.vul_component
WHERE name = 'bauth'
ORDER BY last_scanned DESC;
```

## §10 Archivos de salida por ejecución

Cada ejecución de `security-scan.sh` crea un directorio en `OUTPUT_DIR`:

```
/var/log/bauth-security-scan/<YYYYMMDD-HHMMSS>/
├── scan.log            ← log completo de las 5 fases (colores eliminados)
├── cargo-audit.json    ← salida JSON de cargo-audit
├── cargo-audit.txt     ← salida legible de cargo-audit
├── cargo-deny.txt      ← salida de cargo deny check
├── clippy.txt          ← salida de cargo clippy
└── ingest.sql          ← SQL generado e inyectado en SBOSDB
```

Para leer el resumen de una ejecución específica:

```bash
# Ver resumen del último escaneo
ls -td /var/log/bauth-security-scan/*/ | head -1 | xargs -I{} grep -E "RESUMEN|OK|WARN|FAIL" {}/scan.log
```

## §11 Estado del arte — SA-10 en la industria

### §11.1 Inventario verificado

| Capacidad | Estado | Evidencia |
|-----------|--------|-----------|
| Imagen Podman reproducible | ✅ | `ci/Containerfile.security` — `rust:1.85-slim` + herramientas locked |
| cargo-audit (SCA/dependencias) | ✅ | Fase 2 de `security-scan.sh` — JSON en SBOSDB |
| cargo-deny (política de licencias) | ✅ | `ci/cargo-deny.toml` + Fase 3 |
| cargo-clippy SAST | ✅ | Fase 4 — `-D warnings` activo |
| Automatización semanal (systemd) | ✅ | `bauth-security-scan.timer` — activo en VPS |
| Ingesta en SBOSDB (trazabilidad) | ✅ | Fase 5 — `vul_component` T-527 + `vul_auth_impact` T-528 |
| Cobertura DAST (pruebas dinámicas) | ❌ | No implementado — bAuth es un daemon sin API HTTP expuesta |
| Fuzzing (cargo-fuzz) | ❌ | Planned — aplicable a parsers JSON-RPC y validadores BitMask |
| Análisis de composición con SBOM | ⚠️ | `cargo-sbom` no instalado; `cargo-audit` cubre CVEs parcialmente |

### §11.2 Panorama de la industria (2026)

Los sistemas IAM Enterprise de referencia aplican en 2026:

- **SCA (Software Composition Analysis):** Snyk, Dependabot, Trivy, cargo-audit — escaneo
  de dependencias contra bases de CVEs (NVD, RustSec, OSV). El estándar es ejecución en cada
  PR y semanal contra la rama main.
- **SAST:** Semgrep, CodeQL, cargo-clippy — análisis de código fuente sin ejecutarlo.
- **DAST:** OWASP ZAP, Burp Suite — análisis dinámico de APIs en ejecución. No aplica
  directamente a bAuth por su arquitectura Unix socket (sin HTTP expuesto).
- **SBOM (Software Bill of Materials):** generación de `SBOM.json` (formato CycloneDX/SPDX)
  como artefacto firmado por cada build. Requerimiento emergente en regulaciones EU/US 2025.
- **Contenedores soberanos:** la tendencia de 2026 es mover pipelines a runners sin Docker Hub
  dependiendo de registros privados (Quay.io, Harbor, Nexus). bAuth usa imagen base pública
  (`docker.io/library/rust:1.85-slim`) — migrar a imagen base interna es la evolución natural.

### §11.3 Comparativa honesta

| Capacidad | bAuth | GitHub Actions + Dependabot | GitLab CI + Trivy |
|-----------|:-----:|:---------------------------:|:-----------------:|
| Escaneo de dependencias | ✅ cargo-audit | ✅ Dependabot | ✅ Trivy |
| Política de licencias | ✅ cargo-deny | ⚠️ requires FOSSA | ⚠️ requires liccheck |
| SAST | ✅ clippy | ✅ CodeQL | ✅ Semgrep |
| DAST | ❌ | ✅ ZAP (API HTTP) | ✅ ZAP |
| Sin runtime de terceros | ✅ Podman rootless | ❌ requiere GitHub | ❌ requiere GitLab |
| Ingesta en BD propia | ✅ SBOSDB | ❌ solo alertas | ❌ solo alertas |
| Soberanía total | ✅ | ❌ | ❌ |

**Diferenciador bAuth:** la ingesta directa en `SBOSDB` hace que los hallazgos sean datos de
primera clase, consultables con SQL junto al modelo de identidad — no notificaciones efímeras
en una plataforma de terceros.

### §11.4 Brechas P1/P2/P3

| Brecha | Norma | Prioridad | Propuesta |
|--------|-------|:---------:|-----------|
