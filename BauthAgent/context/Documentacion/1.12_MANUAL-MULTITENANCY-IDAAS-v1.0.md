## 1. Audiencia, propósito y alcance

Este manual documenta cómo bAuth aloja a **múltiples organizaciones (tenants) sobre un solo plano de
identidad**: el modelo de aislamiento, el ciclo de vida del tenant, sus dominios DNS, cómo el tenant
viaja por cada sesión y token, y la superficie **IDaaS** (`bauth.idp.*`) con la que bAuth se ofrece
como proveedor de identidad a clientes externos — el territorio que Auth0/Okta venden como
*Organizations* y que bAuth implementa de forma soberana.

**Audiencia:** desarrolladores bAuth, el instalador `bos` (provisioning de tenants), arquitectos que
evalúan bAuth como IDaaS, operadores multi-cliente.

**Por qué manual propio (detección del vistazo 2026-07-10):** `bauth.tenant.*` (6 métodos) y
`bauth.idp.*` (12 métodos) — 18 métodos, ~16% de la superficie API — no tenían manual dueño; el
tenant aparecía disperso en D00, Directrices y Producto. Este manual consolida y, en el proceso,
**destapa vestigios KC** en la superficie IDaaS (§8) que la reparación debe corregir.

## 2. El principio — un plano, muchos inquilinos soberanos

El tenant es la **frontera de soberanía superior** del modelo de identidad: por encima de la empresa,
la sucursal y el punto lógico. Todo lo que bAuth decide está contenido en un tenant:

```
TENANT  (frontera de aislamiento — este manual)
  └── EMPRESA  (unidad legal — D00)
        └── SUCURSAL  (unidad operativa — D00)
              └── POS LÓGICO  (punto de trabajo — D00)
                    └── sesión (ctx_id — 1.11)
```

Esa jerarquía no es decorativa: es **la estructura del `ctx_id`** (verificado,
`context_plane.rs` — `CtxPlane::new_pending(tenant_id, empresa_id, sucursal_id, pos_logico, ttl)`
exige el `tenant_id` UUID como primera coordenada; sin tenant no se crea contexto). Y es la
estructura del token: el claim `tenant_id` viaja en **todo JWT** (verificado, `jwt_builder.rs`).

**Dos roles simultáneos de bAuth respecto del tenant:**

| Rol | Qué significa | Superficie |
|-----|---------------|-----------|
| **Multi-tenant interno** | El SBOS de un cliente aloja varias organizaciones (grupo empresarial, marcas) | `bauth.tenant.*` |
| **IDaaS externo** | bAuth se ofrece como IdP a aplicaciones/clientes de terceros, por tenant | `bauth.idp.*` |

## 3. El modelo de aislamiento — pool con discriminador

La industria reconoce tres modelos de aislamiento (§9): **silo** (un almacén por tenant), **pool**
(almacén compartido con discriminador) y **bridge** (híbrido). bAuth implementa **pool** con tres
refuerzos de infraestructura:

| Capa | Mecanismo (verificado) | Aislamiento |
|------|------------------------|-------------|
| **Datos** | Un solo schema `bauth` en `SBOS_db`; toda tabla tenant-scoped lleva `tenant_id UUID` y cada handler filtra `WHERE tenant_id = $1` | Lógico (por consulta) |
| **Infraestructura** | `idn_tenant.namespace_k8s` — cada tenant recibe su namespace de infraestructura | Físico parcial |
| **Red / entrada** | Dominios DNS propios por tenant (`idn_tenant_domain`, §5) — cada tenant entra por su FQDN | Perimetral |
| **Token** | `tenant_id` en el claim + `aud` per-tenant (`bchat-{tenant_id}`) — un token de un tenant no valida en otro | Criptográfico |

> ### ⚠️ La debilidad conocida del pool puro (brecha B3 — §10)
> **No hay Row-Level Security** en las migraciones del esquema (verificado:
> `grep 'ROW LEVEL SECURITY' DDLs/migrations/*.sql` → vacío). El aislamiento de datos descansa
> **exclusivamente** en que cada handler recuerde el `WHERE tenant_id` — una sola capa de defensa.
> La práctica de industria para pool es doble capa: el WHERE del código **+ RLS de PostgreSQL**
> (`CREATE POLICY ... USING (tenant_id = current_setting('app.tenant_id')::uuid)`), de modo que un
> handler olvidadizo devuelva **cero filas** en vez de filtrar datos ajenos. Es la brecha P2 más
> importante de este manual. (El schema `bauth` es gobernable por bAuth — la migración se propondrá
> cuando se reabra el código.)

## 4. `idn_tenant` — el ciclo de vida del inquilino

El DDL canónico (`sbos_00__esquema_base.sql`, verificado) es un ciclo de vida completo, no un
catálogo plano:

### 4.1 Identidad y tipo

| Columna | Detalle |
|---------|---------|
| `tenant_id` | `UUID PRIMARY KEY DEFAULT uuidv7()` — ordenable por tiempo |
| `tenant_slug` | `UNIQUE NOT NULL` — identificador legible (`empresa-abc`) |
| `tenant_name` · `tenant_type` | Nombre + `tenant_type_enum` (default `STANDARD`) |

### 4.2 Ciclo de vida — 7 estados + provisioning + soft-delete GDPR

```
status:  PENDING_VERIFICATION → (verified_at/verified_by) → activo → suspended_at → deleted_at
provisioning_status:  PENDING → INFRA_PROVISIONING → SCHEMA_CREATED → IDP_CONFIGURED → COMPLETED
purge_after:  deleted_at + 30 días  — grace period antes del purge definitivo (GDPR Art. 17)
```

Esto codifica dos verdades enterprise: (a) **el alta de un tenant es un pipeline de provisioning**
(infra → esquema → IdP), no un INSERT; (b) **la baja es un derecho reglado** — soft-delete con 30
días de gracia y purga definitiva, exactamente el derecho de supresión del GDPR.

### 4.3 Datos legales y plan

`legal_name` · `tax_id` · `registration_number` · `country` (default `BO`) · `plan_tier` — el tenant
es una **persona jurídica con plan comercial**, la base real de `idp.billing` (§7).

> Nota de vestigio: las columnas `realm_kc` / `realm_kc_ext` pertenecen a la era Keycloak — ver §8.

## 5. Dominios DNS por tenant — `idn_tenant_domain`

Cada tenant posee sus **entradas DNS** (verificado, `domain_crud.rs`):

| Columna | Uso |
|---------|-----|
| `subdomain` · `fqdn` | `empresa-abc` → `empresa-abc.sbos.app` |
| `domain_type` (enum) | Tipo de dominio (app, auth, correo, …) |
| `is_primary` | El dominio principal del tenant |
| `deploy_status` | Estado del despliegue DNS/TLS del dominio |

Los 3 métodos `bauth.tenant.domain.{list,create,delete}` administran este catálogo. Es la base
material del **branding por tenant** (§9): el login del tenant vive en SU dominio — el patrón que
Auth0 llama *sub-domain Organization*.

## 6. El tenant en el plano de ejecución

Dónde toca el tenant cada pieza del sistema en tiempo real (todo verificado):

| Punto | Mecanismo |
|-------|-----------|
| **Arranque** | `startup.rs` — `SELECT tenant_id FROM bauth.idn_tenant WHERE active = TRUE` (precarga de tenants vivos) |
| **Creación de contexto** | `bauth.ctx.create` exige `tenant_id` UUID (error `-32602` si falta) — capa 1 del ctx_id |
| **Token interno** | Claim `tenant_id` en todo JWT (`jwt_builder.rs`) |
| **Token externo (OIDC)** | Claim `sbos_tenant` + `aud` per-tenant (`rocketchat-{tenant_id}`, `bchat-{tenant_id}`) — contrato C-BAUTH-002; **pendiente** (brecha G3 de [4.01 §5](4.01_MANUAL-BAUTH-BNOTIFY-v1.0.md)) |
| **Sesiones** | `ses_context.tenant_id` — toda sesión pertenece a un tenant; los eventos CAEP llevan `tenant_id` |
| **CLI** | `bauthctl tenant list` ([7.04 §4](7.04_MANUAL-CLI-PRUEBAS-EXTERNAS-v1.0.md)) |

## 7. La superficie API — `tenant.*` (real) e `idp.*` (declarativa)

Los 18 métodos, con su **naturaleza verificada** — la distinción es el corazón de la madurez (§10):

### 7.1 `bauth.tenant.*` — 6 métodos, CRUD REAL contra BD ✅

| Método | Handler | Qué hace (verificado) |
|--------|---------|------------------------|
| `tenant.list` | `tenant_list.rs` | `SELECT` sobre `idn_tenant` |
| `tenant.create` | `org_crud.rs` | `INSERT INTO idn_tenant` (slug, name, country, plan_tier, namespace_k8s, status…) |
| `tenant.get` | `org_crud.rs` | Ficha completa del tenant (incl. legal_name, domain) |
| `tenant.domain.list/create/delete` | `domain_crud.rs` | CRUD de `idn_tenant_domain` (con lookup del slug) |

### 7.2 `bauth.idp.*` — 12 métodos, superficie IDaaS DECLARATIVA ⚠️

**Hallazgo de madurez (verificado):** `idp_external.rs` contiene **cero consultas a BD**
(`grep -c sqlx` → 0). Los 12 handlers retornan **JSON estático descriptivo** — declaran la
capacidad, no la ejecutan. Son la *especificación ejecutable* del producto IDaaS, no el producto:

| Método | Promete | Estado real |
|--------|---------|-------------|
| `idp.discovery` | OIDC discovery per-tenant | ⚠️ estático + **endpoints estilo KC** (§8) |
| `idp.isolation` | Estado del aislamiento multi-tenant | ⚠️ estático + **describe realms KC** (§8) |
| `idp.federation` | Federación con IdPs externos (BYO-IdP) | declarativo |
| `idp.portal` | Portal de autogestión del tenant | declarativo |
| `idp.billing` | Facturación por tenant | declarativo (el dato real vive en `idn_tenant.plan_tier`) |
| `idp.sla` | SLA del servicio de identidad | declarativo |
| `idp.saml` | SAML 2.0 per-tenant | declarativo |
| `idp.scim` | Aprovisionamiento SCIM (RFC 7644) | declarativo — **pero el servidor SCIM real EXISTE aparte**: `bauth.scim.*`, 5 métodos con BD (corrección 2026-07-11 — [9.02 §12](9.02_MANUAL-REFERENCIA-API-v1.0.md)) |
| `idp.branding` | Marca por tenant | declarativo (el dato real vive en `idn_tenant_domain`) |
| `idp.admin` | Admin API del IdP | declarativo |
| `idp.compliance` | Reportes de cumplimiento por tenant | declarativo (el dato real vive en `bauth_30__compliance_qa`) |
| `idp.residency` | Residencia de datos por tenant | declarativo |

**La lectura correcta:** bAuth ya **declaró por API** el catálogo IDaaS completo (lo que Auth0/Okta
cobran como enterprise tier) y ya **posee las tablas** donde ese catálogo debe leer (plan_tier,
dominios, compliance_score). La brecha es **conectarlos** — L1→L2/L3, no diseñar desde cero.

## 8. ⚠️ Vestigios Keycloak en la superficie IDaaS

El vistazo de consistencia detectó que la superficie `idp.*` quedó **congelada en la era KC**
(anterior a ADR-010). Tres hallazgos — correcciones pendientes de la reparación (código congelado):

| # | Vestigio (verificado) | Contradicción | Corrección pendiente |
|---|------------------------|---------------|----------------------|
| V1 | `idp.isolation` responde `"model": "realm_por_tenant"`, `"keycloak_version": "26.6.2"` y describe 3 realms KC (`sbos_system`, `tenant_{id}`, `tenant_{id}_ext`) | ADR-010 eliminó KC; los tiers (SU/BIZ/EXT) hoy son **nativos** (BitMask + políticas por tier) | Reescribir la respuesta al modelo real: pool + namespace + dominios + tiers nativos |
| V2 | `idp.discovery` emite endpoints **estilo KC** (`/protocol/openid-connect/auth…`, base `auth.sbos.skull.bo/{tenant}`) — mientras `bauth.oidc.discovery` (nativo, `oidc_provider.rs`) emite la superficie propia | **Dos discoveries divergentes** — un cliente externo recibiría rutas que no existen | Unificar: `idp.discovery` = discovery nativo parametrizado por tenant (un solo emisor de verdad) |
| V3 | Columnas `idn_tenant.realm_kc` / `realm_kc_ext` | Modelo KC en el DDL canónico | Renombrar/reinterpretar (p. ej. `coleccion_biz` / `coleccion_ext` como agrupadores lógicos nativos) — schema `bauth` gobernable, migración al reabrir código |

> Estos tres vestigios son **la misma clase de hallazgo** que el "Python/Apprise" de notify.rs: capas
> que quedaron escritas contra una concepción ya superada. Registrados también en
> `REVISION-CONSISTENCIA-MANUALES-2026-07-10.md`.

## 9. Estado del arte — multi-tenancy IAM 2026: lo que hay y lo que no hay

### 9.1 Los tres modelos de aislamiento de la industria

La taxonomía establecida: **silo** (un almacén de identidad por tenant — máximo aislamiento, máximo
costo), **pool** (almacén compartido con discriminador `tenant_id` — el punto de partida de casi todo
B2B SaaS) y **bridge** (híbrido: silo para los tenants sensibles, pool para el resto). La práctica
común: *empezar pool y silo-izar a los clientes grandes*.

**bAuth es pool** (§3) con refuerzos de infraestructura (namespace, DNS) — correcto para su etapa;
el camino bridge queda abierto por diseño (el `namespace_k8s` por tenant ya apunta ahí).

### 9.2 Las capacidades per-tenant que definen la categoría

| Capacidad (industria) | Quién la vende | bAuth |
|------------------------|----------------|-------|
| Organizations como entidad de 1ª clase | Auth0 Organizations, Okta orgs, Entra tenants | ✅ `idn_tenant` con ciclo de vida MÁS rico (provisioning pipeline + GDPR purge) |
| Sub-domain por organización | Auth0 (patrón sub-domain org) | ✅ `idn_tenant_domain` (fqdn + deploy_status) |
| Branding por tenant | estándar B2B | ⚠️ declarado (`idp.branding`), sin datos conectados |
| **BYO-IdP** (cada tenant trae su IdP: Okta SAML, Entra OIDC, Google) | el diferenciador B2B de Auth0/Okta | ⚠️ declarado (`idp.federation`), sin implementación per-tenant |
| Residencia de datos por tenant | requisito legal creciente | ⚠️ declarado (`idp.residency`); la soberanía TOTAL de bAuth (todo en el servidor del cliente) lo resuelve **por diseño** para el caso single-region |
| SCIM provisioning | RFC 7644, estándar enterprise | ⚠️ **servidor real existe** (`bauth.scim.*`, 5 métodos + BD — L2); falta integrarlo per-tenant y verificar conformidad |
| Aislamiento con RLS (pool endurecido) | práctica recomendada PostgreSQL | ❌ sin RLS (§3) |

### 9.3 El diferenciador soberano

Donde Auth0/Okta ofrecen *residencia por región de SU nube*, bAuth ofrece algo categorialmente
distinto: **el plano completo vive en el servidor del cliente** — la residencia no es una opción de
configuración, es la arquitectura. Para un grupo empresarial boliviano (Ley 164, SIN), eso convierte
la debilidad aparente (no somos SaaS global) en el argumento de venta del pilar VII.

## 10. Madurez L0-L4 y brechas P1/P2/P3

| Capacidad | Madurez | Evidencia |
|-----------|:-------:|-----------|
| Registro y ciclo de vida del tenant | **L3** | DDL 7 estados + provisioning + CRUD real + carga en startup ✅ |
| Tenant en ctx/JWT/sesión | **L3** | Capa 1 del ctx_id + claim en todo token ✅ |
| Dominios DNS per-tenant | **L2** | Tablas + CRUD ✅; deploy_status sin orquestador verificado |
| Aislamiento de datos | **L2** | Pool por discriminador ✅; **sin RLS** (una sola capa) ⚠️ |
| Superficie IDaaS (`idp.*`) | **L1** | 12 métodos **declarativos** (0 consultas BD) + vestigios KC (§8) |
| Claims OIDC externos per-tenant | **L1** | `sbos_tenant`/`aud` per-tenant especificados (contrato), no emitidos |

### Brechas priorizadas

| # | Brecha | Prioridad |
|---|--------|:---------:|
| B1 | **Purgar los vestigios KC de `idp.isolation`/`idp.discovery`** (V1, V2 — §8): la API describe una arquitectura eliminada | **P1** |
| B2 | Emitir `sbos_tenant` + `aud` per-tenant en el perfil OIDC externo (= G3 de 4.01; habilita bChat/bRocket) | **P1** |
| B3 | **RLS por `tenant_id`** en las tablas tenant-scoped (doble capa de aislamiento pool) — migración schema `bauth` | **P2** |
| B4 | Conectar `idp.billing`/`branding`/`compliance` a sus datos reales (plan_tier, tenant_domain, compliance_score) — L1→L2 | **P2** |
| B5 | BYO-IdP per-tenant (federación entrante: el tenant trae Okta/Entra/Google) — el gancho B2B | **P2** |
| B6 | ~~Motor SCIM~~ **corregido 2026-07-11**: el servidor SCIM existe (`scim_server.rs`, 5 métodos, 8 consultas BD). Brecha real: scoping per-tenant + conformidad RFC 7644 verificada + conectar `idp.scim` a él | P3 |
| B7 | Renombrar `realm_kc`/`realm_kc_ext` (V3) — migración DDL, HITL | P3 |
| B8 | Camino bridge: silo opcional (schema o BD dedicada) para tenants regulados | P3 |

**Veredicto (carta rectora):** el **núcleo multi-tenant es L3** (ciclo de vida, contexto, token) —
mejor que el estándar de industria en ciclo de vida (provisioning + GDPR). La **cara IDaaS es L1**:
un catálogo declarado con las tablas ya existentes esperando conexión. La distancia es integración y
limpieza de vestigios — no arquitectura. Consistente con el patrón de todo el corpus.

## 11. Cumplimiento normativo

| Norma | Cómo la cubre el modelo |
|-------|--------------------------|
| **GDPR Art. 17** (supresión) | Soft-delete + `purge_after` 30 días en el DDL (§4.2) — el derecho está codificado en el esquema |
| **ISO 27001:2022 A.5.15** | Acceso segregado por tenant en cada capa (datos/red/token) |
| **NIST SP 800-63C** | Federación per-tenant (declarada; B5) |
| **SCIM RFC 7644 / SAML 2.0 / OIDC** | Superficie declarada (`idp.scim/saml/discovery`) — B1/B6 |
| **Ley 164 / SIN (Bolivia)** | `tax_id`, `registration_number`, `country='BO'` en la ficha legal del tenant |
