## 1. Audiencia, propósito y alcance

Este manual documenta el **Motor de Identidad** de bAuth: el sistema de validación de datos
de entidades que usa políticas AtomLang para verificar, formatear y validar atributos antes
de persistirlos en `idn_identity_attribute`.

**Audiencia:** desarrolladores bAuth, administradores de identidad.

**El motor de identidad NO evalúa permisos.** Eso lo hace el motor BitMask. El motor de
identidad **gestiona y valida** entidades y sus atributos: crea, actualiza, consulta,
valida formatos, verifica contra fuentes externas, y expone todo vía JSON-RPC y CLI.
No requiere el dashboard. Cualquier sistema externo (ERP, RRHH, CRM) puede gestionar
identidades mediante la API.

## 2. Dos motores, un lenguaje

```
MOTOR DE IDENTIDAD                    MOTOR BITMASK
──────────────────                    ─────────────
Valida DATOS                          Evalúa PERMISOS
¿El NIT es válido?                    ¿Juan puede ver el NIT?
¿El email tiene formato?              ¿Juan puede editar el email?
¿La CI fue verificada por SEGIP?      ¿Juan es SET(financieros)?

Opera sobre:                          Opera sobre:
  idn_identity_entity                           privilege_atom
  idn_identity_attribute                          privilege_role_atom
                                        UserBitMask

API:                                  API:
  bauth.entidad.atributo.get()         bauth.access.evaluate()
  bauth.entidad.atributo.set()         bauth.ctx.promote()
  bauth.entidad.atributo.search()

Lenguaje: AtomLang                    Lenguaje: AtomLang
Verbos: validate, verify, format      Verbos: read, write, approve...
```

**Ambos usan el MISMO lenguaje de políticas.** La diferencia es el propósito y los verbos.

## 3. Verbos del motor de identidad

### 3.1 `validate` — validar formato

Evalúa reglas de formato ANTES de guardar el dato. Si TODAS las reglas Permit → guarda.
Si ALGUNA Deny → rechaza con el Effect como mensaje de error.

```yaml
regla "nit_14_digitos"
  target:
    resource: idn_identity_attribute.tributario
    type: NIT
    verbo: validate
  condition:
    property_id: idn_identity_attribute.value_text
    operator: REGEX
    value: "@bauth_config_param.regex_nit_bo"
  effect:
    decision: Permit
```

```
bauth.entidad.atributo.set(t-skull, tributario, NIT, "1234")
  → nit_14_digitos: REGEX no matchea → Deny
  → { error: "NIT inválido — debe tener 14 dígitos" }
```

### 3.2 `verify` — verificar contra fuente externa

Llama a una API externa (SIN, SEGIP, ADSIB) para verificar el dato. Si la API confirma →
marca `is_verified=true` y registra `verified_by`. Si la API rechaza → Deny.

```yaml
regla "nit_verificar_en_sin"
  target:
    resource: idn_identity_attribute.tributario
    type: NIT
    verbo: verify
  condition:
    property_id: idn_identity_attribute.source
    operator: "=="
    value: api_sin
  effect:
    decision: Permit
    obligation:
      api_call: sin_verificar_nit
      marca_verificado: true
      verified_by: api_sin
```

### 3.3 `format` — transformar a canónico

Transforma el valor a formato canónico antes de guardar. No valida — solo normaliza.

```yaml
regla "telefono_a_e164"
  target:
    resource: idn_identity_attribute.telefono
    type: ANY
    verbo: format
  condition: null
  effect:
    decision: Permit
    obligation:
      transform: "strip_spaces → add_country_code_if_missing → store_as_E164"
      display_format: E164
```

```
bauth.entidad.atributo.set(act-jperez, telefono, mobile, "7 1234567")
  → telefono_a_e164: transforma → "+591-7-1234567"
  → GUARDADO con display_format=E164
```

## 5. API JSON-RPC completa del Motor de Identidad

### 5.1 CRUD de entidades

```
bauth.identidad.create(parent_id, nivel, tipo, nombre)
  → Crea entidad en idn_identity_entity
  → Valida contra idn_identity_requirement (completitud mínima)
  → Sincroniza con tablas de gobierno (idn_tenant, org_empresa...)
  → Retorna { entity_id, slug }

bauth.identidad.update(entity_id, cambios)
bauth.identidad.delete(entity_id)
bauth.identidad.get(entity_id)
bauth.identidad.list(parent_id?, nivel?, tipo?)
bauth.identidad.search(nombre, tipo?)
```

### 5.2 CRUD de atributos (con validación)

```
bauth.identidad.atributo.set(entity_id, resource, type, value)
  → format → validate → verify → INSERT/UPDATE + history

bauth.identidad.atributo.get(entity_id, resource, type?)
bauth.identidad.atributo.list(entity_id, category?, dominio_origen?)
bauth.identidad.atributo.search(resource, type?, value_pattern)
bauth.identidad.atributo.delete(entity_id, resource, type?)
```

### 5.3 Consulta de relaciones

```
bauth.identidad.hijos(entity_id)
bauth.identidad.arbol(entity_id)
bauth.identidad.atributos_por_dominio(entity_id, dominio_origen)
```

## 5 bis. Acceso vía CLI (bauthctl)

```bash
# CRUD de entidades
bauthctl identidad create --parent NULL --nivel tenant --tipo externo --nombre "DESARROLLADOR-X"
bauthctl identidad get bd-skull-corp

```

## 6. El Target con `type` explícito

El Target de las reglas de validación usa `resource` + `type` explícito, no codificado
en el path:

```yaml
target:
  resource: idn_identity_attribute.telefono
  type: emergency
  verbo: validate
```

Esto permite búsquedas atómicas sin parsear strings y un catálogo de tipos que crece
sin cambiar la gramática del lenguaje.

## 7. Integración con el motor BitMask

El motor de identidad puebla `idn_identity_attribute`. El motor BitMask gobierna quién puede ver/editar
cada atributo. La conexión está en `idn_identity_attribute.atom_code`:

```
idn_identity_attribute.atom_code ──→ privilege_atom ──→ privilege_role_atom ──→ UserBitMask

Cuando Juan Pérez intenta VER su CI:
  → idn_identity_attribute.atom_code = 5826
  → UserBitMask[5826]? → 1 → Permit → retorna el valor (enmascarado si no es zona RRHH)

Cuando un admin intenta EDITAR el NIT de una empresa:
  → idn_identity_attribute.atom_code = 5812
  → UserBitMask[5812]? → 0 → Deny → { error: "No tiene permisos para editar este atributo" }
```

## §9 — v1.1.0: N-to-N, multi-tenant y visibilidad (2026-07-15)

### Validación de relaciones N-to-N

Cada relación se valida como múltiples filas con el mismo `attr_key`. El motor de
identidad verifica que cada referencia apunte a una entidad existente:

```
Farol DEPO → compatible.sistema_id: TOY-ILUM-CARINA (fila 1)
Farol DEPO → compatible.sistema_id: TOY-ILUM-COROLLA (fila 2)
Farol DEPO → compatible.sistema_id: NIS-ILUM-SENTRA (fila 3)
```

### Referencias cross-tenant

Cuando un atributo referencia una entidad de otro tenant, el `value_data` registra
`origen_tenant`. El motor de identidad valida que la entidad referenciada exista
(aunque esté en otro tenant) y que la visibilidad lo permita.

### Visibilidad controlada

| Visibilidad | Significado |
|---|---|
| PRIVADA | Solo el tenant que creó la referencia puede verla |
| COMPARTIDA | El tenant dueño de la entidad referenciada puede ver quién la usa |
| PUBLICA | Todos pueden ver la referencia |
