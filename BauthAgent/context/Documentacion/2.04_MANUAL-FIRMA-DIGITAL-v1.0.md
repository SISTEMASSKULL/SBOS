## 1. Audiencia, propósito y alcance

Este manual documenta el **sistema de firma digital** de bAuth: los dos motores independientes
(interno y externo), sus jerarquías de certificación, perfiles, flujos, la integración con el
catálogo de roles, y la relación con las otras dos capas de evidencia (hash-chain y anclaje
blockchain).

**Audiencia:** desarrolladores bAuth, administradores de tenant (gestión de certificados
ADSIB), responsables de facturación electrónica, auditores legales.

**Deslinde:** la firma del JWT (JWS con Ed25519) vive en [MANUAL-TOKENS](2.03_MANUAL-TOKENS-v1.0.md)
§4 — es un caso de uso del motor interno. La firma XML-DSig de SAML en
[MANUAL-AUTENTICACION](2.01_MANUAL-AUTENTICACION-v1.0.md) §4. Aquí se documenta el **servicio de
firma como producto**: documentos, facturas, contratos y evidencia legal.

---

## 2. El principio absoluto — dos motores, dos mundos

> **bAuth opera DOS motores de firma digital independientes con propósitos distintos.**
> El Motor Interno firma documentos y datos dentro del ecosistema SBOS.
> El Motor Externo firma documentos destinados a entidades fuera del SBOS,
> especialmente facturas electrónicas para el SIN de Bolivia.
> **Nunca se debe usar el motor equivocado para el contexto equivocado.**

La diferencia no es técnica — es **jurídica**:

| | Motor Interno | Motor Externo |
|---|---|---|
| La firma prueba… | Integridad y origen DENTRO del SBOS | Voluntad jurídica ante TERCEROS |
| La confianza nace de… | La CA raíz propia (Vault) | La PKI nacional: ATT → ADSIB |
| Validez legal externa | ❌ Ninguna | ✅ Plena (Ley 164 Arts. 78–80) |

## 3. Motor Interno — PKI propia vía Vault

### 3.1 Propósito y usos autorizados

Firma todo lo que circula **exclusivamente dentro del ecosistema**: sagas de instalación
(bos → `.sbos_state.json`), eventos CDC antes de publicar en Redis Streams (bkernel),
respuestas JSON-RPC entre daemons, logs de auditoría inmutables, documentos internos y JWT
M2M.

### 3.2 La jerarquía de certificación interna (3 niveles)

```
SBOS Root CA (Vault PKI — OFFLINE, 10 años)
  ├── SBOS Internal Sub-CA (online, 5 años)
  │     ├── Daemon Certificates        (TTL 24 h  · ECDSA P-384)  ← los 7 daemons
  │     ├── Service Account Certs      (TTL 90 d  · ECDSA P-256)  ← ctx-orchestrator, prometheus
  │     ├── Admin User Certs           (TTL 180 d · Ed25519)      ← SU, SYS N1-N2
  │     └── Application Certs          (TTL 365 d · Ed25519)      ← biedata-saga, kong-admin
  └── SBOS Code Signing CA (OFFLINE, 5 años)
        └── Firma de binarios: bosctl y daemons
```

Los TTL cortos son la defensa: un certificado de daemon vive 24 horas — un robo de clave
caduca solo. CRL con TTL 24h + OCSP responder integrado en Vault (RFC 6960).

### 3.3 Los 4 perfiles de firma

| Perfil | Formato | Añade | Uso |
|--------|---------|-------|-----|
| **INT-B** | PAdES-B / XAdES-B / CAdES-B | — | Firma simple de documentos internos |
| **INT-T** | \*-T | Sello de tiempo (Vault TimeStamp) | Logs y sagas — recomendado |
| **INT-LT** | \*-LT | Certificados + CRL/OCSP embebidos | Auditoría — verificable tras expirar el certificado |
| **INT-JWS** | JWS compacto (RFC 7515) | — | Payloads JSON, M2M, respuestas API |

### 3.4 El flujo de firma interna

```
1. Solicitud → { document_hash, profile: "INT-T", format: "XAdES",
                 requester_role: "ROL-SYS-BOS-AGENT", purpose: "saga_install_ficha" }
2. bAuth: verifica permiso del rol sobre el perfil → recupera certificado del Vault
   → firma → (≥T) añade timestamp → (≥LT) embebe CRL/OCSP → contenedor
   → audit (ctx_id, rol, hash, signature_id) → retorna
3. Verificación (cualquier daemon): certificado contra CRL/OCSP interno
   → verify(hash, sig, pubkey) → timestamp válido → {valid, signer_role, sign_date}
```

### 3.5 Políticas de acceso por tier

| Tier | Perfiles | Límite diario | Aprobación |
|------|----------|:-------------:|:----------:|
| SU | Todos | Ilimitado | No |
| SYS N1-N2 | Todos | 10,000 | No |
| SYS N3 | B, T, JWS | 1,000 | > 100/día |
| SYS N4 (M2M) | T, JWS | Ilimitado | No (automático) |
| BIZ N3-N5 | Solo B (docs internos) | 100 | Sí (admin tenant) |
| BIZ N1-N2 · EXT N0 | **No autorizado** | 0 | — |

## 4. Motor Externo — ADSIB / SIN Bolivia

### 4.1 Propósito y usos autorizados

Firma con **validez legal plena (Ley 164)** para: facturas electrónicas SIN (SFV), notas de
crédito/débito fiscales, documentos de exportación (NITEX, SENAVEX), contratos con externos,
declaraciones juradas (IVA/IT/IUE) y licitaciones públicas (SICOES).

### 4.2 La jerarquía nacional PKI Bolivia

```
ATT — Entidad Certificadora Raíz (auto-firmado, 20 años · ATT-DJ-CON SCD 1/21)
└── ADSIB — Entidad Certificadora Pública (10 años · firmadigital.bo · ADSIB-FD-POLT-015 v2.3)
      ├── Certificado Persona Natural   (1 año · RSA 2048 · Nivel Alto = token HW/HSM FIPS 140-2)
      ├── Certificado Persona Jurídica  (1 año · RSA 2048/4096 · HSM homologado ATT obligatorio)
      │     ← el de facturación electrónica SIN
      └── Certificado Firma Automática  (1 año · RSA 2048 · desatendido, firma por lote)
            ← emisión masiva de facturas (DS 3527)
```

### 4.3 Requisitos para facturación electrónica SIN

| Requisito | Detalle | Base legal |
|-----------|---------|-----------|
| Certificado | ADSIB vigente (1 año) | Ley 164 Art. 83 · DS 1793 |
| Formato | XML 1.0 UTF-8 validado contra XSD del SIN | SIN SFV |
| Firma | **XAdES-BES enveloped** dentro del XML | ETSI EN 319 132 · Anexo Técnico SIN |
| Algoritmo | **RSA-SHA256 (PKCS#1 v1.5)** — requerido por ADSIB | RFC 3447 |
| CUFD | Código Único de Facturación Diaria — renovado cada 24h | SIN SFV API |
| Dosificación | Rango de números autorizado previamente | RND 102100000020 |
| QR | Código de verificación en la representación impresa | Especificación QR SIN |
| Archivo | Conservación **8 años** en WORM | Código de Comercio Art. 44 |

### 4.4 El flujo de facturación (5 pasos)

```
1. SmartTax/Tryton/biedata genera el XML según XSD del SIN
2. Solicitud → bauth.sign.external.factura_sin { document_xml, tenant_id,
               certificate_type: "PERSONA_JURIDICA", cufd, purpose }
3. bAuth: certificado ADSIB vigente ✓ → CUFD válido ✓ → número dentro de dosificación ✓
   → clave del tenant desde Vault KV → SHA-256 del XML canónico → firma RSA-SHA256
   → XAdES enveloped → QR de verificación → audit fiscal → retorna XML firmado + QR
4. Transmisión: biedata/SmartTax → endpoint SIN → validación (XSD, firma, CUFD, dosificación)
   → aceptación/rechazo → bAuth registra el resultado
5. Entrega al cliente: PDF (PAdES) con QR + XML firmado descargable
```

### 4.5 Gestión de certificados ADSIB en Vault

Los certificados del tenant viven en `secret/adsib/{tenant_id}/` (Vault KV v2) con su PEM,
clave privada PKCS#8, tipo, nivel de seguridad, serial del HSM, NIT, vigencia y estado de
CRL/OCSP.

**El ciclo de vida gestionado** (Certificate Lifecycle Manager — cron semanal):

```
30 días antes de expirar → alerta al Admin Tenant (S016)
15 días → segunda alerta + Admin bAuth (S006)
 7 días → si auto-renovación: par RSA-4096 nuevo en Vault → CSR → ADSIB
          → certificado nuevo (365 d) → solapamiento con el anterior hasta su expiración
Expirado sin renovar → BLOQUEO de firma externa
Revocado por ADSIB   → BLOQUEO INMEDIATO (OCSP check cada hora en operación)
Máximo 4 reemisiones por certificado (política ADSIB)
```

### 4.6 Cumplimiento Ley 164 — artículo por artículo

| Requisito legal | Implementación bAuth |
|-----------------|---------------------|
| Validez jurídica (Art. 78–80) | Firma con certificado ADSIB vigente = plena validez |
| Control exclusivo del signatario (Art. 78.II) | Clave privada en Vault con acceso restringido y auditado |
| Integridad detectable (Art. 78.III) | SHA-256 + RSA — toda modificación invalida la firma |
| Verificabilidad (Art. 78.IV) | X.509 público + CRL/OCSP de ADSIB |
| Certificado vigente (Art. 82) | Validación automática ANTES de cada firma |
| Conservación 8 años | WORM storage (Loki) + backup S3/MinIO |
| Firma automática (DS 3527) | Certificado dedicado, modo desatendido por lote |

En el RolTemplate, el bloque `digital_signature_config` declara motor habilitado, perfiles,
límite diario y si exige dual-approval.

### 7.2 Los átomos D13 — la firma en el BitMask

El dominio D13 (diseño — MANUAL-BITMASK §8) reserva el módulo **`legalsg`** con 8 átomos
(`legal_sign_doc`, `invoice_sign`…), todos con `min_trust=Critical` y `blockchain_anchored=1`:
firmar legalmente exige el máximo nivel de confianza del dispositivo y deja ancla en cadena.
La evaluación de "¿puede este usuario firmar una factura?" será un bit — como todo en bAuth.

### 7.3 Columna `digital_signature` en T-041 (G-B01-08)

El catálogo de roles `idn_roles_rol_hierarchical` (T-041) materializa el contrato canónico
del rol (SBOS-ROLTEMPLATE-v6_0 bloque B01) incluyendo el campo de firma digital **G-B01-08**.
Esta columna es el receptor estructurado que el Motor de Firma Dual llenará cuando un contrato
de rol sea certificado formalmente.

#### 7.3.1 Estructura de la columna

```sql
digital_signature JSONB NOT NULL DEFAULT '{
    "algorithm":            "EdDSA_Ed25519",
    "signature":            null,
    "signed_at":            null,
    "signed_by":            null,
    "certificate_id":       null,
    "post_quantum_planned": true
}'::jsonb
```

| Campo | Tipo | Descripción | Estado |
|-------|------|-------------|:------:|
| `algorithm` | `string` | Algoritmo de firma. Valor canónico: `"EdDSA_Ed25519"` (NIST SP 800-186 §3.2.1) | ✅ fijo |
| `signature` | `string \| null` | Firma Ed25519 en Base64URL. `null` = contrato aún no certificado | ⏳ motor |
| `signed_at` | `string \| null` | ISO 8601 UTC del momento de firma. Rellenado por el motor | ⏳ motor |
| `signed_by` | `uuid \| null` | UUID del firmante (entidad en `idn_identity_entity`) | ⏳ motor |
| `certificate_id` | `string \| null` | ID del certificado Vault PKI usado para la firma | ⏳ motor |
| `post_quantum_planned` | `boolean` | Indica que la clave Ed25519 migrará a ML-DSA (FIPS 204) antes de 2030. Nunca `false` | ✅ fijo |

#### 7.3.2 Flujo de firma de un contrato de rol

Cuando el Motor de Firma Dual certifique un contrato de rol, el flujo será:

```
1. Motor detecta contrato de rol aprobado (approval_required=true → aprobado en T-152)
2. Solicita firma interna: bauth.sign.internal { perfil: "INT-LT", propósito: "role_contract" }
3. Motor Interno (Vault PKI, Ed25519) firma el hash canónico del rol (id||code||version_number)
4. Motor escribe en la columna:
      UPDATE bauth.idn_roles_rol_hierarchical
      SET digital_signature = jsonb_build_object(
          'algorithm',            'EdDSA_Ed25519',
          'signature',            <base64url>,
          'signed_at',            now()::text,
          'signed_by',            <uuid_firmante>,
          'certificate_id',       <kid_vault>,
          'post_quantum_planned', true
      )
      WHERE id = <rol_id>;
5. version_number se incrementa automáticamente (trigger trg_irrh_version_bump)
6. Evento de auditoría emitido con ctx_id (ISO 27001 A.8.15)
```

#### 7.3.3 Normas aplicables

| Norma | Aplica a |
|-------|----------|
| NIST SP 800-186 §3.2.1 (EdDSA/Ed25519) | Algoritmo de firma — curva Edwards25519 |
| NIST SP 800-207 §3.3 | Zero Trust: todo contrato de acceso debe ser verificable — la firma es la prueba |
| Ley 164 Bolivia Arts. 78–80 | La firma con certificado PKI interno tiene validez dentro del ecosistema soberano |
| ISO 27001:2022 A.8.15 | Registro de auditoría — `signed_at` + `signed_by` constituyen la trazabilidad del contrato |
| FIPS 204 (ML-DSA) | Migración post-cuántica planificada antes de 2030 — señalada por `post_quantum_planned: true` |

#### 7.3.4 Relación con el resto del B01

El campo `digital_signature` es el último subbloque del bloque B01. Los anteriores
(`version_number` con trigger `trg_irrh_version_bump`, `created_by`, `updated_by`) ya están
implementados en T-041. La firma cierra el círculo de evidencia:

```
B01 completo en T-041:
  id, parent_id, type_id, depth, status          — identidad del nodo
  created_at, updated_at                         — timestamps automáticos
  created_by, updated_by                         — actores (⏳ vía API, hoy NULL en migración)
  version_number + trigger                       — ✅ implementado (auto-incremento en UPDATE)
  change_history[]                               — ⏳ vive en T-152 Motor de Versionado (futuro)
  digital_signature                              — ✅ estructura en BD · ⏳ motor de firma pendiente
```

**Estado G-B01-08:** estructura materializada en la BD de producción. El Motor de Firma
Dual la llenará cuando `bauth.sign.internal` (perfil INT-LT) esté implementado (§10.4 P2).

## 8. La API de firma — JSON-RPC

Ambos motores se exponen por la Interface Dual (ADR-020) sobre `/run/bos/bauth.sock`:

| Método | Propósito | Estado |
|--------|-----------|:------:|
| `bauth.sign.internal.document` | Firmar documento interno (PDF/XML/binario) | ❌ diseño |
| `bauth.sign.internal.jwt` | Firmar JWT M2M | ✅ vía `jwt_signer` |
| `bauth.sign.internal` | Firmar payload JSON (hex + pubkey + kid) | ✅ **implementado** (`sign_internal.rs`) |
| `bauth.sign.internal.verify` | Verificar firma interna | ❌ diseño |
| `bauth.sign.internal.certificate` | Certificado del firmante | ❌ diseño |
| `bauth.sign.external.factura_sin` | Firmar factura para el SIN | ❌ diseño |
| `bauth.sign.external.document` | Firmar documento para externo | ❌ diseño |
| `bauth.sign.external.verify` | Verificar contra ADSIB | ❌ diseño |
| `bauth.sign.external.certificate_status` | Estado del certificado ADSIB | ❌ diseño |
| `bauth.sign.external.renew_certificate` | Renovar certificado ADSIB | ❌ diseño |

El handler implementado (`sign_internal.rs`, verificado) firma payloads con Ed25519 vía

básico. Los contenedores AdES, la verificación de permisos por perfil/tier y todo el motor
externo son diseño pendiente (§10.4).

## 9. Las tres capas de evidencia — firma, cadena y anclaje

La firma digital es una de **tres capas complementarias** de evidencia que bAuth apila:

```
CAPA 1 — FIRMA           ¿Quién lo dijo y que no se alteró?
  Ed25519 (interno) / RSA-SHA256 ADSIB (externo, validez legal)
        │
CAPA 2 — HASH-CHAIN      ¿En qué orden ocurrió y que no falta nada?
  prev_hash + token_seq en cada token (MANUAL-TOKENS §5, invariantes I-1/I-2)
        │
CAPA 3 — ANCLAJE         ¿Puede probarse ante terceros sin confiar en bAuth?
  Merkle Engine (merkle.rs — RFC 6962, Keccak-256, lotes de hasta 1M eventos,
  proofs verificables offline) → anclado en Besu QBFT (D12) → verificable externamente
```

Cada capa responde una pregunta distinta y falla de forma independiente: falsificar un evento
exigiría romper la firma, Y la cadena, Y el árbol Merkle anclado en blockchain — con la
tercera capa fuera del control de bAuth (Ley 164 + evidencia externa).

### 10.2 Lo que hace la industria en 2026

1. **La firma remota cualificada es el estándar (CSC API v2.2):** el Cloud Signature
   Consortium publicó la v2.2 de su API (nov. 2025) — el patrón universal: la plataforma envía
   el **hash** al QTSP (proveedor de confianza cualificado), la clave privada firma dentro de
   un **QSCD** (dispositivo cualificado, HSM) y devuelve la firma. **El flujo del motor
   externo de bAuth es exactamente este patrón** — con Vault como custodio y ADSIB como
   autoridad.
2. **La wallet EUDI firma con QES:** la novedad eIDAS 2.0 — el ciudadano firma con calidad
   jurídica desde su wallet de identidad. El CSC Interoperability Event (marzo 2026, Bucarest)
   reunió a proveedores de wallets y QTSPs para probar interoperabilidad. La firma deja de ser
   un applet corporativo y pasa a la identidad personal portátil.
3. **AdES baseline (ETSI EN 319 102/122/132/142)** sigue siendo la gramática universal:
   B (básica) → T (timestamp) → LT (long-term) → LTA (archivo) — la escala que los perfiles
   INT-B/T/LT de bAuth calcan.
4. **Post-cuántico en firma:** FIPS 204 (ML-DSA) publicado — los QTSPs europeos ya planifican
   certificados híbridos. Deadline CNSA 2.0: 2030.
5. **Bolivia:** la PKI nacional (ATT→ADSIB) opera sobre RSA-SHA256 con renovación anual y HSM
   homologado para persona jurídica — sin señales públicas de migración PQC; la modernización
   vendrá por el lado del SIN (SFV) antes que por ADSIB.

### 10.3 Comparativa — bAuth vs los modelos de firma

| Criterio | bAuth (diseño) | QTSP cloud (CSC) | DocuSign/Adobe | Portal ADSIB manual |
|----------|:--------------:|:----------------:|:--------------:|:-------------------:|
| Validez legal Bolivia (Ley 164) | ✅ vía ADSIB | ⚠️ si EC autorizada ATT | ❌ AdES sin EC boliviana | ✅ |
| Firma masiva desatendida (facturas) | ✅ DS 3527 | ✅ | ⚠️ | ❌ manual |
| Custodia de clave | Vault (+HSM nivel Alto) | QSCD/HSM | Cloud propio | Token del usuario |
| Doble motor interno/externo separado | ✅ único | ❌ | ❌ | ❌ |
| Firma integrada al RBAC (perfiles por tier) | ✅ diseño | ❌ | ⚠️ | ❌ |
| Evidencia en 3 capas (firma+cadena+Merkle) | ✅ único | ❌ | ⚠️ audit trail | ❌ |
| API estándar (CSC) | ❌ gap | ✅ | ⚠️ | ❌ |
| Soberano (sin SaaS externo) | ✅ | ❌ | ❌ | ⚠️ |

**Lectura honesta:** el diseño de bAuth es el único que une validez legal boliviana +
facturación masiva + RBAC + evidencia en 3 capas, todo soberano. Pero hoy **solo la capa
JWS/Ed25519 está implementada** — el motor externo (el de la validez legal, el que factura)
es 100% diseño. Es la brecha con mayor impacto de negocio de todo bAuth: sin él no hay
facturación electrónica.

### 10.4 Brechas por prioridad

**P1 — El motor externo (bloquea facturación electrónica):**

| Brecha | Enfoque | Requiere |
|--------|---------|:--------:|
| XAdES-BES enveloped RSA-SHA256 | Módulo `domain/signature/xades.rs` — canonicalización C14N + plantilla del Anexo Técnico SIN; crates candidatas o implementación propia sobre `rsa`+`sha2` | — |
| Handlers `sign.external.*` (5) | `factura_sin` primero: validaciones CUFD/dosificación + firma + QR | — |
| Vault KV `secret/adsib/{tenant}` + Lifecycle Manager | Esquema §4.5 + cron de renovación con alertas S016/S006 | HITL (estructura Vault) |
| Verificación de rol/perfil/límite en TODO handler de firma | El `sign_internal` actual firma sin verificar permisos — aplicar §3.5 y §7.1 antes de exponer | — |

**P2 — Completar el motor interno:**

| Brecha | Enfoque |
|--------|---------|
| Contenedores PAdES/XAdES/CAdES internos (perfiles B/T/LT) | Reutilizar el módulo XAdES de P1; PAdES sobre `lopdf`/equivalente |
| TSA interna (perfil T) | Vault TimeStamp o RFC 3161 propio firmado por la Sub-CA |
| `sign.internal.verify` + `certificate` | Verificador con CRL/OCSP de Vault |
| Desplegar y evidenciar la jerarquía CA 3 niveles | Verificación AA-1 en VPS (root offline, sub-CA online, TTLs) |

**P3 — Futuro:**

- Compatibilidad CSC API v2.2 (bAuth como "QTSP interno" consumible por plataformas de firma estándar)
- Certificados híbridos Ed25519+ML-DSA (FIPS 204) en la PKI interna — antes de 2030
- Verificación de QES de wallets EUDI (cuando lleguen firmantes europeos — enlaza con MANUAL-METODOS §8.2)
- Átomos D13 `legalsg` activos: la autorización de firma como bit (con el DDL D13)
