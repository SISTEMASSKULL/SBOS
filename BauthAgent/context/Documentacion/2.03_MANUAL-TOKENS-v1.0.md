## 1. Audiencia, propósito y alcance

Este manual documenta el **token de bAuth**: su estructura de claims, su firma, su cadena
forense, su cifrado opcional, su ciclo de vida y los protocolos que lo acompañan.

**Audiencia:** desarrolladores bAuth, desarrolladores de daemons SBOS que consumen el token,
auditores de seguridad.

**Deslinde con los manuales hermanos:** los métodos que AUTENTICAN al usuario viven en
[MANUAL-AUTENTICACION](2.01_MANUAL-AUTENTICACION-v1.0.md); la infraestructura de sesiones y sus
brechas (rotación de refresh, logout, PAR) en su §16 — este manual no la repite. Aquí se
documenta el **artefacto token**: qué contiene, cómo se firma, cómo se encadena y cómo se
valida.

## 2. Filosofía del token bAuth

Tres decisiones de diseño definen el token y lo distinguen de un JWT convencional:

1. **El token porta IDENTIDAD y CONTEXTO — no permisos.** El RolBitMask NUNCA viaja en el
   token (§9). Un JWT de bAuth dice *quién eres, dónde estás, cómo te autenticaste y bajo qué
   contexto* — lo que puedes hacer se evalúa server-side en cada petición.
2. **Cada token está encadenado al anterior.** Los claims `prev_hash` y `token_seq` forman una
   hash-chain forense (§5): la secuencia completa de tokens emitidos es verificable y ningún
   token puede insertarse, eliminarse ni reordenarse sin romper la cadena (ISO 27001 A.8.15).
3. **Un solo algoritmo de firma, sin negociación.** EdDSA Ed25519 — el firmador no acepta otro
   (§4). Esto elimina por construcción la familia de ataques de confusión de algoritmo
   (`alg:none`, RS256→HS256) que RFC 8725 lista como amenaza #1.

## 3. La estructura de claims — BauthClaims

La estructura real (`jwt_builder.rs`, verificada) tiene **38 claims principales** organizados
en 8 grupos, más 2 subestructuras (`GeoClaim`, `AuthStep`) — 47 campos públicos en total:

### 3.1 Grupo RFC 7519 — registrados (7)

| Claim | Campo Rust | Tipo | Contenido |
|-------|-----------|------|-----------|
| `sub` | subject | String | UUID del usuario |
| `iss` | issuer | String | `https://bauth.sbos.bo` |
| `aud` | audience | Vec\<String\> opc. | Daemons/clientes destinatarios |
| `exp` | expiration | i64 | Expiración (epoch) |
| `iat` | issued_at | i64 | Emisión |
| `nbf` | not_before | i64 opc. | No válido antes de |
| `jti` | jwt_id | String | ID único del token (anti-replay) |

### 3.2 Grupo OIDC Core (4)

| Claim | Contenido |
|-------|-----------|
| `nonce` | Anti-replay del flujo authorization code |
| `auth_time` | Momento de la autenticación original |
| `acr` | Authentication Context Class (LoA como URI) |
| `amr` | Métodos usados: `["pwd","totp"]` (RFC 8176) |

### 3.3 Grupo Context Plane — SBOS-049 (2)

| Claim | Contenido |
|-------|-----------|
| `ctx_id` | **Obligatorio** — el contexto activo (tenant.bdomain.bsubdomain.pos) |
| `domain_results` | Resultado de la evaluación por dominio al emitir (JSON) |

### 3.4 Grupo organizacional — el árbol D00 (4)

| Claim | Contenido |
|-------|-----------|
| `tenant_id` | Tenant (obligatorio) |
| `empresa_id` · `sucursal_id` · `pos_logico` | bDomain · bSubDomain · punto de operación |

### 3.5 Grupo contexto de autenticación (5)

| Claim | Contenido |
|-------|-----------|
| `level_of_assurance` | LoA 1–3 (AAL alcanzado) |
| `auth_methods` | Métodos de la sesión |
| `device_trust` | Nivel de confianza del dispositivo |
| `session_id` | Sesión en Redis |
| `risk_score` | Score de riesgo al emitir (0.0–1.0) |

### 3.6 Grupo trazabilidad W3C (3)

`traceparent` · `tracestate` (W3C Trace Context) · `invoked_at` (timestamp RFC 3339 de la
invocación) — permiten correlacionar el token con las trazas OpenTelemetry del ecosistema.

### 3.7 Grupo contexto de red (8)

| Claim | Contenido |
|-------|-----------|
| `source_ip` · `source_mac` · `source_hostname` | Origen de red |
| `network_zone` | Zona de red (D7) |
| `geo_location` | Subestructura `GeoClaim`: lat, lon, accuracy_m, country, city |
| `device_id` · `device_category` | Dispositivo registrado y su clase |
| `user_agent` | Cliente HTTP |

### 3.8 Grupo forense + OAuth (5)

| Claim | Contenido |
|-------|-----------|
| `auth_chain` | Subestructura `Vec<AuthStep>`: cada paso de autenticación (método, resultado) |
| `prev_hash` | SHA-256 del token anterior — el eslabón de la cadena (§5) |
| `token_seq` | Número de secuencia monotónico |
| `scope` · `client_id` | OAuth 2.0 clásico |

> **Nota de tamaño:** con 38 claims el token es más grande que un JWT típico (~8 claims).
> Es una decisión deliberada: el token ES el expediente forense portátil de la sesión. Los
> claims opcionales (`Option<T>`) se omiten en la serialización cuando son None — un token
> M2M interno viaja liviano; uno de usuario final con geo + device viaja completo.

## 4. La firma — Ed25519 vía ring y Vault

`jwt_signer.rs` (B48.T02) implementa el firmador:

| Aspecto | Implementación | Evidencia |
|---------|----------------|-----------|
| Algoritmo | **EdDSA Ed25519** — único, sin negociación | `ring::signature::Ed25519KeyPair` |
| Normas | FIPS 186-5 · RFC 8032 · NIST SP 800-186 | encabezado del módulo |
| Clave en desarrollo | Generada en memoria (SystemRandom) | modo development |
| Clave en producción | **Vault PKI** — la privada nunca toca el disco de bAuth | modo producción |
| Identificador de clave | `kid` en el header — habilita rotación de claves | `SignedToken.kid` |
| Salida | JWT compacto + partes separadas (header/payload/signature b64url) | struct `SignedToken` |

La clave pública se publica en el endpoint JWKS del OIDC Provider (`/jwks`) — cualquier daemon
o PEP verifica la firma localmente sin llamar a bAuth.

**Por qué Ed25519 y no RS256/ES256:** firmas de 64 bytes (vs 256 de RSA), verificación más
rápida, sin parámetros elegibles que equivocar (curva y hash fijos), y resistencia a los
ataques de canal lateral que afectan a ECDSA con nonces débiles.

## 5. La hash-chain forense

`token_issue.rs` encadena cada token emitido al anterior. El estado global:

```rust
struct ChainState { last_hash: Option<String>, next_seq: u64 }
// Un único TokioMutex protege ambos — LazyLock global, seq inicia en 1
```

**Las dos invariantes formales (documentadas en el código):**

- **I-1 — Orden total:** el orden de firma ES el orden de la cadena. `prev_hash` y `seq` se
  leen atómicamente dentro de la sección crítica — es imposible que el token con seq=N apunte
  al hash de un token firmado después.
- **I-2 — Sin bifurcaciones:** ningún par de tokens comparte el mismo `prev_hash` — la cadena
  es una lista, nunca un árbol.

**La sección crítica es mínima y sin I/O** (pasos 6–9 del emisor): leer prev_hash+seq →
aplicar claims de cadena (+DPoP si aplica) → firmar → actualizar estado. Todo lo costoso
(consultas, construcción de claims) ocurre fuera del lock.

**Qué habilita:** un auditor puede verificar que la secuencia de tokens de un período está
completa — cada `prev_hash` debe coincidir con el SHA-256 del token anterior y cada
`token_seq` debe ser consecutivo. Un token "fantasma" insertado, un token eliminado o un
reordenamiento rompen la verificación. Combinado con el anclaje Merkle D12, la evidencia es
verificable externamente (Ley 164).

## 6. Cifrado JWE — tokens sensibles

Para claims que no deben ser legibles por intermediarios, `jwe_encrypt.rs` implementa
JWE (RFC 7516) en serialización compacta:

| Parámetro | Valor |
|-----------|-------|
| Key encryption (`alg`) | `dir` — cifrado directo con clave simétrica compartida |
| Content encryption (`enc`) | `A256GCM` — AES-256-GCM (FIPS 197 · NIST SP 800-38D) |
| Formato | `header.encrypted_key.iv.ciphertext.tag` |
| Nonce | 96 bits aleatorios (OsRng) por token |

**Cuándo se usa:** tokens que atraviesan sistemas de terceros o que portan datos personales
(geo_location precisa, source_mac). El JWT firmado es legible por diseño (base64, no cifrado)
— cuando la confidencialidad importa, se envuelve: **JWS dentro de JWE** (firmar primero,
cifrar después).

## 7. Ciclo de vida del token

```
EMISIÓN (token_issue.rs)
  autenticación exitosa → construir BauthClaims (38) → hash-chain (I-1/I-2)
  → firmar Ed25519 → registrar en audit → entregar
       │
VALIDACIÓN (en cada petición)
  1. Firma Ed25519 contra JWKS               ← local, sin red
  2. exp / nbf / iat                          ← local
  3. iss / aud correctos                      ← local
  4. ctx_id VIVO en Redis DB0                 ← el token muere si el contexto murió
  5. (si el átomo lo exige) trust/LoA ≥ mínimo del átomo
       │
REFRESCO
  bauth.token.refresh (saga S5, 5 pasos, ~10s) — emite token nuevo → nuevo eslabón de la cadena
       │
REVOCACIÓN (< 30 s objetivo de diseño)
  invalidar ctx_id/sesión en Redis → el paso 4 de validación rechaza el token
  aunque su firma y exp sigan siendo válidos → audit + evento CAEP session-revoked
```

**TTLs por defecto** (columna de `idn_tenant`, configurables por tenant y tier):
`token_ttl_seconds` = 3600 (1h) · `session_ttl_max` = 28800 (8h) · sesión elevada Step-Up =
300s (5 min, RFC 9470).

**El punto clave del diseño:** la revocación NO depende de la expiración. El paso 4 (ctx_id
vivo) convierte cada validación en una consulta de estado server-side — un token robado deja
de servir en el momento en que la sesión se invalida, sin listas negras de JWT ni esperas de
TTL.

## 8. Protocolos de token — Exchange, DPoP, Introspección

`token_protocols.rs` implementa los tres protocolos complementarios (verificados):

| Protocolo | Handler | Estado | Detalle |
|-----------|---------|:------:|---------|
| **Token Exchange** (RFC 8693) | T40 — `bauth.token.exchange` | ✅ | Un daemon intercambia el token del usuario por uno con su propia audiencia — delegación entre servicios sin re-autenticar |
| **DPoP** (RFC 9449) | T41 — `bauth.token.dpop` | ⚠️ parcial | Valida estructura JWT del proof; falta verificación de firma del proof + binding `jkt` + anti-replay `jti` (brecha P2 — MANUAL-METODOS §7.4) |
| **Introspección** (RFC 7662) | T42 — `bauth.token.introspect` | ✅ | `{active: true/false}` + metadatos — para PEPs que no verifican JWT localmente |

Más los endpoints del OIDC Provider (`oidc_provider.rs`): `/token` (client_credentials +
authorization_code), `/userinfo`, `/jwks`, `/introspect` — todos registrados en el discovery.

## 9. Por qué los permisos NO viajan en el token

La decisión más importante del diseño de tokens de bAuth, contra la práctica común de
empaquetar roles/permisos en el JWT:

| Criterio | Permisos EN el token (práctica común) | Permisos server-side (bAuth) |
|----------|----------------------------------------|------------------------------|
| Tamaño | Crece con los permisos (KBs con cientos de scopes) | Constante — 0 bytes de permisos |
| Cambio de permisos | Requiere esperar exp o re-login | Efecto inmediato — el RolBitMask en Redis se recalcula |
| Revocación de UN permiso | Imposible sin revocar el token entero | Quirúrgica — AND NOT sobre el bitmask (MANUAL-BITMASK §5) |
| Evaluación | Parsear claims + comparar strings | `rol_bitmask[posición]` — <0.5ns |
| Fuga de información | El token enumera todo lo que puedes hacer | El token no revela el mapa de permisos |
| Escala | 548 roles × ~6,000 átomos NO caben en un JWT | El bitmask vive en Redis, indexado por sub |

El token responde *"¿quién es y en qué contexto?"*; el FastPath responde *"¿puede hacer
esto?"*. Separar las dos preguntas es lo que permite tokens livianos, revocación real y
evaluación O(1) — el patrón que la industria llama **phantom token** (token liviano + estado
rico server-side), implementado aquí con Redis en lugar de introspección remota.

## 10. Estado del arte — formatos y prácticas de token 2026: lo que hay y lo que no hay

### 10.1 Lo que hay — inventario verificado

| Capacidad | Estado | Evidencia |
|-----------|:------:|-----------|
| JWT firmado EdDSA Ed25519, algoritmo único sin negociación | ✅ | `jwt_signer.rs` (ring, FIPS 186-5) |
| 38 claims en 8 grupos + GeoClaim/AuthStep | ✅ | `jwt_builder.rs` (47 campos pub) |
| ctx_id obligatorio en todo token (SBOS-049) | ✅ | claim no-opcional |
| Hash-chain forense con invariantes I-1/I-2 bajo mutex | ✅ | `token_issue.rs` |
| `kid` + JWKS para rotación de claves | ✅ | `SignedToken.kid` + `/jwks` |
| JWE dir+A256GCM para tokens sensibles | ✅ | `jwe_encrypt.rs` (RFC 7516) |
| Token Exchange RFC 8693 | ✅ | T40 |
| Introspección RFC 7662 | ✅ | T42 |
| Revocación efectiva vía ctx_id en Redis (sin listas negras) | ✅ diseño | pipeline de validación paso 4 |
| Trazabilidad W3C (traceparent/tracestate) en el token | ✅ | claims §3.6 |
| DPoP completo (firma del proof + jkt + anti-replay) | ⚠️ parcial | T41 — brecha P2 |
| Endpoint estándar de revocación (RFC 7009) | ❌ | MANUAL-AUTENTICACION §16 |
| Rotación de refresh con detección de reuso | ❌ | ídem — brecha P1 |
| Clave de producción en Vault activa (vs dev en memoria) | ⚠️ | modo dual — verificar despliegue |
| Firma híbrida post-cuántica (Ed25519 + ML-DSA) | ⚠️ catálogo | FIPS 204 en `crypto_algorithm` |

### 10.2 Lo que hace la industria en 2026

1. **RFC 8725 (JWT BCP) y su actualización:** la referencia obligada — **15 reglas** (12
   originales + 3 nuevas del draft `rfc8725bis` en curso, que incorpora ataques descubiertos
   desde 2020). Las reglas centrales: algoritmos explícitos (nunca confiar en el header `alg`),
   validar `iss`/`aud` siempre, `typ` explícito para evitar confusión de tipos de token,
   claves por emisor.
2. **PASETO como alternativa "a prueba de errores":** v4 (Ed25519 + XChaCha20 + BLAKE2b) y v3
   (NIST/FIPS: P-384 + AES-CTR-HMAC) eliminan la negociación de algoritmo por diseño — cada
   versión fija su criptografía. Su adopción sigue siendo ~1000× menor que JWT. **bAuth logra
   la misma garantía sin salir de JWT:** un solo algoritmo cableado en el firmador.
3. **Macaroons y Biscuit:** tokens con *caveats* (restricciones que cualquiera puede AÑADIR
   pero nadie quitar) y atenuación offline — delegación de terceros que ni JWT ni PASETO
   tienen. Nicho: sistemas distribuidos con delegación en cadena.
4. **El patrón phantom/opaque:** token opaco hacia afuera + JWT rico hacia adentro (Curity lo
   popularizó). Contra: superficie SSRF hacia el endpoint de introspección. bAuth usa la
   variante con estado en Redis — sin introspección remota en el camino caliente.
5. **Sender-constrained tokens como norma bancaria:** FAPI 2.0 exige mTLS o DPoP — el token
   robado no sirve sin la clave del cliente. Es el complemento del phantom token.

### 10.3 Comparativa — el token bAuth vs los formatos 2026

| Criterio | JWT bAuth | JWT típico | PASETO v4 | Opaque+introspección | Macaroons/Biscuit |
|----------|:---------:|:----------:|:---------:|:--------------------:|:-----------------:|
| Algoritmo no negociable | ✅ cableado | ❌ header `alg` | ✅ por versión | — | ✅ |
| Verificación local sin red | ✅ JWKS | ✅ | ✅ | ❌ introspección | ✅ |
| Revocación inmediata | ✅ ctx_id Redis | ❌ espera exp | ❌ | ✅ | ⚠️ |
| Cadena forense entre tokens | ✅ **único** | ❌ | ❌ | ❌ | ❌ |
| Contexto organizacional/red/geo en claims | ✅ 38 claims | ⚠️ | ⚠️ | — | ⚠️ |
| Permisos fuera del token | ✅ | ❌ scopes dentro | ❌ | ✅ | ⚠️ caveats |
| Confidencialidad de claims | ✅ JWE opcional | ⚠️ JWE raro | ✅ local cifrado | ✅ | ❌ |
| Atenuación offline (caveats) | ❌ | ❌ | ❌ | ❌ | ✅ único |
| Sender-constrained | ⚠️ mTLS ✅ · DPoP parcial | ⚠️ | ❌ | ⚠️ | ❌ |
| Ecosistema/adopción | ✅ JWT estándar | ✅ | ⚠️ ~1000× menor | ✅ | ⚠️ nicho |

**Lectura honesta:** bAuth toma lo mejor de tres mundos — la interoperabilidad de JWT, la
rigidez criptográfica de PASETO (algoritmo único) y la revocabilidad del patrón opaque (estado
en Redis) — y añade lo que ningún formato tiene: la hash-chain forense. Sus brechas son las
del ecosistema OAuth alrededor del token (DPoP completo, RFC 7009, rotación de refresh), no
del formato.

### 10.4 Brechas por prioridad

**P1 — Seguridad del ciclo de vida** (compartidas con MANUAL-AUTENTICACION §16.3 — no se
duplican aquí): rotación de refresh con detección de reuso · endpoint RFC 7009 ·
back-channel logout.

**P2 — Propias del artefacto token:**

| Brecha | Enfoque |
|--------|---------|
| DPoP completo (T41) | Verificar firma del proof con el `jwk` del header + binding `jkt` (claim `cnf`) + anti-replay por `jti` con ventana en Redis |
| Confirmar Vault PKI activo en producción | El firmador tiene modo dual dev/prod — verificar en VPS que la clave NO es la de memoria (evidencia AA-1) |
| `typ` explícito por clase de token | Header `typ: "at+jwt"` (RFC 9068) para access tokens — regla del rfc8725bis contra confusión de tipos |
| Verificador de cadena (`bauth.token.chain_verify`) | Handler que audita la integridad de la hash-chain de un período — hoy la cadena se escribe pero no hay verificador expuesto |

**P3 — Futuro:**

- Firma híbrida Ed25519 + ML-DSA-87 (FIPS 204) — deadline CNSA 2.0: 2030
- Access tokens perfil RFC 9068 (JWT Profile for OAuth 2.0 Access Tokens) para interoperabilidad con PEPs de terceros
- Evaluación de caveats estilo Biscuit para la delegación D10 (atenuar un token delegado sin re-emitir)

### 10.5 Cumplimiento — checklist RFC 8725 (JWT Best Current Practices)

| # | Regla BCP | Estado bAuth |
