## 1. Audiencia, propósito y alcance

Este manual documenta **AtomLang v2.0**: el lenguaje de dominio específico (DSL) para configurar
la autorización en bAuth. Define qué es el lenguaje, cómo se estructura, cómo se usa (constructor
visual), cómo se compila (atomc) y cómo los átomos resultantes fluyen hacia roles y usuarios
hasta la evaluación final por el BitMask.

**Audiencia:** administradores de autenticación (quienes construyen el árbol de autorización),
desarrolladores bAuth (quienes implementan atomc y el dashboard), arquitectos SBOS (quienes
gobiernan los dominios D95-D99), auditores de seguridad (quienes verifican trazabilidad normativa).

## 2. AtomLang como lenguaje de programación DSL

Así como C, Rust o Python son lenguajes de propósito general, AtomLang es un lenguaje de
**propósito específico**: expresar reglas de autorización empresarial. Tiene los mismos
elementos estructurales que cualquier lenguaje de programación:

| Elemento de lenguaje | En Rust | En AtomLang |
|---|---|---|
| Archivo fuente | `main.rs` | Snapshot `.atm.yaml` (export/import para git) |
| Módulo | `mod foo;` | `Dominio` (D00-D13 funcionales, D95-D99 del lenguaje) |
| Namespace | `mod foo { }` | `PolicySet` (zona, bloque) |
| Función | `fn bar() { }` | `Política` (aplicación, capa B7) |
| if/else + guard clause | `if x > 5 { return Ok }` | `Regla` (Target → Condition → Effect) |
| Declaración de constantes | `const MAX: u64 = 100;` | `@bauth_config_param.aprobacion_tier1` |
| Variables (parámetros) | `let x = ctx.risk_score;` | `@ctx.risk_score` (PIP, resuelto en runtime) |
| Tipos enumerados | `enum Color { R, G, B }` | `Verbo`, `Decision`, `Algoritmo`, `Operador` |
| Colecciones tipadas | `HashSet<T>` | `Conjunto: Set<Rol>` (D98) |
| Valor de retorno | `return Ok(valor);` | `Effect { decision: Permit | Deny }` |
| Efectos secundarios | `log::info!()` | `Obligation` (obligatorio), `Advice` (opcional) |
| Compilador | `rustc` | `atomc` (Lexer → Semantic → Codegen) |
| AST (intermedio) | MIR, HIR | Árbol AtomLang (structs Rust en memoria) |
| Bytecode / IR | LLVM IR | Árbol Compilado (.atm.json, solo IDs enteros) |
| VM / Runtime | CPU | PDP de bAuth (BitMask, <0.5ns) |

La diferencia fundamental con un formato de datos (YAML, JSON): un formato describe estructura.
Un lenguaje describe **comportamiento**. Las reglas de autorización son comportamiento — expresan
qué hacer cuando un sujeto intenta una operación sobre un recurso bajo ciertas circunstancias.

## 3. El modelo de tres árboles

AtomLang separa obligatoriamente tres representaciones del modelo de autorización, análogas a
las fases de un compilador: código fuente → AST → bytecode.

```
┌──────────────────────────┐      ┌──────────────────────────┐      ┌──────────────────────────────┐
│   ÁRBOL FUENTE           │      │   ÁRBOL ATOMLANG (AST)   │      │  ÁRBOL COMPILADO (IR)        │
│                          │      │                          │      │                              │
│ "El código fuente"       │      │ "El AST validado"        │      │ "El bytecode"                │
│                          │      │                          │      │                              │
│ ¿Quién? Admin (PAP)      │ ───→ │ atomc Fase 1+2           │ ───→ │ atomc Fase 3                 │
│ ¿Formato? atom_tree (DB) │      │ structs Rust en memoria  │      │ JSONB (.atm.json)            │
│ ¿Legible? SÍ             │      │ NO (máquina)             │      │ NO (máquina)                 │
│ ¿Ejecutable? NO          │      │ NO                       │      │ SÍ (por PDP)                 │
│ ¿Persiste? PostgreSQL    │      │ Solo memoria (efímero)   │      │ privilege_atom_compiled      │
│                          │      │                          │      │                              │
│ ANALOGÍA: main.rs → rustc MIR → binary .wasm               │                              │
└──────────────────────────┘      └──────────────────────────┘      └──────────────────────────────┘
```

### 3.1 Árbol Fuente

Donde el administrador **construye visualmente** el árbol de autorización. Se persiste en
`bauth.atom_tree` (PostgreSQL, una sola tabla con adjacency list). Se exporta a `.atm.yaml`
para git versioning.

### 3.2 Árbol AtomLang (AST)

Representación intermedia validada. Producida por `atomc` Fase 1 (Lexer: resuelve referencias
contra catálogos PostgreSQL) + Fase 2 (Semantic: verifica reglas G-01..G-10, normas D97,
contratos D96). Existe solo en memoria durante la compilación.

### 3.3 Árbol Compilado (IR)

Input **exclusivo** del PDP. Solo IDs enteros, enums, valores tipados. Cero strings comparables
por igualdad textual en runtime. Se persiste en `bauth.privilege_atom_compiled`.

**Invariante de seguridad:** el PDP lee exclusivamente este árbol. Leer el árbol fuente
directamente es equivalente a ejecutar código fuente sin compilar.

## 4. Catálogo de dominios — los módulos del lenguaje

### 4.1 Las DOS taxonomías de dominio (fuente: Manual 1.01 §2)

En bAuth coexisten dos conceptos distintos que comparten la palabra "dominio":

| | **Planos de control (D00-D13 + D99)** | **Dominios funcionales (20 códigos)** |
|---|---|---|
| Pregunta que responden | ¿QUÉ TIPO de control se aplica? | ¿De QUÉ SECTOR de negocio es el rol? |
| Dónde viven | `privilege_domain` (4 bits del AtomBitMask) | `idn_role_template.domains JSONB` (propuesta) |
| Se evalúan en runtime | ✅ — pipeline de 5 fases | ❌ — son clasificación/reporte |

**Regla mnemotécnica:** los planos dicen *cómo se controla*; los funcionales dicen *de qué
trabaja* el rol. Un ROL-CAJERO es del dominio funcional COMERCIAL/FINANZAS, y sus átomos
se evalúan en los planos D1 (login), D3 (límites), D4 (turno) y D2 (puerta).

### 4.2 Planos de control (D00-D13) — los módulos de evaluación del BitMask

Definidos en el Manual 1.01 §4. Cada plano es un evaluador con código Rust en `src/domain/`.
El pipeline de evaluación los ordena en 5 fases con cortocircuito:

| Plano | Nombre | Path | Estándar principal |
|:-----:|--------|------|--------------------|
| **D00** | Identidad Organizacional | Pre-condición (ctx_id) | ISO 24760-2:2025 |
| **D1** | Acceso Lógico | Fast-Path <0.5ns | NIST 800-63B-4 · RFC 9470 |
| **D2** | Acceso Físico | Fast-Path +OSDP | IEC 60839-11-5 · OSDP |
| **D3** | Financiero | Policy-Path | PCI DSS 4.0.1 · SOX §404 |
| **D4** | Temporal | Policy-Path (encadenado a D1) | GTRBAC · RFC 5545 |
| **D5** | Biométrico | External-Path | ISO/IEC 30107-3 |
| **D6** | Geoespacial | External-Path (encadenado a D1) | OGC GeoFence |
| **D7** | Red | External-Path (vía Kong) | SP 800-207 ZTA · IEEE 802.1X |
| **D8** | Contexto/Sesión | Pre-BitMask | SBOS-049 · W3C Trace Context |
| **D9** | Credenciales | Pre-BitMask | SP 800-63B AAL1-3 · FIDO2 |
| **D10** | Delegación | Policy-Path (reducción AND) | INCITS 359 DSD |
| **D11** | Auditoría | Post-hoc (registra, no decide) | ISO 27001 A.8.15 |
| **D12** | Blockchain/Anclaje | External-Path | NIST IR 8202 · W3C DID |
| **D13** | Firma Digital Externa | Diseño (átomos 5929-5964) | Ley 164 · ADSIB |

### 4.3 Dominios del lenguaje AtomLang (D95-D99)

Además de los planos de control, AtomLang define dominios propios que no participan
en la evaluación del BitMask pero son parte de la estructura del lenguaje:

| Dominio | Rol | ¿Quién lo puebla? |
|---|---|---|
| **D95** | Catálogo de Átomos — compilados y listos para asignar a roles | `atomc` (automático) |
| **D96** | Contrato de Métodos — entradas, salidas y flujos de los 18 métodos auth | Arquitecto de identidad |
| **D97** | Conformidad Normativa — requisitos ISO/NIST/XACML que cada nodo debe cumplir | Arquitecto de identidad |
| **D98** | Registro Estructural — constantes, conjuntos de roles, enums | Administrador (PAP) |
| **D99** | Administrativo Global — baseline que garantiza a todos los demás dominios | Arquitecto de seguridad (HITL) |

## 5. Estructuras del lenguaje — el sistema de tipos

### 5.1 Jerarquía de objetos

Cada tipo de nodo tiene una estructura **predeterminada e inmutable**. El administrador no
inventa estructuras — solo coloca objetos, los nombra y completa valores.

```
Dominio              ← MÓDULO. combining_algorithm + hijos (bloques, policies, policysets)
  │
  ├── PolicySet      ← NAMESPACE. combining_algorithm + target (opcional) + hijos
  │     │
  │     ├── Política ← FUNCIÓN. combining_algorithm + application_id + reglas
  │     │     │
  │     │     └── Regla ← IF/ELSE. Target + Condition + Effect
  │     │           │      (los tres YA incluidos — solo se completan valores)
  │     │           │
  │     │           ├── Target      ← subject (ROL|SET|ANY) + resource + verbo
  │     │           │                  + environment[] (opcional)
  │     │           ├── Condition   ← property_id + operator + value
  │     │           │                  (o null si no hay condición adicional)
  │     │           └── Effect      ← decision (Permit|Deny) + obligation + advice
  │     │
  │     └── Guardrail ← Regla standalone. application_id = null.
  │
  └── Bloque (B0-B20) ← Agrupador temático. Hijos: políticas, objetos, listas.
```

### 5.2 Vocabularios cerrados

| Enum | Valores | Fuente |
|---|---|---|
| **Verbo** | read, write, create, delete, approve, execute, export, delegate, configure, audit, login, emit, void | `bauth.privilege_verb` |
| **Decision** | Permit, Deny | XACML 3.0 §2.6 |
| **Algoritmo** | deny-overrides, permit-overrides, first-applicable, deny-unless-permit, permit-unless-deny, aggregate-strictest | XACML 3.0 §7.18 + ext. bAuth |
| **Operador** | ==, !=, >, <, >=, <=, IN, NOT_IN, BETWEEN | XACML 3.0 §A.7 |
| **SubjectKind** | ROL, SET, ANY | XACML 3.0 §5.5 + ANSI INCITS 359 |

### 5.3 La Regla

La Regla es el `if` del lenguaje. Una Regla = UNA Condition. No existen conectores lógicos
entre condiciones dentro de una misma Regla. Múltiples condiciones se modelan como átomos
separados combinados con `combining_algorithm` a nivel Política.

```
SI (Target matchea) Y (Condition es verdadera):
    retornar Effect.decision
    ejecutar Effect.obligation (el PEP DEBE)
SINO:
    NotApplicable
```

### 5.4 Delegación a bi18n — servicio especializado de formato, enmascaramiento y validación regional

Los verbos `validate`, `format` y `mask` definen QUÉ operación se aplica sobre un atributo,
pero **la lógica concreta de CÓMO formatear una fecha, enmascarar un documento o validar
un NIT no reside en AtomLang ni en el PDP**. Esa lógica la provee **bi18n** como servicio
especializado.

**Quién hace qué:**

| Componente | Rol en la ejecución de un verbo |
|---|---|
| **AtomLang (política)** | Declara QUÉ verbo se aplica, sobre QUÉ recurso, con QUÉ condiciones. Define la *autorización*. |
| **Motor de Identidad / PDP (bAuth)** | **Ejecuta** el verbo. Evalúa la política completa (target + condition + combining_algorithm), resuelve Permit/Deny, y ejecuta las obligations. Es el motor de ejecución real. |
| **bi18n (servicio)** | **Provee el CÓMO** — recibe una solicitud del Motor de Identidad y devuelve un resultado concreto. No decide Permit/Deny; solo transforma datos. |

**El patrón de delegación:** cuando una Regla AtomLang necesita una operación que depende de
reglas regionales (formato de fecha, máscara de CI, validación de NIT), la `obligation` declara
`validator: bi18n`. El Motor de Identidad, al ejecutar la obligation, invoca el método JSON-RPC
correspondiente de bi18n, recibe el resultado, y continúa la evaluación:

```
Política AtomLang        Motor de Identidad (PDP)         bi18n (servicio)
─────────────────        ─────────────────────────         ────────────────
                         Evalúa target + condition
                         Decide Permit/Deny
 obligation:               │
   validator: bi18n ──────→ llama bi18n.validate_national_id("bo","nit", valor)
   method: validate_nid    │                                    │
   args: {country: bo}     │                              aplica regex del TOML
                                                            verifica canonicalValues
                           ←───── {valid: true, formatted: "1234567-017"}
                         Continúa la evaluación
                         Retorna Permit/Deny al PEP
```

```yaml
regla "validar_nit_boliviano"
  target:
    resource: idn_identity_attribute.tributario
    type: NIT
    verbo: validate
  condition:
    property_id: idn_identity_attribute.value_text
    operator: REGEX
    value: "@bauth_config_param.regex_nit_bo"
  effect:
    decision: Permit
    obligation:
      validator: bi18n                       # ← el PDP delega el CÓMO a bi18n
      method: validate_national_id
      args: { country: "bo", kind: "nit" }

regla "enmascarar_ci"
  target:
    resource: idn_identity_attribute.id_nacional
    type: CI
    verbo: mask
  condition:
    property_id: idn_identity_attribute.classification
    operator: GTE
    value: "CONFIDENTIAL"
  effect:
    decision: Permit
    obligation:
      service: bi18n                         # ← el PDP delega el enmascaramiento a bi18n
      method: mask_value
      args: { format: "ID_BO", strategy: "partial(4)" }

regla "formatear_fecha_nacimiento"
  target:
    resource: idn_identity_attribute.birth_date
    verbo: format
  effect:
    decision: Permit
    obligation:
      service: bi18n                         # ← el PDP delega el formato a bi18n
      method: format_date
      args: { granularity: "Date", style: "Long" }
```

**Qué metadatos del atributo cubre esta delegación:**

| Verbo AtomLang | Quién lo ejecuta | Qué delega a bi18n | Metadatos involucrados |
|---|---|---|---|
| `validate` | Motor de Identidad (PDP) | `validate_national_id`, `validate_phone`, `validate_email`, `validate_enum`, `validate_pattern` | `pattern`, `canonicalValues`, `input_mask`, `type` |
| `verify` | Motor de Identidad (PDP) — fuentes externas | *No delega a bi18n* (SEGIP, SIN, APIs de verificación) | `ial`, `source`, `evidence_type`, `verification_method` |
| `format` | Motor de Identidad (PDP) | `format_value` — aplicación del patrón ICU4X o plano | `display_format` → `format_map` |
| `mask` | Motor de Identidad (PDP) | `mask_value` — aplicación de la estrategia de enmascaramiento | `mask`, `classification` |

**Sin bi18n, los metadatos `mask`, `display_format` y `pattern` serían texto inerte.**
El valor `"partial(4)"` en la columna `mask` es solo un string — hasta que el Motor de
Identidad, al ejecutar el verbo `mask`, invoca `bi18n.mask_value("7654321-LP", "ID_BO", "partial(4)")`
y bi18n lo resuelve a `MaskStrategy::Partial` y devuelve `"****321-LP"`. La cadena completa es:

```
Metadato en DB → Política AtomLang → PDP ejecuta verbo → obligation → bi18n transforma → valor final
     ↑                                                                                       ↑
  declaración                                                                          comportamiento
```

**bi18n no ejecuta verbos ni decide Permit/Deny.** Es un servicio puro: recibe datos,
aplica reglas regionales, devuelve resultados. El Motor de Identidad es quien orquesta
la ejecución completa de cada verbo, invocando a bi18n cuando necesita formato,
enmascaramiento o validación regional.

Referencia completa en [i18n-orchestrator §12](i18n-orchestrator-rust.md) y [Manual 1.07 §4.0.1](1.07_MANUAL-ATRIBUTOS-v2.0.md).

## 6. El constructor visual — cómo se usa AtomLang

AtomLang **no se escribe como código libre**. El administrador trabaja con un **constructor
visual de objetos predefinidos**: agarra objetos de una paleta, los suelta en el árbol,
los nombra y completa valores desde desplegables conectados a los catálogos en PostgreSQL.

### 6.1 Principio: todo tiene estructura definida, nada se inventa

| Objeto | Estructura fija | Lo que el usuario hace |
|---|---|---|
| Dominio | combining_algorithm + hijos | Nombrarlo. Elegir algoritmo. Soltar hijos dentro. |
| PolicySet | combining_algorithm + target + hijos | Nombrarlo. Elegir algoritmo. Soltar hijos dentro. |
| Política | combining_algorithm + application_id + reglas | Nombrarlo. Elegir algoritmo. Soltar reglas dentro. |
| Regla | target + condition + effect (ya incluidos) | Nombrarla. Completar valores del target, condition y effect. |
| Target | subject + resource + verbo + environment[] | Seleccionar de desplegables (catálogos DB). |
| Condition | property_id + operator + value | Seleccionar propiedad, operador. Ingresar valor o @constante. |
| Effect | decision + obligation + advice | Seleccionar Permit/Deny. Agregar obligation opcional. |

### 6.2 La UI impide errores estructurales

A diferencia de un editor de código, el constructor visual **impide físicamente** los errores:

- No se puede soltar una Regla directamente en un Dominio (la zona de drop no se habilita)
- El campo `verbo` es un desplegable cargado desde `bauth.privilege_verb` — no hay texto libre
- El campo `value` para propiedades AMOUNT solo muestra @constantes, no permite literales
- El campo `decision` solo ofrece `Permit` y `Deny` — no hay tercer valor posible
- `subject.set_id` solo muestra conjuntos declarados en D98 — si no existe, no aparece

### 6.3 Validación post-construcción

La máquina de estados (`atomc validate`) corre **después** de construir el árbol. Verifica:
catálogos (G-05, G-06), algoritmos (G-01), valores (G-08, G-09), duplicados (G-04),
normas D97 y contratos D96. Si pasa → átomos aparecen en D95. Si falla → lista de correcciones.

El detalle completo del constructor visual está en [A.49](anexos/A.49_ANEXO-EDITOR-VISUAL-ATOMLANG-v1.0.md).

## 7. El modelo simplificado: árbol → átomo → rol → usuario → BitMask

Mientras Cedar, OPA y XACML separan el motor de políticas de la asignación a usuarios en dos
sistemas que se integran, **bAuth los unifica en un pipeline lineal de 5 pasos**:

```
PASO 1 — DEFINIR (arquitecto de seguridad, una vez)
  Construye el árbol maestro en el dashboard. Políticas + reglas fabrican átomos.

PASO 2 — COMPILAR (atomc, automático)
  atomc validate → compile. Átomos válidos → D95. Átomos corruptos → desaparecen.

PASO 3 — ASIGNAR átomos a roles (arquitecto de identidad)
  En D98 se definen roles y conjuntos. Átomos de D95 se asignan a roles
  mediante privilege_role_atom. compute_rol_bitmask() precalcula el RolBitMask.

PASO 4 — INSCRIBIR usuarios a roles (admin / RRHH)
  Usuario se inscribe a un rol. Hereda TODOS los átomos del rol automáticamente.
  Solo se define: identidad (nombre, email, tenant, sucursal) + rol base.
  Opcional: átomos extra o bloqueados (privilege_user_atom).

PASO 5 — EVALUAR (PDP, runtime)
  UserBitMask[posición_del_átomo] == 1 → Permit. <0.5ns.
  Sin combining algorithms en runtime. Sin evaluación anidada.
```

El detalle completo del modelo simplificado y la comparativa con la industria está en
[A.50](anexos/A.50_ANEXO-MODELO-SIMPLIFICADO-ROLES-USUARIOS-v1.0.md).

## 8. El compilador atomc

`atomc` es el compilador AtomLang: un binario Rust 1.85+ MUSL en `BauthAgent/tools/atomc/`.

### 8.1 Pipeline de 3 fases

```
FASE 1 — LEXER: resuelve referencias contra catálogos PostgreSQL
  • verb_id → bauth.privilege_verb
  • subject.set_id → D98 conjuntos
  • resource → bauth.privilege_resource
  • property_id → bauth.privilege_attribute
  → ATOMC-E-014 si el valor no existe en catálogo

FASE 2 — SEMANTIC: valida reglas G-01..G-10, D97 (normas), D96 (contratos)
  → ATOMC-E-031 si falta combining_algorithm
  → ATOMC-E-042 si literal numérico en AMOUNT
  → ATOMC-E-021 si atributo duplicado Target/Condition

FASE 3 — EMITTER: genera IR (AtomLang.CompiledTree.v1.json)
  • Solo IDs enteros, enums, valores tipados
  • CERO strings en runtime
  • Publica en privilege_atom_compiled
  • Actualiza D95 (átomos ACTIVOS / CORROMPIDOS)
```

### 8.2 Comandos

```bash
atomc validate   # lint + resolución catálogos
atomc compile    # validate + emisión IR
atomc publish    # activación para PDP (WORM)
atomc fmt        # formateador canónico
```

La arquitectura completa y el catálogo de errores ATOMC están en [A.46](anexos/A.46_ANEXO-ATOMLANG-GRAMATICA-COMPILADOR-v2.0.md).

## 9. Estado del arte — comparativa con la industria

### 9.1 Lo que la industria ya resolvió (y no reinventamos)

| Solución | De quién | Qué adoptamos |
|---|---|---|
| Editor visual multi-modo | Cedar Observer UI (Lucid Computing) | Patrón de paleta + drop + panel de propiedades |
| Language Server Protocol | OPA/Rego (CNCF) | atomc como LSP para integración con editores |
| Playground online | OPA Rego Playground | atomc playground (WASM) |
| Linter standalone | Regal (Styra) | atomc lint |
| Formateador canónico | opa fmt, gofmt | atomc fmt |

### 9.2 Comparativa con otros lenguajes de autorización

| | Cedar (AWS) | OPA/Rego | XACML 3.0 | **bAuth / AtomLang** |
|---|---|---|---|---|
| **Curva de aprendizaje** | Sintaxis Cedar | Datalog | XML verboso | **Constructor visual. Sin sintaxis que aprender.** |
| **Evaluación** | Compiled → IR → engine | Interpretado | PDP con combining anidados | **BitMask: array de bits. <0.5ns.** |
| **Conflictos runtime** | forbid overrides permit | Prioridad | 6 combining algorithms | **Sin conflictos. La fábrica ya resolvió todo.** |
| **Asignación usuarios** | Identity source externo | input.user en Rego | PIP externo | **Inscripción directa: identidad + rol base. Herencia automática.** |
| **Verificación** | SMT solver (Z3) | opa test | Sin verificación formal | D97 normativa. atomc validate. |
| **Roles y grupos** | Group("...") | input.user.groups | Subject Category | **D98: conjuntos nativos. SET(vendedores). Sin sintaxis.** |

### 9.3 Por qué bAuth es más simple

Cedar, OPA y XACML separan el motor de políticas de la asignación a usuarios. Son dos
sistemas que se integran. En bAuth **es un solo sistema**: el árbol fabrica átomos, los
átomos se asignan a roles, los usuarios heredan de roles, el BitMask evalúa en nanosegundos.
Cuatro pasos lineales. Sin integraciones. Sin motores externos. Sin PIP obligatorio.
