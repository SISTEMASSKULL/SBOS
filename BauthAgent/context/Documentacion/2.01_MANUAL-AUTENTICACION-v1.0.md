## 2. Principio de soberanía

bAuth valida credenciales, evalúa políticas y emite JWT **sin depender de motores externos** en el flujo de autenticación. Cada método de autenticación está implementado nativamente en Rust.

```
Autenticación soberana:
  CREDENCIALES → bAuth (Rust nativo) → JWT firmado Ed25519

Sin intermediarios en el path crítico.
```

**¿Por qué?** Los motores externos añaden latencia de red, puntos de fallo y dependencias de versión. bAuth implementa los estándares directamente sobre las bibliotecas criptográficas del ecosistema Rust (`ring`, `webauthn-rs`, `rustls`) — las mismas que se usan en producción en sistemas como Firefox y Android.

**Motores de infraestructura que sí usa bAuth:**

| Motor | Para qué | Por qué es necesario |
|-------|----------|----------------------|
| **Vault** | Firma Ed25519 del JWT + PKI X.509 | HSM de claves — las claves privadas nunca salen de Vault |
| **PostgreSQL 18** | `bauth_db` — fuente de verdad de todo el estado | Framework declarativo, usuarios, sesiones, audit_events |
| **Redis** | Cache de BitMask + sesiones ctx_id (TTL 30s) | FastPath <0.5 ns — sin consultar BD en cada request |
| **Besu/QBFT** | Anclaje blockchain D12 | Inmutabilidad de eventos críticos de autenticación |

### 3.2 El trait `AuthMethod` — contrato de todos los métodos

Todo método de autenticación implementa el mismo trait (`src/domain/auth_methods/mod.rs`):

```rust
pub trait AuthMethod: Send + Sync {
    fn method_id(&self) -> &str;       // Ej: "BAUTH_TOTP"
    fn method_name(&self) -> &str;     // Nombre descriptivo en español
    fn aal_level(&self) -> u8;         // 1, 2 ó 3 (NIST 800-63B-4)
    fn standard_ref(&self) -> &str;    // Ej: "RFC 6238 / NIST SP 800-63B Rev.4 §3.1.4"

    async fn validate(&self, input: &Value) -> Result<ValidateResult, AuthMethodError>;
    async fn enroll(&self, user_uuid: &str, params: &Value) -> Result<EnrollResult, AuthMethodError>;
    async fn revoke(&self, user_uuid: &str, instance_id: &str) -> Result<(), AuthMethodError>;
    async fn health_check(&self) -> bool;
}
```

**`ValidateResult`** retorna: `valid: bool` · `method_id` · `message` · `aal_satisfied: u8`

### 3.3 El `MethodRegistry` — registro central en runtime

El daemon bAuth registra todos los métodos al arrancar. Si un método falla su `health_check()`, se marca degradado pero el sistema sigue operando con los demás.

```rust
pub struct MethodRegistry {
    methods: HashMap<String, Arc<dyn AuthMethod>>,
}
```

Restricción: registrar el mismo `method_id` dos veces retorna error. El ID es inmutable.

> **Este ES el motor de autenticación unificado — patrón PAM.** El `MethodRegistry` + el trait
> `AuthMethod` implementan el patrón **PAM (Pluggable Authentication Module)**, estándar de facto
> Unix/Linux (Red Hat, FreeBSD, Oracle): una **API única** donde cada método se registra y se
> invoca sin que el llamador conozca su mecanismo interno. El llamador pide un `method_id` y el
> registro colecta lo necesario y ejecuta — no hay lógica de método dispersa en los handlers. No se
> reinventa: **se completa**. Hoy cubre **9 de los 18** métodos del catálogo (§4); los 9 restantes
> (passkey, X.509-smartcard, Kerberos, social-brokering, CIBA, device-auth, conditional-OTP,
> client-credentials, token-exchange) se registran bajo el mismo trait — es el contrato **CORE-12**
> (A.43). La criptografía que estos métodos consumen se centraliza aparte, en el Módulo
> Criptográfico (§13.3) — el motor decide *qué* método corre; el módulo cripto ejecuta *el cifrado*.

### 4.2 Contraseña + Argon2id (`BAUTH_PASSWORD`)

**Módulo:** `src/domain/credential.rs` + `src/domain/password/` (módulo-directorio real; corrección 2026-07-10 — no existe `password_policy.rs`)

**¿Cómo valida bAuth?**
1. Recibe `{username, password}` — el password viaja por TLS, nunca en claro en logs
2. Recupera el hash Argon2id almacenado en `bauth.idn_credential`
3. Ejecuta `argon2id.verify(password, stored_hash)` — tiempo constante
4. Si válido: retorna `aal_satisfied = 1`

**Parámetros Argon2id por tier:**

| Tier | t (iteraciones) | m (memoria) | p (paralelismo) | Justificación |
|------|----------------|-------------|-----------------|---------------|
| `SU` / `SYS` | 5 | 128 MB | 2 | OWASP recomendación máxima 2026 |
| `BIZ_N1`–`N5` | 3 | 64 MB | 1 | Balance seguridad/rendimiento |
| `EXT_N0` | 2 | 32 MB | 1 | Volumen alto — usuarios externos |

**Política de contraseñas (NIST SP 800-63B-4):**

| Regla | Valor | Norma |
|-------|-------|-------|
| Longitud mínima `SU` | 20 caracteres | NIST 800-63B-4 §3.1.1.1 |
| Longitud mínima `BIZ` | 12 caracteres | NIST 800-63B-4 §3.1.1.1 |
| Longitud mínima `EXT` | 8 caracteres | NIST 800-63B-4 §3.1.1.1 |
| Longitud máxima | 128 caracteres (se trunca antes de hashear) | Prevención de DoS |
| Rotación periódica forzada | **PROHIBIDA** — solo al detectar compromiso | NIST 800-63B-4 §3.1.1.2 |
| Contraseñas comunes | Screened contra lista HIBP (Have I Been Pwned) | NIST 800-63B-4 §3.1.1.3 |
| Unicode | Permitido — normalización NFC antes de hashear | NIST 800-63B-4 §3.1.1.4 |

### 4.3 TOTP — Time-based One-Time Password (`BAUTH_TOTP`)

**Módulo:** `src/domain/auth_methods/totp.rs`  
**Estándar:** RFC 6238 · NIST SP 800-63B-4 §3.1.4 · AAL2

**Cómo funciona la implementación:**

```
Secreto (base32) + tiempo Unix
        │
        ▼
T = floor(unix_time / período)        [período default: 30s]
        │
        ▼
HMAC(secreto, T.to_be_bytes())        [algoritmo: SHA1/SHA256/SHA512]
        │
        ▼
Dynamic Truncation (RFC 4226 §5.3):
  offset = last_nibble(HMAC)
  p = HMAC[offset..offset+4] & 0x7FFFFFFF
  OTP = p % 10^digits                 [digits default: 6]
        │
        ▼
Comparación en tiempo constante con código presentado
```

**Parámetros del validador:**

| Parámetro | Default | Configurable | Norma |
|-----------|---------|-------------|-------|
| `period` | 30 segundos | Sí | RFC 6238 §4 |
| `digits` | 6 | 6, 7 u 8 | RFC 6238 §5.3 |
| `hash_algo` | SHA1 | SHA1, SHA256, SHA512 | RFC 6238 §3 |
| `window_back` | 1 paso (±30s atrás) | Sí | RFC 6238 §5.2 — tolerancia de reloj |
| `window_forward` | 1 paso (±30s adelante) | Sí | RFC 6238 §5.2 |

**Protección anti-replay:** el mismo código TOTP no puede usarse dos veces dentro del mismo período. bAuth registra el último código validado por instancia en Redis.

**Enrolamiento:** bAuth genera un secreto de 20 bytes aleatorios, lo codifica en base32 y retorna el URI `otpauth://totp/...` para QR. El secreto se almacena cifrado con AES-256-GCM en `bauth.idn_credential`.

**Vectores de prueba oficiales (RFC 6238 Appendix B, verificados en tests):**

| Tiempo Unix | SHA1 (8 dígitos) | SHA256 (8 dígitos) |
|-------------|------------------|--------------------|
| 59 | 94287082 | 46119246 |
| 1111111109 | 07081804 | 68084774 |
| 1234567890 | 89005924 | 91819424 |

### 4.4 HOTP — HMAC-based One-Time Password (`BAUTH_HOTP`)

**Módulo:** `src/domain/auth_methods/hotp.rs`  
**Estándar:** RFC 4226 · AAL2

Mismo algoritmo que TOTP pero con **contador en lugar de tiempo**. El contador se incrementa con cada validación exitosa. El servidor mantiene el contador actual por instancia de método en `bauth.idn_credential`.

**Ventana de re-sincronización:** hasta 10 códigos adelantados (HOTP acepta que el usuario haya generado sin validar).

**¿Cuándo usar HOTP vs TOTP?** HOTP para dispositivos sin reloj sincronizado (tokens hardware físicos). TOTP para aplicaciones de smartphone.

### 4.5 WebAuthn / Passkey / FIDO2 (`BAUTH_WEBAUTHN`)

**Módulo:** `src/domain/auth_methods/webauthn.rs`  
**Estándar:** W3C WebAuthn Level 3 · FIDO2 · AAL2 (Passkey sinc) / AAL3 (hardware)

**Comentario en el código (línea 9):**
> `"Keycloak: COMPLETAMENTE ELIMINADO del path de autenticación."`

bAuth implementa el Relying Party completo en Rust con `ring`:

**Flujo de registro (enrolamiento):**

```
1. bAuth genera challenge (32 bytes aleatorios, SecureRandom)
2. bAuth retorna PublicKeyCredentialCreationOptions:
   - rp: {name: "SBOS bAuth", id: rp_id}
   - user: {id, name, displayName}
   - pubKeyCredParams: [{alg: -7 (ES256)}, {alg: -8 (EdDSA)}]
   - authenticatorSelection: {userVerification: "preferred", residentKey: "preferred"}
   - attestation: "none"
3. Navegador/app llama navigator.credentials.create()
4. bAuth verifica respuesta: signature, clientDataJSON, authenticatorData
5. bAuth almacena public_key_der en bauth.idn_credential
```

**Flujo de autenticación:**

```
1. bAuth genera challenge (32 bytes aleatorios)
2. bAuth retorna PublicKeyCredentialRequestOptions
3. Navegador llama navigator.credentials.get()
4. bAuth verifica assertion: ECDSA P-256 o EdDSA
5. Si válida: aal_satisfied = 2 (Passkey) ó 3 (hardware token)
```

**Algoritmos soportados:**

| Código COSE | Algoritmo | FIPS | AAL |
|-------------|-----------|------|-----|
| -7 | ES256 (ECDSA P-256) | FIPS 186-5 | AAL2-3 |
| -8 | EdDSA (Ed25519) | FIPS 186-5 | AAL2-3 |

### 4.6 SAML 2.0 (`BAUTH_SAML`)

**Módulos:** `src/domain/auth_methods/saml.rs` + `src/domain/auth_methods/saml_signature.rs`  
**Estándar:** SAML 2.0 Web Browser SSO Profile · XML-DSig (RFC 3275) · AAL1-2

bAuth valida Assertions SAML 2.0 firmadas con:
- `RSA-SHA256` (`http://www.w3.org/2001/04/xmldsig-more#rsa-sha256`)
- `ECDSA-SHA256` (`http://www.w3.org/2001/04/xmldsig-more#ecdsa-sha256`)

**¿Para qué se usa?** Integración con IdPs corporativos externos (Active Directory Federation Services, otros sistemas SAML existentes del cliente). bAuth actúa como Service Provider.

**Validaciones que ejecuta bAuth:**
1. Firma XML-DSig válida contra certificado del IdP registrado
2. `Conditions.NotBefore` y `NotOnOrAfter` dentro de ventana temporal (±5 min)
3. `AudienceRestriction` apunta a bAuth como SP
4. `NameID` presente y no vacío

### 4.7 mTLS X.509 (`BAUTH_MTLS`)

**Módulo:** `src/domain/auth_methods/mtls.rs`  
**Estándar:** RFC 8705 (OAuth 2.0 Mutual-TLS) · X.509 · AAL3

La validación TLS completa la realiza la capa de transporte (`rustls`). bAuth valida los **metadatos del certificado**:

- `Common Name (CN)` — identidad del cliente
- `Fingerprint SHA-256` — integridad del certificado (comparación en tiempo constante)
- `Not After` — no expirado

**¿Cuándo se usa mTLS?**
- Daemons SBOS comunicándose entre sí (`M2M` tier)
- Usuarios `SU` / `SYS` con acceso de muy alto riesgo (AAL3)
- Certificados ADSIB (firma digital con validez jurídica — Ley 164 Bolivia)

**Verificación de fingerprint en tiempo constante:**

```rust
let mut result: u8 = 0;
for (a, b) in fingerprint_sha256.as_bytes().iter()
                .zip(expected_fingerprint.as_bytes().iter()) {
    result |= a ^ y;
}
// result == 0 → coinciden exactamente
```

### 4.8 Email OTP (`BAUTH_EMAIL_OTP`)

**Módulo:** `src/domain/auth_methods/email_otp.rs`  
**Estándar:** NIST SP 800-63B-4 §3.1.4 · AAL1 (`restricted`)

**¿Qué significa `restricted`?** NIST 800-63B-4 degradó Email OTP a método restringido. bAuth lo implementa con las siguientes restricciones de política:
- Solo disponible para tier `EXT_N0` (usuarios externos) — no para `BIZ` ni superiores
- TTL del código: 10 minutos máximo
- Un solo uso: el código se invalida al verificarse
- Rate limiting: máximo 5 solicitudes por hora por usuario

**¿Por qué sigue implementado si es `restricted`?** Para compatibilidad con usuarios externos (clientes, proveedores) que no tienen app de autenticación. La norma lo permite con restricciones explícitas.

### 4.9 Push Challenge Ed25519 (`BAUTH_PUSH`)

**Módulo:** `src/domain/auth_methods/push.rs`

bAuth genera un challenge de 32 bytes aleatorios, lo envía al dispositivo registrado del usuario (vía `bnotify`), y el dispositivo firma el challenge con su clave Ed25519 privada. bAuth verifica la firma con la clave pública almacenada.

```
bAuth genera challenge (32 bytes, CSPRNG)
        │
        ▼
bNotify entrega challenge al dispositivo (push notification)
        │
        ▼
Dispositivo firma: Ed25519.sign(private_key, challenge)
        │
        ▼
bAuth verifica: Ed25519.verify(public_key, challenge, signature)
        │
        ▼
aal_satisfied = 2
```

TTL del challenge: 120 segundos. Expirado → `AuthMethodError::Expired`.

---

### 4.10 Recovery Codes (`BAUTH_RECOVERY`)

**Módulo:** `src/domain/auth_methods/recovery.rs`  
**Estándar:** NIST SP 800-63B-4 §3.1.2 — Look-Up Secrets · AAL1

Códigos de recuperación generados una sola vez en el enrolamiento. Se almacenan como hashes SHA-256 (no en claro). Cada código se usa exactamente una vez — validación y eliminación en la misma transacción.

**Generación:** bAuth genera 10 códigos de 12 caracteres alfanuméricos aleatorios (Base32 sin caracteres ambiguos: 0,O,I,l eliminados). El usuario los imprime o guarda fuera de línea.

**¿Cuándo se usan?** Cuando el usuario pierde acceso a todos sus factores MFA. Es el último recurso antes de la recuperación asistida por administrador.

## 5. Pipeline completo de autenticación

### 5.1 Flujo desde credenciales hasta JWT firmado

### 5.2 Paso 1 — Validación de credenciales

El daemon busca el método en `MethodRegistry`, invoca `validate(input)`, obtiene `ValidateResult`. Si `valid = false`, incrementa el contador de intentos fallidos y evalúa si aplica lockout.

### 5.3 Paso 2 — Políticas de autenticación

Antes de emitir token, bAuth consulta `bauth.auth_policy` en BD:
- `rate_limit` — ¿supera el límite de requests/s para este tier?
- `lockout` — ¿supera intentos fallidos consecutivos?
- `mfa.required` — ¿el LoA presentado es suficiente para el rol solicitado?

### 5.4 Paso 3 — Evaluación de acceso (PolicyEngine)

Consulta `ath_policy_dN` via PolicyEngine XACML 3.0. Verifica que el usuario tiene acceso al recurso solicitado en el dominio correspondiente. Si el resultado es `Denegado`: no emite token aunque las credenciales sean válidas.

### 5.5 Paso 4 — Construcción de JWT (JwtBuilder)

`JwtBuilder` (`src/domain/jwt_builder.rs`) ensambla la estructura `BauthClaims` con todos los campos definidos. Ver §6 para el detalle completo de claims.

**Decisión de diseño crítica (comentario en código):**
> `"RolBitMask y AtomBitMask NO se incluyen en el token. El token es solo identidad.`  
> `La evaluación de permisos es server-side vía bauth.access.evaluate(atom_slug, ctx_id)`  
> `→ Redis (30s TTL) → FastPath <0.5ns. Patrón: PDP/PEP (XACML/NIST 800-207).`  
> `El token es la llave, no la carga."`

Esto es intencional: el JWT no contiene permisos — contiene identidad. Los permisos se evalúan server-side en cada request usando el `ctx_id` como llave de caché en Redis.

### 5.6 Paso 5 — Firma Ed25519 (JwtSigner)

`JwtSigner` (`src/domain/jwt_signer.rs`) firma el JWT con Ed25519 usando la clave privada almacenada en Vault (FIPS 186-5). La clave privada **nunca sale de Vault** — bAuth envía el payload a Vault y recibe la firma.

**Hash-chain forense (ISO 27001 A.8.15):**

Cada JWT emitido contiene:
- `prev_hash` — SHA-256 del token anterior emitido en esta sesión
- `token_seq` — número de secuencia monotónico

Esto forma una cadena de custodia: si alguien intenta insertar un token en la secuencia, la cadena se rompe y es detectable en auditoría.

### 5.7 Paso 6 — Auditoría WORM

Cada autenticación genera un `audit_event` inmutable en `bauth.audit_event`:

```sql
INSERT INTO bauth.audit_event (
    actor_id, atom_slug, verb_code, domain_code,
    ctx_id, device_category, trust_level, access_result,
    auth_method_used, loa_achieved, timestamp
) VALUES (...);
```

El campo `access_result` registra `PERMITIDO` o `DENEGADO` con razón. Los audit_events son **append-only** — ningún proceso puede modificar o eliminar registros de auditoría.

```
Intentos fallidos 1–4  → sin bloqueo

```

Rate limiting por tier: `SU` = sin límite de tasa (pero con lockout). `EXT_N0` = 10 requests/segundo.

## 9. Sagas — 12 flujos orquestados

### 9.1 ¿Qué es una saga de autenticación?

Una saga es un flujo de autenticación con **pasos secuenciales y compensaciones inversas**. Si algún paso falla, la compensación revierte todos los pasos anteriores — garantizando consistencia sin transacciones distribuidas.

**Invocación:** `bauth.saga.execute` (JSON-RPC 2.0, `src/server/handlers/saga_execute.rs`)

### 9.2 Catálogo completo

| # | Saga | Pasos | Timeout | Compensación | Cuándo se usa |
|---|------|-------|---------|-------------|---------------|
| S1 | `auth.password.login` | 6 | 45 s | full_rollback | Login básico con contraseña |
| S2 | `auth.mfa.totp` | 4 | 30 s | full_rollback | Segundo factor TOTP |
| S3 | `auth.mfa.webauthn` | 7 | 60 s | full_rollback | Segundo factor WebAuthn/Passkey |
| S4 | `auth.step_up` | 7 | 120 s | full_rollback | Elevación de LoA para operación crítica |
| S5 | `auth.token.refresh` | 5 | 10 s | full_rollback | Renovación de access token con refresh token |
| S6 | `auth.federated.oidc` | 7 | 60 s | checkpoint | Login via IdP externo OIDC |
| S7 | `auth.emergency.break_glass` | 7 | 4 h | manual (HITL) | Acceso de emergencia — requiere aprobación humana |
| S8 | `auth.offline.login` | 6 | 30 s | best_effort | Login sin conexión — solo passkeys device-bound |
| S9 | `auth.password.reset` | 8 | 15 min | full_rollback | Restablecimiento de contraseña perdida |
| S10 | `auth.mfa.enroll` | 6 | 5 min | full_rollback | Enrolamiento de nuevo método MFA |
| S11 | `auth.session.validate` | 5 | 2 s | best_effort | Validación silenciosa de sesión activa |
| S12 | `auth.account.lockout` | 6 | 5 s | checkpoint | Bloqueo de cuenta por intentos fallidos |

### 9.3 Detalle de S1 — `auth.password.login`

El flujo más común en el sistema (Login básico):

```
Paso 1: Resolver usuario (username → UUID en idn_user_template)
Paso 2: Verificar estado del usuario (status = 'ACTIVE', no suspendido)
Paso 3: Validar contraseña (Argon2id verify — tiempo constante ~100ms)
Paso 4: Aplicar políticas (rate_limit, lockout_check, sesiones concurrentes)
Paso 5: Evaluar acceso PolicyEngine (rol del usuario en dominio D1)
Paso 6: Emitir JWT (JwtBuilder + JwtSigner Ed25519)

Compensación (full_rollback):
  Si paso 3 falla → incrementar contador lockout → limpiar contexto
  Si paso 5 falla → log audit DENEGADO → limpiar JWT parcial
  Si paso 6 falla → no emitir nada → marcar jti como inválido
```

### 9.4 Detalle de S4 — `auth.step_up`

Elevación temporal de LoA para operaciones de alto riesgo (RFC 9470):

```
Paso 1: Verificar que el usuario tiene sesión activa válida (ctx_id en Redis)
Paso 2: Determinar LoA requerido para la operación solicitada
Paso 3: Verificar que el LoA actual es insuficiente (de lo contrario, no hay step-up)
Paso 4: Emitir challenge de step-up al usuario
Paso 5: Validar el factor adicional presentado
Paso 6: Emitir JWT elevado (loa incrementado, TTL corto: 5 min)
Paso 7: Registrar audit_event con acr previo y acr nuevo

Compensación: full_rollback — el JWT elevado nunca se emite si cualquier paso falla
Timeout: 120 s — el usuario tiene 2 minutos para completar el step-up
```

### 9.5 Detalle de S7 — `auth.emergency.break_glass`

Acceso de emergencia — supervisión humana obligatoria (HITL):

```
Paso 1: El operador solicita break_glass con justificación documentada
Paso 2: bAuth verifica identidad del operador (AAL3 mínimo: mTLS o WebAuthn hardware)
Paso 3: bAuth abre ticket de emergencia en bos_sync_log
Paso 4: bAuth envía alerta a todos los SU via bNotify (inmediato)
Paso 5: Un segundo SU aprueba el acceso (dual control — NIST AC-5)
Paso 6: bAuth emite JWT de break_glass (TTL: 4 h, scope: break_glass_only)
Paso 7: Al expirar: bAuth genera reporte de auditoría del período de emergencia

Compensación: manual (HITL) — requiere revisión humana del incidente
Timeout: 4 horas — el JWT de emergencia expira solo
```

## 10. Step-Up Authentication (RFC 9470)

### 10.1 ¿Qué es?

Una sesión activa tiene un `loa` (Level of Assurance) alcanzado en el login inicial. Cuando el usuario intenta una operación que requiere mayor LoA, bAuth no requiere re-login completo — emite un **challenge de step-up** y el usuario presenta solo el factor adicional necesario.

### 10.2 Flujo

```
Usuario con loa=1 (solo contraseña)
        │
        │ intenta operación que requiere loa=2
        ▼
bAuth detecta: loa_requerido (2) > loa_actual (1)
        │
        ▼
bAuth retorna: HTTP 401 + header:
  WWW-Authenticate: Bearer error="insufficient_user_authentication",
    acr_values="2", max_age=120
        │
        ▼
Cliente presenta segundo factor (TOTP, WebAuthn, etc.)
        │
        ▼
bAuth valida segundo factor → emite JWT con loa=2, TTL=5min
        │
        ▼
Cliente reintenta la operación con JWT elevado
```

### 10.3 Configuración en el rol

El campo `step_up_enabled` en `idn_role_template` controla si un rol puede recibir challenges de step-up. El campo `loa_required` define el nivel mínimo que se exige para ese rol.

**Norma:** RFC 9470 — OAuth 2.0 Step-Up Authentication Challenge Protocol  
**Implementación:** `src/domain/delegation.rs`

| Implicit Grant | RFC 6749 §4.2 | **deshabilitado permanente** | Proscrito por OAuth 2.1 |

### 12.2 PKCE — obligatorio para clientes públicos

bAuth exige PKCE (`code_challenge_method=S256`) para todos los clientes que no pueden mantener un secreto en secreto (apps móviles, SPAs). Esto previene ataques de intercepción del authorization code.

### 12.3 Token Exchange (RFC 8693) — delegación controlada

Permite que un servicio SBOS intercambie su token por un token con mayor o menor alcance para actuar en nombre del usuario ante otro servicio. Requiere aprobación explícita (`enabled_controlled`) — no disponible por defecto.

## 13. Criptografía — algoritmos y FIPS

### 13.1 Los 12 algoritmos del catálogo

| Categoría | Algoritmo | FIPS | Uso en bAuth |
|-----------|-----------|------|-------------|
| **Hashing de contraseñas** | Argon2id | FIPS 140-3 (SP 800-132) | Hash de contraseñas — parámetros por tier |
| **Hashing general** | SHA-256 | FIPS 180-4 | Hash-chain tokens, fingerprints X.509 |
| **Hashing general** | SHA3-256 | FIPS 202 | Audit event hashing |
| **Firma digital** | ES256 (ECDSA P-256) | FIPS 186-5 | WebAuthn assertions |
| **Firma digital** | ES384 (ECDSA P-384) | FIPS 186-5 | Certificados X.509 de alta seguridad |
| **Firma digital** | Ed25519 | FIPS 186-5 | Firma JWT · Push challenges |
| **Cifrado simétrico** | AES-256-GCM | FIPS 197 | Cifrado de secrets en BD · JWE |
| **Derivación de claves** | HKDF-SHA256 | NIST SP 800-56C | Derivación de claves de sesión |
| **PQC — KEM** | ML-KEM-1024 | FIPS 203 | Intercambio de claves post-cuántico |
| **PQC — firma** | ML-DSA-87 | FIPS 204 | Firma digital post-cuántica |
| **PQC — firma** | SLH-DSA-SHA2-256s | FIPS 205 | Firma stateless basada en hash |

**Nota PQC:** Los algoritmos post-cuánticos (FIPS 203/204/205, agosto 2024) están en el catálogo como preparación para la transición obligatoria NSA CNSA 2.0 (deadline 2030). No son el algoritmo principal de firma de JWT hoy — Ed25519 sigue siendo el primario.

### 13.2 Biblioteca criptográfica Rust

bAuth usa la librería `ring` para operaciones criptográficas en Rust:
- `ring::hmac` — TOTP/HOTP (HMAC-SHA1/256/512)
- `ring::rand::SecureRandom` — generación de challenges y secrets
- ECDSA P-256 — verificación de assertions WebAuthn

Para TLS: `rustls` (TLS 1.3, sin soporte de versiones deprecadas).

### 13.3 El Módulo Criptográfico — frontera única (FIPS 140-3) · ⬜ POR DESARROLLAR

**Estado real (verificado por grep, 2026-07-11):** las primitivas criptográficas están **dispersas**
— `ring` invocado en **34 archivos**, `ed25519`/EdDSA en **15**, `argon2` en **8**, `sha2`/`hmac`
en **9**; **no existe `src/crypto/`**. Cada método (`totp.rs` usa `ring::hmac` en su cuerpo),
credencial (`credential.rs` usa `argon2` directo) y firmante invoca la librería por su cuenta.

**Por qué es un problema normativo.** NIST **FIPS 140-3** define el **cryptographic module** con una
**frontera** (*cryptographic boundary*): las operaciones ocurren **dentro** de un módulo con
interfaces declaradas, **algoritmos aprobados**, *self-tests* (KAT) al arranque y gestión de claves.
Con la cripto dispersa en 34+ archivos, es **imposible verificar de forma auditable** que toda ella
usa los 12 algoritmos aprobados (§13.1) con la misma parametrización — un solo archivo con un
algoritmo débil es un incumplimiento silencioso.

**La decisión (ADR-012).** Centralizar TODA operación criptográfica en el **Módulo Criptográfico**
(`src/crypto/`): ningún archivo invoca `ring`/`argon2`/`ed25519`/`hmac` directo — **solicita la
operación al módulo** (`hash_password`, `hmac`, `firmar`, `verificar_firma`, `cifrar_aead`,
`derivar_clave`, `aleatorio_seguro`), que la ejecuta con el algoritmo aprobado o la **rechaza**
(fail-closed, sin *fallback* débil). Los algoritmos son **enums cerrados**, no strings: uno no
aprobado no compila. El nombre deriva del término normativo FIPS 140-3 «cryptographic module», no
de criterio de diseño. Es al cifrado lo que el **Gestor de Canales** (2.12, ADR-011) es al
transporte. **Beneficio clave:** la transición **PQC** (FIPS 203/204/205, deadline CNSA 2.0 2030)
se hace en **un** módulo, no en 34 archivos. Ficha de implementación: **A.42 §10.ter**.

> **No confundir con el motor de métodos:** el motor que orquesta *cuál* autenticador se ejecuta ya
> existe (`MethodRegistry`, §3.3, patrón PAM). El Módulo Criptográfico es la capa de **abajo** — las
> primitivas de cifrado que esos métodos consumen. Se completan por separado: el motor se **amplía**
> a 18 métodos (§4), la cripto se **centraliza** (esta sección).

### 14.1 `bauth.audit_event` — tabla WORM

| `timestamp` | timestamptz | Momento exacto del evento | ISO 27001 A.8.17 |

### 14.2 Hash-chain forense en JWT

Cada JWT emitido en una sesión forma una cadena:

```
JWT[1]: token_seq=1, prev_hash=null
JWT[2]: token_seq=2, prev_hash=SHA256(JWT[1])
JWT[3]: token_seq=3, prev_hash=SHA256(JWT[2])
```

Si un atacante inserta un token falso en la secuencia, la cadena se rompe — detectable en auditoría comparando `prev_hash` con el token anterior conocido.

**Invariantes del `ChainState` (src/server/handlers/token_issue.rs):**
- **I-1. Monotonicidad:** `token_seq` siempre refleja el orden real de firma
- **I-2. Sin bifurcaciones:** ningún par de tokens puede compartir el mismo `prev_hash`
- **I-3. Sin gaps:** si la firma falla, el estado no se actualiza — no quedan secuencias huérfanas

### 14.3 Consulta de auditoría — autenticaciones fallidas en 90 días

```sql
SELECT actor_id, auth_method_used, access_result, loa_achieved, timestamp
FROM bauth.audit_event
WHERE access_result = 'DENEGADO'
  AND timestamp >= NOW() - INTERVAL '90 days'
ORDER BY timestamp DESC;
```

## 16. Estado del arte — infraestructura de tokens y sesiones 2026: lo que hay y lo que no hay

Esta sección aplica la visión editorial de los manuales bAuth: documentar con la misma honestidad
lo que el sistema **ya tiene** y lo que **aún no tiene**. El análisis método-por-método contra los
47 métodos de autenticación de la industria vive en
[2.02_MANUAL-METODOS-ESTADO-INDUSTRIA-v1.0.md](2.02_MANUAL-METODOS-ESTADO-INDUSTRIA-v1.0.md) — esta sección
cubre lo que ese manual no cubre: la **infraestructura de tokens, sesiones y protocolos** que rodea
a los métodos.

### 16.1 Lo que hay — inventario verificado en código

| Capacidad | Estado | Evidencia |
|-----------|:------:|-----------|
| 9 métodos nativos de autenticación | ✅ | `src/domain/auth_methods/` |
| JWT Ed25519 firmado vía Vault + hash-chain forense | ✅ | `jwt_signer.rs` + `token_issue.rs` (auth_chain, prev_hash, token_seq) |
| Cifrado JWE para claims sensibles | ✅ | `src/domain/jwe_encrypt.rs` |
| OIDC Provider: discovery, authorize, token, userinfo, jwks | ✅ | `oidc_provider.rs` |
| Introspección de tokens (RFC 7662) | ✅ | `token_protocols.rs` T42 — `bauth.token.introspect` |
| Token Exchange (RFC 8693) | ✅ | `token_protocols.rs` T40 — delegación entre servicios |
| DPoP (RFC 9449) | ⚠️ | `token_protocols.rs` T41 — valida estructura JWT del proof; falta verificar firma del proof y binding `jkt` contra el token |
| Step-Up (RFC 9470) | ✅ | Saga S4 + `delegation.rs` |
| 12 sagas de autenticación con compensaciones | ✅ | `saga_execute.rs` + `saga_catalog` |
| Revocación interna < 30 s | ⚠️ | Diseño vía Redis (invalidación de sesión) — sin endpoint estándar |
| Endpoint de revocación (RFC 7009) | ❌ | No aparece en el discovery del OIDC Provider |
| Rotación de refresh token + detección de reuso | ❌ | No existe en `token_issue.rs` |
| Logout de canal trasero (OIDC Back-Channel Logout) | ❌ | No implementado |
| Logout de canal frontal (OIDC Front-Channel Logout) | ❌ | No implementado |
| PAR — Pushed Authorization Requests (RFC 9126) | ❌ | No implementado |
| JARM — respuestas de autorización firmadas | ❌ | No implementado |
| CAE — evaluación continua de acceso | ❌ | Risk Engine (`risk.rs`) dinámico pero solo al login y sin cablear — ver MANUAL-RIESGO-ADAPTATIVO |
| Firma post-cuántica híbrida (Ed25519 + ML-DSA) | ⚠️ | FIPS 203/204/205 en catálogo `crypto_algorithm` — sin firma activa |

### 16.2 Lo que hace la industria en 2026

Cuatro prácticas de infraestructura de tokens son ya estándar en las plataformas tier-1:

1. **Rotación de refresh tokens con detección de reuso** (Auth0 la hizo estándar desde 2021,
   hoy todas la tienen): cada uso del refresh token emite uno nuevo e invalida el anterior. Si un
   refresh token *ya usado* se presenta de nuevo → toda la familia de tokens se revoca (señal
   inequívoca de robo). Es la defensa principal contra exfiltración de tokens.
2. **Logout de canal trasero (Back-Channel Logout):** cuando el usuario cierra sesión en un
   cliente, el proveedor notifica servidor-a-servidor a *todos* los clientes con sesión activa.
   Sin esto, cerrar sesión en la intranet no cierra la sesión del ERP.
3. **CAE — Continuous Access Evaluation** (Microsoft Entra ID lo popularizó): el token deja de
   ser válido *en el momento* en que cambia el riesgo (cuenta deshabilitada, IP anómala, política
   nueva) — sin esperar a que expire. Requiere un canal de eventos entre el emisor y el consumidor.
4. **FAPI 2.0 como perfil bancario:** PAR obligatorio + binding del token (mTLS o DPoP) +
   respuestas firmadas. Es el requisito de entrada al Open Banking.

### 16.3 Brechas por prioridad

**P1 — Crítico (seguridad de tokens):**

| Brecha | Riesgo que mitiga | Enfoque propuesto |
|--------|-------------------|-------------------|
| Rotación de refresh + detección de reuso | Robo de refresh token = sesión eterna del atacante | Familia de tokens en Redis (`token_family_id`); reuso detectado → revocar familia completa + `audit_event` crítico |
| Endpoint RFC 7009 (`/revoke`) | Sin forma estándar de que un cliente revoque su token | Handler `bauth.token.revoke` + registrar en discovery `revocation_endpoint` |
| Back-Channel Logout | Cierre de sesión no se propaga entre clientes | Logout token JWT (`events` claim) enviado a los `backchannel_logout_uri` registrados |

**P2 — Importante:**

| Brecha | Enfoque propuesto |
|--------|-------------------|
| DPoP completo | Completar T41: verificar firma del proof con la clave pública del `jwk` header + validar `jkt` thumbprint contra el token + anti-replay por `jti` |
| PAR (RFC 9126) | Endpoint `/par` que registra la solicitud de autorización y devuelve `request_uri` — requisito FAPI 2.0 |
| CAE ligado al Risk Engine | Canal Redis pub/sub: evento de riesgo → los PEP consultan estado de sesión antes de aceptar el token |
| JARM | Firmar las respuestas de autorización como JWT |

**P3 — Planificar:**

- Firma híbrida Ed25519 + ML-DSA-87 (deadline NSA CNSA 2.0: 2030)
- Tokens de credencial verificable (VC) — depende de D13
- Session management OIDC completo (iframe de monitoreo de sesión)

### 16.4 Cumplimiento de perfiles — objetivo de certificación

| Perfil | Requisitos clave | Estado bAuth |
|--------|------------------|:------------:|
| OIDC Basic Certification | code flow + discovery + userinfo + jwks | ✅ listo para certificar |
| OIDC Session Management | logout front/back-channel | ❌ gap P1 |
| FAPI 2.0 Security Profile | PAR + (mTLS ∨ DPoP) + PKCE | ⚠️ mTLS ✅ · PKCE ✅ · PAR ❌ · DPoP ⚠️ |
| NIST SP 800-63C-4 (federación) | FAL1-3 | ⚠️ FAL2 alcanzable — falta assertion cifrada para FAL3 |
