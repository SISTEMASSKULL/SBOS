## 1. Audiencia, propósito y alcance

Este manual documenta el **sistema de menú contextual** de bAuth y su integración con **bGlobal**:
cómo la interfaz muestra a cada usuario **solo las acciones que sus átomos permiten**, al nivel de
aseguramiento requerido, con step-up cuando aplica. Es la cara visible del control de acceso — la
UI que se adapta a los permisos.

**Audiencia:** desarrolladores frontend, administradores de menús, integradores de bGlobal.

**Deslinde:** el Dashboard que consume este menú está en [2.11 Frontend](2.11_MANUAL-FRONTEND-v1.0.md);
los átomos que lo gobiernan en [1.3 Átomos](1.03_MANUAL-ATOMOS-v1.0.md); el step-up en
[2.1 Autenticación](2.01_MANUAL-AUTENTICACION-v1.0.md) §10. Aquí se documenta el mecanismo de
menú gated como capacidad enterprise.

---

## 2. El principio — la UI es la proyección del BitMask

Un IAM Enterprise no confía en ocultar botones en el frontend: **la UI se deriva de los permisos**.
El principio de bAuth:

> **Un ítem de menú se muestra solo si el usuario tiene el átomo que lo gobierna, al LoA
> requerido.** La interfaz es la proyección visible del RolBitMask — no una lista hardcodeada que
> "casualmente" coincide con los permisos.

```
UI hardcodeada (frágil):   el frontend decide qué mostrar → puede desincronizarse del permiso real
UI proyectada (bAuth):     menu_item_atom liga cada ítem a su átomo → el menú ES el BitMask visible
```

**Por qué es enterprise:** elimina la clase de bug donde la UI muestra una acción que el backend
luego rechaza (mala UX) o —peor— muestra una acción que el usuario no debería ver (fuga de
información sobre capacidades). El menú y la autorización son **la misma fuente de verdad**.

## 3. Las tres tablas del menú

`bGlobal` provee tres tablas (schema `bglobal`, DDL verificado):

| Tabla | Propósito |
|-------|-----------|
| `menu_item` | El árbol de menú: label, route, icon, `parent_id` (jerarquía), sort_order, `menu_type`, `context_key` — **le faltan `owner_daemon` (propietario) y el contexto de propósito (§5.3)** |
| `menu_item_atom` | **El gate:** liga cada ítem a los átomos que lo habilitan (+ LoA + step-up) — §4 |
| `menu_context` | Los contextos de entidad + los catálogos ENUM (doble propósito) — §5 |

`menu_item` es jerárquico (`parent_id` autorreferencial) y tipado (`menu_type_enum`: CONTEXTUAL,
etc.). Un ítem CONTEXTUAL exige `context_key` (el CHECK lo garantiza) — aparece según la entidad
sobre la que se opera.

## 4. `menu_item_atom` — el gate de átomo + LoA + step-up

La tabla clave (DDL verificado) — el mecanismo que convierte el menú en proyección del permiso:

```sql
CREATE TABLE bglobal.menu_item_atom (
    menu_item_id  UUID → menu_item,
    atom_code     INTEGER,            -- el átomo que habilita este ítem
    require_all   BOOLEAN DEFAULT true, -- ¿necesita TODOS los átomos o CUALQUIERA?
    min_loa       INT DEFAULT 1 CHECK (1-3), -- LoA mínimo para ver/usar el ítem
    step_up_flow  TEXT,               -- ★ qué flujo de step-up disparar si falta LoA
    PRIMARY KEY (menu_item_id, atom_code)
);
```

**Las tres dimensiones del gate:**
1. **Átomo** (`atom_code` + `require_all`): el ítem se muestra si el RolBitMask del usuario tiene
   el/los átomo(s) — con lógica AND (`require_all=true`) u OR (`false`). Evaluación O(1)
   ([1.4 BitMask](1.04_MANUAL-BITMASK-v1.0.md)).
2. **LoA** (`min_loa`, 1-3): el ítem exige un nivel de aseguramiento mínimo — un botón de
   transacción crítica pide AAL3 aunque el usuario tenga el átomo.
3. **Step-up** (`step_up_flow`): si el usuario tiene el átomo pero le falta LoA, el ítem
   **dispara el flujo de step-up** al activarse (RFC 9470) — el patrón «Modificar — AAL3» de los
   prototipos ([2.11 Frontend](2.11_MANUAL-FRONTEND-v1.0.md) §7) formalizado en el modelo de datos.

Esto es control de acceso a la UI de grado enterprise: el ítem no solo se muestra/oculta por
permiso, sino que **escala la autenticación** cuando la acción lo exige.

## 5. `menu_context` — doble propósito: menús y ENUMs

`menu_context` (seed verificado) cumple **dos funciones** — una consolidación elegante:

### 5.1 Contextos de entidad (los menús contextuales)

Define sobre qué entidades hay menús contextuales:

| context_key | Entidad | Menú de… |
|-------------|---------|----------|
| `transaccion` | Transaccion | Operaciones financieras |
| `usuario` | Usuario | Administración de usuarios |
| `rol` | Rol | Gestión de roles y permisos |
| `cuenta_onchain` | CuentaOnchain | Operaciones blockchain |
| `documento` | Documento | Acciones sobre documentos anclados |
| `tenant` | Tenant | Administración del tenant (solo SU) |

Al hacer clic derecho / abrir el menú de una entidad, se muestran los ítems CONTEXTUAL de ese
`context_key` que el usuario tiene habilitados.

### 5.2 Catálogos ENUM (antes 5 tablas separadas)

El seed lo dice: *"Datos de selección para UserTemplate (antes eran 5 tablas separadas)"*.
`menu_context` **también** es el catálogo de los ENUMs del UserTemplate:

`account_type` (HUMAN/SERVICE/SYSTEM/GUEST) · `gender` (M/F/NB/NR) · `marital_status` ·
`id_document_type` (DNI/PASSPORT/CI/RUT/NIT…) · `employment_type` (FULL_TIME/CONTRACTOR…).

**La consolidación:** en vez de 5 tablas de catálogo (una por ENUM), todas viven en `menu_context`
como contextos de selección. Es el mismo patrón de extensibilidad de `idn_identidad_atributo`
([1.7 Atributos](1.07_MANUAL-ATRIBUTOS-v1.0.md)): agregar un ENUM nuevo es insertar filas, no crear
una tabla. Esto conecta con la registración de ENUMs de [1.9 Roles](1.09_MANUAL-ROLES-v1.0.md) §5.

### 5.3 Propietario y contexto del menú contextual (corrección de diseño — 2026-07-10)

El menú contextual es un **registro compartido de TODO el ecosistema SBOS** — por eso vive en
`bglobal` (schema compartido), no en `bauth`. Cada daemon (bauth, bos, btax…) aporta y usa sus
propios menús contextuales. Para que **cada daemon sepa cuáles menús le pertenecen y de dónde se
originan**, el modelo necesita dos dimensiones que hoy faltan, más una regla de ecosistema:

**A. Propietario (`owner_daemon`) — qué daemon aporta el menú.** No es un `app_code` interno de
bAuth: es el **daemon del ecosistema** dueño del menú — `bauth`, `bos`, `btax`, `bnotify`,
`bkernel`, `biedata`, `bsearch`, `bnexus`. Cada daemon:
- **declara** sus menús contextuales (los aporta al registro compartido),
- **sabe cuáles puede usar** (los propios + los que se le habiliten),
- **conoce el origen** de cada menú (¿lo aporta `bos`? ¿`btax`?).

Así el menú es un **contrato del ecosistema**: bAuth aporta los menús de identidad/roles, `btax`
los de facturación, `bos` los de despliegue, etc. Esto **confirma que el menú pertenece a
`bglobal`** (compartido) — **NO migra a `bauth`**; su naturaleza es multi-daemon. *(Corrige la nota
de la v1.1.0 que sugería migrarlo — era incorrecta.)*

**B. Contexto (`purpose` / `data_scope` / `usage`) — para qué sirve el menú.** No es el nivel del
árbol: es la descripción funcional de **qué requerimiento cubre, sobre qué datos opera y dónde se
usa**. Campos propuestos:
- `purpose` — qué requerimiento/necesidad cubre el menú
- `data_scope` — sobre qué datos/entidades opera
- `usage` — dónde y en qué situación se usa

Así cualquier daemon o desarrollador entiende, al ver un menú, **para qué existe y de dónde viene**,
sin adivinar — clave en un ecosistema de 8 daemons que comparten el registro.

**C. Regla de ecosistema: TODO ENUM se declara en el menú contextual.** `menu_context` ya alberga
los ENUMs del UserTemplate (§5.2). Se eleva a **regla**: **cualquier ENUM de cualquier daemon DEBE
declararse en `bglobal.menu_context`** — es el **registro canónico único de valores de selección de
todo SBOS**. No hay ENUMs sueltos en tablas por daemon; todos viven aquí, cada uno con su
`owner_daemon` (qué daemon lo aporta) y su contexto (para qué sirve). Extiende la consolidación
«5 tablas → 1» a todo el ecosistema: un solo lugar donde buscar cualquier valor de selección.

**El menú/ENUM contextual completo — cuatro dimensiones:**

```
menú contextual = PROPIETARIO (qué daemon lo aporta: bauth/bos/btax/…)
                + ENTIDAD (context_key: sobre qué entidad se opera)
                + CONTEXTO (purpose/data_scope/usage: para qué sirve, qué datos, dónde)
                + GATE (menu_item_atom: átomo + LoA + step-up — solo para ítems de acción de bAuth)
```

**DDL propuesto** (schema `bglobal` — compartido, coordinación de proyecto/HITL):

```sql
-- Contexto + propietario en el registro de contextos/ENUMs
ALTER TABLE bglobal.menu_context
  ADD COLUMN owner_daemon TEXT NOT NULL DEFAULT 'bauth'
    CHECK (owner_daemon IN ('bauth','bos','btax','bnotify','bkernel','biedata','bsearch','bnexus')),
  ADD COLUMN purpose      TEXT,   -- qué requerimiento cubre
  ADD COLUMN data_scope   TEXT,   -- sobre qué datos opera
  ADD COLUMN usage        TEXT;   -- dónde se usa

-- Propietario en cada ítem de menú (qué daemon lo aporta)
ALTER TABLE bglobal.menu_item
  ADD COLUMN owner_daemon TEXT NOT NULL DEFAULT 'bauth'
    CHECK (owner_daemon IN ('bauth','bos','btax','bnotify','bkernel','biedata','bsearch','bnexus'));

CREATE INDEX ix_menu_item_owner   ON bglobal.menu_item (owner_daemon, context_key);
CREATE INDEX ix_menu_context_owner ON bglobal.menu_context (owner_daemon);
```

**Nota de frontera:** al agregar `owner_daemon`, cada daemon consulta *sus* menús con
`WHERE owner_daemon = '<mi-daemon>'`. bAuth resuelve el **gate** (átomo+LoA) solo para los ítems de
acción; los ENUMs de selección no necesitan gate. Como es `bglobal` (compartido), el cambio se
**coordina a nivel de proyecto** (no es territorio propio de un solo daemon — [1.5 DDL y Seeds](1.05_MANUAL-DDL-SEEDS-v1.0.md) §2).

## 6. El flujo de render del menú contextual

```
Usuario abre el menú de una entidad (context_key = 'transaccion')
  │
  ├── 1. Cargar los menu_item CONTEXTUAL de ese context_key (jerarquía por parent_id)
  ├── 2. Para cada ítem: consultar menu_item_atom
  │        ¿el RolBitMask tiene el/los átomo(s)? (require_all AND/OR) → O(1)
  │           NO → ocultar el ítem
  │           SÍ → ¿ctx.loa >= min_loa?
  │                  SÍ → mostrar habilitado
  │                  NO → mostrar con badge "requiere AAL{n}" → al clic, step_up_flow
  ├── 3. Ordenar por sort_order, respetar is_visible
  └── 4. Renderizar el árbol (parent_id) en el Dashboard
```

El menú resultante es **exacto al permiso**: cada usuario ve un menú distinto, derivado de su
BitMask y su LoA de sesión — sin lógica de permisos duplicada en el frontend.

## 7. La frontera bAuth ↔ bGlobal

**Encuadre (ORQUESTA-051):** `bglobal` es el schema de catálogos compartidos del ecosistema
(países, idiomas, zonas, monedas — [1.7 Atributos](1.07_MANUAL-ATRIBUTOS-v1.0.md) §6.2 — **y** el
menú). bAuth:
- **Provee los átomos** (`atom_code`) que `menu_item_atom` referencia — el gate se resuelve con el
  RolBitMask de bAuth.
- **Consume** `menu_item`/`menu_context` para que el Dashboard renderice el menú correcto.
- **Evalúa** el gate (BitMask + LoA) — la decisión de mostrar/ocultar/step-up es de bAuth.

`bglobal` almacena la estructura del menú; **bAuth decide quién ve qué**. La liga `atom_code`
cruza los schemas (FK lógica) — un cambio en el catálogo de átomos de bAuth se refleja en el gate
del menú sin tocar `bglobal`.

## 8. Estado del arte — UI adaptativa por permisos 2026: lo que hay y lo que no hay

### 8.1 Lo que hay — inventario verificado

| Capacidad | Estado | Evidencia |
|-----------|:------:|-----------|
| Menú jerárquico tipado (`menu_item`) | ✅ DDL | parent_id + menu_type |
| Gate por átomo con AND/OR (`require_all`) | ✅ DDL | `menu_item_atom` |
| Gate por LoA (`min_loa` 1-3) | ✅ DDL | verificado |
| Step-up integrado en el ítem (`step_up_flow`) | ✅ DDL | RFC 9470 en el modelo |
| Contextos de entidad (6 sembrados) | ✅ seed | `menu_context` |
| Catálogos ENUM consolidados (5 en una tabla) | ✅ seed | account_type/gender/… |
| **Propietario = daemon (`owner_daemon`: bauth/bos/btax/…)** | ❌ | corrección §5.3 — cada daemon debe saber cuáles menús son suyos |
| **Contexto = propósito (`purpose`/`data_scope`/`usage`)** | ❌ | corrección §5.3 — para qué sirve, qué datos, dónde |
| **Regla: TODO ENUM del ecosistema declarado en `menu_context`** | ⚠️ | ENUMs de bAuth ✅; regla para todos los daemons pendiente §5.3-C |
| Render del menú en el Dashboard | ❌ | Flutter no iniciado ([2.11 Frontend](2.11_MANUAL-FRONTEND-v1.0.md)) |
| Handler `bauth.menu.resolve` (menú por usuario) | ⚠️ | `dashboard_panels.rs` — cobertura por verificar |
| Menús contextuales poblados por app | ⚠️ | contextos sí; ítems por app pendientes |

### 8.2 Lo que hace la industria en 2026

1. **UI derivada de permisos (policy-driven UI):** el estándar enterprise — la interfaz se genera
   desde el modelo de autorización, no se hardcodea. bAuth lo hace con `menu_item_atom`.
2. **LoA-gated actions / step-up en la UI:** las acciones sensibles exigen elevación en el momento
   del clic (no al login) — el patrón que bAuth tiene en el modelo de datos (`step_up_flow`).
3. **Menús contextuales (right-click / entity actions):** las acciones aparecen según la entidad y
   el permiso — patrón común en ERPs y consolas de admin.
4. **Consolidación de catálogos:** la tendencia a evitar la proliferación de tablas de ENUM — un
   registro de contexto único (como `menu_context`) en vez de N tablas.

### 8.3 Comparativa — el menú contextual de bAuth vs la práctica

| Criterio | bAuth | Admin console típica | ERP con menús |
|----------|:-----:|:--------------------:|:-------------:|
| Menú derivado del permiso (no hardcode) | ✅ | ⚠️ | ⚠️ |
| Gate por átomo O(1) (BitMask) | ✅ único | ❌ | ❌ |
| Gate por LoA + step-up en el ítem | ✅ único | ⚠️ | ❌ |
| Menús contextuales por entidad | ✅ | ⚠️ | ✅ |
| Catálogos ENUM consolidados | ✅ | ❌ | ⚠️ |
| Multi-tenant (menú por tenant) | ✅ | ⚠️ | ⚠️ |
| Render implementado | ❌ gap | ✅ | ✅ |
| Soberano | ✅ | ⚠️ | ⚠️ |

**Lectura honesta:** el modelo de datos del menú contextual es superior — gate por átomo + LoA +
step-up en una sola tabla, multi-tenant, con catálogos consolidados. Es la UI-como-proyección-del-
BitMask hecha bien. Su brecha es de **render**: el Dashboard Flutter que lo consume no está
construido ([2.11 Frontend](2.11_MANUAL-FRONTEND-v1.0.md) es L1-L2). El diseño de datos es L2+;
la experiencia visible es L1.

### 8.4 Brechas por prioridad

**P1 — Corrección de diseño + render:**
- **Agregar `owner_daemon` (propietario: qué daemon aporta) + `purpose`/`data_scope`/`usage`
  (contexto: para qué sirve) a `menu_context`/`menu_item`** (§5.3) — coordinación de proyecto
  (schema `bglobal` compartido, el menú NO migra a bauth) ·
- **Regla de ecosistema: TODO ENUM de cualquier daemon se declara en `menu_context`** (§5.3-C) —
  registro canónico único de valores de selección de SBOS ·
- Handler `bauth.menu.resolve(user, context_key)` que devuelve el menú gated · consumir el menú en
  el Dashboard Flutter (fase 1 del [2.11 Frontend](2.11_MANUAL-FRONTEND-v1.0.md)).

**P2 — Poblar el menú:**
- Ítems de menú por app (cada app declara sus acciones y sus átomos) · más contextos de entidad ·
  verificar el gate LoA+step-up end-to-end (AA-1).

**P3 — Futuro:**
- Personalización de menú por usuario (favoritos) sobre el gate de permiso · menú adaptativo por
  riesgo (ocultar acciones sensibles si el [3.1 Riesgo](3.01_MANUAL-RIESGO-ADAPTATIVO-v1.0.md) es alto).
