## 1. Audiencia, propósito y alcance

Este manual documenta **AtomLang**: el lenguaje de configuración de autorización de bAuth. Define su vocabulario, su gramática, el compilador `atomc` que valida y transforma el árbol fuente en un artefacto técnico ejecutable, y las garantías de corrección que el sistema provee al administrador de autenticación.

**Audiencia:** administradores de autenticación (quienes mantienen el árbol de templates de rol), desarrolladores bAuth (quienes implementan el compilador y el evaluador), auditores de seguridad (quienes verifican que las reglas de autorización son determinísticas y trazables a norma).

**Deslinde:**

| Manual | Qué cubre — y qué NO cubre |
|---|---|
| [1.03 MANUAL-ATOMOS](1.03_MANUAL-ATOMOS-v1.0.md) | El átomo como **unidad de catálogo** (taxonomía, estados, tablas). **No** cubre el lenguaje con que se escribe un átomo |
| [2.05 MANUAL-POLITICAS](2.05_MANUAL-POLITICAS-v1.0.md) | El **motor de evaluación** en runtime (PDP, `cfg_policy_library`, PolicyState en el BitMask). **No** cubre la etapa de autoría |
| **Este manual 2.13** | El **lenguaje** con el que se escribe un átomo o una política en el árbol fuente, y el compilador que lo valida |
| [2.14 MANUAL-COMPOSICION-ARBOL](2.14_MANUAL-COMPOSICION-ARBOL-v1.0.md) | **Dónde** van los átomos en el árbol (zonas, aplicaciones, dominios, motores). **No** cubre la sintaxis de un átomo individual |

## 2. Por qué existe AtomLang — el problema que resuelve

El árbol de templates de rol de bAuth se escribe y mantiene mediante una UI (dashboard Flutter) que permite expresar reglas de autorización en texto semi-libre. Este árbol es legible para un humano pero **no es directamente ejecutable por el evaluador (PDP)**: un lenguaje que permite más de una representación para el mismo significado es, por definición, no determinístico para una máquina.

**Defectos detectados en el árbol real — análisis verificado en VPS (fuente: [A.46 §3](anexos/A.46_ANEXO-ATOMLANG-GRAMATICA-COMPILADOR-v1.0.md)):**

| # | Defecto | Consecuencia de seguridad |
|---|---|---|
| D1 | **Inconsistencia de case:** `verbo = "configure"` vs `valor = ["CONFIGURE"]` | Target-gate falla silenciosamente — la regla más estricta queda inoperante |
| D2 | **Mismo atributo evaluado dos veces** (Target + Condition) | Dos fuentes de verdad con formatos distintos — comportamiento indefinido |
| D3 | **`first-applicable` sobre atoms concurrentes independientes** | El requisito de seguridad más alto se pierde por orden de declaración |
| D4 | **Sin badges en nodos contenedores** | El compilador no puede distinguir PolicySet de Policy sin inferencia manual |
| D5 | **Verbos y subjects como texto libre** | Cualquier variante ortográfica rompe el matching sin error detectable |
| D6 | **Sin etapa de validación Source → Evaluador** | Los defectos D1–D5 llegan directamente a runtime de producción |

**AtomLang** define una gramática cerrada y un compilador (`atomc`) que **detecta y rechaza** estos defectos antes de que lleguen al evaluador, garantizando que el árbol técnico sea 100% determinístico: solo IDs, enums y valores tipados — cero strings comparados por igualdad textual en tiempo de evaluación.

## 3. El modelo de dos árboles

AtomLang introduce una **separación obligatoria** entre dos representaciones del modelo de autorización:

```
┌──────────────────────────────────┐               ┌──────────────────────────────────────┐
│         Árbol SOURCE             │   atomc ───►  │       Árbol CANONICAL (IR)           │
│                                  │               │                                      │
│  Escrito/mantenido por el admin. │               │  Solo IDs, enums, valores tipados.   │
│  YAML legible, nombres humanos.  │               │  Generado por atomc. Nunca editado.  │
│  Validado gramaticalmente.       │               │  Input único del evaluador (PDP).    │
└──────────────────────────────────┘               └──────────────────────────────────────┘
     bos_atom_catalog · Flutter UI                       bos_atom_compiled (tabla)
```

| | Árbol SOURCE | Árbol CANONICAL (IR) |
|---|---|---|
| **Quién lo produce** | Administrador vía UI / `.atm.yaml` | El compilador `atomc` exclusivamente |
| **Lenguaje** | AtomLang (YAML restringido, legible) | Simbólico: IDs (integer), enums, FKs |
| **¿Lo ejecuta el evaluador?** | **No — nunca** | Sí — es el único input del PDP |
| **¿Es editable a mano?** | Sí — es la fuente de verdad del admin. | No — se regenera compilando el SOURCE |
| **Tabla bAuth** | `bos_atom_catalog` · `bos_atom_policy` | `bos_atom_compiled` |
| **Analogía** | Código fuente Rust | Bytecode compilado |

**Invariante crítica de seguridad:** el evaluador (PDP) lee **exclusivamente** `bos_atom_compiled`. Toda ruta que permita al evaluador leer `bos_atom_catalog` directamente constituye un defecto de seguridad — equivalente a ejecutar código fuente sin compilar. La brecha actual (evaluador sin `atomc`) está registrada como **P1 en §8.4**.

## 4. Los constructos del lenguaje

AtomLang es YAML con una gramática restringida — no inventa sintaxis nueva, **restringe YAML** a un subconjunto unívoco validado por JSON Schema + reglas semánticas. La gramática EBNF completa y el JSON Schema de cada constructo están en [A.46 §2](anexos/A.46_ANEXO-ATOMLANG-GRAMATICA-COMPILADOR-v1.0.md). El fundamento normativo de cada constructo (de qué norma proviene, cómo se mapea) está en [A.45](anexos/A.45_ANEXO-FUNDAMENTOS-NORMATIVOS-ATOMLANG-v1.0.md).

### 4.1 Vocabulario cerrado

Todos los campos de tipo "vocabulario" usan catálogos registrados. El compilador rechaza (`ATOMC-E-014`) cualquier valor fuera del catálogo:

| Campo AtomLang | Vocabulario cerrado | Fuente de catálogo |
|---|---|---|
| `verb_id` | 50+ verbos de negocio + verbos D00 de identidad | `bos_verb` ([1.02 §3](1.02_MANUAL-VERBOS-v1.0.md)) |
| `subject.kind` | `ROL` · `SET` · `ANY` | Definición fija del lenguaje |
| `operator` | `>` `<` `>=` `<=` `==` `!=` `IN` `NOT_IN` `BETWEEN` | Definición fija del lenguaje |
| `combining_algorithm` | `deny-overrides` · `permit-overrides` · `first-applicable` · `deny-unless-permit` · `permit-unless-deny` · `aggregate-strictest` | Estándar XACML §7.18 + extensión bAuth |
| `effect.decision` | `Permit` · `Deny` | XACML 3.0 — exactamente dos valores posibles |

### 4.2 Target: Subject, Resource, Environment

El **Target** determina a qué solicitudes aplica un Atom. Conforme XACML 3.0 §2.4, un Target vacío (o `subject.kind: ANY`) coincide con cualquier solicitud. Fundamento normativo completo en [A.45 §3](anexos/A.45_ANEXO-FUNDAMENTOS-NORMATIVOS-ATOMLANG-v1.0.md).

```yaml
target:
  subject:
    kind: SET                         # ROL | SET | ANY
    set_id: aprobadores_finanzas      # FK a bos_group (declarado en D98)
  resource: payment_supplier          # FK a bos_resource_catalog — nunca string libre
  environment:                        # atributos de contexto exigidos en el Target
    - property_id: horario_laboral    # FK a bos_attribute_catalog
      operator: "=="
      value: true
```

**Regla:** `subject.kind: ANY` equivale al Target vacío XACML — *"An empty Target matches any request"*. Uso típico: Guardrails transversales donde la restricción aplica a cualquier actor.

### 4.3 Condition y sus operadores

La **Condition** es una expresión booleana que refina la aplicabilidad del Atom **más allá del Target**. Solo se evalúa si el Target-gate cerró en Match. Conforme XACML 3.0 §5.6: una Condition ausente siempre evalúa `true`.

```yaml
condition:
  property_id: transaction_amount         # FK a bos_attribute_catalog — define el data_type
  operator: ">"
  value: "@bauth_config_param.approval_threshold"  # referencia a parámetro — NUNCA literal
```

**Restricción de parametrización (P1):** valores monetarios, umbrales, monedas y cualquier valor de negocio que pueda variar por tenant o región **DEBEN** referenciar `bauth_config_param` con el prefijo `@bauth_config_param.<clave>`. Un literal numérico en un campo de tipo `AMOUNT` genera **ATOMC-E-042**; un código de moneda literal genera **ATOMC-E-043** (ver [A.46 §4](anexos/A.46_ANEXO-ATOMLANG-GRAMATICA-COMPILADOR-v1.0.md) y [A.48](anexos/A.48_ANEXO-PARAMETRIZACION-BAUTH-CONFIG-PARAM-v1.0.md)).

La ausencia de Condition se declara **explícitamente** (`condition: null`) — nunca por omisión del campo (ambigüedad entre "olvidé escribirla" e "intencionalmente no tiene").

### 4.4 Effect y Obligation

El **Effect** produce exactamente uno de dos valores — no existe un tercer valor (XACML §2.6):

```yaml
effect:
  decision: Permit              # Permit | Deny — dos valores únicos
  obligation:                   # acciones que el PEP DEBE ejecutar (no puede ignorar)
    required_loa: 3
    max_age_seconds: 300
    audit: on
  advice: "Requiere aprobación nivel 3"  # información que el PEP PUEDE ignorar
```

Todo matiz adicional (solo lectura, auditoría reforzada, step-up) se expresa en `obligation`, nunca como un tercer valor de `decision`. Matices sobre el verbo se resuelven como **verbos distintos** (`read` vs `write`), no como Effects distintos.

Las cuatro decisiones posibles del evaluador son `Permit` · `Deny` · `NotApplicable` · `Indeterminate` — las dos últimas solo existen en el motor de evaluación (runtime), no en la definición del Effect del Atom.

### 4.5 combining_algorithm

La Policy contenedora declara **obligatoriamente** el algoritmo que combina los resultados de sus Atoms cuando hay dos o más. El compilador emite **ATOMC-E-031** si una Policy con 2+ Atoms no lo declara:

| Algoritmo | Comportamiento | Uso recomendado en bAuth |
|---|---|---|
| `deny-overrides` | Cualquier Deny → resultado Deny, sin importar el resto | Módulos de control estricto. **Default recomendado** |
| `permit-overrides` | Cualquier Permit → resultado Permit | Módulos donde se prioriza disponibilidad |
| `first-applicable` | Primer Atom aplicable → resultado (orden importa) | Reglas jerárquicas (excepción → regla general) |
| `deny-unless-permit` | Deny salvo Permit explícito; nunca Indeterminate | Guardrails ("silencio = denegado") |
| `aggregate-strictest` | Recorre TODOS los Permit y combina Obligations tomando el valor más estricto campo a campo | Políticas step-up concurrentes — extensión bAuth (ver [A.46 §4](anexos/A.46_ANEXO-ATOMLANG-GRAMATICA-COMPILADOR-v1.0.md)) |

`aggregate-strictest` resuelve el defecto D3 de §2: cuando múltiples Atoms aplican simultáneamente con distintos `max_age_seconds` o `required_loa`, el resultado es siempre el más restrictivo (máximo LoA, mínimo tiempo de sesión), no el primero por orden de declaración.

## 5. La estructura del archivo `.atm.yaml`

Un archivo AtomLang (`*.atm.yaml`) contiene exactamente una Policy o un PolicySet con sus Policies hijas. Un archivo = un dominio de negocio = un diff legible en git.

```yaml
atomlang_version: 1                     # campo obligatorio — permite migraciones v1→v2 sin ambigüedad

policy:
  policy_id: tryton_account_pagos       # snake_case, FK a cfg_policy_library
  application_id: 7                     # FK a bos_application (Caso 1) | null (Caso 2 Guardrail)
  combining_algorithm: deny-overrides   # OBLIGATORIO cuando hay 2+ atoms

  atoms:
    - atom_id: payment_supplier_approve
      verb_id: approve                  # FK a bos_verb — PROHIBIDO string libre
      target:
        subject:
          kind: SET
          set_id: analistas_finanzas    # FK a bos_group (declarado en D98)
        resource: payment_supplier_transaction  # FK a bos_resource_catalog
      condition:
        property_id: proveedor_estado   # FK a bos_attribute_catalog
        operator: "=="
        value: activo                   # enum registrado — resuelto contra bos_attribute_catalog
      effect:
        decision: Permit
        obligation:
          audit: on
```

**Reglas de estilo — enforced por `atomc lint` (no solo convención):**

1. `atomlang_version` es la primera clave, siempre.
2. Todo identificador en `snake_case` — el linter rechaza camelCase, espacios y mayúsculas.
3. `condition: null` explícito si el Atom no tiene condición adicional.
4. Ningún valor de `verb_id`, `resource`, `subject.set_id` puede ser un literal no registrado en catálogo.
5. Ningún literal numérico en campos de tipo `AMOUNT` o `CURRENCY`.

## 6. El compilador `atomc` — fases y garantías

`atomc` es el compilador AtomLang: un binario Rust 1.85+ MUSL, distribuido como artefacto estático dentro de `BauthAgent/tools/atomc/`. Comparte stack, tipos de dominio (`BauthError`, newtypes de `verb_id`) y filosofía de despliegue con el daemon bAuth.

**Madurez actual:** L0 — arquitectura y catálogo de errores especificados en [A.46](anexos/A.46_ANEXO-ATOMLANG-GRAMATICA-COMPILADOR-v1.0.md), sin código Rust implementado. Implementación: **brecha P1**.

### 6.1 Pipeline de compilación — 3 fases

```
Source .atm.yaml
       │
       ▼  FASE 1 — LEXER
       │  Tokeniza YAML. Resuelve cada string contra catálogos (bos_verb, bos_group,
       │  bos_resource_catalog, bos_attribute_catalog). Error si el valor no existe.
       │  → ATOMC-E-014 ("valor no registrado en catálogo")
       │
       ▼  FASE 2 — PARSER / VALIDADOR SEMÁNTICO
       │  Verifica grafo de dependencias: ningún Atom fuera de Policy, combining_algorithm
       │  obligatorio, atributos no duplicados entre Target y Condition, literales prohibidos
       │  en campos AMOUNT/CURRENCY.
       │  → ATOMC-E-031 ("Policy sin combining_algorithm")
       │  → ATOMC-E-041 ("atom_id con dígito o código de moneda")
       │  → ATOMC-E-042 ("literal numérico en campo AMOUNT")
       │  → ATOMC-E-043 ("código de moneda literal")
       │
       ▼  FASE 3 — EMITTER (generador IR)
       │  Emite el Árbol Técnico (.atm.json): solo IDs (integer), enums, valores tipados.
       │  Cero strings comparables por igualdad textual en tiempo de evaluación.
       │
       ▼
Árbol CANONICAL (.atm.json → bos_atom_compiled)
```

### 6.2 Comandos CLI

```bash
atomc lint   ./atoms/src/step_up.atm.yaml     # sintaxis + estilo (sin DB, rápido)
atomc validate ./atoms/src/step_up.atm.yaml   # lint + resolución contra catálogos Postgres
atomc compile  ./atoms/src/*.atm.yaml         # validate + genera IR en ./atoms/compiled/
atomc publish  ./atoms/compiled/step_up.atm.json  # inserta en bos_atom_compiled (con auditoría WORM)
```

`atomc compile` falla el build completo (exit code ≠ 0) si cualquier archivo contiene un error — no hay compilación parcial.

### 6.3 Formato de diagnóstico (legible por agentes IA)

```json
{
  "level": "error",
  "code": "ATOMC-E-042",
  "message": "valor literal '10000' en campo AMOUNT — usar '@bauth_config_param.approval_threshold'",
  "file": "button_rules.atm.yaml",
  "atom_id": "venta_aprobacion_simple",
  "field_path": "atoms[0].condition.value",
  "phase": "semantic"
}
```

Catálogo completo de códigos ATOMC-E-xxx / ATOMC-W-xxx (causa, campo, fase, acción correctiva) en [A.46 §4](anexos/A.46_ANEXO-ATOMLANG-GRAMATICA-COMPILADOR-v1.0.md).

### 6.4 Integración en pipeline CI/CD

```
Admin edita → *.atm.yaml (git, BauthAgent/atoms/src/)
    ↓
Pre-commit hook      → atomc lint     (sin DB — bloquea sintaxis incorrecta antes del commit)
    ↓
CI (al abrir PR)     → atomc validate (con Postgres dev — bloquea merge si hay error semántico)
    ↓
Pipeline release     → atomc compile → atomc publish (Postgres test/prod)
    ↓
bAuth PDP            → recarga bos_atom_compiled (hot-reload o restart controlado)
```

## 7. Los dos casos de Rule: Aplicación vs. Guardrail

Todo Atom en AtomLang existe en uno de dos contextos según el valor de `application_id`. La estructura interna (Target / Condition / Effect) es **idéntica** en ambos casos; lo que cambia es el contexto contenedor y el alcance de evaluación:

### Caso 1 — Rule de Aplicación (`application_id != null`)

El Atom regula operaciones de un módulo de negocio concreto (una fila de `bos_application`). Vive dentro de una Policy que agrupa los Atoms del mismo módulo y declara el `combining_algorithm` que los combina. Ejemplos: `tryton.account`, `tryton.sale`, `orangehrm.leave`, `bos_crm`.

**Invariante compilador:** `ATOMC-E-031` si `application_id != null` y la Policy contenedora no declara `combining_algorithm`.

### Caso 2 — Rule Guardrail (`application_id: null`)

El Atom es una restricción transversal independiente de cualquier módulo. Actúa como pre-filtro antes de las Rules de módulo. No necesita Policy contenedora con `combining_algorithm`. Si varios Guardrails se agrupan en un PolicySet, ese PolicySet sí declara su propio `combining_algorithm`.

Equivalente en la industria: AWS **Service Control Policy (SCP)** / Permission Boundary — un guardrail global independiente de cualquier política de recurso específico.

```
Caso 1 — Rule de Aplicación:
  PolicySet
    └── Policy [application_id=7, combining_algorithm=deny-overrides]
          ├── Atom [payment_supplier_approve]
          ├── Atom [payment_supplier_reconcile]
          └── Atom [payment_supplier_void]

Caso 2 — Rule Guardrail (standalone):
  PolicySet
    └── Atom [application_id=null, payment_amount_threshold_check]

Caso 2 — Guardrails agrupados:
  PolicySet [combining_algorithm=deny-unless-permit]
    ├── Atom [application_id=null, payment_amount_threshold_check]
    └── Atom [application_id=null, horario_laboral_check]
```

Ver YAML completo de ambos casos y sus invariantes de compilador en [A.46 §3](anexos/A.46_ANEXO-ATOMLANG-GRAMATICA-COMPILADOR-v1.0.md).

### 8.2 Panorama de la industria 2026

Los lenguajes de autorización dominantes en IAM Enterprise hoy:

| Lenguaje / Sistema | Paradigma | Stack | Diferenciador |
|---|---|---|---|
| **Cedar** (Amazon) | Declarativo tipado, verificación formal | Rust | Verificación SMT — política estructuralmente correcta garantizada |
| **OPA / Rego** | Declarativo interpretado, Datalog-like | Go | Ecosistema CNCF amplio — Kubernetes, Envoy, Istio |
| **XACML 3.0** | XML estándar OASIS, extenso y formal | Java (mayoría) | Estándar de facto en gobierno, financiero, compliance |
| **Casbin** | Modelo PERM (Policy-Effect-Request-Matchers) | Go / multi-lenguaje | Ligero, embebible, sin servidor externo |
| **ALFA** | Sintaxis abreviada de XACML | Java (Axiomatic) | Legibilidad sobre XACML sin perder compatibilidad |
| **AWS IAM** | JSON declarativo, no formal | Propietario | Escala, SCP/Permission Boundaries, IAM Access Analyzer |

**Tendencia 2026:** Cedar gana tracción por verificación formal + base Rust. OPA domina cloud-native. XACML mantiene cuota en compliance regulatorio europeo (eIDAS 2.0). La verificación formal de política es la frontera del estado del arte.

### 8.3 Comparativa honesta — AtomLang vs. la industria

| Criterio | AtomLang | Cedar | OPA/Rego | XACML 3.0 |
|---|---|---|---|---|
| **Soberanía total** | ✅ Nativo, sin SaaS | ✅ Open source | ✅ Open source | ✅ Open source |
| **Base normativa** | XACML 3.0 + NIST 800-162 | Semántica formal propia | Datalog / Rego | OASIS XACML 3.0 |
| **Tipo de ejecución** | Compilado (YAML→IR) | Compilado (Cedar→IR) | Interpretado | XML + PDP |
| **Verificación formal** | ❌ No (L0) | ✅ SMT solver (Z3) | ❌ No | ❌ No |
| **Legibilidad admin** | ✅ YAML familiar | ✅ Legible (sintaxis propia) | ⚠️ Curva Datalog pronunciada | ❌ XML verboso y extenso |
| **Integración nativa bAuth** | ✅ Nativo: verb_id, set_id, domain, bitmask | ❌ Requiere adaptación total | ❌ Requiere adaptación total | ❌ Requiere adaptación total |
| **Madurez de implementación** | L0–L1 (especificado, no compilado) | L4 (AWS producción) | L4 (producción amplia) | L3 (maduro, en declive) |
| **Parametrización de valores** | ✅ `@bauth_config_param` (diseñado) | ✅ Context attributes | ✅ `input.*` | ✅ PIP externo |

**Diferenciadores irrenunciables de AtomLang:**
- Integración nativa con el modelo bAuth sin capas de adaptación — `verb_id` es la misma FK que usa el BitMask.
- La soberanía es total — el árbol, el compilador y el evaluador son parte del mismo daemon.
- `aggregate-strictest` resuelve el caso de step-up concurrente que los algoritmos XACML estándar no cubren.

**Donde la industria está por delante:**
- Cedar tiene verificación formal (ningún estado de política puede ser incorrecto lógicamente). AtomLang no tiene esto aún — es la brecha técnica más significativa.
- OPA tiene un ecosistema maduro de políticas reutilizables (rego-policies públicas). AtomLang parte de cero.

### 8.4 Brechas priorizadas P1/P2/P3

| Prioridad | Brecha | Norma que la exige | Impacto | Enfoque |
|---|---|---|---|---|
| **P1** | Compilador `atomc` no implementado — evaluador lee árbol fuente directamente | ISO 27001:2022 A.5.15 · NIST SP 800-162 §4.2 | Defectos D1–D6 de §2 llegan a runtime | Implementar `BauthAgent/tools/atomc/` en Rust |
| **P1** | `bos_atom_compiled` sin DDL aplicado | NIST SP 800-162 §4.2 (integridad de política) | Sin IR, sin separación Source/CANONICAL | Crear y aplicar migración `bauth_45__atomlang_compiled.sql` |
| **P2** | `bauth_config_param` sin DDL | NIST SP 800-162 §5 (gobernanza de atributos) | Valores de negocio hardcodeados en árbol | Diseñar DDL y PIP de resolución en runtime ([A.48](anexos/A.48_ANEXO-PARAMETRIZACION-BAUTH-CONFIG-PARAM-v1.0.md)) |
| **P2** | Sin linter en pre-commit/CI | ISO 27001:2022 A.8.9 (gestión de configuración) | Errores llegan a producción sin detección | Configurar git hook → `atomc lint` |
| **P3** | Sin verificación formal del lenguaje | Cedar formal verification (industria) | No hay garantía estructural de corrección lógica | Investigar SMT/Z3 aplicable al modelo bAuth |
