## 1. Audiencia, propósito y alcance

Este manual documenta el **sistema de atributos de identidad** de bAuth: la tabla genérica
`idn_atributo`, su jerarquía de clasificación, sus formatos de presentación y validación, su
integración con los catálogos globales `bglobal.*`, y su relación con el control de acceso
BitMask.

**Audiencia:** desarrolladores bAuth, administradores del Dashboard, diseñadores de DDL.

**Alcance:** los atributos **descriptivos** de identidad — lo que una entidad ES, TIENE o SABE
de forma estable. NO cubre políticas (`ath_policy_dN`), eventos (`audit_event`) ni el catálogo
de átomos (ver MANUAL-BITMASK). La distinción formal está en §11.3.

**Estado real:** el diseño está completo y aprobado a nivel de arquitectura
(`BAUTH-ARQUITECTURA-ATOMICA-FINAL.md` §2.4 lo incluye como tercera tabla de identidad).
El DDL formal está **pendiente de aprobación explícita** (ADR-016) — todo cambio en `DDLs/`
requiere HITL.

## 2. El problema — proliferación de tablas

### 2.1 El antipatrón "Tabla por Tipo"

El diseño original proponía 3 tablas específicas: `org_contacto`, `org_documento`,
`org_direccion`. Ese camino cae en el antipatrón **Tabla por Tipo**: cada nuevo atributo de
identidad exige una tabla nueva, una migración, un struct Rust, un CRUD, handlers JSON-RPC,
tests, seeds y documentación:

```
Nuevo tipo de dato "idioma"
         ↓
  Nueva tabla DDL          ← migración que aprobar y aplicar
  Nuevo struct Rust        ← struct Idioma { ... }
  Nuevo CRUD Rust          ← create/update/delete/list_idioma
  Nuevos handlers JSON-RPC ← bauth.actor.idioma.add/.remove/.list
  Nuevos tests + seeds + documentación
```

La lista de candidatos no termina nunca: idioma, educación, hobbie, certificación, red social,
referencia laboral, aplicación que domina… **El sistema se vuelve inmantenible** — cada tipo
multiplica el código.

### 2.2 Lo que el DDL actual ya usaba (y sus límites)

| Patrón existente | Dónde | Limitación |
|------------------|-------|-----------|
| JSONB en columna | `idn_user_template.template`, `org_empresa.metadata` | Sin queries granulares por atributo, sin validación por campo |
| Tablas parametrizadas | `ath_config_d1..d12`, `ath_policy_d1..d12` | Solo configuración/política — no datos de identidad |
| Jerarquía autorreferencial | `fis_location`, `menu_item` | Jerarquía fija, no extensible a tipos nuevos |

**No existía** ninguna tabla de atributos genérica. Las 3 tablas específicas fueron
**DESCARTADAS** antes de implementarse — reemplazadas por el diseño de este manual.

---

## 3. La solución — EAV jerárquico implícito

Una sola tabla expresa **5 niveles de jerarquía en columnas** (no en filas con `parent_id`):

```
entidad    → entidad_tipo + entidad_id   = "el actor Ana Flores"
categoría  → category                    = "profesional"
tipo       → attr_key                    = "idioma"
subtipo    → attr_subtype                = "inglés"
valor      → value_text + value_data     = "avanzado" + {nivel: B2, certif: TOEFL}
```

Sin JOINs, sin CTEs recursivas — las consultas son directas por índice compuesto:

```sql
-- Todos los emails de Ana:
SELECT * FROM bauth.idn_atributo
WHERE entidad_id = :ana_uuid AND category = 'contacto' AND attr_key = 'email';
```

El nombre lleva el prefijo `idn_` porque ISO 24760-2:2025 clasifica todos estos datos como
**identity attributes**, pertenezcan a una empresa (bDomain) o a una persona (actor).

## 4. La tabla `idn_atributo` — DDL

```sql
CREATE TABLE bauth.idn_atributo (
  id            UUID        NOT NULL DEFAULT gen_random_uuid(),

  -- Entidad propietaria del atributo
  entidad_tipo  TEXT        NOT NULL,   -- 'tenant'|'bdomain'|'bsubdomain'|'pos'|'actor'
  entidad_id    UUID        NOT NULL,   -- FK lógica (sin FK dura: múltiples tablas destino)

  -- Vínculo con el catálogo de privilegios (control BitMask) — OPCIONAL
  atom_code     INT,                    -- NULL = atributo libre · NOT NULL = controlado

  -- Clasificación jerárquica implícita (sin parent_id)
  category      TEXT        NOT NULL,   -- agrupación mayor (§5)
  attr_key      TEXT        NOT NULL,   -- tipo dentro de la categoría
  attr_subtype  TEXT,                   -- variante (work/home/español/MBA...)

  -- Valor (texto simple O estructura compleja — al menos uno presente)
  value_text    TEXT,
  value_data    JSONB,

  -- Presentación y validación (§6)
  display_format      TEXT,             -- código semántico: 'E164', 'TAX_BO', 'LOCALE_BCP47'...
  validation_policy   JSONB,            -- reglas que frontend Y backend aplican

  -- Calidad del valor
  is_primary    BOOLEAN     NOT NULL DEFAULT false,
  is_verified   BOOLEAN     NOT NULL DEFAULT false,
  verified_at   TIMESTAMPTZ,
  verified_by   TEXT,                   -- 'manual'|'api_sin'|'api_registro_civil'|'adsib'

  sort_order    SMALLINT    NOT NULL DEFAULT 0,
  created_at    TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at    TIMESTAMPTZ NOT NULL DEFAULT NOW(),

  CONSTRAINT pk_idn_atributo PRIMARY KEY (id),
  CONSTRAINT fk_idn_atributo_atom FOREIGN KEY (atom_code)
    REFERENCES bauth.privilege_atom(atom_code),
  CONSTRAINT ck_entidad_tipo CHECK (
    entidad_tipo IN ('tenant','bdomain','bsubdomain','pos','actor')),
  CONSTRAINT ck_valor_presente CHECK (
    value_text IS NOT NULL OR value_data IS NOT NULL)
);
```

**Los 4 índices** (cubren el 99% de las consultas de producción):

| Índice | Columnas | Para qué |
|--------|----------|----------|
| `ix_idn_atributo_entidad` | `(entidad_id, category, attr_key)` | La consulta principal: atributos de una entidad |
| `ix_idn_atributo_atom` | `(atom_code, entidad_tipo, entidad_id) WHERE atom_code IS NOT NULL` | Control de acceso BitMask |
| `ix_idn_atributo_data` | `GIN (value_data)` | Búsqueda dentro del JSONB estructurado |
| `ix_idn_atributo_valor` | `(attr_key, value_text)` | Búsqueda inversa: ¿de quién es este email? |

## 5. Jerarquía de clasificación — category → attr_key → attr_subtype

El catálogo es **por convención documentada** — no requiere tabla adicional. Las 6 categorías
base para D00:

| category | attr_key (ejemplos) | attr_subtype (ejemplos) | atom_code | Clasificación |
|----------|--------------------|-----------------------|:---------:|:-------------:|
| `contacto` | email | work, home, billing, legal, technical | 5813 | INTERNAL |
| `contacto` | telefono | mobile, work, whatsapp, fax, emergency | 5814 | INTERNAL |
| `contacto` | red_social | linkedin, github, telegram | — | PUBLIC |
| `documento` | id_nacional | CI, DNI, CC, DUI, CURP, CPF | 5826 | CONFIDENTIAL |
| `documento` | tributario | NIT, CUIT, RUT, CNPJ, RFC | 5812 | CONFIDENTIAL |
| `documento` | pasaporte | nacional, diplomatico | 5826 | CONFIDENTIAL |
| `ubicacion` | direccion | work, home, fiscal, registered, delivery | 5816 | INTERNAL |
| `ubicacion` | coordenadas | gps, what3words | — | RESTRICTED |
| `profesional` | idioma | español, inglés, aymara, quechua… | — | PUBLIC |
| `profesional` | educacion, certificacion, profesion, numero_matricula | libres | — | RESTRICTED/CONFIDENTIAL |
| `personal` | hobbie, habilidad, disponibilidad | libres | — | PUBLIC/RESTRICTED |
| `tecnologia` | aplicacion, lenguaje_prog, plataforma | SAP, Rust, AWS… | — | PUBLIC/INTERNAL |

Agregar una categoría nueva (por ejemplo `financiero` para D3, `dispositivo` para D7) **no toca
el DDL** — solo se documenta la convención y se insertan filas.

## 6. Formato y validación — display_format y validation_policy

Estos dos campos desacoplan la **presentación** y la **validación** del valor respecto del
esquema. El backend los almacena; el frontend los interpreta.

### 6.1 Dos niveles de nomenclatura

```
CÓDIGO UNIVERSAL  → estándar internacional, aplica a todos los países
                    E164, EMAIL, URL, DATE_ISO, PASSPORT_ICAO, MONEY, COORDENADAS_DD

CÓDIGO POR PAÍS   → documentos que cada país estructura a su manera
  ID_XX  → documento de identidad del país XX (ISO 3166-1 alpha-2): ID_BO, ID_AR…
  TAX_XX → documento tributario del país XX: TAX_BO (NIT), TAX_AR (CUIT), TAX_BR_CPF/TAX_BR_CNPJ
```

### 6.2 Integración con los catálogos globales `bglobal.*`

Los formatos dinámicos se resuelven contra los catálogos verificados en `SBOS_db` — ningún
agente hardcodea países ni monedas:

| Catálogo | Registros | Estándar | Uso |
|----------|:---------:|----------|-----|
| `bglobal.global_country` | 196 | ISO 3166-1 · ITU-T E.164 · UN M.49 | `COUNTRY_CODE`, prefijos E164, `ID_XX`/`TAX_XX` |
| `bglobal.global_language` | 125 | ISO 639-1/2/3 · IETF BCP 47 | `LOCALE_BCP47` (`es-BO`, `pt-BR`) |
| `bglobal.geo_timezone` | 319 | IANA tzdata | `TIMEZONE_IANA` (`America/La_Paz`) |
| `bglobal.global_currency` | 143 | ISO 4217 | `MONEY` (`Bs. 1.500,00`) |

**Principio de internacionalización:** el valor canónico en `value_text` siempre se almacena
en formato de intercambio (sin separadores visuales); el `display_format` determina cómo se
muestra según el país del tenant. Los átomos `nit` (5812), `telefono` (5814), `ci` (5815) y
`direccion` (5816) NO están hardcodeados para Bolivia.

### 6.3 `validation_policy` — la misma regla en frontend y backend

```json
{
  "regex": "^\\d{8,12}$",
  "min_length": 8,
  "max_length": 12,
  "checksum": "mod11",
  "catalog_fk": "bglobal.global_country.iso_alpha2"
}
```

El frontend la aplica como máscara de entrada (IMask.js en HTML · `flutter_multi_formatter` +
`reactive_forms` en Flutter); el backend la re-valida al persistir. Una sola fuente de verdad.

## 7. Regla de cardinalidad — columna vs atributo

```
Dato 1:1 por entidad, nunca se repite
  → columna directa en la tabla principal
  → ejemplos: bdomain.type, actor.gender, actor.locale, actor.timezone

Dato 1:N, o que admite múltiples instancias
  → fila en idn_atributo con category + attr_key + attr_subtype
  → ejemplos: emails, teléfonos, direcciones, documentos, idiomas, certificaciones
```

La prueba de escritorio con 10 casos reales (`ENSAYO-D00-PRUEBAS-ESCRITORIO.md`) demostró que
el modelo plano de columnas cubría entre el 20% y el 50% de los casos (Ana Flores con 4
teléfonos y 4 emails; Gabriel Romero con 3 documentos de 2 países; Banco Unión con 5 líneas),
mientras el modelo vertical con `idn_atributo` cubre el **100% de los 10 casos**.

## 8. Control de acceso — atributos controlados vs libres

### 8.1 Atributos controlados (`atom_code NOT NULL`)

El átomo D00 vinculado define qué roles ven o editan el dato, evaluado por BitMask. **El verbo
(ver/editar/crear/eliminar) vive en la estructura del átomo — los 4 bits de acción del
AtomBitMask (ver MANUAL-BITMASK §6) — NO se crean átomos separados por cada operación CRUD
de cada campo.** Esa fue la decisión de diseño (2026-07-10): el catálogo alterno de átomos
CRUD por campo quedó descartado; la dimensión verbo del átomo ya porta la operación.

```
email (atom_code=5813):
  → ver:    evaluar BitMask del átomo 5813 con verbo READ
  → editar: evaluar BitMask del átomo 5813 con verbo UPDATE

NIT (atom_code=5812):   solo BIZ_N2+ ve · solo BIZ_N1+ edita
Documentos (5826):      el actor ve los propios · BIZ_N3+ ve ajenos · BIZ_N2+ edita ajenos
```

### 8.2 Atributos libres (`atom_code IS NULL`)

Sin átomo vinculado, el acceso se rige por la **política de visibilidad de la categoría**,
verificada en los handlers JSON-RPC contra el tier del solicitante:

| Categoría | Visibilidad por defecto | Quién edita |
|-----------|------------------------|-------------|
| `contacto` | El actor ve los propios; su manager puede ver | El actor los propios; BIZ_N2+ los ajenos |
| `profesional` | PUBLIC dentro del tenant | El actor los propios |
| `personal` | Solo el actor | Solo el actor (excepto SU/SYS) |
| `tecnologia` | INTERNAL dentro del tenant | El actor los propios |

## 9. Auditoría dimensional

**Toda** operación sobre `idn_atributo` — con o sin `atom_code` — genera un `audit_event`
con las dimensiones completas (Autenticación Dimensional):

```
audit_event.atom_slug  = 'idn_atributo.profesional.idioma.crear'
audit_event.entidad_id = actor-uuid          (a quién pertenece el dato)
audit_event.actor_id   = quién lo insertó    (puede ser otro: un admin)
audit_event.ctx_id     = contexto activo     (SBOS-049)
audit_event.result     = Permitido | Denegado
```

Esto cubre GDPR Art. 15 (derecho de acceso: qué datos y quién los tocó) e ISO 27001 A.8.15.

## 10. Consultas típicas

```sql
-- Q1: Todos los emails de un actor (ordenados: primario primero)
SELECT attr_subtype, value_text, is_primary, is_verified
FROM bauth.idn_atributo
WHERE entidad_id=:actor_uuid AND category='contacto' AND attr_key='email'
ORDER BY is_primary DESC, sort_order;

-- Q4: Dirección fiscal de un bDomain (facturación SIN)
SELECT value_text, value_data FROM bauth.idn_atributo
WHERE entidad_id=:bdomain_uuid AND category='ubicacion'
  AND attr_key='direccion' AND attr_subtype='fiscal' LIMIT 1;

-- Q5: Todos los actores del tenant que conocen SAP
SELECT DISTINCT entidad_id FROM bauth.idn_atributo
WHERE entidad_tipo='actor' AND category='tecnologia'
  AND attr_key='aplicacion' AND value_text ILIKE 'SAP%';

-- Q7: Perfil completo agrupado por categoría (1 query, sin JOINs)
SELECT category, jsonb_agg(jsonb_build_object(
         'key',attr_key,'subtype',attr_subtype,
         'value',value_text,'data',value_data,'primary',is_primary)
       ORDER BY sort_order) AS atributos
FROM bauth.idn_atributo WHERE entidad_id=:actor_uuid
GROUP BY category ORDER BY category;
```

## 11. Cobertura de dominios D00–D12

### 11.1 `idn_atributo` sirve a TODOS los dominios

La tabla es el **repositorio universal de atributos descriptivos** del SBOS. Cada dominio
aporta nuevas `category` sin tocar el DDL:

| Dominio | ¿Aplica? | category | Ejemplos de attr_key |
|---------|:--------:|----------|---------------------|
| D00 Identidad Org. | ✅ caso principal | contacto, documento, ubicacion, profesional, personal, tecnologia | email, nit, direccion, idioma |
| D1 Lógico | ✅ parcial | acceso_logico | metodo_mfa_preferido, dispositivo_confiable |
| D2 Físico | ✅ parcial | acceso_fisico | zona_asignada, carne_acceso (RFID), vehiculo |
| D3 Financiero | ✅ parcial | financiero | cuenta_bancaria, centro_costo |
| D4 Temporal | ✅ parcial | temporal | disponibilidad, contrato_vigencia |
| D5 Geoespacial | ✅ (en ubicacion) | ubicacion | coordenadas, zona_geografica |
| D6 Biométrico | ✅ solo referencia | biometrico | template_ref → `ref://bionexus/...` (el binario NUNCA entra) |
| D7 Red | ✅ parcial | dispositivo | mac_address, certificado_cliente (mTLS) |
| D8 Contexto | ❌ no aplica | — | el ctx_id es dinámico — vive en Redis (SBOS-049) |
| D9 Delegación | ✅ parcial | delegacion | contacto_emergencia, apoderado_legal |
| D10/D11 Auditoría | ❌ / ✅ parcial | compliance | certificacion_iso, capacitacion GDPR |
| D12 Blockchain | ✅ referencia | blockchain | wallet_address, did (W3C) |

### 11.2 Principio de diseño — Atributo vs Política vs Evento

```
ATRIBUTO (idn_atributo)   → lo que la entidad ES/TIENE/SABE de forma estable.
                            Tiene display_format + validation_policy.
POLÍTICA (ath_policy_dN)  → reglas que el SISTEMA aplica SOBRE el actor.
                            Configuración de seguridad, no dato del actor.
EVENTO (audit_event)      → lo que OCURRE en un momento. Append-only (ISO 27001 A.8.15).
```

Si un dato cambia según la configuración de seguridad → es política. Si registra un hecho
temporal → es evento. Solo si describe establemente a la entidad → es atributo.

## 12. Rendimiento y particionamiento

El EAV tiene fama de lento; con PostgreSQL 18+ y los 4 índices correctos el impacto es mínimo
(estimaciones del diseño con 10 millones de filas):

```
Q1 (emails de un actor)  → ix_idn_atributo_entidad → < 1 ms
Q5 (buscar por app SAP)  → ix_idn_atributo_valor   → < 5 ms
Q7 (perfil completo)     → índice + aggregate       → < 10 ms
```

Si la tabla supera los 100 millones de filas, se particiona por `entidad_tipo` (LIST) sin
cambiar el código que la consume.

| Librerías frontend (IMask.js · flutter_multi_formatter) | ✅ documentadas | Ídem §11 |
| DDL aplicado en `SBOS_db` | ❌ | Pendiente aprobación ADR-016 (HITL) |

| 3 tablas específicas (org_contacto/documento/direccion) | 🗑️ descartadas | Reemplazadas por este diseño |

### 13.2 Lo que hace la industria en 2026

1. **SCIM 2.0 (RFC 7643/7644)** es el estándar de intercambio: esquema base de usuario +
   extensión Enterprise (employeeNumber, costCenter, organization, division, department,
   manager). En mayo de 2026 se publicaron **RFC 9967** (eventos SCIM vía Security Event
   Tokens) y **RFC 9944** (extensión de esquema para dispositivos). La práctica recomendada:
   exponer el endpoint `/Schemas` para que los clientes descubran atributos personalizados
   dinámicamente, y desaprovisionar con `active:false` (soft-delete), no con DELETE.
2. **Okta Universal Directory:** perfil base de 31 atributos estándar (SCIM Core) + atributos
   personalizados tipados definidos con un subconjunto de JSON Schema Draft 4 vía Profile
   Editor o Schema API. En 2026 añadió importación automática de esquemas desde servidores SCIM.
3. **NIST IR 8112 (Attribute Metadata):** define metadatos de esquema y de valor para cada
   atributo federado — origen, método de verificación, frescura, confianza — para que el
   consumidor decida autorización informada por riesgo. Es el fundamento conceptual de los
   campos `is_verified`/`verified_by`/`verified_at` de `idn_atributo`.
4. **eIDAS 2.0 — QEAA:** los atributos se convierten en **credenciales verificables**
   (Qualified Electronic Attestation of Attributes) — cualificaciones profesionales, roles
   corporativos, licencias — emitidas y verificadas criptográficamente vía EUDI Wallet.
   El atributo deja de ser una fila en una BD ajena y pasa a ser un documento firmado portable.

| Metadatos de verificación (NIST IR 8112) | ✅ verified_by/at | ⚠️ | ⚠️ | ❌ | ⚠️ |

| Atributos multi-entidad (empresa Y persona Y pos) | ✅ entidad_tipo | ❌ solo usuarios | ❌ | ❌ | ⚠️ User/Group |
| Interfaz SCIM estándar hacia afuera | ❌ gap | ✅ | ✅ | ✅ | ✅ |
| Atributos como credencial verificable (QEAA/VC) | ❌ gap (D13) | ❌ | ⚠️ Verified ID | ❌ | ❌ |

**Lectura honesta:** el diseño de bAuth es más expresivo que cualquier directorio comercial
(multi-entidad, formato por país, control BitMask por atributo). Su debilidad es de
implementación (DDL sin aplicar) y de interoperabilidad (sin fachada SCIM hacia clientes externos).

### 13.4 Brechas por prioridad

**P1 — Materializar el diseño:**

| Brecha | Enfoque |
|--------|---------|
| DDL de `idn_atributo` sin aplicar | Preparar migración + seed de convenciones → aprobación ADR-016 (HITL) |
| 4 handlers JSON-RPC genéricos | `bauth.atributo.add/.update/.remove/.list` — validan `validation_policy` + BitMask + auditan |
| Seeds de categorías de ejemplo | 10 casos del ensayo de escritorio como datos de prueba |

**P2 — Interoperabilidad:**

| Brecha | Enfoque |
|--------|---------|
| Fachada SCIM 2.0 (servidor) | Mapear `idn_atributo` → esquema SCIM Core + Enterprise; exponer `/Schemas` dinámico |
| Eventos de cambio de atributo (RFC 9967) | Emitir SET cuando cambia un atributo controlado |
| Verificación externa (`api_sin`, `api_segip`) | Conectores biedata para validar NIT/CI contra registros bolivianos |

**P3 — Futuro:**

- Atributos como credencial verificable (QEAA-like) — emitir attestation firmada de un atributo verificado (depende de D13)
- Metadatos NIST IR 8112 completos (confidence score, freshness) en `value_data`
