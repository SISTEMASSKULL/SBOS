## 1. Audiencia, propósito y alcance

Este es el **catálogo de referencia** de la superficie JSON-RPC de bAuth: todo método invocable por
el socket, agrupado por plano funcional, con su **naturaleza verificada** (¿consulta la BD? ¿es
lógica pura? ¿es declarativo?). Es el documento que un integrador (daemon hermano, SDK, frontend) o
un probador externo ([7.04](7.04_MANUAL-CLI-PRUEBAS-EXTERNAS-v1.0.md)) consulta para saber **qué
existe y qué esperar de cada llamada** — sin leer `main.rs`.

**Audiencia:** integradores de daemons SBOS, desarrolladores de SDK/frontend, el Testeador, auditores
de superficie de ataque.

**Alcance:** la referencia enumera y clasifica; **no** documenta el esquema de parámetros de cada
método (eso exigiría una especificación formal tipo OpenRPC — es la brecha R1, §17). Donde un manual
temático profundiza un plano, se enlaza.

## 3. Convención de invocación

Interface Dual (ADR-020): **el mismo método** se invoca por WebSocket RPC (humanos/CLI) o JSON-RPC
2.0 crudo (daemons), siempre sobre `/run/bos/bauth.sock` (0660, grupo `bosagent`) — nunca HTTP/TCP
entre daemons (SBOS-050 P9).

```bash
# Vía CLI (humano):
bauthctl policy eval 1 1 1

# Vía socket crudo (daemon / prueba):
printf '{"jsonrpc":"2.0","method":"bauth.policy.evaluate","params":{"app_code":1,"group_code":1,"atom_code":1},"id":1}\n' \
  | nc -U /run/bos/bauth.sock
```

**Reglas transversales:** toda operación con efecto lleva `ctx_id` (SBOS-049) · los errores son en
español · las respuestas son JSON-RPC 2.0 (`result` o `error`).

## 4. Leyenda de naturaleza

Clasificación **verificada** contando consultas `sqlx::` por archivo handler (evidencia §2 del
informe de consistencia):

| Símbolo | Naturaleza | Significado |
|:-------:|-----------|-------------|
| 🗄️ | **BD real** | El handler consulta/escribe PostgreSQL — estado vivo |
| ⚙️ | **Lógica pura** | Computa sin BD (criptografía, validación, evaluación en memoria) |
| 🔌 | **Delegado** | Reenvía a otro daemon/motor (bnotify, saga engine) |
| 📄 | **Declarativo** | Retorna JSON estático descriptivo — especificación, no ejecución |

## 14. ⚠️ Métodos escritos pero NO montados (huérfanos)

Hallazgo del vistazo (verificado: `grep role_lifecycle src/main.rs` → vacío): dos archivos handler
con lógica y BD **no tienen registro** en el dispatcher — existen como código, no como superficie:

| Archivo | Métodos que declara | Estado |
|---------|---------------------|--------|
| `role_lifecycle.rs` (13 consultas BD) | `bauth.role.{batch,bulk_assign,impact,lifecycle,rollback,search,temporal_assign}` — 7 métodos del ciclo de vida de roles (7 estados DEFINIDO→RETIRADO) | **Huérfano** — sin `dispatcher.register` |
| `domain_remaining.rs` (3 consultas BD) | handlers de dominios restantes sin strings de método propios | Sin registro detectado |

**Implicación:** el ciclo de vida de roles (asignación temporal, rollback, análisis de impacto) está
**escrito pero inaccesible** — nadie puede invocarlo. Es la clase de brecha opuesta a los `idp.*`
declarativos: aquí hay ejecución sin puerta. Registrado como **Q9** en el informe de consistencia;
montarlos es tarea de código (congelado).

## 17. Estado del arte, madurez y brechas

**Industria:** las plataformas IAM publican su superficie como especificación machine-readable
(OpenAPI en REST; **OpenRPC** para JSON-RPC) con esquemas de parámetros por método, generación de
clientes y *try-it*. bAuth tiene `bauth.debug.methods` (discovery de nombres) y este manual
(catálogo curado) — el paso de categoría es la especificación formal.

| Capacidad | Madurez | Nota |
|-----------|:-------:|------|
| Superficie registrada (~141) | **L3** | Mayoría 🗄️ BD real — sistema vivo, no maqueta |
| Naturaleza documentada | **L2→L3** | Este manual la fija con evidencia |
| Esquema formal por método (params/result) | **L1** | Solo implícito en el código de cada handler |
| Discovery | L2 | `debug.methods` lista nombres, sin esquemas |
| Gobierno de la superficie | L2 | Colisión y huérfanos detectados (R2/R3) |

### Brechas priorizadas

| # | Brecha | Prioridad |
|---|--------|:---------:|
| R1 | **Especificación OpenRPC** de la superficie (114+lotes) con esquema de params/result por método — habilita validación, clientes generados y try-it | **P1** |
| R2 | Montar los 7 métodos huérfanos de `role_lifecycle.rs` (§14) — el ciclo de vida de roles es funcionalidad IGA núcleo ([7.01](7.01_MANUAL-GOBERNANZA-IGA-v1.0.md)) | **P1** (código) |
| R3 | Resolver la **doble registración de `token.validate`** (token_validate.rs vs kong_oauth.rs) — el segundo registro pisa al primero silenciosamente; decidir el dueño único | P2 (código) |
| R4 | Gate de `bauth.debug.methods` en producción (¿requiere átomo de admin?) | P2 |
| R5 | Documentar params/result de los ~30 métodos más usados como anexo de este manual (mientras llega R1) | P3 |
