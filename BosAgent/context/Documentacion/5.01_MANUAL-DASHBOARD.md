## 1. Interface Dual (ADR-019/020)

```
/run/bos/bos.sock (0660, grupo bosagent)
  ├── Vía 1: WebSocket RPC → bosctl CLI, dashboard externo (bAuth)
  └── Vía 2: JSON-RPC 2.0 → daemons (bauth...), scripts, agentes IA
```

**Sin HTTP/TCP entre daemons** (SBOS-050 P9). El socket Unix es el ÚNICO canal. Toda la
información del BOS está disponible vía JSON-RPC para ser consumida por el dashboard de bAuth.
Cualquier feature nuevo sigue el patrón: `domain/<servicio>.go` → `server/jsonrpc.go` → `cmd/bosctl/<cmd>.go`.

### 2.1 Auth, timeouts, batch

- **Auth:** token compartido (`/etc/bos/rpc-token`) para métodos destructivos. Sin token → -32600.
- **Timeouts:** 5s lectura, 30s escritura, 600s sagas. `runWithTimeout` con canal buffer 1.
- **Batch:** `dispatchBatch` — goroutine por solicitud, orden preservado, notificaciones omitidas.
- **Errores:** -32001 (context expired), -32005 (not found), -32006 (timeout), -32007 (invalid state).

## 5. RBAC dual — FileRBAC y BauthRBAC

Todos los métodos JSON-RPC están protegidos por dos capas de autorización:

**Capa 1 — FileRBAC (`internal/security/filecheckroles.go`):**
Siempre activa. Lee `/etc/bos/rbac/roles.json` (paths.RBACRoles). No requiere bAuth.
Es el fallback de emergencia: si bAuth está caído, el BOS sigue siendo operable con
el administrador local.

```json
{
  "roles": {
    "admin": ["bos.ficha.*", "bos.bootstrap.*", "bos.tenant.*", "bos.k8s.*"],
    "operator": ["bos.ficha.status", "bos.ficha.list", "bos.ctx.*", "bos.capacity.*"],
    "monitor": ["bos.health.*", "bos.state.read", "bos.capacity.status", "bos.dashboard.*"]
  }
}
```

**Capa 2 — BauthRBAC (`internal/security/bauthroles.go`):**
Activa cuando bAuth está disponible (`/run/bos/bauth.sock` existe).
Evalúa el ctx_id del request contra los 12 dominios bAuth + RolTemplate del tenant.
Un método puede pasar FileRBAC y ser rechazado por BauthRBAC (política de tenant más restrictiva).

**Precedencia:** FileRBAC debe pasar PRIMERO. Si pasa, BauthRBAC es la segunda verificación.
Deny en cualquiera → error `-32003 Forbidden`.

| Método | FileRBAC mínimo | BauthRBAC |
|--------|----------------|-----------|
| `bos.ficha.install` | admin | D00=true, D02=true, LoA≥2 |
| `bos.tenant.create` | admin | D00=true, D08=true, LoA≥3 |
| `bos.ficha.status` | operator | D00=true |
| `bos.capacity.status` | monitor | D00=true |
| `bos.health.check` | (ninguno) | sin validación bAuth |

## 6. Domain Manager — `bos.web.domain.*`

Los 5 métodos del Domain Manager gestionan el ciclo de vida de los dominios web
multi-tenant del servidor S16-webserver (A.03).

| Método | Parámetros | Qué hace |
|--------|-----------|---------|
| `bos.web.domain.add` | `domain, tenant_id, empresa_id?, sucursal_id?` | INSERT T-415 + certbot + genera nginx conf + reload |
| `bos.web.domain.remove` | `domain` | Revoca SSL + elimina conf nginx + reload + T-415 soft-delete |
| `bos.web.domain.list` | `tenant_id?` | Lista dominios activos (todos o por tenant) |
| `bos.web.domain.resolve` | `domain` | O(1) lookup: dominio → tenant/empresa/sucursal (usado por Kong y website-engine) |
| `bos.web.domain.ssl_status` | `domain` | Estado del cert TLS: activo/expirando/vencido + días restantes |

**Tabla T-415 `bos.net_web_domain`** (pendiente de crear — A.03 §5.1 + plan Tarea I.6):
```sql
CREATE TABLE bos.net_web_domain (
    domain_id       UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    domain          TEXT UNIQUE NOT NULL,
    tenant_id       TEXT NOT NULL,
    empresa_id      TEXT,
    sucursal_id     TEXT,
    is_active       BOOLEAN NOT NULL DEFAULT true,
    ssl_provisioned BOOLEAN NOT NULL DEFAULT false,
    ssl_expires_at  TIMESTAMPTZ,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    ctx_id          TEXT NOT NULL
);
CREATE INDEX ON bos.net_web_domain (tenant_id);
```

**CLI:**
```bash
bosctl web domain add skull.sbos.app --tenant skull
bosctl web domain list --tenant skull
bosctl web domain ssl-status skull.sbos.app
bosctl web domain remove old.sbos.app
```
