## 1. Propósito y audiencia

**Audiencia:** operadores que desplegan SBOS en una VPS del cliente, y desarrolladores del
ecosistema que necesitan entender por qué `bosctl setup` puede ejecutarse cualquier número de
veces sin efecto destructivo.

**Propósito:** documentar el principio de idempotencia del instalador BOS — el comportamiento
que garantiza que un mismo comando produce siempre el estado deseado sin importar el estado
previo del servidor: limpio, parcialmente instalado, con errores, o con todo operativo.

**Alcance:** desde la descarga del paquete de GitHub hasta que el daemon BOS queda corriendo
con todas las fichas en estado `INSTALLED` o `PENDING` (en espera de sus dependencias). Cubre
la detección de estado, la bifurcación de caminos, los 7 pasos del deploy, y el comportamiento
del observer como garantía de convergencia continua. No cubre el desarrollo de fichas
individuales (3.01) ni el ciclo de vida de tenants post-deploy (1.03).

## 2. El principio de idempotencia — P15

**Definición (P15 — CLAUDE.md BosAgent):**

> El instalador BOS DEBE detectar si es instalación nueva o actualización. En actualización:
> nunca destruir fichas ni recursos instalados — solo revisar y actualizar.

La idempotencia no es una optimización — es una garantía de seguridad. Un instalador que
ejecuta `remove all → install fresh` en cada invocación es destructivo: borra datos del
cliente, borra configuraciones que tomaron horas ajustar, borra certificados TLS. El BOS
**nunca hace eso**.

**Invariante del instalador BOS:**

```
estado_final(bosctl setup, N veces) = estado_deseado(bos-install.toml + seed.yml)
```

Esta invariante se cumple sin importar:
- Si el servidor está completamente limpio (Ubuntu virgen)
- Si hay una instalación previa funcional
- Si la instalación anterior fue interrumpida (crash, corte de luz, error)
- Si hay fichas en error y otras funcionando correctamente

**Reglas irrenunciables del modo actualización:**

| Regla | Descripción |
|-------|-------------|
| **NO destructiva** | Nunca eliminar fichas instaladas, pods activos, datos ni configuraciones que funcionan |
| **Diff antes de actuar** | Calcular qué cambió entre estado actual y estado declarado antes de aplicar cualquier cambio |
| **Solo lo que cambió** | Aplicar únicamente los deltas — si una ficha está `INSTALLED` y su versión coincide, no tocarla |
| **Compensación por fallo** | Si un paso falla, la saga revierte SOLO ese paso — no hace rollback del sistema completo |
| **Dry-run obligatorio** | Antes de cualquier `kubectl apply` en modo update, ejecutar `--dry-run=server` y verificar el diff |
| **Backup obligatorio antes de update** | Toda ficha con datos persistentes DEBE ejecutar `ficha_backup()` antes de `ficha_update()` — sin backup confirmado, el update no procede |
| **Migración de esquema no destructiva** | Los DDL de update usan exclusivamente `ALTER TABLE ADD COLUMN IF NOT EXISTS`, `CREATE INDEX CONCURRENTLY IF NOT EXISTS`, `ALTER TABLE ADD CONSTRAINT IF NOT EXISTS` — **nunca `DROP COLUMN`, `DROP TABLE`, `TRUNCATE`** sin aprobación HITL explícita |
| **Volúmenes con `Retain`** | Todo PersistentVolume de ficha con datos usa `reclaimPolicy: Retain` — si el pod se borra por error, el volumen persiste y puede revincularse |
| **Configuraciones del cliente como inmutables** | Los archivos en `/etc/bos/`, `/var/lib/<ficha>/`, y los secretos en Vault **no se sobreescriben** en un update — solo se agregan claves nuevas o se actualizan claves que el propio BOS generó |

### Clasificación de fichas por riesgo de datos

El BOS clasifica cada ficha según el tipo de datos que custodia, y aplica un protocolo distinto en cada nivel:

| Nivel | Tipo de ficha | Ejemplos | Protocolo de update |
|:-----:|--------------|---------|---------------------|
| **D0 — Sin estado** | Fichas sin persistencia (reiniciables sin pérdida) | kong, nginx, certbot, bos-preflight | `kubectl rollout restart` + verify. Sin backup. |
| **D1 — Estado de configuración** | Fichas cuyo estado es solo configuración (recreable) | keycloak (sin datos de usuario), vault (sin secretos del cliente) | Backup del ConfigMap + Secret K8s antes de update |
| **D2 — Datos operativos** | Fichas con datos que el cliente puede recuperar desde otra fuente | redis (caché), minio (archivos replicados) | Backup snapshot + `kubectl drain` + update + verify + restore si falla |
| **D3 — Datos críticos irrecuperables** | Fichas cuya pérdida de datos es irrecuperable | **postgresql** (SBOSDB + BDs del cliente), **vault** (secretos Vault, AppRoles, PKI), bauth | **Protocolo completo de 5 fases** — ver §2.1 |

### 2.1 Protocolo completo para fichas D3 (datos críticos)

Las fichas clasificadas D3 siguen un protocolo de 5 fases obligatorio antes de aplicar cualquier
cambio de versión o configuración. **Saltarse una fase es una violación de soberanía** — los datos del
cliente son irrecuperables si el update falla sin backup.

```
FASE 1 — PRE-FLIGHT CHECK (antes de tocar nada)
  ├── Verificar espacio en disco suficiente para el backup (≥ 2× el tamaño del volumen)
  ├── Verificar que el pod está en estado Running y responde a health checks
  ├── Verificar que no hay transacciones activas de larga duración (para PG: pg_stat_activity)
  └── Si algún check falla → ABORT update, emitir alerta → HITL

FASE 2 — BACKUP VERIFICADO (obligatorio, con confirmación)
  Para PostgreSQL:
    pg_dumpall -U postgres > /var/backup/bos/sbosdb-pre-update-<timestamp>.sql
    sha256sum /var/backup/bos/sbosdb-pre-update-<timestamp>.sql > <...>.sha256
    # Verificar que el backup es legible (restore en BD temporal)
    psql -U postgres -d postgres < /var/backup/bos/sbosdb-pre-update-<timestamp>.sql --dry-run
  Para Vault:
    vault operator backup > /var/backup/bos/vault-pre-update-<timestamp>.snap
  Para Redis:
    redis-cli BGSAVE && cp /var/lib/redis/dump.rdb /var/backup/bos/redis-pre-update-<timestamp>.rdb
  
  → BOS registra el path + SHA256 del backup en .sbos_state.json antes de continuar
  → Si el backup falla → ABORT update → HITL

FASE 3 — DRAIN + UPDATE (cambio controlado)
  ├── kubectl drain <nodo> --ignore-daemonsets --delete-emptydir-data (si aplica)
  ├── kubectl apply --dry-run=server -f <nueva-spec.yml>  ← diff visible antes de aplicar
  ├── Aprobación HITL si el diff modifica:
  │     - Recursos del pod (CPU/RAM request/limit)
  │     - Variables de entorno con credenciales
  │     - PersistentVolumeClaim (cambio de storageClass o tamaño)
  ├── kubectl apply -f <nueva-spec.yml>
  └── kubectl rollout status <tipo>/<nombre> --timeout=600s

FASE 4 — MIGRACIÓN DE ESQUEMA (solo si hay cambios DDL)
  Para PostgreSQL:
    Aplicar solo scripts de migración incremental (formato: <version>__<descripcion>.sql)
    Usar exclusivamente:
      ALTER TABLE <tabla> ADD COLUMN IF NOT EXISTS <col> <tipo>;
      CREATE INDEX CONCURRENTLY IF NOT EXISTS <nombre> ON <tabla>(<col>);
      ALTER TABLE <tabla> ADD CONSTRAINT IF NOT EXISTS <nombre> ...;
    PROHIBIDO sin HITL explícita:
      DROP COLUMN, DROP TABLE, TRUNCATE, ALTER COLUMN TYPE (si hay datos)
  
  → BOS registra el script aplicado y su SHA256 en bos.ficha_event

FASE 5 — VERIFY + COMMIT (o rollback)
  ├── health check declarativo del manifest.yml (command/HTTP/TCP)
  ├── Smoke test funcional:
  │     PG: SELECT count(*) FROM bos.ctx_session;  ← debe retornar > 0
  │     Vault: vault status → sealed=false, initialized=true
  │     Redis: redis-cli PING → PONG
  ├── Verificar que los datos previos son accesibles (consulta básica sobre tabla existente)
  ├── Si todo OK → estado = INSTALLED, backup conservado por 7 días
  └── Si falla → rollback automático:
        kubectl apply -f <spec-anterior.yml>
        # Si el esquema fue migrado: aplicar script de rollback <version>__rollback.sql
        # Si el rollback también falla → estado = UNRECOVERABLE → HITL urgente
```

### 2.2 Configuraciones del cliente — regla de inmutabilidad

Las configuraciones que el operador o el cliente editaron manualmente son **sagradas**. El BOS
las trata como inmutables durante un update:

```
Archivos INMUTABLES durante update (el BOS NUNCA sobreescribe):
  /etc/bos/bos-install.toml              ← configuración por empresa (editada por operador)
  /etc/bos/bos.toml                      ← configuración del daemon (generada en primer arranque)
  /var/lib/<ficha>/config/               ← configuraciones locales de la ficha
  Secretos en Vault bajo secret/tenants/ ← secretos del cliente en Vault

Archivos que el BOS SÍ actualiza (los generó él mismo, puede regenerarlos):
  /etc/bos/certs/bos.crt + bos.key      ← renueva TLS si el cert expira en < 30 días
  /etc/bos/blibs/servers/               ← actualiza fichas con nueva versión del paquete
  /opt/bos/core/                         ← actualiza scripts Bash del motor
  /etc/systemd/system/bos.service        ← actualiza unidad systemd (previa aprobación HITL)
```

**Regla de merge para ConfigMaps y Secrets K8s:**

Cuando una ficha actualiza su ConfigMap, el BOS **fusiona** las claves en lugar de reemplazar:

```
ConfigMap existente:
  DB_HOST: "postgresql-0.postgresql"
  DB_PORT: "5432"
  CLIENT_CUSTOM_KEY: "valor-personalizado-del-cliente"  ← clave que agregó el operador

ConfigMap del update (nueva versión):
  DB_HOST: "postgresql-0.postgresql"
  DB_PORT: "5432"
  DB_POOL_SIZE: "20"  ← clave nueva en la versión actualizada

Resultado después del merge BOS:
  DB_HOST: "postgresql-0.postgresql"     ← preservada
  DB_PORT: "5432"                        ← preservada
  CLIENT_CUSTOM_KEY: "valor-..."         ← PRESERVADA (no viene en el update → no se toca)
  DB_POOL_SIZE: "20"                     ← AGREGADA (nueva en el update)
```

La fusión usa la estrategia `strategic merge patch` de kubectl para Deployments y StatefulSets,
y merge explícito (`kubectl get → jq merge → kubectl apply`) para ConfigMaps y Secrets.

## 3. Un solo comando, sin flags

El instalador BOS se invoca con un único comando:

```bash
bosctl setup
```

**No hay flags de modo.** El comando detecta automáticamente el estado del servidor y toma
la decisión correcta. El operador no necesita saber si está en instalación inicial o
actualización — el BOS lo determina.

```
bosctl setup
    │
    ├── Detecta estado del servidor
    │     ├── K8s limpio + sin estado → CAMINO A (instalación inicial)
    │     └── K8s instalado / BOS activo → CAMINO B (observer + idempotencia)
    │
    ├── Si hubo instalación interrumpida → limpia estado zombie antes de continuar
    │
    └── En ambos caminos:
          ├── Fichas ya instaladas y sanas → pasan (no se tocan)
          ├── Fichas con errores → se reparan
          └── Fichas faltantes → se instalan
```

Este diseño refleja cómo funciona cualquier gestor de paquetes maduro (apt, dnf, brew): el
operador declara lo que quiere, el sistema converge al estado deseado sin importar el punto
de partida.

## 4. Cómo se obtiene el paquete — clonación desde GitHub

El instalador BOS se obtiene clonando el repositorio oficial de SKULL directamente en el
servidor donde se va a instalar. El repositorio **es** el instalador — no hay pasos de
extracción ni compilación: los binarios ya vienen incluidos.

```bash
# Clonar el repositorio instalador en el servidor del cliente
git clone https://github.com/SISTEMASSKULL/bos-install.git
cd bos-install

# El instalador trabaja desde el directorio donde fue clonado
# No se necesita moverlo ni copiarlo a ningún otro lugar
```

Una vez clonado, **el operador edita la configuración del cliente antes de lanzar el
instalador**. Este es el único paso manual del proceso:

```bash
# 1. Editar los datos de la empresa
nano bos-install.toml

# 2. Editar los datos del tenant e infraestructura
nano seed-skull.yml

# 3. Lanzar el instalador — el BOS valida la configuración antes de instalar
sudo ./bosctl setup
```

### 4.1 Validación obligatoria del `bos-install.toml` antes de instalar

`bosctl setup` **no arranca la instalación hasta verificar que `bos-install.toml` es válido
y completo**. Esta verificación es el primer acto del comando — antes de copiar binarios, antes
de crear directorios, antes de tocar el sistema operativo.

El objetivo es evitar instalaciones que arrancan, consumen 40 minutos desplegando K8s y
PostgreSQL, y fallan al final porque `client_domain` estaba vacío o `admin_password` tenía el
valor de la plantilla.

**Campos obligatorios que el validador verifica:**

```toml
# bos-install.toml — campos que el validador exige completados

[general]
client_domain = "empresa.sbos.local"   # OBLIGATORIO — no puede ser vacío ni el valor del template
org_name      = "Empresa S.A."         # OBLIGATORIO — nombre legal de la organización
org_short     = "empresa"              # OBLIGATORIO — slug técnico (solo [a-z0-9-], sin espacios)
server_ip     = "192.168.1.100"        # OBLIGATORIO — IP real del servidor (no 0.0.0.0 ni localhost)
timezone      = "America/La_Paz"       # OBLIGATORIO — zona horaria IANA válida
country       = "BO"                   # OBLIGATORIO — código ISO 3166-1 alpha-2
language      = "es"                   # OBLIGATORIO — código BCP-47

[security]
admin_password = "mi-password-segura"  # OBLIGATORIO — no puede ser el valor del template
                                       # ni tener menos de 12 caracteres
```

**Reglas de validación aplicadas:**

| Campo | Regla | Rechazo si… |
|-------|-------|-------------|
| `client_domain` | Formato FQDN válido | vacío · contiene espacios · igual al template (`"skull.sbos.local"`) |
| `org_name` | No vacío, ≥ 3 caracteres | vacío · igual al template (`"SKULL SISTEMAS SRL"`) |
| `org_short` | Solo `[a-z0-9-]`, ≤ 20 chars | contiene mayúsculas · espacios · caracteres especiales |
| `server_ip` | IPv4 válida, no loopback, no 0.0.0.0 | `127.0.0.1` · `0.0.0.0` · formato inválido |
| `timezone` | Zona IANA válida | valor no existe en la base de datos tz |
| `country` | Código ISO 3166-1 alpha-2 | código inválido · más de 2 caracteres |
| `admin_password` | ≥ 12 caracteres, no igual al template | igual a `"cambiar-esto"` · `""` · < 12 chars |

**Flujo de validación en `bosctl setup`:**

```
bosctl setup
    │
    ├── PASO 0: Validar bos-install.toml  ← ANTES de tocar el sistema
    │     ├── ¿Existe el archivo?
    │     │     No → buscar en el paquete clonado
    │     │           No → ERROR: "bos-install.toml no encontrado — ejecutar desde el directorio del repositorio"
    │     │
    │     ├── ¿Es legible como TOML válido?
    │     │     No → ERROR: "bos-install.toml tiene error de sintaxis en línea N: <detalle>"
    │     │
    │     ├── ¿Todos los campos obligatorios están presentes?
    │     │     No → ERROR: "campos faltantes: [client_domain, admin_password]"
    │     │
    │     ├── ¿Todos los campos pasan las reglas de validación?
    │     │     No → ERROR por campo con descripción exacta de qué corregir
    │     │
    │     └── ¿Los valores son los del template sin modificar?
    │           Sí → ERROR: "bos-install.toml contiene valores del template — editar con datos reales del cliente"
    │
    └── Solo si TODAS las validaciones pasan:
          Continuar con la detección de estado + instalación
```

**Ejemplo de salida cuando la validación falla:**

```
bosctl setup — validando configuración...

  ✗ bos-install.toml: campo [general].org_short inválido
    Valor actual: "Empresa S.A."
    Problema: contiene caracteres no permitidos (espacios, mayúsculas, puntos)
    Corrección: usar solo letras minúsculas, números y guiones. Ejemplo: "empresa-sa"

  ✗ bos-install.toml: campo [security].admin_password contiene valor del template
    Valor actual: "cambiar-esto"
    Corrección: establecer una contraseña segura de al menos 12 caracteres

Instalación cancelada — corregir bos-install.toml y volver a ejecutar bosctl setup
```

**Ejemplo de salida cuando la validación pasa:**

```
bosctl setup — validando configuración...

  ✓ bos-install.toml válido
      Organización : Empresa S.A. (empresa-sa)
      Dominio      : empresa.sbos.local
      Servidor     : 192.168.1.100
      Zona horaria : America/La_Paz
      País         : BO

Iniciando instalación...
```

**El repositorio es autocontenido.** Todo lo que el instalador necesita viene dentro del
repositorio clonado: los binarios `bos` y `bosctl` (Go estático, CGO_ENABLED=0), los scripts
`core/`, las 156 fichas declarativas `servers/`, los DDLs, y las plantillas de configuración.

**Sin conexión a internet durante la instalación.** Una vez clonado el repositorio, el
instalador opera completamente offline. Esto es soberanía: el servidor del cliente no necesita
acceso a internet para instalar ni para operar.

## 6. Detección del estado del servidor — la decisión bifurcada

El primer acto de `bosctl setup` es leer el estado actual del servidor. Esta lectura determina
qué camino tomar:

```
cmdSetup() — cmd/bosctl/install_ui.go
│
├── 1. Leer .sbos_state.json
│     ├── No existe → servidor limpio (instalación nueva)
│     ├── Existe sin fichas instaladas → estado inicial válido
│     └── Existe con fichas → comprobar estados
│           ├── INSTALL_FAILED / UPDATE_FAILED / UNRECOVERABLE → detectado como fallo
│           ├── INSTALLING / UPDATING / REPAIRING → zombie (proceso interrumpido)
│           └── INSTALLED / PENDING / READY → instalación previa válida
│
├── 2. Verificar si el daemon responde en el socket
│     isDaemonAlive("/run/bos/bos.sock")
│     ├── No responde → daemon no está corriendo
│     └── Responde → daemon activo
│
└── 3. Bifurcación:
      ├── Fichas zombie → limpiar estado + reiniciar instalación
      └── Daemon activo con fichas OK → CAMINO B (observer)
          Daemon inactivo / servidor limpio → CAMINO A (instalación inicial)
```

**La detección de zombies** (`detectFailedInstall` en `install_ui.go`):

```go
// Estados que indican instalación interrumpida o fallida:
badStates := map[string]bool{
    "INSTALL_FAILED": true,  // falló definitivamente
    "UPDATE_FAILED":  true,  // actualización fallida
    "UNRECOVERABLE":  true,  // fallo sin recuperación
    "INSTALLING":     true,  // proceso fue interrumpido (zombie)
    "UPDATING":       true,  // zombie
    "REPAIRING":      true,  // zombie
}
```

Cuando se detectan zombies, el instalador limpia el estado y arranca de cero:
1. Detiene `bos.service` y `bos-console.service`
2. Elimina el socket residual (evita conexiones a daemon muerto)
3. Elimina el token RPC (el daemon regenera uno nuevo en el próximo arranque)
4. Borra `.sbos_state.json` (el deploy del seed restablece los estados correctos)

## 7. Camino A — Instalación inicial (servidor limpio)

Cuando el servidor está limpio (Ubuntu 26.04 virgen, sin K8s, sin BOS), `bosctl setup`
ejecuta la instalación completa desde cero en 3 fases secuenciales:

### Fase 1 — system-install (preparación del host)

Invocado internamente por `cmdSetup` → `cmdSystemInstall`:

```
Paso 1: binarios    → copia bos/bosctl a /opt/bos/bin/ + symlinks /usr/local/bin/
Paso 2: core        → copia scripts Bash core/ a /opt/bos/core/
Paso 3: blibs       → copia servers/ (156 fichas) a /etc/bos/blibs/servers/
Paso 4: ddls        → copia DDLs a /etc/bos/ddls/ (SBOS_db_V2_DDL.sql + seeds)
Paso 5: env         → copia bos-install.toml del paquete a /etc/bos/bos-install.toml
                      (nunca sobreescribe si ya existe — preserva configuración del operador)
Paso 6: servicios   → instala bos.service + bos-console.service en systemd + systemctl enable
Paso 7: preflight   → ejecuta ficha bos-preflight:
                      crea usuario bosagent, directorios /etc/bos/ /var/log/bos/ /run/bos/,
                      genera TLS autofirmado, configura cgroups, verifica RAM/CPU/disco
```

**Resultado:** el sistema operativo está listo para correr el daemon. Aún no hay K8s.

### Fase 2 — arranque del daemon

```bash
systemctl start bos.service
# Espera hasta 30s que el daemon responda en /run/bos/bos.sock
# El daemon carga 156 fichas → todas en estado PENDING
```

**El daemon en su primer arranque** (`cmd/bos/run_normal.go`):
- Lee `bos.toml` y `bos-install.toml` desde `/etc/bos/`
- Escanea `servers/` → registra 156 fichas, todas en estado `PENDING`
- Arranca el observer loop (no instala nada aún — espera el deploy)
- Expone el socket `/run/bos/bos.sock` (Interface Dual: WebSocket + JSON-RPC 2.0)
- Levanta la Context API en `0.0.0.0:9443` (TLS 1.3)

### Fase 3 — deploy (saga completa)

Ver sección 9 para los 7 pasos detallados.

## 8. Camino B — Observer continuo (K8s ya instalado)

Cuando el daemon BOS ya está corriendo con fichas instaladas, `bosctl setup` **no reinstala
nada**. En cambio:

```
bosctl setup
    │
    └── isDaemonAlive("/run/bos/bos.sock") → true
          │
          ├── Leer .sbos_state.json
          │     ├── Fichas INSTALLED → verificar versión vs declarada
          │     │     ├── Versión coincide + health OK → SKIP (no tocar)
          │     │     ├── Versión diferente → planificar update
          │     │     └── Health degradado → planificar repair
          │     │
          │     ├── Fichas PENDING → instalar (nunca fueron instaladas)
          │     └── Fichas INSTALL_FAILED → repair automático
          │
          └── cmdDeploy(seed.yml) — ejecuta los 7 pasos en modo idempotente
                Cada paso verifica si ya está hecho antes de ejecutar
```

**Comportamiento del deploy en modo idempotente:**

| Estado de la ficha | Acción del deploy |
|-------------------|------------------|
| `INSTALLED`, versión correcta, health OK | `SKIP` — no se toca |
| `INSTALLED`, versión diferente | `UPDATE` — solo los recursos que cambiaron |
| `PENDING` | `INSTALL` — primera instalación |
| `INSTALL_FAILED` | `REPAIR` — intenta recuperar sin destruir |
| `DEGRADED` | `REPAIR` — converge al estado deseado |

## 9. Los 7 pasos del deploy — saga con compensación

`cmdDeploy` en `cmd/bosctl/deploy.go` ejecuta los 7 pasos en secuencia estricta. Cada paso
invoca al daemon BOS vía JSON-RPC (`bos.ficha.install`) — el daemon ejecuta el
`task_catalog.sh` de la ficha correspondiente. **El operador no ejecuta ningún comando manual.**

```
PRE: genera bos-bootstrap.env desde seed.yml
     (variables de entorno para los scripts Bash de cada ficha)

PASO 0 — Kubernetes
  bos.ficha.install "sbos-bootstrap-k8s"
  Instala: kubeadm v1.32.x + Calico 3.28 + CRI-O + kubectl
  Tiempo estimado: ~15 min (descarga de imágenes + init cluster)
  Idempotente: si kubeconfig existe y cluster responde → SKIP

PASO 1 — Namespace K8s
  bos.ficha.install "sbos-namespace"
  Crea: namespace del tenant + NetworkPolicy deny-all + ResourceQuota
  Idempotente: kubectl apply --dry-run=server antes de aplicar

PASO 1.5 — Storage
  bos.ficha.install "sbos-bootstrap-storage"
  Crea: StorageClass local + PersistentVolumes con Retain policy
  Idempotente: verifica si PV existe antes de crear

PASO 2 — PostgreSQL 18.4
  bos.ficha.install "postgresql"
  Despliega: StatefulSet postgresql-0 + Service ClusterIP 10.96.100.10
  Idempotente: si pod postgresql-0 está Running → SKIP install

PASO 2.5 — DDL en SBOSDB
  kubectl exec -i postgresql-0 -- psql -U postgres < SBOS_db_V2_DDL.sql
  Aplica: esquema completo (~170 tablas) + seeds iniciales
  Idempotente: DDL usa CREATE TABLE IF NOT EXISTS + INSERT ON CONFLICT DO NOTHING

PASO 3 — Redis 8.6.2
  bos.ficha.install "redis"
  Idempotente: si Deployment redis-0 está Running → SKIP

PASO 4 — Vault 2.0.1
  bos.ficha.install "vault"
  Inicializa: Shamir 5/3, crea paths AppRole por ficha, PKI
  Idempotente: si vault status = sealed → unseal; si initialized → SKIP init

PASO 5 — Keycloak 26.6.2 + Realm
  bos.ficha.install "keycloak"
  Crea: realm del tenant + SPIs de bauth + client SBOS
  Idempotente: kcadm.sh get realms verifica existencia antes de crear

PASO 6 — Context Plane
  bos.ctx.auto_migrate (JSON-RPC al daemon)
  Crea: índices Redis DB1 por tenant + tablas bos schema en SBOSDB
  Idempotente: CREATE INDEX IF NOT EXISTS + INSERT ON CONFLICT DO NOTHING

PASO 7 — Fichas del tenant en orden topológico
  Para cada ficha en seed.yml["fichas"]:
    bos.ficha.install "<nombre_ficha>"
  El DEPENDENCY_RESOLVER (Kahn) calcula el orden — fichas sin dependencias entre sí
  se instalan en oleadas paralelas
```

**Compensación por fallo:**

Si un paso falla (pasos 0-5 = infraestructura base):
- La saga activa la compensación del paso fallido específico
- Los pasos anteriores que completaron **no se revierten** (no hay `remove all`)
- El siguiente `bosctl setup` detecta el estado, omite lo que está bien, y reintenta solo lo que falló

Si falla una ficha del tenant (paso 7):
- Queda en estado `INSTALL_FAILED`
- El observer loop la reintenta automáticamente en Day 1
- No afecta las otras fichas ya instaladas

## 10. Comportamiento idempotente por cada paso

### Paso 0 — Kubernetes

```bash
# task_catalog.sh de sbos-bootstrap-k8s
ficha_install() {
    # Verificar si K8s ya existe antes de instalar
    if kubectl cluster-info &>/dev/null; then
        echo "${__SBOS__STEP_SKIP__} install — K8s ya operativo"
        return 0
    fi
    echo "${__SBOS__STEP_START__} install"
    kubeadm init --config /etc/bos/kubeadm-config.yml
    # Instalar Calico CNI
    kubectl apply -f /etc/bos/blibs/servers/S00-hostserver/sbos-bootstrap-k8s/resources/calico.yml
    echo "${__SBOS__STEP_OK__} install"
}
```

### Paso 2 — PostgreSQL

```bash
ficha_install() {
    # Si el pod ya está corriendo, SKIP
    if kubectl get pod postgresql-0 -n "${SBOS_NAMESPACE}" 2>/dev/null | grep -q Running; then
        echo "${__SBOS__STEP_SKIP__} install — postgresql-0 ya corriendo"
        return 0
    fi
    echo "${__SBOS__STEP_START__} install"
    kubectl apply -f "${SBOS_FICHA_DIR}/postgresql.k8s.yml" -n "${SBOS_NAMESPACE}"
    kubectl wait --for=condition=Ready pod/postgresql-0 -n "${SBOS_NAMESPACE}" --timeout=600s
    echo "${__SBOS__STEP_OK__} install"
}
```

### Paso 2.5 — DDL

El DDL usa convenciones PostgreSQL estándar para idempotencia:

```sql
-- Toda tabla con IF NOT EXISTS
CREATE TABLE IF NOT EXISTS bos.ctx_session (
    id UUID DEFAULT uuidv7() PRIMARY KEY,
    ...
);

-- Toda inserción con ON CONFLICT DO NOTHING
INSERT INTO bos.ctx_session (id, tenant_id, ...) VALUES (...)
ON CONFLICT (id) DO NOTHING;

-- Todo índice con IF NOT EXISTS
CREATE INDEX IF NOT EXISTS idx_ctx_session_tenant ON bos.ctx_session(tenant_id);
```

Resultado: el DDL puede aplicarse 100 veces — el resultado es siempre el mismo esquema.

## 11. El observer loop — convergencia continua

Una vez completado el deploy, el daemon BOS entra en modo observer permanente. Este loop es el
**corazón del Day 2**: garantiza que el sistema siempre converge al estado declarado en
`manifest.yml`, sin intervención humana.

```
Observer loop (internal/observer/) — ciclo cada 60s
│
├── Para cada ficha en .sbos_state.json:
│     │
│     ├── PENDING → verificar dependencias
│     │     ├── Dependencias satisfechas → transición a READY → instalar
│     │     └── Dependencias pendientes → esperar (no bloquear otras fichas)
│     │
│     ├── INSTALLED → health check declarativo (manifest.yml → health.check)
│     │     ├── Health OK → mantener INSTALLED
│     │     └── Health falla 3 veces consecutivas → DEGRADED → REPAIRING → repair
│     │
│     ├── DEGRADED → reparar con ficha_repair()
│     │     ├── Repair OK → INSTALLED
│     │     └── Repair falla 3 reintentos → UNRECOVERABLE → HITL
│     │
│     └── INSTALL_FAILED → reintentar ficha_install()
│           ├── Install OK → INSTALLED
│           └── Install falla → mantener INSTALL_FAILED (log detallado)
│
└── Reconciliación cada 15min:
      Comparar estado declarado (manifest.yml) vs estado real (kubectl / ps / Redis / PG / Vault)
      SHA-256 por archivo de configuración → detectar drift
      Drift detectado → repair automático
```

**Fichas con `auto_install: false`:**

Algunas fichas opcionales del catálogo tienen `auto_install: false` en su `manifest.yml`. El
observer las registra como `PENDING` pero no las instala automáticamente — esperan activación
explícita por `bosctl ficha install <nombre>` o HITL (Human-In-The-Loop).

Ejemplos: fichas opcionales como `frappe`, `moodle`, `openproject` — aplicaciones de negocio
que el cliente activa según sus necesidades, no parte del stack base.

## 12. Gestión de errores — corrección sin destruir

**Principio:** cuando algo falla, el BOS corrige **solo eso** — nunca reinstala todo.

```
Error en ficha postgresql durante update
    │
    └── Estado: UPDATING → UPDATE_FAILED
          │
          ├── Saga registra el paso fallido
          ├── Compensa SOLO ese paso (rollback del StatefulSet al spec anterior)
          └── Las fichas que dependen de postgresql:
                redis → no afectada (sigue INSTALLED)
                vault → no afectada (sigue INSTALLED)
                keycloak → no afectada (sigue INSTALLED)
```

**Anti-patrón que el BOS NUNCA hace:**

```
❌ Error en postgresql → remove all → install fresh
   Resultado: se borran los datos del cliente, los secretos de Vault,
              los contextos activos de Redis, los tokens de Keycloak.
              Esto es inaceptable.

✅ Error en postgresql → repair postgresql solamente
   Resultado: los datos permanecen intactos, el resto del stack
              sigue operativo mientras se repara postgresql.
```

**Manejo de interrupciones:**

Si el servidor se apaga durante la instalación (corte de luz, reboot accidental), el estado
de las fichas que estaban en `INSTALLING` queda como zombie. En el próximo `bosctl setup`:

1. `detectFailedInstall` detecta los estados zombie
2. Limpia el state file
3. Reinicia `system-install` si el daemon no está corriendo
4. Ejecuta el deploy en modo idempotente — las fichas que completaron se omiten, las zombies
   se reinstalan

## 13. Los dos archivos de configuración del tenant

El instalador BOS utiliza **dos archivos de configuración complementarios**, con propósitos
distintos y separados intencionalmente:

### bos-install.toml — configuración por empresa

```toml
# bos-install.toml — datos específicos del cliente
# Editado por el operador ANTES de ejecutar bosctl setup

[general]
client_domain = "empresa.sbos.local"  # dominio base SBOS
org_name = "Empresa S.A."              # nombre legal
org_short = "empresa"                  # slug corto (slug técnico)
server_ip = "192.168.1.100"           # IP del servidor
timezone = "America/La_Paz"
country = "BO"
language = "es"

[security]
admin_password = "cambiar-esto"        # contraseña admin bootstrap (temporal)
mfa_enabled = true
```

**Quién lo lee:** los scripts Bash de cada ficha (`task_catalog.sh`) a través de
`core/00_MASTER_INSTALL_SBOS.sh`, que lo parsea y exporta cada variable como `BOS_DOMAIN`,
`BOS_ORG_NAME`, `SBOS_ADMIN_PASSWORD`, etc.

**Persistencia:** se copia a `/etc/bos/bos-install.toml` en el paso `env` de `system-install`.
Si el archivo ya existe en `/etc/bos/`, **nunca se sobreescribe** — preserva la configuración
del operador incluso en reinstalaciones.

### seed-skull.yml — datos del tenant e infraestructura

```yaml
# seed-skull.yml — datos del tenant para el deploy Go
enterprise_tenant:
  legal_name: "Empresa S.A."
  jurisdiction_of_registration: "BO"
  domain: "empresa.sbos.local"

identity:
  realm: "empresa"
  display_name: "Empresa Sistemas"
  sso_session_max: "8h"

infrastructure:
  domain_id: "empresa-main"
  network_policy: "deny-all"

databases:
  engine: "postgresql"
  version: "18.4"
  cluster_ip: "10.96.100.10"

vault:
  version: "2.0.1"
  shamir_keys: 5
  shamir_threshold: 3

fichas: []  # fichas opcionales a instalar además del stack base
```

**Quién lo lee:** `cmdDeploy` en Go — los 7 pasos del deploy usan estos valores para crear el
namespace K8s, configurar el realm Keycloak, crear los paths en Vault, y determinar qué fichas
opcionales instalar en el paso 7.

### Relación entre ambos archivos

```
bos-install.toml ──→ Bash (scripts de fichas, 00_MASTER_INSTALL_SBOS.sh)
                      Variables del entorno empresarial: dominio, org, IP, idioma

seed-skull.yml ────→ Go (cmdDeploy, deploy.go)
                      Datos del tenant: realm, namespace K8s, BD, Vault, fichas

Ambos son necesarios. Ambos son complementarios. Ninguno reemplaza al otro.
```

## 14. Estado del arte — comparación con la industria

| Aspecto | Terraform / Ansible | ArgoCD / Flux | **BOS (SBOS)** |
|---------|---------------------|---------------|-----------------|
| **Comando de instalación** | `terraform apply` / `ansible-playbook` | `argocd app sync` | `bosctl setup` |
| **Detección de estado previo** | Manual (`--refresh-only`) | Automática (controller) | **Automática (daemon permanente)** |
| **Idempotencia** | Parcial (depende del provider) | Sí (K8s reconcile) | **Sí (todas las fichas)** |
| **Instalación inicial = actualización** | No (flujos separados) | Parcialmente | **Sí — mismo comando** |
| **Corrección sin destruir** | No garantizado | Sí (K8s desafina diff) | **Sí (compensación por paso)** |
| **Bootstrap del SO** | No (prerequisito manual) | No | **Sí (Ubuntu virgen → K8s + stack)** |
| **Configuración por cliente** | Variables `.tfvars` / inventario Ansible | `values.yaml` Helm | **`bos-install.toml` + `seed.yml`** |
| **Operación offline** | Parcial (depende del registry) | No | **Sí (100% autocontenido)** |
| **Day 2 autónomo** | No | Sí (sync periódico) | **Sí (observer 60s + reconciliación 15min)** |
| **Multi-tenant** | No nativo | Limitado | **Nativo (namespace + bauth + Vault por tenant)** |

**El diferenciador crítico:** ninguna de las herramientas de la industria combina bootstrap del
SO desde cero + idempotencia total + operación offline + Day 2 autónomo + multi-tenant nativo en
un solo binario con un solo comando. El BOS es la única herramienta que hace todo esto.
