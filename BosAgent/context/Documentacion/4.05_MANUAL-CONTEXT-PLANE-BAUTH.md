## 1. BOS como Policy Administrator (NIST SP 800-207)

En la arquitectura Zero Trust del SBOS, el BOS cumple el rol de **Policy Administrator (PA)**:
establece y termina sesiones de acceso, emite y revoca ctx_id, coordina con el PE (bAuth)
y comunica las decisiones al PEP (Kong).

```
┌─────────────┐   request   ┌──────────┐  validar ctx_id  ┌─────────────┐
│  Cliente    │────────────▶│  Kong    │────────────────────▶│    BOS     │
│  (usuario)  │             │  (PEP)   │   ← allow/deny ──  │    (PA)    │
└─────────────┘             └──────────┘                     └─────┬──────┘
                                                                   │ bos.ctx.resolve
                                                                   ▼
                                                            ┌─────────────┐
                                                            │   bAuth     │
                                                            │   (PE)      │
                                                            │ 12 dominios │
                                                            └─────────────┘
```

## 2. Flujo completo bos.ctx.resolve

```
BOS recibe bos.ctx.resolve(ctx_id)
  1. Lookup Redis DB1: clave "bos:ctx:resolve:<ctx_id>" TTL 30s
     → HIT: retorna DomainResult cacheado (P99 < 2ms)
     → MISS: continúa
  2. Verifica ctx_id activo en Redis DB1 (no expirado, no revocado)
     → Si no activo: ErrContextExpired (-32001)
  3. Invoca bauth.context.evaluate sobre /run/bos/bauth.sock (JSON-RPC 2.0)
     payload: {"ctx_id":"...", "domains":["D00","D01",...,"D11"], "tenant":"skull"}
  4. bAuth evalúa 12 dominios contra RolTemplate + políticas del tenant
     → DomainResult: {D00:true, D01:true, D08:false, ...}
  5. BOS cachea DomainResult en Redis DB1 TTL 30s
  6. Retorna DomainResult al caller
```

**Cliente en BOS:** `internal/bauth/client.go` — `EvaluateContext(ctx_id, domains)` via Unix socket.
**Timeout:** 500ms (bAuth debe responder en < 500ms según contrato BOS-BAUTH-CONTRATOS.md).

## 3. Los 12 dominios bAuth (D00-D11)

| Dominio | Nombre | Tipo | Pregunta que responde |
|:-------:|--------|------|----------------------|
| D00 | Identidad Organizacional | L3 núcleo | ¿El usuario pertenece a esta organización? |
| D01 | Autenticación | L3 núcleo | ¿El usuario autenticó correctamente? |
| D02 | Autorización de Roles | L2 | ¿El usuario tiene el rol requerido? |
| D03 | Contexto Temporal | L2 | ¿Está dentro del horario permitido? |
| D04 | Contexto Físico | L2 | ¿Está en la ubicación autorizada? |
| D05 | Contexto de Dispositivo | L2 | ¿El dispositivo está registrado y sano? |
| D06 | Datos Sensibles | L2 | ¿El usuario puede acceder a datos de esta clasificación? |
| D07 | Delegación | L2 | ¿Actúa en nombre de otro usuario autorizado? |
| D08 | Cumplimiento | L2 | ¿El tenant cumple sus políticas internas? |
| D09 | Riesgo | L1 | ¿El score de riesgo de la sesión es aceptable? |
| D10 | Auditoría | L1 | ¿Existe contexto de auditoría para la operación? |
| D11 | Emergencia | L1 | ¿Hay una excepción de emergencia activa? |

**Núcleo L3 (D00+D01):** deben ser `true` en toda sesión válida. Si alguno es `false`, el ctx_id
es inválido independientemente de los demás dominios.

## 4. Kong PEP — Plugin SBOS-Context (Fase III)

Kong es el único punto de entrada al SBOS desde el exterior. Actúa como PEP:
intercepta cada request y verifica el ctx_id con el PA (BOS) antes de permitirlo.

**Flujo Kong PEP:**

```
Request HTTP → Kong Gateway
  1. Extraer ctx_id del header X-SBOS-CTX-ID o Authorization Bearer
  2. Invocar bos.ctx.validate(ctx_id) sobre /run/bos/bos.sock
     → válido: agregar headers X-SBOS-Tenant, X-SBOS-Empresa, X-SBOS-Sucursal al request
     → inválido: 401 Unauthorized {"error":"invalid_ctx","code":"CTX-001"}
     → cross-tenant: 403 Forbidden {"error":"cross_tenant","code":"CTX-002"}
  3. Forward al servicio upstream si ctx_id es válido
```

**Plugin `sbos-ctx-plugin` (Lua para Kong 3.9.x):**
```lua
-- servers/S02-gatewayserver/kong/resources/sbos-ctx-plugin/handler.lua
local socket = require "socket"
local rpc_sock = "/run/bos/bos.sock"

function SBOSCtxPlugin:access(config)
  local ctx_id = kong.request.get_header("X-SBOS-CTX-ID")
  if not ctx_id then
    return kong.response.exit(401, {error="missing_ctx_id"})
  end
  local result = rpc_call(rpc_sock, "bos.ctx.validate", {ctx_id=ctx_id})
  if not result.valid then
    return kong.response.exit(401, {error="invalid_ctx"})
  end
  kong.service.request.set_header("X-SBOS-Tenant", result.tenant_id)
  kong.service.request.set_header("X-SBOS-Empresa", result.empresa_id)
end
```

## 5. FAPI 2.0 sobre el Context Plane

**Financial-grade API Profile 2.0** es el estándar de seguridad más exigente para APIs
de identidad. El SBOS lo adopta como norte de certificación IAM Enterprise.

### 5.1 PAR — Pushed Authorization Request (RFC 9126)

El cliente empuja el request de autorización directamente al AS (Keycloak) antes de
redirigir al usuario, eliminando los parámetros de la URL del navegador:

```
Cliente → POST /par/authorize (parámetros en body) → AS retorna request_uri
Cliente → Redirect a /authorize?request_uri=<uri>&client_id=<id>
```

**Configurar en KC 26.6.2:** `require-pushed-authorization-requests=true` en el realm.

### 5.2 DPoP — Demonstrating Proof-of-Possession (RFC 9449)

El token JWT lleva un `cnf.jkt` (JSON Key Thumbprint) que liga el token a una clave
privada que el cliente demuestra poseer en cada request. Elimina el riesgo de token theft.

```
Token JWT: {"cnf": {"jkt": "0ZcOCORZNYy-DWpqq30jZyJGHTN0d2HglBV3uiguA4I"}}
Request:   DPoP: <jwt-proof-signed-with-private-key>
```

**Configuración KC:** `dpop-bound-access-tokens=true` en el cliente OAuth.

### 5.3 LoA — Level of Assurance (RFC 9470 step-up)

El BOS registra el LoA (1-4) en `bos.ctx_context_session.loa`:

| LoA | Autenticación requerida | ctx_id válido para |
|:---:|------------------------|-------------------|
| 1 | Password | Recursos de baja sensibilidad |
| 2 | Password + TOTP | Operaciones estándar de negocio |
| 3 | Password + TOTP + dispositivo registrado | Operaciones financieras / datos sensibles |
| 4 | Hardware token + biometría | Operaciones críticas + acceso a datos cifrados |

**Step-up automático:** si el recurso solicitado requiere LoA 3 y el ctx_id tiene LoA 2,
el BOS retorna `{"error":"insufficient_loa","required":3,"current":2}` → Kong redirige al
flujo de step-up de KC → usuario reautentica → nuevo ctx_id con LoA 3.

### 5.4 Algoritmos FAPI 2.0

Solo `PS256` (RSA-PSS + SHA-256) y `ES256` (ECDSA + P-256) son permitidos.
En KC 26.6.2: deshabilitar `RS256`, `HS256` y todos los algoritmos simétricos en el realm.

## 6. Cache Redis y consistencia

```
Redis DB1 — keys del Context Plane:
  bos:ctx:<ctx_id>           TTL 43200s (12h)  — estado de la sesión
  bos:ctx:resolve:<ctx_id>   TTL 30s           — DomainResult cacheado
  bos:ctx:hb:<dctx_id>       TTL 30s           — heartbeat cooldown
  bos:ctx:rl:<ip>            TTL 1s             — rate limiting token bucket
```

**Invalidación inmediata:** `bos.ctx.invalidate(ctx_id)` ejecuta `DEL bos:ctx:<ctx_id>` y
`DEL bos:ctx:resolve:<ctx_id>` en la misma transacción Redis (MULTI/EXEC). El ctx_id
deja de ser válido en < 1ms en todos los nodos que lo consultan.
