## 1. Dos tipos de tenant — dos ciclos de provisioning distintos

El BOS reconoce dos tipos de tenant, diferenciados por el campo `idn_tenant.is_internal`:

| | Tenant Interno | Tenant Externo |
|---|---|---|
| **Quién es** | El operador del SBOS (SKULL) | Un cliente que usa el SBOS como servicio |
| **`is_internal`** | `true` | `false` |
| **Control** | Total sobre el sistema | Solo sobre su tenant |
| **Stack desplegado** | PG + Redis + Vault + KC + Kong + daemons | Realm KC aislado + namespace K8s + Vault namespace |
| **Superficie bAuth** | `bauth.tenant.*` (6 métodos CRUD real) | `bauth.idp.*` (12 métodos IDaaS) |
| **tenant_id** | UUIDv7 o NIT boliviano | UUIDv7 |
| **Pipeline provisioning** | PENDING_VERIFICATION → INFRA_PROVISIONING → SCHEMA_CREATED → IDP_CONFIGURED → COMPLETED | PENDING_VERIFICATION → activo |
| **Dominio propio** | `sbos.app` | `cliente.sbos.app` o dominio personalizado |
| **Branding** | Genérico SBOS | Personalizado (logo, colores, CSS, email templates) |
| **Baja** | No aplica (es el dueño) | Soft-delete + 30 días grace period + purge (GDPR Art. 17) |

### 1.1 Cómo el BOS diferencia al hacer deploy

```bash
bosctl deploy seed-skull.yml --tenant=skull
```

El BOS consulta `bauth.tenant.get(tenant_id)` y evalúa `is_internal`:

- **`is_internal = true`**: despliega el stack COMPLETO. Saga de 7 pasos: Realm KC + Namespace
  K8s + 9 BDs PostgreSQL + Vault paths + Redis DB1 + DDL context + fichas del tenant.
  Este tenant ES el dueño del servidor.

- **`is_internal = false`**: despliega solo el perímetro del tenant. Saga reducida de 4 pasos:
  Realm KC aislado + Namespace K8s + Vault namespace + dominio DNS. Sin PostgreSQL compartido
  (usa el schema del tenant en SBOS_db). Sin Redis DB1 propio (usa prefijo `{tenant}:` en keys).

## 2. Modelo de tenant (SBOS-051 v2.0)

### 2.1 Modelo A — Identidad empresarial

`legal_name`, `trading_name`, `tax_identifier` (NIT 7-15 dígitos), `registration_number`,
`entity_legal_form_code` (SRL, SA, UNIPERSONAL...), `jurisdiction_of_registration`,
`entity_status` (ACTIVA, INACTIVA, EN_DISOLUCION).

### 2.2 Modelo B — Dominio técnico

`domain_id` (slug único), `domain_type` (production, staging, development, sandbox, dr),
`tenancy_trust_model` (soft/hard), `isolation_mechanism` (namespace_rbac, runtime_sandbox,
virtual_cluster), `network_policy` (default-deny).

## 3. Ciclo de vida del tenant — 7 estados + provisioning + GDPR

```
status: PENDING_VERIFICATION → (verified) → activo → (suspended) → suspended_at
        → (deleted) → deleted_at → (+30 días grace) → purge definitivo

provisioning_status (solo tenant interno):
  PENDING → INFRA_PROVISIONING → SCHEMA_CREATED → IDP_CONFIGURED → COMPLETED
```

**GDPR Art. 17:** el soft-delete con 30 días de gracia antes del purge definitivo está
codificado en el esquema `idn_tenant.purge_after`. El derecho de supresión es un dato,
no un proceso manual.

## 4. Aislamiento multi-tenant — pool con discriminador + 3 refuerzos

| Capa | Mecanismo | Aislamiento |
|------|-----------|-------------|
| **Datos** | Schema `bauth` compartido, `WHERE tenant_id = $1` en cada query | Lógico |
| **Infraestructura** | `idn_tenant.namespace_k8s` — namespace K8s por tenant | Físico parcial |
| **Red** | Dominios DNS propios por tenant (`idn_tenant_domain`) | Perimetral |
| **Token** | `tenant_id` en claim JWT + `aud` per-tenant | Criptográfico |

**Brecha conocida:** sin Row-Level Security en PostgreSQL. El aislamiento descansa en una
sola capa (el WHERE del handler). La práctica de industria es doble capa: WHERE + RLS.

## 5. Comandos CLI

```bash
bosctl deploy seed-skull.yml                     # alta de tenant (saga 7 pasos)
bosctl tenant list                                # listar tenants
bosctl tenant suspend skull                       # suspender (invalida ctx_id)
bosctl tenant remove skull                        # baja (requiere HITL + dual-control)
bosctl web domain add www.cliente.com --tenant=skull --empresa=cliente_a
```
