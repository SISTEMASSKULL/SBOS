## 1. Por qué existen los 4 motores

Un sistema que solo responde a fallas ya ocurridas no es observable — es reactivo.
El SBOS necesita **anticiparse** a los problemas: predecir cuándo Redis se va a saturar
antes de que lo haga, escalar antes de que el usuario note latencia, bloquear admisión
de nuevos tenants antes de que el sistema colapse.

Los 4 motores implementan el ciclo ITIL 4 de Gestión de Capacidad:
```
Observar → Proyectar → Decidir política → Actuar
(Collector) (Forecaster) (Policy Engine) (Action Engine)
```

## 2. Motor 1 — Collector (`internal/capacity/collector.go`)

Recolecta 30+ métricas cada 60 segundos y las persiste en `bos.cap_sistema_snapshot` (T-406).

### 2.1 Fuentes de métricas

| Fuente | Métricas | Cómo |
|--------|---------|------|
| Redis INFO | `used_memory_pct`, `connected_clients`, `keyspace_hits_pct` | TCP local :6379 |
| PostgreSQL | `pg_connections_pct`, `pg_db_size_bytes`, `pg_replication_lag_s` | `database/sql` |
| Kubernetes | `node_cpu_pct`, `node_mem_pct`, `pod_restarts_total`, `pvc_used_pct` | `kubectl top node` via `k8s.Core` (P1) |
| Kong | `rps_total`, `p99_latency_ms`, `error_rate_pct` | `/status` endpoint :8001 |
| bAuth | `cache_miss_rate`, `domain_eval_p99_ms`, `active_sessions` | `bauth.metrics.*` JSON-RPC |

| BOS daemon | `ficha_degraded_count`, `ficha_unrecoverable_count`, `saga_pending_count` | state.Manager.Read() |
| Host OS | `disk_used_pct`, `iowait_pct`, `load_avg_1m` | `/proc/stat`, `syscall.Statfs` |

### 2.2 Tabla T-406 `bos.cap_sistema_snapshot`

```sql
-- Particionada mensualmente (PARTITION BY RANGE sobre collected_at)
CREATE TABLE bos.cap_sistema_snapshot (
    snapshot_id     UUID DEFAULT gen_random_uuid(),
    collected_at    TIMESTAMPTZ NOT NULL,
    -- Redis
    redis_mem_pct   NUMERIC(5,2), redis_clients   INTEGER, redis_hit_rate NUMERIC(5,2),
    -- PostgreSQL
    pg_conn_pct     NUMERIC(5,2), pg_size_gb      NUMERIC(10,3),
    -- Kubernetes
    k8s_cpu_pct     NUMERIC(5,2), k8s_mem_pct     NUMERIC(5,2), k8s_pod_restarts INTEGER,
    -- Kong
    kong_rps        INTEGER,      kong_p99_ms     NUMERIC(10,2), kong_error_pct  NUMERIC(5,2),
    -- Context Plane
    ctx_lookups_s   INTEGER,      ctx_miss_rate   NUMERIC(5,2),  active_ctx      INTEGER,
    -- Fichas
    units_healthy   INTEGER,      units_degraded  INTEGER,       units_error     INTEGER, units_total INTEGER,
    -- Host
    disk_used_pct   NUMERIC(5,2), iowait_pct      NUMERIC(5,2),
    -- Metadatos
    ctx_id          TEXT NOT NULL,
    PRIMARY KEY (snapshot_id, collected_at)
) PARTITION BY RANGE (collected_at);
```

## 3. Motor 2 — Forecaster (`internal/capacity/forecaster.go`)

Aplica regresión lineal sobre las últimas N muestras de T-406 para proyectar cada métrica
en horizontes de 7, 30 y 90 días con intervalos de confianza.

### 3.1 Algoritmo

```
Para cada métrica M:
  1. Obtener últimas N muestras de cap_sistema_snapshot ORDER BY collected_at DESC
  2. Regresión OLS (Ordinary Least Squares): y = α + β·t
     β = covarianza(t,y) / varianza(t)
     α = ȳ - β·t̄
  3. Proyectar: value_at_horizon = α + β·horizon_seconds
  4. Intervalo de confianza 80%/95%: t-distribution con N-2 grados de libertad
  5. Detectar saturación: t_saturation = (100 - actual_value) / β  (días hasta 100%)
```

### 3.2 Respuesta JSON

```json
{
  "redis_mem_pct": {
    "current": 45.2, "trend_per_hour": 0.21,
    "forecast_7d": 48.7,  "forecast_30d": 66.1,  "forecast_90d": 100.0,
    "ci_80": [43.1, 50.4], "saturates_in_days": 87,
    "status": "warn"
  }
}
```

### 3.3 CLI

```bash
bosctl capacity forecast --horizon 30d    # Proyección 30 días
bosctl capacity forecast --metric redis   # Solo métricas Redis
bosctl capacity forecast --horizon 7d --format json | jq '.redis_mem_pct'
```

## 4. Motor 3 — Policy Engine (`internal/capacity/policy_engine.go`)

Lee las políticas declarativas de `config/cap-policies/default.yml` (o por tenant desde
`bos.cap_tenant_policy` T-407) y compara las métricas actuales contra los thresholds.

### 4.1 Tabla T-407 `bos.cap_tenant_policy`

```sql
CREATE TABLE bos.cap_tenant_policy (
    policy_id    UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id    TEXT NOT NULL REFERENCES bos.cap_tenant(tenant_id),
    policy_mode  TEXT NOT NULL CHECK (policy_mode IN
                   ('autonomous','recommend','block_and_alert','emergency')),
    -- thresholds por métrica
    redis_warn_pct    NUMERIC(5,2) DEFAULT 70,
    redis_crit_pct    NUMERIC(5,2) DEFAULT 85,
    pg_conn_warn_pct  NUMERIC(5,2) DEFAULT 70,
    pg_conn_crit_pct  NUMERIC(5,2) DEFAULT 85,
    k8s_cpu_warn_pct  NUMERIC(5,2) DEFAULT 75,
    k8s_cpu_crit_pct  NUMERIC(5,2) DEFAULT 90,
    disk_warn_pct     NUMERIC(5,2) DEFAULT 80,
    disk_crit_pct     NUMERIC(5,2) DEFAULT 90,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    ctx_id       TEXT NOT NULL
);
```

### 4.2 Modos de política

| Modo | Comportamiento del Action Engine |
|------|----------------------------------|
| `autonomous` | Escala sin preguntar. Solo HITL para decisiones destructivas. |
| `recommend` | Propone acción en logs y Wazuh, espera aprobación humana. |
| `block_and_alert` | Bloquea admisión de nuevos tenants/ctx_id + alerta crítica. |
| `emergency` | Modo de crisis: bloquea TODO tráfico nuevo + evacúa a modo mínimo. |

### 4.3 Evaluación de thresholds

```go
// policy_engine.go — Evaluate() retorna PolicyDecision
type PolicyDecision struct {
    Metric    string
    Current   float64
    Threshold float64
    Level     string  // "ok" | "warn" | "crit"
    Action    string  // "none" | "scale_up" | "block_admission" | "emergency"
}
```

## 5. Motor 4 — Action Engine (`internal/capacity/action_engine.go`)

Ejecuta las acciones decididas por el Policy Engine. Dos principios críticos:

**Anti-death-spiral (A.06 §4):** el BOS nunca delega scaling a HPA y VPA por separado.
Los decide en una sola decisión coordinada con histéresis ≥ 10%:

```
Decisión scale_up: solo si load > (threshold + 10%)
Decisión scale_down: solo si load < (threshold - 10%)
→ Elimina oscilaciones HPA↔VPA que destruyen el rendimiento
```

### 5.1 Acciones disponibles

| Acción | Qué hace | Modo mínimo requerido |
|--------|----------|----------------------|
| `scale_up` | `kubectl scale` via `k8s.Core` con histéresis ≥10% | autonomous |
| `scale_down` | `kubectl scale` con histéresis ≥10% | autonomous |
| `block_ctx_admission` | Rechaza nuevos `device.register` con 503 | block_and_alert |
| `alert_warn` | RocketChat + Prometheus gauge | recommend |
| `alert_critical` | PagerDuty + RocketChat + Prometheus gauge | autonomous |
| `emit_event` | Redis Streams `bos:events:capacity` (consume bAuth, biedata) | all |
| `emergency_mode` | Suspende fichas no-críticas + bloquea admisión total | emergency |

### 5.2 Integración con watchdog (A.08 §3)

```
Watchdog detecta ficha DEGRADED
  → llama bos.query.repair (8 threads diagnóstico paralelo)
  → Action Engine decide si el problema es de capacidad
  → si sí: scale_up antes de iniciar repair saga
  → si no: repair saga sin cambio de capacidad
```
