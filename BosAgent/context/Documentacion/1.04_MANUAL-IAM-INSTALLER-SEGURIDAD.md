## 1. Principio rector — Superficie Mínima de Ataque

> **Cada endpoint, puerto y protocolo que un daemon expone es un vector de ataque.
> Lo que no existe no puede ser atacado.**

Antes de implementar cualquier comunicación: ¿es absolutamente necesaria? ¿puede resolverse
con un canal ya existente? ¿cuál es la superficie mínima?

## 6. NIST SP 800-207 — Los 7 Tenets de Zero Trust

BOS es la implementación del **Policy Administrator (PA)** en la arquitectura ZTA del SBOS.
Kong es el **Policy Enforcement Point (PEP)**. bAuth es el **Policy Engine (PE)**.

| # | Tenet | Implementación en SBOS | Estado |
|:-:|-------|------------------------|:------:|
| 1 | Todo recurso accesible SOLO vía PEP | Kong es el único punto de entrada · deny-all NetworkPolicy por namespace | 🟡 NetworkPolicies pendientes (NRS-04) |
| 2 | Toda comunicación asegurada independientemente de red | TLS 1.3 en :9443 (NRS-01) · mTLS daemons (NRS-03) · SPIFFE/SPIRE entre pods | 🟡 NRS-03 pendiente |
| 3 | Acceso per-request, no per-session | ctx_id verifica en cada request via `bos.ctx.validate` + Kong plugin | ✅ implementado |
| 4 | Acceso determinado por política dinámica | bAuth evalúa 12 dominios (D00-D11) + RolTemplate + ctx_id por request | 🟡 requires bAuth operativo |
| 5 | Monitoreo continuo de integridad | Wazuh SIEM (NRS-04) · `bos_ctx_validate_fail_total` Prometheus · audit log WORM | 🟡 Wazuh pendiente (NRS-04) |
| 6 | Autenticación + autorización estricta antes de acceso | `validSharedToken` P4 (fail-close) · RBAC FileRBAC + BauthRBAC | ✅ implementado |
| 7 | Recolección de telemetría + mejora continua | Prometheus 18+ gauges · Grafana · audit_log con ctx_id · capacity.collector 60s | 🟡 Prometheus pendiente Fase V |

## 7. NRS-03 — mTLS entre daemons (pendiente Fase II)

**Objetivo:** Kong → BOS y BOS → bAuth requieren certificado cliente (mTLS). Un atacante
con acceso a la red interna no puede suplantar un daemon sin el cert emitido por Vault PKI.

**Implementación en `internal/server/api.go`:**

```go
// Activar en api.go tras Vault PKI operativo (Fase II Pasada 2)
tlsCfg := &tls.Config{
    MinVersion:   tls.VersionTLS13,
    ClientAuth:   tls.RequireAndVerifyClientCert,
    ClientCAs:    sbosCAPool,          // CA intermedia Vault PKI
    Certificates: []tls.Certificate{bosDaemonCert},
}
```

**Flujo:** Vault PKI CA intermedia emite cert para cada daemon → cert path en `paths.CertFile` / `paths.KeyFile` → Pasada 2 de instalación los migra de cert autofirmado a Vault PKI (A.07 §4).

## 9. NRS-10 — CI Pipeline de Seguridad (pendiente Fase II)

**Objetivo:** cada PR tiene escáner de seguridad estático bloqueante antes de merge.

**Stack de herramientas:**

| Herramienta | Qué detecta | Umbral para bloquear |
|-------------|-------------|---------------------|
| `gosec` | vulnerabilidades Go: SQLi, path traversal, weak crypto, hardcoded creds | 0 HIGH severity |
| `govulncheck` | CVEs en dependencias Go (usa Go Vulnerability DB) | 0 vulnerabilities affecting code |
| `gitleaks` | secretos y credenciales en git history | 0 leaked secrets |

**`.github/workflows/security.yml` (esqueleto):**

```yaml
name: Security
on: [pull_request]
jobs:
  security:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: securego/gosec@master
        with: { args: '-severity high -nosec ./...' }
      - run: go install golang.org/x/vuln/cmd/govulncheck@latest && govulncheck ./...
      - uses: gitleaks/gitleaks-action@v2
        env: { GITHUB_TOKEN: '${{ secrets.GITHUB_TOKEN }}' }
```
