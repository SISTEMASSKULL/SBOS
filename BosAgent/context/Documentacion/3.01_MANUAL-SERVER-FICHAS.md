## 1. Qué es una ficha y por qué existe

Una **ficha** es la unidad atómica de despliegue del SBOS. Toda aplicación, daemon, dependencia
del SO o configuración del sistema es una ficha. El principio es simple:
Cada ficha es un directorio en `servers/<servidor>/<app>/` con:
- `manifest.yml` — identidad, dependencias, servidor, namespace, puerto, health (OBLIGATORIO)
- `PROPOSITO.md` — qué es, por qué existe, para qué sirve (OBLIGATORIO)
- `task_catalog.sh` — funciones `<app>_install`, `_verify`, `_health`, `_repair`, `_remove` (OBLIGATORIO)
- `resources/` — artefactos: sql/, config/, keycloak/, vault/, migrations/

Sin PROPOSITO.md, el Bibliotecario **rechaza** la ficha.

## 2. El BOS como Kubernetes Operator Soberano (ADR-004)

El BOS implementa el patrón Operator del CNCF:

| Componente Operator | Equivalente en BOS |
|--------------------|---------------------|
| Custom Resource (CRD) | `manifest.yml` de cada ficha (`.spec` = estado deseado) |
| Controller | `observer/loop.go` + `reconcile/scheduler.go` |
| Reconcile Loop | Ciclo de 15min comparando spec vs estado real |

### 2.1 Death spiral de HPA + VPA

HPA y VPA son incompatibles cuando operan sobre las mismas métricas de forma independiente.
La solución es **reconciliar réplicas y dimensionamiento como una decisión coordinada única**
— exactamente lo que el BOS hace con `internal/scaler/` (anti-death-spiral, histéresis,
context-aware).

### 2.2 El BOS escala con semántica empresarial

K8s HPA/VPA son ciegos al contexto. El BOS conoce: tenant, empresa, sucursal, horario,
políticas del manifest.yml, y estado del resto de las fichas. Puede escalar *con semántica*:
sabe que PostgreSQL en fin de mes necesita más recursos que en horario nocturno.

## 3. Los 18 estados (ADR-021) — naming inglés (A.14 v6.0.0)

Todos los identificadores de estado usan inglés en el DDL (`bos.fch_ficha_state`),
en el JSON de respuesta RPC y en `.sbos_state.json`. El código Go en
`internal/ficha/statemachine.go` aún usa las constantes en español — la migración
es la Tarea I.0 del plan de completitud.

**Tabla de correspondencia completa:**

| Constante Go actual | Valor en DDL/RPC (A.14 v6.0.0) | Semántica |
|--------------------|---------------------------------|-----------|
| `StatePendiente` | `PENDING` | ficha declarada, verificando dependencias |
| `StateLista` | `READY` | deps OK, esperando turno en DAG topológico |
| `StateInstalando` | `INSTALLING` | saga install en progreso (timeout 30min) |
| `StateInstalada` | `INSTALLED` | pod Running + health check OK |
| `StateFallaInstalacion` | `INSTALL_FAILED` | saga install falló, activa CLEANUP |
| `StateActualizacionDisp` | `UPDATE_AVAILABLE` | nueva versión detectada por watchdog |
| `StateActualizacionAprobada` | `UPDATE_APPROVED` | tests OK, sin degradación vecina |
| `StateActualizando` | `UPDATING` | saga update en progreso (timeout 15min) |
| `StateFallaActualizacion` | `UPDATE_FAILED` | saga update falló, activa ROLLBACK |
| `StateDegradada` | `DEGRADED` | funciona reducido, auto-repara (3 intentos) |
| `StateErrorFisico` | `PHYSICAL_ERROR` | fallo hardware: disco/red/CPU/memoria |
| `StateErrorLogico` | `LOGICAL_ERROR` | fallo config/deps/schema drift |
| `StateErrorNoCorregible` | `UNRECOVERABLE` | reintentos agotados → HITL obligatorio |
| `StateReparando` | `REPAIRING` | diagnóstico activo + repair (timeout 10min) |
| `StateRollback` | `ROLLBACK` | restaurando versión N-1 (sin cambio de nombre) |
| `StateLimpieza` | `CLEANUP` | eliminando artefactos post-fallo de instalación |
| `StatePausada` | `PAUSED` | admin suspendió — mantenimiento programado |
| `StateDesinstalada` | `UNINSTALLED` | removida del sistema (retención 30d en Kardex) |

**Diagrama de transiciones:**

```
PENDING → READY → INSTALLING → INSTALLED
                                ├→ DEGRADED → REPAIRING → INSTALLED
                                │             └→ UNRECOVERABLE → HITL
                                ├→ UPDATE_AVAILABLE → UPDATE_APPROVED → UPDATING
                                │   └→ UPDATE_FAILED → ROLLBACK → INSTALLED
                                ├→ PAUSED → (estado anterior)
                                └→ UNINSTALLED

INSTALL_FAILED → CLEANUP → PENDING
PHYSICAL_ERROR (disco/red/CPU) → REPAIRING → INSTALLED / UNRECOVERABLE
LOGICAL_ERROR (config/deps)    → REPAIRING → INSTALLED / UNRECOVERABLE
```

### 3.1 Timeouts por operación

| Operación | Timeout | Compensación |
|-----------|:------:|-------------|
| install | 30min | CLEANUP (primer intento) o ROLLBACK (si había versión N-1) |
| update | 15min | ROLLBACK a versión N-1 |
| repair | 10min | 3 reintentos → UNRECOVERABLE → HITL |
| remove | 10min | N/A (irreversible, requiere HITL + dual-control) |

### 3.2 DegradedHandler

`lifecycle.go`: EnterDegraded → AttemptRepair(×3) → Recover (→ INSTALLED) o
Escalate (→ UNRECOVERABLE → HITL).

### 3.3 Port Manager wiring en ciclo de vida (Tarea IV.1-IV.2 del plan)

Al completar INSTALLED: `portman.AssignFromManifest(fichaID, manifest)` → Kardex T-408 `status='assigned'`
Al entrar UNINSTALLED: `portman.Release(fichaID)` → Kardex T-408 `status='released'` (lógico, inmutable RFC 6335)

## 4. El rol del BOS — motor universal vs tarea específica

**Regla de oro (servers.yml §5):** "Función que menciona una app concreta → va en SU
task_catalog.sh. Función universal → va en el motor (bos)."

| Vive en el motor (bos) | Vive en task_catalog.sh (ficha) |
|------------------------|--------------------------------|
| `install()` — orquesta fases | `postgresql_install()` — instala PG |
| `resolveDeps()` — DAG topológico | `postgresql_verify()` — verifica PG |
| `healthCheck()` — ejecuta probe | `postgresql_health()` — health PG |
| `reconcile()` — compara estado | `postgresql_repair()` — repara PG |

## 5. Soberanía de fichas  

1. **SOV-01:** Todo `system_packages` en manifest.yml tiene su task_catalog.sh que lo instala
2. **SOV-02:** Todo archivo/directorio en el sistema es creado por una ficha
3. **SOV-03:** La documentación nunca dice "ejecuta este comando manual"
4. **SOV-04:** `ficha_install()` es idempotente (ejecutar 2 veces = mismo resultado)
5. **SOV-05:** `install.sh` ≤ 25 líneas, sin `apt-get`, `useradd`, `mkdir`
6. **SOV-06:** Las credenciales bootstrap son TEMPORALES — Pasada 2 las migra a Vault
7. **SOV-07:** Auditoría de comandos manuales → cada uno asignado a una ficha
8. **SOV-08:** Sin ficha → crear ficha nueva
