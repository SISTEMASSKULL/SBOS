## 1. Qué es el Context Plane y por qué es la pieza más crítica del BOS

El BOS es el **único dueño del Context Plane**. No es una feature — es LA feature que hace al
BOS un Plano de Control Soberano. Sin Context Plane operativo, bauth no puede evaluar dominios,
bnexus no puede registrar dispositivos, Kong no puede validar requests, y **ningún usuario del
SBOS puede operar**.

### 1.1 Analogía fundamental

```
Linux kernel  →  gestiona procesos (PID)
systemd       →  gestiona servicios (unit)
BOS           →  gestiona contexto empresarial (ctx_id)
```

El `ctx_id` es el "PID" del sistema operativo empresarial. Todo evento, log, request,
transacción y operación en el SBOS está asociado a un ctx_id. Sin él, el sistema funciona
a nivel técnico (K8s, PG, Redis) pero no tiene **significado empresarial**.

### 1.2 Alineación con NIST SP 800-207 (Zero Trust)

| Componente NIST 800-207 | Equivalente en SBOS |
|-------------------------|---------------------|
| Policy Engine (PE) | bAuth — evalúa BitMask, RolTemplate, ctx activo |
| Policy Administrator (PA) | **BOS** — provisiona y destruye contextos de tenant |
| Policy Enforcement Point (PEP) | Kong + plugin SBOS-Context — valida ctx_id en cada request |

El BOS como Policy Administrator es responsable de: crear el contexto al hacer login,
mantenerlo durante la sesión, invalidarlo al hacer logout, y destruir todos los contextos
al suspender un tenant. **Sin BOS operativo, no hay Zero Trust.**

## 2. Los dos identificadores de contexto

### 2.1 dctx_id — Device Context ID (pre-autenticación)

- Estado: PENDIENTE (recién registrado)
- BitMask: `0x0000000000000000` (sin privilegios — invariante pre-auth)
- TTL: 8 horas (ISO 27001 A.9.4.2)
- Se crea cuando un dispositivo (Fedora físico, VDI, terminal POS) arranca
- No autoriza operaciones — solo identifica al dispositivo

### 2.2 ctx_id — Context Session ID (post-autenticación)

- Estado: ACTIVO (sesión válida)
- BitMask: > 0 (invariante post-auth — calculado por bAuth)
- TTL: duración de la sesión Keycloak (máx 12h, ISO 27001 A.9.4.2)
- Se crea cuando el usuario hace login (promote)
- Autoriza operaciones según el BitMask (3 dominios: lógico, físico, financiero)

## 3. Los 6 endpoints de la Context API (:9443, TLS 1.3)

| Método | Endpoint | Propósito | Llamado por |
|--------|----------|-----------|-------------|
| POST | `/api/v1/context/create` | Login → genera ctx_id | Keycloak Event Listener |
| POST | `/api/v1/context/switch` | Cambio de contexto sin reautenticación | App (cambio de sucursal) |
| DELETE | `/api/v1/context/{ctx_id}` | Logout → invalida ctx_id | Keycloak Event Listener |
| GET | `/api/v1/context/{ctx_id}` | Lookup O(1) — **llamado en CADA request** | Kong Plugin SBOS-Context |
| GET | `/api/v1/context/tenant/{t}` | Lista ctx_id activos del tenant | Admin dashboard |
| POST | `/api/v1/context/tenant/{t}/invalidate-all` | Suspensión de tenant | `bosctl tenant suspend` |

**Nota SBOS-054 §1.2:** La Context API original planeaba 6 endpoints. Aplicando la Regla de
Reducción de superficie de ataque, se eliminaron 5 endpoints redundantes. Los 6 actuales son
el mínimo necesario — cada uno tiene una función distinta e irremplazable.

## 6. Lo que falta — por qué no está operativo

El sustrato de código es sólido: tipos, servicio, store, DDL, handlers JSON-RPC. Pero el
Context Plane **no está operativo** porque:

1. **Sin heartbeat:** los dispositivos no pueden mantener sesión pre-auth viva
2. **Sin rate limiting:** vulnerable a enumeración de ctx_id
3. **Sin sanitización:** ctx_id completos en logs → riesgo de fuga
4. **Sin auditoría:** `internal/audit` nunca llamado desde handlers de contexto
5. **Sin health check:** no se monitorea la salud del Context Plane
