## 1. Qué es el Context Plane

El BOS es el **único dueño del Context Plane**. Toda operación del SBOS ocurre EN un contexto:
quién opera, para qué tenant, en qué parte de la jerarquía de identidad, con qué traza
distribuida. El **ctx_id** empaqueta ese contexto y viaja con cada petición.

**La regla del proyecto (SBOS-049):** ninguna operación sin ctx_id — ni logs, ni auditoría,
ni requests. Un daemon que recibe una petición sin contexto la rechaza.

## 2. La estructura del ctx_id — 6 capas (UUIDv7 para todas las PKs)

```
ctx_id = tenant_id : entidad_1 : entidad_2 : entidad_3 : user_id : traceparent
           │            │           │           │           │           │
        UUIDv7       UUIDv7      UUIDv7      UUIDv7      UUIDv7    W3C Trace
       (obligatorio)                                                    Context
```

**RFC 9562 — UUIDv7:** todas las PKs son UUIDv7 (time-ordered, ordenables por tiempo).
La razón: un ctx_id creado después DEBE ser mayor que uno creado antes. PostgreSQL 18
genera UUIDv7 con `DEFAULT uuidv7()`.

### 2.1 Las 6 capas en detalle

| Capa | Campo | Significado | Nivel en D00 |
|------|-------|-------------|:------------:|
| 1 | `tenant_id` | **OBLIGATORIO** — frontera de soberanía. Sin tenant no se crea contexto. `is_internal` determina si es operador o cliente. | tenant |
| 2 | `entidad_1` | Unidad principal (bdomain). Puede ser: empresa, persona, hogar, almacen, datacenter, hospital, hotel, universidad... | bdomain |
| 3 | `entidad_2` | División (bsubdomain). Puede ser: sucursal, oficina, deposito, sala, piso, aula, habitacion... | bsubdomain |
| 4 | `entidad_3` | Punto de operación (pos). Puede ser: caja, terminal, puerta, sensor, estante, rack, estacionamiento... | pos |
| 5 | `user_id` | Quien opera (actor). Puede ser: HUMAN, SERVICE, DEVICE, BOT, producto, vehiculo, servidor... | actor |
| 6 | `traceparent` | Trazabilidad W3C: `00-{traceId}-{spanId}-{flags}`. Correlaciona logs entre todos los daemons. | — |

### 2.2 La jerarquía NO es fija en tipo — solo en nivel

A diferencia de los sistemas tradicionales (tenant → empresa → sucursal → caja → usuario),
el ctx_id del SBOS acepta CUALQUIER tipo de entidad en cada nivel. El modelo de identidad
D00 define 5 niveles con tipos variables validados por el motor AtomLang:

```
Cliente empresa:
  skull(interno) : SKULL-CORP(empresa) : Norte(sucursal) : CAJA-01(caja) : juan(HUMAN)

Persona natural:
  skull(interno) : Juan-Perez(persona) : Oficina(oficina) : Desarrollo(punto_virtual) : juan(HUMAN)

Inventario:
  skull(interno) : Almacen-Central(almacen) : Deposito-A(deposito) : Estante-01(estante) : laptop(producto)

TI:
  skull(interno) : Datacenter(datacenter) : Sala-Servidores(sala) : Rack-01(rack) : servidor-hp(servidor)

Flota:
  skull(interno) : Flota-Norte(empresa) : Patio-Central(patio) : Estacionamiento-01(estacionamiento) : camion(vehiculo)

Salud:
  skull(interno) : Hospital-Central(hospital) : Piso-3(piso) : Habitacion-301(habitacion) : maria(paciente)

Educación:
  skull(interno) : Universidad-Norte(universidad) : Facultad-Ingenieria(facultad) : Aula-101(aula) : pedro(alumno)
```

## 3. El modelo de identidad universal — "todo es una entidad"

En bAuth, **todo es una entidad**. Un empleado, una empresa, un vehículo, un producto de
almacén, un servidor, una puerta OSDP, un bot de integración. Todas comparten la misma
estructura, las mismas tablas, el mismo motor de validación. Lo que cambia es el `tipo`.

### 3.1 Las tres tablas de identidad (schema bauth, D00 v2.0)

| Tabla | Responsabilidad | Estructura |
|-------|----------------|------------|
| `idn_identidad_entidad` | Jerarquía de 5 niveles | `parent_id` (adjacency list) |
| `idn_identidad_atributo` | Atributos extensibles EAV | `atom_code` vincula con BitMask |
| `idn_role` | Roles con herencia DAG | `idn_role_template` + `idn_role_closure` |

### 3.2 Membresía a conjuntos (USERSET) — sin duplicación

Una entidad existe UNA SOLA VEZ. Su pertenencia a conjuntos dice DÓNDE opera:

```
Juan Pérez (actor, HUMAN) → USERSET(autenticacion, RRHH, proveedor, cliente)
Camión Volvo (actor, vehiculo) → USERSET(flota, activos_fijos)
Laptop Dell (actor, producto) → USERSET(inventario)
```

## 4. Los 6 endpoints de la Context API (:9443, TLS 1.3)

| Método | Endpoint | Propósito |
|--------|----------|-----------|
| POST | `/api/v1/context/create` | Login → genera ctx_id con las 6 capas |
| POST | `/api/v1/context/switch` | Cambio de contexto (nueva entidad) sin reautenticación |
| DELETE | `/api/v1/context/{ctx_id}` | Logout → invalida ctx_id |
| GET | `/api/v1/context/{ctx_id}` | Lookup O(1) — Kong lo llama en CADA request |
| GET | `/api/v1/context/tenant/{t}` | Lista ctx_id activos del tenant |
| POST | `/api/v1/context/tenant/{t}/invalidate-all` | Suspensión de tenant |
