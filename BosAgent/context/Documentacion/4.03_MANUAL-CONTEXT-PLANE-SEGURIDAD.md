## 1. Modelo de amenazas del Context Plane

El Context Plane es el sistema más crítico del BOS: sin un ctx_id válido, ninguna
operación autorizada puede ejecutarse. Un atacante que comprometa el CP puede suplantar
cualquier sesión del sistema.

| Amenaza | Vector | Control |
|---------|--------|---------|
| Enumeración de ctx_id | Fuerza bruta de UUIDs | UUIDv7 + respuesta idéntica para "no encontrado" y "expirado" |
| Suplantación de daemon | Daemon malicioso invoca Context API | mTLS: cert cliente requerido en :9443 (NRS-03) |
| Replay de ctx_id | Reutilizar ctx_id revocado | Redis SETNX + TTL 12h · revocación inmediata en Redis |
| Session hijacking | Robo de ctx_id de logs | Sanitización logs: solo 8 chars + hash SHA-256 (SAN-07) |
| Cross-tenant escalation | Usuario tenant A accede a recursos tenant B | SAN-11 + SAN-12 en cada handler |
| DDoS en CP | Saturar endpoint device.register | Rate limiting 100 req/s + SYNPROXY en nftables |

## 2. UUIDs v7 — Anti-enumeración (RFC 9562)

Los ctx_id son UUIDv7 (128 bits, 48 bits timestamp ms + 74 bits aleatorios):

```
01923ac7-4f22-7a3b-b6e1-2c3d4e5f6a7b
│────────────────────│││ ─────────── │
  48 bits timestamp   ver var  74 bits aleatorios
```

**Propiedades de seguridad:**
- Monotónicamente crecientes → índice B-tree eficiente en PG
- 2^74 ≈ 18.9 × 10^21 valores posibles → fuerza bruta infeasible
- Sin información del servidor/tenant en el UUID (a diferencia de UUIDv1)
- Spec: `github.com/google/uuid` v1.6+ con `uuid.New()` → UUIDv4 actual, migrar a UUIDv7 en Fase III

## 3. Anti-enumeración — respuesta idéntica

Cualquier consulta a un ctx_id que no existe, expiró o fue revocado retorna el mismo error:

```go
// internal/server/ctx_handlers.go — rpcCtxGet
// Tanto "no encontrado" como "expirado" retornan ErrContextExpired
// con el MISMO mensaje genérico, mismo HTTP status, misma latencia artificial
var ErrContextExpired = &JSONRPCError{Code: -32001, Message: "context not available"}
```

**Por qué mismo mensaje Y misma latencia:** un atacante que mida latencias puede distinguir
"miss en Redis (rápido)" de "encontrado pero expirado (lento)" si no se igualan los tiempos.
La latencia artificial se implementa con `time.Sleep` hasta un mínimo de 5ms.

## 4. Rate limiting — Token Bucket 100 req/s

Implementado en `internal/ratelimit/` y aplicado en `server/jsonrpc.go:handleJSONRPC`.

```go
// Límites por IP y por método
const (
    DeviceRegisterLimit = 10   // req/s — operación costosa (escribe en PG)
    HeartbeatLimit      = 1    // req/30s por dctx_id — NRS-08
    GeneralLimit        = 100  // req/s por IP — todos los demás métodos
)
```

**Respuesta 429 (Too Many Requests):**
```json
{"jsonrpc":"2.0","error":{"code":-32008,"message":"rate limit exceeded",
  "data":{"retry_after_s":1}},"id":null}
```

## 5. Sanitización de entradas (paquete `internal/sanitize/`)

Toda entrada que llega al Context Plane pasa por sanitización antes de procesarse.
Ver 1.04 §4 para la lista completa de SAN-01..SAN-12.

**Específico del Context Plane:**

| SAN | Uso en CP | Implementación |
|-----|-----------|---------------|
| SAN-09 | Validar ctx_id / dctx_id como parámetro RPC | `sanitize.CtxIDParam(s)` — UUID regex + longitud |
| SAN-07 | Logs internos: nunca loguear ctx_id completo | `sanitize.LogCtxID(s)` → 8 chars + 3 bytes SHA256 |
| SAN-11 | Validar que tenant del request == tenant del ctx | `sanitize.CrossTenantSlug(sesion, recurso)` |
| SAN-04 | Paths de filesystem en operaciones ctx | `sanitize.FilePath(s)` — sin path traversal |

## 6. Cross-tenant isolation

El Context Plane gestiona todos los tenants en la misma instancia del daemon. El
aislamiento es lógico — un error puede cruzar fronteras si no se valida explícitamente.

```go
// Cada handler del Context Plane valida:
if err := sanitize.CrossTenantSlug(sessionTenant, requestTenant); err != nil {
    return &JSONRPCError{Code: -32004, Message: "cross-tenant access denied"}
}
```

**Además en K8s:** cada tenant tiene su propio namespace (`sbos-<tenant_id>`).
Las NetworkPolicies del FWMAN (3.08 §4) impiden el tráfico cross-namespace.
El doble control (lógico en código + físico en K8s) cumple el principio de defensa en profundidad.

## 7. mTLS en endpoints del Context Plane (Fase III — NRS-03)

Los 6 endpoints del Context Plane en `:9443` requieren certificado cliente cuando
`BOS_MTLS_REQUIRED=true` (activo en producción, desactivado en dev con `BOS_NO_RPC_TOKEN`).

**Flujo de autenticación con mTLS:**

```
Kong → BOS :9443
  Kong presenta cert: CN=kong.sbos.internal, emitido por SBOS-CA-Daemons
  BOS verifica: cert en ClientCAs pool (CA intermedia Vault PKI)
  BOS verifica: CN en allowlist de daemons autorizados
  Si falla → TLS handshake rejected (antes de leer el request body)
```

**En `internal/server/api.go` (Fase III):**
```go
tlsCfg.ClientAuth = tls.RequireAndVerifyClientCert
tlsCfg.ClientCAs = loadVaultPKICAPool()  // pool de CAs confiables
```

**Cert efímero ECDSA P-256 por sesión (A.07 §1):** para sesiones críticas (LoA 3-4 según
RFC 9470), el BOS solicita a Vault PKI un cert efímero de 1h para el ctx_id. Kong adjunta
este cert en el header `X-SBOS-Cert-Thumbprint`. El BOS verifica el thumbprint en cada request
de esa sesión (implementación DPoP-like para ctx_id de alta sensibilidad).

## 8. Audit trail WORM del Context Plane

Toda operación ctx escribe en `bos.ctx_context_audit` (T-397) con hash-chain SHA-256.
La cadena de hashes hace que cualquier modificación retroactiva sea detectable.

```
audit[n].hash = SHA256(audit[n-1].hash + ctx_id + method + result + timestamp)
```

Esto cumple ISO 27001:2022 A.8.15 (logging) con garantía de integridad de la cadena.
Los logs del audit se envían también a Wazuh (NRS-04) para correlación en tiempo real.
