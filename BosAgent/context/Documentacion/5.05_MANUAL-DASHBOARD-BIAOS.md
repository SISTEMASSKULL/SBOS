## 1. Qué es biaOS y por qué es soberano

**biaOS** (BOS Intelligent Autonomous Operating System) es el agente de inteligencia
artificial integrado en el daemon BOS. Es un ciudadano de primera clase del BOS,
no un add-on externo.

**Soberano** significa que el modelo de IA corre **dentro del servidor del cliente**:

| Característica | biaOS | ChatGPT / Claude API |
|----------------|-------|----------------------|
| Modelo | Ollama local (Llama 3.2, Mistral, etc.) | Servidor externo |
| Datos enviados fuera | Nunca | Sí (datos del cliente) |
| Disponibilidad offline | Sí | No |
| Costo por token | 0 | Variable |
| GDPR/soberanía | ✅ completo | ❌ datos salen |
| Latencia | < 100ms (mismo servidor) | 500-3000ms (red) |

El modelo de IA se instala como ficha (`servers/S14-aiserver/ollama/`) mediante
`bosctl ficha install ollama`. El BOS garantiza que el modelo esté disponible antes
de usar biaOS.

## 2. Los 4 métodos bos.ai.* JSON-RPC

### 2.1 `bos.ai.ask` — Consulta libre

```json
// Request
{"jsonrpc":"2.0","method":"bos.ai.ask",
 "params":{"prompt":"¿Cuál es el estado del Context Plane?","ctx_id":"..."},"id":1}

// Response
{"jsonrpc":"2.0","result":{
  "answer": "El Context Plane tiene 3 sesiones activas en Redis. El P99 del ctx_id lookup es 3.2ms (dentro del SLO de 5ms). La tabla bos.ctx_context_session tiene 3 filas. Estado: OPERATIVO.",
  "model": "llama3.2:3b",
  "tokens_used": 128,
  "latency_ms": 87
},"id":1}
```

**El sistema prompt incluye contexto real:** estado actual del BOS (de `bos.dashboard.health`),
métricas recientes (de `bos.capacity.status`), logs de las últimas 15min. La IA responde
**con datos reales**, no con generalidades.

### 2.2 `bos.ai.diagnose` — Diagnóstico autónomo (ICAP Engine)

Este es el método más valioso. Implementa el flujo del Anexo A.08 §2 (Etapa 2 ITIL 4).

```json
// Request
{"jsonrpc":"2.0","method":"bos.ai.diagnose",
 "params":{"ficha_id":"nextcloud","ctx_id":"..."},"id":2}

// Response
{"jsonrpc":"2.0","result":{
  "causa":       "OOMKilled: pod nextcloud-0 fue terminado por el kernel (OOM killer)",
  "evidencia":   "kubectl describe pod nextcloud-0 → LastState: OOMKilled, Exit Code: 137",
  "accion":      "SCALE_VERTICAL",
  "parametros":  {"memory_limit": "2Gi", "memory_request": "1Gi"},
  "confianza":   0.91,
  "alternativas": [
    {"accion": "REPAIR_RESTART", "confianza": 0.45, "razon": "puede ser transitorio"},
    {"accion": "HITL",          "confianza": 0.30, "razon": "datos insuficientes"}
  ],
  "requiere_hitl": false,
  "model": "llama3.2:3b",
  "latency_ms": 234
},"id":2}
```

### 2.3 `bos.ai.run` — Ejecutar acción sugerida

```json
// Tras recibir diagnóstico con confianza >= 0.8 y requiere_hitl=false:
{"jsonrpc":"2.0","method":"bos.ai.run",
 "params":{"ficha_id":"nextcloud","action":"SCALE_VERTICAL",
            "params":{"memory_limit":"2Gi"},"ctx_id":"..."},"id":3}

// Si confianza < 0.8 o requiere_hitl=true → error -32010 "HITL required"
```

### 2.4 `bos.ai.catalog` — Catálogo de acciones disponibles

```json
{"jsonrpc":"2.0","method":"bos.ai.catalog","params":{},"id":4}
// → lista de acciones que la IA puede ejecutar con sus parámetros
```

## 3. ICAP Engine — Intelligent Contextual Action Pipeline

El ICAP Engine es la inteligencia que convierte un diagnóstico en una acción ejecutable.

### 3.1 Flujo del ICAP Engine

```
Entrada: {ficha_id, problema_observado, logs, métricas, estado}
    │
    ▼
[1] Recolección de contexto (8 threads paralelos — A.08 §2)
    ├── thread 1: estado de la ficha (bos.ficha.status)
    ├── thread 2: health check (bos.ficha.probe)
    ├── thread 3: drift vs manifest.yml (bos.ficha.diff)
    ├── thread 4: dependencias degradadas (bos.query.repair)
    ├── thread 5: historial de incidentes (bos.ctx_context_audit)
    ├── thread 6: pod logs (bos.k8s.pod.logs)
    ├── thread 7: ctx_id afectados (bos.ctx.list_by_tenant)
    └── thread 8: política de capacidad (bos.capacity.check)
    │
    ▼
[2] Embedding del diagnóstico
    text_embedding = ollama.embed(context_summary)
    → vector de 768 dimensiones
    │
    ▼
[3] Búsqueda en action_catalog.yml (similitud coseno)
    top_k = cosine_similarity(text_embedding, action_embeddings)[:3]
    → ["SCALE_VERTICAL": 0.91, "REPAIR_RESTART": 0.45, "HITL": 0.30]
    │
    ▼
[4] Generación de respuesta con Ollama
    prompt = system_prompt + context + "Diagnóstica y recomienda acción para: " + ficha_id
    response = ollama.generate(prompt, model="llama3.2:3b")
    │
    ▼
[5] Retornar DiagnoseResult con confianza y alternativas
```

### 3.2 `action_catalog.yml` — Catálogo de acciones

```yaml
actions:
  SCALE_VERTICAL:
    description: "Aumentar memory_limit y memory_request del pod"
    triggers: ["OOMKilled", "memory pressure", "exit code 137"]
    requires_hitl: false
    confidence_threshold: 0.75
    implementation: "bos.k8s.scale --type vertical"

  SCALE_HORIZONTAL:
    description: "Aumentar número de réplicas del deployment"
    triggers: ["high RPS", "CPU throttling", "latency P99 > threshold"]
    requires_hitl: false
    confidence_threshold: 0.80

  REPAIR_RESTART:
    description: "Reiniciar pod sin cambiar configuración"
    triggers: ["CrashLoopBackOff transitorio", "deadlock", "memory leak menor"]
    requires_hitl: false
    confidence_threshold: 0.60

  CONFIG_DRIFT_REPAIR:
    description: "Reaplicar manifest.yml contra estado actual del pod"
    triggers: ["drift detectado en diff", "configuración inesperada"]
    requires_hitl: false
    confidence_threshold: 0.85

  HITL:
    description: "Requiere decisión humana — situación no resuelta automáticamente"
    triggers: ["confianza < 0.5", "datos insuficientes", "acción destructiva"]
    requires_hitl: true
    confidence_threshold: 0.0
```

## 4. Integración con el Watchdog y la saga de reparación

```
Watchdog detecta ficha DEGRADED
   │
   ▼
bos.query.repair (8 threads) → genera DiagnosisResult
   │
   ▼
biaOS.Diagnose(fichaID, diagnosisResult)  ← ICAP Engine
   │
   ├── confianza >= 0.75 + requiere_hitl=false
   │     → Action Engine.Execute(accion, params)
   │     → si éxito: ficha vuelve a INSTALLED
   │     → si falla: siguiente alternativa o HITL
   │
   └── confianza < 0.75 o requiere_hitl=true
         → HITL: notificación a admin + ficha en UNRECOVERABLE si no responde en 1h
```

## 5. Modelos disponibles (Ollama en S14-aiserver)

| Modelo | Tamaño | Uso óptimo | RAM requerida |
|--------|:------:|-----------|:-------------:|
| `llama3.2:3b` | 3B | Diagnóstico rápido (< 200ms) | 4GB |
| `llama3.2:7b` | 7B | Diagnóstico profundo (< 500ms) | 8GB |
| `mistral:7b` | 7B | Razonamiento técnico | 8GB |
| `codellama:7b` | 7B | Análisis de código Go/Bash | 8GB |

El modelo por defecto es `llama3.2:3b` (balance latencia/calidad para diagnóstico en tiempo real).
Configurable en `bos.toml`:
```toml
[biaos]
model = "llama3.2:3b"
timeout_seconds = 30
min_confidence = 0.75
```
