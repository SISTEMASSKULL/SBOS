## 1. Qué es el Port Manager

El **Port Manager** es un subsistema del daemon BOS que administra de forma automática,
determinística y trazable cada puerto TCP/UDP del sistema operativo empresarial.

**No es una herramienta externa. No es un script. No es un proceso manual.** Es código Go
compilado dentro del binario `bos` que el daemon invoca cada vez que una ficha se instala,
se verifica, se repara o se remueve.

### 1.1 El problema que resuelve

SBOS despliega 112+ fichas sobre 16 servidores lógicos. Cada ficha consume entre 2 y 10
puertos entre containerPorts, ClusterIPs, puertos de daemons, NodePorts y rangos SKULL
custom. En un sistema completo hay **más de 400 puertos** conviviendo simultáneamente.

Sin el Port Manager, cada asignación es una decisión humana:
- ¿Qué ClusterIP le pongo a esta ficha?
- ¿Colisiona con alguna de las otras 111?
- ¿Alguien lo registró en el documento?
- ¿El Service YAML tiene el puerto correcto?

**Con el Port Manager, el BOS resuelve todo automáticamente en < 10ms.**

### 1.2 Ubicación en la arquitectura

```
DAEMON BOS (binario único, Go estático)
│
├── internal/
│   ├── installer/        ← orquestador de sagas
│   ├── k8s/              ← dispatcher kubectl
│   ├── reconcile/        ← detección de drift
│   ├── health/           ← health checker
│   ├── portman/          ← PORT MANAGER (NUEVO)
│   │   ├── engine.go     ← algoritmos de asignación
│   │   ├── rfc6335.go    ← proceso RFC 6335
│   │   ├── conflict.go   ← verificación 3 capas
│   │   ├── kardex.go     ← CRUD bos.port_assignment
│   │   ├── validate.go   ← drift detection de puertos
│   │   ├── export.go     ← exportador SBOS-050
│   │   └── server/
│   │       └── jsonrpc.go ← 7 métodos JSON-RPC
│   └── ...
```

## 2. Por qué existe — justificación arquitectónica

### 2.1 Principio de no intervención manual (ADR-022)

La regla R1 del SBOS establece: **"Nada se ejecuta de forma manual."** Asignar puertos
manualmente viola esta regla. Cada `kubectl expose` manual, cada Service YAML escrito a
mano con un ClusterIP elegido "porque me pareció libre", es una violación.

El Port Manager materializa ADR-022 en el espacio de puertos: el BOS asigna, verifica y
registra. El humano solo ejecuta `bosctl ficha install`.

### 2.2 Trazabilidad ISO 27001

La norma ISO 27001:2022 A.8.20 exige un inventario actualizado de cada activo de red,
con registro de cambios y responsable. Sin el Kardex, el SBOS no puede demostrar
cumplimiento. Con el Kardex, cada puerto tiene trazabilidad completa: quién lo asignó,
cuándo, para qué, con qué referencia documental.

### 2.3 Idempotencia de la saga de instalación

La saga de instalación debe ser idempotente (regla R3). Si `bosctl ficha install keycloak`
se ejecuta dos veces, la segunda debe detectar que los puertos ya están asignados y
reutilizarlos — no fallar con "puerto en uso" ni asignar otros nuevos. El Kardex
garantiza esto: misma ficha, mismos puertos, siempre.

### 2.4 Escalabilidad del catálogo

Con 112 fichas actuales y crecimiento previsto, el espacio de puertos requiere gestión
automatizada. El Algoritmo A (fórmula) cubre el 95% de casos. El Algoritmo B (hash
SHA256) cubre el 5% restante cuando un bloque de servidor se agota. Sin el Port Manager,
cada ficha nueva requeriría una decisión de arquitectura.

## 3. Cómo funciona — ciclo de vida

### 3.1 Diagrama de flujo

```
OPERADOR: bosctl ficha install <nombre>
              │
              ▼
┌──────────────────────────────────────────────────────────────┐
│                 DAEMON BOS                                    │
│                                                               │
│  ┌─────────────────────────────────────────────────────────┐ │
│  │ installer/orchestrator.go                                │ │
│  │                                                          │ │
│  │  "Instalar ficha <nombre>"                               │ │
│  │         │                                                │ │
│  │         ├──► DEPENDENCY_RESOLVER: orden DAG ✅           │ │
│  │         │                                                │ │
│  │         ├──► PORT MANAGER: bos.portman.assign  ← NUEVO  │ │
│  │         │      │                                         │ │
│  │         │      ├─► engine.go: derivar puertos            │ │
│  │         │      ├─► conflict.go: verificar 3 capas        │ │
│  │         │      ├─► rfc6335.go: validar contra estándar   │ │
│  │         │      ├─► kardex.go: registrar en BD            │ │
│  │         │      └─► retorna Service YAML                  │ │
│  │         │                                                │ │
│  │         ├──► K8S CORE: kubectl apply service.yaml        │ │
│  │         │                                                │ │
│  │         └──► HEALTH CHECK: puerto responde ✅            │ │
│  └─────────────────────────────────────────────────────────┘ │
│                                                               │
│  ┌─────────────────────────────────────────────────────────┐ │
│  │ reconcile/scheduler.go (ciclo cada 300s)                 │ │
│  │                                                          │ │
│  │  PORT MANAGER: bos.portman.validate                      │ │
│  │         │                                                │ │
│  │         ├─► kardex.go: leer todos los puertos asignados  │ │
│  │         ├─► validate.go: comparar con K8s real           │ │
│  │         └─► si drift → alerta watchdog                   │ │
│  └─────────────────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────────────────┘
```

### 3.2 Flujo de asignación (bos.ficha.install)

El Port Manager se invoca automáticamente durante la instalación. El orquestador no elige
puertos — el Port Manager los retorna y el orquestador los aplica.

**Secuencia exacta:**

1. El orquestador verifica que las dependencias de la ficha están satisfechas (DAG)
2. El orquestador invoca `bos.portman.assign` con el `manifest.yml` de la ficha
3. El Port Manager ejecuta el proceso RFC 6335 (5 pasos, < 10ms)
4. El Port Manager retorna las asignaciones + Service YAML generado
5. El orquestador aplica el Service YAML vía K8s Core
6. El health checker verifica que el puerto responde

### 3.3 Flujo de liberación (bos.ficha.remove)

1. El orquestador elimina el Service y Deployment vía K8s Core
2. El orquestador invoca `bos.portman.release` con el `ficha_id`
3. El Port Manager transiciona todos los puertos a `liberado` (RFC 6335 De-Assignment)
4. Los puertos quedan en el Kardex como registro histórico — no se reasignan automáticamente

### 3.4 Flujo de validación (reconciliación cada 300s)

1. El scheduler de reconciliación invoca `bos.portman.validate`
2. El Port Manager lee todos los registros `asignado` del Kardex
3. Consulta `kubectl get svc --all-namespaces` para obtener la realidad K8s
4. Compara: cada registro debe tener un Service. Cada Service debe tener un registro
5. Si hay discrepancia → alerta `DRIFT_PORT` al watchdog unificado

## 4. Los dos algoritmos

### 4.1 Algoritmo A — Fórmula determinística

```
ClusterIP = BASE_SERVIDOR + (ÍNDICE_FICHA × 10) + TIPO_T
```

**Uso:** 95% de los casos. La fórmula es predecible, legible por humanos y trazable sin
herramientas. Un operador puede calcular mentalmente que la ficha 3 del servidor S03 con
tipo HTTP usa el puerto `8200 + (3×10) + 0 = 8230`.

**Origen:** RFC 7422 §5.1 Algorithm 0 (Sequential Deterministic CGN).

### 4.2 Algoritmo B — Hash SHA256

```
hash_input  = ficha_id + ":" + tipo_desc + ":" + clash_counter
hash_bytes  = SHA256(hash_input)[0:4]
hash_int    = big_endian_u32(hash_bytes)
puerto      = RANGO_MIN + (hash_int % RANGO_SIZE)
```

**Uso:** 5% de los casos — cuando el bloque del servidor está agotado. El puerto resultante
no es legible por humanos, pero el Kardex mantiene la trazabilidad.

**Origen:** Marathon-LB (Mesosphere/DCOS) + ISO Code (Rust crate).

### 4.3 Selección automática

El Port Manager decide cuál usar sin intervención humana:
- Si `ficha_index < (TAMAÑO_BLOQUE / 10)` → Algoritmo A
- Si el bloque está agotado tras 5 reintentos N2 → Algoritmo B

## 5. El Kardex — fuente de verdad

El Kardex es la tabla `bos.port_assignment` en `SBOS_db`. Es la **fuente de verdad**
para toda asignación de puertos en el SBOS.

| Propiedad | Valor |
|-----------|-------|
| **Motor** | PostgreSQL 18.4 (misma instancia que SBOS_db) |
| **Schema** | `bos` |
| **PK** | UUIDv7 (RFC 9562) — time-ordered |
| **Inmutabilidad** | Filas nunca se borran — transicionan `asignado → liberado → revocado` |
| **Unicidad** | CONSTRAINT `uq_port_type_ns` sobre `(puerto, tipo_puerto, namespace)` |
| **Trazabilidad** | `asignado_por` + `asignado_en` + `referencia_doc` + `service_name` |
| **Consultable** | JSON-RPC `bos.portman.lookup` + CLI `bosctl port lookup` |

El Kardex es al Port Manager lo que `.sbos_state.json` es al STATE_MANAGER: el estado
centralizado que permite retomar, auditar y reconciliar.

## 6. Interface — JSON-RPC 2.0

El Port Manager expone 7 métodos vía el socket Unix `/opt/skull/SBOS/runtime/bos.sock`:

| Método | Quién lo invoca | Cuándo |
|--------|----------------|--------|
| `bos.portman.assign` | `installer/orchestrator.go` | Durante `bos.ficha.install` |
| `bos.portman.release` | `installer/orchestrator.go` | Durante `bos.ficha.remove` |
| `bos.portman.validate` | `reconcile/scheduler.go` | Ciclo de reconciliación (cada 300s) |
| `bos.portman.lookup` | `bosctl` CLI, `biaos` (agente IA) | Bajo demanda |
| `bos.portman.check` | `bosctl` CLI, `biaos` | Dry-run antes de asignar |
| `bos.portman.list` | `bosctl` CLI | Auditoría, debugging |
| `bos.portman.export` | `bosctl` CLI | Sincronizar SBOS-050.md |

**Interface Dual (ADR-020):** los primeros 3 métodos son invocados por el daemon
(JSON-RPC interno). Los últimos 4 son invocados por `bosctl` (WebSocket RPC) o por
agentes IA vía `biaos` (JSON-RPC).

## 7. CLI — `bosctl port`

```bash
bosctl port lookup 8200                    # ¿Quién usa el puerto 8200?
bosctl port lookup --ficha keycloak        # ¿Qué puertos usa keycloak?
bosctl port list --server S03              # Todos los puertos de identityserver
bosctl port list --state liberado           # Puertos disponibles para reasignar
bosctl port check --server S03 --ficha nueva-app  # ¿Habrá conflicto?
bosctl port validate                       # Auditar Kardex vs K8s real
bosctl port export --format markdown        # Generar SBOS-050.md
```

## 8. Integración con otros subsistemas

| Subsistema | Integración |
|-----------|------------|
| **installer/orchestrator** | Invoca `assign` antes de crear el Service K8s. Invoca `release` después de eliminar el Service |
| **k8s/core** | Recibe el Service YAML generado por el Port Manager y lo aplica |
| **reconcile/scheduler** | Invoca `validate` cada 300s para detectar drift |
| **watchdog/unified** | Recibe alertas `DRIFT_PORT` cuando el Kardex y K8s no coinciden |
| **state/manager** | El Kardex es independiente de `.sbos_state.json` — son fuentes de verdad separadas |
| **health/checker** | Verifica que los puertos del Kardex responden (TCP probe al ClusterIP) |
| **biaos** (agente IA) | Consulta `lookup` y `check` antes de proponer instalación de fichas |
| **context/service** | El ctx_id incluye el puerto de destino. Kong valida contra el Kardex vía Context API |

## 9. Criterios de aceptación

El Port Manager se considera operativo cuando:

| # | Criterio | Verificación |
|:--|----------|-------------|
| C1 | `bosctl ficha install <cualquier-ficha>` asigna puertos sin input humano | Instalar 10 fichas seguidas sin tocar un solo número de puerto |
| C2 | La misma ficha instalada 2 veces recibe los mismos puertos (idempotencia) | `install → remove → install` → mismos ClusterIPs |
| C3 | Un conflicto de puerto se resuelve automáticamente sin bloquear la saga | Instalar ficha con mismo índice → auto-incremento → OK |
| C4 | `bosctl port validate` detecta drift entre Kardex y K8s real | Borrar un Service manualmente (`kubectl delete svc`) → `validate` lo detecta |
| C5 | `bosctl port export` produce un SBOS-050.md idéntico en estructura al documento canónico | `diff <(bosctl port export) <(cat SBOS-050.md)` → solo difieren timestamps |
| C6 | El Kardex sobrevive a un reinicio del daemon sin pérdida de datos | `systemctl restart bos` → `bosctl port list` muestra los mismos puertos |
| C7 | Tests con race detector pasan limpios | `go test -race -count=2 ./internal/portman/...` → PASS |

## 11. El Port Manager en la saga de instalación

El Port Manager no es un paso más en la saga — es un **servicio transversal** que el
orquestador consulta. No aparece como "Paso 8" en la lista de pasos de `deployTenant()`.
Aparece **dentro** de cada instalación de ficha:

```
SAGA deployTenant():
  ┌────────────────────────────────────────────────────────────┐
  │ PASO 0: kubeadm + kubectl                                  │
  │ PASO 1: Namespace K8s + NetworkPolicy                      │
  │   ...                                                      │
  │ PASO 7: Fichas del tenant                                  │
  │   for _, ficha := range cfg.Fichas {                       │
  │     │                                                      │
  │     │  PORT MANAGER (automático, dentro de installFicha)   │
  │     │  ├─ bos.portman.assign                               │
  │     │  ├─ retorna Service YAML                             │
  │     │  └─ registra en Kardex                               │
  │     │                                                      │
  │     installFicha(ficha)  ← Service YAML ya incluye puertos │
  │   }                                                        │
  └────────────────────────────────────────────────────────────┘
```

**El operador de la saga nunca ve los puertos.** El Port Manager los resuelve y la saga
continúa. Esto cumple la regla R1 (nada manual) y R3 (idempotencia).
