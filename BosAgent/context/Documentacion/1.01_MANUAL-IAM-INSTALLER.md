## 1. Audiencia, propósito y alcance

**Audiencia:** todo desarrollador del BOS y del ecosistema SBOS. Este manual explica cómo el BOS
resuelve Day 0: transformar Ubuntu 26.04 virgen en un cluster Kubernetes con el stack completo
(PostgreSQL, Redis, Vault, bauth, Kong) y continuar hasta el escritorio VDI.

**Propósito:** documentar la cadena completa de instalación con honestidad técnica — qué está
implementado, qué compila, qué falta verificar en VPS, y por qué el orden de instalación es
**delicado e innegociable**.

**Alcance:** desde `install.sh` (el único script externo permitido) hasta el VDI server
operativo. Cubre bootstrap del SO, despliegue del stack, y la cadena de dependencias entre
fichas. No cubre el desarrollo de nuevas fichas (3.01) ni el Context Plane en detalle (4.01).

## 2. El problema del huevo y la gallina — ADR-040

### 2.1 El problema

El stack SBOS tiene **dependencias circulares** que impiden una instalación secuencial ingenua:

```
Vault necesita PostgreSQL como backend de almacenamiento
PostgreSQL necesita Vault para obtener credenciales en producción
K8s necesita Calico como CNI
Calico necesita K8s para desplegarse como DaemonSet
NetworkPolicies necesitan Calico
Calico necesita NetworkPolicies para asegurarse
```

Si cada ficha exige que TODAS sus dependencias estén completas antes de empezar, **nada se puede
instalar**. Este es el clásico problema del huevo y la gallina en infraestructura.

### 2.2 La solución — Mínimo Viable Progresivo (ADR-040)

**Cada ficha se instala en modo mínimo viable primero, y se especializa en sucesivas pasadas
hasta alcanzar su configuración completa.**

```
Pasada 1: MÍNIMO VIABLE (cada ficha funciona con defaults bootstrap, sin dependencias externas)
  ├─ PG: credenciales bootstrap en texto plano (desarrollo), sin Vault
  ├─ Vault: init con Shamir, sin secretos de otras fichas aún
  ├─ KC: realm creado con credenciales bootstrap, sin Vault
  └─ Kong: database reachable, sin TLS externo

Pasada 2: ROBUSTECER (segunda pasada sobre las mismas fichas)
  ├─ PG: credenciales migradas a Vault → bosctl ficha repair postgresql
  ├─ Vault: paths para cada ficha → bosctl ficha update vault
  ├─ KC: credenciales en Vault → bosctl ficha repair keycloak
  ├─ Kong: TLS 1.3 con certs Vault PKI → bosctl ficha repair kong
  └─ Redis: ACLs desde Vault → bosctl ficha repair redis

Pasada N: CERTIFICAR (sucesivas pasadas hasta estado deseado)
  └─ bosctl ficha repair <nombre> es idempotente — detecta estado actual y converge
```

### 2.3 Reglas obligatorias para toda ficha

**Toda ficha DEBE:**
1. Tener un modo "mínimo viable" que funcione sin dependencias externas completas
2. `ficha_repair()` DEBE detectar el estado actual y converger al estado deseado (idempotente)
3. Las credenciales bootstrap son TEMPORALES — la segunda pasada las reemplaza por Vault
4. `task_catalog.sh` DEBE detectar el entorno (k3s vs kubeadm) y adaptarse

**Ninguna ficha debe:**
- Exigir que Vault esté operativo para instalarse en Pasada 1
- Fallar si su dependencia existe pero en modo mínimo (no completo)
- Usar `kubectl` sin verificar antes que el kubeconfig existe (short-circuit `&&`)

### 2.4 Por qué el orden de instalación es delicado

Violar el orden de capas o el principio de mínimo viable **rompe la instalación de forma
irreparable**:
- Instalar Vault antes que PostgreSQL → Vault no tiene backend, init falla
- Instalar Kong antes que Keycloak → Kong no tiene OIDC provider, rutas rotas
- Exigir TLS en Pasada 1 → certificados no existen aún (Vault PKI no está operativo)
- Instalar fichas en paralelo sin respetar el DAG topológico → condiciones de carrera

**El BOS protege este orden mediante:**
1. **DEPENDENCY_RESOLVER** (Kahn) — calcula el orden topológico sin ciclos
2. **Ficha Engine** — ejecuta las fichas en oleadas (una oleada = fichas sin dependencias entre sí)
3. **bootstrap verify** — cada capa se certifica (C-01..C-08) antes de avanzar a la siguiente

## 3. La arquitectura de servidores lógicos — crecimiento horizontal futuro

### 3.1 El concepto: servidores lógicos como unidades de migración

El stack SBOS organiza sus ~112 aplicaciones en **16 servidores lógicos** (S00–S15). Cada
servidor lógico es una **unidad de migración horizontal**: el día que el sistema necesite crecer,
el servidor lógico completo se traslada a un VPS físico dedicado.

```
Hoy (single-node):
  ┌─────────────────────────────────────────┐
  │  Ubuntu 26.04 (VPS único)               │
  │  ├─ S00-hostserver (bootstrap, daemons) │
  │  ├─ S01-dataserver (PG, Redis, MinIO)   │
  │  ├─ S02-gatewayserver (Kong, Vault)     │
  │  ├─ S03-identityserver (Keycloak)       │
  │  ├─ ... S04–S15                         │
  │  └─ Todo en UN nodo K8s                 │
  └─────────────────────────────────────────┘

Futuro (multi-node horizontal):
  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐
  │ VPS 1 (host) │  │ VPS 2 (data) │  │ VPS 3 (id)   │
  │ S00-host     │  │ S01-data     │  │ S03-identity │
  │ daemons      │  │ PG, Redis    │  │ Keycloak     │
  └──────────────┘  └──────────────┘  └──────────────┘
  ┌──────────────┐  ┌──────────────┐
  │ VPS 4 (gw)   │  │ VPS 5 (vdi)  │
  │ S02-gateway  │  │ S11-vdi      │
  │ Kong, Vault  │  │ Nextcloud    │
  └──────────────┘  └──────────────┘
```

**Cada servidor lógico se lleva ENTERO a su VPS dedicado: fichas + recursos + datos + políticas.**
No es organización estética — es la frontera de despliegue físico.

### 3.3 Reglas de ubicación

1. **Ubicación por función, no por consumidor.** PostgreSQL vive en S01-dataserver aunque
   Keycloak (S03) lo consuma. MongoDB vive en S01 aunque Rocket.Chat (S10) lo use. La
   pregunta es "¿qué función cumple esta app?", no "¿quién la usa?".

2. **Fuente única, cero réplicas.** `SBOS/servers/` es el ÚNICO lugar donde vive una ficha.
   Prohibido copiarla a BosAgent, BauthAgent, o cualquier agente. Un agente que necesita
   una ficha la LEE de aquí; no la duplica.

3. **Cada servidor es autónomo.** Sus fichas + recursos + políticas migran como bloque. El
   día que S01-dataserver se mueva a su propio VPS, todo lo que necesita viaja con él.

4. **El orden de carga lo resuelve el motor, no una lista manual.** El DEPENDENCY_RESOLVER
   (Kahn) calcula el DAG a partir de `depends_on` del manifest.yml de cada ficha.

### 3.4 Organización K8s — 3 mecanismos para agrupar pods vivos

| Mecanismo | Qué hace | Ejemplo |
|-----------|----------|---------|
| **Label estándar** | `app.kubernetes.io/part-of=<servidor>` en cada pod | `part-of=dataserver` |
| **Namespace** | Un namespace por servidor lógico | `sbos-data`, `sbos-identity`, `sbos-vdi` |
| **Node affinity** | Crecimiento horizontal: pods de un servidor → nodo físico dedicado | `nodeSelector: {tipo: dataserver}` |

Todos los pods heredan el label `part-of=<servidor>` desde el manifest.yml de su ficha.
Así los pods vivos quedan agrupados por la misma lógica que las fichas — una sola verdad.

### 3.5 El rol del BOS en servers/

`servers/` es **espacio público del proyecto** — todos los daemons declaran sus fichas aquí.
Lo que es **exclusivo del BOS** es:

- **Leer** el catálogo de servidores lógicos y descubrir fichas (`internal/ficha/discovery.go`)
- **Instalar** fichas en orden topológico según el DAG de dependencias
- **Reparar** fichas degradadas (`bosctl ficha repair`)
- **Verificar** el estado de cada ficha contra su health check declarado
- **Reconciliar** drift entre lo declarado y lo real cada 15 minutos

**Lo que NO es exclusivo del BOS:**
- Declarar fichas — cualquier daemon puede crear su ficha en el servidor lógico que le corresponda
- Mantener el task_catalog.sh de su propia ficha
- Definir el PROPOSITO.md de sus aplicaciones

**Regla de oro (servers.yml §5):** "Función que menciona una app concreta → va en SU
task_catalog.sh. Función universal → va en el motor (bos)."

### 3.6 Anatomía canónica de una ficha

Toda ficha en `servers/<servidor>/<app>/` debe contener:

| Archivo | Obligatorio | Propósito |
|---------|:-----------:|-----------|
| `manifest.yml` | ✅ | Identidad, dependencias, servidor, namespace, puerto, governance, health |
| `PROPOSITO.md` | ✅ | Qué es, por qué existe, para qué sirve, quién la declara, dependencias, motivo del servidor |
| `task_catalog.sh` | ✅ (si tiene lógica) | Funciones `<app>_install`, `<app>_verify`, `<app>_health`, `<app>_repair`, `<app>_remove` |
| `yaml_engine.yml` | Opcional | Fases declarativas (pre_install, install, post_install, verify, commit) |
| `<app>.k8s.yml` | Opcional | Manifest K8s (Deployment/StatefulSet) |
| `<app>.network` | Opcional | NetworkPolicy |
| `resources/` | Opcional | Artefactos: sql/, config/, keycloak/, vault/, migrations/ |

**Sin PROPOSITO.md, el Bibliotecario rechaza la ficha.** No es opcional.

### 3.7 Arquitectura de base de datos — `SBOS_db` y el schema `bos`

La base de datos del ecosistema SBOS sigue un modelo de **schema-per-service** sobre una
**única base de datos** (`SBOS_db`). Esto permite que 100+ aplicaciones compartan la misma
infraestructura sin colisiones de nombres y con un solo punto de backup.

```
SBOS_db (PostgreSQL 18.4)
  ├─ bglobal.*     → catálogos globales (ISO 4217, 639, 3166, timezone, menús)
  ├─ bos.*         → BOS Control Plane (7 tablas, 5 ENUMs)
  ├─ bauth.*       → núcleo de identidad (~179 tablas, 13 dominios D1-D12+SEC)
  ├─ bcalendar.*   → calendario fiscal multi-nivel
  └─ (futuro) biedata, bsearch, bnexus, bnotify...
```

**El schema `bos` contiene 7 tablas** (definidas en `DDLs/migrations/bos_01__control_plane.sql`,
528 líneas, idempotente):

| Tabla | Propósito | Dueño |
|-------|-----------|-------|
| `bos.registered_device` | Dispositivos pre-auth (dctx_id, BitMask=0x0) | bos.ctx.device.register |
| `bos.context_session` | Sesiones post-auth (ctx_id, BitMask>0, FK→registered_device) | bos.ctx.promote |
| `bos.ficha_state` | Estado actual de cada ficha (18 estados ADR-021) | Saga Engine |
| `bos.ficha_event` | Historial inmutable de eventos por ficha (append-only) | Saga Engine |
| `bos.bootstrap_event` | Registro de eventos de bootstrap (6 capas) | Bootstrap Engine |
| `bos.cap_snapshot` | Instantáneas de ~30 métricas cada 60s (M5.1) | Motor Observación |
| `bos.cap_estimate` | Configuración de capacidad declarada por tenant | bos.capacity.* |

**Ubicación de las DDLs:** `/opt/skull/orquestador/proyectos/SBOS/DDLs/`
- **Migrations:** `DDLs/migrations/` — estructura de tablas (DDL)
- **Seeds:** `DDLs/seeds/` — datos iniciales idempotentes
- **Orquestador:** `DDLs/inicializar_sbos_db.sh` — único punto de carga
- **Doctrina:** `DDLs/ddls.yml` — reglas de nomenclatura y gobierno

**Convención de nombres:** `<servicio>_<NN>__<descripcion>.sql`
- `bos_01__control_plane.sql` — migración del schema bos (528 líneas)
- `bauth_16__ath_config_d1.sql` — seed de configuración D1
- `bglobal_01__global_country.sql` — seed de catálogo global

**Reglas innegociables (ddls.yml):**
1. **Idempotencia:** `CREATE TABLE IF NOT EXISTS`, `ON CONFLICT`, cero `DROP` en carga normal. Cargar dos veces = mismo resultado, sin error.
2. **Una sola BD:** `SBOS_db`. Un schema por microservicio. Cero bases de datos por servicio.
3. **Versión en git, no en el nombre:** Prohibido `_v2`, `_final`, `_clean`, `_fix`. El objeto lógico = un archivo único. Git lleva la historia.
4. **Desarrollo:** se corrige la MISMA DDL in-situ. **Producción:** DDL congelada, cambios vía migraciones incrementales nuevas (ALTER).
5. **Autonomía:** ninguna DDL/seed llama a otra con `\i`/`\ir`. El orden lo decide `inicializar_sbos_db.sh`.
6. **Aprobación humana:** todo cambio de DDL o seed requiere aprobación explícita antes de commitear.

**El BOS y las DDLs:**
- El schema `bos` ya tiene su migración inicial (`bos_01__control_plane.sql`, 528 líneas)
- El código Go actual usa `information_schema.tables` para verificar existencia (AutoMigrate parcial)
- **Falta:** crear los seeds `bos_*` en `DDLs/seeds/` para poblar tablas como `bos.ficha_state` con datos iniciales de fichas
- **Falta:** el código Go debe migrar de queries sin schema (`SELECT * FROM context_sessions`) a queries con schema (`SELECT * FROM bos.context_session`)

## 4. Las 6 capas del bootstrap progresivo

El bootstrap sigue el modelo de ADR-040. **Ningún átomo de Capa N+1 se ejecuta si la Capa N no
está completa y verificada.**

```
CAPA 0 — S-HOST (OS)
  bos-preflight: paquetes SO, usuario bosagent (uid=999), directorios canónicos, TLS cert
  sbos-bootstrap-os: kernel modules (br_netfilter, overlay), sysctl K8s, /data/
  Verificación: C-01 ✅

CAPA 1 — S-HOST (K8s mínimo viable)
  sbos-bootstrap-k8s: kubeadm v1.32.x + containerd (SystemdCgroup=true) + Calico 3.32.0
  sbos-bootstrap-cni: Calico CNI operativo, NetworkPolicy funcional
  sbos-bootstrap-storage: StorageClass local-path, PVCs funcionales
  Verificación: C-02 ✅, C-03 ✅

CAPA 2 — S01 (Datos — Pasada 1 mínima)
  postgresql: PG 18.4, SBOS_db (schemas por daemon) + BDs de aplicaciones, wal_level=logical_slot, credenciales bootstrap
  redis: Redis 8.6.2, 3 DBs (cache/ctx_id/streams), AOF, credenciales bootstrap
  minio: object storage mínimo, 3 buckets (backups/assets/documents)
  Verificación: C-04 ✅, C-05 ✅

CAPA 3 — S02-S03 (Identidad y Gateway — Pasada 1 mínima)
  vault: init + unseal Shamir (3/5), PKI root CA, AppRole por ficha, secret/ engine
  keycloak: realm {tenant}, 5 SPIs custom (BosRolTemplate, FinancialDomain, etc.)
  kong: API Gateway, database reachable, plugins OIDC + rate-limit + ctx-inject
  Verificación: C-06 ✅, C-07 ✅, C-08 ✅

CAPA 4 — S06 (Notificaciones)
  sbos-notifier: push MFA + notificaciones del sistema
  Verificación: C-09 (futuro)

CAPA 5 — S-HOST (Hardening — Pasada 2)
  sbos-bootstrap-hard: CIS hardening, UFW, Kyverno, auditoría
  postgresql (2da pasada): migrar credenciales a Vault
  redis (2da pasada): ACLs desde Vault
  vault (2da pasada): PKI intermediate, rotación de secretos
  keycloak (2da pasada): credenciales en Vault, FAPI 2.0
  kong (2da pasada): TLS 1.3 con certs Vault, ctx-inject Lua plugin
```

**Estado actual (julio 2026):**
- Capas 0-1: código completo, verificado parcialmente en VPS (kubeadm corrió, Calico OK, namespaces creados)
- Capa 2: código completo (postgresql 820 líneas, redis 584 líneas), pendiente verificación en VPS
- Capa 3: código inicial (fichas creadas con task_catalog.sh), pendiente verificación en VPS
- Capa 4-5: sin implementar

## 5. El flujo completo de instalación por CLI

**Un solo comando desde Ubuntu virgen hasta el stack operativo:**

```bash
# 1. Clonar el repositorio de instalación
git clone https://github.com/SISTEMASSKULL/bos-install.git && cd bos-install

# 2. Instalar el sistema (6 pasos automáticos)
sudo ./bin/bosctl setup --mode=prod --seed ./seed-skull.yml

# 3. El daemon arranca automáticamente vía systemd
#    Ejecuta auto_bootstrap → runNormal → inicia 15 subsistemas

# 4. Verificar el estado del daemon
bosctl health
# → running

# 5. Verificar el bootstrap (8 criterios)
bosctl bootstrap verify
# → C-01..C-08 con ✅/❌

# 6. Desplegar el tenant (saga de 7 pasos con compensación)
bosctl deploy seed-skull.yml
# → Paso 1/7: Tenant bauth configurado ✅
# → Paso 2/7: Namespace K8s ✅
# → ...
# → Paso 7/7: Fichas del tenant ✅

# 7. Verificar el stack completo
bosctl bootstrap verify --full
# → 8/8 ✅ APROBADA
```
| Comando | Propósito |
|---------|-----------|
| `bosctl setup --mode=prod` | Instalación inicial del sistema |
| `bosctl setup --mode=prod --seed ./seed.yml` | Instalación con seed pre-configurado |
| `bosctl deploy <seed.yml>` | Desplegar tenant (saga 7 pasos) |
| `bosctl bootstrap verify` | Verificar criterios C-01..C-08 |
| `bosctl bootstrap verify --full` | Verificación completa con salida detallada |
| `bosctl ficha install <nombre>` | Instalar UNA ficha específica |
| `bosctl ficha repair <nombre>` | Reparar ficha (idempotente) |
| `bosctl ficha status <nombre>` | Estado detallado de una ficha |
| `bosctl ficha list` | Listar todas las fichas descubiertas |
| `bosctl ficha plan` | Mostrar DAG de instalación (orden topológico) |
| `bosctl tenant list` | Listar tenants instalados |
| `bosctl health` | Salud del daemon |
| `bosctl health-report` | Reporte completo de salud |

## 6. Fase 1: system-install — los 6 pasos
```bash
sudo bosctl system-install --mode=prod
```

### Paso 1 — binarios
Copia `bos` y `bosctl` a `/opt/bos/bin/`. Detecta la ubicación del ejecutable actual con
`os.Executable()` para encontrar los binarios companion.

### Paso 2 — core
Copia el directorio `servers/` (fichas declarativas) y recursos del sistema a `/opt/bos/core/`.

### Paso 3 — blibs
Copia bibliotecas compartidas a `/opt/bos/blibs/`.

## 7. Fase 2: auto_bootstrap — verificación y corrección del SO

Implementado en `cmd/bos/auto_bootstrap.go` (89 líneas). Se ejecuta al arrancar `bos.service`,
**antes** de `runNormal`.

```go
func autoBootstrap(benv *bootstrapEnv) {
    // 1. Setup del sistema (directorios, sysctl, permisos)
    bootstrap.Setup(cfg)                    // internal/bootstrap/setup.go (273 líneas)

    // 4. Red bridge — conectividad de pods K8s
    network.EnsureBridgeNetwork()
}
```

### Bootstrap Setup (273 líneas)
Verifica y crea la estructura completa de directorios y archivos del sistema. Sin este paso,
los 15 subsistemas de `runNormal` no pueden inicializarse.

### Cgroup v2 (internal/cgroup/cgroup.go)
El BOS requiere cgroup v2 para operar. `auto_bootstrap`:
1. Detecta el estado actual del cgroup
2. Si el ownership es incorrecto → `os.Chown()`
3. Si la delegación falla en bare-metal → configura `systemd Delegate=yes` y recarga
4. Si falla en contenedor → ejecuta `host-setup.sh` o sugiere `--cgroupns=host`

**Es crítico que este paso se complete.** Sin delegación de cgroup, K8s no puede gestionar
recursos de pods y el cluster no funciona.

## 8. Fase 3: runNormal — arranque del daemon y sus 15 subsistemas

Implementado en `cmd/bos/run_normal.go` (445 líneas). Es el corazón del daemon. Inicializa

## 9. Fase 4: deploy — saga de 7 pasos con compensación

Una vez que el daemon está corriendo, el operador despliega el tenant con:


La saga ejecuta 7 pasos en orden. Si el paso N falla, los pasos 1 a N-1 se revierten
automáticamente (compensación inversa). **El sistema nunca queda en estado inconsistente.**

| Paso | Acción | Ficha | Timeout | Compensación |
|:----:|--------|-------|:-------:|-------------|
| 1 | Configurar tenant en bauth como IdP nativo | keycloak | 120s | Eliminar realm |
| 2 | Crear Namespace K8s + NetworkPolicy + Quota | sbos-namespace | 30s | Eliminar namespace |
| 3 | Provisionar SBOS_db + schemas por daemon + BDs de apps | postgresql | 180s | Eliminar BDs y schemas |
| 4 | Crear paths Vault + AppRole | vault | 180s | Eliminar paths |
| 5 | Inicializar Context Registry Redis DB1 | redis | 120s | FLUSHDB DB1 |
| 6 | DDL context_sessions + device_contexts | context | 60s | DROP TABLE |
| 7 | Instalar fichas del tenant (DAG topológico) | varias | 600s | Compensación inversa |
