
### 1.2 Lo que nginx hace hoy (ficha S02/nginx)

| Responsabilidad | Implementación |
|-----------------|---------------|
| TLS termination | Cert autofirmado (openssl x509 SAN IP) o Let's Encrypt (certbot S02) |
| HTTP→HTTPS redirect | `server { listen 80; return 301 https://...}` |
| Reverse proxy VDI | `location /desktop/` → oauth2-proxy → fedora-kde pod |
| Reverse proxy apps | `location /guacamole/`, `/nextcloud/`, `/grafana/`, `/onlyoffice/` |
| Gateway soberano | `location @kong` catch-all → Kong :8000 |
| Landing page SBOS | `/var/www/html/index.html` (HTML estático) |
| Headers de seguridad | HSTS · X-Frame-Options · X-Content-Type-Options · CSP |
| Log SBOS | Formato `ctx_id + tenant + remote + method + status + duration` |
| Certbot ACME | `location /.well-known/acme-challenge/` → `/var/www/certbot` |

### 1.3 Lo que nginx NO hace hoy (gap → S16 / bcms)

- No sirve páginas web de empresas cliente (tenant pages)
- No hay virtual hosting por subdominio (`empresa.sbos.app`)
- No hay CMS — el contenido es solo el `index.html` estático de SBOS
- No hay páginas por sucursal (`sucursal.empresa.sbos.app`)
- No hay sistema de plantillas ni gestión de contenido
- No hay rutas personalizadas por tenant/empresa

## 2. Modelo de dominios

### 2.1 Jerarquía de dominios SBOS

```
sbos.app                         ← dominio raíz del operador (SKULL)
│
├── skull.sbos.app               ← tenant interno (SKULL)
│   ├── app.skull.sbos.app       ← aplicación interna
│   └── admin.skull.sbos.app     ← panel administrativo
│
├── acme.sbos.app                ← tenant externo "ACME SA"
│   ├── www.acme.sbos.app        ← sitio web corporativo (CMS)
│   ├── tienda.acme.sbos.app     ← tienda/catálogo
│   ├── cochabamba.acme.sbos.app ← sucursal Cochabamba
│   └── lapaz.acme.sbos.app      ← sucursal La Paz
│
└── mi-empresa.sbos.app          ← o bien dominio personalizado:
    └── www.mi-empresa.com       ←   dominio propio del cliente
```

### 2.2 Tres niveles de URL para el CMS

| Nivel | URL | Dueño del contenido | Datos clave |
|-------|-----|---------------------|-------------|
| **Tenant** | `acme.sbos.app` | Administrador del tenant | Realm KC, namespace K8s, NIT |
| **Empresa** | `www.acme.sbos.app` o dominio propio | Admin de empresa | empresa_id, RUC/NIT, logo, paleta |
| **Sucursal** | `cochabamba.acme.sbos.app` | Admin de sucursal | sucursal_id, dirección, horarios, lat/lon |

### 2.3 Regla de resolución de dominio

```
Petición: https://cochabamba.acme.sbos.app/
                  │         │
           sucursal_slug    empresa_slug (= tenant_slug en este caso)
                  │
                  ▼
nginx → Kong → bcms.web.resolve(host)
                  │
                  ├── busca en bos.net_web_domain (tabla T-415)
                  ├── identifica tenant_id + empresa_id + sucursal_id
                  └── devuelve el contenido del CMS para esa combinación
```

### 2.4 Dominio propio (custom domain)

```bash
# El admin registra un dominio personalizado
bosctl web domain add \
  --domain www.mi-empresa.com \
  --target bcms.sbos-cms.svc.cluster.local:9080 \
  --ssl                            # certbot genera cert Let's Encrypt
  --tenant acme \
  --empresa empresa_abc
```

BOS:
1. Agrega el registro en `bos.net_web_domain`
2. Actualiza nginx.conf con `server_name www.mi-empresa.com`
3. Ejecuta `certbot certonly --webroot` para TLS real
4. Recarga nginx sin downtime (`nginx -s reload`)

## 3. Cómo BOS gestiona rutas web

### 3.1 BC-06 — Domain Manager (existente en código)

Ya existe en `cmd/bosctl/web.go` y `internal/domain/` el Domain Manager:

```
bosctl web domain add    --domain <host> --target <ip:port> [--ssl]
bosctl web domain remove --domain <host>
bosctl web domain list
bosctl web domain resolve --domain <host>
bosctl web domain ssl-status --domain <host>
```

Estos comandos llaman a `bos.web.domain.*` vía JSON-RPC.

**Gap actual:** la tabla `bos.net_web_domain` (T-415) está pendiente de aprobación HITL.  
La implementación usa `MemWebDomain` (en memoria) — los registros se pierden al reiniciar.

### 3.2 Generación dinámica de nginx.conf

La ficha `S02/nginx` ya implementa `_escribir_nginx_conf()` que:
1. Detecta IPs de Kong y servicios VDI via kubectl
2. Genera el `nginx.conf` completo desde plantilla bash
3. Recarga nginx (`nginx -s reload`)
4. Se llama en `ficha_install`, `ficha_repair`, y `ficha_post_install`

**Para CMS:** se necesita extender `_escribir_nginx_conf()` para incluir bloques
`server { server_name empresa.sbos.app; ... }` por cada dominio registrado.

### 3.3 Virtual hosting: cómo nginx resuelve múltiples dominios

```nginx
# nginx.conf — bloque por tenant/empresa (generado dinámicamente por BOS)
server {
    listen 443 ssl;
    server_name acme.sbos.app www.acme.sbos.app *.acme.sbos.app;

    ssl_certificate     /etc/nginx/certs/acme.sbos.app.crt;
    ssl_certificate_key /etc/nginx/certs/acme.sbos.app.key;

    # Todo el contenido CMS pasa por bcms daemon
    location / {
        proxy_pass http://<kong_ip>:8000;
        proxy_set_header Host $host;
        proxy_set_header X-SBOS-Tenant "acme";
        proxy_set_header X-SBOS-Empresa-Slug $subdomain;  # extraído por map{}
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

Kong identifica el tenant por el header `X-SBOS-Tenant` y enruta al servicio `bcms`.

## 5. S16 — Website Engine: el servidor lógico pendiente

### 5.1 Qué es S16

S16 es el **servidor lógico de presencia web** del SBOS. Según el manual de sagas (1.02):

| Ficha | Servidor | Dependencias | Propósito |
|-------|----------|--------------|-----------|
| `nginx` | S16 | kong | Reverse proxy + TLS + virtual hosting multi-tenant |
| `certbot` | S16 | nginx | SSL por dominio, Let's Encrypt automático |
| `modsecurity` | S16 | nginx | WAF, OWASP Core Rule Set |
| `website-engine` | S16 | postgresql, redis | Renderizado multi-tenant (= bcms) |

**Nota:** `nginx` y `certbot` ya existen en S02. S16 reorganizará las fichas de
presencia web cuando bcms se desarrolle. Por ahora S02 cubre el rol de S16.

### 5.2 Fichas que S16 necesita crear

```
servers/S16/
├── nginx/            ← mover de S02 o crear ficha nueva para virtual hosting
├── certbot/          ← mover de S02 o extender la existente
├── modsecurity/      ← NUEVA: WAF para peticiones CMS
└── website-engine/   ← NUEVA: equivalente a bcms daemon
```

### 5.3 Relación S16 ↔ bcms daemon

`website-engine` en S16 ES la ficha instaladora del daemon `bcms`.
Al igual que `postgresql` instala el pod PG, `website-engine` instala bcms.

## 6. bcms — El daemon de contenido

### 6.1 Identidad técnica

```
Daemon:   bcms (BcmsAgent/)
Socket:   /run/bos/bcms.sock
Namespace JSON-RPC: bcms.*
Puerto:   9480 (rango SBOS-050: 9400-9499)
Stack:    Por definir (propuesta: Rust + Axum — mismo que bAuth/bnexus)
Binario:  bcms (CGO_ENABLED=0, estático)
Servicio: bcms.service (systemd)
```

### 6.2 Responsabilidades de bcms

| Responsabilidad | Descripción |
|-----------------|-------------|
| **Renderizado CMS** | Sirve páginas web de empresas/sucursales desde BD |
| **Gestión de plantillas** | CRUD de templates por tenant/empresa |
| **Gestión de páginas** | CRUD de páginas: slug, contenido, SEO, estado |
| **Gestión de sucursales** | Datos de sucursal: dirección, horario, lat/lon, foto |
| **Routing por host** | Mapea `Host:` header a tenant+empresa+sucursal |
| **Multi-idioma** | Integración con bi18n para contenido en múltiples idiomas |
| **Cache** | Redis para páginas renderizadas (TTL configurable) |
| **API pública** | JSON-RPC para que el VDI (panel admin) gestione el CMS |

### 6.3 API JSON-RPC bcms (catálogo mínimo)


## 7. Diseño propuesto del CMS multi-tenant

### 7.1 Concepto: 3 capas de contenido

```
┌─────────────────────────────────────────────────────────┐
│  CAPA 1 — TENANT (skull, acme, ...)                     │
│  • Configuración global del tenant                       │
│  • Dominio raíz: acme.sbos.app                          │
│  • Realm Keycloak propio                                 │
│  • Templates globales del tenant                         │
└─────────────────────────────────────────────────────────┘
           │ contiene N empresas
┌─────────────────────────────────────────────────────────┐
│  CAPA 2 — EMPRESA (empresa_abc, empresa_xyz, ...)       │
│  • Identidad visual propia (logo, paleta, tipografía)   │
│  • Dominio: www.acme.sbos.app o www.empresa.com         │
│  • Páginas: home, about, services, contact              │
│  • Templates propios (hereda del tenant)                │
└─────────────────────────────────────────────────────────┘
           │ contiene N sucursales
┌─────────────────────────────────────────────────────────┐
│  CAPA 3 — SUCURSAL (cochabamba, lapaz, santacruz, ...)  │
│  • Datos físicos: dirección, horario, teléfono, mapa     │
│  • Dominio: cochabamba.empresa.sbos.app                  │
│  • Páginas: copia de empresa + override local           │
│  • Horario especial, oferta local, eventos              │
└─────────────────────────────────────────────────────────┘
```

### 7.2 Herencia de templates (cascada)

```
Template Global (SBOS) → Template Tenant → Template Empresa → Template Sucursal
     ↓ hereda                ↓ sobrescribe      ↓ sobrescribe     ↓ sobrescribe
   layout base            logo + paleta        datos locales     horario local
   navbar SBOS             navbar empresa       teléfono         eventos locales
```

Un template en el nivel inferior puede `{% extends %}` del nivel superior,
sobreescribiendo solo lo necesario.

### 7.3 Tipos de página soportados

| Tipo | Descripción | Variables disponibles |
|------|-------------|----------------------|
| `home` | Página de inicio | empresa.nombre, empresa.descripcion, sucursal.nombre |
| `about` | Quiénes somos | empresa.historia, equipo[] |
| `services` | Productos/servicios | servicios[], precios[] (desde Tryton ERP) |
| `contact` | Contacto y mapa | sucursal.direccion, sucursal.lat, sucursal.lon, horario |
| `catalog` | Catálogo de productos | productos[] (desde Tryton/biedata) |
| `blog` | Publicaciones | articulos[], categorias[] |
| `custom` | Página libre | variables definidas por el admin |
| `landing` | Página de captación | CTA, formulario, hero image |

### 7.4 Rendering engine

bcms usa un motor de templates embebido (Tera/Minijinja en Rust, análogo a Jinja2):

```rust
// Pseudocódigo Rust — bcms rendering
async fn render_page(host: &str, path: &str) -> Html {
    let ctx = resolve_context(host)?;  // tenant + empresa + sucursal
    let page = db.get_page(ctx, path)?;
    let template = db.get_template(page.template_id)?;
    let variables = build_variables(&ctx, &page)?; // datos del tenant/empresa/sucursal
    tera.render(&template.html, &variables)
}
```

**Integración bi18n:** `bcms` llama a `bi18n.format(locale, key, vars)` para
traducir el contenido cuando hay múltiples idiomas configurados.

**Cache Redis:** páginas estáticas se cachean en Redis con key:
`cms:{tenant_id}:{empresa_id}:{sucursal_id}:{slug}:{locale}` · TTL: 5 min (configurable).

## 8. Modelo de datos

### 8.1 Tablas propuestas (schema `cms` en SBOS_db)

```sql
-- T-CMS-01: Empresas del tenant
CREATE TABLE cms.empresa (
    id          BIGSERIAL PRIMARY KEY,
    tenant_id   TEXT        NOT NULL,          -- FK lógica a idn_tenant
    empresa_id  TEXT        NOT NULL UNIQUE,   -- slug técnico: "acme-sa"
    nombre      TEXT        NOT NULL,          -- "ACME S.A."
    nit         TEXT,                          -- NIT/RUC Bolivia
    logo_url    TEXT,                          -- URL o ruta MinIO
    paleta      JSONB       NOT NULL DEFAULT '{}', -- {primary, secondary, accent}
    dominio     TEXT,                          -- "www.acme.sbos.app" o custom
    estado      TEXT        NOT NULL DEFAULT 'activa',
    created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- T-CMS-02: Sucursales de la empresa
CREATE TABLE cms.sucursal (
    id          BIGSERIAL PRIMARY KEY,
    empresa_id  TEXT        NOT NULL REFERENCES cms.empresa(empresa_id),
    slug        TEXT        NOT NULL,          -- "cochabamba"
    nombre      TEXT        NOT NULL,          -- "Sucursal Cochabamba"
    direccion   TEXT,
    telefono    TEXT,
    email       TEXT,
    lat         NUMERIC(10,6),
    lon         NUMERIC(10,6),
    horario     JSONB,     -- {"lun-vie": "08:00-18:00", "sab": "09:00-13:00"}
    estado      TEXT        NOT NULL DEFAULT 'activa',
    created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    UNIQUE (empresa_id, slug)
);

-- T-CMS-03: Templates de contenido
CREATE TABLE cms.template (
    id          BIGSERIAL PRIMARY KEY,
    tenant_id   TEXT        NOT NULL,
    empresa_id  TEXT,                          -- NULL = template del tenant
    nombre      TEXT        NOT NULL,
    html        TEXT        NOT NULL,          -- template Tera/Minijinja
    css         TEXT        NOT NULL DEFAULT '',
    js          TEXT        NOT NULL DEFAULT '',
    variables   JSONB       NOT NULL DEFAULT '[]', -- declaración de vars requeridas
    parent_id   BIGINT      REFERENCES cms.template(id), -- herencia
    created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- T-CMS-04: Páginas del CMS
CREATE TABLE cms.page (
    id          BIGSERIAL PRIMARY KEY,
    tenant_id   TEXT        NOT NULL,
    empresa_id  TEXT        REFERENCES cms.empresa(empresa_id),
    sucursal_id TEXT,                          -- slug de sucursal o NULL
    slug        TEXT        NOT NULL,          -- "/contacto" "/servicios"
    titulo      TEXT        NOT NULL,
    descripcion TEXT,                          -- meta description SEO
    template_id BIGINT      NOT NULL REFERENCES cms.template(id),
    contenido   JSONB       NOT NULL DEFAULT '{}', -- vars del template rellenas
    estado      TEXT        NOT NULL DEFAULT 'borrador', -- borrador|publicada|archivada
    publicado_en TIMESTAMPTZ,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    UNIQUE (tenant_id, empresa_id, sucursal_id, slug)
);

-- T-CMS-05: Medios (imágenes, videos) almacenados en MinIO
CREATE TABLE cms.media (
    id          BIGSERIAL PRIMARY KEY,
    tenant_id   TEXT        NOT NULL,
    empresa_id  TEXT,
    nombre      TEXT        NOT NULL,
    minio_bucket TEXT       NOT NULL DEFAULT 'cms-media',
    minio_key   TEXT        NOT NULL,          -- "acme/logo.png"
    tipo_mime   TEXT        NOT NULL,          -- "image/png"
    tamano_bytes BIGINT,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- T-CMS-06: Formularios y leads (capturas de contacto)
CREATE TABLE cms.lead (
    id          BIGSERIAL PRIMARY KEY,
    tenant_id   TEXT        NOT NULL,
    empresa_id  TEXT,
    sucursal_id TEXT,
    page_id     BIGINT      REFERENCES cms.page(id),
    datos       JSONB       NOT NULL,          -- {nombre, email, telefono, mensaje}
    ip_origen   INET,
    ctx_id      TEXT        NOT NULL DEFAULT '', -- SBOS-049
    created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

## 9. Integración con el ecosistema SBOS

### 9.1 bcms como consumidor de otros daemons

```
bcms
├── bAuth  (bauth.*)       → valida JWT del panel admin, verifica rol cms_editor
├── bkernel (eventos WAL)  → invalida cache Redis cuando page/empresa/sucursal cambia
├── bi18n  (bi18n.*)       → formateo de fechas, monedas, textos multi-idioma
├── biedata (biedata.*)    → datos de productos Tryton para páginas de catálogo
├── bsearch (bsearch.*)    → búsqueda de contenido CMS
└── bos.web.domain.*       → registra dominios cuando bcms.domain.bind() se llama
```

### 9.2 Kong — rutas para CMS

La ficha `S02/kong` necesita dos rutas adicionales para bcms:

```bash
# Ruta 1: CMS público (no autenticado) — peticiones web de visitantes
bcms-web-route:
  hosts: ["*.sbos.app"]          # wildcard para todos los tenants
  paths: ["/"]
  service: bcms-web              # bcms :9480 (rendering endpoint)
  plugins: []                    # SIN JWT — el sitio web es público

# Ruta 2: CMS admin API (autenticado) — panel de administración
bcms-api-route:
  paths: ["/cms/api/"]
  service: bcms-api              # bcms :9480 (JSON-RPC endpoint)
  plugins: [jwt]                 # CON JWT — solo cms_editor/cms_admin
```

### 9.3 Panel de administración CMS

El administrador gestiona el CMS desde el **VDI Fedora** o desde **Nextcloud** (widget):

```
Admin → VDI Fedora → Chromium → https://acme.sbos.app/cms/admin/
                                │
                                ▼
                           bcms JSON-RPC API
                           (autenticado via Keycloak)
```

El panel admin es una SPA (Svelte/Flutter Web) que llama a `bcms.*` vía JSON-RPC.
El rol de Keycloak requerido: `cms_editor` (editar) o `cms_admin` (todo).

### 9.4 Flujo de publicación

```
1. Admin crea página en panel → bcms.page.create() → estado: "borrador"
2. Admin edita contenido → bcms.page.update()
3. Admin previsualiza → bcms.web.render(host, slug, preview=true)
4. Admin publica → bcms.page.publish() → estado: "publicada", publicado_en=NOW()
5. bkernel detecta WAL change en cms.page → emite evento cms.page.published
6. bcms escucha evento → invalida cache Redis de esa página
7. Próxima petición web → bcms renderiza desde BD (cache miss) → nuevo cache
```

## Resumen ejecutivo

**Situación actual:** nginx está instalado y funcional en S02 como reverse proxy
del SBOS. Sirve la landing page estática, el VDI y las apps del ecosistema.
No tiene capacidad de CMS ni páginas por empresa/sucursal.

**Lo que se necesita:**
1. **Aprobar T-415** — persistir dominios en BD (actualmente en memoria)
2. **Crear bcms daemon** (BcmsAgent) — el motor de CMS multi-tenant
3. **Crear ficha S16/website-engine** — instala bcms
4. **Extender nginx** — virtual hosting por empresa con `server_name` dinámico
5. **DDL schema `cms`** — 6 tablas para páginas, empresas, sucursales, media

**El valor:** cada empresa cliente del SBOS tiene su propia presencia web
(`www.empresa.sbos.app`) administrada desde el VDI, con contenido propio por
sucursal, sin depender de servicios externos, todo soberano en el servidor del cliente.
