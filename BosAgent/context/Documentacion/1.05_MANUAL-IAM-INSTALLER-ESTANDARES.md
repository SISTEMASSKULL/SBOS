## 1. Qué significa "IAM Enterprise"

IAM Enterprise no es un estándar único. Es el cumplimiento simultáneo de:

| Estándar | Qué certifica | Quién lo exige |
|----------|--------------|----------------|
| **FAPI 2.0** | APIs de identidad de nivel financiero (el más exigente) | Bancos, fintechs, reguladores financieros |
| **ISO 27001:2022** | Sistema de gestión de seguridad de la información | Cualquier enterprise, reguladores |
| **NIST SP 800-63B** | Autenticación digital: IAL2, AAL2/3, FAL2 | US Gov, referencia internacional |
| **CIS K8s Benchmark v1.12** | Hardening de Kubernetes | DevSecOps, auditorías cloud |
| **SLSA L2** | Integridad de la cadena de suministro de software | Enterprise con SSC risk |
| **k6 SLOs** | Rendimiento verificado bajo carga real | SRE / acuerdos de nivel de servicio |

El SBOS los cumple todos en una sola plataforma soberana — sin depender de AWS Cognito,
Azure AD, Okta ni ningún SaaS externo.

## 2. FAPI 2.0 — Financial-grade API Profile 2.0

### 2.1 Qué es y por qué importa

FAPI 2.0 (OpenID Foundation) es el perfil de seguridad más exigente para APIs OAuth 2.1.
Si el SBOS cumple FAPI 2.0, cumple automáticamente OAuth 2.1, OIDC Core, y la mayoría
de requisitos de NIST 800-63B FAL2.

### 2.2 Requisitos y su implementación en SBOS

| Requisito FAPI 2.0 | Implementación | Estado |
|-------------------|----------------|:------:|
| PAR (RFC 9126) obligatorio | `require-pushed-authorization-requests=true` en KC realm | 🔴 Fase III |
| DPoP (RFC 9449) obligatorio | `dpop-bound-access-tokens=true` en KC clientes | 🔴 Fase III |
| PKCE obligatorio | KC por defecto desde v21+ | ✅ |
| Solo PS256 / ES256 | Deshabilitar RS256/HS256 en KC realm | 🔴 Fase III |
| mTLS para client authentication | TLS 1.3 + ClientAuth en :9443 (NRS-03) | 🔴 Fase III |
| Endpoint PAR con mTLS | `POST /par/authorize` solo via mTLS | 🔴 Fase III |
| Redirect URI exacto | KC valida redirect_uri por cliente | ✅ |
| JARM (JWT Auth Response Mode) | Response como JWT firmado | 🔴 Fase III |

### 2.3 Procedimiento de certificación (A.17)

1. Levantar KC 26.6.2 en entorno staging con dominio público (*.staging.sbos.app)
2. Configurar realm con todos los requisitos FAPI 2.0 del §2.2
3. Ejecutar la [FAPI 2.0 Conformance Test Suite](https://openid.net/certification/fapi_op_testing/) de OpenID Foundation
4. Objetivo: 0 failures en todos los test plans (FAPI2-Security, FAPI2-Message-Signing)
5. Documentar en `A.17_ANEXO-FAPI2-CERTIFICACION.md`

## 4. NIST SP 800-63B — Niveles de garantía

| Nivel | IAL (Identity Assurance) | AAL (Authenticator Assurance) | FAL (Federation Assurance) | Implementación SBOS |
|:-----:|--------------------------|-------------------------------|---------------------------|---------------------|
| 1 | Autoafirmación | Password single-factor | n/a | LoA 1 en ctx_id |
| 2 | Verificación remota (documentos) | MFA (TOTP o FIDO2) | Assertion firmada | LoA 2 en ctx_id |
| 3 | Verificación presencial | Hardware token (FIDO2 L2) | Assertion cifrada + firmada | LoA 3 en ctx_id |

**AAL2 en SBOS:** KC 26.6.2 con TOTP obligatorio (Google Authenticator / FreeOTP).
**AAL3 en SBOS:** KC con FIDO2 PassKey (WebAuthn L2). Dispositivos: YubiKey 5, PassKey iOS/Android.
**FAL2:** Assertion OIDC firmada con PS256 + DPoP (FAPI 2.0) — Fase III.

## 5. k6 SLOs — Rendimiento verificado (SBOS-PERF-001)

Los SLOs se verifican con k6 v0.52+ contra la VPS real, no contra stubs.

### 5.1 Escenario Alpha — 5 tenants, 500 RPS (Fase VII)

```javascript
// tests/k6/escenario-alpha.js
import http from 'k6/http';
export const options = {
  scenarios: {
    constant_rps: { executor: 'constant-arrival-rate', rate: 500, duration: '60s' }
  },
  thresholds: {
    'http_req_duration{method:POST,url:/rpc}': ['p(99)<150'],     // JSON-RPC P99 < 150ms
    'http_req_duration{name:ctx_lookup}': ['p(99)<5'],             // ctx_id lookup P99 < 5ms
    'http_req_failed': ['rate<0.001'],                             // error rate < 0.1%
  }
};
```

### 5.2 Escenario Beta — 50 tenants, 5K RPS (Fase VII post-Alpha)

| SLO | Objetivo |
|-----|----------|
| JSON-RPC P99 | < 150ms |
| ctx_id lookup P99 | < 5ms (Redis cache hit) |
| `device.register` P99 | < 2s (escribe en PG + Redis) |

| Ficha install P50 | < 60s |
| Error rate bajo carga | < 0.1% |

## 6. CIS Kubernetes Benchmark v1.12

Ejecutar `kube-bench` en CI contra el cluster de la VPS. Objetivo: L1 ≥ 95%.

### 6.1 Controles críticos (no negociables)

| Control CIS | Descripción | Implementación |
|-------------|-------------|----------------|
| 5.1.1 | RBAC habilitado (ya default en K8s 1.32) | ✅ |
| 5.1.6 | Sin wildcard `*` en ClusterRoles de SA de workloads | `kubectl get clusterrolebindings` → ninguno con `*` |
| 5.2.1 | Pod Security Standards: no privileged, no root | `runAsNonRoot: true`, `seccompProfile: RuntimeDefault` |
| 5.3.1 | NetworkPolicy en todos los namespaces SBOS | ✅ deny-all en cada namespace |
| 5.4.1 | Secrets solo como archivos, nunca env vars | Vault Agent escribe archivos, no `env:` |
| 5.5.1 | Registry privada autorizada | Solo imágenes del catálogo ADR-017 verificadas |
| 5.7.1 | Namespaces activos tienen NetworkPolicy | deny-all + allowlist explícita |

### 6.2 Verificación rápida

```bash
# Desde la VPS
kubectl auth can-i delete secrets --as=system:serviceaccount:sbos-system:bosagent
# → no

kubectl auth can-i create clusterrolebindings --as=system:serviceaccount:sbos-data:postgresql
# → no

kube-bench --benchmark cis-1.12 run --targets node
# → PASS: ≥ 95% de controles L1
```

## 7. SLSA L2 — Software Supply Chain Security

SLSA (Supply-chain Levels for Software Artifacts) L2 requiere que cada release tenga
provenance firmada que demuestre qué código produjo qué artefacto.

| Requisito SLSA L2 | Implementación |
|-------------------|----------------|
| Build por CI/CD (no manual) | GitHub Actions workflow controlado |
| Provenance generada por build | `actions/attest-build-provenance@v1` |
| Firma Ed25519 en binario | `cosign sign` con clave KMS o Vault Transit |
| SBOM CycloneDX JSON | `cyclonedx-gomod bom -output bom.json` |
| Verificación de firma | `cosign verify` en despliegue |

```bash
# Verificar integridad del binario en producción
cosign verify-attestation --type slsaprovenance \
  --certificate-identity https://github.com/SISTEMASSKULL/bos-install/.github/workflows/release.yml \
  ghcr.io/sistemasskull/bos:latest
```
