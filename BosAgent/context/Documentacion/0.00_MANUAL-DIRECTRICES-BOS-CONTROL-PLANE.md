## 2. Qué es un Plano de Control Soberano en 2026 — la definición

En 2026, la industria de infraestructura como código reconoce **tres generaciones** de herramientas
(ver [Anexo A.01](Anexos/A.01_ANEXO-INDUSTRIA-CONTROL-PLANES.md) para la comparación completa):

| Generación | Herramientas | Modelo | Limitación |
|-----------|-------------|--------|------------|
| **1ra gen — CLI apply** | Terraform, OpenTofu, Pulumi, Ansible | Ejecutar comando → diff → aplicar → salir | Sin Day 2; drift se acumula entre ejecuciones |
| **2da gen — Control loop** | Crossplane, ArgoCD, Flux, Rancher | Controlador corriendo en K8s; reconcilia continuamente | Solo opera dentro de K8s; no hace bootstrap del SO |
| **3ra gen — Sovereign Control Plane** | **BOS** | Daemon PID 1 en el host; gobierna SO + K8s + apps; zero-touch desde Ubuntu virgen | — (categoría nueva, sin equivalente comercial) |

El Plano de Control Soberano de 3ra generación se define por estos rasgos:

| Rasgo | Qué exige |
|-------|-----------|
| **Soberanía total** | Los datos nunca abandonan el servidor del cliente; sin licencias externas; código auditable en su totalidad; el sistema opera sin depender del fabricante (SBOS-001) |
| **Declaratividad total** | Toda dependencia, configuración y aplicación es una ficha declarativa (manifest.yml + task_catalog.sh + resources/); cero scripts manuales   |
| **Sagas con compensación** | Toda operación multi-paso (install, update, repair, remove) tiene rollback explícito; 18 estados de ficha con transiciones validadas (ADR-021); el sistema nunca queda en estado inconsistente |
| **Reconciliación continua** | Day 2: el daemon compara estado declarado vs estado real en 5 planos (host SO, K8s, PostgreSQL, Vault, Redis) y corrige drift automáticamente |
| **Interface Dual** | WebSocket RPC (humanos, CLI, GUI) + JSON-RPC 2.0 (daemons, scripts, IA) sobre el MISMO Unix socket `/run/bos/bos.sock`; sin HTTP/TCP entre daemons (SBOS-050 P9) |
| **Multi-tenant nativo** | Alta/Baja/Suspensión de tenants con saga de 7 pasos con compensación; namespaces K8s + bauth como IdP nativo + 9 BDs PostgreSQL + paths Vault aislados por tenant |
| **Day 2 autónomo** | 4 motores corriendo cada 60s (Observación → Proyección → Políticas → Acción); bloqueo de admisión antes de degradar; proyección a 7/30/90 días |

## 3. El posicionamiento del BOS — "el systemd del sistema operativo empresarial"

### 3.1 El BOS como Policy Administrator — exigido por NIST SP 800-207

NIST SP 800-207 §3.2 exige tres componentes en toda Zero Trust Architecture:

| Componente NIST | Responsabilidad | Implementación SBOS |
|----------------|-----------------|---------------------|
| **Policy Engine (PE)** | Evaluar cada request contra políticas dinámicas | **bauth** — emite JWT con `bos_contexts`, calcula BitMask 64-bit, evalúa 12 dominios (D1-D12) contra RolTemplate |
| **Policy Administrator (PA)** | Crear/terminar sesiones de infraestructura, gestionar el ciclo de vida del contexto | **BOS** — `bos.ctx.create`, `bos.ctx.promote`, `bos.ctx.switch`, `bos.ctx.invalidate`, `bos.ctx.invalidate_all_by_tenant` |
| **Policy Enforcement Point (PEP)** | Interceptar y decidir cada request | Kong + plugin SBOS-Context — GET :9443 O(1) |

**Dos sesiones, dos dueños (estándar de industria):**

| Sesión | Dueño | Propósito |
|--------|:-----:|-----------|
| **Sesión de identidad** (IdP) | **bauth** | Autenticar usuario, emitir JWT con `bos_contexts`, calcular BitMask, evaluar 12 dominios. Gobierna refresh, logout, step-up (RFC 9470). |
| **Sesión de infraestructura** (ctx_id) | **BOS** | Transportar contexto (tenant, empresa, sucursal, pos) a través de todos los servicios. Gobierna create, switch, invalidate, TTL (ISO 27001 A.9.4.2). |

No compiten — se complementan. **bauth** proporciona identidad y permisos. **BOS** materializa
el contexto en infraestructura (Redis). **bauth** después eleva el ctx_id a
protagonismo superior: lo usa como señal de entrada para evaluar los 12 dominios, verificar
que el contexto sigue siendo válido, y determinar si el BitMask sigue aplicando.

### 3.2 Tenant interno vs externo — dos tipos de soberanía

El BOS reconoce dos tipos de tenant, diferenciados por `idn_tenant.is_internal`:

| | Tenant Interno | Tenant Externo |
|---|---|---|
| **Rol** | Operador del SBOS (dueño del servidor) | Cliente que usa el SBOS como servicio |
| **Stack** | Completo: PG + Redis + Vault + bauth + Kong + daemons | Reducido: tenant en bauth + namespace K8s + Vault namespace |
| **Provisioning** | Saga 7 pasos con compensación | Saga 4 pasos |
| **Ciclo de vida** | 7 estados + GDPR Art. 17 (soft-delete 30 días + purge) | activo → suspended → deleted |
| **Superficie bauth** | `bauth.tenant.*` (CRUD real) | `bauth.idp.*` (IDaaS declarativo) |

El BOS consulta `bauth.tenant.get(tenant_id)` antes de desplegar. Si `is_internal = true`,
ejecuta la saga completa. Si `is_internal = false`, despliega solo el perímetro del cliente.

### 3.3 El modelo de identidad universal — "todo es una entidad"

El ctx_id no está limitado a "empresa/sucursal". El modelo de identidad D00 v2.0 define
**5 niveles con tipos variables** validados por el motor AtomLang. Una entidad puede ser
cualquier cosa:

```
Nivel 1: tenant      → interno | externo
Nivel 2: bdomain     → empresa | persona | hogar | almacen | datacenter | hospital | hotel | universidad
Nivel 3: bsubdomain  → sucursal | oficina | deposito | sala | piso | aula | habitacion
Nivel 4: pos         → caja | terminal | puerta | sensor | estante | rack | estacionamiento
Nivel 5: actor       → HUMAN | SERVICE | DEVICE | BOT | producto | vehiculo | servidor | paciente | alumno
```

Todas las PKs son **UUIDv7** (RFC 9562) — time-ordered, ordenables por tiempo. PostgreSQL 18
genera `DEFAULT uuidv7()`. El ctx_id es más nuevo que uno creado antes por diseño.

### 3.4 La analogía fundamental

```
Linux kernel   →  gestiona hardware de cómputo (CPU, RAM, disco, red)
BOS            →  gestiona recursos empresariales (tenants, fichas, contexto, capacidad)
```

**El BOS es el `systemd` del sistema operativo empresarial SBOS.** No es un instalador. No es una
herramienta que se ejecuta y termina. Es un **daemon soberano permanente** (systemd, Type=simple,
user=bosagent) que corre las 24 horas, dueño del ciclo de vida completo del servidor empresarial.

### 3.2 Posición real en el stack

```
Ubuntu Linux 26.04 (host)
    │
    └── systemd
          └── bos.service  ← EL BOS VIVE AQUÍ, SIEMPRE (PID del plano de control)
                │
                │  gestiona ↓ (NO está adentro de ellos)
                ├── Kubernetes cluster (kubeadm v1.32.x + Calico)
                │     └── Namespaces (creados por bos)
                │           └── Pods / fichas (instaladas por bos)
                ├── PostgreSQL 18.4 (provisiona 9+ BDs de tenants)
                ├── bauth como IdP nativo soberano
                ├── Vault 2.0.1 (crea paths de secretos AppRole por ficha)
                └── Redis 8.6.2 DB1 (el Context Registry — es su propiedad)
```

### 3.3 Lo que el BOS no es

| Podría parecer | La realidad |
|----------------|-------------|
| Una herramienta de monitoreo /proc | /proc es UNA de 30+ fuentes del Motor de Observación — datos secundarios |
| Un CLI que ejecuta comandos | `bosctl` es la interfaz humana. El daemon es el actor real |
| Un proceso que termina al instalar | El BOS corre SIEMPRE. Es el Policy Administrator permanente del sistema |
| Un gestor de Kubernetes | Kubernetes es el runtime. El BOS es el soberano que lo gestiona desde fuera |
| Un orquestador de Helm charts | Las fichas no son Helm charts — son unidades declarativas auto-contenidas con task_catalog.sh |

## 4. Las 5 responsabilidades permanentes del BOS

Estas responsabilidades no son tareas de instalación. Son funciones que el BOS cumple
continuamente mientras está corriendo. Un BOS que no las cumple no es un BOS.

### R1 — Context Plane (CRÍTICA 24/7)

El BOS es el **único dueño del Context Plane**. Cada request HTTP que llega a Kong termina
validando el `ctx_id` contra la Context API del BOS en `:9443`. Si el BOS no responde, **ningún
usuario del SBOS puede operar**. Es la pieza más crítica del ecosistema.

**Ciclo de vida de un usuario:**

```
T+0     Dispositivo Fedora arranca → BOS crea dctx_id pre-auth (bitmask=0x0)
T+N     Usuario presenta credencial → banexus intercepta → bauth autentica → emite JWT con bos_contexts → calcula BitMask
T+N+8ms BOS recibe solicitud de promoción desde bauth → crea ctx_id (sesión de infraestructura) → Redis DB1 (O(1))
T+N+15ms Capacidades activadas: chapas, apps, cajón POS
T+op    CADA request: Kong → GET :9443/api/v1/context/{ctx_id} → Redis O(1)
T+fin   Logout → BOS invalida ctx_id → Redis TTL=0 → todo bloqueado
```

**Los 6 endpoints de la Context API** (Kong los llama en cada request de cada usuario):

| Método | Endpoint | Propósito |
|--------|----------|-----------|
| POST | `/api/v1/context/create` | Login → genera ctx_id |
| POST | `/api/v1/context/switch` | Cambio de contexto sin reautenticación |
| DELETE | `/api/v1/context/{ctx_id}` | Logout → invalida ctx_id |
| GET | `/api/v1/context/{ctx_id}` | Lookup O(1) — llamado en CADA request |
| GET | `/api/v1/context/tenant/{tenant}` | Lista ctx_id activos del tenant |
| POST | `/api/v1/context/tenant/{tenant}/invalidate-all` | Suspensión de tenant |

### R2 — Ciclo de Vida de Tenants (Saga 7 pasos con compensación)

`bosctl deploy seed.yml` ejecuta una saga de 7 pasos. Si el paso N falla, los pasos 1 a N-1
se revierten automáticamente. No hay estado inconsistente.

```
Paso 1: Configurar tenant en bauth (IdP nativo soberano)
Paso 2: Crear Namespace en K8s con labels + NetworkPolicy + ResourceQuota
Paso 3: Provisionar 9 BDs en PostgreSQL
Paso 4: Crear paths Vault + AppRole por ficha
Paso 5: Inicializar Context Registry en Redis DB1
Paso 6: DDL context_sessions + device_contexts en bkernel_db
Paso 7: Instalar fichas del tenant en orden topológico (DAG)
```

**SLO:** Alta de tenant < 30s P50, < 90s P99 (SBOS-PERF-001).

### R3 — Ficha Engine (DAG resolver + 18 estados)

El BOS resuelve el grafo de dependencias entre fichas (Kahn) y garantiza el orden topológico
de instalación. Cada ficha transita por hasta 18 estados (ADR-021): PENDIENTE → LISTA →
INSTALANDO → INSTALADA → DEGRADADA → REPARANDO → ... El BOS monitorea constantemente y actúa
según el estado de cada ficha.

**SLO:** Instalación de ficha < 60s P50, < 180s P99 (SBOS-PERF-001).

### R4 — Reconciliación (loop cada 15 minutos)

El BOS compara el estado **declarado** (manifest.yml de cada ficha) contra el estado **real**
del sistema en 5 planos (kubectl, ps, Redis, PostgreSQL, Vault). Detecta drift (SHA-256 por
archivo) y repara autónomamente con 3 reintentos. Cada discrepancia queda registrada en
`bos.ficha_event` con `ctx_id` — evidencia ISO 27001 A.8.15.

### R5 — Autómata de Capacidad (loop cada 60 segundos, 4 motores)

El BOS no solo instala. Garantiza que el sistema nunca se degrada por falta de capacidad.
Cuatro motores corren en paralelo cada 60 segundos (SBOS-BOS-CAP-001):

```
Motor Observación  → 30+ métricas: ctx_id activos, Redis%, PG conexiones, 
                      Kong RPS, bauth cache miss, MinIO%, K8s nodos
Motor Proyección   → regresión lineal, horizontes 7/30/90 días, intervalo de confianza
Motor Políticas    → YAML declarativo: autonomous | recommend | block_and_alert | emergency
Motor Acción       → HPA override, PgBouncer resize, control admisión 6 niveles, alertas
```

## 5. La arquitectura de comunicación — Interface Dual

```
/run/bos/bos.sock  (0660, grupo bosagent)
(UN solo socket — DOS vías simultáneas sobre el MISMO endpoint)
    │
    ├── Vía 1: WebSocket RPC
    │     Consumidores: bosctl CLI + Core UI Flutter
    │     Propósito: administración humana, comandos interactivos
    │
    └── Vía 2: JSON-RPC 2.0
          Consumidores: biedata, bauth, bsearch, agentes IA
          Propósito: invocación programática, sagas, automatización
          Naming: bos.<modulo>.<operacion>
```

**Puertos TCP:**
- `0.0.0.0:9443` — Context API HTTPS (TLS 1.3) — el ÚNICO endpoint TCP del BOS
- `127.0.0.1:9090` — Métricas Prometheus (solo localhost)
- El resto de la comunicación es vía Unix socket — **cero HTTP/TCP entre daemons** (SBOS-050 P9)

## 6. Los 5 pilares de la categoría y sus criterios

La categoría se descompone en **5 pilares** que cubren el ciclo de vida completo del servidor
empresarial. Cada pilar tiene criterios que un Plano de Control Soberano debe cumplir:

### Pilar I — IAM Installer (R1 + R2: Day 0 bootstrap + Day 1 tenants)
Bootstrap del SO, despliegue del stack de identidad, ciclo de vida de tenants.
**Criterios:** bootstrap zero-touch (Ubuntu virgen → K8s + stack) · stack de identidad completo
(bauth IdP nativo + Vault 2.0.1 + Kong 3.9.x) · saga de 7 pasos con compensación ·
tenant deploy < 30s P50 · NetworkPolicy deny-all (Zero Trust) · TLS 1.3 en :9443 · sin
intervención manual post-bootstrap (ADR-022) · FAPI 2.0 · evidencia ISO 27001.

### Pilar II — SO Observable (Day 2 autónomo)

El BOS no solo instala. Garantiza que el sistema nunca se degrada sin ser detectado y reparado.
Implementa el marco **Google SRE** completo: SLI → SLO → Error Budget → Burn Rate → Alerta → Runbook.

**Criterios Day 2:**
- **Watchdog unificado** 3-capas (Ubuntu + K8s + fichas) cada 30s con diagnóstico pre-repair
- **4 motores de capacidad** cada 60s: Observación (30+ métricas: PG, Redis, Kong, bauth, K8s, ctx_id) → Proyección (regresión lineal 7/30/90 días) → Políticas (YAML: autonomous/recommend/block_and_alert/emergency) → Acción (HPA coordinado anti-death-spiral, PgBouncer resize, control admisión 6 niveles)
- **Reconciliación** cada 15min: drift detection SHA-256 en 5 planos (SO, K8s, PG, Vault, Redis) → auto-reparación 3 reintentos → ERROR_NO_CORREGIBLE → HITL
- **SLOs con Error Budget**: latencia P99 < 50ms PG, disponibilidad > 99.99%, burn rate > 14.4x/hora → alerta crítica. Error budget agotado → deployments congelados
- **Alertmanager**: reglas critical (P0, < 15 min, 24/7), high (< 1h), medium (< 4h). Routing a PagerDuty + RocketChat
- **Rollout canary**: Pre-deploy checks → 10% (15 min) → 50% (30 min) → 100% (15 min obs). Rollback < 30s con `bosctl rollback`
- **14 runbooks** (RK-001 a RK-014): procedimientos documentados para cada escenario (PG caído, nodo NotReady, Vault sellado, CrashLoop, disco lleno, ImagePullBackOff, CoreDump, PVC fault)
- **Dashboard Grafana**: 10 paneles con SLOs en tiempo real (semáforo R/Y/G), Error Budget restante, burn rate actual
- **Health checks multi-capa**: SO (Ubuntu), K8s (nodos, pods), daemons (bauth), fichas (18 estados ADR-021)

### Pilar III — Server FICHAS (R3: Day 1 + Day 2)

Motor administrador de fichas. El BOS es el **Operator Soberano** que gobierna el ciclo de vida
completo de cada aplicación mediante el patrón CNCF: CRD (manifest.yml) + Controller (observer)
+ Reconcile Loop (cada 15min).

**Principio fundacional (SBOS-019):** "Agregar la app número 97 es crear una carpeta." El motor
no sabe qué aplicación instala — solo ejecuta los 3 contratos de cada ficha.

**Criterios:**
- **Ficha como unidad atómica de despliegue** (SBOS-019): 3 contratos (manifest.yml identidad + yaml_engine.yml fases + resources/ artefactos) · 3 tipos (Sistema bash, Aplicación K8s, Opcional Pura) · 4 niveles de conocimiento (Universal motor → Específico task_catalog → Declarativo yaml_engine → Estado resources)
- **Máquina de 18 estados** (ADR-021): PENDIENTE → LISTA → INSTALANDO → INSTALADA → DEGRADADA → REPARANDO → ERROR_FISICO/LOGICO → ERROR_NO_CORREGIBLE → LIMPIEZA → ROLLBACK → PAUSADA → DESINSTALADA. Transiciones validadas: CanInstall, CanRepair, CanUpdate, CanRemove
- **DEPENDENCY_RESOLVER** (Kahn): grafo dirigido + detección de ciclos + oleadas paralelas. `depends_on` es restricción absoluta; `execution_order` es preferencia. Las fichas sin dependencias entre sí se instalan en paralelo
- **Executor de 5 fases** con señales `__SBOS__STEP__`: pre_install → install → post_install → verify → commit. Timeouts por tipo: K8s (5min), DB (10min), Daemon (2min)
- **Parser estricto de manifest.yml**: allowlist SAN-10 por sección, semver validation, licencia OSI-approved, dashboard.json requerido (4 paneles mínimos: health/resources/traffic/errors)
- **Discovery automático**: escaneo de `servers/` → cada subdirectorio con manifest.yml es una ficha. 3 contratos: manifest.yml (WARNING), task_catalog.sh (obligatorio), resources/ (WARNING)
- **Drift detection**: SHA-256 por archivo, comparación declarado vs real en 5 planos. DetectAll multi-ficha en paralelo
- **Health checker declarativo**: 4 tipos (command/HTTP/TCP/none), HealthTracker anti-race, 3 fallos → DEGRADADA → HITL
- **Reconciliación** cada 15min con 3 políticas: autonomous (repara solo), recommend (sugiere), block_and_alert (detiene + notifica)
- **Repair/Rollback/Cleanup**: 3 reintentos → ERROR_NO_CORREGIBLE, rollback a versión N-1, limpieza sin residuos (pods, PVCs, configs, secretos)
- **Versionado semver** con 3 estrategias: hot (sin downtime), cold (drain+replace), canary (10%→50%→100%)
- **Governance dual-control** para operaciones categoría 3 (remove, scale a 0): requieren 2 administradores + ventana 60min + texto exacto de confirmación
- **Soberanía de fichas** (SBOS-055 — 8 reglas SOV): cero intervención manual. Toda tarea manual = bug de diseño = ficha faltante. `install.sh` ≤ 25 líneas, sin apt-get, sin useradd. Credenciales bootstrap TEMPORALES — Pasada 2 las migra a Vault

**Jerarquía de scripts Bash — 5 componentes en `core/` (SBOS-019 §8):**

El directorio `core/` contiene el motor del IAM Installer. Son 5 scripts + 1 archivo YAML de
arquitectura. Cada uno tiene una responsabilidad única e inconfundible:

```
core/00_ARCHITECTURE_SBOS.yml       ← REGISTRO de arquitectura (YAML, no ejecutable)
    Define: principios, lifecycle, fichas, señales. Fuente de verdad declarativa.

core/00_MASTER_INSTALL_SBOS.sh      ← PUNTO DE ENTRADA (440 líneas)
    Recibe: comando + ficha_id [+ version]
    Localiza la ficha en servers/, absorbe su task_catalog.sh (source),
    ejecuta la acción solicitada, y libera funciones.
    Define las 6 señales __SBOS__STEP__* que son el contrato de comunicación.
    Principios: P1 (sbos_k8s_core único), P2 (pre_install falla → ABORT),
    P7 (Absorb / Execute / Release).

core/00_TASK_CATALOG_SBOS.sh        ← LIBRERÍA DE FUNCIONES GENÉRICAS (704 líneas)
    NIVEL 1 de SBOS-019. NUNCA menciona una app concreta.
    check_root_user()               ← verifica root
    check_system_requirements()     ← RAM, CPU, disco mínimos
    check_k8s_cluster_ready()       ← ¿cluster reachable? ¿nodos Ready?
    create_k8s_namespace()          ← namespace + labels + NetworkPolicy
    create_k8s_secret()             ← secreto K8s desde Vault o bootstrap
    sbos_k8s_core()                 ← ÚNICO punto de dispatch kubectl (P1)
    wait_for_pod_ready()            ← espera condición Ready con timeout
    backup_ficha_state()            ← backup pre-operación
    restore_ficha_state()           ← rollback post-fallo

core/00_YAML_ENGINE_SBOS.sh         ← INTÉRPRETE DECLARATIVO (481 líneas)
    NIVEL 3 de SBOS-019. Wraps yq para parsear 00_ARCHITECTURE_SBOS.yml.
    yaml_validate_schema()          ← valida manifesto contra schema
    yaml_dispatch_phase()           ← ejecuta fases en orden (pre→install→post→verify→commit)
    yaml_verify_signal()            ← parsea señales __SBOS__STEP__
    yaml_resolve_deps()             ← resuelve depends_on del manifiesto

core/00_CLEANUP_SBOS.sh             ← LIMPIEZA POST-FALLO (268 líneas)
    Elimina TODOS los artefactos de una instalación fallida:
    contenedores, servicios, state files, sockets, puertos, volúmenes, redes.
    Principio: dejar el sistema exactamente como estaba antes.

servers/<server>/<app>/task_catalog.sh  ← SCRIPT 1: funciones bash CON nombre de app (NIVEL 2)
    Cada ficha implementa las 6 funciones del contrato:
    ficha_pre_install()   ficha_install()   ficha_post_install()
    ficha_update()        ficha_repair()     ficha_uninstall()
    ficha_health()        ficha_diagnosis()  (opcional)

servers/<server>/<app>/yaml_engine.yml   ← SCRIPT 2: fases declarativas (NIVEL 3)
    Define QUÉ ejecutar y en qué orden, sin lógica bash.
    El 00_YAML_ENGINE_SBOS.sh lo interpreta y despacha cada fase.
```

**Las 6 señales — contrato de comunicación entre Bash y Go:**
```bash
readonly __SBOS__STEP_START__="__SBOS__STEP_START__"     # "voy a empezar"
readonly __SBOS__STEP_OK__="__SBOS__STEP_OK__"           # "completado OK"
readonly __SBOS__STEP_FAIL__="__SBOS__STEP_FAIL__"       # "falló — detalles"
readonly __SBOS__STEP_SKIP__="__SBOS__STEP_SKIP__"       # "omitido (idempotente)"
readonly __SBOS__CLEANUP_DONE__="__SBOS__CLEANUP_DONE__" # "limpieza completada"
readonly __SBOS__ROLLBACK_START__="__SBOS__ROLLBACK_START__" # "iniciando rollback"
```

**Ciclo Absorb / Execute / Release (P7):**
```
1. ABSORB:  00_MASTER_INSTALL source task_catalog.sh → funciones cargadas en memoria
2. EXECUTE: YAML_ENGINE despacha fases en orden → llama a ficha_*()
3. RELEASE: unset -f ficha_* → funciones liberadas, sin contaminación entre fichas
```

**Ejemplo real — ficha postgresql (task_catalog.sh, 65 líneas):**
```bash
ficha_install() {
    echo "${__SBOS__STEP_START__} install"                        # ← señal al observer
    sbos_k8s_core "${SBOS_FICHA_DIR}/postgresql.k8s.yml" \       # ← llama al motor (P1)
                  "${SBOS_NAMESPACE}"
    kubectl wait --for=condition=Ready pod/postgresql-0 \         # ← espera readiness
                 -n "${SBOS_NAMESPACE}" --timeout=600s
    echo "${__SBOS__STEP_OK__} install"                           # ← señal al observer
}
```

**Regla de oro:** función que menciona app concreta → va en SU `task_catalog.sh`. Función
universal → va en `core/00_TASK_CATALOG_SBOS.sh`. El `00_MASTER_INSTALL_SBOS.sh` es el
único que orquesta. Nunca al revés. Sin `00_CLEANUP_SBOS.sh`, una instalación fallida
deja residuos.

**Evaluación de la arquitectura Go + Bash + YAML + Señales:**

Esta arquitectura de 4 componentes es la **base técnica de ADR-040** (mínimo viable progresivo)
y la razón por la que el problema del huevo y la gallina tiene solución en SBOS:

```
Go (binario BOS)     → state machine, observer, JSON-RPC, sagas. NO cambia.
Bash (task_catalog)  → ejecución dinámica. Cambia sin recompilar el binario.
YAML (manifest.yml)  → intención declarativa. Lo que el operador quiere.
Señales (__SBOS__)   → protocolo de comunicación Bash ↔ Go en tiempo real.
```

**Por qué Bash no es una debilidad — es el diferencial:** si cada ficha fuera un binario
compilado (Rust/Go), cualquier adaptación —detectar `k3s` vs `kubeadm`, cambiar credenciales
bootstrap por Vault, ajustar timeouts— requeriría recompilar y redesplegar. Con bash:

- **Cero recompilación** — el binario BOS nunca se toca. La ficha cambia, el BOS la absorbe
  con `source` y ejecuta. El mismo binario BOS orquesta 144+ fichas distintas.
- **Pasadas sucesivas (ADR-040)** — la misma ficha `postgresql` se ejecuta en Pasada 1
  (credenciales bootstrap, sin Vault) y Pasada 2 (credenciales Vault, PKI). Mismo binario
  BOS, mismo `task_catalog.sh`, diferente comportamiento porque el script detecta el
  entorno (`[[ -f /etc/bos/.vault_initialized ]] && usar_vault || usar_bootstrap`).
- **Soberanía de daemons** — BauthAgent escribe el `task_catalog.sh` de bauth. BkernelAgent
  el de bkernel. Ninguno toca el binario BOS. Cada daemon es dueño de su ficha.
- **Adaptabilidad** — la ficha `sbos-bootstrap-k8s` (590 líneas) detecta `k3s` (staging) vs
  `kubeadm` (producción) y se adapta automáticamente. Compilar eso en Go requeriría
  recompilación por cada entorno.
- **Idempotencia verificable en vivo** — `ficha_repair()` converge al estado deseado sin
  importar el estado inicial. Si ya está OK, no hace nada. Si está DEGRADADA, repara.
  Si se ejecuta 2 veces, mismo resultado. Todo en bash, sin recompilar.

**El BOS NO es un reemplazo de Ansible ni compite con Rash.** Es una arquitectura propia
donde Go y Bash cooperan: Go para lo que requiere estado, tipado y performance (observer,
sagas, JSON-RPC); Bash para lo que requiere adaptabilidad dinámica sin recompilación
(detección de entorno, idempotencia, comandos del SO). La industria no tiene un producto
equivalente empaquetado. Lo que otras herramientas buscan eliminar (bash), el BOS lo
potencia como capa de ejecución dinámica.

### Pilar IV — Context Plane (R1: transversal a todos los pilares)

El Context Plane es LA responsabilidad que hace al BOS un Plano de Control Soberano. Sin él, el
sistema funciona a nivel técnico (K8s, PG, Redis) pero no tiene **significado empresarial**.
El BOS es el **Policy Administrator** (NIST SP 800-207): crea, mantiene y destruye sesiones de
infraestructura. bauth es el **Policy Engine**: evalúa permisos y calcula el BitMask. Kong es
el **PEP**: valida cada request contra el Context Registry.

**Los dos identificadores — dctx_id y ctx_id:**
- **dctx_id** (Device Context): creado al arrancar un dispositivo (Fedora, VDI, terminal POS).
  Pre-auth, BitMask = 0x0, TTL = 8h (ISO 27001 A.9.4.2). Sin privilegios. Trazabilidad anónima.
- **ctx_id** (Context Session): creado al hacer login. Post-auth, BitMask > 0 (calculado por
  bauth), TTL = duración sesión bauth (máx 12h). Transporta las 6 capas del contexto:
  `tenant_id : entidad_1 : entidad_2 : entidad_3 : user_id : traceparent` (UUIDv7, RFC 9562).

**Ciclo de vida de una sesión (SBOS-049 §16):**
```
Fase 1 — Pre-auth:  Dispositivo arranca → BOS crea dctx_id (bitmask=0x0) → trazabilidad anónima
Fase 2 — Promoción: Usuario se autentica → bauth emite JWT con bos_contexts → calcula BitMask
                     → BOS recibe solicitud → crea ctx_id → Redis DB1 (O(1))
                     → Evento context.promoted (dctx_id → ctx_id, FK preservada)
Fase 3 — Operación: CADA request → Kong extrae ctx_id del header baggage W3C
                     → GET :9443/api/v1/context/{ctx_id} → Redis O(1) < 1ms
                     → Kong inyecta headers X-SBOS-* al servicio destino
Fase 4 — Logout:    bauth invalida sesión → BOS invalida ctx_id → Redis TTL=0
                     → bkernel_db preserva la sesión para auditoría perpetua (ISO 27001 A.8.15)
```

**Arquitectura Redis — Fast-path / Slow-path (patrón de industria 2025):**
- **Fast-path:** Kong → Redis GET ctx:{tenant}:{ctx_id} → O(1) < 1ms. 99% de requests.
- **Slow-path:** Redis miss → PostgreSQL query → recarga en Redis. Degradación elegante:
  si Redis cae, Kong valida directo contra PostgreSQL (mayor latencia, sistema sigue operativo).
- **Graceful degradation:** cliente Redis con exponential backoff (máx 2s), `enableOfflineQueue: false`
  para fail-fast. Sin caché en memoria — Redis o PostgreSQL, nada intermedio.
- **Encryption at rest:** datos de sesión en Redis con AES-256-GCM (patrón BrainGrid 2025).

**Propagación W3C Trace Context + OTel Baggage (estándar CNCF):**
- **`traceparent`:** `00-{traceId32}-{spanId16}-01` — trazabilidad técnica en todos los servicios.
- **`baggage`:** `ctx.id=ctx-88291-a4f9,tenant.id=skull,bdomain.id=SKULL-CORP,bsubdomain.id=Norte,pos.id=CAJA-01,actor.id=juan-perez`
  — contexto empresarial propagado sin modificar el código de las fichas (cero invasión).
  Las keys reflejan el modelo de identidad universal D00 v2.0 (5 niveles con tipos variables,
  no limitado a empresa/sucursal).
- **Seguridad baggage:** fail-closed con allowlist explícito. Máximo 32 items, 8KB total.
  Sanitización contra CRLF injection. No propagar a servicios externos (`PROPAGATE_TO_EXTERNAL=false`).
- **OTel Collector + Baggage Processor:** extrae `ctx.id`, `tenant.id`, `bdomain.id`, `bsubdomain.id`,
  `pos.id`, `actor.id` como atributos en todos los spans y logs (Loki, Grafana, Jaeger).

**Los 6 endpoints de la Context API (:9443, TLS 1.3):**
| Método | Endpoint | Propósito | Llamado por |
|--------|----------|-----------|-------------|
| POST | `/api/v1/context/create` | Login → genera ctx_id | bauth |
| POST | `/api/v1/context/switch` | Cambio de contexto sin reautenticación | App |
| DELETE | `/api/v1/context/{ctx_id}` | Logout → invalida ctx_id | bauth |
| GET | `/api/v1/context/{ctx_id}` | Lookup O(1) — CADA request | Kong plugin |
| GET | `/api/v1/context/tenant/{t}` | Lista ctx_id activos del tenant | Admin |
| POST | `/api/v1/context/tenant/{t}/invalidate-all` | Suspensión de tenant | bosctl |

**Seguridad del Contexto (SBOS-054 §8):**
- **UUIDv7 estricto:** validación regex anti-injection en todos los endpoints (SAN-09)
- **Anti-enumeration:** respuesta idéntica (mismo status, mismo mensaje, misma latencia) para
  "no encontrado" y "expirado". Rate limit 100 req/s por IP (token bucket)
- **Sanitización de logs:** ctx_id → solo primeros 8 chars + hash. `session_bauth` nunca en logs (SAN-07)
- **Cross-tenant validation:** `tenant_id` del request coincide con `tenant_id` del ctx_id (SAN-04)
- **TTL enforcement:** ISO 27001 A.9.4.2. dctx_id 8h, ctx_id 12h máximo

**Integración con bauth (2 sesiones, 2 dueños):**
- **BOS** crea ctx_id (sesión de infraestructura). **bauth** emite JWT (sesión de identidad).
- No compiten: bauth autentica y calcula BitMask. BOS transporta contexto. Kong valida.
- Flujo: `bos.ctx.resolve(ctx_id)` → `/run/bos/bauth.sock` → `bauth.context.evaluate` → 12 dominios
  → DomainResult → BOS cachea en Redis DB1 (TTL 30s)

**Criterios de rendimiento (SLOs SBOS-PERF-001):**
- `device.register` < 2s P99 · `ctx_id lookup` Redis < 1ms P50 / < 5ms P99
- `context.promoted` end-to-end < 15ms P50 / < 40ms P99
- Context API P99 < 5ms bajo carga Alpha (500 req/s)

### Pilar V — Dashboard & Interface Dual (transversal a todos los pilares)

El BOS no tiene GUI propia. Expone toda su información vía **Interface Dual** sobre un solo
Unix socket para que cualquier consumidor —el dashboard de bauth, Grafana, CLI, scripts— la
consuma. Es el contrato de comunicación del daemon con el exterior.

**Interface Dual (SBOS-018 §12):**
```
/run/bos/bos.sock (0660, grupo bosagent)
  ├── Vía 1: HTTP/WebSocket → bosctl CLI, dashboard externo (bauth)
  │   Auth: a nivel OS (pertenecer al grupo bosagent). Sin JWT.
  │   Propósito: comandos administrativos, consultas en tiempo real.
  │
  └── Vía 2: JSON-RPC 2.0 → daemons (bauth, biedata...), scripts, agentes IA
      Auth: token compartido (/etc/bos/rpc-token) para métodos destructivos.
      Namespace: bos.<modulo>.<operacion>
      Sin HTTP/TCP entre daemons (SBOS-050 P9) — solo Unix socket.
```

**JSON-RPC 2.0 — 55 métodos registrados en 11 módulos (rpcRegistry real):**

| Módulo | Métodos | Propósito |
|--------|:-------:|-----------|

| `bos.ctx.*` | 10 | device.register, promote, switch, invalidate, get, list, create, validate, auto_migrate, tenant.suspend |
| `bos.k8s.*` | 10 | node.list, node.cordon, node.uncordon, node.drain, pod.evict, pod.restart, scale, rollout.status, rollout.undo, resources.set |
| `bos.bootstrap.*` | 5 | start, verify, resume, status + pg_auxiliar (4 métodos) |
| `bos.query.*` | 6 | system, repair, vdi, tenant, node, context (sagas de consulta paralelas, deadline 4s) |
| `bos.maintenance.*` | 3 | start, status, cancel |
| `bos.ai.*` | 4 | ask, run, confirm, catalog |
| `bos.capacity.*` | 2 | check, status |
| `bos.release.*` | 2 | check, list |
| `bos.saga.*` | 1 | execute |
| `bos.state.*` | 1 | read |
| `bos.health.*` | 1 | check |
| `system.*` | 1 | listMethods |

**Propiedades del dispatcher (ORQUESTA-043):**
- **Auth:** token compartido (`/etc/bos/rpc-token`) para métodos destructivos. Sin token → -32600.
- **Timeouts:** 5s lectura / 30s escritura / 600s sagas. `runWithTimeout` con canal buffer 1.
- **Batch:** `dispatchBatch` — goroutine por solicitud, orden preservado, notificaciones omitidas.
- **Errores estándar:** -32001 (context expired), -32005 (not found), -32006 (timeout), -32007 (invalid state), -32600 (auth required).
- **RPC-CATALOG.md:** generado desde `rpcRegistry` (184 líneas). Método | auth | timeout | ejemplo.

**Principio de equivalencia:** todo lo que `bosctl` puede hacer, el dashboard de bauth puede
hacer (misma API REST sobre el mismo socket). Sin endpoints duplicados, sin privilegios distintos.

**El dashboard visual NO se desarrolla en este proyecto.** La GUI del BOS se integra en el
proyecto bauth como dashboard unificado (identidad + infraestructura + contexto). El BOS solo
provee la capa de datos: JSON-RPC 2.0 + métricas Prometheus `:9090`.

## 8. El modelo de madurez (L0–L4)

La madurez de cada capacidad se mide en cinco niveles. La madurez es **operación real en VPS**,
no presencia de archivos ni compilación:

| Nivel | Nombre | Criterio | Evidencia requerida |
|:-----:|--------|----------|---------------------|
| **L2** | Implementado (sustrato) | Código existe, compila, tests pasan; **no integrado ni verificado en VPS** | Archivo fuente + `go build ./...` + `go test -race ./...` |
| **L3** | Integrado (operativo) | Desplegado en VPS, verificado con pruebas reales, expuesto vía JSON-RPC y bosctl | Log de VPS + `bosctl` output + respuesta JSON-RPC |
| **L4** | Optimizado (ciclo cerrado) | SLOs verificados con k6, auto-reparación validada, cero intervención manual en ciclo completo | Reporte k6 + `bosctl bootstrap verify --full` 14/14 |

**El diagnóstico transversal del BOS (julio 2026):** el sustrato de código es extenso (32
paquetes Go, compila limpio, ~65 átomos con código genuinamente completo), pero la integración
en VPS está en estadios tempranos (VPS inaccesible, 102 TODOs en el código que postergan
funcionalidad a "cuando el Context Plane esté operativo"). El patrón recurrente: *"archivo
existe y compila ✅, VPS/integración ❌"*. **La categoría plena se alcanza subiendo de L2 a
L3** — verificando en la VPS de pruebas lo que ya está codificado.

## 11. Las 10 directrices editoriales para todos los manuales

Norma que cada manual del BOS (existente y futuro) acata para perseguir la categoría:

1. **Control Plane por defecto.** El BOS se documenta como Plano de Control Soberano de 3ra
   gobierna", "el daemon observa", "la ficha declara".

2. **Pilar y número declarados.** Cada manual declara su pilar (§6), su número de catálogo
   `N.MM` donde N = pilar (1-5) y MM = orden por dependencia dentro del pilar, y sus
   dependencias (manuales que deben leerse antes).

3. **Estado del arte obligatorio.** Cada manual compara con las plataformas de referencia de
   la industria (Terraform, Crossplane, ArgoCD, Rancher, Ansible, Metal³) por categoría. El
   [Anexo A.01](Anexos/A.01_ANEXO-INDUSTRIA-CONTROL-PLANES.md) establece la línea base.

4. **Honestidad de madurez.** Cada capacidad se marca con su nivel real (L0-L4) y la evidencia
   concreta (archivo, commit, salida de VPS). Distinguir explícitamente *"código compila"* (L2)
   de *"funciona en VPS"* (L3). Sin VPS → declarar "pendiente verificación en VPS". Sin código
   → declarar "especificado, sin implementar".

5. **Los diferenciadores no se diluyen.** Zero-touch bootstrap, fichas declarativas, sagas con
   compensación, Interface Dual, Context Plane O(1), Day 2 autónomo, soberanía total — se
   afirman donde apliquen, sin relativizarlos.
7. **Evidencia verificable.** Las afirmaciones de funcionamiento se respaldan con: salida de
   `bosctl`, respuesta JSON-RPC, log de VPS, o resultado de `go test -race`. Sin evidencia =
   marcar como "no verificado". Usar `verificar_afirmacion.sh` (AA-1).

8. **Referencias cruzadas.** Los manuales se citan entre sí con rutas relativas; ninguna
   verificación directa contra código fuente son las fuentes de verdad del estado.

9. **Soberanía primero.** Ninguna directriz que exija enviar datos a la nube, depender de un
   SaaS externo, o requerir licencias. La soberanía es innegociable (SBOS-001-VISION). El
   BOS opera 100% en el servidor del cliente.

10. **Ciclo cerrado.** Donde aplique, la madurez apunta a L4: observación continua →
    proyección → políticas → acción → verificación → remediación. No basta con "el código
    existe" — la capacidad debe probarse en ciclo completo sin intervención.

## 12. La hoja de ruta al plano de control pleno

Las tres olas de integración que llevan al BOS de "Plano de Control en sustrato" a "Plano de
Control operativo", en orden de valor:

### Ola 1 — Recuperar la VPS y verificar el sustrato (L2→L3)
**Objetivo:** todo lo que compila, probarlo contra infraestructura real.
- Restaurar acceso SSH a la VPS de pruebas (13.140.128.230)
- Desplegar `bos.service` y verificar bootstrap (M1.1–M1.5)
- Ejecutar `bosctl deploy seed-skull.yml` contra K8s real (M2.2–M2.4)
- Verificar motor de fichas: install/repair/remove de postgresql, redis, minio
- Probar 50+ métodos JSON-RPC contra daemon real (M4.1)
- Ejecutar `bosctl bootstrap verify --full` → 8/8 ✅

### Ola 2 — Completar el Context Plane (L1→L2→L3)
**Objetivo:** resolver los 102 TODOs y activar el Context Plane.
- Resolver TODOs F5: heartbeat, rate limiting, auditoría, sanitización
- Implementar WebSocket sobre Unix socket (F3.C.1)
- Crear contracts/events/ con tipos puros (F3.C.5)
- Verificar P99 ctx_id < 5ms con Redis real y k6 (M3.2)
- Completar seguridad de red: NRS/SAN  

### Ola 3 — Encender los motores de capacidad (L1→L2→L3)
**Objetivo:** Day 2 autónomo con 4 motores.
- Implementar Motor Observación (30+ métricas) y Motor Proyección (regresión lineal)
- Implementar Motor Políticas (YAML declarativo) y Motor Acción (HPA, control admisión)
- Completar governance dual-control para operaciones categoría 3
- Certificar SLOs con k6: P99 < 150ms JSON-RPC, < 5ms ctx_id, < 30s tenant deploy
- Cobertura ≥ 70% en internal/, benchmarks, tests de carga
