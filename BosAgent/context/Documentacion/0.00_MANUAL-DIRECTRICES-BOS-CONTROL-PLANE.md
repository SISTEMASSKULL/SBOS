## 1. Propósito — por qué esta carta

Los manuales del BOS documentan el sistema con honestidad técnica. Esta carta les da un **norte
común**: la categoría **Plano de Control Soberano** (Sovereign Control Plane). Establece (a) qué
significa esa categoría en 2026, (b) cómo el BOS se posiciona en ella frente a la industria, (c)
los criterios que cada pilar debe cumplir, y (d) la norma editorial que todos los manuales acatan
para perseguirla.

**Regla rectora:** ningún manual describe al BOS como "un instalador con TUI" o "un script de
bootstrap". El BOS **es el systemd del sistema operativo empresarial SBOS** — un daemon soberano
permanente que corre en el host Ubuntu, fuera de Kubernetes, con acceso privilegiado a todos los
planos del sistema, las 24 horas del día. Cada manual documenta su parcela de esa categoría y se
mide contra sus criterios.

**Inspiración editorial:** la [carta rectora de bAuth](../BauthAgent/context/Documentacion/0.00_MANUAL-DIRECTRICES-IAM-ENTERPRISE.md) — el BOS es al Plano de Control lo que bAuth es al IAM Enterprise.

## 2. Qué es un Plano de Control Soberano en 2026 — la definición

En 2026, la industria de infraestructura como código reconoce **tres generaciones** de herramientas
(ver [Anexo A.01](Anexos/A.01_ANEXO-INDUSTRIA-CONTROL-PLANES.md) para la comparación completa):

| Generación | Herramientas | Modelo | Limitación |
|-----------|-------------|--------|------------|
| **1ra gen — CLI apply** | Terraform, OpenTofu, Pulumi, Ansible | Ejecutar comando → diff → aplicar → salir | Sin Day 2; drift se acumula entre ejecuciones |
| **2da gen — Control loop** | Crossplane, ArgoCD, Flux, Rancher | Controlador corriendo en K8s; reconcilia continuamente | Solo opera dentro de K8s; no hace bootstrap del SO |
| **3ra gen — Sovereign Control Plane** | **BOS** | Daemon PID 1 en el host; gobierna SO + K8s + apps; zero-touch desde Ubuntu virgen | — (categoría nueva, sin equivalente comercial) |

El Plano de Control Soberano de 3ra generación se define por estos rasgos:

| Rasgo | Qué exige |
|-------|-----------|
| **Soberanía total** | Los datos nunca abandonan el servidor del cliente; sin licencias externas; código auditable en su totalidad; el sistema opera sin depender del fabricante (SBOS-001) |
| **Zero-touch desde el SO** | Ubuntu 26.04 virgen → stack completo en ~48 min sin intervención humana; el humano solo aprueba decisiones de negocio (HITL) mediante el wizard TUI |
| **Declaratividad total** | Toda dependencia, configuración y aplicación es una ficha declarativa (manifest.yml + task_catalog.sh + resources/); cero scripts manuales   |
| **Sagas con compensación** | Toda operación multi-paso (install, update, repair, remove) tiene rollback explícito; 18 estados de ficha con transiciones validadas (ADR-021); el sistema nunca queda en estado inconsistente |
| **Reconciliación continua** | Day 2: el daemon compara estado declarado vs estado real en 5 planos (host SO, K8s, PostgreSQL, Vault, Redis) y corrige drift automáticamente |
| **Interface Dual** | WebSocket RPC (humanos, CLI, GUI) + JSON-RPC 2.0 (daemons, scripts, IA) sobre el MISMO Unix socket `/run/bos/bos.sock`; sin HTTP/TCP entre daemons (SBOS-050 P9) |
| **Multi-tenant nativo** | Alta/Baja/Suspensión de tenants con saga de 7 pasos con compensación; namespaces K8s + realms Keycloak + 9 BDs PostgreSQL + paths Vault aislados por tenant |
| **Day 2 autónomo** | 4 motores corriendo cada 60s (Observación → Proyección → Políticas → Acción); bloqueo de admisión antes de degradar; proyección a 7/30/90 días |

## 3. El posicionamiento del BOS — "el systemd del sistema operativo empresarial"

### 3.1 El BOS como Policy Administrator — exigido por NIST SP 800-207

NIST SP 800-207 §3.2 exige tres componentes en toda Zero Trust Architecture:

| Componente NIST | Responsabilidad | Implementación SBOS |
|----------------|-----------------|---------------------|
| **Policy Engine (PE)** | Evaluar cada request contra políticas dinámicas | bAuth — 12 dominios, BitMask 64-bit, RolTemplate |
| **Policy Administrator (PA)** | Crear/terminar sesiones, emitir tokens de acceso | **BOS** — `bos.ctx.promote`, `bos.ctx.invalidate`, `bos.ctx.invalidate_all_by_tenant` |
| **Policy Enforcement Point (PEP)** | Interceptar y decidir cada request | Kong + plugin SBOS-Context — GET :9443 O(1) |

El BOS es el **Policy Administrator del SBOS**. Sin BOS operativo, no hay Zero Trust. Esta
responsabilidad está exigida por NIST SP 800-207 (Tenet 3: acceso por sesión con privilegio
mínimo, tiempo limitado) e ISO 27001:2022 A.9.4.2 (TTL en sesiones de acceso).

### 3.2 La analogía fundamental

```
Linux kernel   →  gestiona hardware de cómputo (CPU, RAM, disco, red)
BOS            →  gestiona recursos empresariales (tenants, fichas, contexto, capacidad)
```

**El BOS es el `systemd` del sistema operativo empresarial SBOS.** No es un instalador. No es una
herramienta que se ejecuta y termina. Es un **daemon soberano permanente** (systemd, Type=simple,
user=bosagent) que corre las 24 horas, dueño del ciclo de vida completo del servidor empresarial.

### 3.2 Posición real en el stack

```
Ubuntu Linux 26.04 (host)
    │
    └── systemd
          └── bos.service  ← EL BOS VIVE AQUÍ, SIEMPRE (PID del plano de control)
                │
                │  gestiona ↓ (NO está adentro de ellos)
                ├── Kubernetes cluster (kubeadm v1.32.x + Calico)
                │     └── Namespaces (creados por bos)
                │           └── Pods / fichas (instaladas por bos)
                ├── PostgreSQL 18.4 (provisiona 9+ BDs de tenants)
                ├── Keycloak 26.6.2 (crea realms, configura 5 SPIs)
                ├── Vault 2.0.1 (crea paths de secretos AppRole por ficha)
                └── Redis 8.6.2 DB1 (el Context Registry — es su propiedad)
```

### 3.3 Lo que el BOS no es

| Podría parecer | La realidad |
|----------------|-------------|
| Un instalador con TUI | La TUI es solo la interfaz. El BOS es el motor que corre detrás, siempre |
| Una herramienta de monitoreo /proc | /proc es UNA de 30+ fuentes del Motor de Observación — datos secundarios |
| Un CLI que ejecuta comandos | `bosctl` es la interfaz humana. El daemon es el actor real |
| Un proceso que termina al instalar | El BOS corre SIEMPRE. Es el Policy Administrator permanente del sistema |
| Un gestor de Kubernetes | Kubernetes es el runtime. El BOS es el soberano que lo gestiona desde fuera |
| Un orquestador de Helm charts | Las fichas no son Helm charts — son unidades declarativas auto-contenidas con task_catalog.sh |

## 4. Las 5 responsabilidades permanentes del BOS

Estas responsabilidades no son tareas de instalación. Son funciones que el BOS cumple
continuamente mientras está corriendo. Un BOS que no las cumple no es un BOS.

### R1 — Context Plane (CRÍTICA 24/7)

El BOS es el **único dueño del Context Plane**. Cada request HTTP que llega a Kong termina
validando el `ctx_id` contra la Context API del BOS en `:9443`. Si el BOS no responde, **ningún
usuario del SBOS puede operar**. Es la pieza más crítica del ecosistema.

**Ciclo de vida de un usuario:**

```
T+0     Dispositivo Fedora arranca → BOS crea dctx_id pre-auth (bitmask=0x0)
T+N     Usuario presenta credencial → banexus intercepta → bAuth → BOS
T+N+8ms BOS recibe BitMask (3 dominios) → crea ctx_id → Redis DB1 (O(1))
T+N+15ms Capacidades activadas: chapas, apps, cajón POS
T+op    CADA request: Kong → GET :9443/api/v1/context/{ctx_id} → Redis O(1)
T+fin   Logout → BOS invalida ctx_id → Redis TTL=0 → todo bloqueado
```

**Los 6 endpoints de la Context API** (Kong los llama en cada request de cada usuario):

| Método | Endpoint | Propósito |
|--------|----------|-----------|
| POST | `/api/v1/context/create` | Login → genera ctx_id |
| POST | `/api/v1/context/switch` | Cambio de contexto sin reautenticación |
| DELETE | `/api/v1/context/{ctx_id}` | Logout → invalida ctx_id |
| GET | `/api/v1/context/{ctx_id}` | Lookup O(1) — llamado en CADA request |
| GET | `/api/v1/context/tenant/{tenant}` | Lista ctx_id activos del tenant |
| POST | `/api/v1/context/tenant/{tenant}/invalidate-all` | Suspensión de tenant |

### R2 — Ciclo de Vida de Tenants (Saga 7 pasos con compensación)

`bosctl deploy seed.yml` ejecuta una saga de 7 pasos. Si el paso N falla, los pasos 1 a N-1
se revierten automáticamente. No hay estado inconsistente.

```
Paso 1: Crear Realm en Keycloak + 5 SPIs custom
Paso 2: Crear Namespace en K8s con labels + NetworkPolicy + ResourceQuota
Paso 3: Provisionar 9 BDs en PostgreSQL
Paso 4: Crear paths Vault + AppRole por ficha
Paso 5: Inicializar Context Registry en Redis DB1
Paso 6: DDL context_sessions + device_contexts en bkernel_db
Paso 7: Instalar fichas del tenant en orden topológico (DAG)
```

**SLO:** Alta de tenant < 30s P50, < 90s P99 (SBOS-PERF-001).

### R3 — Ficha Engine (DAG resolver + 18 estados)

El BOS resuelve el grafo de dependencias entre fichas (Kahn) y garantiza el orden topológico
de instalación. Cada ficha transita por hasta 18 estados (ADR-021): PENDIENTE → LISTA →
INSTALANDO → INSTALADA → DEGRADADA → REPARANDO → ... El BOS monitorea constantemente y actúa
según el estado de cada ficha.

**SLO:** Instalación de ficha < 60s P50, < 180s P99 (SBOS-PERF-001).

### R4 — Reconciliación (loop cada 15 minutos)

El BOS compara el estado **declarado** (manifest.yml de cada ficha) contra el estado **real**
del sistema en 5 planos (kubectl, ps, Redis, PostgreSQL, Vault). Detecta drift (SHA-256 por
archivo) y repara autónomamente con 3 reintentos. Cada discrepancia queda registrada en
`audit_events` con `ctx_id` — evidencia ISO 27001 A.8.15.

### R5 — Autómata de Capacidad (loop cada 60 segundos, 4 motores)

El BOS no solo instala. Garantiza que el sistema nunca se degrada por falta de capacidad.
Cuatro motores corren en paralelo cada 60 segundos (SBOS-BOS-CAP-001):

```
Motor Observación  → 30+ métricas: ctx_id activos, Redis%, PG conexiones, WAL lag,
                      Kong RPS, bAuth cache miss, MinIO%, K8s nodos
Motor Proyección   → regresión lineal, horizontes 7/30/90 días, intervalo de confianza
Motor Políticas    → YAML declarativo: autonomous | recommend | block_and_alert | emergency
Motor Acción       → HPA override, PgBouncer resize, control admisión 6 niveles, alertas
```

## 5. La arquitectura de comunicación — Interface Dual

```
/run/bos/bos.sock  (0660, grupo bosagent)
(UN solo socket — DOS vías simultáneas sobre el MISMO endpoint)
    │
    ├── Vía 1: WebSocket RPC
    │     Consumidores: bosctl CLI + Core UI Flutter
    │     Propósito: administración humana, comandos interactivos
    │
    └── Vía 2: JSON-RPC 2.0
          Consumidores: biedata, bkernel, bauth, bsearch, agentes IA
          Propósito: invocación programática, sagas, automatización
          Naming: bos.<modulo>.<operacion>
```

**Puertos TCP:**
- `0.0.0.0:9443` — Context API HTTPS (TLS 1.3) — el ÚNICO endpoint TCP del BOS
- `127.0.0.1:9090` — Métricas Prometheus (solo localhost)
- El resto de la comunicación es vía Unix socket — **cero HTTP/TCP entre daemons** (SBOS-050 P9)

## 6. Los 5 pilares de la categoría y sus criterios

La categoría se descompone en **5 pilares** que cubren el ciclo de vida completo del servidor
empresarial. Cada pilar tiene criterios que un Plano de Control Soberano debe cumplir:

### Pilar I — IAM Installer (R1 + R2: Day 0 bootstrap + Day 1 tenants)
Bootstrap del SO, despliegue del stack de identidad, ciclo de vida de tenants.
**Criterios:** bootstrap zero-touch (Ubuntu virgen → K8s + stack) · stack de identidad completo
(Keycloak 26.6.2 + Vault 2.0.1 + Kong 3.9.x + bAuth) · saga de 7 pasos con compensación ·
tenant deploy < 30s P50 · NetworkPolicy deny-all (Zero Trust) · TLS 1.3 en :9443 · sin
intervención manual post-bootstrap (ADR-022) · FAPI 2.0 · evidencia ISO 27001.

### Pilar II — SO Observable (R4 + R5: Day 2)
Observación del host, Kubernetes y el propio BOS. Detección de drift. Proyección de capacidad.
**Criterios:** watchdog unificado 3-capas (Ubuntu + K8s + fichas) cada 30s · recolección 60s de
30+ métricas · regresión lineal con horizonte 7/30/90 días · políticas YAML (autonomous/recommend/
block_and_alert/emergency) · scaling HPA coordinado anti-death-spiral · control de admisión
6 niveles · health checks multi-capa (SO, K8s, daemons, fichas) · alertas graduadas.

### Pilar III — Server FICHAS (R3: Day 1 + Day 2)
Motor administrador de fichas. Instala, actualiza, repara y remueve aplicaciones con sagas compensadas.
**Criterios:** máquina de 18 estados (ADR-021) · parser estricto de manifest.yml (allowlist SAN-10,
semver, licencia OSI, dashboard.json requerido) · ejecutor de 5 fases con señales `__SBOS__STEP__` ·
dependency resolver topológico (Kahn) con oleadas · discovery automático (escaneo de servers/) ·
drift detection (SHA-256 por archivo) · health checker declarativo (command/HTTP/TCP/none) ·
reconciliación cada 5min con 3 políticas · versionado semver (hot/cold/canary) · governance
dual-control para operaciones categoría 3 (remove, scale a 0).

### Pilar IV — Context Plane (R1: transversal a todos los pilares)
Administrar, observar, proveer y validar el ctx_id. Integrar con bAuth para evaluación de 12 dominios.
**Criterios:** device.register < 2s P99 · dctx_id heartbeat 30s con TTL 8h renovable · ctx_id
lookup Redis < 1ms P50 / < 5ms P99 · context.promoted end-to-end < 15ms P50 · Context API :9443
con TLS 1.3 (6 endpoints) · cache Redis DB1 · integración bAuth vía Unix socket `/run/bos/bauth.sock` ·
W3C Trace Context + OTel Baggage · anti-enumeration (respuesta idéntica para "no encontrado" y
"expirado") · rate limiting 100 req/s por IP · sanitización de ctx_id en logs · audit_event por
cada operación · invalidate_all_by_tenant para suspensión.

### Pilar V — Dashboard & Interface Dual (transversal a todos los pilares)
Dotar al dashboard GUI (Flutter) de toda la información del BOS. Interface Dual para humanos y daemons.
**Criterios:** WebSocket RPC + JSON-RPC 2.0 sobre mismo Unix socket (ADR-019/020) · catálogo
50+ métodos JSON-RPC con RPC-CATALOG.md generado · P99 < 150ms bajo carga Alpha (5 tenants,
500 RPS) · contratos de eventos tipados en contracts/events/ · SAGA_SNAPSHOT para reconexión ·
3 momentos de conexión TUI (pre/durante/post instalación)   · headless-first:
deploy sin TUI (DTC-01) · sin secretos en canal de eventos (DTC-10) · daemon nunca bloquea
esperando TUI (DTC-02) · múltiples observadores simultáneos (DTC-04).

## 8. El modelo de madurez (L0–L4)

La madurez de cada capacidad se mide en cinco niveles. La madurez es **operación real en VPS**,
no presencia de archivos ni compilación:

| Nivel | Nombre | Criterio | Evidencia requerida |
|:-----:|--------|----------|---------------------|
| **L2** | Implementado (sustrato) | Código existe, compila, tests pasan; **no integrado ni verificado en VPS** | Archivo fuente + `go build ./...` + `go test -race ./...` |
| **L3** | Integrado (operativo) | Desplegado en VPS, verificado con pruebas reales, expuesto vía JSON-RPC y bosctl | Log de VPS + `bosctl` output + respuesta JSON-RPC |
| **L4** | Optimizado (ciclo cerrado) | SLOs verificados con k6, auto-reparación validada, cero intervención manual en ciclo completo | Reporte k6 + `bosctl bootstrap verify --full` 14/14 |

**El diagnóstico transversal del BOS (julio 2026):** el sustrato de código es extenso (32
paquetes Go, compila limpio, ~65 átomos con código genuinamente completo), pero la integración
en VPS está en estadios tempranos (VPS inaccesible, 102 TODOs en el código que postergan
funcionalidad a "cuando el Context Plane esté operativo"). El patrón recurrente: *"archivo
existe y compila ✅, VPS/integración ❌"*. **La categoría plena se alcanza subiendo de L2 a
L3** — verificando en la VPS de pruebas lo que ya está codificado.

## 11. Las 10 directrices editoriales para todos los manuales

Norma que cada manual del BOS (existente y futuro) acata para perseguir la categoría:

1. **Control Plane por defecto.** El BOS se documenta como Plano de Control Soberano de 3ra
   generación, nunca como "instalador con TUI". El lenguaje refleja la categoría: "el BOS
   gobierna", "el daemon observa", "la ficha declara".

2. **Pilar y número declarados.** Cada manual declara su pilar (§6), su número de catálogo
   `N.MM` donde N = pilar (1-5) y MM = orden por dependencia dentro del pilar, y sus
   dependencias (manuales que deben leerse antes).

3. **Estado del arte obligatorio.** Cada manual compara con las plataformas de referencia de
   la industria (Terraform, Crossplane, ArgoCD, Rancher, Ansible, Metal³) por categoría. El
   [Anexo A.01](Anexos/A.01_ANEXO-INDUSTRIA-CONTROL-PLANES.md) establece la línea base.

4. **Honestidad de madurez.** Cada capacidad se marca con su nivel real (L0-L4) y la evidencia
   concreta (archivo, commit, salida de VPS). Distinguir explícitamente *"código compila"* (L2)
   de *"funciona en VPS"* (L3). Sin VPS → declarar "pendiente verificación en VPS". Sin código
   → declarar "especificado, sin implementar".

5. **Los diferenciadores no se diluyen.** Zero-touch bootstrap, fichas declarativas, sagas con
   compensación, Interface Dual, Context Plane O(1), Day 2 autónomo, soberanía total — se
   afirman donde apliquen, sin relativizarlos.


7. **Evidencia verificable.** Las afirmaciones de funcionamiento se respaldan con: salida de
   `bosctl`, respuesta JSON-RPC, log de VPS, o resultado de `go test -race`. Sin evidencia =
   marcar como "no verificado". Usar `verificar_afirmacion.sh` (AA-1).

8. **Referencias cruzadas.** Los manuales se citan entre sí con rutas relativas; ninguna
   verificación directa contra código fuente son las fuentes de verdad del estado.

9. **Soberanía primero.** Ninguna directriz que exija enviar datos a la nube, depender de un
   SaaS externo, o requerir licencias. La soberanía es innegociable (SBOS-001-VISION). El
   BOS opera 100% en el servidor del cliente.

10. **Ciclo cerrado.** Donde aplique, la madurez apunta a L4: observación continua →
    proyección → políticas → acción → verificación → remediación. No basta con "el código
    existe" — la capacidad debe probarse en ciclo completo sin intervención.

## 12. La hoja de ruta al plano de control pleno

Las tres olas de integración que llevan al BOS de "Plano de Control en sustrato" a "Plano de
Control operativo", en orden de valor:

### Ola 1 — Recuperar la VPS y verificar el sustrato (L2→L3)
**Objetivo:** todo lo que compila, probarlo contra infraestructura real.
- Restaurar acceso SSH a la VPS de pruebas (13.140.128.230)
- Desplegar `bos.service` y verificar bootstrap (M1.1–M1.5)
- Ejecutar `bosctl deploy seed-skull.yml` contra K8s real (M2.2–M2.4)
- Verificar motor de fichas: install/repair/remove de postgresql, redis, minio
- Probar 50+ métodos JSON-RPC contra daemon real (M4.1)
- Ejecutar `bosctl bootstrap verify --full` → 8/8 ✅

### Ola 2 — Completar el Context Plane (L1→L2→L3)
**Objetivo:** resolver los 102 TODOs y activar el Context Plane.
- Resolver TODOs F5: heartbeat, rate limiting, auditoría, sanitización
- Implementar WebSocket sobre Unix socket (F3.C.1)
- Crear contracts/events/ con tipos puros (F3.C.5)
- Implementar SAGA_SNAPSHOT y 3 momentos de conexión TUI (F20.A)
- Verificar P99 ctx_id < 5ms con Redis real y k6 (M3.2)
- Completar seguridad de red: NRS/SAN  

### Ola 3 — Encender los motores de capacidad (L1→L2→L3)
**Objetivo:** Day 2 autónomo con 4 motores.
- Implementar Motor Observación (30+ métricas) y Motor Proyección (regresión lineal)
- Implementar Motor Políticas (YAML declarativo) y Motor Acción (HPA, control admisión)
- Completar governance dual-control para operaciones categoría 3
- Certificar SLOs con k6: P99 < 150ms JSON-RPC, < 5ms ctx_id, < 30s tenant deploy
- Cobertura ≥ 70% en internal/, benchmarks, tests de carga
