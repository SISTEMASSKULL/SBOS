# Manual de Nomenclatura de Recursos Kubernetes — Motor Server FICHAS
## Convención SBOS para nombres, labels y estructura de recursos K8s

**Versión:** 1.0.0 · **Fecha:** 2026-10-22 · **Autor:** bos-developer — SBOS
**Motor:** ③ Server FICHAS · **Complementa:** [3.01](3.01_MANUAL-SERVER-FICHAS.md), [3.08](3.08_MANUAL-PORT-MANAGER.md)
**Estado:** Vigente — aplicar en toda ficha nueva o modificada

---

## 1. Propósito

Hacer que los nombres de recursos Kubernetes sean predecibles y uniformes, para
poder administrarlos (kubectl, RBAC, NetworkPolicy, monitoreo, scripts) sin
depender de los nombres autogenerados. Esta convención es **obligatoria** en toda
ficha SBOS nueva o modificada a partir de la versión 1.0.0 de este manual.

---

## 2. Convención de nombres

### 2.1 Workload (Deployment / StatefulSet / DaemonSet)

```
<app>
```

- Minúsculas, kebab-case, igual al nombre de la app.
- Sin sufijos de versión (`-v2`), entorno (`-prod`) ni namespace.
- Si la misma app tiene roles distintos en el mismo namespace: `<app>-<rol>`
  (ej. `tryton-workers`, `tryton-cron`, `loki-gateway`).

| ✅ Correcto | ❌ Incorrecto |
|------------|-------------|
| `postgresql` | `postgresql-db`, `postgresql-v15` |
| `kong` | `kong-gateway`, `kong-prod` |
| `tryton` | `tryton-erp`, `tryton-server` |
| `tryton-workers` | `tryton-worker-deployment` |

### 2.2 Service

```
<app>           ← Service principal (ClusterIP)
<app>-headless  ← Service headless de StatefulSet (clusterIP: None)
<app>-<rol>     ← Cuando hay varios roles (ej. kong-proxy, kong-admin)
```

### 2.3 ConfigMap / Secret / PVC

```
<app>-config    ← ConfigMap de configuración principal
<app>-secret    ← Secret de credenciales
<app>-data      ← PVC de datos persistentes
<app>-<función> ← Cuando hay varios (ej. postgresql-data, postgresql-config)
```

### 2.4 Namespace

Prefijo `sbos-<dominio>` (ya existente). Un dominio por namespace. No modificar.

## 3. Labels obligatorios

Todos los recursos K8s de una ficha SBOS (metadata, selector y pod template)
deben incluir los cinco labels estándar de Kubernetes:

```yaml
labels:
  app.kubernetes.io/name: <app>           # nombre de la app (ej. kong)
  app.kubernetes.io/instance: <app>       # instancia (igual a name en SBOS single-tenant)
  app.kubernetes.io/component: <rol>      # rol funcional (server, worker, cron, proxy, db...)
  app.kubernetes.io/part-of: sbos         # siempre "sbos"
  app.kubernetes.io/managed-by: bos       # siempre "bos" (fichas SBOS)
```

**Ejemplo completo** en un Deployment:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: kong
  namespace: sbos-gateway
  labels:
    app.kubernetes.io/name: kong
    app.kubernetes.io/instance: kong
    app.kubernetes.io/component: proxy
    app.kubernetes.io/part-of: sbos
    app.kubernetes.io/managed-by: bos
spec:
  selector:
    matchLabels:
      app.kubernetes.io/name: kong
      app.kubernetes.io/instance: kong
  template:
    metadata:
      labels:
        app.kubernetes.io/name: kong
        app.kubernetes.io/instance: kong
        app.kubernetes.io/component: proxy
        app.kubernetes.io/part-of: sbos
        app.kubernetes.io/managed-by: bos
```

> **CRÍTICO:** `spec.selector` es **inmutable** en Deployments y StatefulSets.
> Cambiar el selector requiere recrear el recurso. Ver §5.

## 4. Restricciones de migración

### 4.1 StatefulSets con datos — NO renombrar sin plan de PVC

Renombrar un StatefulSet cambia el nombre de los PVC generados por
`volumeClaimTemplates` (patrón `<pvc-name>-<sts-name>-N`) y deja los datos
**huérfanos**. Para cualquier StatefulSet con estado persistente:

1. Hacer backup de la BD/datos antes de cualquier cambio
2. Crear el nuevo StatefulSet apuntando a los PVC existentes (con `claimName` fijo)
3. Migrar el tráfico al nuevo recurso
4. Eliminar el viejo StatefulSet

**Workloads con estado — NO renombrar sin plan:**
`postgresql`, `mysql`, `redis`, `vault`, `qdrant`, `keycloak`, `tryton`,
`rabbitmq-erp`, `rabbitmq-search`, `ollama`, `nextcloud`, `onlyoffice`,
`paperless-ngx`, `docuseal`, `solr`, `stalwart`, `vaultwarden`, `wikijs`,
`openproject`, `trilium`, `alertmanager`, `prometheus`, `loki`, `tempo`

### 4.2 Recursos gestionados por Helm — NO modificar con kubectl

Los resources con `app.kubernetes.io/managed-by: Helm` (zabbix, loki-stack, etc.)
se modifican solo via `helm upgrade` con los valores correctos, nunca con
`kubectl edit` ni `kubectl patch` directo.

### 4.3 Recursos de sistema — NO tocar

`kube-system`, `kyverno`, `calico`, `local-path-provisioner`, `cert-manager`,
`metallb`, `kube-state-metrics` (nombre estándar de la comunidad).

## 5. Plan de migración por fases

La migración sigue el orden de menor a mayor riesgo:

### Fase 0 — Labels estándar (sin riesgo)

Agregar los cinco labels a `metadata.labels` del workload. **No** cambia
`spec.selector` ni `spec.template.metadata.labels` — solo metadata del recurso.
Se aplica con `kubectl patch` o `kubectl label`.

```bash
kubectl patch deployment <app> -n <ns> --type merge \
  -p '{"metadata":{"labels":{
    "app.kubernetes.io/name":"<app>",
    "app.kubernetes.io/instance":"<app>",
    "app.kubernetes.io/component":"<rol>",
    "app.kubernetes.io/part-of":"sbos",
    "app.kubernetes.io/managed-by":"bos"
  }}}'
```

### Fase 1 — Labels en pod template (precaución)

Agregar labels estándar al `spec.template.metadata.labels` **además** de los
labels selector existentes (nunca reemplazarlos). Causa rolling restart.

### Fase 2 — Renombrar Services stateless

Recrear el Service con el nombre correcto. Actualizar todas las referencias
internas (`<svc>.<ns>.svc.cluster.local`). Bajo riesgo — los Services son
rápidos de recrear.

### Fase 3 — Renombrar Deployments stateless

Recrear el Deployment con el nombre correcto. **Verificar** que ningún
HPA, RBAC, NetworkPolicy ni variable de entorno lo referencia por nombre.
Aplicar `kubectl diff` antes de recrear.

### Fase 4 — StatefulSets con estado (alto riesgo)

Solo con backup verificado y en ventana de mantenimiento. Ver §4.1.

## 6. Script de validación

```bash
#!/usr/bin/env bash
# Valida que todos los workloads SBOS tienen los labels obligatorios
set -euo pipefail

FAIL=0
for ns in $(kubectl get ns --no-headers 2>/dev/null | awk '{print $1}' | grep "^sbos-"); do
  for kind in deployment statefulset daemonset; do
    while IFS= read -r name; do
      [[ -z "$name" ]] && continue
      for label in "app.kubernetes.io/name" "app.kubernetes.io/instance" \
                   "app.kubernetes.io/component" "app.kubernetes.io/part-of" \
                   "app.kubernetes.io/managed-by"; do
        val=$(kubectl get "$kind" "$name" -n "$ns" \
          -o jsonpath="{.metadata.labels['$label']}" 2>/dev/null || true)
        if [[ -z "$val" ]]; then
          echo "FAIL [$ns/$kind/$name] falta label: $label"
          FAIL=1
        fi
      done
    done < <(kubectl get "$kind" -n "$ns" --no-headers 2>/dev/null | awk '{print $1}')
  done
done

(( FAIL == 0 )) && echo "OK — todos los workloads cumplen la convención" || exit 1
```

## 7. Lo que NO se renombra (y por qué)

| Recurso | Motivo |
|---------|--------|
| `zabbix-zabbix-*` | Gestionado por Helm chart; renombrar requiere `helm upgrade --set` |
| `kube-state-metrics` | Nombre estándar de la comunidad, referenciado en dashboards Prometheus |
| `prometheus-node-exporter` | Ídem — scrape configs lo referencian por nombre |
| Todos los StatefulSets listados en §4.1 | Requieren plan de migración de PVC + backup |
| `loki-gateway` | Nombre `<app>-<rol>` ya cumple la convención |

## 8. Incoherencias actuales detectadas (inventario 2026-10-22)

| Recurso actual | Problema | Acción |
|----------------|---------|--------|
| Todos los workloads | 0/50 tienen labels `app.kubernetes.io/*` | Fase 0 |

| `rabbitmq-erp`, `rabbitmq-search` | Sufijo de namespace como disambiguación | Aceptable: mismo app en dos NS |
