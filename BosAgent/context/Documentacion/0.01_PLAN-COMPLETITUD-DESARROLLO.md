## Principio rector

> **Una etapa está completa cuando el operador puede verificarla en la VPS real sin leer el código.**

Cada etapa produce un estado del sistema **observable** con comandos concretos. Si la verificación
falla, la etapa no está completa — sin importar si el código "se ve bien". Este principio viene
de `bosctl bootstrap verify` (A.11 R1-R7): el criterio es el comportamiento observable, no la
intención del código.

`bosctl port list` muestra los puertos asignados en tiempo real.

**Referencia:** 3.08 · A.12 (Port Manager Kardex) · RFC 6335

### Tareas de código

| 4.2 | Wire en `lifecycle.go` — al estado `INSTALADA`: llamar `portman.AssignFromManifest(fichaID, manifest)` | `internal/ficha/lifecycle.go` |
| 4.3 | Wire en `lifecycle.go` — al estado `REMOVIDA`: llamar `portman.Release(fichaID)` | `internal/ficha/lifecycle.go` |
| 4.4 | `reconcile/scheduler.go`: cada 300s, llamar `portman.ValidateKardex()` — detecta puertos en Kardex que no tienen pod activo | `internal/reconcile/scheduler.go` |
| 4.5 | `bosctl port list` — tabular todos los registros del Kardex T-408 | `cmd/bosctl/port.go` |
| 4.6 | `bosctl port lookup <puerto>` — quién usa este puerto | `cmd/bosctl/port.go` |
| 4.7 | `bosctl port validate` — comparar Kardex vs puertos K8s reales (detectar drift) | `cmd/bosctl/port.go` |

### Verificación de la Etapa 4

```bash
# Instalar una ficha y verificar que el puerto queda en el Kardex
bosctl ficha install postgresql
bosctl port list
# Esperado: postgresql  5432  TCP  HOST_PHYSICAL  assigned  <fecha>

bosctl port lookup 5432
# Esperado: servicio=postgresql, ficha=postgresql, estado=assigned

# Verificar que al remover, el puerto se libera
bosctl ficha remove postgresql
bosctl port list
# Esperado: postgresql  5432  TCP  HOST_PHYSICAL  released  <fecha>
# (inmutabilidad lógica — la fila existe pero estado=released)

# Validar Kardex vs K8s real
bosctl port validate
# Esperado: "Kardex consistente — 5 puertos verificados"
```

**Criterio de salida:** cada `bosctl ficha install` de cualquier ficha con puerto produce una
fila en el Kardex T-408 verificable con `bosctl port list`.

## Etapa 5 — Autómata de Capacidad (4 motores)

**Objetivo:** el BOS no solo instala — OBSERVA y PROYECTA. Los 4 motores de capacidad corren
cada 60s automáticamente dentro de `run_normal.go`. `bosctl capacity status` muestra el estado
de cada componente. `bosctl capacity forecast` muestra proyección a 7/30/90 días.

**Referencia:** 2.01 · 2.02 · 2.03 · 2.04 · BOS-REPAIR-02 (Operator Soberano)

### Los 4 motores

```
Motor 1 — Observación  → recolecta 30+ métricas cada 60s → escribe en bos.cap_sistema_snapshot (T-406)
Motor 2 — Proyección   → regresión lineal + horizonte 7/30/90d + intervalo de confianza
Motor 3 — Políticas    → evalúa capacidad.yml declarativo → autonomous | recommend | block_and_alert
Motor 4 — Acción       → HPA scaling + alertas graduadas + bloqueo de admisión
```

### Tareas de código

| # | Tarea | Paquete |
|---|-------|---------|
| 5.1 | `capacity.Collector.Collect()`: 30+ métricas — Redis %, PG conexiones, K8s CPU/RAM, Kong RPS, bauth cache miss | `internal/capacity/calculator.go` |
| 5.2 | Integrar `Collector` en `run_normal.go` subsistema #16 — goroutine con ticker 60s | `cmd/bos/run_normal.go` |
| 5.3 | `capacity.Forecaster.Forecast()`: regresión lineal sobre últimas N muestras de cap_db, horizonte configurable | `internal/capacity/model.go` |
| 5.4 | `capacity.PolicyEngine.Evaluate()`: leer `capacity.yml` declarativo, comparar métricas vs thresholds | nuevo: `internal/capacity/policy.go` |
| 5.5 | `capacity.ActionEngine.Act()`: HPA scale-up, alerta por webhook, bloqueo de nuevos ctx_id si crítico | nuevo: `internal/capacity/action.go` |
| 5.6 | `bosctl capacity status` — tabla con 30+ métricas, estado (OK/WARN/CRIT) y tendencia | `cmd/bosctl/` |
| 5.7 | `bosctl capacity forecast --horizon 30d` — proyección con confianza | `cmd/bosctl/` |
| 5.8 | `bos.capacity.check` JSON-RPC — retorna estado del sistema en tiempo real | `internal/server/` |

## Etapa 10 — VDI + sbos-client — La Cúspide

**Objetivo:** el usuario final accede a un escritorio Fedora KDE completo vía navegador.
`sbos-client` se descarga desde el servidor y conecta automáticamente al VDI del tenant.
Esta etapa es el objetivo final del SBOS.

**Referencia:** BOS-REPAIR-09 (SBOS-052 VDI Spec) · BOS-REPAIR-14 (sbos-client spec) · A.02

### Componentes

| Componente | Descripción |
|------------|-------------|
| `S11-vdiserver` | Nextcloud (S11), OnlyOffice, Fedora KDE (Guacamole), escritorio virtual |
| `sbos-client` | Binario descargable: conecta WS mTLS :9444, SSO automático, modo kiosk |
| ISO SBOS | Imagen booteable con sbos-client preinstalado para hardware del tenant |
| Guacamole | Proxy HTML5 para escritorio Fedora accesible desde cualquier navegador |

### Verificación de la Etapa 10

```bash
# Instalar VDI server
bosctl ficha install --server S11

# Acceder al escritorio
curl -k https://<tenant>.sbos.app/desktop
# Esperado: redirige a Guacamole → Fedora KDE accesible en navegador

# sbos-client
./sbos-client --server https://<tenant>.sbos.app --user admin
# Esperado: autenticación SSO → escritorio Fedora disponible
```

**Criterio de salida:** escritorio Fedora KDE accesible desde navegador.
sbos-client descargable y funcional. ISO generada con datos del tenant.
