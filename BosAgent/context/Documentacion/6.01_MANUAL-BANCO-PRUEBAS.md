## Protocolo de prueba

Cada prueba tiene **dos vías obligatorias**:
- **Vía 1** — bosctl CLI (WebSocket sobre `/run/bos/bos.sock`)
- **Vía 2** — JSON-RPC 2.0 crudo (curl + Unix socket)

**Preflight:** el daemon `bos.service` debe estar activo con `BOS_NO_RPC_TOKEN=true` en entorno de desarrollo.

```bash
# Verificar daemon activo
systemctl status bos.service | grep Active

# Verificar socket
ls -la /run/bos/bos.sock

# Helper: JSON-RPC crudo
alias bos_rpc='curl -s -X POST --unix-socket /run/bos/bos.sock http://unix/rpc \
  -H "Content-Type: application/json" \
  -H "Authorization: Basic c2Jvc19hZG1pbjpkZXY6ZGV2LXRva2VuLTIwMjY=" \
  -d'
```

## Módulo ④ Context Plane — bos.ctx.*

### P-CTX-01 — bos.ctx.device.register

**Descripción:** registrar un dispositivo pre-autenticado (estado PENDIENTE).

```bash
# Vía 1 (no hay comando bosctl directo — solo JSON-RPC)
# Vía 2
bos_rpc '{"jsonrpc":"2.0","method":"bos.ctx.device.register",
  "params":{"hostname":"nodo-01","tenant_id":"skull","node_k8s":"k8s-01","ip":"10.0.0.1"},
  "id":1}'
```

**Esperado:** `{"result":{"dctx_id":"<uuid>","state":"PENDIENTE",...}}`

---

### P-CTX-02 — bos.ctx.promote

**Descripción:** promover DeviceContext a SessionContext (simula post-autenticación bAuth).

```bash
# Vía 2
bos_rpc '{"jsonrpc":"2.0","method":"bos.ctx.promote",
  "params":{"dctx_id":"<id>","empresa_id":"e1","sucursal_id":"s1",
            "pos_logico":"p1","user_id":"admin","bitmask":15,"loa":2,
            "traceparent":"00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01"},
  "id":2}'
```

**Esperado:** `{"result":{"ctx_id":"<uuid>","state":"ACTIVO","bitmask":15,...}}`

**Audit:** verificar entrada en `/var/log/bos/audit.log` con `action=promote`.

---

### P-CTX-03 — bos.ctx.get

**Descripción:** recuperar SessionContext activo por ctx_id.

```bash
# Vía 1
bosctl ctx get <ctx_id>

# Vía 2
bos_rpc '{"jsonrpc":"2.0","method":"bos.ctx.get","params":{"ctx_id":"<id>"},"id":3}'
```

**Esperado:** campos completos con `expired: false`.

---

### P-CTX-04 — bos.ctx.heartbeat ✅ NUEVO (2026-07-30)

**Descripción:** extender TTL de un ctx_id activo (SBOS-049 §3.3).

```bash
# Vía 1
bosctl ctx heartbeat <ctx_id>

# Vía 2
bos_rpc '{"jsonrpc":"2.0","method":"bos.ctx.heartbeat","params":{"ctx_id":"<id>"},"id":4}'
```

**Esperado:** `{"result":{"ctx_id":"<id>","expires_at":"<+12h>","extended":true}}`

**Verificar:** que `expires_at` es posterior a la expiración anterior.

**Casos de error:**
- ctx_id vacío → `-32602` (InvalidParams)
- ctx_id no existente → `-32001` (ContextExpired)
- ctx_id ya expirado → `-32001` (ContextExpired)

## Módulo ① Tenants — bosctl tenant

### P-TENANT-01 — tenant suspend ✅ NUEVO (2026-07-30)

**Descripción:** suspender un tenant (invalida todas sus sesiones activas).

```bash
# Vía 1
bosctl tenant suspend skull

# Vía 2
bos_rpc '{"jsonrpc":"2.0","method":"bos.ctx.tenant.suspend",
  "params":{"tenant_id":"skull"},"id":10}'
```

**Esperado:**
- Vía 1: `Tenant skull suspendido — sesiones activas invalidadas`
- Vía 2: `{"result":{"tenant_id":"skull","invalidated":N}}`
- Audit: `action=tenant.suspend tenant=skull invalidated=N result=ok`

**Verificar después:** `bosctl ctx list --tenant=skull` → `total: 0`

---

### P-TENANT-02 — tenant remove ✅ NUEVO (2026-07-30)

**Descripción:** saga inversa de eliminación de tenant (7 pasos, HITL requerido).

```bash
# Vía 1 (requiere confirmación interactiva)
bosctl tenant remove skull
# Escribir "skull" cuando lo solicite
```

**Esperado:** saga 7 pasos en orden inverso:
1. Invalidación de sesiones (bos.ctx.tenant.suspend)
2. Aviso fichas de aplicación
3. Eliminación Keycloak realm
4. Eliminación paths Vault
5. Limpieza Redis context registry
6. Eliminación bases de datos PostgreSQL
7. Eliminación namespace K8s

**Verificar:** `bosctl ficha list` → sin fichas activas del tenant.

---

### P-TENANT-03 — tenant remove cancelado

**Descripción:** el operador escribe confirmación incorrecta → operación cancelada.

```bash

```

**Esperado:** `Confirmacion incorrecta. Operacion cancelada.` — sin cambios en el sistema.

## Módulo ① Seguridad — NRS/SAN ✅ NUEVO (2026-07-30)

### P-SEC-01 — NRS-07 Anti-enumeration (ctx_id no encontrado = expirado)

**Descripción:** `bos.ctx.get` con ctx_id inexistente debe retornar el mismo error que uno expirado.

```bash
# Vía 2 — ctx_id inventado
bos_rpc '{"jsonrpc":"2.0","method":"bos.ctx.get","params":{"ctx_id":"00000000-0000-4000-8000-000000000000"},"id":1}'
```

**Esperado:** `{"error":{"code":-32001,"message":"ctx_id no válido o expirado"}}`

**Verificar:** el mensaje es IDENTICO tanto para "no encontrado" como para "expirado" — no distinguibles.

---

### P-SEC-02 — NRS-08 Rate limiting (429 al exceder 100 req/s)

**Descripción:** 101 solicitudes en menos de 1 segundo desde la misma IP deben activar el rate limit.

```bash
# Vía 2 — 110 requests en paralelo rápido
for i in $(seq 1 110); do
  bos_rpc '{"jsonrpc":"2.0","method":"bos.health.check","params":{},"id":'$i'}' &
done | grep -c '"code":-32029' || echo "rate limit no activado"
```

**Esperado:** al menos algunas respuestas con `{"error":{"code":-32029,"message":"demasiadas solicitudes..."}}` y HTTP 429.

**Nota:** Unix socket (bosctl) NO tiene rate limit — solo el endpoint HTTP :9443.

---

### P-SEC-03 — NRS-09 Métricas de validación de ctx_id

**Descripción:** tras validar ctx_ids, los contadores Prometheus deben incrementar.

```bash
# Validar un ctx_id (OK)
bos_rpc '{"jsonrpc":"2.0","method":"bos.ctx.get","params":{"ctx_id":"<valid>"},"id":1}'

# Validar un ctx_id inválido (FAIL)
bos_rpc '{"jsonrpc":"2.0","method":"bos.ctx.get","params":{"ctx_id":"invalid"},"id":2}'

# Consultar métricas (endpoint /metrics si habilitado)
curl http://localhost:9443/metrics | grep bos_ctx_validate
```

**Esperado:**
```
bos_ctx_validate_ok_total N
bos_ctx_validate_fail_total M
```

### P-SEC-04 — NRS-01 TLS 1.3 en :9443

**Descripción:** el endpoint HTTPS debe rechazar TLS 1.2 y versiones anteriores.

```bash
# Verificar TLS 1.3
openssl s_client -connect localhost:9443 -tls1_3 2>&1 | grep "Protocol"
# → TLSv1.3

# Verificar rechazo de TLS 1.2
openssl s_client -connect localhost:9443 -tls1_2 2>&1 | grep "handshake failure"
# → debe mostrar error de handshake
```

**Esperado:** solo TLS 1.3 aceptado; TLS 1.2 rechazado.

---

### P-SEC-05 — SAN-07 ctx_id seguro en logs

**Descripción:** los logs de BOS no deben contener ctx_ids completos.

```bash
# Promover una sesión y verificar logs
tail -n 20 /var/log/bos/audit.log | grep "ctx_id"
```

**Esperado:** los ctx_id en logs siguen el patrón `4bf92f35…abc123` (8 chars + "…" + hash) — nunca el UUID completo.

**Nota:** `sanitize.LogCtxID("4bf92f35-77b3-4da6-a3ce-929d0e0e4736")` → `"4bf92f35…<hash6chars>"`

### P-SEC-06 — SAN-05 Email (formato RFC 5321)

**Descripción:** validar que `sanitize.Email` acepta emails válidos y rechaza malformados.

```go
// En tests Go (internal/sanitize/sanitize_test.go)
sanitize.Email("admin@skull.com")        // → true
sanitize.Email("sin-arroba")             // → false
sanitize.Email("")                       // → false
```

---

### P-SEC-07 — SAN-06 JSONPayload (tamaño + validez)

**Descripción:** `sanitize.JSONPayload` debe rechazar JSON malformado, vacío o que exceda límite.

```go
sanitize.JSONPayload([]byte(`{"k":"v"}`), 1024)   // → nil (OK)
sanitize.JSONPayload([]byte(`{broken`), 1024)      // → error (JSON inválido)
sanitize.JSONPayload([]byte(`{}`), 1)              // → error (excede 1 byte)
sanitize.JSONPayload(nil, 1024)                    // → error (vacío)
```

---

### P-SEC-08 — SAN-10 HeaderValue (CRLF injection)

**Descripción:** cabeceras con `\r`, `\n` o byte nulo deben ser rechazadas.

```go
sanitize.HeaderValue("application/json")           // → ("application/json", nil)
sanitize.HeaderValue("val\r\nX-Bad: injected")     // → ("", error)
sanitize.HeaderValue("val\x00null")                // → ("", error)
```

---

### P-SEC-09 — SAN-11 CrossTenantSlug (protección inter-tenant)

**Descripción:** tenant de la sesión debe coincidir con el tenant del recurso.

```bash
# Vía 2 — ctx_id de tenant "skull" intentando acceder recurso de "acme"
bos_rpc '{"jsonrpc":"2.0","method":"bos.ctx.get","params":{"ctx_id":"<ctx_skull>"},"id":1}'
# Los handlers que llamen a CrossTenantSlug("skull", "acme") retornarán error
```

**Esperado:** cualquier operación cross-tenant retorna `-32602` o `-32001`.

---

### P-SEC-10 — SAN-12 CrossTenantK8sName (namespace K8s)

**Descripción:** nombres de recursos K8s deben seguir el patrón del tenant.

```go
sanitize.CrossTenantK8sName("skull", "skull")           // → nil (OK)
sanitize.CrossTenantK8sName("skull", "skull-postgres")  // → nil (OK)
sanitize.CrossTenantK8sName("skull", "acme-postgres")   // → error (otro tenant)
sanitize.CrossTenantK8sName("skull", "skulls-redis")    // → error (prefijo parcial no cuenta)
```
