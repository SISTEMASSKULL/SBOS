## §1 Principios del mantenimiento

El mantenimiento de bi18n se rige por **ISO/IEC 14764:2022**, que clasifica cuatro tipos de mantenimiento. Todo cambio al código fuente debe ser identificado como uno de ellos antes de comenzar:

| Tipo | ISO 14764 | Ejemplo en bi18n |
|---|---|---|
| **Correctivo** | §3.1 — corregir defectos detectados | Bug en un handler; método RPC devuelve campo erróneo |
| **Adaptativo** | §3.2 — adaptar a nuevo entorno | Actualización mayor de una librería; migración de SO |
| **Perfectivo** | §3.3 — mejorar rendimiento o mantenibilidad | Refactorizar handler para bajo < 50 líneas; añadir nuevo método RPC |
| **Preventivo** | §3.4 — incrementar fiabilidad futura | Añadir prueba de regresión; auditar dependencias |

**Regla de análisis de impacto (ISO 14764 §6.3):** antes de cualquier cambio se responde:
1. ¿Qué métodos RPC se ven afectados?
2. ¿El cambio rompe el contrato del dispatcher (nombres, parámetros, tipos de retorno)?
3. ¿Requiere actualizar la batería de pruebas (A.11 / A.12)?
4. ¿Implica cambio en `Cargo.toml` o `Cargo.lock`?

## §2 Árbol de decisión para versiones del daemon

bi18n sigue **Semantic Versioning 2.0.0** ([semver.org](https://semver.org)):

```
MAJOR.MINOR.PATCH  (actualmente declarado en Cargo.toml)

PATCH  →  bug fix sin romper API pública (corrección interna de handler)
MINOR  →  nuevo método RPC, nueva librería expuesta, mejora de rendimiento
MAJOR  →  eliminación de método RPC existente, cambio de parámetros obligatorios,
           cambio de nombre de método, cambio de estructura de respuesta
```

Los commits usan **Conventional Commits v1.0.0** ([conventionalcommits.org](https://www.conventionalcommits.org)):

```
fix(bi18n): corrige guard_str_non_blank cuando value es solo espacios   → PATCH
feat(bi18n): añade bi18n.format.mask_nit_bo                              → MINOR
feat(bi18n)!: renombra bi18n.validate.from_json → bi18n.validate.is_json → MAJOR
```

El footer `BREAKING CHANGE:` o el sufijo `!` en el tipo activan un bump de MAJOR.

## §3 Gestión de dependencias — ciclo de actualización

### 3.1 Política SemVer por tipo de update

| Tipo | Cuándo hacerlo | Riesgo | Procedimiento |
|---|---|---|---|
| **PATCH** (`0.0.X`) | En cada PR automáticamente (CI) | Mínimo | `cargo update --locked` — dentro del rango declarado |
| **MINOR** (`0.X.0`) | Revisión semanal | Bajo | `cargo upgrade --compatible` + `cargo check` + pruebas |
| **MAJOR** (`X.0.0`) | Decisión deliberada, con análisis de impacto | Alto | Leer CHANGELOG de la librería; migrar código; pruebas completas |

### 3.2 Comandos del ciclo de mantenimiento de dependencias

```bash
# 1. Instalar herramientas (una sola vez por entorno de desarrollo)
cargo install cargo-edit   # cargo upgrade
cargo install cargo-audit  # auditoría de seguridad

# 2. Auditoría semanal de seguridad
cargo audit
# Si hay RUSTSEC con severidad HIGH o CRITICAL: actualizar de inmediato

# 3. Actualizar parches (CI automático — dentro del rango de Cargo.toml)
cargo update
cargo check --locked
cargo test --locked

# 4. Subir minor versions (revisión semanal en rama feature/deps)
cargo upgrade --compatible   # solo sube X.Y.Z donde Y cambia (no X)
cargo check
cargo test
# Si pasa → PR → aprobación → merge

# 5. Subir major version (decisión deliberada)
cargo upgrade --incompatible ask   # pide confirmación por cada cambio mayor
# Leer el CHANGELOG de la librería afectada
# Adaptar el código en src/server/handlers/lib_<nombre>.rs
# Ejecutar A.11 + A.12 completos
# PR + revisión de código + aprobación

# 6. Verificar build reproducible (OBLIGATORIO en CI)
cargo build --locked --release
# --locked falla si Cargo.lock no coincide con el repo — evita "funciona en mi máquina"
```

### 3.3 `Cargo.lock` — siempre commiteado

Per [Rust Blog 2023-08-29](https://blog.rust-lang.org/2023/08/29/committing-lockfiles/): todo proyecto binario debe commitear `Cargo.lock`. El CI usa `--locked` para garantizar reproducibilidad exacta.

```bash
git add Cargo.lock    # siempre incluir en el commit que actualiza dependencias
```

### 3.4 Procedimiento de adición de nueva librería

1. Añadir en `Cargo.toml` con rango exacto: `nueva-lib = "X.Y"`
2. Leer `~/.cargo/registry/src/.../nueva-lib-X.Y.Z/src/` — verificar API real
3. Crear `src/server/handlers/lib_<nombre>.rs` (≤ 800 líneas, funciones ≤ 50 líneas)
4. Registrar en `src/server/dispatcher.rs` (arms del match)
5. Registrar en `src/server/handlers/mod.rs` (`pub mod lib_<nombre>;`)
6. Añadir módulo CLI en `src/cli/<nombre>.rs`
7. Referenciar en `src/bin/bi18nctl.rs`
8. Actualizar A.10 (inventario API) y REGISTRO-ESTADO-DOS.md
9. Añadir pruebas a A.11 (CLI) y A.12 (Frontend)
10. Ejecutar `cargo audit` + `cargo check --locked` + `cargo test --locked`

## §4 Procedimiento de adición de nuevo método RPC

```
Spec → Handler → Dispatcher → CLI → Pruebas → Registro → Commit
```

### 4.1 Paso a paso

**Paso 1 — Especificar (antes de codificar)**
Escribir en papel o comentario: nombre del método, parámetros de entrada, estructura de retorno, casos de error. Ejemplo:
```
bi18n.format.mask_nit_bo
  entrada: { "ctx_id": "...", "text": "123456789" }
  salida:  { "masked": "123.456.789-0" }
  error:   ParamAusente si text vacío
```

**Paso 2 — Handler**
Añadir función en el `lib_*.rs` correspondiente al namespace:
```rust
/// Enmascara NIT boliviano (9 dígitos → NNN.NNN.NNN-D).
/// Entrada: `{ "text": "123456789", "ctx_id": "..." }`.
/// Salida: `{ "masked": "123.456.789-0" }`.
pub async fn format_mask_nit_bo(_ctx: &ServerContext, params: &Value)
    -> Result<Value, Bi18nError>
{
    let text = extraer_text(params)?;
    let masked = mask(text, "XXX.XXX.XXX-X");
    Ok(json!({ "masked": masked }))
}
```

**Paso 3 — Dispatcher**
En `src/server/dispatcher.rs`, dentro del `match method`:
```rust
"bi18n.format.mask_nit_bo" => {
    handlers::lib_universal_mask::format_mask_nit_bo(ctx, &params).await
}
```

**Paso 4 — CLI**
En `src/cli/format_fase2.rs` (o el módulo correspondiente), añadir variante al enum:
```rust
/// Enmascara NIT boliviano (9 dígitos).
MaskNitBo { #[arg(long)] text: String },
```
Y su arm en `construir_llamada`:
```rust
FormatFase2::MaskNitBo { text } => (
    "bi18n.format.mask_nit_bo",
    json!({ "ctx_id": ctx_id, "text": text }),
),
```

**Paso 5 — Pruebas**
Añadir caso en A.11 (CLI) y A.12 (Frontend).

**Paso 6 — Registro**
Actualizar `REGISTRO-ESTADO-DOS.md`: tabla de tracking, total de métodos.

**Paso 7 — Commit**
```bash
cargo check --locked      # 0 errores
cargo audit               # 0 vulnerabilidades nuevas
git add -p                # revisar archivo por archivo
git commit -m "feat(bi18n): añade bi18n.format.mask_nit_bo"
```

### 4.2 Reglas de naming del dispatcher

- Formato: `bi18n.<namespace>.<accion>` (todo minúsculas, guiones bajos)
- Namespace debe existir ya en el dispatcher o justificarse con spec (anexo A.08.XX)
- Nunca inventar un método que no esté en el spec — usar A.10 como referencia de la API real

## §5 Actualización zero-downtime en producción

### 5.1 Arquitectura systemd + socket activation

bi18n usa **socket activation** de systemd. El socket `/run/bos/bi18n.sock` es propiedad de systemd — nunca deja de escuchar durante un reinicio del daemon:

```
systemd (dueño del socket)
  │
  ├── bi18n.socket   ← el kernel encola conexiones mientras bi18nd reinicia
  │
  └── bi18n.service  ← el proceso puede reiniciarse sin perder el socket
```

Esto garantiza que los clientes (bAuth, biedata, frontend) no reciban `ECONNREFUSED` durante un update.

### 5.2 Procedimiento de deploy en producción

```bash
# 1. Compilar en el servidor de build (nunca compilar en producción)
cargo build --locked --release --target x86_64-unknown-linux-musl

# 2. Copiar binario al servidor de producción
scp target/x86_64-unknown-linux-musl/release/bi18nd ops@servidor-prod:/tmp/bi18nd.new
scp target/x86_64-unknown-linux-musl/release/bi18nctl ops@servidor-prod:/tmp/bi18nctl.new

# 3. En el servidor de producción:
sudo cp /tmp/bi18nd.new /usr/local/bin/bi18nd
sudo cp /tmp/bi18nctl.new /usr/local/bin/bi18nctl

# 4. Reiniciar el daemon — el socket NO se interrumpe (socket activation)
sudo systemctl restart bi18nd

# 5. Verificar que el daemon está activo y responde
systemctl is-active bi18nd        # → active
bi18nctl estado                   # → {"status":"ok",...}

# 6. Verificar health completo
bi18nctl health check
```

### 5.3 Graceful shutdown — cómo funciona internamente

Cuando systemd envía `SIGTERM` al proceso:
1. La señal es capturada por `signal::manejar_sigterm()` en `src/domain/signal.rs`
2. Se activa el `watch::Sender<bool>` — todos los servidores (Unix, WebSocket, gRPC) dejan de aceptar nuevas conexiones
3. Se espera hasta `drain_timeout_secs` (configurable en `bi18n.toml`) a que las solicitudes activas terminen
4. El proceso finaliza con código 0

```toml
# /etc/bos/bi18n.toml
[servidor]
drain_timeout_secs = 30    # tiempo máximo de drenado antes de forzar salida
```

### 5.4 Recarga de configuración con SIGHUP (sin reiniciar)

```bash
# Recargar country-rules y traducciones FTL sin reiniciar el daemon
sudo systemctl reload bi18nd
# internamente envía SIGHUP → recargar() → ArcSwap atómico

# O directamente:
sudo kill -HUP $(pidof bi18nd)
```

El `FluentLoader.recargar()` usa `ArcSwap::store()` — swap atómico que no bloquea lectores en vuelo.

### 5.5 Rollback de emergencia

```bash
# Restaurar el binario anterior
sudo cp /usr/local/bin/bi18nd.prev /usr/local/bin/bi18nd
sudo systemctl restart bi18nd
bi18nctl estado   # verificar
```

**Convención:** el script de deploy debe guardar el binario anterior como `.prev` antes de sobreescribir.

## §6 CI/CD — pipeline mínimo exigible

```yaml
# .github/workflows/bi18n.yml (esquema mínimo)
steps:
  - name: Auditoría de seguridad
    run: cargo audit

  - name: Compilación reproducible
    run: cargo build --locked --release

  - name: Verificación estática
    run: cargo clippy --locked -- -D warnings

  - name: Tests de unidad
    run: cargo test --locked -- --test-threads=1

  - name: Verificar que el dispatcher cubre todos los métodos CLI
    run: |
      # Extraer métodos que genera el CLI
      grep -rh '"bi18n\.' src/cli/ | grep -oE '"bi18n\.[a-z0-9_.]+' | tr -d '"' | sort -u > /tmp/cli.txt
      # Extraer métodos registrados en el dispatcher
      grep -oE '"bi18n\.[a-z0-9_.]+[a-z0-9]' src/server/dispatcher.rs | tr -d '"' | sort -u > /tmp/disp.txt
      # La intersección A-B debe ser vacía (todo CLI debe estar en dispatcher)
      diff_out=$(comm -23 /tmp/cli.txt /tmp/disp.txt)
      if [ -n "$diff_out" ]; then echo "ERROR: métodos CLI sin registro en dispatcher:"; echo "$diff_out"; exit 1; fi
```

## §7 Monitoreo en producción

### 7.1 Watchdog systemd

El daemon bi18nd está configurado con `WatchdogSec=30` en su unit. Cada 15s (WatchdogSec/2) envía `sd_notify WATCHDOG=1`. Si el daemon se bloquea, systemd lo reinicia automáticamente.

```bash
# Verificar que el watchdog está activo
systemctl show bi18nd --property WatchdogSec
# → WatchdogSec=30s

# Ver si el daemon fue reiniciado por el watchdog
journalctl -u bi18nd -n 50 | grep -i "watchdog\|restart"
```

### 7.2 Métricas de salud disponibles

```bash
# Estado básico
bi18nctl estado

# Número de solicitudes activas
# (retornado en bi18n.health.check → active_requests)
bi18nctl health check

# Logs en tiempo real
journalctl -u bi18nd -f

# Errores de las últimas 24h
journalctl -u bi18nd --since "24h ago" -p err
```

### 7.3 Alertas recomendadas

| Condición | Umbral | Acción |
|---|---|---|
| `active_requests` sostenido > 100 | > 5 min | Investigar clientes sin timeout |
| `bi18n.health.check` falla | 3 intentos seguidos | Alerta + restart automático |
| `cargo audit` retorna HIGH/CRITICAL | Inmediato | Actualizar dependencia afectada |
| Tiempo de respuesta > 100ms | P99 | Revisar logs; posible contención de ArcSwap |

## §8 Checklist de revisión de código (code review)

Antes de mergear cualquier PR que modifique código de bi18n:

- [ ] `cargo check --locked` — 0 errores
- [ ] `cargo clippy --locked -- -D warnings` — 0 warnings
- [ ] `cargo audit` — 0 vulnerabilidades nuevas
- [ ] Módulo ≤ 800 líneas; función ≤ 50 líneas (DOC-SBOS-001 N3)
- [ ] Todo código documentado en español (propósito, params, retorno)
- [ ] Cero `unwrap()` en producción — usar `Result<T, Bi18nError>`
- [ ] Cero `clone()` innecesario
- [ ] Si se añadió método RPC: registrado en dispatcher + CLI + A.11/A.12
- [ ] Si se cambió nombre/parámetro de método: BREAKING CHANGE en commit
- [ ] `Cargo.lock` incluido en el commit si hay cambio en dependencias
- [ ] Prueba nueva o actualizada para el cambio (A.11 y/o A.12)
- [ ] REGISTRO-ESTADO-DOS.md actualizado si cambió el total de métodos

grep -rh '"bi18n\.' src/cli/ | grep -oE '"bi18n\.[a-z0-9_.]+' | tr -d '"' | sort -u \
