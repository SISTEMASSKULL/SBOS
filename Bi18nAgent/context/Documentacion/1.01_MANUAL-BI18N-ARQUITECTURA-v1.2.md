## 1. Audiencia, propósito y alcance

Este manual documenta la arquitectura del **orquestador de internacionalización (bi18n)** de SBOS:
un daemon Rust que expone una API unificada de i18n para todo el ecosistema, delegando en las
mejores librerías del ecosistema Rust — sin reimplementar nada.

**Audiencia:** desarrolladores de cualquier componente SBOS que defina atributos (bAuth, bpay,
btax, bcms, bhnexus, etc.), arquitectos SBOS, administradores de plataforma.

**Aclaración de alcance:** bi18n es un servicio **horizontal**. bAuth es uno de varios
consumidores — no el dueño del servicio ni el único invocador. Cualquier componente que
defina atributos con metadatos `mask`/`display_format`/`pattern` puede invocar bi18n de la
misma forma. bi18n en sí mismo **nunca** participa en autenticación ni autorización — su
integración con bAuth (descrita abajo) es exactamente eso: una integración con un consumidor,
del mismo tipo que tendría con cualquier otro daemon SBOS.

**bi18n es el servicio que el Motor de Identidad de bAuth invoca vía `obligation.service: bi18n`**
para validar, formatear y enmascarar atributos de identidad según reglas regionales — este es
el caso de uso mejor documentado hasta ahora, pero no es exclusivo.
Sin bi18n, los metadatos `mask`, `display_format` y `pattern` del [Manual de Atributos v2.1.0](../../BauthAgent/context/Documentacion/1.07_MANUAL-ATRIBUTOS-v2.0.md)
son texto inerte — no producen ningún efecto real.
La integración con el [Motor de Identidad](../../BauthAgent/context/Documentacion/2.15_MANUAL-MOTOR-IDENTIDAD-v1.0.md)
está documentada en su §4.

## 2. Qué es y qué no es bi18n

### 2.1 Qué ES

Un **orquestador de librerías existentes**, no una librería propia. Su trabajo:

```
Cliente (bAuth, CLI, dashboard)
  │  JSON-RPC 2.0 → /run/bos/bi18n.sock
  ▼
bi18nd
  │
  ├── "formatear fecha en es-BO"          → icu_datetime (CLDR)
  ├── "validar teléfono +59171234567"     → phonenumber (libphonenumber)
  ├── "convertir UTC a America/La_Paz"    → jiff (IANA tzdata)
  ├── "validar CI Bolivia 7654321-LP"     → regex (contra country-rules/bo.toml)
  ├── "enmascarar NIT ****8901234"        → mask (función pura)
  └── "traducir enum M→Masculino"          → TOML (enum_display por tenant)
```

### 2.2 Lo que bi18n NO hace

- **No almacena** catálogos de países, monedas ni lenguajes — las librerías (ICU4X, jiff, phonenumber) y bglobal ya los proveen
- **No reimplementa** formato de fechas, números ni validación telefónica — delega en ICU4X, jiff y phonenumber
- **No persiste** configuraciones de tenant — esa responsabilidad es de bAuth en `idn_tenant`
- **No requiere PostgreSQL para operar** — es stateless. Las reglas de país son archivos TOML en disco

## 3. Modelo de fuentes de datos

Cada necesidad de i18n se resuelve desde UNA sola fuente. El orquestador unifica el acceso.

| Necesidad | Fuente primaria | Tipo | ¿Por tenant? |
|---|---|---|---|
| Locale BCP 47 (validar "es-BO") | **`icu_locale_core`** (crate) | Librería compilada | Sí — el tenant define su locale |
| Formato fecha "15 de julio de 2026" | **`icu_datetime`** (crate) | Librería — CLDR | Sí — la presentación depende del locale del tenant |
| Formato número "1.500,50" | **`icu_decimal`** (crate) | Librería — CLDR | Sí — separadores por locale |
| Zona horaria "America/La_Paz" → UTC-4 | **`jiff`** (crate) | Librería — IANA tzdata | Sí — cada tenant tiene su timezone |
| Teléfono "+59171234567" válido | **`phonenumber`** (crate) | Librería — libphonenumber | No — patrones telefónicos son globales |
| País "BO" → nombre, moneda, idiomas | **`bglobal.global_country`** (BD) | Referencia SBOS | No — catálogo global compartido |
| Idioma "es-BO" → dirección LTR | **`bglobal.global_language`** (BD) | Referencia SBOS | No — catálogo global compartido |
| Moneda "BOB" → símbolo "Bs.", decimales | **`bglobal.global_currency`** (BD) | Referencia SBOS | Sí — cada tenant define su moneda |
| **CI Bolivia** → regex `^\d{7,8}-[A-Z]{2}$` | **`country-rules/bo.toml`** (archivo) | Regla nacional | Sí — cada tenant tiene su país |
| **NIT Bolivia** → regex `^\d{7,14}$` | **`country-rules/bo.toml`** (archivo) | Regla nacional | Sí — cada tenant tiene su país |
| **Dirección postal Bolivia** → campos | **`country-rules/bo.toml`** (archivo) | Regla nacional | Sí — cada país define la suya |
| **Placa Bolivia** → regex `^\d{4}-[A-Z]{3}$` | **`country-rules/bo.toml`** (archivo) | Regla nacional | Sí — cada país define la suya |
| **Sinónimos** "farol"=["foco","optica"] | **`country-rules/bo.toml`** (archivo) | Regla nacional | Sí — regionalismos |
| **Enum** gender:M→"Masculino" | **`country-rules/bo.toml`** (archivo) | Regla nacional | Sí — traducción de enums de negocio |

**Regla de decisión:** si una librería (ICU4X, jiff, phonenumber) o el catálogo `bglobal` ya tiene
el dato, se usa esa fuente. Solo lo que no existe en ningún estándar internacional — patrones de
documentos nacionales, formato postal, placas, sinónimos, enums de negocio — se mantiene en
archivos TOML declarativos por país, resueltos por tenant.

**Principio de handlers compartidos:** la lógica de negocio vive en `server/handlers/*.rs`.
Tanto el dispatcher JSON-RPC como el servidor gRPC llaman al mismo handler. El transporte
(Unix socket vs gRPC) es transparente para la lógica de dominio. Esto garantiza la
paridad de capacidades exigida por C11 sin duplicar código.

## 5. Resolución multi-tenant

**Principio:** cada tenant tiene su propia configuración regional. bi18n resuelve el `RegionalConfig`
al inicio de cada operación. **Nunca del sistema operativo del servidor.**

### 5.1 Jerarquía de resolución

```
1. Usuario individual  (preferencia personal de locale/zona)
        ↓ si no está definida
2. Sucursal / Branch   (si opera en otro país)
        ↓ si no está definida
3. Tenant / Empresa    (configuración regional principal)
        ↓ si no está definida
4. Default del país    (del country-rules/{iso}.toml)
```

### 5.2 Flujo tenant → reglas de país

```
bAuth: bi18n.attr.pipeline(tenant_id="acme-sa", key="CI", value="7654321-LP")
  │
  ├── 1. Resolver tenant "acme-sa" → country="BO", locale="es-BO", tz="America/La_Paz"
  │      Fuente: bAuth envía estos datos en el request (ya los resolvió de idn_tenant)
  │
  ├── 2. Cargar reglas del país "BO" → country-rules/bo.toml (cacheado en memoria)
  │
  ├── 3. Validar CI contra [national_id.ci].pattern → regex
  │
  └── 4. Devolver AttrResult con valid, masked, display
```

### 5.3 Implementación

El trait `RegionalConfigResolver` define el contrato. La implementación inicial es estática
(HashMap cargado de `bi18n.toml`). En producción, bAuth envía la configuración regional
como parte de cada request JSON-RPC — bi18n no necesita consultar la BD.

```rust
#[async_trait]
pub trait RegionalConfigResolver: Send + Sync {
    async fn resolve(
        &self,
        tenant_id: &str,
        branch_id: Option<&str>,
        user_id: Option<&str>,
    ) -> Result<RegionalConfig, Bi18nError>;
}
```

## 6. Cobertura de librerías — 100%

El anexo [A.01 v2.0.0 — Cobertura de Librerías](anexos/A.01_ANEXO-BI18N-COBERTURA-LIBRERIAS-v1.0.md)
documenta 23 librerías verificadas organizadas en 9 categorías. **No hay gaps de librería.**

| Categoría | Librerías |
|---|---|
| Traducción | fluent, rust-i18n, shakehand |
| Fechas y horas | jiff, icu_datetime, chrono |
| Formatos regionales | icu_locale_core, icu_datetime, icu_decimal, prism3-core |
| Validación | valida, validy, validator, scrutiny, phonenumber, prism3-core, regex |
| Enmascaramiento | mask-pii, veil, universal_mask |
| Máscaras de entrada | rat-input, clipass_rs |
| Serialización | serde, serde_with, toml |
| Catálogo referencia | bglobal (4 tablas) |

y enums de negocio son datos que cada país define. bi18n los carga desde TOML declarativo
— mismo mecanismo para Bolivia, Argentina, Brasil o cualquier otro.

## 7. Componentes desarrollados en bi18n

Lo que las librerías NO cubren y bi18n implementa.

### 7.1 format_map — los 18 códigos display_format

El [Manual de Atributos v2.1.0 §5](../../BauthAgent/context/Documentacion/1.07_MANUAL-ATRIBUTOS-v2.0.md) define 18 códigos de presentación. bi18n mapea cada uno a su mecanismo concreto:

| Código | ICU4X / Librería | Máscara entrada | Validación | Enmascarado |
|---|---|---|---|---|
| `E164` | phonenumber | `+999 99 9999999` | phonenumber | No |
| `EMAIL_RFC5321` | plain | `email` | validator | No |
| `TAX_BO` | plain | `9999-999999-999-99` | regex TOML | **Sí** |
| `TAX_AR` | plain | `99-99999999-9` | regex TOML | **Sí** |
| `TAX_BR_CPF` | plain | `999.999.999-99` | regex TOML | **Sí** |
| `TAX_BR_CNPJ` | plain | `99.999.999/9999-99` | regex TOML | **Sí** |
| `ID_BO` | plain | `9999999-AA` | regex TOML | **Sí** |
| `PASSPORT_ICAO` | plain | `AA9999999` | regex TOML | **Sí** |
| `IPV4` | plain | `999.999.999.999` | regex | No |
| `ADDR_INTL` | TOML [postal] | varía por país | TOML | No |
| `LOCALE_BCP47` | icu_locale_core | `aa-AA` | BCP 47 | No |
| `TIMEZONE_IANA` | jiff | `text` | IANA | No |
| `DATE_ISO` | icu_datetime | `99/99/9999` * | iso 8601 | No |
| `MONEY` | icu_decimal | `currency` * | numérico | No |
| `COORDENADAS_DD` | plain | `-99.999999, -999.999999` | rango | No |
| `URL` | plain | `url` | validator | No |
| `UUID` | plain | `hex-36` | formato | No |
| `NULL` | plain | `text` | — | No |

> \* Las máscaras de fecha y moneda se **derivan** del patrón CLDR del locale (A.01 §4.4). `99/99/9999` es para `es-BO` (dd/MM/yyyy); `en-US` produce `99/99/9999` también (MM/dd/yyyy — misma máscara, distinto orden semántico).

### 7.2 Mecanismo de máscaras de entrada

**Problema:** el frontend (dashboard Flutter, web) necesita máscaras de formulario para cada campo según el país del tenant. No debe mantener una tabla propia — las recibe de bi18n.

**Mecanismo (diseño canónico §7):**
1. ICU4X expone el **patrón CLDR** para el locale: `dd/MM/yyyy` (es-BO)
2. bi18n **traduce** carácter por carácter: `d`→`9`, `M`→`9`, `y`→`9`, `/`→`/`
3. Resultado: `99/99/9999` — máscara de entrada lista para el frontend

```
CLDR (ICU4X)              →  Máscara (bi18n)       Uso
dd/MM/yyyy (es-BO)        →  99/99/9999             Frontend: campo fecha
MM/dd/yyyy (en-US)        →  99/99/9999             Frontend: campo fecha
yyyy-MM-dd (ISO)          →  9999-99-99             Frontend: campo fecha
#,##0.00 (es-BO)          →  #.###,##               Frontend: campo número
#,##0.00 (en-US)          →  #,###.##               Frontend: campo número
+CC XX XXX XXXX (E.164)   →  +999 99 9999999        Frontend: campo teléfono
```

### 7.3 Pipeline AttrBuilder

Cada atributo de identidad sigue el mismo pipeline. El orden lo garantiza el builder pattern en tiempo de compilación:

```
raw_value → validate? → transform* → format → mask
```

| Etapa | Qué hace | Ejemplo CI Bolivia |
|---|---|---|
| 1. raw | Valor original | `"7654321-lp"` |
| 2. validate | Regex contra TOML del país | `ID_BO` → `^\d{7,8}(-[A-Z]{2})?$` → ✅ |
| 3. transform | 11 operaciones en secuencia | uppercase → `"7654321-LP"` · striphyphen → `"7654321 LP"` |
| 4. format | Presentación según display_format | `ID_BO` → `"7654321 LP"` |
| 5. mask | Enmascaramiento PII | `partial(4)` → `"****321-LP"` |

**11 transformaciones:** Uppercase · Lowercase · TitleCase · Trim · StripHyphen · StripSpaces · StripAccents · DigitsOnly · AlphaOnly · PadLeft · PadRight

**6 estrategias de máscara (representación interna, `enum MaskStrategy` en Rust):** None · Full · Partial{from_end} · PartialPrefix{from_start} · PartialBoth{prefix,suffix} · FromCountryRule

**Convención de wire format (JSON-RPC / CLI):** al serializarse hacia clientes remotos o el CLI
`i18nctl`, cada variante se representa como una cadena estilo función, no como la notación de
struct de Rust — así aparece en el ejemplo real de §8.2 y así debe usarse de forma consistente
en toda integración externa:

| Variante Rust | Wire format (string) |
|---|---|
| `None` | `"none"` |
| `Full` | `"full"` |
| `Partial{from_end: 4}` | `"partial(4)"` |
| `PartialPrefix{from_start: 3}` | `"partial_prefix(3)"` |
| `PartialBoth{prefix: 2, suffix: 2}` | `"partial_both(2,2)"` |
| `FromCountryRule` | `"from_country_rule"` |

Cualquier documento o cliente que exponga esta convención (incluido A.02, adapters de
plataforma, `i18nctl`) debe usar esta tabla como referencia única — evita que cada
integración invente su propia sintaxis de string para la misma estrategia.

### 7.4 DateGranularity

No todos los atributos de fecha son datetime completos (diseño canónico §7.2):

| Granularidad | Ejemplo | ICU4X usa |
|---|---|---|
| `DateTime` | `created_at` — "16 de julio de 2026, 05:00 AM" | DateTimeFormatter |
| `Date` | `birth_date` — "16 de julio de 2026" | DateFormatter |
| `YearMonth` | `credit_card_expiry` — "julio 2026" | YearMonthFormatter |
| `Year` | `anio` (vehículo) — "2026" | solo año |
| `Time` | `horario` — "05:00 AM" | TimeFormatter |

### 7.5 Integración con AtomLang

El Motor de Identidad de bAuth ejecuta los verbos. bi18n es invocado vía `obligation.service`:

```yaml
regla "nit_validar"
  target:
    resource: idn_identidad_atributo.tributario
    type: NIT
    verbo: validate
  condition:
    property_id: idn_identidad_atributo.value_text
    operator: REGEX
    value: "@bauth_config_param.regex_nit_bo"
  effect:
    decision: Permit
    obligation:
      service: bi18n                            # ← el orquestador
      method: validate_national_id
      args: { country: "bo", kind: "nit" }
```

Esto significa que las reglas de validación se escriben en AtomLang (como cualquier política bAuth), pero la ejecución real la hace bi18n. bAuth no necesita saber validar un NIT boliviano — solo necesita saber que bi18n lo resuelve.

## 8. Interface Triple (C11) — JSON-RPC + gRPC

bi18n cumple la norma C11 (ORQUESTA-048) desde el diseño inicial: expone sus capacidades
por **tres vías con paridad de capacidades**. No existe método disponible en una vía que
no esté disponible en las demás.

### 8.1 Las tres vías

| Vía | Socket | Protocolo | Puerto TCP |
|---|---|---|---|
| WebSocket RPC + JSON-RPC 2.0 | `/run/bos/bi18n.sock` | JSON-RPC 2.0 newline-delimited | **Ninguno** |
| gRPC | `/run/bos/bi18n-grpc.sock` | gRPC sobre Unix domain socket | **Ninguno** |
| CLI | `i18nctl` (binario local) | Llamada directa al core | N/A |

**Sin TCP en ninguna vía** (daemons en el mismo VPS) — SBOS-050 P9 se cumple íntegramente.
Para **frontends remotos** (web, Flutter, iOS, Android) se añade un cuarto canal: WebSocket sobre
TLS expuesto vía Kong, que hace *transcoding* al Unix socket interno. El daemon no necesita
saber que Kong existe — solo expone sus interfaces habituales. Ver §8.3.

Especificación gRPC completa: [A.03 — Interfaz gRPC](anexos/A.03_ANEXO-BI18N-GRPC-INTERFACE-v1.0.md)

### 8.2 Métodos MVP y su equivalente gRPC

| Método JSON-RPC | Método gRPC | Librería / Fuente | Fase |
|---|---|---|---|

### 8.3 Ligadura a frontends remotos (WebSocket)

La técnica de ligadura de bi18n a componentes de UI es *Metadata-driven attribute binding con
adapters de renderizado por plataforma* — una variante minimal de **SDUI**, aplicada a nivel de
campo individual (no de pantalla completa). Patrón: el servidor describe reglas, el cliente las
interpreta vía un **Adapter** específico por plataforma.

**Contrato (dos llamadas, no más):**

```
// Al abrir el formulario (una sola vez, batch)
→ bi18n.attr.config_batch { fields: [...], locale, country, tenant_id }
← { CI: { mask_pattern, display_format, validator_profile }, ... }

// Al perder foco o al submit (una por campo)
→ bi18n.attr.pipeline { field_id, value, validator_profile, locale }
← { valid, display, masked, validation_errors: [...] }
```

**Reglas de integración:**
- Un cliente **WebSocket singleton** por sesión de app (no uno por campo).
- La máscara se aplica **local y síncrona** (sin red); solo la validación necesita debounce (250–300ms).
- La máquina de estados por campo (`idle → validating → valid / warning / error`) evita condiciones de carrera.
- **Siempre revalidar todo en `on_submit`** — nunca confiar en la validación mostrada previamente.
- Si se corta la conexión: máscara cacheada sigue activa, validación pasa a `pending`, nunca a `valid`.

Especificación completa, técnicas servidor/cliente y ejemplos en 4 plataformas: [A.04](anexos/A.04_ANEXO-BI18N-TECNICA-LIGADURA-FRONTEND-v2.1.md)

## 9. Roadmap de construcción

Fases de implementación según el diseño canónico (§13), ordenadas por dependencia.
Cada fase desbloquea a la siguiente.

| Fase | Alcance | Librerías nuevas | Desbloquea |
|---|---|---|---|
| **Fase 1 — Núcleo** | Locale (icu_locale_core) · formato fecha (jiff) · número/moneda (icu_decimal) · format_map (18 códigos) · country-rules/bo.toml · máscaras PII | icu_*, jiff, regex | Validación CI/NIT Bolivia |
| **Fase 2 — Mensajes** | fluent · enum_display · DateGranularity | fluent | Traducción de UI + enums |
| **Fase 3 — Multi-tenant** | RegionalConfigResolver contra BD (bglobal) · SET timezone PG · inyección TZ/LC_* por tenant | — (usa bglobal) | Tenant Bolivia ≠ Tenant Alemania |
| **Fase 4 — Validación** | phonenumber real · validator (email) · country-rules Argentina+Brasil | phonenumber, validator | Validación telefónica + email |
| **Fase 5 — CLI + Daemon** | i18nctl (clap) · bi18nd (systemd) · **Interface Triple (C11)**: JSON-RPC + WebSocket + **gRPC** sobre Unix socket · proto compilado con tonic-build | clap, tonic, prost | Operación del daemon — todas las vías activas |
| **Fase 6 — Collation** | icu_collator (UTS #10) · bidi (UAX #9) · calendarios no gregorianos | icu_* | Ordenamiento + RTL + calendarios |
| **Fase 7 — API builder** | AttrBuilder · 11 transformaciones · pipeline validate→format→mask | — (código propio) | bAuth invoca `bi18n.attr.pipeline` |
| **Fase 8 — Empaquetado** | crates.io · features opcionales · MUSL release | — | Distribución |

**MVP = Fase 1 + Fase 5 + Fase 7:** daemon funcionando con formato ICU4X/jiff, validación de
documentos bolivianos vía TOML, y pipeline de atributos completo. bAuth puede invocar
`bi18n.attr.pipeline` para validar y enmascarar CI/NIT.

### 10.2 Panorama de la industria

| Plataforma | Cómo resuelve i18n |
|---|---|
| **ICU4X** (Unicode Consortium) | Librería modular `no_std`. CLDR 1000+ locales. Sucesor de ICU4C/ICU4J. |
| **Globalize.js** (JS) | ICU CLDR para JS. Mismo principio: orquestar CLDR + IANA tzdata. |
| **Java java.util.Locale + ICU4J** | Mismo modelo: locale BCP 47 + ResourceBundle + CLDR. |
| **Salesforce / SAP** | Multi-tenant con configuración regional por org/tenant. Jerarquía: user → org → default. |

### 10.3 Comparativa — qué aporta cada capa

| Capacidad | Librerías solas | bi18n (orquestador) | Mecanismo |
|---|---|---|---|
| Formato fecha/hora localizado | icu_datetime + jiff | Unifica en un solo método | Orquesta `icu_datetime` + `jiff` |
| Formato numérico | icu_decimal | Unifica en un solo método | Orquesta `icu_decimal` |
| Cálculo temporal zone-aware | jiff | Expone vía JSON-RPC | Orquesta `jiff` |
| Validación telefónica E.164 | phonenumber | Expone vía JSON-RPC | Orquesta `phonenumber` |
| Pipeline de atributos (validate→format→mask) | disperso en múltiples crates | Un solo método `attr.pipeline` | AttrBuilder + valida |
| Enmascaramiento PII | mask-pii, veil, universal_mask | Unifica estrategias + TOML | Orquesta 3 crates |
| Documentos nacionales (CI, NIT) | regex | Patrones por país vía TOML | CountryRulesLoader + regex |
| Interface Dual ADR-020 | — | Unix socket + JSON-RPC 2.0 | Daemon systemd |
| Traducción con plurales/género | fluent, rust-i18n | Expone vía JSON-RPC | Orquesta `fluent` |

**bi18n no reemplaza las librerías — las une.** Cada librería resuelve su dominio.
bi18n aporta la API unificada, el pipeline de atributos, los datos por país (TOML),
y la infraestructura de daemon (Unix socket + JSON-RPC).

### 10.5 Gestión de traducciones — hot-reload sin redeploy

Los textos de UI y enums de negocio (`translations/*.ftl`/`.toml`) tienen dos problemas de
fricción: edición manual por desarrolladores y redeploy para que los cambios sean visibles.
bi18n los resuelve con dos piezas independientes:

**Plataforma de edición:** [Weblate](https://weblate.org) self-hosteado (GPLv3+, sin límite de
proyectos/usuarios). El equipo de negocio edita claves en la web UI; Weblate commitea
directamente al repo. Alternativa evaluada: Tolgee (edición *in-context* sobre la app en vivo
— tiene límite en el tier free del self-hosted; evaluar para pantallas donde sea prioritario).

**Hot-reload en bi18nd:** `bi18n.admin.reload_translations` (RPC interno, no expuesto en Kong).
Construye la nueva estructura `Translations` **completa** en memoria, y solo al terminar hace
un swap atómico via `arc-swap` crate (143M+ descargas, patrón estándar en Rust). Los requests
en vuelo siguen viendo la versión anterior completa; nunca hay estado a medio reconstruir.
File watcher con `notify` crate como red de seguridad (activa también cuando alguien edita
directamente en el VPS).

**Gobernanza diferenciada** (reconcilia con A.05):
- `country-rules/*.toml` — riesgo alto (regex fiscal/legal) → aprobación `CODEOWNERS` obligatoria
- `translations/*.ftl` — riesgo bajo (texto de UI) → solo gate CI de paridad de claves, sin aprobación humana

**Si bi18nd corre en 2+ réplicas (HA):** el RPC de recarga debe llamarse contra cada instancia
individualmente, no a través de la ruta balanceada de Kong — o las réplicas quedan desincronizadas.

Especificación completa: [A.06](anexos/A.06_ANEXO-BI18N-DAEMON-TRADUCCIONES-v1.1.md)
