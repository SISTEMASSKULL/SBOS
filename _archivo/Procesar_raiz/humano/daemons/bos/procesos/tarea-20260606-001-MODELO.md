## 🔍 Análisis — Sequential Thinking

### Pensamiento 1 — Entender el problema

El archivo `install_ui.go` (~3901 líneas) tiene 15 pantallas. Solo P5 implementa viewport.Model correctamente. Las otras 14 renderizan su cuerpo como strings sueltos: concatenan `\n` manuales, centran con `strings.Repeat("\n", pad)` en algunos casos, y en la mayoría simplemente asumen una altura fija de terminal.

Esto causa dos problemas concretos:
1. **Terminal alto (>30 líneas):** el contenido queda pegado arriba con espacio vacío debajo
2. **Terminal pequeño (<20 líneas):** el contenido desborda sin scrollbar, haciendo la TUI inusable

El documento `SBOS-TUI-decisiones.md` §0 establece la arquitectura correcta:
- Zona TOP fija (topbar + stepper? + title + divider)
- Zona BODY dinámica (`viewport.Model` que ocupa `height - topH - botH`)
- Zona BOTTOM fija (footer)

La regla es explícita: **"El body SIEMPRE usa viewport.Model — SIN EXCEPCIONES"**.

La solución no es `vCenter()` con strings (primer intento, descartado por el documento). La solución es agregar un `bodyVP viewport.Model` global al struct `model` y refactorizar `View()` para usarlo.

### Pensamiento 3 — Diseño de la solución

**Enfoque elegido:** Un solo `viewport.Model bodyVP` en el model raíz. `SetContent()` se llama en cada evento que modifica el body.

**Estructura de View() después del cambio:**
```go
func (m model) View() string {
    if m.width == 0 { return "Iniciando SBOS..." }

    // Splash: pantalla completa sin top/bottom
    if m.screen == ScreenWelcome  { return m.viewSplashWelcome() }
    if m.screen == ScreenGoodbye  { return m.viewSplashGoodbye() }

    // TOP fijo
    top := lipgloss.JoinVertical(lipgloss.Left,
        m.viewTopBar(),
        m.viewStepper(),          // "" si no aplica
        m.viewScreenTitle(),
        strings.Repeat("─", m.width),
    )

    // BOTTOM fijo
    bottom := lipgloss.JoinVertical(lipgloss.Left,
        m.viewErr(),              // "" si no hay error
        m.viewFooter(),
    )

    // BODY: viewport dinámico
    var body string
    if m.screen == ScreenInstalling ||
       m.screen == ScreenInstallLog ||
       m.screen == ScreenInstallErr {
        body = m.viewInstalling()  // P5 ya tiene sus propios viewports
    } else {
        body = m.bodyVP.View()     // resto: viewport global
    }

    return lipgloss.JoinVertical(lipgloss.Left, top, body, bottom)
}
```

**Cálculo de bodyHeight:**
```go
func (m *model) recalcBodyHeight() {
    topH := 3        // topbar(1) + screen-title(1) + divider(1)
    if m.showStepper { topH++ }  // stepper solo en P1–P5
    botH := 1        // footer
    if m.errMsg != "" { botH++ } // viewErr visible
    m.bodyHeight = m.height - topH - botH
}
```

**Alternativas descartadas:**

| Alternativa | Por qué se descartó |
|-------------|---------------------|
| `vCenter()` con `strings.Repeat("\n", pad)` | SBOS-TUI-decisiones.md §0 lo prohíbe explícitamente: "Nunca renderices body como string suelto" |
| Un viewport por pantalla (14 viewports) | Innecesario. Un viewport global alcanza porque `SetContent()` cambia el contenido |
| Refactorizar a sub-modelos por pantalla | Fuera de alcance para esta sesión. El cambio es mecánico, no arquitectónico |
| Usar `lipgloss.Height()` dinámico | El documento lo prohíbe: "Usa contadores enteros: topH, botH, bodyHeight = height - topH - botH" |

**Por qué SetContent() en cada tick:** El contenido del body cambia con el spinner animado (`m.spinner.View()`), elapsed time, y logs en vivo. Sin `SetContent()` en `tickMsg`, el viewport mostraría la primera versión congelada.

### Pensamiento 4 — Riesgos y mitigaciones

| Riesgo | Prob | Impacto | Mitigación |
|--------|------|---------|------------|
| **P5 conflicto con bodyVP** — doble render si bodyVP intenta mostrar P5 | Alta | Alto | Guard explícito en `View()`: P5/P5B/P5C usan `viewInstalling()` directamente. En `tickMsg`/`wsEventMsg`: skip `SetContent()` si screen es P5/P5B/P5C |
| **textinputs en P2/P3 pierden foco** dentro del viewport | Baja | Medio | Los textinputs se manejan en `Update()`, independiente de `View()`. El viewport solo muestra el string renderizado — el foco no se ve afectado |
| **Regresión visual en terminal 80×24** — cambio percibido por el usuario | Media | Medio | Probar cada pantalla en 80×24 antes de dar por completada. El cuerpo centrado con viewport debe verse idéntico al layout actual en terminal estándar |
| **bodyContent() retorna ""** en una pantalla no mapeada | Muy baja | Bajo | Viewport muestra vacío sin crash. El `default: return ""` en el switch de bodyContent ya existe |
| **Compilación rota** por cambio de firma en bodyContent | Baja | Alto | Verificar `go build ./cmd/bosctl/` después de cada fase |

**Riesgo principal:** Conflicto P5/bodyVP. **Mitigación:** P5 tiene su propio path en `View()` y los handlers de `Update()` verifican `m.screen` antes de tocar `bodyVP`.
