# 2.03 — Interface Dual de bNexus (ADR-020)
## `/run/bos/bhnexus.sock` + TCP 9444 — dos caminos, un daemon

**Versión:** 1.0.0  
**Fecha:** 2026-08-04  
**Estándar:** ADR-020 Interface Dual  
**Carta rectora:** `0.00_MANUAL-DIRECTRICES-NEXUS.md`  

---

## 1. El contrato ADR-020 aplicado a bNexus

ADR-020 (Interface Dual) define que **todo daemon SBOS debe exponer exactamente dos interfaces sobre el mismo Unix socket**:

1. **WebSocket RPC** — para herramientas humanas (CLI, dashboards)
2. **JSON-RPC 2.0** — para comunicación entre daemons

bhnexus cumple este contrato exactamente igual que bAuth. La distinción de bNexus es que también expone TCP 9444 para recibir conexiones de agentes banexus remotos (la Puerta 1). Eso no viola ADR-020 — el TCP 9444 es el canal de borde, no el canal inter-daemon.

---

## 2. Las tres interfaces de bhnexus

```
bhnexus expone:

  [A] /run/bos/bhnexus.sock   — Interface Dual (ADR-020)
       ├── WebSocket RPC       — operadores humanos, bOS CLI
       └── JSON-RPC 2.0        — bOS, bAuth, biedata (daemons hermanos)

  [B] TCP 9444                 — Puerta 1 (WebSocket mTLS)
       └── banexus agents      — agentes de borde remotos y locales

  [C] /run/bos/bauth-nexus.sock — Canal Privilegiado bidireccional
       └── bAuth (exclusivo)   — emergencias, revocaciones, sincronización
```

La Interface Dual (A) y el Canal Privilegiado (C) son para el plano de control.  
La Puerta 1 (B) es para el plano de borde.  
**NUNCA HTTP/TCP entre daemons hermanos** — eso viola SBOS-050 P9. Solo `bhnexus.sock`.

---

## 3. Interface A — Unix socket dual

### 3.1 Ruta y permisos

```
Socket: /run/bos/bhnexus.sock
Tipo:   AF_UNIX, SOCK_STREAM
Perms:  0660
Owner:  bos:bos
Grupo:  bosagent

Acceso: procesos en grupo 'bos' o 'bosagent'
```

### 3.2 Negociación de protocolo

El mismo socket acepta dos tipos de clientes. El protocolo se negocia al conectar:

```
Cliente WebSocket (humano/CLI):
  → HTTP/1.1 GET /ws
  → Header: Upgrade: websocket
  → bhnexus responde: 101 Switching Protocols
  → Canal WebSocket establecido

Cliente JSON-RPC (daemon hermano):
  → No envía HTTP Upgrade
  → Envía directamente: Content-Type: application/json\r\n\r\n{json-rpc payload}
  → bhnexus detecta: primer byte no es 'G' de "GET" → modo JSON-RPC
```

### 3.3 Namespace JSON-RPC `bhnexus.*`

Todos los métodos expuestos a daemons hermanos usan el namespace `bhnexus.*`:

| Método | Emisor | Descripción |
|--------|--------|-------------|
| `bhnexus.status` | Cualquier daemon | Estado del broker: nodos conectados, cache size, latencia |
| `bhnexus.node.list` | bOS | Listar nodos banexus activos con su estado |
| `bhnexus.node.kick` | bOS | Desconectar un nodo banexus (forzar reconexión) |
| `bhnexus.node.blacklist` | bOS | Agregar nodo a deny-list (permanente hasta `unblacklist`) |
| `bhnexus.cache.stats` | bOS / biedata | Estadísticas del Auth Cache (hits, misses, entries) |
| `bhnexus.cache.flush` | bOS | Vaciar Auth Cache completamente (emergencia) |
| `bhnexus.cache.invalidate_user` | bAuth | Invalidar cache de un user_id específico |
| `bhnexus.policy.reload` | bAuth | Forzar recarga de políticas desde bAuth |
| `bhnexus.zone.security_up` | bOS / bAuth | Elevar security_level de una o más zonas |
| `bhnexus.zone.security_down` | bOS | Restaurar security_level de zonas elevadas |

### 3.4 WebSocket RPC — comandos del operador

Para uso desde bOS CLI, dashboards o herramientas de auditoría:

| Comando | Descripción |
|---------|-------------|
| `node-list` | Listar todos los nodos banexus: estado, uptime, last_heartbeat |
| `node-info <node_id>` | Detalle de un nodo: forma, zona, certs, cache_hits |
| `node-kick <node_id>` | Desconectar y forzar reconexión de un nodo |
| `auth-cache-show` | Mostrar primeras 100 entradas del Auth Cache |
| `auth-cache-stats` | Estadísticas: size, hit rate, miss rate, evictions |
| `policy-push <user_id>` | Forzar push de política actualizada a todos los nodos del usuario |
| `zone-status` | Mostrar security_level actual de todas las zonas |
| `zone-lock <zona_id> <sl>` | Elevar temporalmente una zona a un security_level |
| `audit-tail` | Stream de los últimos eventos de auditoría en tiempo real |
| `version` | Versión del daemon, uptime, capacidad de carga |

## 4. Interface B — TCP 9444 (Puerta 1)

Esta interfaz no es parte de ADR-020 — es la Puerta 1 específica de bNexus.

```
Puerto: 9444 (SBOS-050 rango 9400-9499)
TLS:    TLS 1.3 obligatorio
Auth:   mTLS bidireccional (SPIFFE/SVID)
Proto:  WebSocket sobre TLS 1.3

CERT bhnexus: spiffe://sbos.skull/daemon/bhnexus (emitido por Vault PKI)
CERT banexus: spiffe://sbos.skull/agent/banexus/<node_id>

Capacidad: 10.000 conexiones concurrentes (conexiones persistentes de larga duración)
Backpressure: sí — si la cola de mensajes supera el límite, bhnexus aplica backpressure
Heartbeat: banexus envía PING cada 30s; bhnexus responde PONG; sin PONG en 60s → timeout
```

Ver `2.01_MANUAL-PUERTA-1-AGENTES.md` para el protocolo completo de la Puerta 1.

## 5. Interface C — Canal Privilegiado `/run/bos/bauth-nexus.sock`

Socket exclusivo entre bhnexus y bAuth. No forma parte de la Interface Dual — es un canal bilateral adicional definido en la arquitectura de bNexus.

```
Socket: /run/bos/bauth-nexus.sock
Perms:  0600 (solo bOS y bhnexus — más restrictivo que bhnexus.sock)
Proto:  newline-delimited JSON
Uso:    eventos de emergencia y sincronización que no toleran la latencia del sub-canal A

bAuth abre la conexión (cliente). bhnexus escucha (servidor).
1 sola conexión persistente — no pool.
```

Ver `2.02_MANUAL-PUERTA-2-BAUTH.md` §2 para el protocolo completo.

## 6. Restricción de firewall (SBOS-050)

```
Puerto 9444:
  Entrada: ACCEPT desde banexus agents (IPs del rango interno + WAN para sucursales)
  Entrada: DROP todo lo demás

Puerto bhnexus.sock (Unix):
  Solo procesos del grupo 'bos' o 'bosagent'
  Firewall: no aplica (Unix socket — solo acceso local)

Regla general SBOS-050 P9:
  NUNCA abrir HTTP/TCP entre daemons SBOS en el mismo host.
  Si bOS necesita hablar con bhnexus → usa /run/bos/bhnexus.sock
  Si bAuth necesita hablar con bhnexus → usa /run/bos/bhnexus.sock (JSON-RPC)
                                          + /run/bos/bauth-nexus.sock (emergencias)
```

---

## 7. Ciclo de vida del socket al arrancar bhnexus

```
1. bhnexus arranca (systemd Type=notify)
2. Crea /run/bos/bhnexus.sock (elimina socket viejo si existe)
3. Abre TCP 9444 con TLS 1.3 y carga los certificados SPIFFE desde Vault
4. Conecta al socket /run/bos/bauth.sock (sub-canal A — pool 100 conexiones)
5. Escucha /run/bos/bauth-nexus.sock para que bAuth lo conecte (sub-canal B)
6. Emite sd_notify("READY=1") → systemd marca el servicio como activo
7. Acepta conexiones en los tres puntos de entrada
```
