## 1. Modelo de seguridad general

bNexus sigue el modelo de defensa en profundidad: cada capa tiene su propio control de seguridad independiente, de modo que la vulneración de una capa no compromete el sistema completo.

```
Capas de defensa en bNexus:

Capa 5 (Identidad)   bAuth — PDP único — ningún actor puede decidir acceso por sí solo
Capa 4 (Tránsito)    mTLS 1.3 en Puerta 1 — cifrado + autenticación mutua
Capa 3 (Proceso)     bhnexus — broker sin estado de decisión — no almacena secretos
Capa 2 (Borde)       banexus — Integrity Monitor — auto-shutdown si binario modificado
Capa 1 (Hardware)    OSDP SC AES-128 — canal cifrado lector↔bhnexus
```

### 1.1 Invariantes de seguridad no negociables

1. **Ninguna decisión de acceso sin bAuth.** bhnexus no tiene lógica de autorización propia.
2. **Cache máximo 30s.** La ventana de riesgo de un SAM-128 comprometido es ≤30s.
3. **Fail-secure siempre.** Si hay duda → DENY. Nunca fail-open en software.
4. **Sin biometría en reposo.** Ni bhnexus ni banexus almacenan templates o imágenes.
5. **ctx_id en toda operación.** Cada evento es trazable end-to-end.

## 2. mTLS — Autenticación mutua TLS 1.3

### 2.1 Puerta 1 (banexus ↔ bhnexus)

La Puerta 1 es el WebSocket mTLS que comunica banexus con bhnexus en el puerto TCP 9444.

**Negociación TLS:**
- Versión mínima: TLS 1.3 (RFC 8446). TLS 1.2 rechazado.
- Cipher suites: `TLS_AES_256_GCM_SHA384`, `TLS_CHACHA20_POLY1305_SHA256`
- Curvas: X25519, P-256
- Verificación: ambas partes presentan certificado → autenticación mutua

**Certificados:**
- CA interna SBOS (Vault PKI, Ed25519): firma todos los certificados de bNexus
- Tiempo de vida del certificado de nodo: 90 días (rotado automáticamente por bOS)
- Certificado de bhnexus: CN=`bhnexus.sbos.skull`, SAN=`spiffe://sbos.skull/daemon/bhnexus`
- Certificado de banexus: CN=`banexus-<node_id>.sbos.skull`, SAN=`spiffe://sbos.skull/agent/banexus/<node_id>`

**Verificación de SPIFFE ID en conexión:**

```
banexus conecta a wss://bhnexus-host:9444/ws

bhnexus verifica:
  1. cert.signature verified by CA ✅
  2. cert.not_after > now() ✅
  3. cert.san contains spiffe://sbos.skull/agent/banexus/* ✅
  4. node_id extraído del SAN → existe en idn_identity_entity ✅
  5. node estado = ACTIVE ✅

Si cualquiera falla → 403 + log + Wazuh NEXUS-003
```

### 2.2 Puerta 2 Sub-canal A (bhnexus ↔ bAuth)

Unix socket `/run/bos/bauth.sock`:
- Propietario: `bauth:bos-group`, permisos `0660`
- Solo procesos en el grupo `bos-group` pueden conectar
- bhnexus no accede como root — usa las capabilities mínimas
- Frame TLV: `[4 bytes uint32 BE: longitud][N bytes JSON UTF-8]`
- Timeout: 1000ms — si bAuth no responde → cache hit o DENY (fail-secure)

### 2.3 Puerta 2 Sub-canal B (bhnexus ↔ bAuth, privilegiado)

Unix socket `/run/bos/bauth-nexus.sock`:
- **bhnexus crea el socket** (owner `bhnexus:bos-group`, permisos `0660`)
- **bAuth se conecta como cliente** a este socket (no al revés)
- Canal bidireccional push — no polling
- bAuth → bhnexus: `emergency_revoke`, `invalidate_cache`, `security_level_up`, `blacklist_node`, `policy_sync`
- bhnexus → bAuth: `device_tamper`, `node_offline`, `auth_spike`, `hardware_failure`, `integrity_breach`

## 3. AES-256-GCM — Policy Cache de banexus

### 3.1 Derivación de clave (HKDF-SHA256)

La clave de cifrado del policy cache de banexus se deriva del material de la clave privada mTLS del nodo. Este diseño hace que la clave sea única por nodo y no requiera almacenamiento de secreto adicional:

```
input_key_material = private_key_bytes(banexus_mtls_cert)
salt               = node_id.as_bytes()
info               = b"banexus-policy-cache-v1"
output_len         = 32 bytes

key = HKDF-SHA256(ikm=input_key_material, salt=salt, info=info, len=32)
```

**Propiedad de seguridad**: si el certificado mTLS es revocado y reemplazado (rotación), la clave del cache cambia automáticamente → los datos del cache anterior son irrecuperables.

### 3.2 Formato del archivo cifrado

```
/var/lib/banexus/policy_cache.enc

[Offset]  [Bytes]  [Campo]
0         4        Magic "BNXC"
4         4        Versión de formato (uint32 LE, actualmente 1)
8         8        Timestamp de creación (unix ms, uint64 LE)
16        8        TTL en segundos (uint64 LE)
24        12       Nonce AES-256-GCM (12 bytes aleatorios)
36        4        Longitud del ciphertext (uint32 LE)
40        N        Ciphertext (payload JSON cifrado)
40+N      16       GCM auth tag
```

### 3.3 Payload (antes de cifrar)

```json
{
  "version": 1,
  "node_id": "Ventas-01",
  "created_at": "2026-08-04T08:00:00Z",
  "expires_at": "2026-08-04T12:00:00Z",
  "policies": [
    {
      "user_id": "uuid-cajero",
      "sam128_word_a": "0x...",
      "sam128_word_b": "0x...",
      "actuator_commands": [...],
      "roltemplate_hash": 12345678
    }
  ]
}
```

### 3.4 Ciclo de vida del cache

| Estado | Condición | Comportamiento |
|--------|-----------|----------------|
| Válido + online | TTL vigente + bhnexus accesible | Usa cache, actualiza en background |
| Válido + offline | TTL vigente + sin conexión | Usa cache, log INFO |
| **Expirado + offline** | TTL caducado + sin conexión | **DENY todo** (fail-secure) |
| Expirado + online | TTL caducado + bhnexus accesible | Solicita nuevo policy snapshot |
| Primera vez | Sin cache + online | Descarga policy snapshot completo |
| Primera vez + offline | Sin cache + sin conexión | **No arranca** (forzosamente online) |

**Excepción fail-safe**: puertas de evacuación configuradas con `fail_mode=fail_safe` en `idn_identity_entity` son controladas por hardware mecánico independiente del software. El DENY de software no afecta su apertura de emergencia.

## 4. Threat Model del canal privilegiado (Sub-canal B)

### 4.1 Superficie de ataque

El canal privilegiado sub-canal B (`/run/bos/bauth-nexus.sock`) tiene la superficie de ataque más alta de bNexus porque:
- bAuth puede emitir `emergency_revoke` y `blacklist_node` que afectan a todos los nodos
- bhnexus puede reportar `auth_spike` que puede disparar lockout de usuarios

### 4.2 Amenazas y controles

| Amenaza | Descripción | Control |
|---------|-------------|---------|
| **Proceso malicioso suplantando a bAuth** | Un proceso sin privilegios intenta escribir en el socket | Socket `0660 bhnexus:bos-group` — solo el proceso de bAuth (que corre como grupo `bos-group`) puede conectar |
| **Suplantación de bhnexus** | Un proceso intenta recibir mensajes del sub-canal B | Socket creado por bhnexus con `0660`; solo bAuth (cliente) puede conectar |
| **Inyección de `emergency_revoke` falso** | Atacante con acceso al socket intenta revocar accesos masivamente | bAuth verifica la integridad del frame con HMAC-SHA256 usando la clave de sesión del sub-canal |
| **DoS al sub-canal** | Inundación de mensajes `auth_spike` | Rate limiting: máximo 100 mensajes/segundo por canal; los siguientes son descartados con log WARNING |
| **Replay de mensajes** | Atacante reutiliza un frame `blacklist_node` capturado | Monotonic sequence counter por sesión; frame fuera de secuencia → descartado + SIEM |

### 4.3 Mitigación sistémica

```
Si el sub-canal B está comprometido → el impacto es:
- Revocar accesos (denial of service temporal) — no da GRANT de acceso
- Reportar falsos positivos de tamper — bAuth puede investigar antes de actuar

El sistema está diseñado para que un atacante en el sub-canal B
solo pueda hacer más restrictivo el acceso, nunca más permisivo.
```

## 5. Reglas Wazuh de bhnexus

bhnexus emite eventos Syslog (RFC 5424) al agente Wazuh local. Las siguientes reglas detectan anomalías:

```xml

  <description>ALTO: Múltiples auth denied desde el mismo nodo (&gt;10/min)</description>
  <group>iso_27001_A.8.15,nist_800-207</group>
</rule>

<rule id="100101" level="8">
  <decoded_as>syslog</decoded_as>
  <match>NEXUS-002</match>
```

### 5.1 Formato de evento Syslog emitido por bhnexus

```
<134>1 2026-08-04T10:15:30.123Z bhnexus-host bhnexus 1234 NEXUS-001 [bos@32473 ctx_id="00-abc..." node_id="Ventas-01" denied_count="12"] Múltiples auth denied desde Ventas-01
```

| Campo | Descripción |
|-------|-------------|
| `<134>` | Facility 16 (local0) + Severity 6 (info) → en alertas críticas cambia a severity 1 |
| hostname | `bhnexus-host` (configurable) |
| appname | `bhnexus` |
| msgid | `NEXUS-001` a `NEXUS-008` |
| Structured Data | `ctx_id`, `node_id`, métricas relevantes |

## 6. Seguridad sin almacenamiento de biometría

bNexus tiene una garantía arquitectónica fuerte respecto a datos biométricos:

| Componente | ¿Almacena biometría? | Justificación |
|-----------|:-------------------:|---------------|
| bhnexus (proceso) | ❌ | Solo procesa el hash PBKDF2-SHA256 en tránsito |
| bhnexus (disco/BD) | ❌ | Audit trail guarda el hash anonimizado, no datos brutos |
| banexus | ❌ | Captura el hash del chip del lector, lo reenvía, lo descarta |
| Chip del lector OSDP | ✅ (template protegido) | Permanece en el chip — nunca sale del hardware |

Esta arquitectura cumple:
- RGPD Art. 9 (datos biométricos como categoría especial)
- NIST SP 800-63-4 §5.1.9 (biometric constraints)
- ISO 27001 A.8.11 (borrado de información)

## 7. Hardening de bhnexus en producción

### 7.1 Capabilities Linux de bhnexus

```ini
# /etc/systemd/system/bhnexus.service
[Service]
User=bhnexus
Group=bos-group
AmbientCapabilities=CAP_SYS_RAWIO    # acceso a GPIO/RS-485
CapabilityBoundingSet=CAP_SYS_RAWIO
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=strict
ProtectHome=true
RestrictNamespaces=true
SystemCallFilter=@system-service
```

### 7.2 Capabilities Linux de banexus

```ini
# /etc/systemd/user/banexus.service
[Service]
User=banexus
Group=banexus
AmbientCapabilities=CAP_SYS_RAWIO CAP_BPF CAP_PERFMON
CapabilityBoundingSet=CAP_SYS_RAWIO CAP_BPF CAP_PERFMON
NoNewPrivileges=true
RestartPreventExitStatus=99
```

`CAP_BPF` + `CAP_PERFMON` solo son necesarios cuando `audit_method=ebpf` en zonas sl=4.
