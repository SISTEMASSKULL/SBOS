## 1. Qué es una saga en bNexus

Una **saga** es una secuencia de pasos coordinados a través de múltiples componentes (bAuth, bhnexus, banexus) donde cada paso puede fallar y cada fallo tiene un manejador definido. Las sagas de bNexus garantizan que el sistema siempre queda en un estado consistente — nunca en un estado intermedio indeterminado.

No son transacciones distribuidas. No hay commit de dos fases. Son secuencias compensables: si el paso N falla, se ejecuta la compensación del paso N-1, y así sucesivamente.

---

## 2. Catálogo de sagas (4 sagas principales)

| Saga | Trigger | Duración típica | Fallo más común |
|------|---------|:--------------:|-----------------|
| S-01 Conexión mTLS | banexus arranca | 1.2s | Cert expirado o Vault inaccesible |
| S-02 Reconexión con backoff | Pérdida de Puerta 1 | Variable | Red inestable en sucursal |
| S-03 Policy Push | RolTemplate cambia en bAuth | 50-200ms | banexus desconectado |
| S-04 Recuperación offline | banexus reconecta tras offline | 2-5s | Cache corrupto o expirado |

## 3. S-01 — Conexión mTLS inicial

### Descripción
El proceso completo que ejecuta banexus al arrancar por primera vez para establecer la conexión con bhnexus y recibir su primer paquete de políticas.

### Pasos

```
P1. banexus arranca (systemd Type=notify)
    → Carga SPIFFE SVID desde /run/bos/certs/banexus.crt + banexus.key
    → Si cert no existe → solicita a Vault PKI por bOS API (BLOQUEA aquí hasta recibir)

P2. banexus establece TLS 1.3 con bhnexus:9444
    → Conecta TCP a bhnexus (retry x3 antes de entrar en S-02)
    → Handshake TLS 1.3 con mTLS bidireccional
    → bhnexus verifica el SVID de banexus contra la CA de Vault
    → banexus verifica el SVID de bhnexus contra la CA de Vault
    → Si verificación falla → ERROR: cert inválido, alarma SIEM, NO reintentar

P3. banexus envía auth_request de tipo "handshake"
    payload:
    {
      "type":       "auth_request",
      "request_id": "<uuid>",
      "node_id":    "<node_id>",
      "spiffe_id":  "spiffe://sbos.skull/agent/banexus/<node_id>",
      "form":       "daemon|gateway|sdk|virtual",
      "version":    "3.0.0",
      "ctx_id":     "<trace>",
      "timestamp":  "<RFC3339>"
    }

P4. bhnexus valida el handshake:
    → Busca node_id en idn_identity_entity (SBOSDB via bAuth sub-canal A)
    → Verifica que el node_id corresponde al SVID presentado
    → Comprueba que el nodo no está en blacklist
    → Si node_id no existe → DENY con code: node_not_registered
    → Si en blacklist → DENY con code: node_blacklisted

P5. bhnexus retorna auth_response con el primer SAM-128 de arranque:
    {
      "type":        "auth_response",
      "request_id":  "<uuid de P3>",
      "status":      "connected",
      "policies": { ... },   // paquete de políticas de la zona
      "zone_config": { ... },
      "timestamp":   "<RFC3339>"
    }

P6. banexus persiste el paquete de políticas:
    → Cifra con AES-256-GCM (key = HKDF-SHA256 del cert mTLS)
    → Escribe en /var/lib/banexus/policy_cache.enc
    → Emite sd_notify("READY=1")
    → Primera heartbeat enviada a bhnexus

RESULTADO: banexus operativo, cache local hidratado, listo para procesar auth_request
```

### Compensaciones

| Paso falla | Acción compensatoria |
|-----------|---------------------|
| P1 — Vault inaccesible | Reintentar cada 60s. Si hay cache local válido → arrancar en modo degradado (solo cache) |
| P2 — bhnexus inalcanzable | Entrar en S-02 (backoff) |
| P4 — node_not_registered | DENY permanente: no reconectar. Alerta al operador para registrar el nodo |
| P4 — node_blacklisted | DENY permanente: no reconectar. Solo bOS puede levantar el blacklist |

## 4. S-02 — Reconexión con backoff exponencial

### Descripción
La saga que ejecuta banexus cuando pierde la conexión con bhnexus (o cuando S-01 falla en P2).

### Pasos y tiempos

```
Estado: Conexión establecida (S-01 completado)
Evento: PING sin PONG en 60s → ConnectionDead

Intento 1: espera 1s → reintenta conexión TCP
Intento 2: espera 5s → reintenta
Intento 3: espera 15s → reintenta
Intento 4: espera 30s → reintenta
Intento 5+: espera 60s → reintenta (máximo; se repite indefinidamente)

Durante el backoff:
  banexus entra en modo OFFLINE:
  → Sirve auth_request desde el Policy Cache local (AES-256-GCM)
  → Rechaza tipos de credencial que requieren verificación online (biométrico, QR Dinámico)
  → Acepta tipos con cache válido (NFC con TTL vigente, smartcard con cert válido)
  → Log: cada decisión offline marcada con "offline_mode:true" en audit_event
  → Counter: offline_events++ (reportado en node_online al reconectar)

Al reconectar (S-01 se ejecuta de nuevo):
  P1 ya completado (cert no expira en < 4h tipicamente)
  Se salta al P2 directamente
  Tras reconexión exitosa:
    → Invalida el Policy Cache local (ya hay datos frescos de bhnexus)
    → Solicita policy_update completo
    → Envía node_online con offline_events count al canal B
```

### Política de cache durante offline

```
Tipo de credencial | ¿Acepta offline? | Condición
NFC DESFire        | Sí               | Cache entry < 4h TTL
Smartcard X.509    | Sí               | Cert vigente (no expirado)
PIN                | Sí               | Hash en cache local
RFID Wiegand       | Sí               | Mapping en cache
QR Dinámico        | No               | Requiere HMAC-key fresco de bAuth
Biométrico OSDP    | No*              | Requiere verificación de hash en bAuth
BLE Aliro          | Sí               | Token offline del SDK almacenado

*La excepción es si el template biométrico está almacenado localmente (banexus-gateway
 con biometric_local_cache=true en la configuración). Fuera de eso: deniega.
```

## 5. S-03 — Policy Push (propagación de cambio de política)

### Descripción
La saga que se activa cuando bAuth detecta que un RolTemplate cambió y necesita propagar ese cambio a todos los nodos banexus afectados.

### Flujo completo

```
ORIGEN: Operador modifica un RolTemplate en bAuth (o registra/revoca un usuario)

P1. bAuth detecta el cambio (trigger en SBOSDB):
    → Calcula lista de usuarios afectados por el cambio
    → Calcula nuevo roltemplate_hash

P2. bAuth envía policy_sync por canal privilegiado a bhnexus:
    {
      "event":            "policy_sync",
      "roltemplate_id":   "<uuid>",
      "roltemplate_hash": "0x<hex4>",
      "affected_users":   ["uuid1", "uuid2", ...],
      "action":           "invalidate_cache",
      "ts":               "<RFC3339>"
    }

P3. bhnexus recibe policy_sync:
    → Para cada user_id en affected_users:
      a. Elimina la entrada del Auth Cache (in-memory)
      b. Identifica los nodos banexus que tienen sesiones activas de ese usuario
    → Construye el mensaje policy_update para cada nodo afectado:
    {
      "type":             "policy_update",
      "user_ids":         ["uuid1", "uuid2"],
      "roltemplate_hash": "0x<hex4>",
      "action":           "invalidate_cache",
      "ctx_id":           "<trace>",
      "timestamp":        "<RFC3339>"
    }

P4. bhnexus envía policy_update a cada banexus afectado (por Puerta 1):
    → Para nodos conectados: entrega inmediata
    → Para nodos desconectados (offline): encola el mensaje
      → Al reconectar, bhnexus entrega los mensajes encolados en orden

P5. banexus recibe policy_update:
    → Invalida las entradas del Policy Cache local para los user_ids recibidos
    → Si el usuario tiene una sesión activa en el lector (credencial pendiente de validar):
      a. La validación ya en curso continúa (no la interrumpe)
      b. La siguiente solicitud del mismo usuario irá a bhnexus para obtener datos frescos

P6. En la siguiente auth_request del usuario afectado:
    → bhnexus ya no tiene cache entry → consulta bAuth por sub-canal A
    → bAuth retorna el nuevo bitmask con la política actualizada
    → bhnexus actualiza el Auth Cache con el nuevo entry
    → bhnexus envía auth_response con actuator_commands al banexus
```

### Tiempo total de propagación

```
P1 (bAuth detecta): < 10ms (trigger en SBOSDB)
P2 (canal B):       < 5ms
P3 (bhnexus):       < 5ms por usuario (lineal)
P4 (Puerta 1):      < 50ms por nodo (WebSocket + mTLS overhead)
P5 (banexus):       < 2ms
P6 (próximo auth):  < 10ms (sub-canal A TLV)

TOTAL para que el nuevo permiso sea efectivo en el primer acceso posterior:
  ~72ms (online) + tiempo hasta el próximo acceso del usuario
```

## 6. S-04 — Recuperación offline completa

### Descripción
La saga que ejecuta banexus al reconectar después de un período offline prolongado (> TTL del Policy Cache = 4h).

### El problema
Si banexus estuvo offline más de 4h, su Policy Cache local expiró. Al reconectar, no puede simplemente usar el cache viejo — puede haber cambios de políticas, revocaciones, o incluso invalidaciones de emergencia que no recibió.

### Pasos

```
P1. banexus detecta que el cache local expiró (timestamp > TTL 4h)

P2. banexus reconecta por S-02 (backoff ya completado)

P3. En el handshake de reconexión (S-01 P3), banexus incluye:
    {
      "type":                   "auth_request",
      "node_id":                "<node_id>",
      "cache_state":            "expired",
      "last_policy_hash":       "0x<hex4>",  // último hash conocido
      "offline_duration_s":     14400,        // tiempo offline
      "offline_cache_hits":     23,
      "offline_cache_misses":   2,
      ...
    }

P4. bhnexus detecta cache_state = "expired":
    → Solicita a bAuth un "policy_snapshot" completo de la zona del nodo
    → bAuth construye el snapshot: todos los usuarios con acceso a la zona + sus SAM-128

P5. bhnexus envía el snapshot completo al banexus:
    {
      "type":        "auth_response",
      "status":      "connected",
      "recovery":    true,
      "policies":    { ... snapshot completo ... },
      "cache_rebuild": true,  // indica que el banexus debe reemplazar su cache
      "timestamp":   "<RFC3339>"
    }

P6. banexus reconstruye el Policy Cache desde cero:
    → Borra el cache expirado
    → Cifra y escribe el snapshot completo
    → TTL reiniciado a 4h

P7. banexus entra en modo normal (online):
    → Emite node_online al canal B con estadísticas del período offline
```

## 7. Sagas encadenadas — ejemplo real

Una revocación de emergencia activa tres sagas en secuencia:

```
[bAuth detecta compromiso de credencial]
  → S-03 Policy Push: emergency_revoke vía canal B
    → bhnexus flushea cache del usuario
    → Envía invalidate_cache a todos los nodos del usuario
      → banexus (online): S-03 P5 — invalida inmediatamente
      → banexus (offline): encola el mensaje
        → Al reconectar: S-04 — reconstruye cache con usuario sin acceso
```

El usuario no puede acceder en ningún punto posterior al emergency_revoke, estén online u offline los nodos.
