## 1. Driver OSDP v2.2.2 (`osdp_driver.rs`)

### Estándar
OSDP (Open Supervised Device Protocol) v2.2.2 — SIA / IEC 60839-11-5.

### Características
- Canal cifrado AES-128 bidireccional (Secure Channel — OSDP SC)
- bhnexus actúa como **ACU** (Access Control Unit) — master del bus RS-485
- El lector actúa como **PD** (Peripheral Device) — esclavo
- Soporta: NFC, RFID, biométrico, teclado, display, relé, tamper

### Parámetros de conexión

```toml
[[hal.devices]]
protocol         = "osdp_v2"
device_id        = "PHY_DEV_OSDP_ENTRADA"
address          = "/dev/ttyUSB0"       # RS-485 via USB adapter
extra            = {
  osdp_address   = "1",                 # dirección del PD en el bus (0-127)
  baud_rate      = "9600",              # 9600 | 19200 | 38400 | 57600 | 115200
  secure_channel = "true",              # habilitar OSDP Secure Channel AES-128
  vault_key_path = "secret/bhnexus/osdp/entrada"  # clave OSDP en Vault
}
```

### Eventos producidos

| CredentialType | Cuándo | Payload |
|----------------|--------|---------|
| `NFC_MIFARE_DESFIRE` | Lector NFC DESFire | Sector cifrado AES (base64) |
| `RFID_125KHZ` | Lector Wiegand vía OSDP | facility_code + card_number |
| `FINGERPRINT_HASH` | Lector biométrico OSDP Biometric Profile | Hash PBKDF2-SHA256 del template |
| `FACE_HASH` | Cámara facial con OSDP | Hash del embedding facial |
| `PIN_HASH` | Teclado OSDP | HMAC-SHA256(pin_key, dígitos) |
| `SMARTCARD_X509` | Lector OSDP Smart Card Profile | Cert + firma del challenge |

### Comandos de actuador soportados

```
oCmd_OUT (relay) — activar relé para abrir cerradura
oCmd_LEDER — controlar LEDs del lector (verde/rojo/naranja/parpadeo)
oCmd_BUZZ — activar buzzer del lector (beep de GRANT o DENY)
oCmd_TEXT — mostrar texto en pantalla del lector (si tiene display)
oCmd_MFST — activar/desactivar tamper LED
```

### Tamper detection

OSDP incluye línea de tamper hardware. Si el lector detecta que se abre su carcasa:
- El driver recibe el bit de tamper en el poll response
- El driver emite `device_tamper` al canal B (bhnexus → bAuth)
- bAuth activa protocolo de respuesta a incidente (SIEM + blacklist opcional)

## 2. Driver Wiegand (`wiegand_driver.rs`)

### Estándar
Wiegand 26-bit (más común), 34-bit, 37-bit — protocolo legacy sin estándar formal.

### Advertencia de seguridad

```
⚠️ WIEGAND ES INSEGURO — SOLO PARA INFRAESTRUCTURA LEGADA

El protocolo Wiegand transmite los datos de la tarjeta en CLARO por el cable.
No tiene cifrado, no tiene autenticación, no tiene anti-replay.
Las tarjetas de 125kHz son trivialmente clonables.

USAR SOLO CUANDO:
  - La infraestructura ya tiene lectores Wiegand instalados
  - El costo de reemplazo es prohibitivo
  - Se acepta explícitamente el riesgo (documentado en la política de seguridad del tenant)

NO USAR PARA ZONAS DE SECURITY_LEVEL ≥ 2.
```

### Conexión vía GPIO (Raspberry Pi / ARM SBC)

```toml
[[hal.devices]]
protocol   = "wiegand"
device_id  = "PHY_DEV_WIEGAND_ESTACIONAMIENTO"
address    = "/dev/gpiochip0"          # GPIO chip
extra      = {
  data0_pin  = "17",                   # DATA0 — lógica "0"
  data1_pin  = "27",                   # DATA1 — lógica "1"
  format     = "26",                   # 26 | 34 | 37 bits
  timeout_ms = "25"                    # timeout entre pulsos (ms)
}
```

### Protocolo eléctrico

```
Wiegand 26-bit:
  bit 0 (paridad par):  sobre bits 1-12
  bits 1-8  (8 bits): facility_code
  bits 9-24 (16 bits): card_number
  bit 25 (paridad impar): sobre bits 13-24

La señal es diferencial: DATA0 pulso bajo = bit 0, DATA1 pulso bajo = bit 1
Duración de pulso: 50µs, intervalo entre pulsos: 1ms-25ms (implementaciones varían)
```

### Mapeo a user_uuid

El driver Wiegand solo conoce `(facility_code, card_number)`. El mapeo al `user_uuid` se realiza en bAuth:

```json
// bitmask_request para Wiegand
{
  "type":         "bitmask_request",
  "user_id":      null,
  "query_type":   "wiegand",
  "facility_code": 1,
  "card_number":   12345,
  ...
}
```

bAuth busca en `bauth.auth_credential` donde `method_code = 'RFID_WIEGAND'` y `credential_data JSONB` contiene `{"facility": 1, "card_number": 12345}`.

## 3. Driver MQTT (`mqtt_driver.rs`)

### Estándar
MQTT 5.0 (OASIS) sobre TLS 1.3.

### Uso típico
Sensores IoT, sistemas de alarma, actuadores industriales que publican en tópicos MQTT.

### Parámetros de conexión

```toml
[[hal.devices]]
protocol  = "mqtt"
device_id = "PHY_DEV_SENSOR_TEMPERATURA_RACK01"
address   = "mqtts://10.0.1.10:8883"   # TLS obligatorio (mqtts://)
extra     = {
  topic_subscribe = "sbos/sensors/rack01/access",   # tópico de entrada
  topic_publish   = "sbos/commands/rack01",          # tópico de actuación
  qos             = "1",                             # QoS: 0 | 1 | 2
  client_id       = "bhnexus-rack01-sensor",
  vault_cert_path = "pki/bhnexus/mqtt/rack01"        # cert TLS cliente
}
```

### Esquema del mensaje de entrada (sensor → bhnexus)

```json
{
  "event_type":     "access_attempt",
  "device_id":      "PHY_DEV_SENSOR_RACK01",
  "credential_type": "rfid_125khz",
  "payload":        "<base64 del dato del sensor>",
  "timestamp":      "RFC3339"
}
```

El driver valida el JSON, extrae el `payload`, y construye el `CredentialEvent`.

### Esquema del mensaje de actuación (bhnexus → sensor)

```json
{
  "command":    "OPEN",
  "target":     "RELAY_01",
  "duration_ms": 5000,
  "ctx_id":     "string"
}
```

## 4. Driver ONVIF (`onvif_driver.rs`)

### Estándar
ONVIF Profile S (streaming), Profile T (avanzado), Profile C (control de acceso).

### Uso típico
Cámaras IP de seguridad con reconocimiento facial o detección de objetos.

### Parámetros de conexión

```toml
[[hal.devices]]
protocol  = "onvif"
device_id = "PHY_DEV_CAMARA_ENTRADA_PRINCIPAL"
address   = "https://192.168.1.101"    # dirección de la cámara
extra     = {
  onvif_profile  = "Profile_C",
  username       = "admin",
  vault_password = "secret/bhnexus/onvif/camara-entrada"  # en Vault
}
```

### Modo de operación

El driver ONVIF opera en modo **pull** (sondeo periódico) o **push** (event subscription):

```
Modo push (preferido):
  bhnexus se subscribe a GetEventProperties del servicio ONVIF
  La cámara notifica eventos de detección en tiempo real
  Latencia: < 100ms desde detección hasta CredentialEvent

Modo pull (fallback para cámaras ONVIF básicas):
  bhnexus sondea GetRecordings cada 500ms
  Analiza si hay nuevo frame con detección
  Latencia: 500ms - 1s
```

### Credential type producido

La cámara retorna el hash del embedding facial (no la imagen):

```rust
// El driver ONVIF produce:
CredentialEvent {
    credential_type: CredentialType::FaceHash,
    payload: hash_bytes,  // FACE_HASH: embedding hash del proveedor de visión
    ...
}
```

bhnexus envía el hash a bAuth que lo compara contra `bauth.auth_biometric_template`.

## 5. Driver USB HID (`usb_hid_driver.rs`)

### Uso típico
Este driver opera **en banexus** (no en bhnexus directamente). Captura lectores QR o NFC conectados por USB al workstation/POS donde corre banexus.

Ver `4.01_MANUAL-INPUT-HOOKING.md` para el mecanismo de intercepción udev.

### Configuración en banexus (no en bhnexus)

```toml
# banexus.toml
[[hal.devices]]
protocol  = "usb_hid"
device_id = "PHY_DEV_QR_VENTAS_01"
address   = "usb:046a:0023"   # VID:PID del lector
extra     = {
  udev_rule = "true",         # crea regla udev para captura exclusiva
  input_type = "qr",          # "qr" | "nfc"
}
```

### Captura exclusiva via udev

```
udev regla instalada por banexus:
  SUBSYSTEM=="usb", ATTR{idVendor}=="046a", ATTR{idProduct}=="0023", \
  GROUP="banexus", MODE="0660"

banexus abre el dispositivo con O_RDONLY ANTES de que evdev lo registre.
Los datos llegan al driver USB HID — evdev nunca los ve.
Esto previene que cualquier proceso del usuario pueda leer la tarjeta NFC o QR.
```

## 6. Driver HTTP (`http_driver.rs`)

### Uso típico
Terminales POS con API REST propia, interfonos IP, kioskos que pueden llamar a un endpoint en lugar de ser un servidor.

### Dos modos de operación

**Modo servidor** (bhnexus expone un endpoint que el terminal llama):

```toml
[[hal.devices]]
protocol = "http"
device_id = "PHY_DEV_INTERFONO_LOBBY"
address   = "0.0.0.0:9453"   # bhnexus escucha en este puerto
extra     = {
  mode = "server",
  path = "/api/v1/credential",
  tls  = "true",
  vault_cert_path = "pki/bhnexus/http/lobby"
}
```

Esquema de la request que el terminal envía:

```json
POST /api/v1/credential
{
  "device_id":      "PHY_DEV_INTERFONO_LOBBY",
  "credential_type": "nfc",
  "payload":        "<base64>",
  "timestamp":      "RFC3339"
}
```

**Modo cliente** (bhnexus sondea el terminal periódicamente):

```toml
[[hal.devices]]
protocol = "http"
device_id = "PHY_DEV_POS_CHECKOUT"
address   = "https://10.0.1.20:8443/events"
extra     = {
  mode          = "client",
  poll_interval = "500",        # ms
  vault_cert_path = "pki/bhnexus/http/pos-checkout"
}
```

## 7. Extensibilidad — agregar un driver nuevo

Para soportar un protocolo no incluido (ej: KNX, BACnet, OSDP v3):

```rust
// 1. Crear el módulo: src/hal/knx_driver.rs
pub struct KnxDriver { /* ... */ }

#[async_trait]
impl DeviceDriver for KnxDriver {
    fn protocol(&self) -> &str { "knx" }
    async fn connect(&mut self, params: ConnectionParams) -> Result<(), DriverError> { /* ... */ }
    async fn listen(&self, tx: Sender<CredentialEvent>) -> Result<(), DriverError> { /* ... */ }
    async fn send_command(&self, cmd: ActuatorCommand) -> Result<(), DriverError> { /* ... */ }
    fn health_check(&self) -> DeviceHealth { /* ... */ }
    async fn disconnect(&mut self) -> Result<(), DriverError> { /* ... */ }
}

// 2. Registrar en DriverRegistry (src/hal/mod.rs):
registry.register("knx", Box::new(KnxDriver::new()));

// 3. Configurar en bhnexus.toml:
// [[hal.devices]]
// protocol = "knx"
// device_id = "PHY_DEV_KNX_CLIMATIZACION"
// address = "10.0.1.30:3671"
```

No se toca ningún otro archivo del núcleo. El DriverRegistry detecta la nueva clave "knx" y usa el driver registrado.
