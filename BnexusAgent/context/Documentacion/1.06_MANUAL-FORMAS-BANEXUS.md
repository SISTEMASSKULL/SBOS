## 1. Principio de universalidad

**banexus siempre existe en alguna forma.**

La pregunta no es _"¿se necesita banexus?"_ — banexus siempre está presente en cualquier escenario de autenticación no-trivial. La pregunta es _"¿qué forma toma banexus en este contexto?"_

El único caso sin ninguna forma de banexus es el **HAL Directo de bhnexus**: hardware mudo en el mismo edificio que bhnexus, conectado por cable o LAN local — la chapa no es un cliente de bAuth, es un periférico controlado por el driver del HAL.

---

## 2. La distinción fundamental: software vs hardware

Antes de elegir una forma, es necesario entender la diferencia entre un **cliente de software** y un **periférico de hardware**:

**Cliente de software:** corre en un OS de propósito general, hace llamadas HTTP/WebSocket, puede instalar librerías. Una app web, un backend, un CLI, una app móvil — todos son clientes de software. **Todos usan banexus-implicit.**

**Periférico de hardware:** no corre un OS de propósito general, no puede ejecutar una librería arbitraria. Una chapa OSDP habla RS-485. Una cámara habla ONVIF. Un torniquete responde a pulsos de relé. **Estos no son clientes de bAuth — bhnexus HAL los controla.**

La caja registradora (POS) es un híbrido: es un computador de propósito general (parte software → banexus-implicit para la app, banexus-daemon para el hardware adjunto) con periféricos físicos conectados (cajón de dinero serial, lector NFC — parte hardware → banexus-daemon los controla).

---

## 3. Las cinco formas — resumen

| # | Forma | Cuándo | Binario | Autenticación |
|---|-------|--------|---------|---------------|
| 1 | **banexus-implicit** | Cualquier app de software (la forma base universal) | Ninguno | mTLS + JWT/OIDC + W3C Trace Context |
| 2 | **banexus-daemon** | PC / workstation con hardware físico adjunto | Rust MUSL, systemd --user | SPIFFE/SVID mTLS |
| 3 | **banexus-gateway** | Hardware en sitio remoto sin conexión directa al servidor | Mismo Rust MUSL, `mode = gateway` en SBC/Pi | SPIFFE/SVID mTLS |
| 4 | **banexus-sdk** | App móvil iOS/Android con acceso físico BLE/UWB/NFC | Librería nativa Aliro CSA 2023 | mTLS embebido en la librería |
| 5 | **banexus-virtual** | Dispositivo con firmware HTTP/REST que puede auto-actuarse | Ninguno — el firmware llama a bAuth | mTLS desde el firmware |

---

## 4. banexus-implicit — la forma base universal

banexus-implicit es el modo en que **cualquier aplicación de software** se conecta a bAuth como su proveedor de autenticación. Es la forma más amplia y más frecuente.

No requiere instalar ningún binario propietario. Usa tres protocolos RFC estándar que cualquier lenguaje y framework soporta:

```
① mTLS X.509  (RFC 8446)
   → El certificado del servidor/app prueba quién está llamando
   → Soportado en: curl, Python requests, PHP Guzzle, Go net/http, .NET HttpClient, etc.
   → Distribuido por: bOS vía SCEP/ACME (apps SBOS) o portal bAuth (apps externas)

② JWT/OIDC    (RFC 6749 + RFC 7519)
   → bAuth emite JWT firmados — cualquier librería OAuth2 estándar los consume
   → Soportado en: laravel/passport, django-allauth, spring-security, nuxt-auth, etc.

③ W3C Trace Context  (W3C + OpenTelemetry)
   → El header `traceparent` inyecta automáticamente el ctx_id en cada llamada HTTP
   → SDK de OpenTelemetry disponible en 15+ lenguajes
```

**Quién usa banexus-implicit:**

| Tipo de aplicación | Ejemplo | Tenant |
|-------------------|---------|--------|
| App SBOS interna | Core UI (Flutter), bOS CLI, bkernel dashboard | Interno |
| Daemon M2M de SBOS | biedata, bnotify, bsearch (sin usuario interactivo) | Interno |
| App web del cliente | Sistema ERP del cliente en Laravel, Django | Interno |
| SPA frontend | Dashboard Vue, React, Angular del cliente | Interno |
| App de desarrollador externo | App de un tercero que usa bAuth como OIDC Provider | Externo |
| Backend de tercero | API Spring Boot, FastAPI, Rails que delega auth a bAuth | Externo |

**SBOS usa banexus-implicit para sus propias apps.** La Core UI de SBOS se conecta a bAuth exactamente igual que una app Laravel de un cliente externo. El protocolo es idéntico; lo que difiere es el tenant.

## 5. banexus-daemon — hardware físico en workstation

banexus-daemon es el binario Rust MUSL que corre como servicio systemd --user en una workstation o POS terminal de Fedora. Gestiona hardware físico adjunto al mismo equipo donde corre.

**Hardware que controla:**
- Cajón de dinero (serial RS-232/RS-485)
- Relés GPIO (apertura de puertas, barreras)
- Lectores USB (QR, NFC, banda magnética) — via udev + libusb antes de evdev
- Módulo PAM (`pam_banexus.so`) — Shell Sentinel para comandos sensibles

**Capacidades exclusivas de banexus-daemon:**

```
Input Hooking:
  udev rule 99-banexus → asigna lector USB al grupo 'banexus', permisos 0660
  libusb bulk transfer → captura datos del lector ANTES de evdev
  Protege contra: USB Rubber Ducky, inyección de eventos HID falsos

Shell Sentinel:
  pam_banexus.so en auth phase de PAM
  Intercepta: apt-get, dnf, systemctl, rm -rf, sudo
  Consulta a bhnexus → GRANTED/DENIED para el comando
  Fail-open con cache local si bhnexus no responde

Actuator Controller:
  serialport-rs → relés via /dev/ttyUSB0
  GPIO (tokio-gpiod en ARM) → control directo de pines
  Auto-close timer: configurable (default 5s para puertas)
```

**Configuración canónica:**
```toml
[agent]
node_id   = "Ventas-01"
mode      = "daemon"          # ← distingue de gateway
host_url  = "wss://sbos-server:9444"
tls_cert  = "/etc/banexus/tls/agent.crt"
tls_key   = "/etc/banexus/tls/agent.key"
ca_cert   = "/etc/banexus/tls/ca.crt"

[input]
intercept_usb   = true
reader_devices  = ["/dev/banexus/reader-*"]

[shell_sentinel]
sensitive_commands = ["apt-get", "dnf", "systemctl", "rm -rf"]

[actuators]
relay_port = "/dev/ttyUSB0"
```

## 6. banexus-gateway — hardware en sitio remoto

banexus-gateway es el **mismo binario** de banexus-daemon, con `mode = gateway`, desplegado en un dispositivo embebido (Raspberry Pi, ARM SBC, PC industrial) instalado físicamente en una ubicación remota — una sucursal, un edificio distante, un almacén.

El gateway actúa como proxy: los dispositivos físicos de la sucursal (chapas OSDP, cámaras, torniquetes) se conectan al SBC por cable, y el SBC tuneliza las credenciales al bhnexus central del servidor.

```
[Sucursal remota]
  Chapa OSDP A (RS-485) ──┐
  Chapa OSDP B (RS-485) ──┼──→ banexus-gateway (Raspberry Pi)
  Torniquete (Wiegand) ───┘         │
                                    │ WebSocket mTLS (Puerta 1)
                                    │ SPIFFE/SVID
                                    ▼
                             bhnexus (servidor central)
                                    │ Puerta 2
                                    ▼
                             bAuth (fuente de verdad)
```

**Diferencia con banexus-daemon:**
- banexus-daemon: el hardware está en el **mismo equipo** donde corre el binario
- banexus-gateway: el hardware está en la **misma sucursal** que el SBC, pero la autoridad (bhnexus+bAuth) está en el servidor central

**Configuración canónica:**
```toml
[agent]
node_id  = "Sucursal-Lima-01"
mode     = "gateway"            # ← modo gateway
host_url = "wss://sbos-central:9444"
tls_cert = "/etc/banexus/tls/gateway-lima-01.crt"
...

[osdp]
enabled  = true
port     = "/dev/ttyAMA0"     # RS-485 en Raspberry Pi
baudrate = 9600

[wiegand]
enabled  = true
d0_pin   = 23
d1_pin   = 24
```

## 7. banexus-sdk — app móvil con acceso físico

banexus-sdk es una **librería nativa** (iOS Swift Package / Android AAR) que implementa el estándar **Aliro CSA 2023** para acceso físico mediante BLE (Bluetooth Low Energy), UWB (Ultra-Wideband) y NFC (Near Field Communication).

Permite que una app iOS o Android corporativa actúe como credencial física de alta seguridad: el teléfono presenta su identidad a un lector compatible con Aliro sin necesitar tarjeta ni PIN.

**Stack técnico:**
- iOS: Swift Package con Core Bluetooth + Core NFC + NearbyInteraction (UWB)
- Android: AAR con BluetoothLeScanner + NfcAdapter + UwbManager
- Protocolo: Aliro (CSA 2023) — protocolo de acceso sin contacto estándar
- Autenticación con bhnexus: mTLS embebido en la librería (certificado del dispositivo)

**Casos de uso:**
- Empleado abre puerta con su iPhone sin tarjeta de acceso
- Técnico accede a rack de servidores con Android corporativo
- Visitante usa pase digital en su teléfono (credencial temporal)

**Alcance de la librería:**
```
banexus-sdk (iOS/Android)
  ├── BLE Advertise/Scan (descubrimiento del lector)
  ├── UWB Ranging (verificación de proximidad < 1m)
  ├── NFC NDEF + ISO 14443 (toque para abrir)
  ├── mTLS con bhnexus (autenticación de la sesión)
  └── W3C Trace Context (ctx_id para auditoría)
```

**NO incluye:** Shell Sentinel, Input Hooking (no aplica a móviles), actuadores seriales.

---

## 8. banexus-virtual — dispositivo auto-actuante

banexus-virtual aplica a dispositivos con capacidad de conexión HTTP/REST propia — pueden llamar a un endpoint de bAuth/bhnexus y ejecutar comandos ellos mismos, sin necesitar un agente externo.

**Ejemplo canónico:** cerradura WiFi con firmware que soporta REST API.

```
[Cerradura WiFi]
  firmware llama → POST /bauth/api/v1/access
                   { "device_id": "cerradura-hab-301",
                     "credential": "QR_HASH_XYZ" }
                   Headers:
                     Authorization: Bearer <JWT del dispositivo>
                     X-mTLS-Cert: <cert fingerprint>

  bAuth responde → { "result": "granted",
                     "action": "unlock",
                     "ttl_ms": 5000 }

  firmware ejecuta → abre el mecanismo de cierre por 5 segundos
```

**Diferencia con banexus-daemon/gateway:**
- En daemon/gateway: banexus recibe el comando y lo traduce al hardware
- En virtual: el propio dispositivo ejecuta la acción — banexus-virtual es el firmware del dispositivo

**Autenticación del dispositivo virtual:**
- El dispositivo obtiene un certificado X.509 de bAuth (via portal o bOS)
- Llama al endpoint de bAuth con mTLS + JWT del dispositivo
- bAuth verifica identidad y retorna la decisión con los comandos de actuación

## 9. Árbol de decisión — qué forma elegir

```
¿El cliente es una aplicación de software?
(app web, backend, CLI, desktop, daemon)
│
└─ SÍ ────────────────────────────────→ banexus-implicit
                                         (cualquier lenguaje, cualquier framework)

¿Es hardware en una workstation/POS con periféricos físicos?
(cajón serial, relé GPIO, lector USB HID)
│
└─ SÍ ────────────────────────────────→ banexus-daemon
                                         (Rust MUSL, systemd --user en Fedora)

¿Es hardware en un sitio remoto sin conexión directa al servidor?
(sucursal distante, edificio separado)
│
└─ SÍ ────────────────────────────────→ banexus-gateway
                                         (mismo binario, mode=gateway, SBC/Pi in situ)

¿Es una app móvil iOS/Android con acceso físico BLE/UWB/NFC?
│
└─ SÍ ────────────────────────────────→ banexus-sdk
                                         (librería Aliro CSA 2023)

¿Es un dispositivo con firmware HTTP/REST que se auto-actúa?
(cerradura WiFi, terminal IP con REST API propia)
│
└─ SÍ ────────────────────────────────→ banexus-virtual
                                         (sin agente — el firmware llama a bAuth)

¿Es hardware mudo en el mismo edificio que bhnexus?
(chapa OSDP local, cámara ONVIF en LAN, sensor MQTT)
│
└─ SÍ ────────────────────────────────→ HAL Directo de bhnexus
                                         (ninguna forma de banexus — bhnexus controla directamente)
```

Para la matriz completa de escenarios → `A.05_ARBOL-DECISION-FORMAS-BANEXUS.md`.

## 10. Tabla de capacidades por forma

| Capacidad | implicit | daemon | gateway | sdk | virtual |
|-----------|:--------:|:------:|:-------:|:---:|:-------:|
| Input Hooking (udev+libusb) | ❌ | ✅ | ✅* | ❌ | ❌ |
| Shell Sentinel (PAM) | ❌ | ✅ | ❌ | ❌ | ❌ |
| Actuadores seriales (relé, GPIO) | ❌ | ✅ | ✅ | ❌ | ✅** |
| Cache local (AES-256-GCM) | ❌*** | ✅ (4h) | ✅ (4h) | ✅ (1h) | ❌ |
| BLE/UWB/NFC (Aliro) | ❌ | ❌ | ❌ | ✅ | ❌ |
| mTLS con bhnexus | ❌**** | ✅ | ✅ | ✅ | ✅ |
| SPIFFE/SVID | N/A | ✅ | ✅ | ❌ | ❌ |
| Binario Rust MUSL | ❌ | ✅ | ✅ | ❌ | ❌ |

*gateway activa input hooking en el SBC local, no en el servidor central  
**virtual el firmware ejecuta la actuación — no es un controlador de actuadores externo  
***implicit usa el cache del navegador/servidor host, no un cache de banexus  
****implicit usa mTLS directamente con bAuth/Kong, no con bhnexus
