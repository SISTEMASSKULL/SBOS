## 1. Qué son las políticas físicas avanzadas

Las políticas físicas avanzadas son restricciones de acceso que van más allá de "¿tiene el usuario el átomo para esta zona?". Involucran **estado**: el historial de movimiento del usuario, la presencia simultánea de otras personas, o la secuencia de puertas abiertas.

Tres políticas estándar de la industria PACS (Physical Access Control Systems):

| Política | Problema que resuelve | Requisito de estado |
|---------|----------------------|---------------------|
| **Anti-Passback (APB)** | Un usuario no puede entrar dos veces sin salir primero (o viceversa) | Posición lógica del usuario en cada zona |
| **Two-Person Rule (2PR)** | Una zona crítica no puede tener menos de 2 personas — nadie entra solo ni sale dejando a alguien solo | Recuento de ocupantes por zona |
| **Mantrap** | Dos puertas en secuencia donde solo una puede estar abierta — previene tailgating | Estado de apertura de cada puerta |

**Nota importante sobre el PDP**: bhnexus **no es el PDP**. Las tres políticas se evalúan en bAuth. bhnexus solicita el SAM-128 a bAuth y aplica el resultado. El estado de posición, ocupantes y apertura de puertas se persiste en SBOSDB y se consulta desde bAuth durante la evaluación.

## 2. Anti-Passback (APB)

### 2.1 El problema

Sin APB, un empleado puede:
1. Usar su tarjeta para abrir la puerta de entrada al CPD (GRANT)
2. Prestarle la tarjeta a un colega que entra con ella (segundo GRANT — sin salida previa)
3. El sistema no detecta que la misma tarjeta "entró" dos veces sin salir

Con APB: el segundo intento de entrada es denegado porque el sistema sabe que la tarjeta ya está "dentro".

### 2.2 Tipos de APB

| Tipo | Descripción | Uso típico |
|------|-------------|-----------|
| **Hard APB** | DENY inmediato si viola la regla | Zonas de alta seguridad (CPD, cámara acorazada) |
| **Soft APB** | GRANT con alerta — el administrador es notificado | Zonas de baja seguridad (oficinas abiertas) |
| **Timed APB** | La posición se olvida tras N minutos — permite entradas repetidas con intervalo | Estacionamientos, zonas de paso rápido |
| **Global APB** | La posición se comparte entre múltiples puertas de la misma zona | Zonas con múltiples puntos de entrada |

### 2.3 Modelo de datos en SBOSDB

La posición lógica del usuario se registra en la tabla de contexto de sesión:

```sql
-- Campo en ses_context o tabla dedicada
-- bAuth consulta esto durante la evaluación del SAM-128
INSERT INTO bos.audit_events (
    entity_type, entity_id, action, metadata
) VALUES (
    'nexus_apb',
    'uuid-usuario',
    'zone_entry',              -- zone_entry | zone_exit
    '{
      "zone_id":    "zona-cpd-01",
      "door_id":    "puerta-cpd-entrada",
      "node_id":    "Servidor-CPD-01",
      "position":   "inside"   -- inside | outside
    }'
);
```

### 2.4 Flujo de evaluación APB en bAuth

```
T+0ms   Usuario presenta tarjeta en puerta-cpd-entrada

T+5ms   bhnexus envía bitmask_request a bAuth:
        {
          "user_id":     "uuid-usuario",
          "node_id":     "Servidor-CPD-01",
          "domain":      "D14",
          "operation":   "physical_access.zone_entry",
          "apb_check":   true
        }

T+6ms   bAuth consulta última posición del usuario:
        SELECT metadata->>'position'
        FROM bos.audit_events
        WHERE entity_type='nexus_apb' AND entity_id='uuid-usuario'
          AND metadata->>'zone_id'='zona-cpd-01'
        ORDER BY created_at DESC LIMIT 1;
        → 'inside'

        Regla APB: position='inside' + operación=zone_entry → VIOLACIÓN

T+7ms   Hard APB: bAuth retorna SAM-128 con outcome=DENY
        SAM-128 WORD-B bit 24 (BIT_APB_VIOLATION) = 1

T+8ms   bhnexus recibe DENY + APB violation
        → No activa actuador
        → Emite event bhnexus.apb_violation → bAuth canal B (para audit trail)
        → OSDP LED rojo parpadeante en el lector
```

### 2.5 Restablecimiento de posición

Situaciones donde la posición debe restablecerse manualmente:
- Evacuación de emergencia (la puerta falla abierta mecánicamente)
- Reset manual por administrador (el empleado salió por una salida de emergencia)
- Timed APB expirado

```bash
# Restablecer posición APB de un usuario via bnexusctl
bnexusctl auth apb-reset --user-id "uuid-usuario" --zone-id "zona-cpd-01" --reason "evacuación"
```

## 3. Two-Person Rule (2PR) — Regla de Dos Personas

### 3.1 El problema

En zonas de alta criticidad (sala de servidores, cámara de seguridad, centro de procesamiento nuclear), nadie debe estar solo. Los riesgos:
- Una persona sola puede robar o sabotear sin testigos
- Una persona sola puede sufrir un accidente médico sin ayuda

La 2PR exige que siempre haya **al menos dos personas** en la zona. Consecuencias:
- Un usuario **no puede entrar** si es el único que va a entrar (la zona estaría con 1 persona)
- Un usuario **no puede salir** si es el último — dejaría a alguien solo

### 3.2 Conteo de ocupantes

bAuth mantiene el conteo de ocupantes de cada zona en tiempo real:

```sql
-- Vista de ocupantes activos por zona (derivada de audit_events)
SELECT
    metadata->>'zone_id' as zone_id,
    COUNT(*) as occupants
FROM bos.audit_events
WHERE entity_type = 'nexus_apb'
  AND action = 'zone_entry'
  AND metadata->>'position' = 'inside'
  -- Se excluyen los zone_exit correspondientes
GROUP BY metadata->>'zone_id';
```

### 3.3 Flujo 2PR — intento de entrada cuando zona tiene 0 ocupantes

```
Usuario A intenta entrar solo a zona 2PR (zona-servidor-01):

bAuth consulta: occupants('zona-servidor-01') = 0

Regla 2PR: entrar con 0 ocupantes actuales → 1 ocupante total → VIOLACIÓN
→ SAM-128 DENY con reason=2PR_MINIMUM_NOT_MET

bhnexus:
  → DENY al actuador (puerta no se abre)
  → LED rojo + mensaje en display OSDP: "Requiere compañía"
  → Alerta SIEM si se repite > 3 veces en 5 min
```

### 3.4 Flujo 2PR — intento de salida cuando quedaría 1 persona

```
Usuario A y B están dentro. Usuario A intenta salir:

bAuth consulta: occupants('zona-servidor-01') = 2

Regla 2PR: si A sale → 1 ocupante restante → VIOLACIÓN (B quedaría solo)
→ SAM-128 DENY con reason=2PR_WOULD_LEAVE_ALONE

bhnexus:
  → DENY (salida bloqueada)
  → Display OSDP: "No puede salir solo — espere compañía"
```

### 3.5 Excepción de emergencia

La 2PR tiene una excepción de emergencia configurable:
- Si la zona está en modo `emergency_exit=true` (activado por bOS), la 2PR se suspende
- Cualquier usuario puede entrar/salir independientemente
- Todas las excepciones se registran en audit_events con reason=emergency_override

## 4. Mantrap — Antecámara de Seguridad

### 4.1 El problema

El tailgating (colarse detrás de alguien) es el ataque más común en control de acceso físico: un atacante espera a que alguien abra la puerta con credencial válida y se cuela en el mismo movimiento.

Un mantrap es una antecámara con **dos puertas en secuencia**:

```
[EXTERIOR] → [Puerta A] → [ANTECÁMARA] → [Puerta B] → [ZONA PROTEGIDA]
```

**Regla**: solo una puerta puede estar abierta a la vez. Si la Puerta A está abierta, la Puerta B no puede abrirse hasta que la A se cierre y viceversa.

### 4.2 Configuración del mantrap en SBOSDB

El mantrap se declara en `idn_identity_entity` como una relación entre dos puntos de acceso:

```json
// En idn_identity_entity (tipo=access_point), metadata del mantrap:
{
  "mantrap": {
    "enabled": true,
    "partner_door_id": "PHY_DEV_PUERTA_B_CPD",
    "role": "door_a",          // "door_a" o "door_b"
    "max_open_seconds": 10,    // Puerta se cierra automáticamente tras 10s
    "antipassback_in_mantrap": true  // APB también aplica en la antecámara
  }
}
```

### 4.3 Flujo de Mantrap

```
Estado inicial: Puerta A CERRADA, Puerta B CERRADA

T+0ms   Usuario presenta credencial en Puerta A

T+8ms   bAuth evalúa: usuario tiene átomo physical_access.zona_cpd ✅
        Puerta B estado = CERRADA ✅ (condición mantrap)
        → SAM-128 GRANT

T+9ms   bhnexus activa Puerta A (OPEN, 10 segundos)
        Registra en estado mantrap: puerta_a=OPEN, puerta_b=LOCKED

T+10ms  Usuario entra a la antecámara, Puerta A se cierra (auto-close)
        Estado: puerta_a=CERRADA, puerta_b=CERRADA

T+11ms  Usuario presenta credencial en Puerta B

T+14ms  bAuth evalúa: usuario tiene átomo ✅
        Puerta A estado = CERRADA ✅ (condición mantrap OK)
        → SAM-128 GRANT

T+15ms  bhnexus activa Puerta B (OPEN)
        Usuario entra a la zona protegida
```

### 4.4 Intento de abrir Puerta B mientras Puerta A está abierta

```
Estado: puerta_a=OPEN (alguien entró y la puerta no cerró aún)

Otro usuario presenta credencial en Puerta B:

bAuth consulta estado mantrap de puerta_b:
  partner_door_id='puerta_a' → estado='OPEN'
  → Condición mantrap violada → DENY

bhnexus: DENY + alerta SIEM (posible tailgating)
         Display OSDP Puerta B: "Acceso no permitido — antecámara ocupada"
```

### 4.5 Estado del Mantrap en tiempo real

El estado (OPEN/CERRADA) de cada puerta de mantrap se trackea en memoria por bhnexus para evaluación O(1):

```rust
struct ManTrapState {
    door_a_open: bool,
    door_b_open: bool,
    last_entry_ts: Instant,
    user_in_trap: Option<Uuid>,  // UUID del usuario en la antecámara
}
```

bAuth consulta este estado via el payload del `bitmask_request` cuando detecta que el `device_id` tiene configuración mantrap.

## 5. Combinación de políticas

Las tres políticas pueden coexistir en la misma zona:

| Zona | APB | 2PR | Mantrap | Nivel seguridad |
|------|:---:|:---:|:-------:|:---------------:|
| Oficina general | Soft | ❌ | ❌ | sl=1 |
| Sala de reuniones confidencial | Hard | ❌ | ❌ | sl=2 |
| CPD (sala servidores) | Hard | ✅ | ✅ | sl=3 |
| Vault / cámara acorazada | Hard | ✅ | ✅ | sl=4 + step-up MFA |

Cuando hay conflicto entre políticas (por ejemplo, la 2PR bloquea la salida pero es una emergencia), prevalece el operador de seguridad con privilegio `nexus.policy.emergency_override`.
