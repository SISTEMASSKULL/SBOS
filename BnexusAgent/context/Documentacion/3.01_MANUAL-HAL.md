## 1. El principio declarativo

> **Agregar un dispositivo al SBOS es declarativo — no requiere código.**

Si el protocolo del dispositivo ya está soportado en los 6 drivers incluidos:
1. Registrar el dispositivo en SBOSDB (`bauth.auth_device` + `bauth.idn_identity_entity`)
2. Declarar los parámetros de conexión en `bhnexus.toml`
3. Reiniciar bhnexus — el HAL lo detecta y lo activa

Si el protocolo es nuevo:
1. Implementar el trait `DeviceDriver` en un nuevo crate Rust
2. Registrar el driver en `DriverRegistry`
3. El núcleo de bhnexus no se modifica

Esta separación es el contrato de extensibilidad del HAL.

## 2. Arquitectura del HAL

```
bhnexus (núcleo)
  │
  ├── DriverRegistry             ← mapa: protocol_name → Box<dyn DeviceDriver>
  │     ├── "osdp_v2"     → OsdpDriver
  │     ├── "wiegand"     → WiegandDriver
  │     ├── "mqtt"        → MqttDriver
  │     ├── "onvif"       → OnvifDriver
  │     ├── "usb_hid"     → UsbHidDriver  (solo para HAL directo; normalmente en banexus)
  │     └── "http"        → HttpDriver
  │
  ├── HAL EventBus              ← canal tokio::mpsc ilimitado
  │     │
  │     │  Todos los drivers producen CredentialEvent
  │     │  El EventBus los encola y los entrega al Authorization Handler
  │     ▼
  └── Authorization Handler     ← recibe CredentialEvent, consulta Auth Cache o bAuth
```

### Flujo de un evento desde el hardware

```
Hardware físico
  → Driver (protocol-specific) captura el evento bruto
  → Driver normaliza → CredentialEvent estándar
  → CredentialEvent enviado al EventBus (tokio channel)
  → Authorization Handler recibe el evento
  → Consulta Auth Cache (O(1) lookup por user_id + node_id)
  → Si miss: consulta bAuth por sub-canal A
  → Recibe SAM-128 + actuator_commands
  → ActuatorDispatcher ejecuta los comandos
  → audit_event emitido
```

## 3. El trait DeviceDriver

```rust
use async_trait::async_trait;
use tokio::sync::mpsc::Sender;

/// Trait que todo driver del HAL debe implementar.
/// Permite agregar nuevos protocolos sin modificar el núcleo de bhnexus.
#[async_trait]
pub trait DeviceDriver: Send + Sync {
    /// Identificador único del protocolo — debe coincidir con la clave en DriverRegistry
    /// Ejemplos: "osdp_v2", "mqtt", "wiegand", "onvif", "usb_hid", "http"
    fn protocol(&self) -> &str;

    /// Establece la conexión física o de red al dispositivo.
    /// Idempotente — llamar varias veces no duplica la conexión.
    async fn connect(&mut self, params: ConnectionParams) -> Result<(), DriverError>;

    /// Escucha eventos del dispositivo y los envía al EventBus.
    /// Retorna solo en error — es un loop perpetuo.
    async fn listen(&self, tx: Sender<CredentialEvent>) -> Result<(), DriverError>;

    /// Envía un comando al actuador del dispositivo (abrir relé, bloquear, etc.)
    async fn send_command(&self, cmd: ActuatorCommand) -> Result<(), DriverError>;

    /// Verifica el estado de salud del driver y del dispositivo.
    /// Llamado cada 30s por el Health Monitor.
    fn health_check(&self) -> DeviceHealth;

    /// Cierra la conexión limpiamente.
    async fn disconnect(&mut self) -> Result<(), DriverError>;
}
```

## 4. El CredentialEvent — lenguaje universal del HAL

Todos los drivers producen exactamente este tipo. El Authorization Handler no sabe qué protocolo generó el evento — solo procesa `CredentialEvent`.

```rust
/// Evento de credencial normalizado — producido por cualquier driver del HAL.
/// Es el lenguaje universal entre el hardware y el motor de autorización.
pub struct CredentialEvent {
    /// Identificador único del evento (para dedup y correlación)
    pub event_id: Uuid,

    /// Timestamp de captura en el hardware (no de recepción en el driver)
    pub timestamp: DateTime<Utc>,

    /// Identificador del dispositivo en SBOSDB (idn_identity_entity.name)
    /// Ejemplo: "PHY_DEV_QR_ZV_PUERTA_PRIN"
    pub device_id: DeviceId,

    /// Identificador del punto de acceso que controla este dispositivo
    /// Ejemplo: "PHY_AP_ZV_PUERTA_PRIN"
    pub location_id: LocationId,

    /// Identificador del nodo banexus o HAL que capturó el evento
    /// Ejemplo: "Ventas-01"
    pub node_id: NodeId,

    /// Tipo de credencial capturada (QR, NFC, biométrico, etc.)
    pub credential_type: CredentialType,

    /// Payload cifrado con la clave de Vault del dispositivo.
    /// El Authorization Handler lo envía a bAuth para su verificación —
    /// el HAL nunca descifra el payload.
    pub payload: Bytes,

    /// Dirección de acceso — entrada o salida (para anti-passback)
    pub direction: Direction,

    /// Protocolo bruto original — solo para trazabilidad en audit_event
    /// Ejemplo: "osdp_v2", "wiegand", "mqtt"
    pub raw_protocol: String,
}
```

## 5. Los 6 drivers del HAL

| Driver | Protocolo | Dispositivos típicos | Seguridad | Iniciador |
|--------|-----------|---------------------|:---------:|:---------:|
| `OsdpDriver` | OSDP v2.2.2 (SIA/IEC 60839-11-5) | Lectores NFC, RFID, biométrico, teclados, cerraduras | Alto | bhnexus |
| `WiegandDriver` | Wiegand 26/34/37-bit | Lectores legacy (infraestructura de 40+ años) | Bajo | bhnexus |
| `MqttDriver` | MQTT 5.0 + TLS | Sensores IoT, actuadores industriales, alarmas | Alto | Dispositivo |
| `OnvifDriver` | ONVIF Profile S/T/C | Cámaras IP, videoporteros | Medio | bhnexus |
| `UsbHidDriver` | USB HID + udev | Lectores QR USB, NFC USB (en banexus) | Alto | banexus local |
| `HttpDriver` | REST HTTPS + mTLS | Terminales POS, interfonos IP, kioskos | Alto | Configurable |

Ver `3.02_MANUAL-DRIVERS.md` para el protocolo detallado de cada driver.

## 6. ConnectionParams — configuración por driver

```rust
/// Parámetros de conexión para un driver del HAL.
/// Se leen de bhnexus.toml en la sección [[hal.devices]].
pub struct ConnectionParams {
    /// Protocolo del driver — selecciona qué driver instanciar
    pub protocol: String,

    /// Identificador del dispositivo en SBOSDB
    pub device_id: String,

    /// Dirección de conexión (IP, puerto serie, topic MQTT, URL REST, etc.)
    pub address: String,

    /// Parámetros específicos del protocolo (como HashMap<String, String>)
    pub extra: HashMap<String, String>,

    /// Tiempo de espera para operaciones de conexión (ms)
    pub connect_timeout_ms: u64,

    /// Intervalo de retry si la conexión falla (ms)
    pub retry_interval_ms: u64,
}
```

### Ejemplo de configuración en bhnexus.toml

```toml
[[hal.devices]]
protocol    = "osdp_v2"
device_id   = "PHY_DEV_OSDP_ENTRADA"
address     = "/dev/ttyUSB0"            # puerto serie RS-485
extra       = { osdp_address = "1", baud_rate = "9600" }
connect_timeout_ms  = 5000
retry_interval_ms   = 30000

[[hal.devices]]
protocol  = "mqtt"
device_id = "PHY_DEV_SENSOR_RACK01"
address   = "mqtts://10.0.1.10:8883"
extra     = { topic = "sbos/sensors/rack01/access", qos = "1" }

[[hal.devices]]
protocol  = "wiegand"
device_id = "PHY_DEV_WIEGAND_ESTACIONAMIENTO"
address   = "/dev/gpiochip0"
extra     = { data0_pin = "17", data1_pin = "27" }
```

## 7. ActuatorCommand — comandos de salida del HAL

El HAL también tiene la dirección inversa: recibir comandos desde el Authorization Handler y ejecutarlos en el hardware.

```rust
/// Comando enviado a un actuador físico.
/// Generado por bAuth en el actuator_commands del bitmask_response.
pub struct ActuatorCommand {
    /// Identificador del actuador en el nodo (RELAY_01, DRAWER_01, LOCK_01, etc.)
    pub target: String,

    /// Acción a ejecutar
    pub action: ActuatorAction,

    /// Duración de la acción en ms (solo para PULSE — abre y cierra automáticamente)
    pub duration_ms: Option<u64>,
}

pub enum ActuatorAction {
    Open,    // abrir (cerradura, barrera, válvula)
    Close,   // cerrar
    Pulse,   // open(duration_ms) → close automático
    Toggle,  // invertir estado
    Alarm,   // activar alarma (en dispositivos con alarma integrada)
}
```

## 8. DeviceHealth — monitoreo de salud

```rust
/// Estado de salud reportado por cada driver.
pub struct DeviceHealth {
    pub device_id:     String,
    pub status:        HealthStatus,
    pub last_event_ts: Option<DateTime<Utc>>,
    pub error_count:   u32,
    pub details:       String,
}

pub enum HealthStatus {
    Ok,
    Degraded,   // conectado pero con errores intermitentes
    Offline,    // sin conexión
    Unknown,    // nunca se ha conectado desde el arranque
}
```

bhnexus publica métricas de salud del HAL en Prometheus:
- `bhnexus_hal_device_status` (gauge) — 1=Ok, 0=Offline
- `bhnexus_hal_event_total` (counter) — total de eventos capturados por device_id
- `bhnexus_hal_error_total` (counter) — total de errores por device_id + error_type

## 9. Anti-replay en el HAL

Cada `CredentialEvent` tiene un `event_id` (Uuid v4 generado por el driver). El Authorization Handler mantiene un bloom filter de los últimos 10.000 `event_id` procesados (ventana de 60s). Si el mismo `event_id` llega dos veces en la ventana → el segundo se descarta con `duplicate_event: true` en el log.

Esto previene que un atacante que pueda inyectar un evento en la red interna repita un acceso previo.
