# 5.03 — Offline y Fail-Secure en bNexus
## Comportamiento ante pérdida de conectividad — tres escenarios, reglas definitivas

**Versión:** 1.0.0  
**Fecha:** 2026-08-04  
**Fuente:** SBOS-NEXUS-CONCEPTUALIZACION-v3_0.md §13  
**Carta rectora:** `0.00_MANUAL-DIRECTRICES-NEXUS.md`

## 1. El principio rector

> **En bNexus, la incertidumbre sobre el estado de autorización se resuelve denegando acceso.**

Esto se llama **fail-secure** (o fail-closed): cuando no hay certeza de si un acceso es legítimo, la decisión por defecto es denegar. No hay acceso "por defecto permitido" cuando el sistema no puede verificar.

La única excepción es la física: puertas de emergencia/evacuación. Esas puertas tienen `fail_mode = fail_safe` a nivel de hardware — se abren mecánicamente sin corriente, independientemente de lo que decida el software.

---

## 2. Los tres escenarios de offline

bNexus tiene tres capas de conectividad. Cada capa puede fallar independientemente:

```
Capa 1: banexus ↔ bhnexus (Puerta 1 — WebSocket mTLS, TCP 9444)
Capa 2: bhnexus ↔ bAuth   (Puerta 2 — Unix socket TLV, sub-canal A)
Capa 3: bAuth   ↔ SBOSDB  (PostgreSQL — acceso a la base de datos)
```

---

## 3. Escenario 1 — banexus pierde conexión con bhnexus

### Causa
Red caída, bhnexus reiniciando, fallo de TCP 9444.

### Comportamiento de banexus

```
Estado: banexus detecta pérdida de conexión (PING sin PONG en 60s)

Acción inmediata:
  → Activa S-02 (backoff exponencial: 1s → 5s → 15s → 30s → 60s)
  → Entra en modo OFFLINE

Modo OFFLINE — reglas de autorización:
  ┌─────────────────────────────────────────────────────────────┐
  │  SI el Policy Cache local está VIGENTE (< 4h de antigüedad) │
  │    → Evalúa la credencial contra el cache local             │
  │    → Tipos de credencial aceptados en modo offline:         │
  │       ✅ NFC DESFire (con entry válida en cache)            │
  │       ✅ Smartcard X.509 (cert no expirado + entry en cache)│
  │       ✅ PIN (hash en cache)                                │
  │       ✅ RFID Wiegand (mapping en cache)                    │
  │       ❌ QR Dinámico (requiere HMAC-key online de bAuth)    │
  │       ❌ Biométrico (requiere hash-compare online en bAuth) │
  │       ✅ BLE Aliro (offline token del SDK vigente)          │
  │                                                             │
  │  SI el Policy Cache local está EXPIRADO (> 4h)             │
  │    → DENY a TODA credencial sin excepción                  │
  │    → Razón: policy_cache_expired                           │
  └─────────────────────────────────────────────────────────────┘

Auditoría durante offline:
  Cada decisión se registra localmente con:
    offline_mode: true
    bhnexus_unavailable: true
    cache_age_s: <segundos desde creación del cache>
  Al reconectar: los eventos se envían a bhnexus para forwarding a bAuth
```

### Cuándo termina el escenario 1

```
banexus reconecta → S-02 exitoso → S-01 (handshake)
  → Policy Cache refrescado desde bhnexus
  → node_online enviado al canal B (con estadísticas offline)
  → Modo ONLINE restaurado
```

## 4. Escenario 2 — bhnexus pierde conexión con bAuth

### Causa
bAuth reiniciando, SBOSDB caído, socket bauth.sock no responde.

### Comportamiento de bhnexus

```
Estado: bhnexus intenta consultar bAuth por sub-canal A, timeout 1000ms

Timeout detectado:
  → bhnexus intenta reconectar al socket /run/bos/bauth.sock
  → Reintentos: cada 5s (hasta reconexión)

Comportamiento con los agentes banexus durante este período:

  CASO A: Usuario en Auth Cache de bhnexus (entry < 30s TTL)
    → bhnexus responde desde el cache: GRANT con el SAM-128 almacenado
    → Sin consulta a bAuth (eso es exactamente el propósito del cache)
    → Latencia < 0.1ms (sin I/O)

  CASO B: Usuario NO en Auth Cache (cache miss o TTL expirado)
    → bhnexus NO puede consultar bAuth
    → bhnexus retorna DENY:
    {
      "status": "denied",
      "deny_reason": "auth_service_unavailable",
      "deny_message": "Servicio de autenticación temporalmente no disponible.",
      "retry_after_ms": 5000
    }
    → banexus emite el DENY al hardware (puerta no abre)
    → banexus registra el evento con auth_service_unavailable: true

  CASO C: Auth Cache completamente vacío (arranque de bhnexus)
    → DENY a todos los accesos
    → bhnexus no puede operar sin bAuth al menos una vez (primer arranque)
```

### Cuándo termina el escenario 2

```
bAuth vuelve a estar disponible:
  → bhnexus detecta que el socket responde
  → Las consultas pendientes (en queue) se procesan en orden
  → Auth Cache se rehidrata en los próximos accesos
```

## 5. Escenario 3 — bAuth pierde acceso a SBOSDB

### Causa
PostgreSQL caído, red K8s fallando, SBOSDB inalcanzable desde bAuth.

### Comportamiento en cascada

```
bAuth no puede consultar SBOSDB:
  → bAuth no puede evaluar nuevos bitmask_request (necesita la BD para el rol del usuario)
  → bAuth puede responder DESDE SU PROPIO CACHE REDIS (si está habilitado y vigente)
  → Si Redis también falla o no tiene la entrada: retorna bitmask_error

bhnexus recibe bitmask_error:
  → Aplica el CASO B del Escenario 2 (DENY con auth_service_unavailable)

banexus durante el Escenario 3:
  → Recibe DENY de bhnexus
  → Puede usar su Policy Cache local si está vigente (idem Escenario 1)
```

### La cadena de resiliencia completa

```
SBOSDB caído
  → bAuth: ¿Redis cache? → Sí (vigente): responde desde Redis (no es un fallo completo)
                         → No: retorna bitmask_error
  → bhnexus: ¿Auth Cache? → Sí (< 30s TTL): responde desde Auth Cache
                           → No: DENY (auth_service_unavailable)
  → banexus: ¿Policy Cache? → Sí (< 4h TTL): responde desde Policy Cache
                             → No: DENY (policy_cache_expired)
```

## 7. Primer arranque (no hay cache)

El primer arranque de cualquier componente siempre requiere el siguiente componente disponible:

```
banexus primer arranque → DEBE poder conectar a bhnexus (S-01)
  → No hay cache local → sin conexión = DENY total (fail-secure)
  → El operador debe asegurarse de que bhnexus esté online en el primer arranque

bhnexus primer arranque → DEBE poder consultar bAuth (sub-canal A)
  → No hay Auth Cache → sin bAuth = DENY total para todos los usuarios
  → bOS verifica que bAuth esté operativo antes de arrancar bhnexus

bAuth primer arranque → DEBE poder conectar a SBOSDB
  → No hay estado en memoria → sin SBOSDB = error de arranque
  → systemd reinicia bAuth hasta que SBOSDB esté disponible
```

Esta regla se llama **"first startup must be online"** — el sistema no arranca en modo degradado desde cero. Solo puede entrar en modo degradado DESPUÉS de haber tenido al menos una sesión online exitosa.

## 8. Fail-safe vs fail-secure en hardware

La distinción hardware no es una decisión de bNexus — es física:

```
Cerradura fail_secure (la mayoría):
  → Sin corriente → permanece cerrada
  → Si banexus dice DENY → sin corriente → cerrada
  → Si banexus está apagado → sin corriente → cerrada
  → Máxima seguridad: nadie entra sin verificación

Cerradura fail_safe (puertas de emergencia):
  → Sin corriente → se abre (spring bolt retrae)
  → Si banexus dice DENY → la puerta SIGUE ABRIENDO si se empuja
  → Si banexus está apagado → la puerta abre sin resistencia
  → Máxima evacuación: nadie queda atrapado

REGLA: banexus NO tiene autoridad sobre fail_safe.
  banexus puede emitir DENY para la sesión del usuario.
  Pero no puede cerrar físicamente una puerta fail_safe.
  Son dos sistemas independientes: software (banexus) y hardware (cerradura).
```

## 9. Métricas de disponibilidad objetivo

```
bhnexus disponibilidad objetivo:    99.9% (< 8.7h/año offline)
banexus modo online objetivo:       99.5% (< 43h/año offline)
banexus modo degradado (cache):     0.4% del tiempo (sin afectar operación para usuarios en cache)
DENY total por cache expirado:      < 0.1% del tiempo

Estos objetivos se miden por zona, no globalmente.
Una sucursal sin internet puede tener más tiempo offline — se dimensiona el cache en consecuencia.
```
