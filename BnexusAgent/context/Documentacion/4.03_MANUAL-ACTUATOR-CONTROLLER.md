## 1. Responsabilidad del Actuator Controller

El Actuator Controller es el componente de banexus que **ejecuta físicamente los comandos de actuación** sobre el hardware local de la workstation o POS. Opera en el extremo final de la cadena de autorización:

```
bAuth (PDP)
  ↓ SAM-128 + actuator_commands
bhnexus (broker)
  ↓ auth_response con actuator_commands
banexus
  ↓ [Actuator Controller]
Hardware físico (cerradura, cajón de dinero, barrera, alarma)
```

El Actuator Controller nunca genera sus propios comandos. Solo ejecuta los `ActuatorCommand[]` que llegaron en el `auth_response` de bhnexus, originados en bAuth.

---

## 2. Protocolos de actuación soportados

| Protocolo | Uso típico | Hardware conectado |
|-----------|-----------|-------------------|
| **RS-232 (serial)** | Cerraduras electromagnéticas, relés seriales | Puerto COM, adaptador USB-Serial |
| **GPIO (sysfs / libgpiod)** | Relés directos, pines de control | GPIO pins del SBC (Raspberry Pi, etc.) |
| **HTTP REST** | Actuadores IP (cerraduras WiFi, barreras IP) | Red LAN |
| **OSDP output** | Cerradura en el mismo bus OSDP del lector | RS-485 (compartido con driver OSDP) |

## 3. RS-232 — Protocolo de comunicación con relés seriales

### 3.1 Formato de trama

banexus usa un protocolo binario minimalista sobre RS-232 para controlar relés:

```
Trama de comando (3 bytes):
  Byte 0: 0x01 (cabecera fija — identifica trama de control)
  Byte 1: relay_id (0x01 a 0xFF — número del relé)
  Byte 2: action   (0x01 = OPEN / 0x00 = CLOSE)

Ejemplo — Abrir relé 1:  [0x01, 0x01, 0x01]
Ejemplo — Cerrar relé 2: [0x01, 0x02, 0x00]
```

### 3.2 Parámetros de conexión

```toml
[actuators.serial]
port      = "/dev/ttyUSB0"   # o /dev/ttyS0 para puerto COM nativo
baud_rate = 9600
data_bits = 8
stop_bits = 1
parity    = "none"
timeout_ms = 500              # tiempo máximo de write
```

### 3.3 Implementación de ejecución

```rust
/// Ejecuta un comando sobre un relé conectado por RS-232.
/// open_duration_ms: tiempo que permanece abierto antes del auto-close.
fn execute_relay_rs232(
    port: &str,
    relay_id: u8,
    action: ActuatorAction,
    open_duration_ms: u32,
    ctx_id: &str,
) -> Result<(), ActuatorError> {
    let mut port = serialport::new(port, 9600)
        .timeout(Duration::from_millis(500))
        .open()?;

    let cmd_byte: u8 = match action {
        ActuatorAction::Open  => 0x01,
        ActuatorAction::Close => 0x00,
        ActuatorAction::Pulse => 0x01,   // Pulse = Open + auto-close schedulado
        _ => return Err(ActuatorError::UnsupportedAction),
    };

    port.write_all(&[0x01, relay_id, cmd_byte])?;

    log::info!(
        ctx_id = ctx_id,
        relay_id = relay_id,
        action = ?action,
        "Comando relé RS-232 enviado"
    );

    // Auto-close schedulado si la acción es Open o Pulse
    if matches!(action, ActuatorAction::Open | ActuatorAction::Pulse) && open_duration_ms > 0 {
        schedule_auto_close(port.to_string(), relay_id, open_duration_ms, ctx_id.to_string());
    }

    Ok(())
}
```

## 4. GPIO — Control directo de pines

### 4.1 Cuándo usar GPIO

GPIO (General Purpose Input/Output) se usa cuando el hardware físico se controla con una señal eléctrica directa en un pin del SBC (Single Board Computer como Raspberry Pi). Típico en banexus-gateway.

```toml
[[actuators.devices]]
id          = "RELAY_GPIO_01"
type        = "gpio_relay"
gpio_pin    = 17              # pin BCM en Raspberry Pi
active_high = true            # true = nivel alto = OPEN; false = inverso
```

### 4.2 Implementación via libgpiod

```rust
/// Activa o desactiva un pin GPIO.
fn execute_gpio(
    gpio_pin: u8,
    active_high: bool,
    action: ActuatorAction,
    open_duration_ms: u32,
    ctx_id: &str,
) -> Result<(), ActuatorError> {
    let chip = gpiod::Chip::open("/dev/gpiochip0")?;
    let line = chip.get_line(gpio_pin as u32)?;
    let handle = line.request(
        gpiod::LineRequestFlags::OUTPUT,
        if active_high { 0 } else { 1 },   // estado inicial = cerrado
        "banexus",
    )?;

    let value: i32 = match (action, active_high) {
        (ActuatorAction::Open | ActuatorAction::Pulse, true)  => 1,
        (ActuatorAction::Open | ActuatorAction::Pulse, false) => 0,
        (ActuatorAction::Close, true)  => 0,
        (ActuatorAction::Close, false) => 1,
        _ => return Err(ActuatorError::UnsupportedAction),
    };

    handle.set_value(value)?;

    log::info!(ctx_id = ctx_id, gpio_pin = gpio_pin, value = value, "GPIO activado");

    if matches!(action, ActuatorAction::Open | ActuatorAction::Pulse) && open_duration_ms > 0 {
        schedule_gpio_auto_close(gpio_pin, active_high, open_duration_ms, ctx_id.to_string());
    }

    Ok(())
}
```

## 5. HTTP REST — Actuadores IP

Para cerraduras WiFi o barreras vehiculares con API REST propia:

```toml
[[actuators.devices]]
id       = "CERRADURA_IP_01"
type     = "http_relay"
url      = "https://cerradura-ip.local/api/unlock"
method   = "POST"
headers  = { Authorization = "Bearer <token-local>" }
body_template = '{"action": "{{action}}", "duration_ms": {{duration_ms}}, "ctx_id": "{{ctx_id}}"}'
timeout_ms = 3000
```

```rust
fn execute_http(device: &HttpActuatorConfig, action: ActuatorAction, ctx_id: &str) -> Result<()> {
    let body = device.body_template
        .replace("{{action}}", &format!("{:?}", action).to_lowercase())
        .replace("{{duration_ms}}", &device.default_duration_ms.to_string())
        .replace("{{ctx_id}}", ctx_id);

    let resp = reqwest::blocking::Client::new()
        .request(device.method.into(), &device.url)
        .headers(device.headers.clone())
        .body(body)
        .timeout(Duration::from_millis(device.timeout_ms))
        .send()?;

    if !resp.status().is_success() {
        return Err(ActuatorError::HttpError(resp.status()));
    }
    Ok(())
}
```

## 6. Auto-close — Cierre automático temporizador

Toda apertura de actuador en banexus tiene un temporizador de cierre automático. Esto garantiza que ninguna puerta o relé quede abierto indefinidamente si ocurre un error.

### 6.1 Funcionamiento del timer

```rust
/// Schedula el cierre automático de un actuador tras open_duration_ms.
/// El cierre se ejecuta incluso si banexus pierde la conexión con bhnexus.
fn schedule_auto_close(
    device_id: String,
    open_duration_ms: u32,
    ctx_id: String,
) {
    tokio::spawn(async move {
        tokio::time::sleep(Duration::from_millis(open_duration_ms as u64)).await;

        // Ejecutar cierre — siempre, independientemente del estado de conexión
        if let Err(e) = execute_close(&device_id, &ctx_id).await {
            log::error!(
                ctx_id = ctx_id,
                device_id = device_id,
                error = ?e,
                "CRÍTICO: Fallo en auto-close — verificar estado físico del actuador"
            );
            // Alerta SIEM: actuador posiblemente abierto sin cierre
            emit_siem_alert("actuator_autoclose_failed", &device_id, &ctx_id);
        }
    });
}
```

### 6.2 Valores de duración por tipo de actuador

| Actuador | Default `open_duration_ms` | Máximo configurable |
|---------|:--------------------------:|:--------------------:|
| Cerradura de puerta | 5,000ms (5s) | 30,000ms (30s) |
| Cajón de dinero | 3,000ms (3s) | 10,000ms (10s) |
| Barrera vehicular | 10,000ms (10s) | 60,000ms (60s) |
| Torniquete | 2,000ms (2s) | 5,000ms (5s) |
| Relé auxiliar (alarma) | N/A (manual close) | Sin límite |

La duración es dictada por bAuth en los `actuator_commands`. banexus respeta ese valor pero **nunca supera el máximo configurado** en banexus.toml como medida de seguridad.

## 7. Estado del actuador — tracking en memoria

banexus mantiene el estado de cada actuador en memoria para:
- Evitar comandos duplicados (idempotencia)
- Reportar estado real en el heartbeat hacia bhnexus
- Detectar inconsistencias (actuador debería estar cerrado pero el sensor dice abierto)

```rust
struct ActuatorState {
    device_id:       String,
    current_state:   ActuatorStatus,   // Open | Closed | Unknown
    last_command_ts: Instant,
    last_ctx_id:     String,
    auto_close_at:   Option<Instant>,  // Some(ts) si hay auto-close pendiente
}

enum ActuatorStatus {
    Open,
    Closed,
    Unknown,   // Estado al arrancar — antes del primer comando
}
```

### 7.1 Heartbeat con estado de actuadores

El estado de cada actuador se incluye en el heartbeat hacia bhnexus:

```json
{
  "type":           "heartbeat",
  "node_id":        "Ventas-01",
  "uptime_seconds": 86400,
  "actuators": {
    "RELAY_01":     {"state": "closed", "last_cmd_ts": "2026-08-04T10:14:55Z"},
    "DRAWER_01":    {"state": "closed", "last_cmd_ts": "2026-08-04T10:14:55Z"},
    "CERRADURA_01": {"state": "open",   "auto_close_in_ms": 2341}
  }
}
```

## 8. Manejo de errores

| Error | Comportamiento | Alerta |
|-------|---------------|--------|
| Timeout write RS-232 (>500ms) | Reintento una vez; si falla → log ERROR | Heartbeat marca actuador como `error` |
| GPIO pin no disponible | Log ERROR + intento alternativo si hay fallback | SIEM alert |
| HTTP 4xx/5xx | Log ERROR; no reintento | SIEM si es cerradura crítica |
| 3 fallos consecutivos en mismo actuador | Alerta en heartbeat → bhnexus → bAuth | Wazuh alerta de hardware |
| Fallo en auto-close | Log CRITICAL + SIEM | Operador debe verificar estado físico |

## 10. Propagación del ctx_id

Cada comando de actuación propaga el ctx_id del `auth_response` original:

```
auth_request (banexus → bhnexus)          ctx_id: "00-trace-span-01"
  → bAuth evalúa
  → auth_response (bhnexus → banexus)     ctx_id: "00-trace-span-01"
    → actuator_command ejecutado          ctx_id: "00-trace-span-01" (mismo)
      → audit_event en SBOSDB            ctx_id: "00-trace-span-01" (trazable)
```

Esto permite reconstruir el recorrido completo en bsearch: desde que se presentó la credencial hasta que se abrió la cerradura, pasando por cada capa.
