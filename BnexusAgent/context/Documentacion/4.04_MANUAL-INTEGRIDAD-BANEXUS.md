## 1. El problema: un agente de borde modificado

banexus es el agente que controla el hardware físico — cerraduras, cajones de dinero, barreras vehiculares. Si un atacante puede modificar el binario de banexus, puede:

- Hacer que abra puertas sin credencial
- Suprimir el registro de auditoría de accesos
- Retransmitir credenciales capturadas a un servidor externo
- Hacer pasar un GRANT por cualquier credencial arbitraria

El Integrity Monitor de banexus existe para detectar que el binario en disco fue modificado y tomar acción antes de que el binario comprometido procese la siguiente credencial.

---

## 2. Arquitectura del Integrity Monitor

```
banexus (proceso en ejecución)
  │
  └── Integrity Monitor (hilo separado, spawn al arrancar)
        │
        │  Cada 5 minutos (configurable):
        ▼
  1. Calcular SHA-256 del binario en disco:
     actual_hash = sha256_file("/opt/banexus/banexus")

  2. Comparar contra el hash canónico:
     expected_hash = read("/etc/banexus/banexus.sha256")
                     + firmado por bOS (Ed25519 Vault PKI)

  3a. Si match → OK: log DEBUG, heartbeat.integrity_ok = true

  3b. Si discrepancia → ALERTA CRÍTICA:
     - Emite device_tamper → bhnexus → bAuth (canal B)
     - Log CRITICAL en journald con SHA256 real vs esperado
     - Alerta SIEM vía Wazuh syslog
     - Auto-shutdown: process::exit(1) con código 99
```

## 3. El hash canónico y su cadena de custodia

### Generación del hash (durante la instalación/actualización)

```bash
# bOS genera el hash durante el provisioning del nodo
sha256sum /opt/banexus/banexus | awk '{print $1}' > /etc/banexus/banexus.sha256

# bAuth firma el hash con Ed25519 (Vault PKI)
vault write pki/bauth/sign-node \
    node_id="<node_id>" \
    hash=$(cat /etc/banexus/banexus.sha256) \
    common_name="banexus-integrity-<node_id>"

# La firma se almacena junto al hash
# /etc/banexus/banexus.sha256         — hash SHA-256 del binario
# /etc/banexus/banexus.sha256.sig     — firma Ed25519 de bAuth
```

### Verificación de la firma (durante el chequeo)

```rust
/// Verifica la integridad de banexus:
/// 1. Calcula el hash actual del binario
/// 2. Compara con el hash canónico
/// 3. Verifica que el hash canónico esté firmado por bAuth (Vault PKI)
fn verify_integrity(binary_path: &Path, hash_path: &Path, sig_path: &Path) -> IntegrityResult {
    // Calcular hash del binario en disco
    let actual_hash = sha256_file(binary_path)?;

    // Leer el hash canónico esperado
    let expected_hash = read_to_string(hash_path)?.trim().to_string();

    // Verificar firma del hash canónico (previene que un atacante reemplace
    // el hash junto con el binario)
    let sig = read(sig_path)?;
    let vault_public_key = load_vault_public_key()?;  // de /etc/banexus/vault_ca.pem
    verify_ed25519(&vault_public_key, expected_hash.as_bytes(), &sig)?;

    if actual_hash == expected_hash {
        IntegrityResult::Ok
    } else {
        IntegrityResult::Compromised {
            actual: actual_hash,
            expected: expected_hash,
        }
    }
}
```

**Sin la firma del hash canónico**, un atacante que tiene acceso al host podría:
1. Reemplazar `/opt/banexus/banexus` con su versión maliciosa
2. Calcular el SHA-256 de su versión maliciosa
3. Sobrescribir `/etc/banexus/banexus.sha256` con el nuevo hash

El hash canónico firmado por bAuth (Ed25519) rompe este ataque: el atacante no puede generar una firma válida sin la clave privada de Vault.

## 4. El heartbeat como canal de integridad continua

banexus envía un `heartbeat` a bhnexus cada 30 segundos. El heartbeat incluye el campo `integrity_ok`:

```json
{
  "type":            "heartbeat",
  "node_id":         "Ventas-01",
  "uptime_seconds":  86400,
  "active_sessions": 2,
  "cache_entries":   3,
  "last_auth_ts":    "2026-08-04T08:30:00Z",
  "integrity_ok":    true,
  "last_check_ts":   "2026-08-04T08:28:00Z"
}
```

Si bhnexus recibe un heartbeat con `integrity_ok: false`:
- Emite `device_tamper` al canal B → bAuth
- bAuth puede emitir `blacklist_node` para ese nodo (banexus ya se apagó, pero previene reconexión)
- Alerta SIEM (Wazuh)

Si bhnexus deja de recibir heartbeats de un nodo (más de 90s sin heartbeat):
- Asume que el nodo se apagó (por auto-shutdown u otra causa)
- Emite `node_offline` → canal B → bAuth
- bAuth registra el nodo como offline

## 5. Auto-shutdown — proceso de cierre de emergencia

Cuando el Integrity Monitor detecta una discrepancia de hash:

```rust
fn emergency_shutdown(actual: &str, expected: &str) {
    // 1. Log CRITICAL inmediato (antes de cualquier otra acción)
    log::error!(
        "INTEGRIDAD COMPROMETIDA — banexus será detenido. \
         Hash actual: {} | Hash esperado: {}",
        actual, expected
    );

    // 2. Emitir device_tamper al canal B (no bloqueante — best-effort)
    // Si bhnexus no responde, el shutdown continúa igual
    let _ = emit_device_tamper(actual, expected);

    // 3. Alerta SIEM vía syslog (Wazuh la recoge)
    syslog::alert!(facility::SECURITY,
        "banexus_integrity_breach node_id={} actual_hash={} expected_hash={}",
        NODE_ID, actual, expected
    );

    // 4. Terminar inmediatamente con código 99 (distinguible de crash normal)
    // Todos los hilos son terminados — no se aceptan nuevas credenciales
    std::process::exit(99);
}
```

### Código de salida 99

systemd está configurado para NO reiniciar banexus cuando sale con código 99:

```ini
# /etc/systemd/user/banexus.service
[Service]
ExecStart=/opt/banexus/banexus
Restart=on-failure
RestartPreventExitStatus=99    # código 99 = NO reiniciar (compromiso detectado)
```

Esto previene que systemd reinicie automáticamente un banexus comprometido. El operador debe intervenir manualmente para:
1. Verificar qué modificó el binario
2. Restaurar el binario original desde un repositorio de confianza
3. Verificar que el hash coincide con el firmado por bAuth
4. Reiniciar manualmente el servicio

## 6. Protección del directorio de instalación

```bash
# Permisos del directorio de banexus
/opt/banexus/         drwxr-x--- root banexus
/opt/banexus/banexus  -r-xr-x--- root banexus   # el binario es READ-ONLY
                                                  # incluso para el grupo banexus

/etc/banexus/         drwxr-x--- root banexus
/etc/banexus/banexus.sha256     -r--r----- root banexus
/etc/banexus/banexus.sha256.sig -r--r----- root banexus
/etc/banexus/vault_ca.pem       -r--r----- root banexus
```

El binario `/opt/banexus/banexus` tiene permisos `r-xr-x---` — no es escribible por root ni por el grupo banexus. Para modificarlo se necesita:
1. Acceso root + capacidad de modificar permisos (requeriría `chmod` previo)
2. El `chmod` quedaría registrado en los logs del sistema

## 7. Verificación en el arranque

Antes de que banexus comience a aceptar conexiones, ejecuta una verificación de integridad inicial:

```rust
fn main() {
    // 1. Verificación de integridad antes de arrancar
    match verify_integrity(BINARY_PATH, HASH_PATH, SIG_PATH) {
        IntegrityResult::Ok => {
            log::info!("Verificación de integridad OK — arrancando banexus");
        }
        IntegrityResult::Compromised { actual, expected } => {
            // No se puede notificar a bhnexus porque aún no estamos conectados
            // Se loguea y se termina ANTES de abrir ningún socket o conexión
            log::error!("Verificación inicial de integridad FALLIDA — abortando arranque");
            syslog::alert!(...);
            std::process::exit(99);
        }
    }

    // 2. Solo si la verificación fue OK, continúa el arranque
    // ...
}
```

Esto previene que un binario modificado arranque incluso por primera vez.

## 8. Reglas Wazuh para banexus

banexus emite logs estructurados a syslog (facility=SECURITY). Wazuh los captura con estas reglas:

```xml
<!-- /etc/wazuh/rules/banexus.xml -->

  <decoded_as>syslog</decoded_as>
  <match>banexus_integrity_breach</match>
  <description>CRÍTICO: Integridad de banexus comprometida — binary hash mismatch</description>
  <group>pci_dss_11.5,hipaa_164.312.b,gdpr_IV_35.7.d,iso_27001_A.12.2.1</group>

<rule id="100201" level="12">
```

## 9. Parámetros de configuración

```toml
[integrity]
enabled           = true
check_interval_s  = 300        # 5 minutos entre verificaciones
binary_path       = "/opt/banexus/banexus"
hash_path         = "/etc/banexus/banexus.sha256"
sig_path          = "/etc/banexus/banexus.sha256.sig"
vault_ca_pem      = "/etc/banexus/vault_ca.pem"
auto_shutdown     = true        # si false: alerta pero no se apaga (no recomendado)

[integrity.siem]
syslog_facility   = "SECURITY"
syslog_level      = "ALERT"
wazuh_integration = true
```
