## 1. La misión de bNexus

**bNexus traduce la autoridad de identidad de bAuth en eventos físicos.**

Cuando bAuth dice GRANTED, bNexus abre una puerta, libera un cajón, activa un relé. Cuando dice DENIED, bNexus niega — sin excepciones. bNexus no evalúa políticas, no emite tokens, no toma decisiones de identidad. Recibe decisiones de bAuth y las materializa en el hardware en menos de 50ms.

---

## 2. Las tres capas

bNexus no es un solo daemon. Es un **motor de tres capas** que operan como una sola entidad funcional:

```
┌─────────────────────────────────────────────────────────────────────────┐
│  CAPA 1 — bAuth                                                          │
│  Decide. Motor PDP nativo (ADR-010). Fuente de verdad de identidad.      │
│  "¿Puede este sujeto hacer esta operación en este contexto?"             │
│                                                                         │
│  /run/bos/bauth.sock          /run/bos/bauth-nexus.sock                 │
│         │ (Unix TLV)                    │ (canal privilegiado)          │
└─────────┼──────────────────────────────┼──────────────────────────────┘
          │                              │
┌─────────▼──────────────────────────────▼──────────────────────────────┐
│  CAPA 2 — bhnexus                                                        │
│  Ruta. Broker físico central. Auth Cache (SAM-128, TTL 30s). HAL.        │
│  "¿Quién conectó? ¿Está en cache? ¿Dónde va el comando?"               │
│                                                                         │
│  Puerto TCP 9444 · WebSocket mTLS                                       │
│         │ (Puerta 1)                                                    │
└─────────┼──────────────────────────────────────────────────────────────┘
          │
┌─────────▼──────────────────────────────────────────────────────────────┐
│  CAPA 3 — banexus  (cinco formas)                                        │
│  Actúa. Agente de borde. Captura credenciales. Ejecuta actuadores.       │
│  "Capturé una credencial. La envío. Ejecuto el comando que llega."      │
└─────────────────────────────────────────────────────────────────────────┘
```

Las tres capas son **tres daemons distintos** — tres binarios Rust MUSL independientes, tres servicios systemd, tres ciclos de vida. Su relación es de dependencia, no de fusión.

| Capa | Daemon | Tipo systemd | Puerto | Socket |
|------|--------|-------------|--------|--------|
| bAuth | `bauth.service` | system | 9450-9453 | `/run/bos/bauth.sock` |
| bhnexus | `bhnexus.service` | system | 9444-9447 | `/run/bos/bauth-nexus.sock` |
| banexus | `banexus.service` | --user | — | (cliente WebSocket) |

## 3. Las dos puertas

Las tres capas se comunican por dos puertas. Cada puerta tiene su protocolo y su dirección.

### Puerta 1 — banexus ↔ bhnexus

El canal de campo. Transporta:
- **banexus → bhnexus:** credenciales capturadas del mundo físico (`auth_request`, `heartbeat`)
- **bhnexus → banexus:** decisiones de bAuth y comandos de actuador (`auth_response`, `policy_update`)

| Aspecto | Valor |
|---------|-------|
| Transporte | WebSocket sobre TLS 1.3 |
| Autenticación mutua | mTLS (SPIFFE/SVID, CA interna SBOS) |
| Endpoint bhnexus | `wss://<host>:9444/ws` |
| Identidad de banexus | SVID X.509 — `spiffe://sbos.skull/agent/banexus/<node_id>` |
| Heartbeat | cada 30s desde banexus |
| Reconexión | backoff exponencial: 1→5→15→30→60s |
| Latencia objetivo total | < 50ms (credencial física → actuator ejecutado) |

### Puerta 2 — bhnexus ↔ bAuth

El canal de autoridad. Dos sub-canales con propósitos distintos:

**Sub-canal A — request/response (bitmask resolution):**

| Aspecto | Valor |
|---------|-------|
| Socket | `/run/bos/bauth.sock` |
| Iniciador | siempre bhnexus → bAuth |
| Framing | TLV: `[4 bytes uint32 BE: longitud][N bytes JSON UTF-8]` |
| Timeout | 1000ms · Pool: máx 100 conexiones concurrentes |
| Latencia objetivo | < 10ms |
| Cuándo se usa | Cache miss en bhnexus → consulta SAM-128 a bAuth |

**Sub-canal B — canal privilegiado (push bidireccional):**

| Aspecto | Valor |
|---------|-------|
| Socket | `/run/bos/bauth-nexus.sock` |
| Carácter | Persistente · bidireccional · latencia < 5ms |
| bAuth → bhnexus | `emergency_revoke`, `invalidate_cache`, `security_level_up`, `blacklist_node`, `policy_sync` |
| bhnexus → bAuth | `device_tamper`, `node_offline`, `auth_spike`, `hardware_failure`, `integrity_breach` |

## 4. La topología invariable

```
banexus (borde)
     │
     │ Puerta 1: WebSocket mTLS (SPIFFE/SVID)
     │
 bhnexus (central)
     │                    │
     │ Puerta 2A:         │ Puerta 2B:
     │ Unix TLV           │ Canal privilegiado
     │ (request/response) │ (push bidireccional)
     │                    │
 bAuth (fuente de verdad)
```

**Regla de topología — NUNCA:**

```
❌  banexus → bAuth           (saltar bhnexus = perder routing y cache)
❌  dispositivo → bhnexus     (saltar banexus = perder interceptación soberana)
❌  dispositivo → bAuth       (saltar ambas capas = perder toda la cadena)
❌  banexus → otro PDP        (bAuth es el único PDP del ecosistema — ADR-010)
```

**Justificación:** sin banexus no hay interceptación del evento USB/serial antes del SO. Sin bhnexus no hay cache, routing, ni distribución del SAM. Sin la topología estricta se rompe la cadena de custodia del evento de autenticación física.

## 5. El flujo soberano completo

```
T+0.000  Usuario presenta QR al lector USB en la workstation
T+0.001  banexus: udev hook intercepta el evento USB antes de evdev
T+0.002  banexus: construye auth_request + HMAC → envía por WebSocket (Puerta 1)
T+0.005  bhnexus: recibe, identifica el nodo (node_id del SPIFFE ID)
T+0.006  bhnexus: consulta Auth Cache → ¿cache hit?
          → SÍ (hit): T+0.007 → responde en < 1ms sin consultar bAuth
          → NO (miss): T+0.006 → consulta bAuth por Unix socket (Puerta 2A)
T+0.010  bAuth: evalúa RolTemplate + UserTemplate → genera SAM-128
T+0.012  bhnexus: almacena SAM-128 en Auth Cache (TTL 30s)
T+0.013  bhnexus: construye auth_response + actuator_commands → Puerta 1
T+0.014  banexus: recibe respuesta
T+0.015  banexus: ejecuta en paralelo:
          → Shell: libera sesión del usuario (si GRANTED)
          → Relay: envía pulso al cajón de dinero (si actuator_commands lo incluye)

TOTAL: ~15ms (objetivo < 50ms garantizado)
```

## 6. Posición en el ecosistema SBOS

bNexus es uno de los 8 daemons del ecosistema SBOS. Su posición es única: es el único daemon con presencia física en los nodos de borde.

| Daemon | Relación con bNexus |
|--------|---------------------|
| **bAuth** | Superior jerárquico — fuente de verdad de identidad, PDP |
| **bOS** | Instalador y gobernador — despliega bhnexus y banexus |
| **bkernel** | Receptor de eventos WAL — bhnexus registra cada acceso físico |
| **biedata** | Orquestador de datos — puede consultar eventos de acceso |
| **bsearch** | Motor de búsqueda — indexa eventos de autenticación |
| **bnotify** | Notificaciones — recibe alertas de hardware crítico |
| **bi18n** | Internacionalización — mensajes de error en el idioma del tenant |

**Canal con bAuth (bidireccional):**
- bhnexus consulta SAM-128 a bAuth en cada cache miss
- bAuth empuja revocaciones de emergencia y sincronización de políticas a bhnexus
- bhnexus reporta eventos de hardware crítico (tamper, nodo offline) a bAuth

## 7. Bhnexus — capacidades

| Capacidad | Descripción |
|-----------|-------------|
| **Router central** | Todo tráfico de credenciales físicas del SBOS pasa por bhnexus |
| **Auth Cache** | SAM-128 in-memory, TTL 30s, 10.000 entradas, LRU eviction |
| **Hardware Bridge** | HAL con 6 drivers: OSDP v2.2, MQTT 5.0, ONVIF Profile C, Wiegand, USB HID, HTTP |
| **Distribuidor de políticas** | Recibe policy_update de bAuth y propaga invalidación a banexus |
| **Canal privilegiado** | Bidireccional con bAuth: revocación emergencia, alertas hardware |

**Bhnexus NO puede:** tomar decisiones de identidad propias, modificar RolTemplates, autenticar directamente sin bAuth, almacenar templates biométricos.

## 9. Registro de identidades — en SBOSDB, no en YAML

Los nodos banexus y los dispositivos físicos controlados por bhnexus **no se registran en ficheros YAML ni en una base de datos propia de bNexus**. Se registran como entidades en SBOSDB:

```
bAuth → idn_identity_entity (árbol universal de 5 niveles)
  entity_type = 'banexus_node'   → nodo banexus registrado
  entity_type = 'osdp_reader'    → lector OSDP
  entity_type = 'nfc_reader'     → lector NFC
  entity_type = 'ip_camera'      → cámara ONVIF
  entity_type = 'iot_sensor'     → sensor MQTT
```

Para el detalle completo → `1.03_MANUAL-IDENTIDADES-NEXUS.md`.
