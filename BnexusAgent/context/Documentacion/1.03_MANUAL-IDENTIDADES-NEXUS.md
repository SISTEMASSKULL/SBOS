## 1. Principio fundamental

Los nodos banexus, los lectores OSDP, las cámaras ONVIF, los sensores MQTT — **todo dispositivo y nodo de bNexus se registra en SBOSDB como una entidad en el árbol universal de bAuth**.

No existe un fichero YAML de device fichas. No existe una base de datos propia de bNexus. El registro de dispositivos es parte del plano de identidad soberana de bAuth — los dispositivos son entidades de primer nivel en el mismo árbol donde están los usuarios, los servidores y los daemons.

---

## 2. El árbol universal de 5 niveles

```
idn_identity_entity — árbol de adyacencia (SBOSDB, schema bauth)

NIVEL 0  tenant       → raíz de aislamiento. Separa organizaciones.
NIVEL 1  bdomain      → unidad principal: empresa, edificio, datacenter, flota
NIVEL 2  bsubdomain   → división: sucursal, sala, piso, zona, deposito
NIVEL 3  pos          → punto de operación: puerta, terminal, rack, cámara, sensor
NIVEL 4  actor        → quien opera: HUMAN · SERVICE · DEVICE · BOT
```

**La jerarquía es fija. El `entity_type` es variable.** Esto permite registrar cualquier tipo de entidad — empleados, vehículos, servidores, lectores, nodos banexus — sin cambiar el DDL.

---

## 3. Tipos de entidad en bNexus

| Entidad | Nivel | `entity_type` | Función en bNexus |
|---------|-------|---------------|-------------------|
| Edificio / campus | `bdomain` | `edificio` | Contenedor geográfico |
| Datacenter | `bdomain` | `datacenter` | Contenedor de infraestructura TI |
| Planta / piso | `bsubdomain` | `piso` | División física del edificio |
| Zona de acceso | `bsubdomain` | `zona` | Área con `security_level` propio |
| Sala de servidores | `bsubdomain` | `sala` | División de TI |
| Puerta con cerradura | `pos` | `puerta` | Punto de acceso controlado |
| Cámara de vigilancia | `pos` | `camara` | Punto de captura de video (ONVIF) |
| Sensor / actuador | `pos` | `sensor` / `actuador` | Punto de captura o acción |
| Terminal / caja | `pos` | `terminal` | POS, tótem, quiosco |
| Rack / servidor | `pos` | `rack` | Infraestructura TI en posición |
| Lector OSDP / NFC / USB | `actor` | `DEVICE` | Hardware que captura credenciales |
| Nodo banexus | `actor` | `SERVICE` | Agente de frontera de bAuth |
| Nodo bhnexus | `actor` | `SERVICE` | Ruteador de comunicación física |
| Bot / pipeline | `actor` | `BOT` | Integración automatizada |
| Empleado / usuario | `actor` | `HUMAN` | Identidad humana con credenciales |

## 4. Las tres tablas del modelo de identidad

```
T-156  idn_identity_entity     ← Capa 1: QUIÉN es (árbol organizacional)
T-320  idn_user                ← Capa 2: CÓMO accede (Subscriber Account)
T-330  auth_credential         ← Capa 3: CON QUÉ se autentica
```

No todo dispositivo necesita las tres capas:

| Tipo de entidad | Necesita T-156 | Necesita T-320 | Necesita T-330 |
|----------------|:--------------:|:--------------:|:--------------:|
| Lector OSDP / sensor pasivo | ✅ | ❌ | ❌ |
| Cámara ONVIF | ✅ | ❌ | ❌ |
| Nodo banexus | ✅ | ✅ | ✅ (mTLS X.509) |
| Nodo bhnexus | ✅ | ✅ | ✅ (mTLS X.509) |
| Usuario humano | ✅ | ✅ | ✅ (múltiples métodos) |

**Regla:** un lector OSDP no necesita `idn_user` ni `auth_credential` porque bhnexus HAL lo controla directamente — el lector es un endpoint, no un sujeto autenticable. Un nodo banexus SÍ necesita las tres capas porque se autentica ante bhnexus con mTLS.

---

## 5. Tablas complementarias (postura y gobernanza)

Estas tablas añaden información de hardware y gobernanza al árbol de identidad. **No lo reemplazan** — `idn_identity_entity` siempre es la fuente de verdad de QUIÉN es la entidad.

| Tabla | Propósito | Para quién |
|-------|-----------|------------|
| `auth_device` | Postura de hardware: `trust_level`, MDM, config OSDP, `last_seen` | Dispositivos físicos con WebAuthn o OSDP |
| `auth_device_posture` | Evaluación de postura (antivirus, parches, cifrado) | Laptops y móviles corporativos bajo MDM |
| `idn_roles_nhi_identity` | Gobernanza NHI: propietario, fecha revisión, rotación de secretos | Daemons y service accounts |
| `idn_nhi_svid` | SPIFFE SVID (X.509/JWT) para mTLS | bhnexus, banexus — autenticación workload |

> **Error a evitar:** `auth_device` NO es la identidad del dispositivo — es su postura de hardware. La identidad vive en `idn_identity_entity`. Acceder a `auth_device` sin antes registrar en `idn_identity_entity` es un error de modelo.

---

## 6. Atributos de identidad — EAV

Los atributos de cada entidad se almacenan en `idn_identity_attribute` (modelo EAV — Entity-Attribute-Value). Los namespaces aplicables a entidades de bNexus:

| Namespace | Atributos típicos en bNexus |
|-----------|----------------------------|
| `core` | `fabricante`, `modelo`, `location`, `descripcion` |
| `security` | `serial`, `firmware`, `osdp_address`, `node_id`, `spiffe_id`, `trust_level` |
| `professional` | `zona_servicio`, `horario_operacion`, `responsable` |
| `contact` | `ip_address`, `mac_address`, `endpoint_url` |

## 7. Ejemplo: lector OSDP en árbol de identidad

```
SKULL (tenant)
  └── Edificio-Central (bdomain, entity_type='edificio')
        └── Planta-1 (bsubdomain, entity_type='piso')
              └── Puerta-Principal (pos, entity_type='puerta')
                    └── Lector-OSDP-001 (actor, entity_type='DEVICE')
                          │
                          ├── idn_identity_entity:
                          │     entity_id:  "uuid-lector-001"
                          │     name:       "Lector OSDP Principal"
                          │     type_level: "actor"
                          │     entity_type: "DEVICE"
                          │
                          ├── idn_identity_attribute (ns=security):
                          │     serial        = "ZK-SB1000-4F2A"
                          │     osdp_address  = "1"
                          │     firmware      = "v3.2.1"
                          │     trust_level   = "HIGH"
                          │
                          ├── idn_identity_attribute (ns=core):
                          │     fabricante = "ZKTeco"
                          │     modelo     = "SB1000"
                          │
                          ├── auth_device (postura):
                          │     device_type:  "osdp_reader"
                          │     trust_level:  "HIGH"
                          │     osdp_address: 1
                          │     protocol:     "OSDP_V2"
                          │
                          └── (NO idn_user — no se loguea como suscriptor)
                              (NO auth_credential — bhnexus HAL lo controla)
```

                          │

## 9. Protocolo de registro de un nuevo nodo banexus

El registro de un nuevo nodo banexus en SBOSDB se hace en este orden:

```
1. Crear entidad en idn_identity_entity
   (tenant_id, parent_id, name, entity_type='SERVICE')

2. Agregar atributos en idn_identity_attribute
   (node_id, spiffe_id, protocol, location)

3. Crear Subscriber Account en idn_user
   (loa_min='AAL3', method=MTLS_X509)

4. Registrar credencial en auth_credential + auth_credential_x509
   (vault_path donde Vault almacena el certificado de firma)

5. Registrar gobernanza NHI en idn_roles_nhi_identity
   (owner, review_date, rotation policy)

6. Emitir SVID via SPIRE
   (bOS provisiona el agente SPIRE en el nodo banexus)

7. Primer arranque de banexus.service
   (banexus se autentica con mTLS → bhnexus valida contra SBOSDB)
```

Para ejemplos completos de SQL INSERT → `A.04_IDENTIDADES-BNEXUS-SBOSDB.md`.

## 10. Reglas de registro

| Regla | Descripción |
|-------|-------------|
| **Una entidad por hardware** | Un lector OSDP = una fila en `idn_identity_entity`. No duplicar. |
| **El parent_id es obligatorio** | Toda entidad tiene padre en el árbol. Un lector sin Puerta es un error de modelo. |
| **Los lectores no son suscriptores** | Lectores, cámaras, sensores → sin `idn_user`. Solo `idn_identity_entity` + atributos + `auth_device`. |
| **Los nodos banexus sí son suscriptores** | banexus necesita `idn_user` + `auth_credential` para autenticarse por mTLS. |
| **entity_type es un enum** | Los valores válidos están en la tabla `idn_entity_type_catalog`. No inventar valores nuevos. |
