## QR, NFC, RFID, biométrico, smartcard, BLE, PIN — flujos y niveles de aseguramiento

## 1. Principio de agnosticismo de credencial

bNexus no privilegia ningún tipo de credencial. La elección del tipo depende del security_level de la zona, el hardware disponible, y las políticas del tenant.

Todo tipo de credencial produce el mismo resultado: un `auth_request` a bhnexus con `input_type` + `payload`. bhnexus normaliza la credencial y consulta bAuth para obtener el SAM-128. El tipo de credencial no cambia la estructura del SAM — cambia el LoA que bAuth puede garantizar.

## 3. QR Dinámico

### Flujo de generación (bAuth como emisor)

```
Core UI solicita QR → bAuth genera:
  URI: sbos://auth/{user_uuid}/{timestamp_unix}/{HMAC-SHA256}

  HMAC calculado con:
    key   = hmac_key_<user_uuid> (almacenado en Vault, rotado cada 24h)
    msg   = user_uuid + timestamp_unix
    algo  = HMAC-SHA256

  TTL: 30 segundos (configurable en RolTemplate por usuario)
  Renovación: Core UI puede solicitar un nuevo QR en cualquier momento
```

### Flujo de validación (bhnexus)

```
1. banexus captura QR via lector USB (udev+libusb)
2. banexus extrae URI: sbos://auth/{user_uuid}/{ts}/{hmac}
3. banexus envía auth_request → bhnexus
4. bhnexus valida:
   a. timestamp: now() - ts < 30s (anti-replay por TTL)
   b. Recupera hmac_key de Vault para el user_uuid
   c. Recalcula HMAC: HMAC-SHA256(key, user_uuid+ts)
   d. Compara: hmac_calculado == hmac_recibido
5. Si OK → consulta bAuth → SAM-128
```

**Ventaja:** no requiere hardware especializado — cualquier cámara USB sirve.  
**Limitación:** LoA 2 máximo. No apto para zonas sl=4.

## 4. NFC DESFire AES-128

### Flujo de captura

```
Tarjeta NFC DESFire EV2/EV3:
  Almacena: user_uuid cifrado con AES-128-CBC
  Clave:    rotada cada 90 días en Vault, distribuida por bOS a los lectores

banexus/HAL captura:
  1. Lector lee sector cifrado de la tarjeta
  2. payload = bytes cifrados (no el UUID en claro)
  3. auth_request con input_type="nfc", payload=<base64 del payload cifrado>

bhnexus descifra:
  1. Recupera AES key del reader_id desde Vault
  2. Descifra → user_uuid
  3. Consulta bAuth → SAM-128 con LoA=3
```

**Ventaja:** LoA 3 — la clave en la tarjeta nunca es legible sin el chip.  
**Limitación:** requiere lector NFC MIFARE DESFire; tarjetas legacy Mifare Classic son inseguras (clonable).

## 5. RFID 125kHz Wiegand (legacy)

### Flujo de captura

```
Tarjeta RFID legacy (EM4100, HID Prox):
  Transmite: facility_code (8 bits) + card_number (16 bits)
  Sin cifrado — transmisión en claro por radiofrecuencia

bhnexus (Wiegand driver):
  1. Recibe: 26 bits = 1 bit paridad + 8 facility + 16 card + 1 paridad
  2. Extrae facility_code + card_number
  3. Busca en tabla de mapeo: (facility, card_number) → user_uuid
  4. Consulta bAuth → SAM-128 con LoA=1

Tabla de mapeo: bauth.auth_credential (method_code='RFID_WIEGAND')
  credential_data JSONB: {"facility": 1, "card_number": 12345}
```

**Ventaja:** compatible con instalaciones legadas que ya tienen tarjetas Wiegand.  
**Limitación:** LoA 1 — las tarjetas son clonables. Solo para zonas sl=1. No recomendado para instalaciones nuevas.

## 6. Biométrico OSDP (dactilar / facial)

### Principio RGPD: el raw biométrico nunca sale del chip

```
Lector OSDP con Biometric Profile (ZKTeco, Suprema, HID Lumidigm):

1. Sensor captura imagen dactilar/facial
2. Template extraído LOCALMENTE en el chip del lector (enclave seguro)
3. Template convertido a hash PBKDF2-SHA256 LOCALMENTE
4. Hash transmitido por canal OSDP Secure Channel (AES-128 cifrado)
5. bhnexus (OSDP driver) recibe el hash cifrado
6. bhnexus → bAuth: {query_type:"biometric", hash:"<hash>"}
7. bAuth compara hash vs bauth.auth_biometric_template (hashes almacenados)
8. Match → user_uuid → SAM-128 con LoA=3

INVARIANTE:
  Raw biométrico NUNCA sale del chip del lector hacia ningún servidor.
  Solo el hash viaja — y solo cifrado por el canal OSDP Secure.
  RGPD compliant.
```

**Ventaja:** LoA 3, máximo nivel de aseguramiento físico sin hardware adicional.  
**Limitación:** requiere lector OSDP con Biometric Profile (más caro). Enrollamiento presencial obligatorio.

## 7. Smartcard X.509

### Flujo de autenticación

```
Tarjeta smartcard con chip PKI (ADSIB Bolivia, FNMT España, etc.):
  Almacena: clave privada RSA-2048 o ECDSA P-256 (no exportable del chip)
  Certificado X.509 con user_uuid en el campo Subject CN

Lector OSDP (Smart Card Profile):
  1. Envía challenge aleatorio (32 bytes) a la tarjeta
  2. Tarjeta firma el challenge con su clave privada (operación en chip)
  3. Firma + certificado enviados por OSDP Secure Channel a bhnexus

bhnexus:
  1. Verifica firma contra la clave pública del certificado
  2. Verifica certificado contra la CA de bAuth (Vault PKI)
  3. Extrae user_uuid del CN del certificado
  4. Consulta bAuth → SAM-128 con LoA=3
```

**Ventaja:** LoA 3, non-repudiación legal, compatible con ADSIB (firma digital válida en Bolivia — Ley 164).  
**Limitación:** requiere PKI y distribución de tarjetas físicas.

## 8. BLE + UWB (Aliro CSA 2023)

### Protocolo Aliro

```
App móvil (banexus-sdk iOS/Android) + lector compatible con Aliro:

1. Fase BLE: el teléfono descubre el lector (anuncio BLE)
2. Fase UWB: ranging para verificar proximidad < 1m (anti-relay attack)
3. Fase NFC/BLE: autenticación criptográfica Aliro
   - El lector envía challenge
   - El teléfono firma con la clave del dispositivo móvil (Secure Enclave iOS / StrongBox Android)
   - Respuesta enviada al lector

Lector Aliro → bhnexus:
  auth_request con input_type="ble"
  payload = "ble:<device_uuid>:<challenge_response_hex>"

bhnexus → bAuth: SAM-128 para device_uuid → user_id
```

**Ventaja:** LoA 3, sin tarjeta física, "hands-free" (no requiere sacar el teléfono). UWB previene ataques de relay.  
**Limitación:** requiere lector Aliro (más nuevo) y app móvil instalada.

## 9. PIN numérico

### Flujo

```
Teclado integrado en el lector o panel:

1. Usuario ingresa PIN (4-8 dígitos)
2. banexus/HAL recibe secuencia de teclas
3. PIN hasheado con HMAC-SHA256(pin_key, pin_digits) en el nodo
4. auth_request con input_type="pin", payload="pin:<hmac_sha256>"
   (el PIN en claro NUNCA se envía por la red)

bAuth valida:
  Busca el hash en auth_credential (method_code='PIN_HMAC')
  Match → SAM-128 con LoA=1
```

**Ventaja:** hardware muy simple, bajo costo.  
**Limitación:** LoA 1 — susceptible a shoulder surfing y reutilización. Usar solo en zonas sl=1 o como segundo factor.

## 10. Combinación de credenciales (MFA)

Para zonas sl=3 o sl=4, bAuth puede exigir múltiples factores en secuencia:

```
Zona Sala de Servidores (sl=4):
  Política: NFC + Biométrico (dos factores distintos)

Flujo:
  1. Usuario presenta tarjeta NFC → LoA=3, factor A verificado
  2. bAuth retorna: {result:"step_up_required", step_up_methods:["biometric"]}
  3. bhnexus envía auth_response con step_up_required=true a banexus
  4. Usuario presenta huella → LoA=3, factor B verificado
  5. bAuth retorna SAM-128 completo con LoA=3 confirmado por dos factores

Tiempo total: ~20-25ms (dos rondas de Puerta 2A)
```
