## 1. El problema que resuelve el Input Hooking

En un workstation Linux que tiene un lector de tarjetas NFC o un escáner QR conectado por USB, el SO lo registra como un dispositivo de entrada HID (Human Interface Device). Por defecto:

- **evdev** lo expone en `/dev/input/eventN`
- **libinput** lo reenvía al servidor gráfico (Wayland/X11)
- **Cualquier aplicación** en sesión gráfica puede leer los datos del lector

Esto significa que sin intervención, el payload de una tarjeta NFC pasaría por:
1. El kernel USB driver
2. `/dev/input/eventN` (legible por cualquier proceso del usuario)
3. El servidor gráfico
4. La aplicación que tenga foco

**El resultado**: un proceso malicioso con sesión de usuario puede leer las tarjetas presentadas por otros empleados — incluso si banexus está corriendo.

El Input Hooking resuelve esto interceptando los datos del lector **antes** de que lleguen a evdev.

## 2. Arquitectura del Input Hooking

```
Lector NFC/QR (USB)
        │
        │  USB bulk transfer (kernel driver usbhid)
        ▼
  /dev/bus/usb/<bus>/<device>    ← acceso raw al dispositivo
        │
        │  banexus abre este archivo con O_RDONLY EXCLUSIVO
        │  ANTES de que udev_monitor detecte el dispositivo como HID
        ▼
  banexus (UsbHidDriver)         ← único proceso que lee los datos
        │
        │  Los datos nunca llegan a:
        │    /dev/input/eventN (bloqueado)
        │    evdev (bloqueado)
        │    servidor gráfico (no recibe el evento)
        ▼
  EventBus → Authorization Handler → bAuth
```

## 3. Reglas udev para intercepción exclusiva

banexus instala reglas udev durante el proceso de instalación (mediante bOS provisioning):

```
# /etc/udev/rules.d/80-banexus-hid.rules
# Intercepta lectores QR y NFC conocidos antes de que evdev los use

# Honeywell Xenon 1900 (QR)
SUBSYSTEM=="usb", ATTRS{idVendor}=="0c2e", ATTRS{idProduct}=="0007", \
    GROUP="banexus", MODE="0660", ATTR{authorized}="1", \
    RUN+="/opt/banexus/bin/banexus-hook attach %k"

# ACR122U (NFC USB)
SUBSYSTEM=="usb", ATTRS{idVendor}=="072f", ATTRS{idProduct}=="2200", \
    GROUP="banexus", MODE="0660", \
    RUN+="/opt/banexus/bin/banexus-hook attach %k"

# Desautorizar el dispositivo como HID (evita registro en evdev)
# banexus lo reautorice como USB raw
SUBSYSTEM=="usb", ATTRS{idVendor}=="0c2e", ATTRS{idProduct}=="0007", \
    ATTR{authorized}="0"
```

### Efecto de `ATTR{authorized}="0"`

Cuando udev procesa el dispositivo USB con `authorized=0`:
- El kernel NO carga el driver `usbhid` para ese dispositivo
- El dispositivo NO aparece en `/dev/input/eventN`
- El dispositivo SÍ aparece en `/dev/bus/usb/<bus>/<device>` (raw USB)

banexus entonces lo abre en modo raw con `libusb`:

```rust
/// Abre el dispositivo USB en modo exclusivo usando libusb.
/// Si otro proceso ya lo abrió → error DeviceBusy → alarma SIEM.
fn open_exclusive(vid: u16, pid: u16) -> Result<DeviceHandle, DriverError> {
    let ctx = Context::new()?;
    let handle = ctx.open_device_with_vid_pid(vid, pid)
        .ok_or(DriverError::DeviceNotFound)?;

    // Reclamar la interface HID — si falla → otro proceso la tiene
    handle.claim_interface(0)
        .map_err(|_| DriverError::DeviceBusy)?;

    // Desconectar el driver del kernel si está activo
    if handle.kernel_driver_active(0)? {
        handle.detach_kernel_driver(0)?;
    }

    Ok(handle)
}
```

## 4. Monitor udev — detección de nuevos lectores

banexus monitorea eventos udev en tiempo real para detectar lectores conectados en caliente:

```rust
/// Monitor de dispositivos USB en caliente.
/// Detecta nuevos lectores QR/NFC cuando se conectan y los intercepta.
async fn watch_udev(tx: Sender<UdevEvent>) {
    let monitor = MonitorBuilder::new()?
        .match_subsystem("usb")?
        .listen()?;

    for event in monitor {
        if event.action() == Some("add") {
            let vendor  = event.attribute_value("idVendor");
            let product = event.attribute_value("idProduct");
            if is_supported_reader(vendor, product) {
                tx.send(UdevEvent::DeviceAdded(event.devnode())).await?;
            }
        }
    }
}
```

Al detectar un lector nuevo:
1. banexus verifica si el VID:PID está en su lista de lectores configurados
2. Si está → aplica `authorized=0` + abre en raw libusb
3. Si no está → log INFO + no intercepta (el SO lo maneja normalmente)

## 5. Anti-inyección de credenciales

El Input Hooking también previene **inyección de credenciales** — ataques donde un proceso malicioso intenta simular una credencial legítima.

### Vectores de inyección bloqueados

**Vector 1 — Escritura en /dev/input/eventN**:
```
Sin banexus: un proceso con acceso al grupo 'input' puede escribir eventos
             simulando una tarjeta NFC → aplicación lo trata como lectura real

Con banexus: el dispositivo nunca aparece en /dev/input/eventN
             No hay superficie de inyección vía evdev
```

**Vector 2 — Inyección de socket de banexus**:
```
banexus expone un socket Unix local para recibir eventos del hardware.
El socket está protegido: 0660, grupo 'banexus', solo procesos del mismo grupo.

Un proceso malicioso que NO está en el grupo 'banexus' no puede conectarse
al socket → no puede inyectar credenciales.
```

**Vector 3 — Replay de CredentialEvent serializado**:
```
Cada CredentialEvent tiene un event_id (Uuid v4).
El Authorization Handler mantiene un bloom filter de los últimos 10.000 event_ids
(ventana de 60 segundos).

Si el mismo event_id llega dos veces → el segundo es descartado:
  log: "credencial duplicada detectada, posible replay"
  audit_event: {type: "replay_detected", event_id: "...", node_id: "..."}
```

**Vector 4 — TOCTOU (time-of-check vs time-of-use)**:
```
El payload cifrado capturado del lector es válido por el TTL del QR (30s) o por el
TTL del SAM-128 que bAuth retorna.

banexus valida el timestamp del CredentialEvent:
  if event.timestamp.elapsed() > MAX_PROCESSING_DELAY (5s) {
      → descarta el evento: demasiado antiguo para ser confiable
  }
```

## 6. Límite del Input Hooking

El Input Hooking opera solo sobre dispositivos USB HID. Para dispositivos conectados por otros medios:

| Dispositivo | Interceptado por |
|-------------|-----------------|
| Lector NFC USB | UsbHidDriver (banexus) |
| Lector OSDP en RS-485 | OsdpDriver (bhnexus HAL Directo) |
| Sensor MQTT | MqttDriver (bhnexus) |
| Cámara ONVIF | OnvifDriver (bhnexus) |
| Lector GPIO Wiegand | WiegandDriver (bhnexus) |

El Input Hooking es un mecanismo de banexus para captura local en el workstation/POS. Para hardware en el servidor central, el equivalente es el HAL Directo de bhnexus.

## 7. Configuración completa en banexus.toml

```toml
[input_hooking]
enabled = true

# Lista de VID:PID de lectores a interceptar
[[input_hooking.readers]]
name     = "honeywell-xenon-1900"
vid      = "0c2e"
pid      = "0007"
type     = "qr"
device_id = "PHY_DEV_QR_VENTAS_01"

[[input_hooking.readers]]
name     = "acr122u-nfc"
vid      = "072f"
pid      = "2200"
type     = "nfc"
device_id = "PHY_DEV_NFC_CAJA_01"

[input_hooking.anti_replay]
bloom_filter_size = 10000   # entradas en el bloom filter
window_seconds    = 60      # ventana de dedup

[input_hooking.timing]
max_processing_delay_s = 5  # si el event tiene > 5s de antigüedad → descartado
```
