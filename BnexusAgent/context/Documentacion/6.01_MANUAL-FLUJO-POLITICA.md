# 6.01 — Flujo de Política en bNexus
## Del cambio en bAuth a la puerta que abre — propagación end-to-end

**Versión:** 1.0.0  
**Fecha:** 2026-08-04  
**Fuente:** SBOS-NEXUS-CONCEPTUALIZACION-v3_0.md §15  
**Carta rectora:** `0.00_MANUAL-DIRECTRICES-NEXUS.md`

## 1. Visión general

El flujo de política es la cadena completa que convierte un cambio administrativo en bAuth (cambio de RolTemplate, asignación de rol, revocación) en un resultado físico observable: una puerta que abre o cierra.

Este flujo tiene dos ramas principales:

- **Rama A — Cambio proactivo**: un administrador modifica una política → el cambio se propaga
- **Rama B — Solicitud reactiva**: un usuario presenta una credencial → se evalúa la política vigente

---

## 2. Rama A — Propagación de cambio de política

### 2.1 Diagrama de flujo

```
[Administrador] → bAuth: modifica RolTemplate
                          o registra nuevo usuario
                          o revoca credencial
                          o cambia asignación de rol
                          o eleva LoA requerido para zona

  bAuth (SBOSDB trigger)
    → Calcula affected_users[]
    → Calcula nuevo roltemplate_hash
    → Emite policy_sync por canal privilegiado → bhnexus

  bhnexus (canal B)
    → Invalida Auth Cache para affected_users
    → Identifica qué nodos banexus tienen sesiones de esos usuarios
    → Emite policy_update a cada nodo afectado (Puerta 1)

  banexus (Puerta 1)
    → Invalida Policy Cache local para los user_ids recibidos
    → Si el usuario está físicamente frente al lector con credencial pendiente:
        La validación ya en curso CONTINÚA (no se interrumpe mid-flight)
        La SIGUIENTE solicitud irá a bhnexus para datos frescos

  Resultado: el próximo acceso del usuario reflejará la nueva política
```

### 2.2 Tipos de cambio y su impacto

| Cambio en bAuth | Efecto en bhnexus | Efecto en banexus | Tiempo efectivo |
|----------------|------------------|------------------|:---------------:|
| Revocación de credencial | emergency_revoke via canal B | Invalida cache inmediato | < 5ms + próx. acceso |
| Cambio de RolTemplate | policy_sync via canal B | Invalida cache users afectados | < 50ms + próx. acceso |
| Nuevo usuario registrado | policy_sync (afectado = nuevo_user_id) | Cache vacío → consulta bhnexus | Primer acceso online |
| Elevación de security_level en zona | security_level_up via canal B | Actualiza zone_config en cache | < 5ms — inmediato |
| Cambio de horario | policy_sync | Cache actualizado con nuevo schedule | < 50ms + próx. acceso |

## 3. Rama B — Solicitud reactiva (credencial presentada)

### 3.1 Flujo completo de una presentación de credencial

```
T+0ms   Usuario presenta credencial al lector (NFC, QR, huella, etc.)

T+1ms   banexus (driver HAL):
         Captura el payload del hardware
         Construye auth_request:
         {
           "type":            "auth_request",
           "request_id":      "uuid-v4",
           "node_id":         "Ventas-01",
           "user_credential": {
             "input_type":  "nfc",
             "payload":     "<base64 del sector cifrado>"
           },
           "ctx_id":          "00-hex32-hex16-01",
           "timestamp":       "RFC3339"
         }
         Envía auth_request → bhnexus (Puerta 1, WebSocket mTLS)

T+3ms   bhnexus recibe auth_request:
         1. Identifica el tipo de credencial (nfc)
         2. Descifra el payload NFC → user_id
         3. Consulta Auth Cache: (user_id, "Ventas-01")
            → CACHE HIT (entry < 30s): responde inmediatamente sin consultar bAuth

T+3.5ms bhnexus (cache hit):
         Verifica que el TTL del SAM-128 en WORD-B no haya expirado
         Compone auth_response con el SAM-128 del cache + actuator_commands
         Envía auth_response → banexus

T+5ms   banexus recibe auth_response:
         Verifica la firma del response (integrado en el framing TLV)
         Extrae actuator_commands: [{target: "RELAY_01", action: "PULSE", duration_ms: 5000}]
         Ejecuta el comando al hardware: activa el relé 200ms
         Registra el evento en audit_log local con ctx_id

T+6ms   Puerta abre (acción física)

TOTAL: ~6ms puerta a puerta (con cache hit)
```

### 3.2 Flujo con cache miss (primera vez del usuario o TTL expirado)

```
T+0ms   Credencial presentada
T+1ms   banexus envía auth_request → bhnexus
T+3ms   bhnexus: CACHE MISS → debe consultar bAuth

T+3ms   bhnexus envía bitmask_request → bAuth (sub-canal A TLV):
         {
           "type":            "bitmask_request",
           "request_id":      "uuid-v4",
           "user_id":         "<uuid>",
           "node_id":         "Ventas-01",
           "domain":          "D14",
           "operation":       "access.physical.zone_ventas",
           "credential_type": "nfc",
           "ctx_id":          "00-hex32-hex16-01",
           "timestamp":       "RFC3339"
         }

T+7ms   bAuth evalúa:
         Consulta SBOSDB → rol del usuario → átomos → BitMask 64-bit
         Evalúa PolicyEngine: ¿tiene el átomo "access.physical.zone_ventas"?
         Verifica schedule: ¿es lunes-viernes 07:00-20:00?
         Verifica LoA: ¿NFC cumple el LoA requerido (2) para sl=2?
         Calcula SAM-128: WORD-A con bits de zona + WORD-B con TTL y flags
         Retorna bitmask_response con sam128 + actuator_commands

T+11ms  bhnexus recibe bitmask_response:
         Almacena entry en Auth Cache: (user_id, "Ventas-01") → {sam128, TTL 30s}
         Construye auth_response para banexus

T+13ms  banexus recibe auth_response
T+14ms  Comando al hardware
T+15ms  Puerta abre

TOTAL: ~15ms con cache miss (consulta bAuth)
```

### 3.3 Flujo con DENY

```
T+0ms   Credencial presentada
T+1ms   banexus envía auth_request → bhnexus
T+3ms   bhnexus evalúa (desde cache o bAuth)
         Resultado: DENY (usuario sin acceso a esta zona, o fuera de horario, o credencial inválida)

T+3ms   bhnexus retorna auth_response:
         {
           "status":       "denied",
           "deny_reason":  "insufficient_privilege",
           "deny_message": "El usuario no tiene acceso a esta zona.",
           "actuator_commands": []   // ninguna acción de actuador
         }

T+5ms   banexus recibe auth_response:
         No ejecuta ningún comando de actuador
         Opcionalmente: activa LED rojo en el lector (si el hardware lo soporta)
         Registra el DENY en audit_log

TOTAL: ~5ms puerta a puerta (con cache hit, resultado DENY)
Puerta: no abre
```

## 4. Flujo de step-up (MFA físico en dos pasos)

Para zonas sl=3 o sl=4 que requieren dos factores:

```
T+0ms   Usuario presenta NFC
T+15ms  bAuth evalúa → LoA insuficiente para sl=3 → retorna step_up_required
         {
           "status":           "step_up_required",
           "step_up_methods":  ["biometric"],
           "step_up_timeout":  30
         }

T+15ms  bhnexus envía auth_response con step_up_required=true a banexus
T+17ms  banexus activa: LED azul parpadeante en el lector (indicador de espera de segundo factor)
         Muestra mensaje en el panel: "Coloque su huella dactilar"

T+Xs    Usuario coloca huella (dentro de los 30s de timeout)
T+X+1ms banexus captura el hash biométrico, envía NUEVO auth_request:
         {
           "step_up":     true,
           "session_id":  "<uuid del primer factor>",   // correlación
           "credential":  { "input_type": "biometric", "payload": "<hash>" }
         }

T+X+3ms bhnexus: conoce el session_id → ya tiene el factor A verificado
T+X+7ms bAuth evalúa el factor B (biométrico): LoA=3 con dos factores
         → GRANT con SAM-128 completo para sl=3
T+X+15ms Puerta abre

Si el timeout de 30s se agota sin el segundo factor:
  → bhnexus emite DENY con deny_reason: "step_up_timeout"
  → banexus: LED rojo, "Tiempo agotado"
```

## 5. Invariantes del flujo de política

```
INV-01: ctx_id presente en TODOS los mensajes del flujo.
         El mismo ctx_id viaja desde el auth_request original hasta el audit_event final.
         Sin ctx_id → audit_event invalido → RECHAZO por el validador de auditoría.

INV-02: actuator_commands provienen EXCLUSIVAMENTE de bAuth.
         bhnexus NO inventa comandos de actuador.
         banexus ejecuta SOLAMENTE los comandos recibidos de bhnexus.
         Si bhnexus no envía actuator_commands → banexus no activa ningún hardware.

INV-03: El resultado (GRANT/DENY) proviene EXCLUSIVAMENTE de bAuth.
         Ni bhnexus ni banexus toman decisiones de autorización propias.
         Son "policy enforcement points" — aplican lo que bAuth decide.

INV-04: El roltemplate_hash en el SAM-128 identifica la versión de política usada.
         Si el hash cambia entre dos accesos del mismo usuario, bhnexus actualiza el cache.

INV-05: El TTL del cache (30s en bhnexus, 4h en banexus) es el límite de "frescura" de la política.
         Un cambio en bAuth se hace efectivo en el próximo acceso después del TTL, en el peor caso.
         La revocación de emergencia (canal B) es la excepción: invalida inmediatamente.
```
