## 1. Propósito y diseño fundamental

El Auth Cache de bhnexus es el componente de rendimiento más crítico del sistema de acceso físico. Su rol: **eliminar la latencia de consulta a bAuth para usuarios recurrentes**.

Sin el Auth Cache:
- Cada acceso de tarjeta o QR requiere una consulta a bAuth (sub-canal A, < 10ms)
- En un acceso masivo al inicio de jornada laboral (todos los empleados en < 5 min), bAuth recibiría miles de consultas simultáneas

Con el Auth Cache:
- La primera consulta de un usuario en un nodo va a bAuth (< 10ms)
- Las consultas subsiguientes en los próximos 30s son O(1) en memoria (< 0.1ms)

## 2. Estructura de datos

### 2.1 Clave de cache

```
Clave: (user_id: Uuid, node_id: String)

Por qué la clave incluye node_id:
  El SAM-128 de un usuario varía por nodo (zona física).
  Un empleado puede tener acceso a la zona de ventas (node-01) pero no a la sala
  de servidores (node-02). El cache es por combinación usuario × nodo.
```

### 2.2 Valor de cache: CacheEntry

```rust
/// Entrada del Auth Cache para un par (user_id, node_id)
struct CacheEntry {
    /// SAM-128: WORD-A (privilegios físicos) + WORD-B (contexto/TTL/flags)
    sam128: Sam128,

    /// Comandos de actuador precomputados para la acción de acceso estándar
    actuator_commands: Vec<ActuatorCommand>,

    /// Timestamp de creación de la entrada (UTC)
    created_at: Instant,

    /// TTL de la entrada en segundos (normalmente 30, configurable por zona)
    ttl_seconds: u32,

    /// Hash del RolTemplate usado para calcular el SAM-128
    /// Permite detectar si la política cambió sin invalidar por TTL
    roltemplate_hash: u32,
}
```

### 2.3 Sam128

```rust
/// Estructura SAM-128: autorización en 128 bits
struct Sam128 {
    word_a: u64,  // WORD-A: 64 bits de privilegios físicos
    word_b: u64,  // WORD-B: 64 bits de contexto, TTL y flags
}
```

Ver `1.05_MANUAL-SAM128.md` y `anexos/A.06_SAM128-MAPA-BITS.md` para el mapa de bits completo.

## 4. Implementación del Auth Cache

### 4.1 Estructura Rust

```rust
use std::collections::HashMap;
use std::time::Instant;

/// Auth Cache de bhnexus — acceso O(1) a SAM-128 por (user_id, node_id)
struct AuthCache {
    /// Mapa principal: (user_id, node_id) → CacheEntry
    entries: HashMap<(Uuid, String), CacheEntry>,

    /// Orden de acceso para LRU (más antiguo al frente)
    lru_order: VecDeque<(Uuid, String)>,

    /// Capacidad máxima
    capacity: usize,

    /// Contadores de diagnóstico
    hits: u64,
    misses: u64,
    evictions: u64,
}
```

### 4.2 Consulta (camino crítico)

```rust
/// Consulta el cache. O(1). Sin I/O. Sin locks de escritura en el camino feliz.
fn get(&self, user_id: Uuid, node_id: &str) -> Option<&CacheEntry> {
    let key = (user_id, node_id.to_string());
    match self.entries.get(&key) {
        None => {
            self.misses.fetch_add(1, Ordering::Relaxed);
            None
        }
        Some(entry) if entry.created_at.elapsed().as_secs() > entry.ttl_seconds as u64 => {
            // Entrada expirada — tratar como miss (borrado lazy al próximo write)
            self.misses.fetch_add(1, Ordering::Relaxed);
            None
        }
        Some(entry) => {
            self.hits.fetch_add(1, Ordering::Relaxed);
            Some(entry)
        }
    }
}
```

### 4.3 Escritura con evicción LRU

```rust
/// Inserta o actualiza una entrada. Si el cache está lleno, evicta el LRU.
fn insert(&mut self, user_id: Uuid, node_id: String, entry: CacheEntry) {
    let key = (user_id, node_id);
    if self.entries.len() >= self.capacity && !self.entries.contains_key(&key) {
        // Evictar el más antiguo (LRU)
        if let Some(lru_key) = self.lru_order.pop_front() {
            self.entries.remove(&lru_key);
            self.evictions += 1;
        }
    }
    self.entries.insert(key.clone(), entry);
    // Mover al final (más reciente) en el orden LRU
    self.lru_order.retain(|k| k != &key);
    self.lru_order.push_back(key);
}
```

## 5. Mecanismos de invalidación

El cache se invalida por cuatro vías distintas, ordenadas de mayor a menor urgencia:

### 5.1 Invalidación de emergencia (canal B)

```
Trigger:  bAuth emite emergency_revoke (credencial comprometida, lockout forzado)
Acción:   bhnexus elimina TODAS las entradas de cache del user_id
          en TODOS los nodos
Tiempo:   < 5ms (canal B ya establecido)
```

### 5.2 Invalidación por cambio de política (canal B)

```
Trigger:  bAuth emite policy_sync con action=invalidate_cache
Acción:   bhnexus elimina las entradas de cache de los affected_users
Tiempo:   < 5ms por usuario
```

### 5.3 Invalidación por TTL (lazy)

```
Trigger:  La entrada lleva más de ttl_seconds desde su creación
Acción:   En la siguiente consulta de ese usuario, se detecta TTL expirado
          → cache MISS → se consulta bAuth → entry actualizada
Tiempo:   Automático — sin proceso activo
```

### 5.4 Invalidación por roltemplate_hash

```
Trigger:  bhnexus recibe un bitmask_response con un roltemplate_hash diferente
          al almacenado en la entrada de cache existente
Acción:   bhnexus reemplaza la entrada con el nuevo SAM-128
          (aunque el TTL no haya expirado)
Tiempo:   < 1ms — ocurre inline durante el procesamiento del response
```

## 6. Hit rate y dimensionamiento

### Hit rate esperado

```
Escenario: 200 empleados, jornada laboral 8h, cada empleado accede 10 veces/día

Accesos totales: 2.000
Accesos en < 30s del acceso anterior del mismo usuario en el mismo nodo: < 5%
→ Hit rate realista: ~95% en entornos con tráfico constante

Accesos en hora pico (entrada 8:00-8:30am):
  200 empleados × 1 acceso = 200 auth_request en 30 minutos
  → 6-7 por minuto → NO hay presión de cache
  → Cada empleado entra UNA vez → 0% cache hits en entrada masiva
  → Sin cache: 200 consultas a bAuth → < 10ms cada una → bAuth lo maneja sin problema
```

### Dimensionamiento de 10.000 entradas

```
Máximo teórico:
  10.000 usuarios × 1 nodo = 10.000 entradas
  10.000 usuarios × 5 nodos = 50.000 combinaciones posibles

En la práctica:
  Un empleado con acceso a 3 nodos: 3 entradas en el cache
  10.000 / 3 = ~3.333 usuarios únicos cubiertos simultáneamente
  → Suficiente para instalaciones enterprise de hasta 2.000-3.000 empleados
  → Si se necesita más: aumentar capacity en config.toml
```
