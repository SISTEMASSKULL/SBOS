## 1. Mandato de bNexus

**bNexus es el motor de comunicación física de bAuth.**

bAuth decide. bNexus ejecuta. Esa es la relación completa.

bNexus traduce la autoridad de identidad soberana de bAuth en eventos físicos observables: una puerta que abre, un cajón que se libera, un lector que acepta una credencial, un acceso remoto que se concede. Sin bNexus, bAuth no tiene presencia en el mundo físico. Sin bAuth, bNexus no tiene autoridad para actuar.

bNexus no toma decisiones de identidad. No evalúa políticas. No emite tokens. Recibe decisiones de bAuth y las materializa en el hardware.

## 2. Las tres capas — identidad de cada una

```
┌─────────────────────────────────────────────────┐
│  bAuth                                           │
│  Decide — Motor PDP, fuente de verdad soberana  │
│  "¿Puede este sujeto hacer esto?"               │
└────────────────────┬────────────────────────────┘
                     │
                     │  Puerta 2 (Unix socket TLV + canal privilegiado)
                     │
┌────────────────────▼────────────────────────────┐
│  bhnexus                                         │
│  Ruta — Broker de acceso físico, Auth Cache     │
│  "¿Quién conectó? ¿Está en cache? ¿A dónde va?" │
└────────────────────┬────────────────────────────┘
                     │
                     │  Puerta 1 (WebSocket mTLS, SPIFFE)
                     │
┌────────────────────▼────────────────────────────┐
│  banexus  (cinco formas)                         │
│  Actúa — Agente de borde, interceptor físico    │
│  "Capturé una credencial. Ejecuto el comando."  │
└─────────────────────────────────────────────────┘
```

Las tres capas son **tres daemons distintos** — tres binarios independientes, tres servicios systemd, tres ciclos de vida. Su relación es de dependencia, no de fusión.

## 3. Los tres principios rectores

### 3.1 Frontera soberana

bNexus es la membrana entre el mundo físico y el plano de identidad de bAuth. Nada entra ni sale de esa membrana sin pasar por la autoridad de bAuth.

Un lector OSDP, una cámara ONVIF, un torniquete, una cerradura WiFi: ninguno habla directamente con bAuth. bhnexus los abstrae mediante su HAL. banexus los traduce a credenciales verificables.

La soberanía física es una extensión de la soberanía digital de bAuth. Comprometerla equivale a comprometer la identidad.

### 3.2 Fidelidad de bAuth

bNexus no improvisa. Cuando bAuth dice GRANTED con `actuator_commands`, bNexus ejecuta exactamente esos comandos y no otros. Cuando bAuth dice DENIED, bNexus niega — sin excepciones, sin lógica local alternativa.

Las únicas excepciones documentadas son de resiliencia (§3.3): cache offline TTL 4h y fail-secure si no hay cache. Ambas están acotadas, auditadas, y no constituyen decisiones propias de bNexus.

### 3.3 Resiliencia de borde

bNexus opera en entornos físicamente impredecibles: caídas de red, hardware defectuoso, sitios remotos sin conexión estable. La resiliencia no es una funcionalidad opcional — es un requisito de seguridad física.

Los mecanismos de resiliencia son:

| Mecanismo | Capa | Cobertura | Límite |
|-----------|------|-----------|--------|
| Auth Cache in-memory (TTL 30s) | bhnexus | Cache hit < 1ms sin consultar bAuth | Invalida en 30s o por `invalidate_cache` |
| Policy Cache cifrado (TTL 4h) | banexus | Operación offline total hasta 4h | Invalida al reconectar; AES-256-GCM |
| Fail-secure | banexus | Si no hay cache + no hay conexión → DENY | Sin excepción; primer arranque siempre online |
| Canal privilegiado push | bAuth → bhnexus | Revocación de emergencia < 5ms | Socket dedicado `/run/bos/bauth-nexus.sock` |
| Backoff exponencial | banexus | Reconexión ordenada sin tormenta de reconexiones | 1→5→15→30→60s |

## 4. Las dos puertas

**Puerta 1** — banexus ↔ bhnexus

El canal de campo. Transporta credenciales capturadas del mundo físico hacia el broker, y comandos de actuador en sentido inverso. WebSocket sobre mTLS. Protocolo: SPIFFE/SVID. Latencia objetivo: < 50ms extremo a extremo.

**Puerta 2** — bhnexus ↔ bAuth

El canal de autoridad. Dos sub-canales:
- **Request/response** (Unix socket TLV): bhnexus consulta SAM-128 a bAuth en cache miss.
- **Canal privilegiado** (bauth-nexus.sock): bAuth empuja revocaciones de emergencia, sincronización de políticas, alertas de seguridad. bhnexus reporta eventos de hardware críticos.

Estos dos canales no son visibles para las aplicaciones cliente. Las aplicaciones se conectan directamente a bAuth mediante el **Motor de Comunicación (banexus-implicit)** — no pasan por bhnexus.

> **Referencia:** `BauthAgent/context/Documentacion/2.18_MANUAL-MOTOR-COMUNICACION-v1.0.md`  
> Protocolo universal agnóstico de framework: WS+JSON-RPC 2.0 · mTLS · JWT/OIDC · W3C Trace Context.  
> Implementaciones en TypeScript/React/Vue, PHP/Laravel, Dart/Flutter, Rust M2M, Python/Django.

## 5. Las cinco formas de banexus

banexus siempre existe en alguna forma en cada escenario de autenticación no-software. La forma depende del contexto de despliegue:

| Forma | Cuándo | Resumen |
|-------|--------|---------|
| **banexus-implicit** | Cualquier app de software | mTLS + JWT + OTEL — sin binario propietario |
| **banexus-daemon** | PC/workstation con hardware físico adjunto | Binario Rust MUSL, systemd --user |
| **banexus-gateway** | Hardware en sitio remoto | Mismo binario, `mode = gateway` en SBC/Pi |
| **banexus-sdk** | App móvil con acceso físico | Librería Aliro CSA 2023 — BLE+UWB+NFC |
| **banexus-virtual** | Dispositivo con firmware HTTP/REST | El dispositivo se auto-actúa — sin binario |

El HAL Directo de bhnexus es el único caso sin ninguna forma de banexus: hardware mudo en el mismo edificio que bhnexus, conectado por cable o LAN.

## 6. Criterios editoriales del corpus

Todo manual del corpus bNexus se evalúa contra estos criterios:

### 6.1 Criterio de frontera clara

Cada manual declara explícitamente su capa (bAuth / bhnexus / banexus), su puerta (Puerta 1 / Puerta 2 / HAL / ninguna), y su forma de banexus si aplica. Sin frontera clara, el manual está incompleto.

### 6.2 Criterio de latencia nombrada

Todo protocolo, cache, o flujo documenta su latencia objetivo. bNexus opera en el plano físico donde los milisegundos determinan la experiencia de acceso. La latencia no es un detalle de implementación — es un requisito de calidad.

| Plano | Latencia objetivo |
|-------|-----------------|
| Puerta 1 (banexus → bhnexus → bAuth → actuador) | < 50ms total |
| Puerta 2 request/response (bhnexus → bAuth) | < 10ms |
| Canal privilegiado (bAuth → bhnexus) | < 5ms |
| Cache hit bhnexus (sin consultar bAuth) | < 1ms |
| Cache hit banexus (offline) | < 0.5ms |

### 6.3 Criterio de trazabilidad

Todo evento físico debe poder reconstruirse completo con: `ctx_id` (W3C traceparent), `node_id` (banexus que capturó), `device_id` (hardware que generó la credencial), `user_id` (JWT.sub si aplica), `ts` (timestamp del servidor, autoritativo). Los manuales documentan en qué campos se propaga cada dato.

### 6.4 Criterio de fail-secure visible

Todo manual que describe un flujo con riesgo de interrupción documenta explícitamente el comportamiento en falla: qué ocurre si bhnexus no responde, si banexus pierde conexión, si el hardware no reacciona. El silencio sobre la falla es un error editorial.

### 6.5 Criterio de evidencia AA-1

Toda afirmación verificable (latencia, tamaño de estructura, número de entradas de cache, TTL) incluye la fuente: código Rust verificado, DDL real, o medición reproducible. Sin evidencia, la afirmación es un estimado — debe marcarse como tal.

### 6.6 Criterio de no-decisión propia

Ningún manual de bNexus describe lógica de evaluación de identidad, políticas de acceso, o emisión de tokens. Eso es dominio de bAuth. Si un flujo necesita una decisión de identidad, el manual referencia a bAuth y al manual correspondiente del corpus bAuth.

## 7. Glosario mínimo

| Término | Definición en contexto bNexus |
|---------|-------------------------------|
| **bhnexus** | Rust daemon, broker físico central. Gestiona conexiones de banexus, Auth Cache, HAL, Puerta 2 |
| **banexus** | Agente de borde en una de sus cinco formas. Captura credenciales, ejecuta actuadores |
| **HAL** | Hardware Abstraction Layer de bhnexus — 6 drivers: OSDP, MQTT, ONVIF, Wiegand, USB HID, HTTP |
| **SAM-128** | Estructura 128-bit de autorización en bhnexus Auth Cache: 64-bit bitmask + 64-bit contexto físico |
| **Puerta 1** | Canal WebSocket mTLS banexus ↔ bhnexus |
| **Puerta 2** | Canal Unix socket TLV + canal privilegiado bhnexus ↔ bAuth |
| **Canal privilegiado** | Sub-canal push bidireccional `/run/bos/bauth-nexus.sock` — revocación de emergencia, policy sync |
| **SPIFFE/SVID** | Identidad de workload para mTLS entre banexus y bhnexus — `spiffe://sbos.skull/agent/banexus/<node_id>` |
| **Credencial** | QR, NFC, RFID, biométrico, smartcard, BLE, PIN — toda señal que banexus captura e identifica |
| **Actuador** | Elemento físico que bNexus controla tras GRANTED: relé, chapa, cajón, barrera |
| **Fail-secure** | Si no hay cache válida + no hay conexión → DENY. No hay acceso no autorizado por defecto |
| **node_id** | Identificador único de un nodo banexus registrado en SBOSDB (`idn_identity_entity`) |
