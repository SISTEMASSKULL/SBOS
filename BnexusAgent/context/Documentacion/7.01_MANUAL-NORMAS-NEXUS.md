## 2. OSDP v2.2.2 — SIA / IEC 60839-11-5

### 2.1 Descripción

OSDP (Open Supervised Device Protocol) es el protocolo industrial estándar para comunicación entre paneles de control de acceso (ACU) y dispositivos periféricos (PD) como lectores, teclados y biométricos. La versión 2.2.2, estandarizada como SIA OSDP v2.2.2 e IEC 60839-11-5, añade el **Secure Channel (SC)** con AES-128.

bhnexus actúa como **ACU (Access Control Unit) master** en el bus RS-485. Cada lector OSDP conectado es un **PD (Peripheral Device)** subordinado.

### 2.2 Requisitos de implementación en bNexus

| Requisito OSDP | Implementación bhnexus | Estado |
|---------------|------------------------|:------:|
| Secure Channel AES-128 obligatorio (v2.2.2) | `OsdpDriver` establece SC antes de cualquier comando | ✅ |
| Polling cada 200ms (modo nativo) | `OsdpDriver` thread de polling en bhnexus | ✅ |
| Supervisión de dispositivo (tamper) | `tamper` bit en `osdp_status_report` → `device_tamper` event | ✅ |
| Biometric Profile (BIO) | Extrae hash sin almacenar template | ✅ |
| Smart Card Profile | Challenge-response X.509 APDU | ✅ |
| Múltiples PD en bus RS-485 | Direcciones OSDP 0-126 configurables | ✅ |

### 2.3 Mensajes OSDP usados por bNexus

| Comando/Respuesta | Dirección | Uso |
|-------------------|:---------:|-----|
| `osdpCmd_POLL` | ACU→PD | Polling de estado cada 200ms |
| `osdpCmd_ID` | ACU→PD | Identificación del PD durante init |
| `osdpCmd_CAP` | ACU→PD | Capacidades del PD (biométrico, NFC, SC) |
| `osdpCmd_OUT` | ACU→PD | Activar relé o cerradura |
| `osdpCmd_LEDER` | ACU→PD | Control de LED del lector |
| `osdpCmd_BUZZ` | ACU→PD | Control de buzzer |
| `osdpCmd_TEXT` | ACU→PD | Texto en display |
| `osdpReply_KEYPAD` | PD→ACU | PIN introducido en teclado (cifrado SC) |
| `osdpReply_RAW` | PD→ACU | Datos de tarjeta crudos |
| `osdpReply_FMT` | PD→ACU | Datos de tarjeta formateados (NFC sector) |
| `osdpReply_BIO` | PD→ACU | Hash biométrico (Biometric Profile) |
| `osdpReply_MFGREP` | PD→ACU | Tamper + status de dispositivo |

### 2.4 Limitación de Wiegand

Wiegand **no es un estándar formal** — es un protocolo de facto sin cifrado, sin autenticación del dispositivo y sin anti-replay. Su uso en bNexus está marcado `⚠️ INSECURE` en la documentación del driver. Se soporta exclusivamente para compatibilidad con hardware legacy mientras el cliente migra a OSDP.

## 3. MQTT 5.0 — OASIS MQTT 5.0

### 3.1 Descripción

MQTT 5.0 (OASIS MQTT Version 5.0, 2019) es el protocolo de mensajería estándar para IoT. bNexus lo usa para:
- Recibir eventos de sensores IoT (movimiento, temperatura, humedad) que disparan lógica de seguridad
- Publicar comandos a actuadores MQTT (cerraduras IP, barreras, alarmas)
- Integrar con hardware que no soporta OSDP pero sí MQTT

### 3.2 Perfil de uso en bNexus

| Parámetro | Valor |
|-----------|-------|
| Versión | MQTT 5.0 |
| Transporte | `mqtts://` (TLS 1.3 + cert mTLS) |
| QoS | QoS 1 (entrega al menos una vez) |
| Retain | false (eventos instantáneos) |
| Keep-alive | 60s |
| Session expiry | 300s (permite reconexión sin pérdida) |

### 3.3 Nuevas características MQTT 5.0 usadas

- **Message Expiry Interval**: descarta eventos de sensor con más de 10s de antigüedad
- **Correlation Data**: vincula publicación con respuesta del actuador (mismo ctx_id)
- **User Properties**: propaga `ctx_id` y `node_id` en propiedades del mensaje
- **Shared Subscriptions**: múltiples instancias de bhnexus consumen el mismo topic (HA)

## 4. ONVIF — Profile S / Profile T / Profile C

### 4.1 Descripción

ONVIF (Open Network Video Interface Forum) define perfiles de interoperabilidad para cámaras y sistemas de control de acceso IP.

| Profile | Función | Uso en bNexus |
|---------|---------|---------------|
| Profile S | Video streaming (RTSP) | Streaming hacia bOS dashboard |
| Profile T | Video avanzado (H.264/H.265, análisis) | Face hash en ONVIF events |
| Profile C | Control de acceso IP | Puerta de acceso controlada vía ONVIF |

### 4.2 Restricción RGPD en ONVIF Profile T

bhnexus **nunca almacena imágenes ni frames de vídeo**. El `OnvifDriver` extrae solo el `face_hash` del evento de análisis de la cámara. La imagen raw no sale de la cámara. Esto cumple:
- RGPD Art. 9 (datos biométricos como categoría especial)
- ISO 27001 A.8.11 (borrado de información)

### 4.3 Modos de operación del OnvifDriver

- **Pull**: bhnexus consulta a la cámara cada 500ms vía `GetEventMessages`
- **Push**: la cámara suscribe a bhnexus y empuja eventos cuando ocurren (preferido por eficiencia)

## 5. Aliro CSA 2023 — BLE + UWB + NFC

### 5.1 Descripción

**Aliro** (Connectivity Standards Alliance, 2023) es el estándar abierto para credenciales de acceso físico en dispositivos móviles. Sucede al protocolo propietario de Apple/Google para llaves de hogar y auto digitales. Usa:
- **BLE** para detección de proximidad (rango ~5m)
- **UWB** para ranging de alta precisión (±10cm, anti-relay)
- **NFC** como respaldo en campo cercano

### 5.2 Implementación en bNexus

Aliro se implementa en **banexus-sdk** (iOS/Android) con el chip del Secure Enclave del smartphone:

| Componente | Responsabilidad |
|-----------|----------------|
| banexus-sdk | Protocolo Aliro en el lado móvil |
| Lector Aliro (hardware) | Bridge BLE/UWB → bhnexus |
| bhnexus BleToken handler | Recibe `device_uuid + response` y consulta a bAuth |
| bAuth | Resuelve `device_uuid` → `user_uuid` + SAM-128 |

### 5.3 Anti-relay UWB

El ranging UWB verifica que el smartphone está a **menos de 1 metro** del lector. Si la distancia es mayor → aborta. Esto previene ataques de relay donde alguien toma la señal BLE a distancia y la retransmite al lector.

## 6. SPIFFE — Identidad de cargas de trabajo

### 6.1 Descripción

SPIFFE (Secure Production Identity Framework for Everyone) v1.0 define una forma estándar de asignar identidades criptográficas a procesos y servicios (cargas de trabajo). La identidad se expresa como un SPIFFE ID en formato URI y se materializa en un SVID (SPIFFE Verifiable Identity Document) basado en X.509.

### 6.2 IDs SPIFFE en bNexus

| Proceso | SPIFFE ID |
|---------|-----------|
| bhnexus | `spiffe://sbos.skull/daemon/bhnexus` |
| banexus (por nodo) | `spiffe://sbos.skull/agent/banexus/<node_id>` |

### 6.3 Uso en mTLS (Puerta 1)

Cuando banexus se conecta a bhnexus via WebSocket TLS:
1. banexus presenta su certificado X.509 con el SPIFFE ID en la extensión SAN
2. bhnexus verifica que el SPIFFE ID corresponde al patrón `spiffe://sbos.skull/agent/banexus/*`
3. Extrae `node_id` del SPIFFE ID → verifica que el nodo existe en `idn_identity_entity`
4. Autoriza la conexión si el nodo está registrado y activo

## 7. NIST SP 800-207 — Arquitectura Zero Trust

### 7.1 Principios aplicados en bNexus

bNexus implementa el modelo Zero Trust según NIST SP 800-207:

| Principio ZT | Implementación bNexus |
|-------------|----------------------|
| **Nunca confiar, siempre verificar** | Toda credencial se valida en bAuth. Cache máximo 30s, no indefinido |
| **Asumir compromiso** | Integrity Monitor banexus, auto-shutdown en tamper |
| **Mínimo privilegio** | SAM-128 es el privilegio exacto requerido — no más |
| **Microsegmentación** | Cada zona física tiene bits dedicados en SAM-128 WORD-A |
| **Visibilidad completa** | ctx_id en toda operación, Prometheus + Wazuh + audit trail |

### 7.2 PEP/PDP en bNexus

Según el modelo de referencia NIST SP 800-207:
- **PEP (Policy Enforcement Point)**: bhnexus — aplica la decisión de acceso (abre/cierra el actuador)
- **PDP (Policy Decision Point)**: bAuth — evalúa identidad, roles, condiciones y emite SAM-128
- **PAP (Policy Administration Point)**: bOS — define políticas via `idn_roles_template`
- **PIP (Policy Information Point)**: SBOSDB — provee atributos de identidad a bAuth

## 8. ISO 27001:2022 — Seguridad física (A.7)

### 8.1 Controles A.7 implementados

| Control ISO 27001 A.7 | Implementación en bNexus |
|-----------------------|--------------------------|
| A.7.1 — Perímetros físicos | SAM-128 zonas definen perímetros con bits independientes |
| A.7.2 — Controles de entrada física | Cada acceso requiere credencial válida evaluada por bAuth |
| A.7.3 — Seguridad de oficinas | Átomos específicos por tipo de espacio (oficina, CPD, sala técnica) |
| A.7.4 — Supervisión física | OnvifDriver: face hash events + audit trail con ctx_id |
| A.7.5 — Protección de instalaciones | Fail-secure en toda zona crítica (software DENY si cache expirado) |
| A.7.6 — Trabajo en zonas seguras | step-up MFA para sl=4 |
| A.7.7 — Escritorio y pantalla limpios | Fuera del alcance de bNexus |
| A.7.9 — Protección de activos | Integrity Monitor protege el binario banexus |
| A.7.11 — Equipamiento de apoyo | UPS detectado vía MQTT; corte de luz → blackout_event |
| A.7.14 — Descarte y reutilización | Fuera del alcance de bNexus |

### 8.2 Controles A.8 relevantes

| Control ISO 27001 A.8 | Implementación en bNexus |
|-----------------------|--------------------------|
| A.8.15 — Registro de actividades | Audit trail completo: cada auth_request con ctx_id, timestamp, resultado |
| A.8.16 — Monitoreo | Prometheus 6 métricas + Wazuh 7 alertas |
| A.8.28 — Codificación segura | Rust con análisis estático, sin `unsafe` en drivers críticos |
